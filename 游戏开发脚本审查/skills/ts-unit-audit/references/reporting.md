# 报告规则

骨架见 `assets/report-template.md`（复制后填充）。本文件只写规则。

## 三件套门槛（缺一不可）

一条问题要成立，必须同时给出：

| 要素 | 不合格 | 合格 |
|---|---|---|
| 位置 | 「在 FOV 里」 | `fov/FOV.ts:458-471` |
| 证据 | 「理论上会死循环」 | `radius=Infinity 时 -Infinity+1 仍为 -Infinity` |
| 后果 | 「可能有问题」 | 「配表产生无穷半径后主线程卡死」 |

- **没有实测证据的，标注「未实测（静态分析）」**，不得伪装成已验证
- 「应该」「可能」「似乎」一律不成立
- 说不出后果的问题不成立 —— 通常意味着它不是真问题，或没想清楚

## 必写章节

1. **结论** —— 等级计数表 + 是否阻断发布
2. **问题** —— 按 `B<批>-<序号> <等级> — <一句话>` 逐条展开
3. **逐单元结论** —— 表格，让调用方一眼看到哪些单元要处理
4. **验证过没问题的部分** —— 必写
5. **架构裁决**（若有）
6. **附：复现脚本位置**

### 逐单元结论的取值

| 结论 | 含义 |
|---|---|
| **阻断发布** | 有 P0 |
| **需修** | 有 P1 |
| **需发布加固** | 默认值安全类问题 |
| **未发现新增 P0/P1** | 干净 |

## 「验证过没问题的部分」为什么必写

很多历史坑**已经被修好了**。逐个实测确认并列出：

- 避免后续重复报已修问题
- 告诉读者「这些地方可以放心用」
- 揭示该单元的维护质量

写法：

```markdown
| 检查项 | 实测 |
|---|---|
| 免疫判定在取整之前 | ✅ stage 给 0.02 → 补到 1，不误判免疫 |
| 护甲用除法不用减法 | ✅ `v * (100/(100+armor))` |
```

## 记录审查工具自身的教训

若探针/扫描器出过错（误报、设计错误），写进报告。这些和被测代码的缺陷一样有价值。

```markdown
> 第一版探针得出「repeat(times=3) 只执行 1 次」的错误结论，差点误报成致命 bug。
> 实际是 dt 被 clamp 了。**审查工具和被测代码一样需要验证。**
```

## 语言风格

- 用「静默」「不报错」「无日志」点出**无感知失效**——这是定级依据
- 后果从**用户视角**描述：「血条消失」比「hp 被写入 NaN」更有说服力
- 每条缺陷的第一句能独立看懂（会被单独摘出来引用）
- 不用「可能存在」「建议关注」这类模糊表述

## 等级标记

除 P0/P1/P2 外，按需使用：

| 标记 | 用途 |
|---|---|
| **regression** | 修复 A 时引入 B。修复复核场景的核心关切，必须标注 |
| **praise** | 实现得当、值得保留。结构化地写进「验证过没问题的部分」 |
| **pre-existing** | 本次未改动但发现的老问题。与新增问题分开计数 |

## 全库总报告（119 单元这种规模）

| 章节 | 内容 |
|---|---|
| 结论 | 是否建议发布；最优先的阻断项清单 |
| 覆盖与验证 | 单元覆盖数、源文件数、测试通过数、各扫描项状态 |
| 分批结果 | 每批的单元数 / P0 / P1 / P2 / 主要风险 / 报告链接 |
| 建议修复顺序 | 分阶段 |
| 仓库治理问题 | 文档与实际不符处、脚本退出码、台账宣称已修但未修项 |
| 交付文件 | 各报告与复现脚本链接 |

**建议修复顺序的分阶段范式**：

1. **安全与资产正确性** —— 原型污染、经济漏洞、数据损坏
2. **统一边界守卫** —— 新增共享守卫并应用到所有同类入口
3. **修复地基与回归测试** —— 先修地基，再把复现脚本转为正式测试
4. **发布与架构治理** —— 默认值加固、平行实现退役、补齐交付物

## 进度文件

| # | 单元 | 状态 | P0 | P1 | P2 |
|---|---|---|---|---|---|

状态：未开始 / 已出报告（待批准）/ 已修复 / 复核通过。

## 命名

- 报告：`精审_<单元名>.md` 或 `batch<N>_review.md`
- 复现脚本：`audit/repro_findings.js`
- 探针：`audit/probe_<单元名>.ts`
- 进度：`审查框架与排期.md`
- 扫描基线：`扫描结果_全量.txt` / `扫描结果_P0.txt`
