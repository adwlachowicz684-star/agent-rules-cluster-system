# 审查工作流（六步完整展开）

## 第 1 步 · 摸清现状

**目的**：避免把别人已做过的事再做一遍。

先看是否已有历史审核报告（用户可能提供，或仓库里有 `审查记录.md` / `review/` 等）。若有：

1. 提取每个被审过的单元名与缺陷计数，统计**哪些单元完全没有覆盖** → 未覆盖的才是新工作量
2. 按 P0/P1 计数排序 → 决定复核顺序
3. 检查报告里的目录名与当前源码目录名是否一致（常见别名差异：连字符、时态、缩写，
   如 `auto-quality` vs `autoquality`）→ 建立别名映射，避免重复审
4. 记录总缺陷数，作为后续「修了多少」的基线

**产出**：一张表，列出「已覆盖单元 + 计数」「未覆盖单元」「别名映射」。

**关键提醒**：
- 扫描器对**已修过的单元**会报残留项而非原问题。复核前先确认该单元是否修过。
- **台账宣称「已修」不等于真修了**。实测复现一遍再关闭；关闭时须绑定修复 commit
  与回归测试，不能只更新审查文字。

## 第 2 步 · 全库模式扫描

```bash
python3 scripts/pattern-scan.py --src=<根>            # 全量
python3 scripts/pattern-scan.py --src=<根> --p0       # 只看致命
python3 scripts/pattern-scan.py --src=<根> --json     # 结构化
python3 scripts/pattern-scan.py --self-test           # 先确认模式本身没失效
```

输出三部分：模式命中排行 → 按模式分组的明细（模块 / 文件 / 行号 / 片段）→ 合计数。

**怎么处理结果**：

- **先处理计数少的模式**（空 if 块、fail-open、参数未使用、路径污染、默认启用等）。
  命中少但几乎条条是真问题。
- **计数多的模式**（`??` 未收口、返回内部引用、循环边界未收口，常达数百）
  抽样确认后按族批量修，不要逐条写报告。
- 保存输出为索引文件，后续所有工作引用它。

## 第 3 步 · 依赖与交付物扫描

**依赖合规**（仅当目标是「每个单元可独立拷走」）：

```bash
python3 scripts/dep-scan.py --src=<根> --infra=<基础设施目录,逗号分隔>
```

基础设施目录 = 允许被所有模块依赖的共享层（如 `_core` / `ds` / `utils`）。
输出：横向依赖违规、`type-only` 标记、基础设施反向依赖、零依赖模块清单。

**交付物完整性**：

```bash
python3 scripts/doc-scan.py --src=<根>                  # 默认：被任何示例引用即算有
python3 scripts/doc-scan.py --src=<根> --strict         # 要求专属示例文件
python3 scripts/doc-scan.py --src=<根> --missing-only   # 只列缺失
```

**先确认该仓库的示例组织约定**再选模式：

- 约定「每单元一个专属示例」→ `--strict`
- 约定「批量综合示例」（如 `batch15-usage.ts` import 十几个模块）→ 默认模式

两种模式下缺失清单会差很多倍（实测：1 个 vs 117 个），判据错了会得出无意义结论。

## 第 4 步 · 验证候选（独立步骤，不可跳过）

> **这一步是六步里最容易被跳过、也最不该跳过的。**

扫描器产出的是候选，不是结论。它本质是**形状匹配**——能告诉你"这里有这个形状"，
但不知道这是不是问题。实测 118 个模块扫出 2352 处候选，直接倒给用户等于没做审查。

**为什么独立成步**（借鉴 Anthropic 官方 Code Review 的架构）：

```
多 agent 并行分析  →  verification step 对照实际行为过滤误报  →  去重  →  按严重度排序
                      ^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^
                      这是独立的专门环节，不是顺带做的
```

**对每条候选**：

1. 打开 `文件:行号`，**先读上方注释**
2. 问三个问题：
   - 这个变量/参数**可能**取到非法值吗？（来自配置、用户输入、前序运算 → 是）
   - 取到非法值后**会报错吗**？（不报错 = 静默失效，严重度更高）
   - 能恢复吗？（不可逆 → 严重度更高）
3. 按 `pattern-detection.md` 的降级表判断是否为误报
4. 存疑的写探针实测，不靠推理下结论

**产出对比**：

| 阶段 | 数量级 | 性质 |
|---|---|---|
| 扫描后 | 2352 | 候选，含大量误报 |
| **验证后** | **数十至数百** | **真问题清单** |
| 精审+实测后 | 个位数至数十 | 确认缺陷，可分级入报告 |

**最高频的误报来源**：没读注释。大量"看起来像 bug"的写法上方都有长注释解释原因
（如"这里不能用 while 递减，必须取模"）。所以第 1 条操作是"先读注释"。

## 第 5 步 · 人工精审 + 探针实测

读 `references/manual-review.md`，7 项清单逐项过：

1. 单元特有算法的正确性
2. 数值语义的方向
3. 文档与代码的三处对照
4. 时间单位一致性
5. 形状与坐标语义
6. 依赖合规
7. destroy 幂等与生命周期

读 `references/global-consistency.md`，做跨单元比对（扫描器完全覆盖不到）：

- 坐标系口径（Y 轴方向、矩形 min/max 语义）
- 边界包含语义（`<` vs `<=`）
- 时间单位
- 平行实现及其分工说明
- **地基优先**：先确认 `_core` / `ds` / `utils` 的正确性，再回归上层

**探针**：

```bash
cp scripts/probe-template.ts audit/probe_<单元>.ts
npx tsc --outDir build --module commonjs --target ES2019 \
        --skipLibCheck --lib ES2019,DOM audit/probe_<单元>.ts
node build/audit/probe_<单元>.js
```

必测九类对抗性输入，速查卡见 `assets/adversarial-inputs-card.md`，
详解见 `references/adversarial-inputs.md`。

**关键认知**：测试全绿 ≠ 可发布。某库 3,451 项测试全通过，人工精审仍发现 39 个 P0，
原因就是现有用例只覆盖正常路径。

**探针自身的三个陷阱**（都会导致误报）：

| 陷阱 | 表现 | 规避 |
|---|---|---|
| 被测单元内部 clamp 了 dt | 「跑了 60 帧」实际只推进很少时间 | 打印累计时间核对，或增大帧数 |
| 注册顺序影响回调顺序 | 想测「A 取消 B」，结果 B 先执行 | 显式控制注册顺序，先打印执行序列 |
| 状态串扰 / 原型污染残留 | 上一组影响下一组 | 每组 `{}` 独立作用域；污染类 probe 测完 `delete Object.prototype.xxx` |

**第一版探针的结论必须能复现**，否则先修探针再下判断。

## 第 6 步 · 分级、报告、修复、补测

**定级**：读 `references/severity.md`（三级定义 + 附加标记 + 5 条升级规则 + 驳回清单）。

**写报告**：骨架取 `assets/report-template.md`，规则见 `references/reporting.md`。

**修复**：按族取 `references/fix-code-core.md`（A–H）、`fix-code-data.md`（I–O）
或 `fix-code-advanced.md`（P–W）。

**补测**：每个缺陷补一条能复现它的测试。命名写清期望：

```typescript
// 好：失败时一眼看出期望
test('repeat(NaN) 应拒绝注册，而非每帧执行', () => {
  const s = new Scheduler();
  let n = 0;
  s.repeat(NaN, () => n++);
  for (let i = 0; i < 5; i++) s.update(0.1);
  eq(n, 0, 'NaN 间隔不得执行');
});

// 坏：失败时不知道哪里错
test('scheduler repeat', () => { ... assert(n); });
```

**修复前先确认力度**：默认「先报不改」，等用户批准。若已授权直接改，区分：

- 保签名修内部（不动对外 API，已有调用点不用改）—— 默认推荐
- 破坏性重构（签名、命名一起改到最优）—— 需用户明确同意

## 批量推进顺序

1. 全库扫描，拿到候选索引
2. **未覆盖单元优先精审**（这些是真新工作）
3. **地基单元次之**（`_core` / `ds` / `utils` / `pool` / `rng` 之类），
   缺陷会传染所有依赖它的上层
4. 有 P0 的单元做修复复核，标注 regression
5. 空 if 块、fail-open、路径污染这类「少而准」的模式逐个确认
6. 剩余按模式族批量修
7. 全局议题单独裁决（不混在单元报告里）

## 进度维护

维护一个进度文件，状态：未开始 / 已出报告（待批准）/ 已修复 / 复核通过。

| 单元 | 状态 | P0 | P1 | P2 |
|---|---|---|---|---|

另维护一张**全局议题表**（坐标系、边界语义、平行实现、容量口径等），
这些不归属单个单元，需统一裁决。

执行清单见 `assets/review-checklist.md`，可逐单元打勾。
