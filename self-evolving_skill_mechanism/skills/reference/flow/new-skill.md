# 从零建设一个新 skill

> **本区性质：flow / 端到端流程。**
> 从零建一个能力包；往已有库加条目请走 `consolidation.md`（`FL-01`）。

> **流程 ID**：`FL-03`（**分配后不改**）
> **前置**：无
> **本步交付**：一个能被引擎检索到、且首次任务就能命中的新 skill
> **对应**：做法 `howto/writing-rules.md` · `howto/layers.md` · 审核 `audit/anti-patterns.md`

> ⓘ **本流程与 `FL-01`（整合）的区别**：
> `FL-01` 是**往已有库里加条目**（增量）；本流程是**建一个全新的能力包**（从零）。
> 两者判定不同——见下方「第 0 问」。

ⓘ 七节顺序**固定**。

---

## 0. 交付物定义

跑完本流程，应该能**直接指认**：

1. 一个**目录骨架**（`SKILL.md` + `rules/` + `reference/` + `scripts/`）
2. **`index.py --find <关键词>` 能找到它**
3. 首次真实任务**能命中**，且命中后照做就能产出

⚠ 第 2 条指认不出来 = 白建。
**建了但检索不到，是最常见的"建了个寂寞"**——文件都在，只是没人找得到。

---

## 第 0 问：该建新 skill，还是往已有 skill 加条目？

⛔ **先回答这个，再动手。** 判错方向的代价是返工整包。

| 判据 | 建新 skill | 往已有 skill 加 |
|---|---|---|
| **覆盖面** | 一个**完整能力域**（能独立解决一类任务） | 该域下的**一条做法 / 一个坑** |
| **独立性** | 单独拿出来能用 | 脱离原 skill 就没上下文 |
| **检索词** | 有**自己的一套关键词**，不与已有包重叠 | 关键词属于某个已有包 |
| **体量预期** | 预期 ≥20 条条目 / 多份文档 | 只是几条 |
| **归属** | 属于某个大类下的**一个能力** | 属于某个能力的**一个细节** |

**判定顺序**：
1. 先用 `index.py --find <关键词>` 查——**查不到 ≠ 没有**（见 [EC-01](../common/blocks.md#ec-01-查不到--没有)，原第十八条：先证明"查了"且"查法对"，用原子词再查一次）
2. 查到了 → **往已有 skill 加**，走 `FL-01`
3. 确认真没有 → 建新 skill，走本流程

⚠ **查不到就建新的，是 skill 爆炸的主因**——同一个能力在库里变成两个包，
之后每次命中都命中到不同的那个，永远修不干净。

⛔ **反向也要防**：明明是一个完整能力域，却拆成十几条塞进 `_common`，
结果是**没人知道有这套能力**（它散落在几十条里，检索命中率极低）。
判据：**这东西单独拿出来能用吗？** 能 → 它是 skill，不是条目。

## 2. 工序

### Step 1　定边界　`[FL-03#S1]`

【读】`howto/layers.md#划分判据（拿不准时用）`

【做】写下三行，写进开发记录：

```text
做什么：<一句话>
不做什么：⛔ <至少两条，明确排除>
验收标准：<可观测，不是"能用">
```

【产出】一段边界声明（落盘，不是脑子里）

【判据】能把这三行念给另一个人听，对方能复述出同样的范围

【审】⛔ **先读 howto 会被它的完整内容带着走，做出需求外的东西**

### Step 2　定大类归属　`[FL-03#S2]`

【读】`howto/domain-routing.md`

【做】`python3 scripts/domain.py --route "<这个 skill 的描述>"`

【产出】目标大类（如 `dev` / `game` / `tooling`）；装不下则走 `structure-evolution.md` 建新大类

【判据】`--route` 输出命中该类且**不是靠泛词**；⛔ 归错类比不归更糟

【审】`howto/structure-evolution.md#装不下`

### Step 3　定契约（目录骨架）　`[FL-03#S3]`

【读】`howto/writing-rules.md#领域包写法（与条目型库不同）`

【做】建骨架：

```
<skill-name>/
├── SKILL.md          # 入口，≤200 行，常驻
├── rules/            # 领域硬约束（每次任务都读）
├── reference/        # 按需加载的五区（howto/audit/flow/common/craft）
├── scripts/          # 多行逻辑封成命令
└── assets/           # 模板 / 变更溯源
```

【产出】目录骨架 + `SKILL.md` 的目录地图

【判据】**只看 `SKILL.md` 就知道去哪找什么**（核心原则 ③：细节写全、按需加载）

【审】`audit/anti-patterns.md`（先过反模式，别把已知坑再写一遍）

### Step 4　填内容　`[FL-03#S4]`

【读】`howto/writing-rules.md#第一问：这条写进 reference/ 的哪个区？`

【做】按五区归类填写，**每条带三件套**（来源 / 证据 / 后果）

- 写 `howto/` 时读 `howto/`，写 `audit/` 时读 `audit/`——⛔ **不要同时打开两册**

【产出】条目 + 每条的三件套

【判据】每条说得出「不这么做会怎样」；说不出 = 通常不是真技能 → 驳回

【审】`audit/rejection.md`（6 条驳回清单）

### Step 5　注册索引　`[FL-03#S5]`

【读】`howto/loading.md#重建索引`

【做】`python3 scripts/index.py`

【产出】更新后的索引（新 skill 进入可检索状态）

【判据】`index.py --find <关键词>` **能找到这个新 skill**

【审】⛔ **本步最容易被跳过**——跳过后文件都在，但**定向加载找不到**，
表现为"我明明建了却检索不到"。**这是静默失效，不报错。**

### Step 6　首次命中验证　`[FL-03#S6]`

【读】`howto/loading.md#冷热分层的诊断`

【做】拿一个真实任务跑一遍：模拟检索 → 命中 → 照做 → 看能否产出

【产出】命中记录 + 照做的结果

【判据】**检索能命中，且命中后照做就能产出**；命中不了 → keywords 太窄，补同义词

【审】`howto/consolidation-place.md#冷热分层的诊断：0 命中到底是哪种`

### Step 7　留痕　`[FL-03#S7]`

【读】`howto/consolidation-gate.md#入库三件套（缺一不可）`

【做】`python3 scripts/note.py "<ID>" 新增 "<原因>" --src <来源>`，写 changelog

【产出】变更溯源记录

【判据】半年后看到这条，能答出「它怎么来的、为什么这么写」

【审】`audit/anti-patterns.md`

## 3. 参考实现

一次完整新建的最小命令序列：

```bash
# 0. 先确认该不该建（查不到 ≠ 没有，用原子词再查）
python3 scripts/index.py --find <原子词1> --find <原子词2>

# 2. 定大类
python3 scripts/domain.py --route "<描述>"

# 3-4. 建骨架 + 填内容（手工）

# 5. 注册索引（⛔ 不可省）
python3 scripts/index.py

# 6. 验证能被检索到
python3 scripts/index.py --find <关键词>
```

ⓘ **批量填充**（手上有大批量现成素材时）见下方专节。

## 4. 验收清单

- [ ] 「第 0 问」答过了（不是查不到就建）
- [ ] 大类归属是 `--route` 验证过的，不是靠泛词命中
- [ ] `SKILL.md` ≤200 行，且**只看它就知道去哪找什么**
- [ ] 每条有三件套；说不出后果的已驳回
- [ ] ⚠ `index.py --find` **能找到**（第 5 步）
- [ ] ⚠ 拿真实任务跑过，**能命中且照做就能产出**（第 6 步）
- [ ] changelog 有记录

⛔ 不能"文件都建好了"就过。

## 5. 常见返工

⚠ **跳过第 5 步注册索引** —— 文件全在，但**定向加载找不到**。
**静默失效**：不报错、不为空，只有下次检索才发现"我明明建了"。

⚠ **查不到就建新的** —— skill 爆炸的主因。
同一个能力变两个包，之后每次命中命中的是不同的那个。

⚠ **该建 skill 却拆成条目塞进 `_common`** ——
结果是没人知道有这套能力（散落在几十条里，检索命中率极低）。

⚠ **两册同时打开写** —— 建设时想着"别犯错"会写得又短又空。
判据：写完的条目是"要做什么"还是"什么情况下不成立"？混了就是两册串了。

⚠ **先读素材再定边界** —— 会被素材内容带着走，做出需求外的东西。
**⛔ 先定「做什么 / 不做什么」，再读素材。**

⚠ **只验证"能检索到"，不验证"照做能产出"** ——
检索命中 ≠ 内容可用。命中了但照做做不出来，等于建了个空壳。

## 批量填充（手上有大批现成素材时）

ⓘ 当素材不是"一条条经验"，而是**一整批现成文档 / 规范库**时，
Step 4 不能用"逐条写三件套"的方式做——量太大，且**素材本身已有结构**。

**判据：素材是「散点经验」还是「已有结构的成批内容」？**
后者走下面的批量路径。

### 批量四步（替换工序第 4 步）

```
B1 盘点  → 素材分几类？每类大概多少条？先分类，不逐条读
B2 定映射 → 每类素材 → 落哪个区？（howto/audit/flow/common/craft）
B3 灌入  → 按映射批量落位，保留素材原有结构
B4 抽条目 → 从灌入的内容里抽「索引条目」，
            每条带三件套，让检索能命中具体内容
```

⚠ **B2 定映射必须在灌入之前做**。
先灌再分类 = 所有内容堆在一个区里，之后要重新分——**比一开始就分好贵十倍**。

⚠ **B4 不能省**。灌进去的成批文档如果不抽索引条目，
**检索命中率会极低**（`index.py` 靠关键词找，长文档只有很少的关键词）。
判据：**拿真实任务查，能命中到具体小节吗？** 只能命中到文件 = B4 没做。

### 批量特有的两个坑

| 坑 | 后果 | 防法 |
|---|---|---|
| **同源重复** | 素材里同一件事写了多遍，灌进去变多条 | 灌入前先按**语义**去重，不看字面 |
| **素材过期** | 素材是某个版本的，与当前实现不一致 | 灌入时标来源版本；与实现冲突的**标冲突不覆盖** |

⛔ **批量灌入最容易犯的错**：把素材当"已经验证过的正确内容"全盘接收。
**素材是输入，不是结论**——它与现有实现冲突时，标冲突，不静默覆盖。
