# 骨架兜底与全局层

> **本区性质：flow / 端到端流程。**
> 与上篇 `step-spec.md`（Step 怎么写）配对：
> **那篇讲有细化流程时怎么写，本篇讲没有细化流程时怎么办。**

---

## 一、来源

与上篇同源（game-dev 的 Godot 流程体系）。
那边 **11 个已细化域、110 个域靠骨架兜底**——
这个比例本身就是结论：**细化永远是少数，兜底才是常态。**

## 二、骨架兜底原则

> **⛔ 不允许"没有流程就凭记忆开工"。**

现实中不可能给每种情况都写细化流程。做法是：

1. 写一个**通用骨架**（六步：定边界 → 定契约 → 最小闭环 →
   接外部 → 异常边界 → 验收）
2. 细化流程只写给高频域，其余**一律套骨架**
3. ⚠ **细化后的流程应能映射回骨架六步**——**映射不上的骨架步 = 该域的盲区**

第 3 条是关键：映射不上时，要么补，要么**显式说明"这是有意的"**，
⛔ 不是悄悄漏掉。

> 例：角色控制域没有独立的"定契约"步——因为它的契约就是参数表，
> 被并进了总览和验收。可接受，但**要知道它是有意的**。

### 骨架六步的顺序不能乱

⚠ **最小闭环必须在异常边界之前。**
反过来（先写异常处理）会陷入"异常写了一半、主干还没验证"的泥潭——
**而且此时出错你无法定位是主干的问题还是异常处理的问题。**

⚠ **第 0 步之前还有一步：先定「做什么」。**
流程是从需求派生的，不是固定的——同一个域，
"做个伤害结算"和"做一套连招系统"是两条不同流程。
**⛔ 先读做法文档会被它的完整内容带着走，做出需求外的东西。**

✅ 正确顺序：先写「做什么 / ⛔不做什么 / 验收标准」→ 再逐步执行。

## 三、"不做什么"至少两条

```text
做什么：<一句话>
不做什么：⛔ <至少两条，明确排除>
验收标准：<可观测，不是"能跑">
```

**边界不清就开工，做出来的是另一个东西**——
而且等到做完才发现时，返工量比写这两行大几个数量级。

判据：**能把这三行念给另一个人听，对方能复述出同样的范围吗？**

## 四、接缝清单

流程之间对接时，逐个列出接缝：

| 接缝 | 上游产出 | 我这边期望 | 是否一致 |
|---|---|---|---|
| | | | |

⚠ **不一致的接缝要显式处理**（单独立一步适配），
**⛔ 不要在各处偷偷转格式**——那些转换会散落多处，以后改接口时找不到。

判据：**接缝清单里每一行都标注了"一致"或"已适配"。**

## 五、参数回填

⚠ **实测参数必须回填，⛔ 不留示例值。**

```
⛔ @export var accel := 2000.0      # 示例值，一直没实测
✅ @export var accel := 1850.0      # 实测：从 0 到最高速 0.31s
```

判据：**能说出这个值是怎么测出来的。**
留着示例值的参数在真机上一定会出问题，而且出问题后没人怀疑它
（"文档里就是这么写的"）。

## 六、锚点 ID 稳定

节点 ID（`[域/文件#S3]`）、通用块 ID（`GC-xx`）一旦分配**不要改**。

⚠ **ID 一改，进度就断了**——流程工具按它记录"哪个节点做完了"，
引用它的所有文件也全变成死链。

## 七、多对多全局层

⚠ 通用内容**不要每个流程各写一遍**——改一处要改几十处，且必然漂移。

做法：写进 `common/`，分配**稳定锚点 ID**，各流程引用。

```
【读】common/howto/principles.md#GC-01
```

**索引表要能双向查**：
- 正向：这块被哪些流程引用（改这块时知道要回归哪些）
- 反向：这个流程要用哪些块（做这个流程时知道先读什么）

⚠ **单向登记不算索引**——只记"块→流程"就查不到"流程→块"。

## 八、多个流程怎么组合（大任务）

ⓘ 这是最容易想错的部分。"做一个完整系统"横跨多个流程——
**不是把几个流程排个序就完事**。

### 8.1 为什么"排序"不够

真正的难点不是顺序，是**接缝**：

```text
流程 A 产出：能跳的角色 + 手感参数表
流程 B 依赖：受击方能播放受击、能进硬直
                ↑
        这个"能进硬直"是 A 产出的吗？不一定——
        两边对"硬直归谁管"没有约定
```

⚠ **A 做完的产出，B 接不上**，因为接口没约定。
这才是跨流程返工的主要来源，**不是顺序排错**。

### 8.2 产物契约（可指认的产出物）

每个流程必须声明**能指到具体符号/文件/信号**的产出物：

```text
✅ HitResolver.resolve(ctx) -> HitResponse ＋ hit_resolved 信号
⛔ 完成了伤害结算
```

理由：下游要**按名字对接**，上游改接口时下游能立刻发现。

### 8.3 组合的三种关系

| 关系 | 含义 | 处理 |
|---|---|---|
| **依赖** | B 需要 A 的产出物 | 拓扑排序，A 先做 |
| **接缝** | A 的产出与 B 的期望格式不一致 | 加**接线流程**（glue） |
| **共享** | 多个流程都要改同一个东西 | ⛔ **危险信号**，见 8.4 |

⚠ **接缝最容易被忽略**。判断方法：把两边的产出物/依赖并排写，
**对不上（命名不同、单位不同、时序不同）就是接缝**，需要显式处理。

⛔ **不要在流程内偷偷适配对方的格式**（"反正我这边转一下就行"）——
这个适配会**散落多处，以后改接口时找不到**。
✅ 单独立一个接线流程，它有名字、有验收、以后能被找到。

### 8.4 共享是危险信号

多个流程都要改同一个文件 / 类 / 配表 → ⚠ **这是耦合，不是复用**。

处理（按优先级）：
1. 抽成独立流程，明确归属某一个
2. 明确 owner，其他流程**提需求不改代码**
3. ⛔ 最坏情况：各流程各改各的 → 冲突 + 静默覆盖
