# 排障索引：按症状，不按注意事项

> **本区性质：flow / 元规则。**
> 验收怎么写见 [`acceptance.md`](acceptance.md)；
> 多个流程先后见 [`sequence.md`](sequence.md)。

---

## 一、为什么单独一层

流程文件是**正向**的：先做什么、再做什么。
但人遇到问题时手里有的是**症状**，不是流程。

```
正向：  Step 1 → Step 2 → Step 3
反向：  「远端玩家来回抽搐」→ 为什么？→ 回去改哪一步？
```

⛔ **只有正向流程，出问题的人要把它从头读一遍才知道错在哪**。
而 97 个功能点里 **60 个**都带了一张反向表——这不是偶然。

---

## 二、三列表：症状 / 原因 / 回到

实测统计：game-dev 的 97 个功能点文件中，**60 个**的
「常见返工」节用的是这个形态：

| 症状 | 原因 | 回到 |
|---|---|---|
| 位置同步越来越滞后 | 高频数据走了 reliable | S2 |
| 客户端调 RPC 没反应也不报错 | 默认 authority | S2 |
| `await` 后 sender 变 0 | 没存局部变量 | S4 |
| 导 Web 后连不上 | 用了 ENet | S5 |
| 大包丢一片全废 | 按 32MB 设计 | S6 |
| 断线后实体残留 | 没接 `peer_disconnected` | S1 |

### 三列各自的作用（缺一列就废一半）

| 列 | 作用 | 缺了会怎样 |
|---|---|---|
| **症状** | 让人**认出**是自己这个 | 拿着原因去对号入座，对不上 |
| **原因** | 让人**理解**为什么 | 只知道"要改 S2"，不知道改什么 |
| **回到** | 让人知道**回去改哪一步** | 知道原因但不知道改哪儿 |

⚠ **「回到」这一列最常被省**，而它恰恰是排障最需要的一列——
排障的终点是"去改某个地方"，不是"知道了原因"。

---

## 三、⛔ 索引必须按「手里有什么」建

**核心判据**：

> **出问题的人手里有的是症状，不是注意事项清单。**

所以表要按**症状**索引。反例：

```
⛔ 「要注意 RPC 的 authority 设置」     ← 注意事项形态
   → 出问题时我想不起来"我这是 authority 的问题"
```

```
✅ 「客户端调 RPC 没反应也不报错 → 默认 authority → 回 S2」
   → 我看到"没反应也不报错"，直接命中
```

⚠ **注意事项只能防，不能查**。
它假设读者已经知道问题出在哪一类——而**不知道才要来查**。

ⓘ 与 `../craft/substance.md` 第五节同源：
体积上限是成本、不是充实度——**同理，注意事项是预防、不是排障**。

---

## 四、症状必须写「可观测的现象」，不写结论

```
⛔ 「同步策略有问题」        —— 这是结论，不是症状
✅ 「位置同步越来越滞后」    —— 可观测
⛔ 「队列设计不当」
✅ 「服务端卡住后客户端卡死」
```

判据：**能不能照着这句话去比对"我是不是这样"？**
写结论的话，读者得先自己诊断出结论才能用这张表——**循环依赖**。

⛔ 还有一个隐蔽的坑：症状要写**反直觉的**那些。

```
✅ 「客户端调 RPC 没反应**也不报错**」
                          ↑ 没报错才是关键
```

**报错了反而是好事**——不报错的失败才难查。
只写"报错类"症状，等于把所有静默失效排除在外，
而静默失效正是 `../audit/self-verification-silent.md` 讲的最高危一类。

### ⛔ 症状最容易漏写的一类：它「容易被误判成什么」

实测（对象池缺状态重置的表现）：

> ⚠ **周期性卡顿**（⛔ 不是持续低帧，是一阵一阵的）
> —— 这个特征**很容易误判成"渲染问题"**。

⚠ 只写症状本身还不够：
**同一个现象，人第一反应会归因到错误的方向**，
于是去查一个根本没问题的地方。

| 只写症状 | 加上「易误判为」 | 差别 |
|---|---|---|
| 「周期性卡顿」 | 「周期性卡顿（**易误判为渲染问题**）」 | 后者直接排掉一个错误方向 |

判据：**这个症状最常被误判成什么？** 写不出来 = 还没真正诊断过它。

ⓘ 与 [`../flow/acceptance.md`](acceptance.md) 第五节同源：
验收要分档（理想/一般/恶劣）——
**同一个"看起来正常"的现象，在不同档位下有完全不同的归因**。

---

## 五、同一症状可能有多个原因：分开列，不合并

实测：netsync 的「纠正 → 再错 → 再纠正」在 03 和 04 里
**各出现一次**，原因都是「重放用了帧 delta」，但**回到不同的步**。

⛔ **不要因为原因相同就合并成一行**——
它出现在两个不同阶段，回到的是两个不同的地方。

**判据：这两行会被同一个人在同一次排障里用到吗？**
不会 → 分开列（各自带上自己那步的上下文）。

---

## 六、⛔ 排障表会过期：改了流程就要回头改表

「回到 S2」是**指向流程里的位置**。
流程一改（加一步、删一步、换顺序），**所有"回到"全错**。

⚠ 这是最难发现的一类失效：
流程改了、表没改，**表看起来还是完整的**——
每一行的症状和原因都对，只有"回到"那一列是错的。
而错了之后，人被指到一个**无关的步**上去改。

判据：**改流程之后，「回到」列是不是逐行核过？**

ⓘ 与 [EC-01](../common/blocks.md#ec-01-查不到--没有)（查不到 ≠ 没有）是同一族：
**表在、内容对、指向错**——最难发现的失效形态。

⛔ 无法自动验证：没有工具知道"S2 现在还是不是那一步"。
所以**改流程时必须人工核这一列**，这是流程维护的一部分。

## 七、自检（30 秒）

- [ ] 表是按**症状**索引的，还是按注意事项罗列的？
- [ ] 三列齐全吗？（症状 / 原因 / **回到**——最后一列最常省）
- [ ] 症状写的是**可观测现象**，不是结论？
- [ ] 有没有覆盖**不报错的**失败（静默类）？
- [ ] 同一症状在不同阶段出现时**分开列**了吗？
- [ ] 改流程之后，**「回到」列逐行核过吗**？
