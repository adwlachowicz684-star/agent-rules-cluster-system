# 验收怎么写：环境、档位、基准、假完成

> **本区性质：flow / 元规则。**
> 多个流程的先后见 [`sequence.md`](sequence.md)；
> 单流程内部每步的写法见 [`step-spec.md`](step-spec.md)。

---

## 一、为什么单独一层

`step-spec.md` 说了「【判据】必须可观测」，但**可观测 ≠ 有效**：

```
✗ 「保存成功，文件存在」        —— 可观测，但没测断电
✗ 「联机跑通了」                —— 可观测，但局域网延迟 <5ms
✗ 「成就列表能显示」            —— 可观测，但四类结构没分
```

三条都**满足"可观测"**，三条都是**假验收**。

**判据的可观测性是必要条件，不是充分条件。**

---

## 二、验收环境必须匹配该事的真实失败环境

反面案例（原文）：

> ⚠ **本域是所有域里最"本地测不出来"的一个。**
> 局域网延迟 <5ms、丢包 0%，**所有抖动问题都被隐藏**。

**"单机跑一切正常、上线才炸"** —— 失败只在真实环境出现，
而验收跑在舒适环境里，于是**验收永远绿、问题永远在验收之后**。

**判据：这个东西最可能在哪儿坏？验收在那儿做了吗？**

| 事 | 舒适环境（无效） | 真实失败环境（该在这测） |
|---|---|---|
| 网络同步 | 局域网 <5ms | 150ms 延迟 + 5% 丢包 |
| 存档 | 正常保存 | **写入 50% 时强杀进程** |
| 成就 | 列表能显示 | 累计型"击杀 100"有没有地方放 |
| 角色手感 | 开发者自己玩 | 未参与开发的人玩 |

⛔ **验收跑在舒适环境，等于没验收**——它证明的是
「在不会出问题的条件下不会出问题」。

---

## 三、分档验收，恶劣档必须可用

不要只定一个"通过/不通过"，要**分档**：

| 档位 | 延迟 | 丢包 | 要求 |
|---|---|---|---|
| 理想 | 20ms | 0% | 基准 |
| 一般 | 80ms | 2% | 本地无等待感 |
| ⚠ **恶劣** | 150ms | 5% | **本档必须可用** |

> ⚠ **只测"理想"档等于没测。** 150ms+ 是跨区联机的真实情况。

**判据：最差那一档的要求写了吗？** 没写 → 验收只覆盖了最好的情况。

⚠ 分档不是为了好看：它让「退化」可判定。
只测理想档时，从 20ms 退化到 100ms **看不出来**——因为根本没测过。

## 四、⛔ 假完成：验收清单能打勾 ≠ 真的做对了

**这是本节最硬的一条。**

实例（原文）：

> ⚠ **本步最容易"看起来做完了"：成就列表能显示就行。**
>
> ⛔ **常见假完成**：把成就当成一个 `Array` 加几个字符串常量，
> ⚠ 界面确实能列出成就，
> ⛔ 但四类成就（一次性/累计/条件/复合）共用一套结构，
> 到做"击杀 100"时才发现**进度无处放**，
> 而此时 id 已经散落在代码各处。

三步拆开看：

```
① 验收清单打勾       ✓（界面能列成就）
② 这一步真的做对了？ ✗（四类结构没分）
③ 什么时候暴露？     做下一步才发现 → 那时 id 已散落各处
```

⚠ **假完成的代价不在"没做对"，而在"发现得太晚"**——
等到下一步才暴露，错误已经扩散，改起来比重做贵。

### 判据（两条，缺一就可能是假完成）

| # | 判据 |
|---|---|
| 1 | **能不能当场演示？**（⛔ 只说"做了"不算） |
| 2 | **下一步能不能基于它继续？**（⛔ 下一步撞墙 = 这步是假的） |

第 2 条更狠：**假完成只有走到下一步才现形。**
所以 `sequence.md` 第三节「一个做完才进下一个」不只是纪律，
它同时也是**假完成的探测器**——跳着做会让探测器失效。

### 写法：每个功能点开头就写「假完成长什么样」

```markdown
⚠ 本步最容易"看起来做完了"：<一句话>
⛔ 常见假完成：<具体形态>
```

⛔ 不写这两行，验收清单再详细也可能全是假完成——
**因为没人知道"看起来做完了"长什么样。**

### ⛔ 验收假完成的方法：主动破坏你假设成立的前提

实测（VIP 域的到期判据）：

> ⛔ 常见假完成：写了 `Time.get_unix_time_from_system()` 当到期判据，
> 在**自己没改系统时间的情况下一切正常**——于是认为"到期逻辑没问题"。
>
> 做完这一步，应该能**当场演示**：
> 1. 把设备时间改到一年后，**权益不变**
> 2. 把设备时间改到一年前，**权益不变**
> 3. 时间转换失败时**不会静默落到 1970**

⚠ **假完成之所以能通过验收，是因为验收发生在"前提成立"的环境里**——
而你从没检查过那个前提是不是真的成立。

⇒ **判据（第三条，也是最实用的一条）**：

> **我假设成立的那个前提，能不能主动把它破坏掉？**
> 破坏之后还正确 → 真的做对了。

| 假设 | 怎么破坏它 |
|---|---|
| "系统时间可信" | 把设备时间改到一年后 |
| "翻译已加载" | 不预先加载就切语言 |
| "网络正常" | 断网 / 注入 500ms 延迟 |
| "这次不会失败" | 人为让提交失败 |

ⓘ 与第一节（验收环境必须匹配真实失败环境）的分工：
那条讲**环境要恶劣**，这条讲**前提要主动破坏**——
后者更精确：它指出了具体破坏什么。

### ⛔ API 文档里的「条件句」= 隐含前置条件

实测（`set_locale()`）：

> ⛔ 官方描述是**条件句**：
> *"If translations have been loaded beforehand for the new locale,
> they will be applied."*
>
> ⚠ 翻译**没先加载**就切，切了也不生效，⛔ **且不报错**。
> 排查时会误以为是"翻译文件有问题"。

⇒ 判据：**读到条件句（if / 若 / 只有…才）时，
它的前提条件有没有被显式满足？**

ⓘ 与 [`diagnosis.md`](diagnosis.md) 同源：
这类失效的**症状与原因分离**——
表现为"翻译文件有问题"，实际是"加载顺序错了"。
⇒ 排障表里的症状，多半就是这么来的。

## 五、回归基准：录下来，改完重放

```
【做】录一段标准操作（跑 → 小跳 → 大跳 → 转向 → 落地 → 上坡 → 下坡）
⚠ 这段录像作为**回归基准**：以后改任何参数，都要重录对比，确认没有退化。
```

**为什么需要**：手感/数值类的改动，**没有基准就无法判定是改进还是退化**。
改完觉得"好像更顺了"，但可能是别处变差了。

判据：**改完之后，能不能跟改之前并排比？** 不能 → 没有基准。

ⓘ 与 `../howto/ratchet.md`（棘轮机制：只进不退）配套：
棘轮说"不能变差"，回归基准说"怎么知道有没有变差"。

## 六、陌生人测试：找没参与的人

```
【做】找 ≥3 名**没参与开发**的人操作
```

**为什么是"没参与开发的"**：

参与开发的人**知道该怎么操作**，会**无意识地避开**有问题的路径。
他测不出"我以为按了跳但没跳"这类问题——因为他知道什么时候该按。

ⓘ **两端独立得出同一条**：
game-dev 的验收要求 ≥3 名未参与者试玩（产品视角）；
引擎侧 [`../craft/taste.md`](../craft/taste.md) 的总判据也是它（文档视角）。
**统一表述与判据见 [EC-04](../common/blocks.md#ec-04-陌生人测试)。**

ⓘ 本文件保留的是**可执行部分**（≥3 名、怎么找）
——判据本身不在这里重复定义。

## 七、常见返工节：每条都要写后果

「常见返工」不是"注意事项"，是**按代价排序的清单**：

```markdown
⚠ 用 RigidBody 做主控角色 —— 物理引擎接管速度，手感不可控。
   **发现就得整个换掉**。
```

**判据：这条返工被发现的代价是什么？** 写不出后果的，不值得列。

⛔ 代价相近的凑一堆 = 读者无法判断先防哪个。
✅ 把「发现就得整个换掉」排在最前面。

ⓘ **但清单本身该按什么索引？** 按症状，不按注意事项——
见 [`diagnosis.md`](diagnosis.md)（97 个功能点里 60 个用的是
「症状 → 原因 → 回到哪步」三列表，不是罗列注意事项）。

## 八、故障演练：主动注入故障，每条真跑

**验收不能只测"正常用"。** 存档域的 10 条演练：

| # | 故障 | 预期 |
|---|---|---|
| 1 | 保存写到 50% 杀进程 | 旧档完好可读 |
| 2 | 写完 tmp、rename 前杀进程 | 旧档完好 |
| 3 | 主档内容改成全零 | 自动退 `.bak` |
| 4 | 主档和 `.bak` 都坏 | **明确提示 + 保留损坏文件** |
| 5 | 磁盘写满时保存 | 明确报错，旧档完好 |
| 6 | 迁移中途抛异常 | 回滚到 `.pre_migrate` |
| 7 | 改系统时间到一年后 | 云同步不让旧档赢 |
| 8 | 断网时保存 → 联网重开 | 进度正确 |
| 9 | 云端放一份坏档 | **拒绝下载**，本地不受影响 |
| 10 | 高版本存档喂给低版本程序 | **明确拒绝，不静默载入** |

> ⚠ **这 10 条每条都要真的执行**，
> ⛔ **不能"代码看起来是对的"**。

**判据：这个东西在真实世界里会怎么坏？我主动让它坏过吗？**

没主动注入过故障 = 只验证了「在不出问题时不出问题」，
**与第二节（验收环境）是同一个失效的两种表现**。

### ⛔ 失败时要留证据，不要静默吞掉

三条演练的**预期**里都有同一个要求：

```
4  主档和 .bak 都坏  → 明确提示 + **保留损坏文件**
9  云端坏档          → **拒绝下载**，本地不受影响
10 高版本喂低版本    → **明确拒绝，不静默载入**
```

⚠ 这不是凑巧：**失败路径上最贵的错是"静默"**——
静默清空 / 静默载入 / 静默覆盖，都会让可恢复的问题变成不可恢复的。

判据：**失败时有没有留下可追查的东西？**
（保留损坏文件 = 还有机会救；清空了 = 永远没了。）

ⓘ 与 `../audit/self-verification-silent.md` 第九条同源：
**「配置坏了静默降级」**是本项目最高频的失效形态。

## 九、对抗性验收：主动攻击自己的实现

网络域的验收要求：

```
2. 伪造 RPC / 改内存 / 重放旧包 **全部被拒**
```

⚠ **这是第四节「假完成」的对立面**——
假完成是"看起来做对了其实没有"，
对抗性验收是**主动想办法证明它没做对**。

**判据：我试过让它失败吗？还是只试过让它成功？**

只构造能让实现通过的输入，等于**只验证了实现者的假设**。
⛔ 而实现者的假设恰恰是最可能有问题的地方。

| 常见手段 | 验的是什么 |
|---|---|
| 伪造输入 / 改内存 | 信任边界（客户端数据不可信） |
| 重放旧包 | 幂等与序号校验 |
| 极端值 / NaN | 数值校验 |
| 打乱顺序 / 重复调用 | 时序与幂等 |
| 高版本喂低版本 | 兼容性不静默降级 |

ⓘ 与 `../audit/self-verification-falsepos.md` 第四条（正反双样本）
是递进关系：**正反双样本防的是"判据写错"，
对抗性验收防的是"没想过它会怎么被绕过"。**

## 十、⛔ 验证要在入口做，不在出口做（早失败）

反哺自配表域的「导入期校验是必做步骤」：

> ⚠ **校验失败应该报错并阻止导入**，不是警告——
> 否则坏数据进了包，**问题会在运行时以完全无关的形式出现**。

⛔ 这是排障成本的分水岭：

| 验证位置 | 出问题时 |
|---|---|
| **入口**（写入时） | 症状 = 原因，直接指到那一行 |
| 出口（运行时） | **症状与原因分离**——表现形式和根因毫无关系 |

⚠ 后者的代价不是"更难找"，而是**根本不会往那个方向找**。

实测佐证（同域）：报错往往**不是**"文件不存在"，
而是**拿到一个空资源**——表现形式和根因完全无关。

**判据**：

> **这条数据/内容如果错了，最早能在哪一步发现？**
> 答案不是"写入时" → 把验证前移。

ⓘ 与 [`diagnosis.md`](diagnosis.md) 是配套的：
排障表（症状→原因→回到）**治的是晚失败的后果**，
而本条治的是**别让它晚失败**。

## 十一、⛔ 未验证的预案 = 没有预案

反哺自稳定性域，**这是本项目自己的现状**：

> ⚠ 另一类（风险）是：备份、回滚、扩容预案
> **只存在于文档而从未验证**。

引擎侧的实情：主链路「捕获→整合→归档→索引→召回」
**从未在真实数据上跑通过**——所有自检都是在临时目录
造样例验证**机制本身**，不是验证**这条链**。

⚠ 这条为什么难被发现：**文档在、流程在、自检全绿**。
看起来万事俱备，而唯一没做过的事是"真的走一遍"。

**判据**：

> **这个预案/流程，有谁真的照着做过一次吗？**
> 答不出具体那一次 → 它还没被验证。

ⓘ 与第四节「假完成」同源但不同层：
假完成是**某一步**看起来做完了；
未验证的预案是**整条链**一次都没走过——
后者的自证更难，因为每一步单独看都是对的。

ⓘ 与 [EC-02](../common/blocks.md#ec-02-正反双样本缺反侧等于没验证)
的关系：自检用例属于"机制验证"，
而**真跑一遍**属于"链路验证"，两者不能互相替代。

---

## 十二、⛔ 单点防护缺失会互相放大

反哺自稳定性域：

> ⚠ **最危险的不是某次代码缺陷，而是
> "无超时 + 无限流 + 无熔断 + 无界重试"
> 把一次局部抖动放大成全链路雪崩。**

ⓘ 单独的每一项都只是"少了个保护"，
**合起来才是灾难**——而合起来的后果无法从单项推出来。

⚠ **这类风险无法靠"逐项检查"发现**：
逐项看每一条都成立（超时有、限流有……），
只有看**组合**才能发现缺口在哪。

**判据**：

> **这几个防护同时失效会怎样？**
> ⛔ 只问"每项有没有"问不出这个问题。

ⓘ 与 [`sequence.md`](sequence.md) 的「接缝」同源：
流程接缝是**产出对不上**，这里讲的是**防护留白叠加**——
两者都是"单看没问题，合起来出事"。

## 十三、⛔ 接缝复查是单独一级：部件全合格也可能拼不起来

反哺自 game-dev 的 28 个域流程——**每个域的 07 验收都有独立一步「接缝复查」**，
逐条核对 00 总览里的接缝契约表。

> ⛔ **这六条不查，部件全合格也可能拼不起来。**

⇒ 审核不是两级，是**三级**：

| 级 | 查什么 | 时机 |
|---|---|---|
| 步骤级【审】 | 这一步做对了吗 | 做的时候 |
| 功能点级复查 | 这个功能点做完了吗 | 做完复查 |
| **域级接缝复查** | **各部分拼起来还成立吗** | **全部做完** |

ⓘ 第三级为什么必须独立成步：**前两级都是"看自己"，第三级是"看别人"。**
⛔ 合并进功能点级会自然退化成再查一遍自己的交付物——
因为做的时候不知道别人那边长什么样。

⚠ 最容易漏的原因是**顺序**：接缝复查在**所有部件都做完之后**，
那时"每个部件都通过了"的实感最强，
而"拼起来怎么样"恰恰是**谁都没单独验证过的**。

### 写法

接缝复查步要列出**契约表**（对哪个域 / 复查点），
每条都要**实测证据**，⛔ 不能只写"已确认"。

## 十四、⛔ 验收针对「非常规路径」，不是「能跑通就算过」

反哺自 mod 域。它的判断方式值得单独学：

> ⚠ **本域的核心不是"能不能加载一个 PCK"，
> 而是"在敌意环境与非常规路径下是否仍然成立"。**
>
> Mod 系统的失败有个共同特征：**正常环境下全绿**。
> 只在换顺序、换机器、从搜索栏启动、缺依赖、恶意包时才暴露。

⇒ **先问：这类事的失败，是不是集中在"正常环境下全绿"？**
是 → 验收清单必须**专门针对非常规路径**设计，
⛔"能加载就算过"这类常规路径验收一条都不该做为主判据。

⚠ 实测的非常规路径清单（该域列了 6 条，全部真跑）：
四种启动方式（双击 / 快捷方式 / 搜索栏 / 符号链接）结果一致 ·
preload 场景仍受 Mod 影响 · 依赖错排时报错指向真因 ·
循环依赖报出具体 id · 恶意包不写出任何文件 · 换一批同数量 Mod 存档校验不通过。

ⓘ 与第二节（验收环境匹配真实失败环境）的关系：
那条判**环境**（延迟/丢包/单机），本条判**路径**（你怎么到达那个功能）。
⇒ 环境对了但只走常规路径，仍然测不到它特有的失败。

---

## 十五、⛔ 验收场景跑不出来时，改定性，不改场景

反哺自 gem / class / relic 三个域验收（逐字出现 3 次）：

> ⛔ 场景跑不出来时，**改定性而不是改场景**。
> ⚠ 把场景改成"实际实现的样子"是自欺——验收就失去意义。

⇒ 这是"验收失败"这个时刻最自然的错误反应：
场景是我自己定的，实现也是我自己做的，
**改哪个都行，而改场景显然更省力**。

⛔ 但改场景等于**把验收标准降到已实现的水平**——
它必然通过，也就必然什么都没验证。

判据：**这个场景是在别的域/需求里定义的，还是我实现完才补的？**
后者 = 自欺。

ⓘ 与第四节（假完成）配套：假完成是"看起来做完了"，
本条是"验收没过时把它改成能过"——**后者更主动，也更难发现**，
因为它看起来像是"修正了写错的验收标准"。
