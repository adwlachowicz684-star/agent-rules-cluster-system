# 推进顺序：多个流程/功能点之间怎么走

> **本区性质：flow / 元规则。**
> 单个流程**内部**的写法见 [`step-spec.md`](step-spec.md)；
> 没有流程可套时见 [`skeleton.md`](skeleton.md)。

---

## 一、为什么单独一层

`step-spec.md` 管「一个流程内部每步怎么写」，
`skeleton.md` 管「没流程时套什么」。

**但中间还有一层是空的**：

```
多个流程 / 多个功能点，按什么顺序走？
什么时候算"这个做完了可以进下一个"？
```

**单个流程写对了，不等于多个流程的推进顺序是对的。**
实测后果：跳着做之后出问题，**分不清是哪一步的问题**
（"跳跃手感没做完就去接动画，你分不清是移动的问题还是动画的问题"）。

---

## 二、先打开总览，⛔ 不要直接跳编号

一套被拆成多个功能点的流程，**必须有一个总览入口**：

```
00-域流程总览.md   ← 永远先看这个
01-<功能点>.md
02-<功能点>.md
…
```

总览要给出：**功能点拆解 + 依赖顺序 + 哪些必须先做**。

⛔ **不要直接跳到某个编号文件**——功能点之间有**前置关系**，
凭直觉挑一个开始做，会在中途撞上"这步依赖的那步还没定"。

**判据：能不能不打开任何一个功能点文件，就说出"先做哪个、为什么"？**
说不出 → 总览没写清楚（或根本没有）。

### ⛔ 先筛选，再排序：不是所有功能点都要做

一套流程被拆成 N 个功能点，**不等于每次都要走完 N 个**。
实例（原文）：

> ⚠ **第 0 步：先定做什么。**
> 本域有 7 个功能点，⛔ **不是全做** —— 按本次需求挑。

写法是给一张**需求 → 功能点子集**的映射表：

| 本次要做的 | 走哪些功能点 |
|---|---|
| 只要几个一次性成就 | **不要套本域** |
| 有累计型（击杀 100） | 01 → 02 → 03 → 07 |
| 全套 | 01 → … → 07 |

⚠ 表里**必须有一行是「不要套这套流程」**——
需求简单时套全流程，得到的全是**用不上的结构**，
而这些结构后面每一步都要维护。

**判据：这次需求真的需要走完吗？有没有更短的路径？**

### 顺序按风险排，不是按实现便利排

实例（原文，存档域）：

> ⚠ **存档是唯一"出错就不可逆"的系统**——玩家进度没了不会重来。
> 所以本域的功能点顺序是按**风险**排的，不是按实现便利排的。

按实现便利排的典型错误：

```
① 先做云存档再做本地原子落盘
   → 云同步会把本地的坏状态同步到所有设备
   → 一个断电损坏变成全设备损坏
```

**判据：这两个顺序，哪个出错时代价小？**
⛔ 不是"哪个先做更顺手"。

### ⛔ 更通用的一条：先做的，会不会被后做的推翻

各域「最容易做反的顺序」形态高度一致——**都是把会变的先固化了**：

| 域 | 做反的顺序 | 先固化的 | 后被推翻 |
|---|---|---|---|
| UI | 先摆控件再想分辨率 | 控件位置 | 分辨率策略 |
| UI | 先做界面再补手柄 | 界面 | 焦点/交互模型 |
| 关卡 | 先搭场景再抽数据 | 场景 | 数据结构 |
| 角色 | 先调参数再搭结构 | 手感参数 | 结构 |
| 角色 | 先接动画再做移动 | 动画表现 | 移动正确性 |

**判据（一句话）**：

> **如果后做那步的结论不同，先做的这步要不要重来？**
> 要 → 顺序错了。

⚠ 这比「按风险排」更通用：风险排序处理的是**不可逆**的事，
本条处理的是**会被推翻**的事——后者更常见。

ⓘ 反过来说也成立：**先做的应该是"后做的都依赖它"的那个**
（分辨率 ← 控件位置；数据结构 ← 场景；结构 ← 参数）。

ⓘ 「不可逆」的事（存档、迁移、发布、删除）**一律优先**——
它们没有"回头再修"这个选项。

## 三、一个做完并验收通过，才进下一个

> ⚠ **这是本文件最硬的一条。**

**判据：上一步的验收清单逐条打完勾了吗？** 没有 → 不许开始下一步。

**为什么不能跳着做**（理由比规则本身重要）：

```
跳着做会让后面的验收无法判定。
例：跳跃手感没做完就去接动画 ——
    出问题时分不清是移动的问题还是动画的问题。
```

⚠ **"分不清是哪一步的问题"比"某一步有问题"贵得多**——
前者要重新定位，后者直接修。

ⓘ **这一条同时也是「假完成」的探测器**：
有些步**验收清单能打勾、但其实没做对**（假完成），
它只有在**下一步撞墙时**才现形。跳着做会让探测器失效。
详见 [`acceptance.md`](acceptance.md) 第四节。

反过来也成立：**各部件合格 ≠ 拼起来能用**。
大功能要**集成验收**（见 `skeleton.md` 第 8 节）。

## 四、审查必须嵌在流程的出口，不是流程之外

每个功能点文件的**最后一节**必须指向审查册：

```markdown
## 6. 下一步
  完成后去哪个功能点；以及**自审入口**（audit 文件）
```

> ⛔ **做完不看 `audit/` 等于把审核环节省了。**

⚠ 为什么必须是**最后一节而不是独立步骤**：
放在流程末尾，它是"这一步做完的标志"；
放在流程外，它是"有空再说"——而"有空再说"等于没有。

**这与闭环（FL-02）的第 ④ 步是同一条规则的两个落点**：
FL-02 说"审查完要回看建设册"，本条说"流程本身要给审查留一个出口"。

## 五、⛔ 有副作用的步骤，顺序按「可逆性」排

实测（成就域的解锁事务）：

> ⛔ 顺序固定：**判达成 → 标记 → 发奖 → 通知**
>
> ⚠ 先弹通知再发奖励：正常流程下玩家看到弹窗也拿到了东西，
> ⛔ **但奖励发放失败时玩家看到解锁却没拿到**，
> 且重放事件会**重复发奖**——这是可直接刷取的漏洞。

**抽象判据**：

> **这几步里，哪一步失败了就收不回来？**
> 收不回来的放**最后**。

| 步骤 | 可逆？ |
|---|---|
| 判达成 | 纯判断，无副作用 |
| 标记 | 可回滚 |
| 发奖 | ⚠ 可回滚但要幂等键 |
| **通知** | ⛔ **不可逆**（玩家已经看到） |

⚠ 为什么这条容易被违反：
**正常流程下两种顺序的表现完全一样**——
玩家都看到弹窗、都拿到东西。
只有**失败时**才分出高下，而失败路径最常被跳过。

ⓘ 与第三节（一个做完才进下一个）是不同层：
那条管**要不要并行**，这条管**串行时的先后**。

## 六、⛔ 成对操作只写一半：正常流程对，异常一来就废

实测（相机状态机）：

> ⛔ 常见假完成：**只写"进入"逻辑**——
> ⚠ 死亡/过场/菜单的相机状态机**只写 enter 不写 exit**，
> ⛔ 异常中断时相机**停在中间态**，玩家无法自行恢复。
>
> 应该能当场演示：
> 4. ⚠ 状态机**有 exit**且从**快照**恢复（不是置 true）

⚠ 这是**最难被发现的一类缺陷**：

```
正常流程  → 全对
异常中断  → 停在中间态，且不可自行恢复
```

⇒ **只走正常路径的验收，永远发现不了它。**

ⓘ 与 [`../audit/self-verification-falsepos.md`](../audit/self-verification-falsepos.md)
第六、十二、十九那族同源，也与第七节的「查漏了 B 要从 A 出发」一致：
**成对操作查的是"另一半在不在"**。

### ⛔ 恢复要回到**快照**，不是回到默认

同一条实测里的第 4 点值得单列：

> ⚠ 状态机有 exit 且从**快照**恢复（**不是置 true**）

```
⛔ 中断后把标志位置 true          —— 那是"默认值"，不是"之前的值"
✅ 中断后恢复到**进入之前**的状态  —— 才是真的回滚
```

ⓘ 与 [`../craft/techniques.md`](../craft/techniques.md)
的「复用前重置」是镜像：
- 重置：清掉上一次的残留
- 回滚：回到这一次的**进入前**

⚠ **两者的对象不同**（残留 vs 进入前状态），
混为一谈会导致"重置过头"或"回滚不到位"。

## 七、七节顺序固定：位置可预测

多个功能点文件共用一套模板时，**节的顺序必须固定**：

```
0 交付物定义 → 1 前置检查 → 2 工序 → 3 参考实现
→ 4 验收清单 → 5 常见返工 → 6 下一步
```

**为什么顺序要固定**（不是为了好看）：

> **调用时位置可预测。**

一套 169 个文件的流程库，如果每个文件节序不同，
想找"验收清单"就得先读完整个文件——
**按需加载就失效了**，只能全量读。

判据：**能不能直接跳到第 4 节，而不用先扫一遍目录？**

## 八、工序里的参数是起点，不是终点

```text
✅ 工序里的参数值都是起点，手感/数值类参数必须实测后回填
⛔ 留着示例值当生产参数
```

⚠ 模板里给的参数是**让你能先跑起来**，不是最终值。
验收时**必须回填实测值**，且**能说出怎么测出来的**。

**登记待核实项**（而不是就地写死）：
标了「待核实」的值⛔ 不得直接当生产参数——
要有地方登记、有办法在运行时回填。
判据见 `../audit/self-verification-credibility.md` 第二十条
（未验证结论必须条目化）。

> 两端独立得出同一条：game-dev 侧用脚本登记待核实项并运行时回填，
> 引擎侧用第二十条「未验证结论必须条目化」——**形态不同，判据相同**。

ⓘ 本文件不写具体脚本名：引擎侧目前没有对应的登记工具，
⛔ 写了就是死链（LK002 会报 error）。

## 九、⛔ 不要把 flow 当知识库查

```
查「这个 API 怎么用」  → howto/
查「按什么顺序做」     → flow/
查「哪里会踩坑」       → audit/
```

⚠ 拿流程文件当知识库查，会同时得到两个坏结果：
① 找到的不是最全的做法（做法在 howto/ 里）；
② 把"顺序"和"知识"混在一起，之后两边都不好改。

**判据：我要的是「怎么查到完整说明」还是「下一步该干什么」？**

## 十、自检（30 秒）
- [ ] 有副作用的步骤，**不可逆的排最后**了吗？（失败时收不回的那一步）
- [ ] 成对操作（enter/exit、进入/中断）**两半都写了吗**？异常路径走过吗？
- [ ] 回滚回到的是**进入前的快照**，不是默认值？

- [ ] 这套流程有**总览入口**吗？能不能不看细节就说清先后？
- [ ] 上一步**验收通过**了吗？（跳着做会分不清是哪步的问题）
- [ ] 最后一节指向 `audit/` 了吗？（⛔ 没指向 = 把审核省了）
- [ ] 节序跟其他流程文件**一致**吗？（位置可预测）
- [ ] 参数是**实测回填**的，还是模板示例值？
- [ ] 有没有拿 flow 当 howto 查？
