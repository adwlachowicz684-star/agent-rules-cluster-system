# 闭环迭代协议：建设 → 审查 → 回看 → 互补

> **本册性质：流程册（怎么做）。**
> 讲两册怎么配合着把技能库迭代强化。判据与归属见 `split-two-books.md`。

---

## 一、为什么需要闭环

只建设不审查 → 技能写得顺手，但没人知道它在哪会失效。
只审查不回看 → 每次都在报同一类问题，而**建设册里从来没有对应的那一句**。

后一种是最常见的停滞形态：审查册越写越厚（因为它不断吸收新失效），
建设册原地不动（因为没人回去补那句"该怎么做"）。
结果同一个坑反复踩——**审查册记录了十次"这里会静默失效"，
建设册始终没写"这里必须显式报错"**。

实测（本仓库）：`self-verification.md` 从 137 行涨到 441 行，
17 条里有 5 条是这几轮补的；同期建设册只增加了驳回清单的拆出。
**审查册在独自长大**——这正是闭环缺失的症状。

## 二、五步闭环

```
① 建设   用建设册写 / 改 / 生成技能
              ↓
② 审查   用审查册逐条对照，出「哪里不行」清单
              ↓
③ 调整   按审查结果改技能本身
              ↓
④ 回看   拿审查结果反查建设册，问三个问题（见下）
              ↓
⑤ 互补   建设册补"该怎么做"，审查册补"漏了哪种失效"，互相确认
              ↓
        回到 ①
```

**第 ④ 步是闭环的关键**，也是最容易跳过的——
因为改完技能后"事情已经做完了"，而回看建设册是**额外的一步**。
所以要把三个问题写成硬性的，不是"有空再看"。

### 第 ④ 步：回看建设册的三问

审查报出一条问题后，逐条问：

| # | 问 | 命中了要做什么 |
|---|---|---|
| 1 | **流程不够详细？** 建设册里的步骤，是不是细到陌生 AI 照做不会走偏？ | 补具体动作。判据：**能不能只靠这一个文件干活**（核心原则 ③） |
| 2 | **内容有疏漏？** 这个失效形态，建设册里有没有对应的一句"该怎么做"？ | 补那一句。这是审查册反哺建设册的主通道 |
| 3 | **代码 / 脚本不够严谨？** 报出的问题，是不是某个脚本静默失败 / 假绿 / 参数不校验导致的？ | 改脚本，并**把失效形态补进审查册**（见下） |

**第 2 问是审查册反哺建设册的唯一通道。**
审查册记的是"会怎么失效"，建设册要的是"该怎么做"——
同一件事在两册各有一句，才是闭环（判据见 `split-two-books.md`）。

### 第 ⑤ 步：审查册也要自查

**审查到「审查不全面的内容」时，必须补审查册。**

判定：这次报出的问题，在审查册里**找不到对应的判据**——
说明它是靠人肉发现的，下次换个人就发现不了。

补法：把它写成一条判据，带上三件套（位置 / 证据 / 后果）。
**没有判据的发现是不可复现的发现。**

| 情况 | 处置 |
|---|---|
| 问题能在审查册里找到对应判据 | 只改技能，不动审查册 |
| **问题在审查册里找不到判据** | **补一条判据**（这才是审查册长大的正当理由） |
| 同一形态反复报出 | 说明建设册缺那一句 → 走第 ④ 步第 2 问 |

### 互相确认（双向，不是单向）

建设册补充时，问：**这个"该怎么做"，它的失效形态审查册里有吗？**
没有 → 审查册补一条。

审查册补充时，问：**这个"不能怎么做"，建设册里有对应的"怎么做"吗？**
没有 → 建设册补一句。

> **单向补充会让两册失衡。** 只补审查册 → 技能库全是"别这样别那样"，
> 没有可执行步骤；只补建设册 → 没人知道它在哪失效，下次照踩。

## 三、自检器：触发拆分与回看

闭环靠自觉不会转（本仓库实测：`_hot.md` 命中数长期全 0）。
所以把触发条件做成 `scripts/lint.py` 的自动检查：

| 检查项 | 触发 | 提示做什么 |
|---|---|---|
| **体积预警** | 超过上限 | 拆文件或下沉细节 |
| **接近上限预警** | 达到上限 **80%**（新增） | **现在就规划拆分**，别等到超限 |
| **章节过多** | 单文件 `##` 章节 > 12（新增） | 内容已不适合单文件，按主题拆 |
| **孤立知识点** | 写了「要注意 X」但不改变任何一步 | 改写或删除 |
| **豁免可验证** | 声明了体积豁免 | 理由不成立就该拆 |
| **标题重复 `#`** | `## ## x` | 拼接时多带了一组 |

**接近上限预警为什么要有**：等到超限才报，往往已经长到拆不动了
（400 行的文件拆成三份，要重写目录和交叉引用）。
80% 时提示，还有余裕规划。

跑法：

```bash
python3 scripts/lint.py            # 全量检查
python3 scripts/lint.py --json     # 机器可读
python3 scripts/lint.py --self-test  # 验证检查项本身还工作
```

## 四、自我迭代强化（累积效应）

闭环跑起来后，技能库会自己变强，不需要外部推动：

1. 每次踩坑 → 审查册多一条判据（下次同类坑自动被抓）
2. 每条判据 → 建设册多一句"该怎么做"（下次不会踩）
3. 建设册越细 → 审查报的问题越少、越聚焦
4. 审查册越全 → 第 ④ 步的三问越容易命中

**判据：技能库在变强还是只在变厚？**

| 信号 | 含义 |
|---|---|
| 审查册涨、建设册不动 | **停滞**——同一个坑反复踩，只是记录得越来越详细 |
| 两册同步增长 | 健康——每次失效都转化成了可执行步骤 |
| 同一形态反复报出 | 第 ④ 步第 2 问没做——建设册缺那一句 |

## 五、自检（30 秒）

- [ ] 这次审查报的问题，**逐条**问过三个问题了吗（不是只挑容易的问）
- [ ] 有没有「审查册找不到判据」的发现？有 → 补判据了吗
- [ ] 建设册补的那句，审查册有对应失效形态吗？（双向确认）
- [ ] 审查册补的那条，建设册有对应"怎么做"吗？（双向确认）
- [ ] `lint.py` 报的接近上限 / 章节过多，规划拆分了吗
