# 技巧：怎么做到「好」

> **本区性质：craft / 技巧层。**
> 与 `taste.md`（什么算好）配对：**那边给判据，这边给手法。**
> 与 howto 的区别：howto 是**流程**（照着走完一件事），
> 本区是**手法**（遇到某类问题时的具体做法，可单独取用）。

---

## 一、为什么单独一层

howto 是完整的流程，从头走到尾。
但很多时候你**不是要走完整个流程**，而是卡在某一步上：

```
流程：捕获 → 整合 → 归档 → 索引 → 召回
                 ↑
              卡在这里：两个条目看着像，该合并还是并存？

howto/versioning.md      讲整个版本分化流程
craft/techniques.md      讲「怎么判断两个条目是同一件事的两种写法
                          还是两件不同的事」这一个具体手法
```

**手法是可复用的，流程是一次性的。**

## 二、判断类技巧

### 1. 判「换个项目还成立吗」

核心原则 ① 的可操作形式。两个追问让它落地：

| 追问 | 排除掉的东西 |
|---|---|
| **换个项目还成立吗？** | 项目事实（路径、文件名、一次性数据） |
| **换个领域还成立吗？** | 领域知识（Godot 的 API、金融的术语） |

剩下的才是**技能**（做法）。

> 反直觉的一点：**换个项目就变的东西，价值往往更高**——
> 但那不是技能库该存的，该存在项目自己的 rules/ 里。

### 2. 判「该合并还是并存」

两个条目看着像时，按这个顺序问：

1. **去掉环境差异后还不同吗？** 不同 → 两件事，并存；相同 → 继续
2. **是同一个做法的两个版本吗？** 是 → 合并，留 `applies_to` 标注
3. **会不会同时用？** 会 → 并存（不是版本问题，是用途不同）

（完整流程见 `../howto/versioning.md` 与 `../howto/env.md`）

### 3. 判「这条该放哪个大类」

```
关键词命中数 ≥ 2        → 自动推荐
仅命中泛词（通用/流程/…） → 不算命中，必须问用户
多个大类都命中          → 提提案，不自行改结构
```

**归错类比不归更糟**——不归还能检索到，归错了会被定向加载跳过。

### 4. 判「是不是真的这里出问题」（先定位，再动手）

反哺自对象池/性能域。**凭直觉定位的代价不是"改错"，是"改乱"**：

```
凭感觉改 → 改完没用 → 怀疑工具不准 →
转而去改"看起来可疑"的地方 → 越改越乱
```

⚠ **第三步最致命**：改完没用之后，人不会去质疑**定位**，
而是去质疑**工具**，然后换一个同样没依据的方向重来一遍。

| 直觉 | 实测（性能域的三条对照） |
|---|---|
| "节点太多了所以卡" | 节点数量很少是瓶颈，DrawCall 和脚本逻辑才是 |
| "贴图太大" | 通常是材质切换次数（合批被打断），不是单张尺寸 |
| "物理太重" | 先确认是不是每帧在做空间查询 |

**判据**：

> **我准备改的这个地方，是实测出问题最多的地方吗？**
> 只能答"看起来像" → 先去定位，别动手。

#### ⛔ 直觉对**非线性**关系完全没有判断力

实测（强化系统的期望次数）：

| 失败规则 | 期望次数 |
|---|---:|
| 失败等级不变 | 约 **31** |
| 50% 回退 1 级 | 约 **205** |
| 100% 回退 1 级 | 约 **2557** |

⚠ "失败掉一级"听起来只是"稍微严一点"，
**实际是 82 倍**——对普通玩家近似不可达。

**为什么这条重要**：非线性关系的**直觉误差是数量级的**，
不是百分比。而人的直觉天生按线性外推。

⇒ 判据：**这个关系是线性的吗？** 不确定 → 算，别估。
ⓘ 和第二十三条（「能数出来的」≠「该判的」）互补：
那条说别用可数指标代替判断，这条说**别用线性直觉代替计算**。

ⓘ 与第二十三条（「能数出来的」≠「该判的」）是**镜像**：
那条说别拿**可数指标**代替判断，这条说别拿**直觉**代替定位。
两条合起来：**判断要有依据，依据不能是"最容易拿到的那个"**。

### 5. 判「复用前重置了吗」

反哺自对象池。**不彻底的复用比不复用更糟**：

> ⚠ 池不是"用 `queue_free` 换成 `hide`"就完事——
> **不做状态重置的池比不池化更糟**，
> 因为它把**偶发 bug 变成必现 bug**。

回池前必须清理的四类状态（漏一类就会复用出 bug）：

| 状态 | ⛔ 不清理的后果 |
|---|---|
| 速度/方向残留 | 从池里取出就往旧方向飞 |
| 已命中集合 | 第二发打不中 |
| 已连接的信号 | 回调打到旧目标 |
| 视觉残留（拖尾/粒子） | 残影出现在新对象上 |

**抽象到引擎侧**：

> **复制一个模板/流程/清单来做新的，上次的残留清了吗？**

⚠ 最常见的残留是**编号与 ID**——复制 `flow/_template.md`
却沿用了 `[FL-xx#Sn]` 占位符，检查器认不出来，人也认不出来。

判据：**这个东西被第二次用的时候，上一次的内容还在吗？**

## 三、写法类技巧

### 1. 把"要注意 X"改写成动作

判据：**它改变了哪个流程的哪一步？**

```
✗ 「要注意注释里的示例会被扫描器命中」
✓ 「fixture 样本写完后跑 --comment-test：
     把样本整段注释掉再扫，必须零命中」
```

**从"知道"变成"做"，才算落地。**

### 2. 给判据配反例，而不是只配正例

正例证明"这样能命中"，反例证明"那样不会误报"。
**只有正例的规则会无限误报**，最后被人关掉。

### 3. 用「失败形态」驱动写排除条件

```
命中条件：看到 has()
排除条件：若该 has() 是池的重复归还拦截（查"是否已空闲"），
          则语义与归属校验相反，不算
```

写法模板：**命中条件 + 「但」+ 例外场景 + 为什么不同。**

### 4. 数字不要散落在正文里

```
✗ 正文写着「超过 300 行就该拆」，而 config.yaml 里是 400
✓ 正文写「上限见 config.yaml」，并把 300 改成引用
```

**散落的数字迟早和配置漂移**，而且没人会去对。

## 四、验证类技巧

### 1. 变异测试：先让它红

加检查项 / 改判据后，把缺陷**注入回去**看测试会不会红：

```bash
python3 scripts/lint.py --self-test      # 先绿
# 故意破坏判据
python3 scripts/lint.py --self-test      # 必须红
```

**不变红 = 检查没在查。** 这是唯一能发现"假绿"的方法。

### 2. 检查自己会不会误报

刚写完的检查，拿**正常的、正确的**内容跑一遍。
误报的检查会被人关掉——**被关掉的检查比没有更糟**，
因为它曾经给出过绿色信号。

### 3. 改完立刻校验落盘

```python
# 改文件后立刻验大小或关键字，别只信脚本打印的「已完成」
assert '新内容' in open(p, encoding='utf-8').read()
```

**已知踩过两次**：① 中途重新 `open(p).read()` 丢掉前面所有改动
② assert 抛异常导致文件没写盘——两次都打印了"成功"。

## 五、沉淀类技巧

### 1. 经验按「失效形态」归类，不按「发生位置」

```
✗ 「Godot 的坑」「Python 的坑」      —— 换个语言就用不上
✓ 「静默类」「误报类」「假绿类」     —— 换个语言照样成立
```

**按失效形态归类才能跨领域复用。** 这也是 audit/
按失效模式而非按模块组织的原因。

### 2. 一句话该进哪一册，看它的动词

| 动词形态 | 归属 |
|---|---|
| 「应该…」「先做…再…」 | howto |
| 「不要…」「会失效如果…」 | audit |
| 「好的…应该…」「判断标准是…」 | craft |
| 「第一步…第二步…」 | flow |
| 「本文讲…」「本区性质是…」 | common |

### 3. 三件套一次写全

来源 / 证据 / 后果，缺一件就不入库。
**半年后没人记得一条规则怎么来的**，而改旧规则前必查溯源。

### 6. 判「该自己造还是复用」（双向取舍表）

反哺自插件生态域。**只写一个方向必然走偏**：

```
只写「不该自己写」  →  什么都引入
只写「不该引入」    →  什么都自己造
```

✅ **必须两个方向都写**（那边是一张四列表）：

| 环节 | 建议 | **不该自己写**的触发点 | **不该引入**的触发点 |
|---|---|---|---|
| 对话 | 接成熟工具 | 有分支、变量、多语言时 | 仅三句、无分支 |
| 行为树 | 接现成库 | 需要可视化调试时 | 几个状态用 FSM 就够 |
| 网络 | 先吃透内置 | 需权威服/预测回滚时 | 回合制、低频同步 |

**抽象到引擎侧**（该自己写一条规则，还是复用已有的）：

| | 该自己写 | 该复用 |
|---|---|---|
| 内容 | 这个库里**没有**对应条目 | 已有条目，只是没检索到 |
| 形态 | 换个项目还成立（是**技能**） | 换个项目就变（是**项目事实**） |

⛔ **引入的不只是功能，还有它的假设**——
那边的原话（任务/库存系统）：

> ⚠ 引入它 ≈ **用一个插件的设计哲学重写整个游戏**。

抽象：**复用一段现成内容，也接受了它的组织方式**。
⇒ 判据：**复用的这个东西，它的假设和我的场景冲突吗？**

ⓘ 与第 2 条（判该合并还是并存）是同一族的两种问法：
那个问「两个**已有**条目」，这个问「**已有** vs **新造**」。

---

### 7. 判「这两个词是不是一回事」（名称相似 ≠ 结构相同）

反哺自 4 份做法文档的**同一节**（都叫「先分清三件事」）：

> ⓵ 转职 / 觉醒 / 多职业——**数据模型完全不同**，
> 先定是哪一个，否则做到一半会发现**结构撑不住**。
>
> ⓶ 宝石 / 符文 / 附魔——中文项目里经常混用，但**结构不同**。
>
> ⓷ 遗物 / 词条 / 局外解锁——**归属不同**。

⚠ **这类混淆的代价不是"用错词"，是做到一半发现结构撑不住**——
那时已写的部分要按另一种结构重来。

### ⛔ 区分的判据要可观测，不能靠定义

这是最值得学的一点。它们的判据**都不是定义**，而是：

| 组 | 判据 |
|---|---|
| 宝石 / 符文 | **挂在谁身上**（换装备就没 vs 换装备还在） |
| 遗物 / 词条 | **什么时候消失**（换装失效 vs 一局结束） |
| 转职 / 觉醒 | **旧状态还在不在**（消失 vs 保留+追加层） |

⇒ 判据：**它挂在哪？什么时候消失？**

⚠ **用定义区分会循环**（"宝石是可以镶嵌的"——那什么是镶嵌？），
**用生命周期区分是可观测的**。

ⓘ **引擎侧五区分类用的是同一招**：
howto / audit / flow / common / craft 的判据是**动词**
（「应该…」/「不要…」/「第一步…」/「本文讲…」/「好的…应该…」），
不是各区的定义。

ⓘ 与 [`../../flow/step-spec.md`](../../flow/step-spec.md)
的【判据】必须可观测是同一条要求：
**能观察到"是哪一个"，而不是"书上怎么写"**。
