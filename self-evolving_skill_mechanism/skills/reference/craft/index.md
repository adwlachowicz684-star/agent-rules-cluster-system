# craft 层索引：品位与技巧

> **本区性质：craft / 品位与技巧（主观层）。**

> 本层回答：**做到什么程度算好**。
> `howto` 教你怎么做完，`audit` 告诉你哪里不行，**本层告诉你什么算好**。

ⓘ **没有 craft 层的后果**：只会「做完」和「没毛病」。
**没毛病 ≠ 好**——一份文档可以既不违反任何 audit 判据，又完全不好用。

---

## ⛔ 本层是主观的，且明确标注为主观

这是本层与其余四层**最关键的差别**，反哺自 game-dev 的 craft 层（两端第四
次独立收敛到同一结构时发现的）。

| 层 | 装什么 | 性质 | 引用禁忌 |
|---|---|---|---|
| `howto` | 怎么做 | **事实**（可核实） | — |
| `audit` | 不能怎么做 | **事实**（可核实） | — |
| `flow` | 按什么顺序做 | 流程 | — |
| `common` | 元规则 | 约定 | — |
| **`craft`** | **做到什么程度算好** | **经验（主观）** | ⛔ **不要当事实引用** |

### ⛔ 为什么必须标

不标注的后果是**读的人把经验区间当成判据用**：

```
本层写「土狼时间 80–150ms」  （行业经验区间）
被引用为「土狼时间必须 80–150ms」（当成判据）
```

⇒ 一条**参考值**被当成**硬约束**，而后有人基于它去审查、去报错。

ⓘ 这正是第二十三条讲的：能数出来的不等于该判的。
**本层的数字是"经验区间"，不是"阈值"。**

### ⛔ 只抄区间中值是最差的做法

> 区间两端的体验是不同的，取中值等于**两边都不讨好**——
> 表现为「说不上哪里不对，但就是不够爽」。

✅ 正确用法：看**选哪端**（什么情况取大、什么取小），按自己的场景定。
⛔ 不要取中值——中值对应的不是"折中"，是"两种都不是"。

## ⛔ 按动作接入：什么时候会撞到本层

「按需求入口」解决"我想判断 X 时看哪"，
**但它要求读者先意识到自己需要判断**——而这恰恰是最难的一步。

⇒ 补一张**按动作**的表：你在做哪个动作时，本层有话要说。

| 你在做什么 | 会撞到哪条 | 不看的后果 |
|---|---|---|
| **落笔写一条规则** | [`taste.md#1. 写正确的废话`](taste.md) | 写出来格式对、判据有，但读的人不知道该怎么办 |
| **给判据写条件** | [`taste.md#3. 排除条件和命中条件一样重要`](taste.md) | 只写命中条件 ⇒ 到处误报 ⇒ 检查被关掉 |
| **判该写到多长** | [`judgment.md#① 写全 vs 精简`](judgment.md) | 用字数判断 ⇒ 该展开的被压扁、该收的被注水 |
| **拆 / 合并文件** | [`judgment.md#② 拆分 vs 合并`](judgment.md) | ⛔ **为指标拆**（拆了不为按需加载） |
| **决定要不要自动化** | [`judgment.md#③ 自动化 vs 人工`](judgment.md) | 硬做成检查器 ⇒ 100% 误报 ⇒ 关掉 |
| **这次做还是记下来** | [`judgment.md#④ 现在做 vs 记下来`](judgment.md) | 要么过度铺开，要么欠账越滚越多 |
| **判一个模块空不空** | [`substance.md#八个维度`](substance.md) | 用行数判断 ⇒ 空模块一直空着、好内容被注水 |

ⓘ 这七条是从 **46 条里按「撞到的概率」挑的**——不是全集。
其余条目按需求入口表查。

### ⛔ 为什么按动作接入比按需求接入更容易命中

```
按需求：我得先意识到"我需要判断这个文档够不够好"
按动作：我正在拆分文件 → 表告诉我该看哪条
```

⇒ 前者依赖**自我觉察**（最不可靠），后者依赖**正在做的事**（必然发生）。

⚠ 这与 howto/audit 的触发方式不同：那两区靠动词（应该 / 不要）
在写的时候自然被想到；**本层没有专属动词**，
所以必须靠"动作 → 条目"的显式映射。

## 四册的分工

```
taste       什么算好           → 品位的方向
judgment    什么程度该停       → 度
techniques  怎么做到的手法     → 技巧
substance   内容是不是空的     → 充实度
```

ⓘ `judgment` 与 `techniques` 易混：

| | judgment | techniques |
|---|---|---|
| 回答 | **做到哪一层 / 什么时候停** | **怎么做到** |
| 动词 | 「够了」「停」「取舍」 | 「先…再…」「用…手法」 |

## ⚠ 读者只问三件事

反哺自 `game-dev/references/craft/godot/aesthetics.md` 的「可读性」：

> ⚠ 读者**不会**去理解你的分类体系，只会问三件事
> （对应产品侧的"能去哪、哪危险、哪里值得去"）。

| 读者的问题 | 对应到本层 |
|---|---|
| **能去哪** | 我要判断的事，有没有对应的册？ |
| **哪危险** | 哪条是硬约束（不能违反），哪条只是经验值？ |
| **哪里值得去** | 哪条最可能改变我的决定？ |

⛔ **三个都要靠文档本身回答，不能靠读者去理解体系。**

⇒ 这也是本层「主观必须显式标注」的另一半理由：
不标注，读者就分不清**哪危险**——把经验值当硬约束，
或者反过来把硬约束当建议。**两种都错，且第二种更隐蔽。**

## ⛔ 本层的使用禁忌

1. **不要把经验值当判据引用** —— 需要硬约束时查 `audit/`
2. **不要只抄区间中值** —— 两端对应不同取舍，中值两边不讨好
3. **不要在「功能」没做完时做「惊喜」** —— 会变成华而不实（见 `judgment.md` 第六节）
4. **不要用堆量解决廉价感** —— 廉价感来自**不协调**，不是量少（见 `taste.md` 第五节）

## ⓘ 接入现状（诚实标注，不是指标）

`check_craft_refs` 会报**条目级接入率**。首次上线实测：

```
46 条判据 · 条目级接入率 0%（0/46）   ← 首次上线
             10%（5/46）              ← 按撞到的概率接了第一批
             23%（11/46）             ← 补「按动作接入」表后
```

⇒ 本层 1191 行此前**没有任何一条被条目级指向**——
所有引用都是文件级（`craft/taste.md`），**读的人要自己去找那一条**。

⛔ **文件在 ≠ 内容在**（`../craft/substance.md`）。

已接入的（按撞到的概率选，不是凑数）：
`substance#八个维度`（判空不空）· `judgment#改一个字会怎样`（判够不够）·
`taste#判据要在接收方`（写判据）· `techniques#一句话该进哪一册`（归区）。

**剩余 35 条仍是欠账**——不为接入率刷数而机械加引用。

⛔ **本表的自指不计入接入率**。实测：若计入，`index.md` 把 46 条
列一遍就能让接入率变成 100%——**但读的人仍然不知道什么时候该来本层**。
⇒ 假接入比低接入更危险（第二十一条）。`EV-M45` 守着。

ⓘ 接入率从 0% → 23% 不是靠"到处加引用"，是靠**先建触发机制**
（「按动作接入」表）：有了它才知道**哪些动作该接**，
接进去的都是真会撞到的。⛔ 反过来（先刷引用）会让接入率变高，
但读的人仍然不知道什么时候该来本层。
