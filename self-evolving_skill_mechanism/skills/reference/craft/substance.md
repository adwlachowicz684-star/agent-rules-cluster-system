# 充实度：怎么判断一个模块「够不够」

> **本区性质：craft / 品位与技巧。**
> 判定模块是"写透了"还是"只是堆了字数"。
> 多少算够见 [`judgment.md`](judgment.md)；什么算好见 [`taste.md`](taste.md)。

---

## 一、为什么单独一层

`taste.md` 判「好」，`judgment.md` 判「度」，但都回答不了一个更基本的问题：

```
这个模块是空的，还是已经写透了？
```

最容易犯的错是**拿可量化的东西代替判断**：

```
⛔ 「这个模块才 50 行，太空了」      ← 行数当充实度
⛔ 「这里有 200 条规则，肯定够全了」  ← 条数当充实度
⛔ 「12 个章节都写满了」             ← 结构完整度当充实度
```

**这三个都不是充实度。** 它们只是最容易数出来的东西。

---

## 二、总判据：**能不能据此做出正确的决定**

不看写了多少，看**用的时候够不够**：

> 一个真实问题摆在面前，只看这个模块，
> **能不能据此做出正确的决定？**

| 情况 | 结论 |
|---|---|
| 能，且能说清为什么 | **充实** |
| 能，但说不清为什么（靠猜的） | **推导不真实** |
| 只能做出一部分，关键处要另找 | **覆盖不全** |
| 看完了还是不知道该怎么办 | **等于空的**，无论多少行 |

⛔ **"看完了不知道该怎么办"的模块，写 500 行也是空的。**

---

## 三、八个维度（不看数量，看质量）

| # | 维度 | 判据（问一句就能定） | 空的典型表现 |
|---|---|---|---|
| 1 | **覆盖面** | 这个域的**主要情况**都覆盖了吗？**有没有整类缺失**？ | 只写了最常见的那种，边角全无 |
| 2 | **规则完善** | 每条规则有**来源 / 证据 / 后果**吗？**排除条件**写了吗？ | 只有"不要 X"，没有"什么时候 X 是对的" |
| 3 | **流程规整** | 有明确**步骤**吗？每步的**产出**和**判据**清楚吗？ | 一堆要点，没有"先做什么后做什么" |
| 4 | **原理透彻** | 写清**为什么会这样**了吗？还是只写了**现象**？ | "会出错"，不说错在哪一层 |
| 5 | **逻辑严密** | 推导链**跳步**吗？有没有**自相矛盾**的地方？ | 结论对，但中间三步是跳过去的 |
| 6 | **推导真实** | 结论是**实测/推导**出来的，还是**想当然**？ | 标了【实测】但没人真跑过 |
| 7 | **深度** | 有没有**第二层**——别人想不到的那层？ | 全是常识，读与不读没差别 |
| 8 | **体量匹配** | 这个域**本来就这么多内容**吗？还是**注水**或**欠写**？ | 简单概念写 300 行 / 复杂机制一句带过 |

⚠ 第 8 条「体量匹配」是**唯一跟量有关的**，但它判的是**比例**，不是绝对值：

```
判据：这个域的复杂度，配上这个体量，合理吗？
       —— 不是"多少行算够"（没有这个数字）
```

同一个 400 行：对一个横切机制可能**注水**，对一个完整协议库可能**远远不够**。
**脱离域的复杂度谈行数，没有意义。**

---

## 四、⛔ 不能用什么代替判断

| 拿这个当充实度 | 为什么不行 |
|---|---|
| **行数** | 注水能撑满行数；精确表达反而可能很短 |
| **条数** | 200 条人人都知道的 = 0 条真正有用的 |
| **章节数** | 12 个空章节比 3 个写透的差得多 |
| **有没有文件** | 文件在 ≠ 内容在。`check_reference_zones` 会报"区目录空"，但**有内容 ≠ 内容对** |
| **自检全绿** | 见第二十二条：全绿 ≠ 覆盖了历史缺陷 |
| **引用数** | 被引用多可能是**历史包袱**，不代表质量 |

⛔ **共同点：它们都是「容易数出来的」**，
而充实度恰恰是**数不出来的那部分**。

**判据：这个指标能不能靠注水刷高？** 能 → 它就不是充实度指标。

---

## 五、体积上限是成本，不是充实度

⚠ 特别说清一件事，因为它最容易被误读：

```
config.yaml 的 size_limits（行数）
config.yaml 的 token_limits（token）
```

**这两个是「加载成本」的上限，不是「充实度」的判据。**

| | 管什么 | 超了说明什么 |
|---|---|---|
| 体积上限 | 一次读进来占多少上下文 | **该拆了**（按需加载），不是"写多了" |
| 充实度 | 内容够不够支撑决策 | 不够就是不够，**跟行数无关** |

⛔ **不要因为"还没到上限"就认为写够了**——
一个 30 行的模块可能远没到上限，但**完全是空的**。

⛔ 反过来：**也不要因为"超了上限"就认为写得很好**——
它可能只是注水。超限的处置是**拆分**，不是**表彰**。

> 超限检查的提示语里有"按主题拆开，每份可独立定向加载"——
> 拆分的目的是**按需加载**，不是降低行数（见 `judgment.md` ③）。

## 六、怎么判（30 秒流程）

遇到"这个模块够不够"时，按序问：

1. **有没有整类缺失？**（覆盖面）—— 拿这个域的 3 个真实场景试
2. **关键处能不能据此决策？**（总判据）—— 不能就是空
3. **结论是实测还是想当然？**（推导真实）—— 想当然的标出来
4. **有没有第二层？**（深度）—— 全是常识就是没深度
5. **体量跟复杂度匹配吗？**（体量匹配）—— 注水 / 欠写

⚠ **不要用"行数太少"直接下结论。** 50 行写透一个机制，
比 500 行堆砌强得多。

⛔ **如果判不出来，说明缺的不是内容，是判据**——
补一条判据（不是补字数）。

---

## 七、与「空」的区分

一个模块看着"少"，可能是三种完全不同的情况：

| 情况 | 怎么识别 | 处置 |
|---|---|---|
| **真空** | 三个真实场景一个都答不出 | 补内容 |
| **精简但充实** | 场景都能答出，且能说清为什么 | **不要动**，这是最好的状态 |
| **暂不需要** | 这个域本来就简单，或还在搭建 | 标清楚状态，别让它混进"已完成" |

⛔ **把第二种当成第一种，会往好内容里注水**——
为了让它"看起来充实"而加一堆正确的废话，
结果**信息密度被稀释**，反而变差。

这正是 `judgment.md` 里「再改一个字，读的人会做出不同决定吗」的反向应用：
**删一个字，读的人会少知道什么吗？** 不会 → 那字本来就不该在。

---

## 八、⛔ 写全 ≠ 假装全知道 —— 未知边界也是内容

实测：118 份做法文档里，**42 份**有「待核对项（运行时验证）」节。

```
36% 的成熟文档都显式标注了"这部分我没有答案"。
```

⚠ **反过来看**：一份文档**没有任何**待核对项，
要么这个域真的全已知（少见），
要么**把不确定的东西写成了确定的**——后者更可能。

### 判据

> **这份文档有没有说清"我不知道什么"？**
> 完全没说 → 它的"全"很可能是把猜测写成了结论。

ⓘ 与第七节（与「空」的区分）配套：
- 空：**该有的没有**（已知的东西没写）
- 假全：**不该有的装作有**（未知的东西写成了已知）

⇒ **假全比空更危险**——空看一眼就知道，假全要用到才发现。

ⓘ 与 [`../audit/self-verification-credibility.md`](../audit/self-verification-credibility.md)
第二十条一致：待核对要**条目化**，且每条写**怎么验证**。
本条补的是另一半：**一份文档连待核对项都没有，本身就是可疑信号**。

---

## 九、自检（30 秒）

- [ ] 判"空不空"时，我是不是先看了行数/条数/章节数？（⛔ 这些都不是充实度）
- [ ] 三个真实场景，只看这个模块能不能决策？
- [ ] 结论标了【实测】吗？还是想当然？
- [ ] 排除条件写了没？（只有命中条件的判据必然误报）
- [ ] 有没有**第二层**——别人想不到的那层？
- [ ] 体量跟这个域的复杂度匹配吗（注水 / 欠写）？
- [ ] 有没有把「精简但充实」误判成「空」而注水？
- [ ] 超限的分清是**成本问题**（该拆）还是**充实度问题**（该补）？
