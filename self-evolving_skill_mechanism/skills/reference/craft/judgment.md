# 尺度与取舍

> **本区性质：craft / 品位与技巧。**
> 讲「多少算够、冲突时选哪个、什么时候该停」。
> 什么算好见 [`taste.md`](taste.md)；具体手法见 [`techniques.md`](techniques.md)。
> ⓘ 尺度判据与 [EC-04](../common/blocks.md#ec-04-陌生人测试) 配套：
> 陌生人测试判「能不能照做」，本文件判「做到什么程度该停」。

---

## 一、为什么单独一层

`howto/` 教你**怎么做完**，`audit/` 告诉你**哪里不行**，
`taste.md` 告诉你**什么算好**——但三者都回答不了一个问题：

```
两个都对的东西冲突时，选哪个？做到什么程度该停？
```

这不是"怎么做"的问题，也不是"对不对"的问题，
是**程度**的问题。没有这一层，会出现两种典型偏差：

| 偏差 | 表现 | 来源 |
|---|---|---|
| **过度** | 每条规则都配三件套、样例、反例，写到没人读 | 把"写全"理解成"无上限" |
| **不足** | 一句"要注意 X"就当写过了 | 把"精简"理解成"不展开" |

ⓘ **本层是「好」与「对」之间的校准器**：
`taste.md` 定标准，本文定**度**。

---

## 二、总判据：**改一个字会怎样**

拿不准"多少算够"时问一句：

> **再改一个字，读它的人会做出不同的决定吗？**

| 答案 | 结论 |
|---|---|
| 会 | 还**没写够**，继续 |
| 不会 | 已经**够了**，停 |

⛔ 不要用"字多不多"判断——**长不等于啰嗦，短不等于精炼**。
一段 200 字的排查步骤可能是精确的；
一句"检查边界条件"可能是废话。

**判据是「信息量」，不是「字数」。**

## 三、四组常见冲突（没有标准答案，只有取舍原则）

### ① 写全 vs 精简

用户偏好 F002 明确「宁可写全写详细，不要为精简牺牲完整性」。
但**写全不是无限写**——它的边界是：

```
⛔ 不该省的：来源、证据、后果、判据、反例
✅ 该省的：同义复述、客套、把判据换个说法再说一遍
```

⚠ **最常见的"伪写全"**：同一条判据在正文、表格、自检清单里各写一遍。
三处一旦不同步，读的人不知道该信哪个——**这比只写一遍更糟**。

**判据：三处里有一处改了，另外两处会自动跟着改吗？**
不会 → 说明它们本该是一处（留指针）。

### ② 拆分 vs 合并

| 拆 | 合 |
|---|---|
| 各部分**独立可查** | 必须**整体对照**才有用 |
| 单独加载能读懂 | 拆了要来回翻 |
| 更新频率不同 | 总是一起改 |

**判据：能不能举出"只读其中一份就够了"的场景？**
能 → 拆；不能 → 合。

⚠ **为了指标拆是最常见的错**：文件超限就机械地切成两半，
结果两半都读不完整。**拆分的目的是"按需加载"，不是"降低行数"**。

### ③ 自动化 vs 人工

能自动查的一定要自动查（`self-verification` 第十九条）。
但**不是所有判据都能自动化**：

| 能自动查 | 不能（至少暂时不能） |
|---|---|
| 死链、重复、字段缺失、ID 冲突 | 「这条判据写得对不对」 |
| 格式违规、体积超限 | 「这个分类合不合理」 |

⛔ **不要为了"全自动化"把不能自动查的判据硬写成能查的**——
硬写的判据必然误报，而**误报的检查会被关掉**。

**判据：这条判据误报的代价多大？** 大到无法接受 → 留人工，标清楚。

### ④ 现在做 vs 记下来

| 现在做 | 记 backlog |
|---|---|
| **静默**失效（假绿 / 漏报 / 覆盖） | 可见的瑕疵 |
| 会导致**错误决策** | 只是不好用 |
| 影响**已入库内容**的正确性 | 只影响效率 |

⚠ **排序错了的代价**：先修"不好用"而放着"假绿"不管，
等于把工具打磨得很好用，只是它**一直在说谎**。

## 四、什么时候该停（四条）

**① 陌生人能照做** —— [`taste.md`](taste.md) 的总判据（统一表述见 [EC-04](../common/blocks.md#ec-04-陌生人测试)），达到了就停。

**② 反面用例写出来了** —— 能说清"什么情况会失效"，
说明你真的理解了这条规则；说不出 → 还没想透，继续想不是继续写。

**③ 自检清单能列出** —— 列不出"我怎么知道做对了"，
说明这条规则本身不可验证。**不可验证的规则不该入库**。

**④ 再写就是换个说法重复** —— 立刻停。
重复不会增加说服力，只会**增加不同步的风险**。

## 五、过度与不足的信号

| 信号 | 说明 |
|---|---|
| 一份文档三年没人动，但每次都要读 | **过度**：它已经变成了仪式 |
| 有人照做还是做错 | **不足**：缺了关键一步，不是"他没认真" |
| 自检清单全是"检查有没有…" | **不足**：只有动作没有判据 |
| 同一条改了三次还在改 | **过度或不足**：先判是哪种，别一直微调 |

⚠ **"有人照做还是做错"是不足的最强信号**——
不要归因为执行者的问题。判据写对了，陌生人就该能做对（[EC-04](../common/blocks.md#ec-04-陌生人测试)）。

## 六、分层推进：顺序不能颠倒，跳层不是加速

反哺自打磨四层模型。**四层的验收顺序是固定的**：

```
① 能用（功能） → ② 知道发生了什么（反馈）
              → ③ 有层次（润色） → ④ 超出预期（惊喜）
```

| 层 | 状态 | 读的人感受 | ⛔ 跳层的后果 |
|---|---|---|---|
| **1 功能** | 能做这件事 | "能用" | — |
| **2 反馈** | 做了有反应 | "知道发生了什么" | ⛔ 跳过反馈直接润色 = **好看但不知道自己在干嘛** |
| **3 润色** | 反应有层次 | "做得挺细" | — |
| **4 惊喜** | 超出预期一点 | "这个有想法" | ⛔ 功能没做完就加惊喜 = **华而不实** |

### ⛔ 最常见的错是在第 1 层没做完时做第 4 层

表现为：有漂亮的结构和措辞，但基础判据有错——评语会是"华而不实"。

判据：**下一层的人用得了吗？**
第 1 层没做完时，第 4 层做的东西**建立在一个会变的基础上**，返工概率极高。

### ⚠ 每层的停止条件不同

反哺自分层终止条件：

| 层 | 停的信号 |
|---|---|
| 反馈层 | **每个操作都有回应** → 停 |
| 润色层 | **没有重复感、有层次** → 停 |
| 惊喜层 | **每个模块 1–2 个** → 停 |

⇒ ⛔ 用一个统一标准（比如"写够 N 行"）卡所有层，
会让反馈层注水、惊喜层永远不敢加。

### ⛔ 顺序错了不只是浪费，还会**放大问题**

反哺自「打磨不是万能的」：

> **功能有 bug 的时候，打磨会让 bug 更明显。**
>
> ⛔ 典型错误顺序：手感不好 → 于是加顿帧、加屏震、加粒子
> → 结果"手感差"变成了"手感差且很吵"。

⇒ 补救措施**放大**了它想掩盖的问题：原本只是一个缺陷，
现在是一个缺陷**加上一层显眼的装饰**。

**抽象到写文档**：

| 原本的问题 | 错误的补救 | 结果 |
|---|---|---|
| 判据不准 | 加更多判据 | 不准 + 更长，且更难定位哪条不准 |
| 概念没讲清 | 加更多例子 | 讲清的部分被例子淹没 |
| 结构混乱 | 加目录与索引 | 混乱 + 一层过期的索引 |
| 章节缺失 | 先排版式 | 排版好了，空的还是空的 |

判据：**关掉所有"装饰"，它还能用且清楚吗？**
（对应产品侧的"关掉所有特效，游戏还能玩且清楚吗"）

⚠ 与第一节「再改一个字会怎样」的关系：那条判**够不够**，
本条判**顺序对不对**——顺序错时，加多少都不够，且越加越糟。

### ⚠ 判据有适用范围——这条判据本身就是例子

> 「读的人**主动提到**的打磨 = 有效的；没提到 = 可能是自嗨。」
>
> ⛔ **但反馈层是例外**：好的反馈是"感觉不到存在"的，
> **读的人永远不会提**。所以这条判据**只适用于惊喜层**。

ⓘ 值得单列：这是一条**带适用范围的判据**。
写判据时不写适用范围，会被套到它不该管的地方（falsepos 第十四条的近亲）。

## 七、自检（30 秒）

- [ ] 再改一个字，读的人会做出不同决定吗？（不会 = 够了）
- [ ] 有没有同一条判据在三处各写一遍的"伪写全"？
- [ ] 拆分是为了**按需加载**还是为了**降低行数**？
- [ ] 不能自动查的判据，有没有为了自动化而硬写？
- [ ] 排序对吗——先修**静默**失效，还是先修"不好用"？
- [ ] 有人照做还是做错时，我有没有先怀疑判据不足？
- [ ] 当前在第几层？有没有在第 1 层没做完时做第 4 层？
- [ ] 停止条件是**这一层**的吗？（⛔ 别用统一行数卡所有层）
- [ ] 有没有在「还没能用」时先加装饰？（⛔ 会放大问题）
- [ ] 横评八个维度，**最差的那个**是哪个？（⛔ 别看平均分）
