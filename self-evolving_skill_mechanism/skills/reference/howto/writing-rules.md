# 条目写法规范

> **本区性质：howto / 怎么做）。**
> 写 / 改 / 生成技能时读；审核与提优化建议时请读审查册——
> 两册分工见 `split-two-books.md`。


> 一句话总纲：**只写该怎么做，不写犯过什么错、不写发生过什么。**

## 第一问：这条写进 reference/ 的哪个区？

**落笔前先定区，写错区的内容等于白写**——
放在 howto 的审核判据不会在审核时被读到，
放在 audit 的操作步骤不会在建设时被读到。

| 区 | 装什么 | 动词判据 |
|---|---|---|
| `howto/` | 具体怎么做 | 「应该…」「先做…再…」 |
| `audit/` | 不能怎么做 | 「不要…」「会失效如果…」 |
| `flow/` | 端到端流程 | 「第一步…第二步…」 |
| `common/` | 元规则、共用约定 | 「本文讲…」 |
| `craft/` | 品位与技巧 | 「好的…应该…」「判断标准是…」 |

**六种易混边界**（完整版见 `../common/split-two-books.md` 第三节）：

1. **排除条件属 `audit/`**，不属 `howto/`——混进 howto 会让判据越写越长
2. **「为什么」两区都要**，但 howto 给执行者（不做的后果）、audit 给排查者（怎么失效）
3. **驳回清单属 `audit/`**——整合时跳转，不抄回流程
4. **`craft/` ≠ `howto/`**：howto 是"做完"，craft 是"做好"
5. **`craft/` ≠ `audit/`**：audit 是下限（不许坏），craft 是上限（要好）
6. **`flow/` ≠ `howto/`**：flow 是走完一件事，howto 是解决一个问题

> **只有 howto 和 audit 会停在「做完、没毛病」，不知道「好」长什么样。**
> 写完自问：这条是教人做完，还是教人做好？后者进 `craft/`。

## 唯一允许的例外：⚠ 反直觉标记

少数规则如果不点破本能反应，下次还会踩。这类用 ⚠ 开头，且**只写必须做什么**：

```
✅ ⚠ 本能会想 X，但必须 Y
❌ 上次我做了 X，结果错了，后来改成 Y 才好
```

⚠ 条目占全库比例应 < 20%。超过说明你其实在写错题集。

## 对照表

| 场景 | ❌ 这么写 | ✅ 这么写 |
|---|---|---|
| 改文件 | 上次直接覆写把用户内容冲掉了 | 修改已有文件前先 read 原文件 |
| 交付 | 上次返回了一堆路径被说乱 | 产物 ≥5 个先打包 zip，只返一个路径 |
| 格式 | 上次格式没对齐 | 表格列宽对齐，二级标题下空一行 |
| 通用性 | 改 A 项目配置时要备份 | 改任何配置文件前先备份 |
| 判据 | 要认真检查 | 提交前逐项核对：路径 / 编码 / 依赖 |
| 命令 | 可以用 python 处理 | `python3 -m json.tool < in.json` |
| **事实** | 配置文件在 `/etc/nginx.conf` | 找配置文件用 `rg --files -g '*.conf'` |
| **事实** | 这次交付 8 个文件 | 产物 ≥5 个打包 zip，只返一个路径 |
| **事实** | 用户要蓝色 | 品牌色 / 主色向用户确认后再用 |

**规律**：把"上次 / 错了 / 结果"这类时间状语和负面词全删掉，剩下的就是正确做法；
再把剩下的**具体路径、文件名、项目名换成通用描述或占位符**，就得到了可迁移的技能。

## 措辞检查（落笔前 10 秒）

- [ ] 有没有"上次 / 之前 / 错了 / 失败 / 不行 / 被说"？有 → 删掉重写
- [ ] **有没有具体路径 / 文件名 / 项目名 / 一次性数据？** 有 → 抽象或删除
- [ ] 没参与过这个项目的 AI 能看懂并用上吗？
- [ ] 主语是不是动作本身而不是事件？
- [ ] 能不能再抽象一层？（换了个项目还成立吗）
- [ ] 有没有写进可执行的命令？能写就写
- [ ] **它落在哪个流程的第几步？** 指不出来 → 孤立知识点，不写或改写
      （见 `knowledge-landing.md`；`lint.py` 会自动报）
- [ ] **有判据吗？** 「要注意 X」必须给出「怎么算做到了」

## 自由度匹配：给多少「自己看着办」的空间

反哺自 Agent Skills 官方规范（Degrees of Freedom）。
**按任务的脆弱度决定指令的具体程度**——不是越细越好，也不是越粗越好。

| 自由度 | 适用 | 写法 |
|---|---|---|
| **高** | 多种做法都成立、决定依赖具体情境（如代码审查怎么写评语） | 文本指令，讲清判据与目标 |
| **中** | 有首选模式但允许变通（如报告格式、流程骨架） | 伪代码 / 带参数的脚本 / 模板 |
| **低** | 脆弱易错、一致性是关键（如数据迁移、文档补丁、ID 分配） | 具体脚本、少参数、逐步清单 |

判据一句话：**走错一步的代价越大，给的自由越少。**

```
窄桥两侧是悬崖 → 需要护栏（低自由度）
开阔场地       → 允许多条路线（高自由度）
```

⚠ 两种常见错配：

| 错配 | 后果 |
|---|---|
| **该低却给高**（脆弱操作只写"注意备份"） | 每次做法不同 → **结果不可复现**，出错无法定位 |
| **该高却给低**（创造性任务写死脚本） | 遇到没预见的情况就卡死，而**脚本不知道自己该不该变通** |

⛔ **不要为了"显得严谨"把所有东西都写成低自由度**——
那会让技能变成一堆死步骤，遇到边界就失效。

ⓘ 与「四道门槛」的关系：可执行 ∧ 已验证 决定能不能入库，
**自由度决定入进来之后怎么写**——两道不同的关。

## 各库写法要点

| 库 | 重点 | 常见毛病 |
|---|---|---|
| `_hot.md` | 触发场景 + 动作，一句话说完 | 把领域专属规则塞进热区 |
| `domains/*.md` | 完整流程 + 判断依据 + 变体 | 为了精简砍掉细节 |
| 领域包「流程」段 | 每步带判据和命令 | 只写空泛的动作描述 |
| 领域包「注意事项」段 | **每条都要能指回流程某一步** | 写成孤立的正确废话 |
| `_preferences.md` | 用户要什么，具体到可执行 | 写成"用户喜欢高质量" |
| `_commands.md` | 可直接复制，变量显眼 | 写伪代码 / 省略关键参数 |

## 知识点必须落地（与「命令化」是两道关）

「操作命令化」管**动作怎么表达**；「落地」管**知识有没有改变行为**。
一条可以命令化得很好却仍然孤立——流程里没有任何一步会走到它。

| 强度 | 形式 | 合格？ |
|---|---|---|
| ★★★ | 脚本自动查（`lint.py`） | ✅ |
| ★★☆ | 流程某一步的判据 | ✅ |
| ★☆☆ | 可判定的检查项 | ⚠ 必须挂到流程步骤上 |
| ☆☆☆ | 「要注意 X」无判据 | ❌ |

写完跑 `python3 scripts/lint.py`，孤立知识点会被逐条报出。
完整协议（四问、反例、反向检索命令）见 `knowledge-landing.md`。

## 长度红线

ⓘ **行数是成本，不是充实度**。判「这个模块空不空」不看数量与行数，
看八个维度（覆盖面 / 规则完善 / 流程规整 / 原理透彻 / 逻辑严密 /
推导真实 / 深度 / 体量匹配）——见
[`../craft/substance.md#八个维度`](../craft/substance.md)，
以及 [`../craft/substance.md#八维度都及格`](../craft/substance.md)
（⛔ 八维度都覆盖 ≠ 充实：整体被**最差的**那块拉低）。

- 单条目 ≤ 一行表格（命令类可例外）
- 条目型库（`_hot.md` / `_commands.md`）单文件 ≤ 40 条
- `SKILL.md` 主文件 ≤ 120 行，超了就往 `reference/` 挪
- **领域包没有上限** —— 写全写详细（见 F002），靠分层解决占用问题

## 领域包写法（与条目型库不同）

领域包是**文档**，八段式结构，不追求精简：

| 段落 | 必写 | 要点 |
|---|---|---|
| frontmatter | 是 | `keywords` 写全同义词；`applies_to` 标环境；`verified` 标是否实测过 |
| 适用场景 | 是 | **必须写「不适用」**，边界比正例重要 |
| **前置依赖** | 是 | 需要什么工具/包 + 安装命令 + 不满足时怎么办 |
| 完整流程 | 是 | 分步骤，**每步精确到可判定**，带命令 |
| **失败处理** | 是 | 每步的失败判据 + 失败后动作（重试/降级/中止询问） |
| 关键判断依据 | 是 | 写「为什么这么定」，否则 AI 遇变体就瞎改 |
| 已知坑 | 是 | ⚠ 格式：本能会想 X，但必须 Y |
| 变体 | 是 | 真实任务总有意外，列成表格 |
| 可复用片段 | 建议 | 骨架 / 模板，可直接复制改 |

### `verified` 字段：只标注，不校验

```yaml
verified: yes     # 这条我真跑过 / 实测过
verified: no      # 从文档或推理得来，没实测
verified: partial # 部分步骤验证过
```

**它只是一个标注，不做任何自动校验**——不因为标了 `no` 就拒绝加载，
也不因为标了 `yes` 就免检。作用是**回溯时知道该信几分**：

- 标 `no` 的条目出错 → 优先怀疑它，而不是怀疑流程
- 标 `yes` 的条目出错 → 检查是不是环境变了（见 `versioning.md`）

`python3 scripts/lint.py` 会列出未标注的条目，纯提示，不影响使用。

**但标注本身会退化。** 手填的字段既没有填错的成本，也没有填对的反馈，
于是会自然收敛到同一个值（全 `no`、命中全 0）。表面「标注齐全」，
实际读的人还是得逐个怀疑——**字段活着，但已经死了**。

所以：

- **能实测的 → 脚本跑完自动回填**，别手填
- **填不了的 → 至少能发现退化**：条目数 ≥ 阈值且取值只有一种 → `lint.py` 预警
- 退化预警**不是要求标 yes**，而是要求**有区分度**

完整机制（三态返回值、正反双样本、扫描范围自报）见
`reference/audit/self-verification.md`。

ⓘ **正反双样本的统一判据**见 [EC-02](../common/blocks.md#ec-02-正反双样本缺反侧等于没验证)——缺反侧的用例是恒绿但无效的用例。

### 变更溯源：改动要留痕

改了技能就在 `assets/changelog.md` 记一行，别靠记忆：

```bash
python3 scripts/note.py "LAW-R003" 补充 "合同审查漏了违约金条款" --domain legal
python3 scripts/note.py "C047" 更新 "macOS sed 需空参数" --src "实测"
```

**为什么值得记**：半年后看到一条规则，没人记得它怎么来的、为什么这么写。
一行记录能回答这两个问题。类型：新增 / 补充 / 修正 / 更新 / 参考 / 合并 / 拆分 / 冷藏。

### 单文件体积上限

超过就该拆（`python3 scripts/lint.py` 会预警，不硬报错）：

| 文件 | 上限 | 超了怎么办 |
|---|---|---|
| `rules/*.md` | 50 行 | 混进了流程 → 移到 `skills/` |
| `agents/*.md` | 100 行 | 按场景拆角色 |
| `SKILL.md` | 200 行 | 细节下沉 `reference/` |
| `assets/*.md` | 300 行 | 按年/季度归档 |
| `reference/*.md` | 400 行 | 按主题拆 |
| `skills/*.md` | 500 行 | 按子任务拆包，`related` 互链 |

**`rules/` 的 50 行最要紧**：它每次任务都要读，
混进流程会让「必读」变成「读不完」，等于没有约束。

### 体积豁免：超限但有理由

用户偏好 F002 是「宁可写全写详细，不要为精简牺牲完整性」，
与体积预警直接冲突。没有豁免机制时，为了消掉预警去砍内容，
**等于为了指标牺牲质量**。

确有理由不拆时，在文件头声明：

```markdown
<!-- oversize-exempt: 确认候选时需整体对照本包全部判据 -->
```

`lint.py` 识别后**降为提示**，并把理由一并输出（理由也要能被复核）。
**强制写理由**是为了防止豁免被滥用成「不想拆就标一下」。

#### 豁免的边界：常驻层不豁免

**只有按需加载的层（ `reference/` · `skills/` ）能豁免；
每次必读的常驻层（ `SKILL.md` · `rules/` ）不能。**

判据很简单：常驻层超限，**占的上下文是实打实每次都付的**——
再充分的理由也不能让它不占。而按需层超限，代价只在真读到它时才发生，
「需要整体对照」这类理由是成立的。

所以：主文件超限 → **只能下沉内容**，没有第二条路。

#### 下沉的配套检查：孤儿判定要跟着搬

内容下沉到 `reference/` 后，引用关系随内容一起走了。
若孤儿检查只扫主文件，那些「只在子文档里被提到」的脚本/资源
会被全部判成孤儿：

```
命令段下沉到 references/commands.md
  → 其中引用的 14 个脚本在 SKILL.md 里不再出现
  → 全部报「孤儿文件」
  → 为了消掉告警，只能把命令搬回主文件
  → 与「细节下沉」直接冲突，体积治理自我推翻
```

**判据：检查项的判定范围必须与内容的组织方式匹配。**
孤儿检查应扫 `SKILL.md` + `references/*.md` + `assets/*.md` 全部文档，
而不是只扫主文件。

这条是通用的：**凡是加了「下沉/拆分」机制，就要同步检查
配套的引用类检查是否还在只扫主文件**，否则机制会互相打架。

### 操作必须命令化（硬性要求）

**凡是能写成命令或脚本的操作，一律写成命令，不用散文描述。**

三个理由，缺一不可：
- **省思考时间**：照着跑就行，不用每次现想
- **省上下文**：一行命令比一段描述短
- **保证一致**：手写容易走样，命令每次执行结果相同

| ❌ 散文描述 | ✅ 命令化 |
|---|---|
| 先把原文件备份，再批量替换内容 | `cp X X.bak && sed -i 's/旧/新/g' X` |
| 检查一下各库条目数，超过 40 要合并 | `grep -c '^\| [A-Z][0-9]' SKILLS/*.md` |
| 改动后记得重建索引 | `python3 scripts/index.py` |
| 加了新的检查项 | 同步加 `--self-test` 坏样例，确认它真能红 |
| 判定某描述归属哪个大类 | `python3 scripts/structure.py --route-check "<描述>"` |

**三条细则**：
1. **单行能搞定** → 直接给命令，标注 `applies_to`（`os:linux` / `python>=3.9`）
2. **多行逻辑** → 封成 `scripts/` 下的脚本，技能里**只留一行调用**
3. **命令必须可直接复制**，只改变量，不留待填空的伪代码

**自检方法**：技能里如果出现「先…然后…再…」「检查一下…」「记得…」这类句式，
说明还在用散文描述操作——该抽成命令或脚本了。

### 步骤精确性（最常犯）

| ❌ 模糊 | ✅ 可判定 |
|---|---|
| 检查 id 是否有效 | 检查 id 是否为 6 位字符串 |
| 注意格式 | 表格列宽对齐，二级标题下空一行 |
| 适当处理异常 | 文件不存在时提示用户并给出创建命令 |

判据：不熟悉该领域的 AI 照着做，能明确知道"这步做没做对"吗？

### 执行意图：Run 还是 See

引用脚本必须说清是**执行**还是**参考阅读**：

```
✅ 运行 analyze_form.py 提取字段      （执行）
✅ 提取算法参见 analyze_form.py        （参考）
❌ 使用 analyze_form.py                （意图不明 → AI 可能去读该运行的脚本）
```

### description 规范（决定 AI 会不会选中它）

- **第三人称**："处理 X 并生成 Y"，不是"我能帮你处理 X"
- **同时写「做什么」+「何时用」**
- **嵌入用户可能说的同义词**

```yaml
# ✅
description: 分析 Excel 表格、创建透视表、生成图表。当用户提到 Excel、电子表格、表格数据或 .xlsx 文件时使用。
# ❌
description: 帮助处理文档
```

**质量标准**：陌生 AI 只看这一个文件，能独立完成该类任务。
写的时候假设读者看不到对话历史、对你的项目一无所知。

细节参见 `SKILLS/domains/skill-authoring.md`（编写 skill 的 skill，自举）。
