# 路由信号：确定性扫描 vs 关键词匹配

> **本区性质：howto / 怎么做。**
> 讲「怎么把一个任务路由到正确的技能包」。
> 本规范提炼自 code-audit 的 `route.py`（**二次路由**，实测结构）。

---

## 一、核心判据：事实 vs 猜测

```
⛔ AI 靠「这项目像有插件」是猜
✅ 脚本扫到 plugins/ 是事实
```

**关键词匹配**（`index.py --find`）的本质是：拿输入文本去比对预先写好的 `keywords`。
它有两个先天缺陷：

| 缺陷 | 后果 |
|---|---|
| **keywords 是人写的** | 写窄了召不回，写宽了到处误命中 |
| **输入文本未必含那个词** | 用户说"这个插件加载不了"，库里写的是"沙箱" → 判 0 命中 |

**确定性扫描**不依赖输入措辞——它扫**对象本身**（目录 / 文件 / 构建配置 / 代码正则），
机械扫一遍不会漏。

ⓘ **不是替代，是分工**：

| 场景 | 用哪种 |
|---|---|
| 检索「库里有没有这个」 | 关键词匹配（`index.py --find`） |
| 判定「这个对象属于哪一类」 | **确定性扫描**（本规范） |

⚠ 只用关键词做归属判定，是**"查不到就新建"**的主要成因——
见 `flow/new-skill.md` 第 0 问。

## 二、信号三级分级（置信度）

```
[结构]  目录 / 文件 / 构建配置      —— 几乎不会错，直接采信
[特征]  正则命中代码                —— 有命中即相关，但要看密度
[文档]  README / 配置里的关键词      —— 弱信号，仅作提示
```

**为什么必须分级**：不分级的话，`README 里提到 Godot` 和
`存在 project.godot 文件` 会被当成同等证据，
而后者几乎不可能误判，前者可能是"打算支持 Godot"的空话。

**用法**：
- 输出时**带上信号类型**，让审核的人知道该信几分
- 只命中[文档]的不算归属 → **提示，不采信**
- [特征] 要看**密度**（命中 1 次 vs 12 次是两回事）

## 三、信号类型（四种）

| 类型 | 判据 | 例 |
|---|---|---|
| `dir` | 存在某目录 | `plugins/` `src-tauri/` `.github/` |
| `file` | 存在某文件（支持通配） | `project.godot` `Cargo.toml` `vite.config.*` |
| `ext` | 存在某扩展名的文件 | `.gd` `.rs` `.py` |
| `rx` | 正则命中代码 | `\.unwrap\s*\(` |

**四类覆盖两个维度**：`dir`/`file`/`ext` 看**长相**（几乎不会错），
`rx` 看**内容**（有命中即相关）。

⚠ **`ext` 漏一个就会整类漏判**——而且**表现为 0 命中**：

> 实测：`.gd`（GDScript）早先漏了 → Godot 项目里扫到 0 个文件 →
> 输出「未命中任何场景」，看起来像"这个项目没什么可审的"，
> 实际是**路由压根没看 GDScript**。

**判据：新增一种受支持的对象类型时，先确认路由认得它。**
这与「扫描器不认某语言输出 0 命中」是同一类失效
（见 `audit/self-verification-silent.md` 第十八条）。

## 四、两级路由（二次路由）

**这是 code-audit 结构里最值得学的一点。**

```
第一级：风险面（横切）    s-numerics / s-lifecycle / s-sandbox / s-build …
第二级：语言平台（纵切）  p-python / p-go / p-java / p-cpp / p-rust
                         p-cocos / p-godot
```

**为什么必须两级**：一个 Python 项目既有「生命周期泄漏」也有「可变默认参数」，
前者是**横切风险**（任何语言都有），后者是**语言特有**。
只分一级的话：

- 只按语言分 → 横切风险要在每个语言包里**各写一遍**，必然漂移
- 只按风险分 → 语言特有缺陷无处安放

ⓘ **判据：这条会随语言变，还是不随语言变？**
不随 → 风险面（`s-`）；随 → 语言包（`p-`）。

**两级都要路由，结果取并集**——一个项目同时命中 `s-lifecycle` + `p-python` 是正常的。

## 五、不设命中上限，改分批

```
⛔ 命中 4 个就截断输出   → 大项目命中 10+ 是正常的，截断会漏检
✅ 分批：一批审完再加载下一批
```

**截断是最隐蔽的漏检**：输出看起来很完整（"命中 4 个"），
没人知道第 5 个被截掉了。

**判据：命中数超限时，是"分批"还是"截断"？**
分批保证不漏且每批读得深；截断是**静默少做**。

## 六、路由结果 → 具体条目（特征过滤）

路由到场景后，不该整列该场景的全部条目：

```
⛔ 一个场景 12~19 条，全列出来 = 整文件读，条目级索引白做了
✅ 用路由命中的**特征名**去筛条目
```

实测教训（三个连续的坑）：

| 坑 | 后果 |
|---|---|
| 把 `keywords` 也算进匹配字段 | keywords 里全是 `loop`/`size` 这类通用词，**等于没筛**，命中 13 条 |
| 特征名带 `×N` 计数后缀没剥 | 拿 `clamp×3` 去匹配，**一条都对不上** → 静默回退"全 P0" |
| 只用四个字段（判据/特征/典型/正确） | 其余字段太泛，筛完仍是一大把 |

**匹配字段只有四个**：`判据` / `特征` / `典型` / `正确`。

**筛不出来时怎么办**：⛔ 不瞎猜——给 P0 做**起步集**，并说明"特征对不上"。
⚠ 没有特征信号时（只有结构命中，如 `package.json`）也走 P0 起步集，
跟"特征对不上"同一处理。

## 七、索引缺失不报错

```
索引（items.json）读不出来 → 路由照常工作，只是不输出条目建议
```

⛔ **不因缺索引而报错退出** —— 路由的价值在于"判定归哪类"，
条目建议是**附加**。缺了附加功能就让主功能失效，是把增强当成了依赖。

⚠ 但要**说一声**——否则用户以为"没有条目建议 = 这个场景没有条目"。
判据：降级时要可见（见 `audit/self-verification-silent.md` 第九条）。

## 八、场景 → 执行器映射

```
有专用扫描器的场景，不必整列条目 —— 直接指向扫描器
```

```python
SCENE_SCANNER = {
    's-numerics': 'scan-ts.py',
    'p-python':   'scan-py.py',
    'p-godot':    'godot-audit.py',
}
```

**为什么**：整列条目让人自己看，指向扫描器是**机器直接出结果**。
能机器做的不要让人做。

⚠ **映射表必须自动推导或从单一来源生成**——
手写名单漏一个，那个场景就"能路由到但没人执行"，
**表现为该场景 0 命中**。这个坑在本仓库踩过六次。
