# 整合的规则库（判据与标准）

> **本区性质：howto / 怎么做。**
> 本文件是**被 `flow/consolidation.md` 的【读】引用的细节库**，
> 不是流程本身——要"按什么顺序做"请读 `../flow/consolidation.md`。

ⓘ **为什么单独拆出来**：流程文件应该只讲"按什么顺序做"，
判定标准（`四道门槛`、`归位决策`、`ID 规范`…）是**查的东西**，
不是**走的东西**。混在一起会让流程文件越来越长，
而每次整合其实只需要按顺序走 + 在特定步查特定标准。

判据：**它是"走完一件事"，还是"解决一个判定问题"？**
后者都在本文件（见 `../common/split-two-books.md` 3.6）。

---

## 整合之后：回看建设册

整合完成不等于闭环。审查报出的每条问题，都要回看建设册三问
（流程够细？内容有疏漏？脚本严谨？）——
**只审查不回看，同一失效会反复报，而建设册始终缺那一句**。
协议见 `closed-loop.md`。

## 驳回清单 → 见 `rejection.md`

整合时若发现条目该驳回，去 `reference/audit/rejection.md` 对照
（本册只讲**怎么做**，驳回属于「不能怎么做」，已拆到审查册）。

## 入库三件套（缺一不可）

| 件 | 内容 |
|---|---|
| **来源** | 哪次任务、什么信号捕获的（`note.py --src`） |
| **证据** | 实测输出，或可验证的推导链 |
| **后果** | 不这么做会怎样 |

**判据：说不出「不这么做会怎样」的，通常不是真技能。**
这跟审查技能里「说不出后果的问题不成立」是同一条——
想不出后果，意味着要么它不是真问题，要么还没想清楚。

## 批量相似条目：抽样，不逐条

一次会话捕获了 N 条相似草稿时，**不要逐条入库**。

```
① 抽样确认 3~5 条
② 性质一致 → 合并成一条通用条目，只入一条
③ 性质不一致 → 才逐条入
```

逐条入几十条同质内容，会把真正重要的那条淹掉，
也让「同一个坑在库里变成三条」——正是整合要避免的。

`consolidate.py` 会用 `▸ 草稿之间重复 N 组` 标出这批，先合并再入库。

## 整合量分档

| 草稿量 | 策略 |
|---|---|
| **< 5 条** | 一次过完，逐条过门槛 |
| **5~20 条** | 先分诊丢弃（第零道闸一轮带走大半），再按归属分组批量处理 |
| **> 20 条** | **先处理跨领域通用的（地基），再处理领域专属的** |

**地基优先的理由**：跨领域条目会影响多个领域的后续归类。
先定通用层，领域条目归属时才不会摇摆——这与审查技能「地基模块先审，
它的结论会推翻上层判断」是同一个道理。

## 长会话：分段整合，别攒到最后

「不要边干活边写库」（避免碎片化）与「审完立刻写结论，攒着会丢细节」
看起来矛盾，实际是**量化问题**：

| 情形 | 做法 |
|---|---|
| 短会话（捕获 < 5 条） | 会话结束统一整合 |
| 长会话（捕获 ≥ 10 条，或跨多个子任务） | **按子任务分段整合**，每段结束过一次闸 |

判据：**细节还热乎时写，损失最小**；
但同时**同一子任务内不要边做边写**（那才会碎片化）。

## 冷热分层的诊断：0 命中到底是哪种

长期 0 命中只有两种可能，处置完全相反：

| 可能 | 判据 | 处置 |
|---|---|---|
| **真低频** | 换同义词检索能召回，只是没用上 | 冷藏保留，命中即回热 |
| **关键词太窄，召不回** | 换同义词仍检索不到 | **补 keywords 同义词** |

区分方法：`python3 scripts/index.py --find <同义词>`，
换两三种说法试。都召不回 → 是关键词问题，不是低频。
**误判成低频就冷藏掉了，等于这条技能永久消失。**

## 正样本：也记「验证过没问题的」

库里只记教训会有个副作用：**没记录 = 看起来没验证过**，
下次同场景又要重新试探一遍。

整合时顺带记一条：本轮哪些做法是**确认可行、值得保留**的。
对应审查技能的 `praise` 标记（写进「验证过没问题的部分」）。

## 改完必须重跑：改 A 引入 B 按最高级

| 改了什么 | 必跑 |
|---|---|
| 改了技能条目 | `python3 scripts/lint.py` + `python3 scripts/index.py --check` |
| 新增/归位了包 | `python3 scripts/index.py`（重建，否则定向加载找不到） |
| 改了大类结构 | `python3 scripts/structure.py --check` |

**比对基线**：改前留一份 `lint.py --json`，改后比对，确认没引入新问题。
整合时顺手改了无关条目而引入的问题（regression），**一律按 L1 处理**——
它比原本那条问题更隐蔽，因为它藏在「我刚刚改过」的信任里。

## 归位决策第二步：放 reference/ 的哪个区？

（第一步是放哪个大类，见下节。本节解决**进了本 skill 之后放哪个区**。）

整合八步的第 6 步「判定归属」实际要做**两次**：

```
① 放哪个大类？      → domain-routing（9 个大类）
② 放 reference/ 哪个区？  → 本节
```

**第 ② 步常被跳过**——因为写的时候知道自己在写什么，
但半年后审核的人不知道该去哪个区找。

| 你要写的这句话… | 进 |
|---|---|
| 遇到 X 情况该怎么做 | `howto/` |
| 什么情况下它不成立 | `audit/` |
| 第一步…第二步… | `flow/` |
| 本文讲…（元规则） | `common/` |
| 好的 X 应该…（判断标准） | `craft/` |

**判定不了时**：默认进 `howto/`（它是主路径），
但**在文首写明「本区性质」**，下次整理时按性质再挪。
`lint.py` 会按区检查，放错的区会在审核时显出来。

## 归位决策：放哪里

| 判据 | 去向 |
|---|---|
| 跨领域通用、每次任务都可能用到 | `SKILLS/_hot.md`（H#） |
| 属于某个任务领域的完整流程 | `SKILLS/domains/<领域>.md`（D#） |
| 领域已存在，只是补充细节 | 追加到该领域包的对应段落 |
| 单个可复用命令 | `SKILLS/_commands.md`（C#） |
| 用户偏好 | `SKILLS/_preferences.md`（F#） |

**新建 vs 追加**：领域包已存在时**优先追加**，不要为了"独立"拆成新包。
只有当一个包超过 ~200 行、且内部能清晰切成两个子任务时，才拆包（用 `related` 互链）。

## 归属判定：写进哪个大类

**四问，从强信号到弱信号**（完整协议见 `reference/howto/domain-routing.md`）：

| 问 | 判据 | 结论 |
|---|---|---|
| 1. 换个大类还成立吗 | 成立 | → `_common` |
| 2. 当前项目接入哪个大类 | `domain.py --detect` | → 该大类（**最强信号**） |
| 3. 关键词命中哪个 | `domain.py --route "<描述>"` | → 推荐候选 |
| 4. 是技能还是知识 | 知识（法条 / API 参数） | → `rules/`，不进 `skills/` |

**推荐 ≠ 自动写入**：置信度不足时向用户确认，归错类比不归更糟。

**补充优先于新建**：目标大类已有同类技能 → 编辑该文件追加段落，不要新建重复包。

**装不下则提结构提案**：若 `--route-check` 返回 `no_match` / `ambiguous`，
说明现有分类不适配 → 走 `reference/howto/structure-evolution.md` 的提案流程，
**不硬塞、不自行新建目录**。

## 第零道闸：技能还是事实

先分诊，再判断。**事实不进后面的流程**，直接丢弃。

| 判据 | 事实（丢） | 技能（留） |
|---|---|---|
| 描述"是什么"还是"怎么做" | 配置在 `/etc/nginx.conf` | 改配置前先备份 |
| 换个项目还成立吗 | 这次交付 8 个文件 | 产物 ≥5 个打包 zip |
| 需要回想"哪次的事"才懂吗 | 用户 A 项目要蓝色 | 品牌色向用户确认后再用 |

## 四道门槛详解

| 关卡 | 拷问 | 典型淘汰 |
|---|---|---|
| **可迁移** | 换个项目还成立吗 | "这次 JSON 少个逗号" |
| **已抽象** | 是模式还是个案 | 把"改 A 文件报错"抽象成"改配置前先备份" |
| **可执行** | 能照着做吗 | "要更认真一点" ❌ |
| **已验证** | 真跑通过吗 | 凭空想象的"感觉应该" |

**抽象三段式**：具体事件 → 场景模式 → 通用原则。能升到原则层的绝不留在事件层。

## 强度分级

- **L1 铁律**：违反必出事故。任务前必扫
- **L2 强建议**：大概率正确，有反例时可绕开
- **L3 提示**：锦上添花的优化

## ID 规范

| 前缀 | 位置 | 示例 |
|---|---|---|
| H | `_hot.md` 热区 | H007 |
| D | `domains/*.md` 领域包 | D003 |
| C | `_commands.md` 命令 | C019 |
| F | `_preferences.md` 偏好 | F004 |

**ID 一经分配永久保留，永不复用**（避免旧引用指向新内容）。

## 冷热分层（替代删除）

**不删除任何技能。** 命中数决定**加载优先级**，不决定存亡。

| 层 | 判据 | 加载方式 |
|---|---|---|
| 🔥 `hot` | 命中高 / 跨领域通用 | 任务前必扫 |
| ❄️ `cold` | 有命中但低频，或新入库 | 索引命中时加载 |
| 🧊 `archive` | 长期 0 命中（>90 天） | 仅存索引，命中即回热 |

**冷藏操作**：把文件移到 `SKILLS/archive/`，frontmatter 改 `tier: archive`。
**索引里保留该条目**，下次被检索到时自动回热（`index.py` 已实现）。

### 为什么不用「删除」

| | 删除 | 冷藏 |
|---|---|---|
| 低频但重要的技能 | 误删，下次从零摸索 | 保留，命中即回 |
| 库体积 | 变小，但也变弱 | 变大，但分层后不占上下文 |
| 长期目标 | 库停滞在小规模 | 持续扩充成集群 |

**体积不是问题，加载才是。** 分层 + 索引已经解决了加载成本，
所以没有理由为了省空间牺牲技能积累。

## 静默 vs 确认

默认**写入前确认**。用户可授权静默写入，但任何 L1 条目的新增/修改仍须显式告知——铁律的变动必须让人知道。

## 增长预期（与旧版不同）

旧版目标是"体积增长越来越慢"——**这个目标已作废**。

新版目标：

- **体积持续增长**（这是好事，说明在积累）
- **常驻开销保持稳定**（L0+L1 ≈ 110 行，不随库增长）
- **命中率提升**（库越全，任务越容易命中现成流程）
- **命中分布集中**：常用的那几个稳定在热区，长尾安静待在冷区

**健康信号**：任务开始前经常能命中现成领域包。
**不健康信号**：库很大但总是命中不了 → 说明 keywords 写得太窄，回去补同义词。
