# 捕获信号详解

> 主文件只放了简表。这里解决"这个到底该不该记"的边界问题。

## A 类：自我修正（AI 自身信号）

**明确捕获**
- 说出「不对 / 我错了 / 让我重新想 / 等等 / 实际上 / 应该反过来」
- 同一子任务重试 ≥ 2 次
- 工具调用失败后换方法成功 → 记「可用的那条路」，不记失败那条
- 生成了内容又推翻重写
- 在两三个方案间反复摇摆 → 说明决策依据不清，记下**最终选定的判据**

**不捕获**
- 纯粹的格式/笔误修正（打错字、少个逗号）→ 一次性事件
- 外部原因导致的失败（网络超时、服务不可用）→ 不是能力问题

## B 类：用户纠正（外部信号）

**明确捕获**
- 「不是这样 / 你搞错了 / 应该是 X / 我说的是 Y 不是 Z」
- 用户没否定但重新表述了一遍需求 → 大概率第一次理解偏了，记下**正确理解**
- 用户对结果不满意却说不清哪里不对 → 记下当时输出的特征，做反向归纳

**判据**：用户花力气纠正意味着这个错会再犯。用户随口一提、没坚持的，标 L3 观察。

## C 类：绕路（无错但低效）

- 走了一串步骤后发现更短的等价路径 → 记**短的那条**
- 用错工具绕了一圈才发现有专用工具 → 记「这类任务 → 该用哪个工具」
- 本可一次问清却来回确认多轮 → 记「这类任务开局该问清哪几个维度」

## D 类：偏好（用户习惯）

- 用户**第 2 次**表达同一偏好 → 从"偶然"升级为"稳定偏好"，必须记
- 用户主动夸奖某个输出 → 记该输出的特征（正样本同样重要）
- 用户纠正语气 / 格式 / 详略 → 进 `_preferences.md`

## E 类：明知故犯（元信号）

skill 里已写了的规则，本次仍违反 → **不新增条目**，走「违反即升级」重构那条规则。

反复新增"同一件事的正确做法"是 skill 腐烂最快的路径。

## F 类：可复用命令

- 写出一段通用代码 / 命令行，改改变量就能再用 → 进 `_commands.md`
- 判据：**下半个月还会用第二次吗？** 只用过一次的别记
- 多行逻辑封成 `scripts/` 下的脚本，命令库里只留一行调用
- **技能里出现「先…然后…再…」的散文步骤 → 抽成命令**。
  省思考时间、省上下文、保证每次执行一致。手写容易走样，命令不会。

## 归属判定（捕获时顺手标注）

捕获时同时判断归属，省得整合时再想一遍：

| 信号来源 | 默认归属 |
|---|---|
| 当前项目大类内的任务 | 该项目的大类 |
| 明显跨领域通用 | `_common` |
| 拿不准 | 整合时用 `--route` 判定 |

**领域知识不进技能库**：法条内容、API 参数、疾病特征属于「是什么」，
进 `rules/` 或知识库；`skills/` 只收「怎么用这些知识干活」。

## G 类：结构不适配（元信号）

捕获时发现以下情况，说明**现有分类体系需要调整**——
不要硬塞，走结构提案流程（见 `reference/structure-evolution.md`）：

| 表现 | 含义 | 动作 |
|---|---|---|
| 找不到合适的大类 | 装不下 | `--route-check` 确认 → `--propose-new` |
| 两个大类都能放 | 边界模糊 | 提议中间大类，或拆技能各自归属 |
| 某大类 >40 个技能 | 太臃肿 | 提议建子目录（优先于新建大类） |
| 单包 >200 行 | 该拆 | 提议拆包，`related` 互链 |
| 频繁跨类引用同一技能 | 归类有偏差 | 考虑晋升到 `_common` |

**只提案，不执行**：AI 提 `--propose-new`，用户 `--apply` 后才生效。

## G 类：隐式负反馈（最容易被漏掉）

**用户不会每次都明确说"你错了"。** 更常见的是用行为表达不满：

| 隐性信号 | 含义 | 记什么 |
|---|---|---|
| 用户**重新执行了同一任务** | 上次结果没解决 | 当时输出缺了什么 |
| 用户**换个说法重问** | 上次理解偏了 | 正确的理解角度 |
| 用户**自己动手改了**你的输出 | 输出不达预期 | 差距在哪 |
| 用户**只要了部分结果** | 其余部分无用 | 哪部分该砍 |
| 用户**没采用建议**且无反馈 | 建议不适用 | 什么情况下不适用 |
| 追问"还有别的办法吗" | 当前方案不满意 | 更优路径 |

**为什么重要**：显式纠正只占少数，大量改进机会藏在沉默里。
捕获成本极低（一行），但漏掉的代价是同一个坑反复踩。

**判据**：用户投入了额外动作（重做、改、绕开）→ 说明上次没达标。

## 一律不捕获

| 不记 | 原因 | 该去哪 |
|---|---|---|
| **项目事实**：路径、文件名、项目名、某次的具体数据 | 换个项目就作废，还会稀释命中率 | 对话上下文，用完即弃 |
| **领域知识**：某个概念是什么、某个 API 的参数 | 是"是什么"不是"怎么做" | 技能库 / 笔记，不是技能库 |
| 一次性事实（"XX 文件在 /tmp/xx"） | 不可复用 | 上下文，用完即弃 |
| 未验证的猜测 | 可能是错的 | 验证后再说 |
| 用户没确认过的自作主张 | 可能是误读 | 先问 |
| 犯错过程的心理描写 | 不写错题集 | 直接写正确做法 |

## 技能 vs 事实：拿不准时的判定流程

```
这条内容里有没有具体的路径 / 文件名 / 项目名 / 一次性数据？
├─ 有 → 能不能把具体值换成占位符，让它通用？
│      ├─ 能 → 抽象后入库（"改配置前先备份" ✅）
│      └─ 不能 → 丢弃，它是纯事实（"配置在 /etc/nginx.conf" ❌）
└─ 没有 → 它描述的是动作还是概念？
       ├─ 动作（怎么做）→ 入库 ✅
       └─ 概念（是什么）→ 丢弃，归领域知识 ❌
```

**经验法则**：技能库里的任何一条，都应该能让一个**没参与过这个项目**的 AI 看懂并用上。
读到某条需要回想"这是哪次的事"才能理解 → 它就是事实，删掉。
