# 自检协议

> 一句话：**检查会以「看起来在跑，其实什么也没查」的方式失效。**

## 为什么单列一节

技能库里的"检查"分两类：查外部对象（代码/文档/配置）与查库自身。
两者会以**同一种方式**失效：规则写了、脚本跑了、输出一片绿，但一个目标都没扫到。

- 一个 131 条规则的检查库，每条的验证状态都是「未验证」，输出却写「通过」
- 一个规范检查脚本，在空目录上跑完输出「✓ 规范检查通过」

这不是实现 bug，是**设计上就没让失效可见**。下面五条是防它的最低配置。

## 一、检查项必须能红

加检查项时**同步加坏样例**，确认它真能查出来。永远绿的检查等于没有检查。

```bash
python3 scripts/lint.py --self-test    # 造已知缺陷，跑一遍必须全部命中
```

⚠ 本能会只造「应该报出来」的样例。必须**正反两侧都造**：

| 该造的样例 | 验证什么 |
|---|---|
| 有缺陷的对象 | 检查项抓得到（不会假阴性） |
| 没缺陷的对象 | 检查项不误伤（不会假阳性） |
| **自检用例自身** | 用例没造错（否则它永远通过） |

第三条最易漏：坏样例里若漏建「本该存在的文件」，
「已存在的引用不该报」这条就从未被验证过——**用例自己假通过了**。

## 二、工具必须自报扫描范围

输出「通过」时必须附上：扫了几个目标、跳过了什么。

**在空集上跑出来的通过没有意义。** 目录不存在、后缀不匹配、路径基准写错，
都会让检查在空集上跑完还显示通过——这种失效从输出上完全看不出来。

```bash
python3 scripts/lint.py
# 扫描范围：引擎自身 23 个文件；domains 技能包 0 个；未初始化大类 9 个
#   ! 本次未检查到任何 domains 技能包 → 下面若显示「通过」，只代表引擎自身文件合规
```

判据：**不看你有没有输出「通过」，看你有没有说明检查了什么。**

## 三、三态，不要二态

「没跑起来」与「跑了但没命中」是两件事，合并成一个返回值就会互相冒充：

| 合并后 | 后果 |
|---|---|
| 失败 → 当成无结果 | 扫描器崩溃被统计成「这条没有样本」 |
| 无结果 → 当成通过 | 「未覆盖」被算进「已验证」 |

返回 `(ok, result, error)` 三元组，失败单独报出：

```python
ok, hits, err = _run_scanner(scanner, src, rule_id)
# ok=False  → 没跑起来（超时/崩溃/无输出），hits 无意义
# ok=True   → 跑起来了，hits 是多少就是多少
```

同理，统计口径也要分：「未覆盖 N 条」与「执行失败 M 条」分开报，
不要把失败并进未覆盖——那会让「到底有多少没验证」这个数字本身不可信。

## 四、检测类规则必须配正反双样本

每条能自动检出的规则，配两个样本：

| 样本 | 要求 | 证明什么 |
|---|---|---|
| `tp` | **必须命中** | 规则抓得到真问题（不是死规则） |
| `fp` | **必须不命中** | 规则不过宽（不是误报源） |

⚠ 本能会只写 tp——它直观、好造，而且跑通了很有成就感。
但**只写 tp 的规则，精度永远无法验证**：知道它抓得到，不知道它会不会误伤。

没配 fp 的规则，状态字段应停在「未验证」，不得与已验证的混在同一张表里
（见 `_hot.md` H015：混在一张表等于声称全部已验证）。

**样本形态要匹配判据作用域**：判据看单文件就给单文件样本；
判据看整棵工程（忽略清单、CI 配置、多入口的策略覆盖）就要给整棵目录，
否则样本根本触发不到那条规则，还以为规则失效了。

## 五、标注字段必须可回填

手填的状态字段（`verified` / 命中数 / 验证状态）**既没有填错的成本，
也没有填对的反馈**，于是会自然收敛到同一个值：全 `no`、全 `0`、全「未验证」。

表面「标注齐全」，实际上读的人还是得逐个怀疑——**字段活着，但已经死了**。

三条出路，按强度排：

| 强度 | 做法 |
|---|---|
| ★★★ | 能实测的 → **脚本跑完自动回填**，不许手填 |
| ★★☆ | 填不了的 → 检测退化：条目数 ≥ 阈值且取值只有一种 → 预警 |
| ★☆☆ | 至少让「未标注」可见（`lint.py` 已做） |

退化预警**不是要求标成「已验证」**，而是要求**有区分度**。
全 0 的命中列有两种可能：规则从没触发过，或触发了没人更新——
两种情况都得处理，但都不会自己报错。

## 落地强度对照

| 强度 | 形式 | 例 |
|---|---|---|
| ★★★ | 脚本自动查 | `lint.py` 报死链 / 重复副本 / 标注退化 / 扫描范围 |
| ★★☆ | 流程某一步的判据 | 「加检查项 → 同步加 `--self-test` 坏样例」 |
| ★☆☆ | 可判定的检查项 | 「输出『通过』时附扫描范围」—— 一眼能看出做没做 |
| ☆☆☆ | 「要注意自检有效性」 | ❌ 不合格，不许停在这 |

## 与「知识点落地」的关系

`knowledge-landing.md` 管**知识点有没有改变行为**；
本节管**声称在做的检查是不是真在查**。

一条检查可以写得落地、判据清晰、命令化良好，却**一次也没真正执行过**——
它依然通过前者的检查。所以是两道关，顺序是先落地再自检。
