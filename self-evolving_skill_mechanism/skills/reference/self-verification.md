# 自检协议

> 一句话：**检查会以「看起来在跑，其实什么也没查」的方式失效。**

## 为什么单列一节

技能库里的"检查"分两类：查外部对象（代码/文档/配置）与查库自身。
两者会以**同一种方式**失效：规则写了、脚本跑了、输出一片绿，但一个目标都没扫到。

- 一个 131 条规则的检查库，每条的验证状态都是「未验证」，输出却写「通过」
- 一个规范检查脚本，在空目录上跑完输出「✓ 规范检查通过」

这不是实现 bug，是**设计上就没让失效可见**。下面五条是防它的最低配置。

## 一、检查项必须能红

加检查项时**同步加坏样例**，确认它真能查出来。永远绿的检查等于没有检查。

```bash
python3 scripts/lint.py --self-test    # 造已知缺陷，跑一遍必须全部命中
```

⚠ 本能会只造「应该报出来」的样例。必须**正反两侧都造**：

| 该造的样例 | 验证什么 |
|---|---|
| 有缺陷的对象 | 检查项抓得到（不会假阴性） |
| 没缺陷的对象 | 检查项不误伤（不会假阳性） |
| **自检用例自身** | 用例没造错（否则它永远通过） |

第三条最易漏：坏样例里若漏建「本该存在的文件」，
「已存在的引用不该报」这条就从未被验证过——**用例自己假通过了**。

## 二、工具必须自报扫描范围

输出「通过」时必须附上：扫了几个目标、跳过了什么。

**在空集上跑出来的通过没有意义。** 目录不存在、后缀不匹配、路径基准写错，
都会让检查在空集上跑完还显示通过——这种失效从输出上完全看不出来。

```bash
python3 scripts/lint.py
# 扫描范围：引擎自身 23 个文件；domains 技能包 0 个；未初始化大类 9 个
#   ! 本次未检查到任何 domains 技能包 → 下面若显示「通过」，只代表引擎自身文件合规
```

判据：**不看你有没有输出「通过」，看你有没有说明检查了什么。**

## 三、三态，不要二态

「没跑起来」与「跑了但没命中」是两件事，合并成一个返回值就会互相冒充：

| 合并后 | 后果 |
|---|---|
| 失败 → 当成无结果 | 扫描器崩溃被统计成「这条没有样本」 |
| 无结果 → 当成通过 | 「未覆盖」被算进「已验证」 |

返回 `(ok, result, error)` 三元组，失败单独报出：

```python
ok, hits, err = _run_scanner(scanner, src, rule_id)
# ok=False  → 没跑起来（超时/崩溃/无输出），hits 无意义
# ok=True   → 跑起来了，hits 是多少就是多少
```

同理，统计口径也要分：「未覆盖 N 条」与「执行失败 M 条」分开报，
不要把失败并进未覆盖——那会让「到底有多少没验证」这个数字本身不可信。

## 四、检测类规则必须配正反双样本

每条能自动检出的规则，配两个样本：

| 样本 | 要求 | 证明什么 |
|---|---|---|
| `tp` | **必须命中** | 规则抓得到真问题（不是死规则） |
| `fp` | **必须不命中** | 规则不过宽（不是误报源） |

⚠ 本能会只写 tp——它直观、好造，而且跑通了很有成就感。
但**只写 tp 的规则，精度永远无法验证**：知道它抓得到，不知道它会不会误伤。

没配 fp 的规则，状态字段应停在「未验证」，不得与已验证的混在同一张表里
（见 `_hot.md` H015：混在一张表等于声称全部已验证）。

**样本形态要匹配判据作用域**：判据看单文件就给单文件样本；
判据看整棵工程（忽略清单、CI 配置、多入口的策略覆盖）就要给整棵目录，
否则样本根本触发不到那条规则，还以为规则失效了。

## 五、标注字段必须可回填

手填的状态字段（`verified` / 命中数 / 验证状态）**既没有填错的成本，
也没有填对的反馈**，于是会自然收敛到同一个值：全 `no`、全 `0`、全「未验证」。

表面「标注齐全」，实际上读的人还是得逐个怀疑——**字段活着，但已经死了**。

三条出路，按强度排：

| 强度 | 做法 |
|---|---|
| ★★★ | 能实测的 → **脚本跑完自动回填**，不许手填 |
| ★★☆ | 填不了的 → 检测退化：条目数 ≥ 阈值且取值只有一种 → 预警 |
| ★☆☆ | 至少让「未标注」可见（`lint.py` 已做） |

退化预警**不是要求标成「已验证」**，而是要求**有区分度**。
全 0 的命中列有两种可能：规则从没触发过，或触发了没人更新——
两种情况都得处理，但都不会自己报错。

## 六、检测类规则必须排除「非被执行的代码」

一条规则若直接扫**文件原文**，它扫到的不只是代码，还有三类"看起来像代码
其实不会执行"的文本。不排除的话，规则会**命中描述它自己的文字**。

| 类别 | 例 | 典型形态 |
|---|---|---|
| 注释 | `// 例：user.name=xxx` | 规则在注释里举例说明自己 |
| 文档字符串 | `"""…ALL PASS 判定…"""` | 规则在 docstring 里写判据 |
| 字符串字面量 | `out.append((i, '用 mod.X = ...'))` | 规则输出的告警文案、规则表里对它的描述 |
| 内嵌测试数据表 | `("AR-05", "mod.ROOT='/x'…", True)` | 自检样本存在常量表里 |

实测（一个 23 脚本的检查库自扫）：最先报出的 3 条命中里，2 条是规则
命中了自己注释与文档字符串里的示例。用户看到的表现是
「扫真实项目时冒出一堆看不懂的命中」，且**无法通过加样本发现**——
样本文件里不会有"把规则说明抄进注释"这种形态。

**唯一的发现办法：把样本整段注释掉再扫一遍，必须零命中。**

```bash
# code-audit 侧的等价命令（本集群另一个 skill）：
#   rule-registry.py --comment-test
# 116 组样本全部注释后必须零命中；去掉过滤后它确实变红。
```

⚠ 排除要有例外：**输出语句的参数确实会被输出**。
判断"某字面量是不是输出内容"而不能一律剔除——后者会让真阳性一起消失。

## 七、新建设施必须配「接入率检查」

仓库里常见一类设施：造出来是为了**每处都接上**的——参数守卫、日志、
错误上报、豁免标记。它的价值 = **覆盖率 × 单次价值**；覆盖率低时约等于零。

但设施造好后，没有任何机制提醒"还有 17 个入口没接"。
于是它稳定处于「有这个东西，但大部分地方没用」的状态，
而**没接的地方表现与没造之前完全一样**——静默。

实测：一个未知参数守卫造好后，23 个脚本里只有 6 个接了；
另外一个"剔除非代码行"的辅助函数，只有 2 条规则调用它，
其余同类规则继续各写各的、各漏各的。

| 强度 | 做法 |
|---|---|
| ★★★ | 自动统计「应接入点」与「实际接入点」，差集**逐个列出** |
| ★★☆ | 至少让新建设施的文档里写明"怎么确认全覆盖"的命令 |

差集要**逐个列出**，不能只报个数——个数不知道去哪补。

⚠ 「应接入点」要认全合法形态，否则会把**换了一种实现方式**的入口
误报成没接。实测：某脚本用自建 `KNOWN_FLAGS` 名单拒绝未知参数，
效果与 `_flagguard` 完全相同，但按"只有 _flagguard 算接入"来查会被
报成漏接——**误报的检查会被关掉**。

落地形态（code-audit 侧 `check-list-drift.py` 第 5 项）：
`_flagguard` / `argparse` / 自建 `KNOWN_*` 名单，三者任一即算接入。

## 八、豁免必须可验证

标记了豁免（`# ignore` / 白名单 / 例外清单）之后，**命中数就该减少**。
如果没减少，只有两种可能：豁免没接上，或豁免写错了位置。

实测：给某规则的三处命中加了行级豁免，命中数一条没变——
因为那条规则的分支里**根本没调用豁免判断**。
加了豁免却没生效是最容易被忽略的失效：人已经"处理过"了。

| 强度 | 做法 |
|---|---|
| ★★★ | 加豁免后立即复跑，断言命中数下降；不降就报错 |
| ★★☆ | 统计豁免标记总数 vs 实际生效数 |

⚠ 豁免位置也有讲究：只检查「上一行/本行」的实现里，
豁免注释**必须写成一行**——写成两行时第一行会滑出检查窗口，静默失效。

## 九、单条规则异常不能静默

规则执行时抛异常，若被 `except Exception: pass` 吞掉并计入"0 命中"，
那么**规则整个挂了**与**这次确实没问题**在输出上完全一样。

实测：一次重构漏写了一个函数，调用它的规则抛 `NameError` 被吞，
该规则的命中数从 6 降到 0 —— 当时被当成"精度修好了"。
**自检恰好也通过了**，因为自检喂的是样本而不是那段坏代码。

| 强度 | 做法 |
|---|---|
| ★★★ | 单条规则的异常单独计数并上报，不混进"无命中" |
| ★★★ | 把「规则命中数突降到 0」本身当成可疑信号 |
| ★★☆ | 至少 stderr 打印，不静默 |

与「三态，不要二态」同源：那节讲**整个工具**的失败 vs 无结果，
本节讲**单条规则**——粒度更细，也更难发现。

## 十、判据必须认「等价的正确写法」

一条判据若只认**一种**写法，那么"换了个更好的写法"会被判成违规。
结果是逼着人把对的改回错的——**检查在奖励退化**。

实测（退出码分类这条）：判据原先只统计**字面量数字**退出码，于是
三种等价的正确写法全被判成"没分类"：

| 写法 | 为什么更好 | 原判据怎么看 |
|---|---|---|
| `return USAGE` / `die(ENV, …)` | 语义常量比裸数字可读 | 认不出 → 算 0 种 |
| `sys.exit(main())` | 码写在 main 里，出口统一 | 不跟进 → 算 0 种 |
| `return 1 if fail else 0` | 三元表达式 | 认不出 → 算 0 种 |

三条修完，同一份代码从"8 条违规"变成"0 条"——**代码一行没改**。

**修判据时同步在判据正文写明"哪些写法算合规"**。
否则下一个人照着字面量判据写，会重新把正确写法判成违规。

同类教训：`TS-O02` 曾按变量名白名单判"除法无零防护"，
白名单内 5/5 命中、白名单外 0/8；改判据（不看名字看上下文）后 8/8。

## 十一、文本匹配判据必须走 AST，不能扫原文

`'argparse' in src` 这种判断会命中**文档字符串里提到 argparse**的文件。
在库模块上尤其常见：库不解析命令行，文档里却会解释"它与 argparse 的关系"。

实测：一个只定义常量的库模块被判成"命令行入口脚本没装参数守卫"——
因为它的文档字符串里出现了 argparse 一词。

| 强度 | 做法 |
|---|---|
| ★★★ | 用 AST 看真实引用（`ast.Attribute(attr='argv')` / `ast.Call`） |
| ★★☆ | 至少排除注释与文档字符串后再匹配 |

与第六条同源：那节讲"规则扫到注释/文档串里的示例"，
本节讲"**判据**扫到注释/文档串里的词"——同一类失效的两种形态。

## 十二、提取规则按「最常见的出现形式」定，不按「最好匹配的形式」定

写一条检查时，先问：**这类东西在真实文本里最常以什么形式出现？**
而不是"哪种形式最好写正则"。

实测（断链检查）：某检查只认**反引号包裹**的引用 `` `scripts/某脚本.py` ``，
因为反引号最好匹配。但文档里脚本 90% 出现在**代码块的可执行命令**里
（形如代码块里的 `python3 <某个脚本路径> --src=<根>`，本段故意不写真名，
否则举的这个例子会被本集群的断链检查抓成死链——它确实会扫代码块）。

于是两条真死链（一个早就拆成两个的脚本，两个文档仍在教人跑它）
**长期存在而无人知晓**。照着代码块敲命令是新手最典型的用法，
恰恰是这里的死链危害最大。

| 应该问的 | 容易犯的 |
|---|---|
| 这种引用最常以什么形式出现？ | 哪种形式正则最好写？ |
| 有没有第二种同样常见的形式？ | 匹配上了就算完成 |

**同一功能不要在两处各实现一遍。** 本集群就出过：断链检查在
code-audit 侧只认反引号、在引擎侧认所有形式——同一个功能，
一个对一个错，而**错的那个照样输出绿色**。
两处实现必然随各自修改而分叉，且没有任何机制比对它们的判据。

## ## 十三、检查长期红灯 = 检查已经死了

一个检查如果**长期失败而没人修**，它就不再是检查。

人的反应是可以预测的：第一次红会去看，第十次红会跳过，第一百次红会
在脚本里加 `|| true`。此后它输出什么都与决策无关——**真问题混进来时
同样看不见**。

实测（本仓库 CI）：`--check` 因注册表未同步持续退出码 1，五个语言包的
自检在流水线里一次都没跑。更糟的是**红灯本身掩盖了这个事实**——
所有人都以为"CI 红是常态"，没人去看红的是哪一条。

| 强度 | 做法 |
|---|---|
| ★★★ | CI 里区分「新增失败」与「已知失败」，只对前者阻断 |
| ★★☆ | 已知失败必须有显式登记（为什么暂不修、谁负责、何时清） |
| ★☆☆ | 至少不允许在命令后裸写 `|| true` 把红灯抹成绿的 |

**红线**：把失败改成成功（吞异常 / `|| true` / 降级为 info）比留着红灯更糟——
后者至少还看得到，前者连信号都没了。这与第九条同源：
那节讲「单条规则异常不能静默」，本节讲「整条检查的失败不能常态化」。

## 十四、判据看语义方向，不看表面特征

同一个 API、同一个写法，在两处可能是**语义相反**的两件事。
按表面特征写判据，会把其中一半判错。

实测两例，方向恰好相反：

| 写法 | A 处语义 | B 处语义 |
|---|---|---|
| `has()` 存在性判断 | 对象池：**扣减前的归属校验**（缺 = 漏检） | 对象池：**重复归还拦截**（查"是否已空闲"，方向与归属相反） |
| 信号未 disconnect | 跨生命周期连接：泄漏 | `CONNECT_ONE_SHOT`：本就触发一次自动断开，要求 disconnect 是误报 |

第二例还有个反面：文档常说"节点释放后 Tween 一定泄漏"，但官方明确
**绑定对象释放时 Tween 自动销毁**——把它写成无条件判据就是误报源。

**判据要写明「排除条件」，而不只是「命中条件」。** 命中条件决定抓得全不全，
排除条件决定报得准不准；后者写漏了，检查就会因为误报被关掉。

与第十条的分界：第十条讲「**不同写法**达到同一效果」（等价写法被判违规），
本节讲「**同一写法**在不同位置语义相反」（表面相同被当成一回事）。

## ## 落地强度对照

| 强度 | 形式 | 例 |
|---|---|---|
| ★★★ | 脚本自动查 | `lint.py` 报死链 / 重复副本 / 标注退化 / 扫描范围 / 豁免未生效 |
| ★★☆ | 流程某一步的判据 | 「加检查项 → 同步加 `--self-test` 坏样例」 |
| ★☆☆ | 可判定的检查项 | 「输出『通过』时附扫描范围」—— 一眼能看出做没做 |
| ☆☆☆ | 「要注意自检有效性」 | ❌ 不合格，不许停在这 |

## 与「知识点落地」的关系

`knowledge-landing.md` 管**知识点有没有改变行为**；
本节管**声称在做的检查是不是真在查**。

一条检查可以写得落地、判据清晰、命令化良好，却**一次也没真正执行过**——
它依然通过前者的检查。所以是两道关，顺序是先落地再自检。

## 自检（30 秒）

- [ ] 新增的检查项，`--self-test` 里有没有对应坏样例？正反两侧都造了吗？
- [ ] 工具输出「通过」时，有没有说明扫了多少、跳过了什么？
- [ ] 失败与「无结果」在返回值里是分开的吗？
- [ ] 检测类规则是只有 tp，还是 tp/fp 都有？
- [ ] 手填的状态字段，最近一次是什么时候被回填/更新过？全同值了吗？
- [ ] 把样本整段注释掉再扫，是零命中吗？（规则有没有扫到注释/文案）
- [ ] 新造的设施，23 个入口接了几个？差集列出来了吗？
- [ ] 加了豁免之后，命中数真的下降了吗？
- [ ] 某条规则命中数突降到 0，是修好了还是它挂了？
- [ ] 判据只认一种写法吗？换了等价的正确写法会不会被判违规？
- [ ] 用 `'xxx' in src` 判据的地方，会不会命中文档字符串里的词？
- [ ] 提取规则是按「最常见的形式」定的，还是按「最好匹配的形式」定的？
- [ ] 有没有检查长期红灯？它是「还没修」还是「已经被当成噪音了」？
- [ ] 判据写了排除条件吗？同一个写法在别处会不会是语义相反的另一种情况？
