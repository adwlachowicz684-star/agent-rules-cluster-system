# 结构演进协议

> **核心原则**：AI 发现现有类目装不下时，**主动提出新建或调整**，
> 但**只能提案，不能自行改结构**——执行必须用户确认。

## 为什么需要这套机制

分类体系不可能一开始就设计对。三类信号说明"现有结构不精准"：

| 信号 | 表现 | 应对 |
|---|---|---|
| **装不下** | 新技能在所有大类里都找不到合适位置 | 新建大类 / 新建子目录 |
| **分不清** | 两个大类得分持平，归属摇摆 | 缺中间层 → 新建；或拆技能各自归属 |
| **太臃肿** | 某大类 >40 个技能，或单包 >200 行 | 拆子目录 / 拆包 |

不处理会怎样：技能被硬塞进不合适的大类 → 检索命中不了 → 库看着大但用不上。

## 判定：现有结构装得下吗

```bash
python3 scripts/structure.py --route-check "基因测序数据分析流程"
```

| 判定 | 含义 | 动作 |
|---|---|---|
| `ok` / `core_hit` | 归属明确 | 直接归位 |
| `weak_match` | 只命中边缘词 | 确认后归属，或考虑新建 |
| `ambiguous` | 两个大类持平 | 提议新建中间大类 |
| `no_match` | 专业词一个没命中 | **提议新建大类** |

### 关键设计：泛词不算归属

**仅靠「流程/输出/文件」这类泛词命中 `_common`，不算真正归属。**
否则任何描述都会被判定"装得下"，永远发现不了缺失的大类。

```yaml
generic_words: [通用, 流程, 输出, 文件, 交付, 打包, 沟通, 搜索, 写作, 整理]
```

### 关键设计：核心词免确认

每个大类标注 `core`（核心词），命中 1 个即确认归属，不必二次确认：

```yaml
legal:
  core: [合同, 诉讼, 法条, 民法典, 起诉, 仲裁]
  keywords: [法条, 法规, 法律, 合同, 诉讼, 合规, ...]
```

- 命中 `core` → 归属明确
- 只命中 `keywords` 边缘词 → 需确认
- 只命中泛词 → 视为没归属

## 提案流程（AI 提议 → 用户确认 → 执行）

```
① 发现装不下
   python3 scripts/structure.py --route-check "<描述>"
        ↓
② AI 提议（生成提案，不执行任何变更）
   python3 scripts/structure.py --propose-new 生物信息 \
       --key bio --kw "基因,测序,蛋白,组学" --core "基因,测序" \
       --desc "生物信息学与组学数据分析"
        ↓
③ 用户查看提案
   python3 scripts/structure.py --show
        ↓
④ 确认后执行（自动备份）
   python3 scripts/structure.py --apply        逐项确认
   python3 scripts/structure.py --apply --yes  全部执行
        ↓
⑤ 反悔可回滚
   python3 scripts/structure.py --undo
```

**AI 在第②步就停住**，不自行执行。这是硬约束——
结构变更影响所有后续归类，误操作代价远高于多问一次。

## 提案类型

| 动作 | 用途 | 关键参数 |
|---|---|---|
| `new-domain` | 新建大类 | `key` `name` `keywords` `core` `desc` |
| `new-subdir` | 大类下建二级分类 | `name`（如 skills/合同/） |
| `move-skill` | 移动技能到别的大类 | `src` `target` |
| `split-skill` | 拆包（>200 行） | 人工执行，脚本提示 |
| `rename` | 重命名 | `src` `name` |

`new-domain` 执行时自动完成：建目录 → 生成 rules/agents 模板 →
建 `_common` 通用链接 → 注册到 `config.yaml`。

## 安全机制

- **dry-run 预览**：`--apply` 先跑一遍干跑，列出受影响文件
- **自动备份**：执行前备份到 `pending/_backup/<时间戳>/`
- **操作日志**：`pending/structure-log.json` 记录每次变更
- **可回滚**：`--undo` 恢复（自动覆盖风险高，默认提示人工核对）
- **不删除**：移动 = 复制 + 保留原处；删除需用户明确要求

## 什么时候该新建大类

**判断依据：这个方向会持续产生技能吗？**

| 情况 | 建议 |
|---|---|
| 一次性任务 | 不建，归 `_common` 或最近的大类 |
| 偶尔出现（<3 个技能） | 先归相近大类，观察 |
| 反复出现、有专业术语体系 | **建** |
| 与其他大类频繁交叉 | 建，并设计好 `core` 与其他类区分 |

**宁可先粗后细**：大类分太细会导致"一个技能不知道归哪"，
比"一个大类里技能多了点"更难处理（后者可以建子目录，前者要重新归类）。

## 结构优先级：先子目录，后新大类

```
某大类技能 > 40 个
   ↓
先问：这些技能能自然切成几组吗？
   ├─ 能（如合同类/诉讼类）→ 建子目录 skills/合同/ ✅ 更轻量
   └─ 不能，且它们其实是不同领域 → 才新建大类
```

**子目录 vs 新大类**：子目录不增加归属判定的复杂度，
新大类会增加一个候选，让后续判定更容易摇摆。

## 反模式

| ❌ 不要 | 后果 | ✅ 应该 |
|---|---|---|
| AI 自行新建目录 | 用户不知情，结构失控 | 提案 + 确认 |
| 一有技能就建大类 | 大类碎片化，归属摇摆 | 先子目录，观察再定 |
| 靠泛词就算归属 | 永远发现不了缺失的大类 | 泛词不算数 |
| 空大类也报警 | 噪音淹没真问题 | 空位是预留，正常 |
| 执行前不备份 | 改错无法回退 | 自动备份 + 日志 |
