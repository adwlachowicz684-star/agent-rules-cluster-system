# reference/ 五分体系：howto · audit · flow · common · craft

> **本区性质：common / 元规则。**
> 它定义 reference/ 下五个分区各自装什么、一句话该进哪个区。
> **不确定读哪个区时，先看本文件。**

## 一、为什么必须分区

一句话：**建设时想着「别犯错」，会让你写得又短又空；
审查时想着「怎么做」，会让你把问题改写成建议。**

两件事的目标函数相反：

| | 建设（写技能） | 审查（审技能） |
|---|---|---|
| 要产出 | 一个能照着做的流程 | 一份「哪里不行」的清单 |
| 注意力 | 这件事**该怎么做** | 这份东西**在哪会失效** |
| 失败形态 | 写得含糊、不可执行 | 报得笼统、没有位置/证据/后果 |
| 读错册的代价 | **缩手缩脚**，写出来的全是免责声明 | **下手改坏**，把有理由的设计当缺陷改掉 |

实测的代价：

- **建设时读审查册** → 满脑子"这样会不会被驳回"，结果写出的技能
  通篇是「注意…」「不要…」，而**没有任何可执行步骤**。
  这正是 `knowledge-landing.md` 批判的"正确的废话"——
  它只是换了个方向产生。
- **审查时读建设册** → 看到的是"这个流程应该这样走"，
  于是把「这里不符合流程」写成「建议改成 X 流程」，
  **丢掉了位置和证据**，变成一条无法执行的优化建议。

## 二、判据：一句话该进哪个区

**核心判据（一句话**：它在描述「要做什么」，还是「什么情况下它不成立」？
前者进建设性分区，后者进 `audit/`。

五个分区各自的落点：

| 区 | 装什么 | 一句话判据 | 读的时机 |
|---|---|---|---|
| **`howto/`** | 具体怎么做 | 「遇到 X 情况，**该怎么做**」 | 写 / 改技能时 |
| **`audit/`** | 不能怎么做 | 「**什么情况下**它不成立」 | 审核 / 提优化建议时 |
| **`flow/`** | 端到端流程 | 「**第一步…第二步…**」 | 要走完一整件事时 |
| **`common/`** | 元规则、共用约定 | 「本文**讲**…」「本区性质是…」 | 不确定读哪个区时 |
| **`craft/`** | 品位与技巧 | 「**好的** X 应该…」「判断标准是…」 | 想做得更好时 |

⛔ **`craft/` 是唯一「主观」的一层**（索引见 [`../craft/index.md`](../craft/index.md)）。
其余四层装的都是可核实的事实/流程，**本层装的是经验值**。
⇒ ⛔ 不标注的后果：经验区间被当成判据引用（"必须 80–150ms"）。
ⓘ 两端第四次独立收敛到同一结构时发现——这是前三次都没注意到的一层差别。

**按动词快速判**（`craft/techniques.md` 第五节有完整表）：

| 动词形态 | 归属 |
|---|---|
| 「应该…」「先做…再…」 | `howto/` |
| 「不要…」「会失效如果…」 | `audit/` |
| 「第一步…第二步…」 | `flow/` |
| 「本文讲…」「本区性质是…」 | `common/` |
| 「好的…应该…」「判断标准是…」 | `craft/` |

## 三、分区的边界（易混的五种）

### 3.1 「排除条件」属于 `audit/`，不属于 `howto/`

混进 howto 会让判据越写越长、越写越不敢用。
howto 只给主路径，排除条件由 audit 逐条列。

### 3.2 「为什么」两区都要，但落点不同

- `howto/` 给**执行者**：不做的后果是什么
- `audit/` 给**排查者**：这个失效形态怎么发生的

### 3.3 驳回清单属于 `audit/`

整合时跳转到 `audit/rejection.md`，**不要抄回流程**。

### 3.4 `craft/` 与 `howto/` 的区别：做完 vs 做好

| | 回答 | 照着做的结果 |
|---|---|---|
| `howto/` | **怎么做完** | 能产出 |
| `craft/` | **什么算好 / 怎么做好** | 产出能用且好用 |

**没有 craft 只会「做完」和「没毛病」，不知道「好」长什么样。**
例：每条规则都格式正确、来源明确，但没有一条是你真正会遇到的情况。

### 3.5 `craft/` 与 `audit/` 的区别：上限 vs 下限

```
audit   不许坏    —— 违反就是缺陷
craft   要好      —— 做不到不算错，但不好用
```

**只做 audit 会得到「合格的平庸」。**
判据：这条做不到会算缺陷吗？会 → audit；不会、只是不够好 → craft。

### 3.6 `flow/` 与 `howto/` 的区别：一次性 vs 可复用

- `flow/` 是从头走到尾的**完整流程**（整合九步、闭环五步）
- `howto/` 是可单独取用的**具体做法**（怎么划层、怎么路由）

判据：**它是"走完一件事"，还是"解决一个判定问题"？**

⛔ **不要把 flow 当知识库查。** 拿流程文件当完整说明书用，
会同时得到两个坏结果：① 找到的不是最全的做法（做法在 `howto/`）；
② 把"顺序"和"知识"混在一起，之后两边都不好改。
判据：**我要的是「怎么查到完整说明」还是「下一步该干什么」？**

**⚠ 判定标准不属于流程文件。** 四道门槛、归位决策、ID 规范这类内容
是**查的东西**不是**走的东西**——混在流程里会让流程文件越来越长，
而每次整合只在特定步查特定标准。
所以它们放在 `howto/consolidation-rules.md`，流程文件在【读】里指向它。

### 3.7 `flow/` 内部：meta 与 procedure 必须分开标记

| `flow-type` | 是什么 | 受哪些检查 |
|---|---|---|
| `meta` | 讲「流程该怎么写」，本身不是流程 | **不检查** Step 五字段 |
| `procedure` | 一个可照着走完的流程 | 五字段 + 两级审核 + flow-id |
| `template` | 空白模板 | 不检查 |

⚠ **必须区分**：元规范里必然**举例** Step（"七节模板"），
不区分的话示例会被当成真步骤检查——**举例的模板永远不完整，
必然误报，而误报的检查会被关掉**。

## 五、已落地实例：Godot 镜像册（多处独立得出同一结构）

本仓库 code-audit 侧已有一对同名镜像册（**两端独立得出同一结构，
可作为判据的实证**）：

```
game-dev/references/godot/*.md              82 份 · 只写「怎么做」
code-audit/references/godot-antipatterns/*.md  79 份 · 只写「不能怎么做」
                                             ↑ 1:1 同名，互为镜像
```

审查册那侧格式统一：每份开头都写
「本文件只写『不能怎么做』」+ 指向开发侧同名的「怎么做」。

**它踩了单向互补的坑**：审查册 79/79 全都有指向建设册的指针，
而建设册 82 份里只有 10 份指回审查册——**单向**。

后果：开发时看不到对应的反模式清单，写完不知道该去哪查
"我这样写有没有坑"。**审查册再全，开发时也用不到。**

已补齐 69 份反向指针；另 3 份（`game-systems` / `verification` /
`version-47-48`）**没有对应的反模式册** —— 这是审查册的缺口，
登记在此，不伪造指针（指向不存在的文件 = 死链）。

> 判据：**镜像册要双向都能走到**。查法：
> `grep -L "对侧关键词" 建设册/*.md` 列出来的就是断的那半边。

### 同一理念被三处独立得出

| # | 出处 | 形态 |
|---|---|---|
| ① | 引擎侧 `split-two-books.md` | 建设册 / 审查册总纲（本文） |
| ② | 审查侧 `code-audit/references/godot-antipatterns/` | 79 份反模式册，明写「只写不能怎么做」 |
| ③ | 开发侧 `game-dev/SKILL.md` | 核心原则第 4 条：**「不写『不能怎么做』」** |

开发侧的原文：

> 本 skill 只写「怎么做」——实现方案、选型依据、完整代码、参数含义。
> 「不能怎么做」（反模式、常见坑、漏写清单）全部在审查侧。
> 本 skill 的每个功能域文档末尾只留**一行指向**，不重复写判据。

**三处彼此独立、互不知情，却收敛到同一结构。** 这比任何论证都更能说明
两册分工不是某种偏好，而是被问题本身逼出来的形状——
值得作为判据的实证记在这里。

其中开发侧落地最彻底：**79 份反模式册（1666 行）已从开发文档整段迁走**，
开发侧原地只留一行指向。

## 3.8 技能数据跟着仓库走，不放在家目录（2026-09-26）

```
root: domains          # ← 相对路径，相对 skill 根
# 旧：root: ~/.ai/domains
```

### ⛔ 实测动机

环境重置后：`ls: cannot access '/root/.ai/domains'`
⇒ 1 个真技能包**没了**，而 git 管不到它：无法版本化、无法 review、
无法回滚、换机即丢。且 lint 长期报「大类根目录不存在 → 检查不完整」。

### 判据：能不能由脚本重新生成？

| | 进 git | 例子 |
|---|---|---|
| **资产** | ✅ | `domains/<大类>/skills/*.md`、`rules/*.md`、`_common/**`、`pending/archive-*.md` |
| **派生物** | ⛔ | `INDEX.md`（index 生成）、`<大类>/_common`（软链接）、`.last_consolidated`（指纹） |

### ⛔ 软链接必须相对，且不进 git

```
domains/开发/_common -> ../_common                    ✅ 相对
domains/开发/_common -> /home/x/.../domains/_common   ⛔ 绝对，换机即断
```

⛔ **进 git 的软链接在 Windows 上可能被 checkout 成文本文件**
（无 symlink 权限时 git 就这么做）→ **静默损坏，且不报错**。
ⓘ Linux/macOS 上跑得好好的，**只有换到 Windows 才现形**，
而那时报错的是别的东西（"找不到目录"），没人会联想到 symlink。

### 覆盖机制

环境变量 `SKILL_DOMAINS_ROOT` 优先——需要"每台机器独立积累"时用。
⛔ 不写死绝对家目录路径：那会让 skill 无法分发。

## ⛔ 不要在目录里写「N 个文件」——它会过期，而且过期得很安静

ⓘ 这是本文件**第 4 次**修同一个数字：

```
howto  10 → 16 → 17
audit   3 →  6 →  7
```

⚠ **每次都是"加了文件但没回来改这里的计数"**——
而读的人会把这个数字当成现状。

⇒ **判据**：

| ⛔ 不要写 | ✅ 写什么 |
|---|---|
| 「howto 有 17 个文件」| 区的**判据**（动词），让人自己去看 |
| 「共 2249 行」 | **怎么算**：`ls reference/howto/*.md \| wc -l` |

```
⛔ 计数是快照，会变
✅ 判据是稳定的
```

ⓘ 与 EC-03（数字会过期，见 [`../common/blocks.md`](../common/blocks.md)）
同源——**这次是它第 4 次自证**。

⚠ 唯一例外：在**变更溯源/统计报告**里写计数是可以的，
因为那本来就是"某时某刻的快照"，且带了日期。
⛔ 在**目录/索引**里写 = 声明了一个会失效的事实。
