## 为什么有这个文件

⚠ **本文件里的每个块，都是已经被逐字重复写过多遍的内容。**

实测统计（2026-09-25，扫 `reference/` 全部文件）：

| 内容 | 关键词命中 | **语义同义数**（真实） |
|---|---|---|
| 「查不到 ≠ 没有」 | 8 个文件 / 11 次 | **8 —— 语义一致** ✅ |
| 「正反双样本」 | 10 个文件 | **2** ⚠ |
| 「数字会过期」 | 5 个文件 | **1** ⚠ |
| 「陌生人测试」 | 4 个文件 | **4 —— 语义一致** ✅ |

### ⛔ 统计口径错误（本轮自查发现）

第一版用 `grep -rl "反例\|正反双样本"` 数出 10 个文件，
**这是错的**。逐个核实后，「反例」在这 10 处里有**四种不同含义**：

| 出处 | 这里的「反例」指什么 | 与 EC-02 同义？ |
|---|---|---|
| `craft/techniques.md:78` | 检测判据的正反样本（"只有正例会无限误报"） | ✅ 是 |
| `craft/taste.md:62` | **文档写作的反例**（"不要 X，因为 Y 会 Z"） | ❌ 写作手法 |
| `howto/knowledge-landing.md:54` | 写法对照表（❌ 流于理论 / ✅ 落地） | ❌ 排版手法 |
| `howto/consolidation-gate.md:32` | **例外情况**（"有反例时可绕开"= 被证伪） | ❌ 完全不同的意思 |

「数字会过期」同理：5 处里 3 处讲的是**指向会变**
（流程改了 → 表里的"回到 S2"错了），与"文档里的统计数字过期"
是**相关但不同**的两件事。

⛔ **这正是第二十三条「能数出来的 ≠ 该判的」的自证**：
我拿「关键词出现次数」这个**最容易数的东西**，
代替了「语义是否相同」这个**真正该判断的东西**。

> ⛔ **在各文件里各写一遍 → 改一处要改几十处，且必然漂移。**

这就是它必须被抽出来的唯一理由——**不是因为它重要，而是因为它重复**。

### ⛔ 收录标准（不满足就不要加进来）

| # | 标准 | 判据 |
|---|---|---|
| 1 | **语义同义地重复过 ≥3 次** | ⛔ **必须逐个核实语义，不能 grep 关键词**——见上方「统计口径错误」 |
| 2 | **不是某个区的专属内容** | 是 flow 专用的 → 留在 `flow/` |
| 3 | **改了要通知多处** | 改了只影响一处 → 不算跨文件 |

⚠ **第 1 条最容易违反**：人容易把"我觉得很重要"当成全局块。
⛔ 重要性不是收录标准——**重复次数才是**。

## EC-01 查不到 ≠ 没有

**适用**：一切"搜索 / 查询 / 检查返回 0 条"的场景。

三种「0 命中」，**只有一种是真空白**：

| | 形态 | 表现 |
|---|---|---|
| ① | **空转** | 旧路径 → `listdir` 得空 → 收集 0 条 → **正常退出不报错** |
| ② | **误判** | 查「录像回放」判 0，实际有 `replay.md` |
| ③ | **真空白** | 确实没有 |

⛔ **①②都会输出"没有"，只有③是真的没有。**
**失败模式是「返回 0 条」而不是「报错」**——
所以任何能跑通的检查都查不出来。

**判据**：

> **报「没有」之前，先证明「查了」且「查法对」——用原子词再查一次。**

ⓘ **变体：搜索方向**（第二十七条）
要查「漏了 B」必须从 A 出发找 B，不能从 B 出发——
从 B 出发时，漏掉的那些**不在搜索结果里**，
于是"0 命中"被误读成"都做到了"。

#### 注：数字会过期（原 EC-03）

**报出一个数字之前，先问它是"事实"还是"快照"。**

实测自证：总纲里五区文件数全部过期
（`howto` 10→16、`audit` 3→6、`flow` 2→12、`craft` 2→4）。
⚠ **过期数字会被当成现状继续引用**——而引用它的人不会去核对。

| 类型 | 处理 |
|---|---|
| 会变的统计 | **指向生成它的命令**（如 `ls \| wc -l`） |
| 会变的清单 | **指向索引文件**，⛔ 不在正文抄一遍 |
| 不变的常量 | 可以写死（如退出码码表） |

⛔ 与 EC-01 同源：**"报出去之前先证明它还是对的"**——
EC-01 说的是"报没有之前先证明查了"，这里说"报数字之前先证明它没过期"。

## EC-02 正反双样本（缺反侧 = 没在验证）

**适用**：一切检查项、规则、判据、自检用例。

```
正样本：有缺陷 → 必须报
反样本：没缺陷 → 必须不报
```

⛔ **只有正样本的检查会退化为"永远报警"**，
而报警一旦长期为真，人就会关掉它（第十三条）。

⚠ **最常见的失效：用例蹭真库数据过的。**
真库干净 → 断言被跳过 → **用例恒绿而从未验证**；
真库脏 → 又依赖具体脏在哪。

**判据**：

> **用例必须在自己造的样本上成立，且要先断言样本确实触发了目标状态。**

ⓘ 空列表会让 `all()` 恒真、`any()` 恒假——
**两条都会产生恒绿但无效的用例**。

## EC-04 陌生人测试

**适用**：一切"写完了，怎么知道好不好"的场景。

> **一个不认识你、没参与过上下文的人，只看这一个文件，
> 能不能照着干成活？**

⚠ **为什么必须是"没参与的"**：
参与过的人**知道该怎么操作**，会**无意识地避开**有问题的路径。

ⓘ **两端独立得出同一条**（2026-09-25）：
- game-dev 侧：验收要求 **≥3 名未参与开发的人**试玩（产品视角）
- 引擎侧：`craft/taste.md` 的**总判据就是它**（文档视角）

⚠ **两个视角的共同点**：
**"参与过"本身就是一种污染**——你补上的那部分上下文，别人没有。

## 新增块的流程

1. 确认**已被重复写过 ≥3 次**（grep 数一遍，⛔ 不要凭印象）
2. 分配 `EC-xx` ID（**分配后不改**）
3. 写块正文 + 判据
4. **更新本文件两张索引表**（单向登记不算索引）

⛔ **不要为"我觉得重要"建块**——
建了没人引用，反而增加一层要维护的跳转。
