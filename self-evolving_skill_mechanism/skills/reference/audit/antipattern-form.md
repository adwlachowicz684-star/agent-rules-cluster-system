# 反模式清单怎么写：误解类 vs 遗漏类

> **本区性质：audit / 元规则（讲反模式清单本身怎么写）。**
> 具体反模式见 [`anti-patterns.md`](anti-patterns.md)；
> 失效形态见 [`self-verification.md`](self-verification.md) 及三册。

---

## 一、为什么单分：实测有两种截然不同的形态

game-dev 的 109 份反模式册，表头只有两种：

| 形态 | 表头 | 份数 |
|---|---|---|
| **误解类** | `本能以为` / `实际` | **79** |
| **遗漏类** | `漏写` / `后果` / `审查规则` | **22** |

⛔ **这不是风格差异，是两种不同性质的缺陷**：

| | 误解类 | 遗漏类 |
|---|---|---|
| 人**做没做** | **做了**，但理解错了 | **根本没做** |
| 典型 | "以为 `@rpc` 默认不可靠" | "忘了设 `up_direction`" |
| 后果 | 按错误理解写出的代码是错的 | 功能缺失，且**不报错** |
| 怎么发现 | 对照表**逐条问自己** | 搜索**有没有写** |

**混在一张表里会两头不讨好**：
误解类需要"读一条、对照一次"，遗漏类需要"搜一遍、查漏"——
混起来只能做其中一件。

## 二、误解类：`本能以为 / 实际`

```markdown
| # | 本能以为 | 实际 |
|---|---|---|
| 2 | `@rpc` 默认不可靠 | **默认 reliable**，高频同步要显式改 |
| 3 | 客户端能直接调 RPC | 默认 authority，调用被**静默忽略** |
```

### 判据：这条是不是"多数人会猜错"？

⚠ **写成"正确/错误"就没用了**。

```
⛔ 「@rpc 应该显式声明 unreliable」      ← 是规范，不是反模式
✅ 「本能以为 @rpc 默认不可靠 / 实际默认 reliable」
```

区别在哪：**规范告诉你该怎么做；误解表告诉你"你现在的想法是错的"**。
后者才会在你**带着错误假设**去写的时候拦住你。

### ⛔ 一定要写「实际」的可观测表现

```
⛔ 「客户端调 RPC 有问题」           —— 不知道怎么发现自己中招
✅ 「调用被**静默忽略**」            —— 没反应也不报错，可对照
```

⚠ **"静默"要显式写出来**：不报错的失败最难自查，
而反模式表是**自查工具**——只写"会出错"等于没写。

ⓘ 与 [`flow/diagnosis.md`](../flow/diagnosis.md) 第四节同源：
症状必须写可观测现象，且要覆盖不报错的失败。

## 三、遗漏类：`漏写 / 后果 / 审查规则`

```markdown
| # | 漏写 | 后果 | 审查规则 |
|---|---|---|---|
| 4 | 没设 `up_direction` | `is_on_floor()` 永远 false，跳不起来 | 人工 |
| 7 | collision_layer / mask 随便填 | 表现为"穿墙"或"撞空气" | 人工 |
```

### 判据：这条**漏了会不会被发现**？

⚠ 收录标准是「**漏了不报错**」——漏了立刻崩的不必写，
因为编译器/运行时会告诉你。

```
✅ 「没设 up_direction → is_on_floor() 永远 false」
   漏了不报错，只是跳不起来，且你会去调别的地方
⛔ 「没写冒号 → 语法错误」
   漏了立刻报错
```

### 「审查规则」列：能机扫的写规则号，不能的写"人工"

⚠ **写"人工"不是敷衍，是诚实标注**：
它告诉读者"这条机器不会替你查"——
而⛔ 不写这一列会让人以为全表都可机扫。

ⓘ 与 `../audit/self-verification-credibility.md` 第二十条
（未验证结论必须条目化）同一思路：
**把"哪些没被机器覆盖"显式登记出来**。

## 四、⛔ 自查方向：从「申请」找「释放」，不能反过来

这是 GA-02（资源没配对）里最精彩的一句：

> ⛔ **反过来搜（找释放点确认有申请）是无效的**
> —— **漏掉的根本没写释放**。

拆开看：

```
正向搜：找所有 connect()，逐个确认有 disconnect()
        ✓ 能发现"漏了释放"的——因为它们成对出现时另一个不存在
反向搜：找所有 disconnect()，确认有 connect()
        ✗ 漏掉释放的那次调用，压根没有 disconnect() 可找
```

**这是 [EC-01](../common/blocks.md#ec-01-查不到--没有)（查不到 ≠ 没有）的一个精确变体**：
反向搜会**返回 0 条**，而 0 条既可能是"都配对了"也可能是"根本没写"——
**两个方向的结果无法区分**。

**判据（通用化）**：

> **要查「漏了 B」，必须从 A 出发找 B，不能从 B 出发。**
> 从 B 出发时，漏掉的那些**不在搜索结果里**，
> 于是"0 命中"被误读成"都做到了"。

ⓘ 同族还有：查「有没有漏写 disconnect」要从 `connect` 出发；
查「缓存有没有失效路径」要从缓存**写入点**出发（GA-05）；
查「状态 exit 有没有清理」要从 `enter()` 出发（GA-06，判据是
**enter 与 exit 逐个配对**，⛔ 不是"看起来没问题"）。

## 五、判据要重新定义问题，不要直接给答案

GA-03（硬编码易变值）的判据：

> ⛔ 判据不是"**能不能改**"，而是"**改它要不要重新打包**"。

⚠ 「能不能改」几乎对所有值都成立——所以它不是判据。
换成"改它要不要重新打包"，立刻能区分：

| 值 | 能不能改 | 改了要重新打包吗 |
|---|---|---|
| 动画名字符串 | 能 | 要 → **是硬编码** |
| 配置表里的数值 | 能 | 不要 → 不是 |

ⓘ 类似的好判据（都可抄这个思路）：
- GA-04：**数据不变的帧里，赋值次数应为 0**（不是"大概不会每帧改"，**要实测**）
- GA-05 三问：什么时候失效 / 谁是权威源 / 推还是拉
  （**答不出 = 缺陷**；⛔ 答"不需要"通常意味着永不失效）

**判据：这个问法会不会对大多数情况都答"是"？**
会 → 它没有区分力，要换一个问法。

## 六、⛔ 清单要声明豁免，否则体积检查会误伤

实测：109 份反模式册**全部**带这一行：

```markdown
<!-- oversize-exempt: 反模式清单，审核用 -->
```

**为什么必须声明**：反模式清单是**查表型**文档
（用法是"我这个情况属于哪条"，不是从头读到尾），
**它只会增长**——拆了还会再超。

ⓘ 与第十五条同源：约束要么生效，要么正式改掉。
⛔ 反模式册若不声明，体积检查会逼着人拆一份
**本来就该在一起**的对照表——拆开后每次要翻两个文件。
