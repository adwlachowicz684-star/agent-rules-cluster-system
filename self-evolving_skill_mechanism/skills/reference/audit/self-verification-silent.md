# 自检协议·静默类：检查在跑，但没在查

> **本区性质：audit / 不能怎么做。**
> **有检查、有输出、有绿色信号——但它根本没在查。**
> 这是最危险的一类：**它还在输出通过**。

---

## 一、检查项必须能红

加检查项时**同步加坏样例**，确认它真能查出来。永远绿的检查等于没有检查。

```bash
python3 scripts/lint.py --self-test    # 造已知缺陷，跑一遍必须全部命中
```

⚠ 本能会只造「应该报出来」的样例。必须**正反两侧都造**：

| 该造的样例 | 验证什么 |
|---|---|
| 有缺陷的对象 | 检查项抓得到（不会假阴性） |
| 没缺陷的对象 | 检查项不误伤（不会假阳性） |
| **自检用例自身** | 用例没造错（否则它永远通过） |

第三条最易漏：坏样例里若漏建「本该存在的文件」，
「已存在的引用不该报」这条就从未被验证过——**用例自己假通过了**。

## 二、工具必须自报扫描范围

输出「通过」时必须附上：扫了几个目标、跳过了什么。

**在空集上跑出来的通过没有意义。** 目录不存在、后缀不匹配、路径基准写错，
都会让检查在空集上跑完还显示通过——这种失效从输出上完全看不出来。

```bash
python3 scripts/lint.py
# 扫描范围：引擎自身 23 个文件；domains 技能包 0 个；未初始化大类 9 个
#   ! 本次未检查到任何 domains 技能包 → 下面若显示「通过」，只代表引擎自身文件合规
```

判据：**不看你有没有输出「通过」，看你有没有说明检查了什么。**


### ⛔ 第 5 次：入口文件不在扫描范围内

`check_orphan_table_row` 第一版扫 `reference/`，
而**这个缺陷就是在 `SKILL.md` 里发现的**——它不在那个目录下。

⚠ **最常被读的文件，恰恰是最容易漏在检查范围外的**：
它是单点，不在任何"批量扫描的目录"里。

**判据**：

> **新建扫描类检查时，先问：入口文件在不在范围内？**
> ⛔ 只扫"内容目录"会让入口永远不被检查。

ⓘ 同形态已出现 5 次：断链检查、扫描器清单、体积检查、
引擎侧 `check_size` 的 `glob`→`rglob`、本次。
**每次都是"目录分层了，检查没跟着走"**。


## 七、新建设施必须配「接入率检查」

仓库里常见一类设施：造出来是为了**每处都接上**的——参数守卫、日志、
错误上报、豁免标记。它的价值 = **覆盖率 × 单次价值**；覆盖率低时约等于零。

但设施造好后，没有任何机制提醒"还有 17 个入口没接"。
于是它稳定处于「有这个东西，但大部分地方没用」的状态，
而**没接的地方表现与没造之前完全一样**——静默。

实测：一个未知参数守卫造好后，23 个脚本里只有 6 个接了；
另外一个"剔除非代码行"的辅助函数，只有 2 条规则调用它，
其余同类规则继续各写各的、各漏各的。

| 强度 | 做法 |
|---|---|
| ★★★ | 自动统计「应接入点」与「实际接入点」，差集**逐个列出** |
| ★★☆ | 至少让新建设施的文档里写明"怎么确认全覆盖"的命令 |

差集要**逐个列出**，不能只报个数——个数不知道去哪补。

⚠ 「应接入点」要认全合法形态，否则会把**换了一种实现方式**的入口
误报成没接。实测：某脚本用自建 `KNOWN_FLAGS` 名单拒绝未知参数，
效果与 `_flagguard` 完全相同，但按"只有 _flagguard 算接入"来查会被
报成漏接——**误报的检查会被关掉**。

落地形态（code-audit 侧 `check-list-drift.py` 第 5 项）：
`_flagguard` / `argparse` / 自建 `KNOWN_*` 名单，三者任一即算接入。

## 九、单条规则异常不能静默

规则执行时抛异常，若被 `except Exception: pass` 吞掉并计入"0 命中"，
那么**规则整个挂了**与**这次确实没问题**在输出上完全一样。

实测：一次重构漏写了一个函数，调用它的规则抛 `NameError` 被吞，
该规则的命中数从 6 降到 0 —— 当时被当成"精度修好了"。
**自检恰好也通过了**，因为自检喂的是样本而不是那段坏代码。

| 强度 | 做法 |
|---|---|
| ★★★ | 单条规则的异常单独计数并上报，不混进"无命中" |
| ★★★ | 把「规则命中数突降到 0」本身当成可疑信号 |
| ★★☆ | 至少 stderr 打印，不静默 |

与「三态，不要二态」同源：那节讲**整个工具**的失败 vs 无结果，
本节讲**单条规则**——粒度更细，也更难发现。

## 十三、检查长期红灯 = 检查已经死了

一个检查如果**长期失败而没人修**，它就不再是检查。

人的反应是可以预测的：第一次红会去看，第十次红会跳过，第一百次红会
在脚本里加 `|| true`。此后它输出什么都与决策无关——**真问题混进来时
同样看不见**。

实测（本仓库 CI）：`--check` 因注册表未同步持续退出码 1，五个语言包的
自检在流水线里一次都没跑。更糟的是**红灯本身掩盖了这个事实**——
所有人都以为"CI 红是常态"，没人去看红的是哪一条。

| 强度 | 做法 |
|---|---|
| ★★★ | CI 里区分「新增失败」与「已知失败」，只对前者阻断 |
| ★★☆ | 已知失败必须有显式登记（为什么暂不修、谁负责、何时清） |
| ★☆☆ | 至少不允许在命令后裸写 `|| true` 把红灯抹成绿的 |

**红线**：把失败改成成功（吞异常 / `|| true` / 降级为 info）比留着红灯更糟——
后者至少还看得到，前者连信号都没了。这与第九条同源：
那节讲「单条规则异常不能静默」，本节讲「整条检查的失败不能常态化」。

## 十五、约束要么生效，要么正式改掉——没有「记一笔」这个选项

声明了上限，超限却只打一行 INFO，这等于**取消了这条约束**，
而且比没有约束更糟：读者以为它还在生效。

实测（本仓库）：7 个脚本超 300 行上限（scan-ts 1992、rule-registry 1115、
scan-app 864…），`check-skill.py` 一律以 INFO 打印，理由是
「脚本按需执行不占上下文」。理由本身是成立的——**但那就该把脚本从
这条约束里正式剔除，写进例外条款**，而不是每次都报又不阻断。

| 做法 | 后果 |
|---|---|
| 超限 → 报错 | 真实约束，但会被迫拆好的文件 |
| 超限 → 警告 | 可接受，但要有清理期限，否则警告堆积成噪音 |
| **超限 → INFO + 合理理由** | **约束已死**，只是没人宣布 |
| 正式写进例外条款 | 诚实：这条约束不适用于该类对象 |

判据：**能不能举出一个"因为这条检查而改了代码"的实例？**
举不出，它就是死的——无论它当前输出什么。

与第十三条的分界：第十三条讲检查**失败**被常态化，
本节讲检查**通过**（且永远通过）被当成约束还在。

## 十六、分支不可达 = 规则静默失效，而测试看不见

一条规则的代码可能因为上游逻辑而**永远走不到**，
表现为"规则在、测试绿、但从不报"。

实测（本仓库 Q06）：排除条件的 `prev` 切片包含了当前行，
于是 `var.clear()` 自身必然命中 `.clear(` → 恒 `continue`
→ **Q06 对 `clear` 形态永远不报**。这个分支里还藏着一个 `NameError`，
因为从未执行过所以也没暴露。

**为什么测试发现不了**：测试用的是能走到的路径。
「某条规则从不命中」不在任何断言里——除非专门检查
「每条规则都必须有 TP 命中」（本仓库 `rule-registry.py --test` 正是这么做的，
但 fixture 只覆盖了 `clear` 以外的形态，所以照样全绿）。

| 检测手段 | 能发现什么 |
|---|---|
| 覆盖率检查（每条规则须有 TP） | 规则整体失效 |
| **同规则多形态样本**（tp / tp2 / tp3） | 某个形态失效 |
| 变异测试 | 样本有没有能力发现问题 |

与第十条的分界：第十条讲判据**认不出等价写法**，
本节讲判据的**代码路径根本没被执行到**。

### ⚠ 第二次：连续两次 write，第二次用了旧的变量

写 `check_scan_scope` 时自己踩的（2026-09-25）：

```python
s = open(p).read()
o1 = '...'; n1 = '...'
open(p, 'w').write(s.replace(o1, n1, 1))   # ① 生效
o2 = '...'; n2 = '...'
open(p, 'w').write(s.replace(o2, n2, 1))   # ⛔ s 还是旧的！① 被覆盖
```

**脚本打印了两次「已修」，实际只留下第二次。** 全程绿信号。

ⓘ 与第一版「中途重新 `open(p).read()` 丢弃内存态改动」是同一形态，
只是触发方式不同：一个是**读回旧内容**，一个是**写回旧变量**。

**判据**：

> **连续多次改同一个文件时，第二次起必须重新读盘**
> （或把改动累积到同一个变量里再一次写出）。
> 改完立刻校验**关键字或文件大小**——别只信脚本打印的「已完成」。


## 十七、格式缺陷 100% 静默，只能靠自动查

往 Markdown 里**插入**段落时，常见写法是
`text.replace(anchor, new_text + anchor)`。若 `new_text` 结尾带了 `## `
（为下一段预留），拼接后就成了 `## 标题` —— 渲染成错误的层级，
而**写它的人看不出来**：diff 里是两个各自正常的 `##`，谁也不会盯着数。

本仓库实测同一处写法连犯 3 次，次次都以为改完了。

这类缺陷的共同特征：**没有任何检查会去数 `#` 的个数**，
且它不影响任何脚本运行 —— 100% 静默。

**能发现它的只有自动检查。** 本轮为此在 `lint.py` 加了
`check_markdown_headings`（含正反自检：代码块里的 `#` 不误报）。

推广：凡是**靠字符串拼接生成**的内容（Markdown、代码模板、配置），
都要有一个「生成结果是否合法」的自动检查，
而不是相信拼接逻辑写对了。

| 强度 | 做法 |
|---|---|
| ★★★ | 生成后跑格式校验（Markdown 用解析器，代码用 AST） |
| ★★☆ | 至少检查最易犯的几种（重复 `#`、缩进标题、未闭合围栏） |
| ★☆☆ | 提交前人工看一次渲染结果 |

**红线**：这类拼接 bug 不能靠"下次注意"——它已经证明会重复发生。

**同一形态还有「改了但没落盘」**：分段改文件时，若某个分支只改了内存变量
而后续又 `open(p).read()` 重新读盘，前面所有内存态改动会被**无声丢弃**，
而脚本照样打印「已补」——绿信号，空的。

本仓库实测：改 README 时先 `s = s.replace(...)` 加了整段内容，
随后又 `s = open(p).read()` 只为改一个数字，最后写盘
→ 整段内容丢失，只剩数字改动生效。

| 做法 | 后果 |
|---|---|
| 全程用同一个变量，**只写一次盘** | 安全 |
| 每段改动后立即写盘 | 安全 |
| **中途重新 `open(p).read()`** | **前面所有未落盘的改动静默丢失** |

判据：改完立刻校验**文件大小或关键字**，别只信脚本打印的「已完成」。
本轮正是靠"上传字节数与改动前一致"才发现这次丢失的。

## 十八、查不到 ≠ 没有——三种「0 命中」

**同一结论，三个来源，都踩过**：

```text
① 空转   输入语料为空 → 收集 0 条 → 脚本正常退出、不报错
         （残留迁移前旧路径 flow/godot，该目录下是子目录没有直接 .md，
           listdir 过滤 .md 得空列表 → 整套「待核对」机制空转一整轮）

② 误判   查法不对 → 判 0 命中 → 误判为「真空白」→ 去新建一个早已存在的
         （查「录像回放」判 0，实际有 replay.md；
           查「敌人AI」判 0，实际有 4 篇。已踩两次）

③ 真空白  确实没有
```

⛔ **① 和 ② 都会输出"没有"**，而只有 ③ 是真的没有。
**失败模式是"返回 0 条"而不是"报错"，所以任何"能跑通"的检查都查不出来。**

| 类型 | 怎么识别 | 怎么防 |
|---|---|---|
| **空转** | 扫之前先**断言输入非空** | 目标数为 0 时报 error，不是 info |
| **误判** | 用**原子词**再查一次 | 别用连续词组（`录像回放` 匹配不到 `回放`） |
| **真空白** | 前两者排除后才成立 | — |

**判据：报「没有」之前，先证明「查了」且「查法对」。**

⚠ **原子词这一条对查重尤其致命**：查重判 0 命中 → 判定"不重复" → 新增，
于是同一个东西在库里变成两条。**查不到不等于没有，等于没查到。**

## 二十一、「声明了」不等于「生效了」——假生效

配置写了、标记打了、豁免声明了，**但代码路径根本读不到它**。
这类失效比"没声明"更糟：**没声明至少知道要处理，假生效会让人以为已经处理过了**。

实测三种形态：

```text
① 正则不吃换行
   EXEMPT_RX = r'<!-- oversize-exempt: (.+?) -->'
   理由写成多行 → 匹配失败 → 豁免没生效 → 文件仍被判超限
   （`.` 默认不含 \n。加了 re.S 才好）

② 名单写死，新增的进不来
   注册表里没有 scan-rust → 规则能跑但**不计入任何统计**
   （同一个坑在本仓库踩过六次）

③ 分支不可达
   检查解析不到写死正则 → 返回"无法解析" → 调用处跳过 → 检查静默停摆
```

**共同点：都有一个"看起来生效了"的表面**——
配置里能看到、标记能搜到、声明能读出来。

**判据：能不能举出一个「因为它而改变了结果」的实例？**
举不出 → 它大概率是假生效。

| 类型 | 怎么防 |
|---|---|
| 解析类（正则/配置） | 用**多行/边界**样本实测，不只是单行正常样本 |
| 名单类 | 与**事实源**做交叉比对（`check-list-drift.py` 的做法） |
| 分支类 | 断言"检查真的跑了"，不是只断言"没报错" |

⚠ **对豁免尤其致命**：豁免的本意是"有理由可以不拆"，
若它没生效，文件会一直被报，**而人以为已经豁免了**——
最后要么无视噪音，要么为了消掉提示去砍内容。
**两种都是被一个假信号驱动的错误决策。**


### ⛔ 变体：检查因「被测对象缺了东西」而静默罢工

写 `check_antipattern_tables` 时自己踩的（EV-M11）：

```python
# 用完整匹配识别类型
is_omit = all(k in j for k in ("漏写", "后果", "审查规则"))
```

⛔ **缺了「审查规则」就识别不出这是遗漏类表 → 检查直接跳过。**
而缺列恰恰是要报的问题。

**检查因被测对象缺了东西而静默罢工**——
比没有检查更危险，因为它还在输出绿色结果。

**判据**：

> **先按主键认出它是哪一类，再查这一类的必需列。**
> ⛔ 不要用「全部必需列都在」来判定类型——
> 那样缺任何一个都会让检查自己消失。

⇒ 改成 `is_omit = "漏写" in j`（主键识别），缺列单独报。

ⓘ 与第十六条「分支不可达」同族：
一个是分支走进不去，一个是类型认不出来——**都是检查自己不生效**。


> ⛔ **「检查没在查」这一族**（一 / 七 / 十八 / 二十一）
> 的**写检查六问清单**见
> [`../howto/writing-checks.md`](../howto/writing-checks.md)。
> 本册只记失效形态；六问的用法是**写检查时对照**，
> ⛔ 混进来会让查表的人要跳过一大段清单。

## ⛔ 最危险的一族：测量工具本身失效

前面讲的是「**被测对象**有问题」，还有一类完全不同：

> **你用来发现问题的工具/方法，本身是失效的。**

实测（反模式册的「坑类」13 份，全是这个形态）：

| 坑 | 后果 |
|---|---|
| 崩溃时看 stdout | `print` 未刷新，**最后一行日志骗你** |
| 靠 `MEMORY_STATIC` 查 release 泄漏 | **恒为 0**，得到"没问题" |
| 多线程打断点 | 断点**静默失效**，以为代码没跑 |
| 只看 FPS 判断瓶颈 | 无法区分 CPU/GPU，**优化方向错** |
| release 用 `assert` 校验 | 被剥离，**校验消失** |

### 为什么比前三类危险

| | 被测对象有问题 | 测量工具有问题 |
|---|---|---|
| 你会得到 | 一个错误结果 | **一个"没问题"的结论** |
| 你的动作 | 去修那个错误 | **基于假结论做决策，且不质疑结论** |

ⓘ 两端的表述几乎一致：
- 那边：「断点**静默失效**，以为代码没跑」
- 本册：「检查存在、跑得绿、返回 0 条——三种都可能是"没在查"」

**判据**：

> **这个工具/方法，有没有可能给出「没问题」而实际上没测到？**
> 能 → 它必须先被验证，才能用来验证别人。

ⓘ 与第十九条（自检全绿 ≠ 覆盖了历史缺陷）同源：
**工具的绿，不等于被测对象的绿。**

### ⚠ 第 4 次：同一个脚本里连续两次 `write(s.replace(...))`

```python
open(p,'w').write(s.replace(o1, n1))   # ① 生效，但 s 没更新
open(p,'w').write(s.replace(o2, n2))   # ⛔ s 还是旧的 → ① 被覆盖
```

⚠ **两次都打印了「已修」，实际只留下第二次的那处。**

ⓘ 与前三次同族，**但触发方式不同**：
前三次是"写了但没被读到"，这次是"**读了但没写进去**"。

⇒ 判据：**一个脚本里对同一个文件做多处修改时，
要么把 `s` 重新赋值，要么攒到最后一次性 `write`。**
⛔ `write(s.replace(...))` 这种写法最多只能出现一次。

### ⚠ 第三次：声明的格式要求没被满足，声明静默失效

同一天里踩的第二次（EV-M21）：

```html
<!--
flow-type: meta
oversize-exempt: 理由
-->
```

而正则要求 `oversize-exempt` **紧跟** `<!--`——
`\s*` 匹配不到 `flow-type: meta` 这段文字 → **声明了但不生效**。

ⓘ 与第一次（re.S 不吃换行）是**同一形态的第二次**：
都是「**写了，但格式没被满足**」。

**判据**：

> **声明的格式要求是什么？我的写法满足吗？**
> ⛔ 声明之后要**看到它真的改变了结果**，
> 不能只看"我写了"。

ⓘ 三次合起来看：**声明这个动作本身不产生效力**，
它必须被**某个读它的东西**按它期待的格式读到。
