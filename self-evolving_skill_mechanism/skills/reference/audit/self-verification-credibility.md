# 自检协议·可信度类：信号有了，但真假难辨

> **本区性质：audit / 不能怎么做。**
> **信号确实产生了，但无法判断它是不是真的**——
> 「没跑起来」冒充「跑了没命中」、手填字段全同值、豁免加了却没生效。

---

## 三、三态，不要二态

「没跑起来」与「跑了但没命中」是两件事，合并成一个返回值就会互相冒充：

| 合并后 | 后果 |
|---|---|
| 失败 → 当成无结果 | 扫描器崩溃被统计成「这条没有样本」 |
| 无结果 → 当成通过 | 「未覆盖」被算进「已验证」 |

返回 `(ok, result, error)` 三元组，失败单独报出：

```python
ok, hits, err = _run_scanner(scanner, src, rule_id)
# ok=False  → 没跑起来（超时/崩溃/无输出），hits 无意义
# ok=True   → 跑起来了，hits 是多少就是多少
```

同理，统计口径也要分：「未覆盖 N 条」与「执行失败 M 条」分开报，
不要把失败并进未覆盖——那会让「到底有多少没验证」这个数字本身不可信。

## 四、检测类规则必须配正反双样本

每条能自动检出的规则，配两个样本：

| 样本 | 要求 | 证明什么 |
|---|---|---|
| `tp` | **必须命中** | 规则抓得到真问题（不是死规则） |
| `fp` | **必须不命中** | 规则不过宽（不是误报源） |

⚠ 本能会只写 tp——它直观、好造，而且跑通了很有成就感。
但**只写 tp 的规则，精度永远无法验证**：知道它抓得到，不知道它会不会误伤。

没配 fp 的规则，状态字段应停在「未验证」，不得与已验证的混在同一张表里
（见 `_hot.md` H015：混在一张表等于声称全部已验证）。

**样本形态要匹配判据作用域**：判据看单文件就给单文件样本；
判据看整棵工程（忽略清单、CI 配置、多入口的策略覆盖）就要给整棵目录，
否则样本根本触发不到那条规则，还以为规则失效了。

## 五、标注字段必须可回填

手填的状态字段（`verified` / 命中数 / 验证状态）**既没有填错的成本，
也没有填对的反馈**，于是会自然收敛到同一个值：全 `no`、全 `0`、全「未验证」。

表面「标注齐全」，实际上读的人还是得逐个怀疑——**字段活着，但已经死了**。

三条出路，按强度排：

| 强度 | 做法 |
|---|---|
| ★★★ | 能实测的 → **脚本跑完自动回填**，不许手填 |
| ★★☆ | 填不了的 → 检测退化：条目数 ≥ 阈值且取值只有一种 → 预警 |
| ★☆☆ | 至少让「未标注」可见（`lint.py` 已做） |

退化预警**不是要求标成「已验证」**，而是要求**有区分度**。
全 0 的命中列有两种可能：规则从没触发过，或触发了没人更新——
两种情况都得处理，但都不会自己报错。

## 八、豁免必须可验证

标记了豁免（`# ignore` / 白名单 / 例外清单）之后，**命中数就该减少**。
如果没减少，只有两种可能：豁免没接上，或豁免写错了位置。

实测：给某规则的三处命中加了行级豁免，命中数一条没变——
因为那条规则的分支里**根本没调用豁免判断**。
加了豁免却没生效是最容易被忽略的失效：人已经"处理过"了。

| 强度 | 做法 |
|---|---|
| ★★★ | 加豁免后立即复跑，断言命中数下降；不降就报错 |
| ★★☆ | 统计豁免标记总数 vs 实际生效数 |

⚠ 豁免位置也有讲究：只检查「上一行/本行」的实现里，
豁免注释**必须写成一行**——写成两行时第一行会滑出检查窗口，静默失效。

## 二十、未验证的结论必须条目化，不能只是一句注解

文档里写着大量"我没有实测过"的结论。这些如果和已验证结论混在一起，
读者无法区分"可以直接信"和"要先测一下"——
**而后者被当成前者用，正是最难排查的一类问题**：
代码写对了、逻辑想通了，但**前提是错的**。

⚠ **只写一句「待核实」是不够的**，它有三个问题：

| 问题 | 后果 |
|---|---|
| **无索引** | 想知道"我现在该验证哪些"要全文搜 |
| **无状态** | 验证完了也不知道记在哪 |
| **无归属** | 不知道该在什么环境验证 |

✅ 改成**条目**：有 ID、有状态、可按文档/关键词过滤、可运行时回填。

```
python3 verify.py --pending              # 现在该验证哪些
python3 verify.py --verify=V012 --result=failed --note="4.7.2 实测没有该节点"
```

**判据：能不能列出"我现在该验证哪些"？**
列不出 → 那些"待核实"只是注解，不是条目，
**等于没标**——半年后没人知道哪些结论是悬空的。

⛔ **标注"待核实"的值不得直接当生产参数用。**

## 二十二、自检全绿 ≠ 覆盖了历史缺陷

**手写用例证明的是「我写的这个样例能被查出」，
证明不了「历史上真实发生过的那个缺陷能被查出」。**

这两者的差距就是盲区，而且**实测差距不小**：
引擎侧把真实修过的 5 个缺陷做成变异回放，
其中 1 个（豁免只覆盖超限档、不覆盖接近上限档）**手写用例漏了**，
是跑变异才发现的。

⛔ 「自检 55/55 全绿」这个数字**没有覆盖语义**——
它只说明那 55 个手写样例都过了。

**判据：能不能列出「历史上修过哪些缺陷，各自被哪条用例守着」？**
列不出 → 全绿是虚假的安全感。

做法：把真实修过的缺陷沉淀成**可回放的变异**：

```text
mutations.json  每条：old 片段 → new 片段（改回缺陷）+ expect + 来源
mutate.py       注入 → 跑测试 → 看 KILLED / SURVIVED → 还原
```

| 结果 | 含义 | 处置 |
|---|---|---|
| **KILLED** | 测试抓到了 → 守住了 | 保持 |
| **SURVIVED** | 测试没抓到 → **盲区** | 补用例；或改变异的 expect 并写明"不该管"的理由 |
| **NOT_APPLIED** | 变异没生效 → **配置问题** | 更新 old 片段（代码改过了） |

⛔ **SURVIVED 与 NOT_APPLIED 必须分开**：
NOT_APPLIED 时测试当然绿，混在一起会被误报成 KILLED——
**于是「KILLED」可能只是因为变异压根没生效**。

⛔ **不能因为「看着绿」就删掉变异定义**——那等于抹掉历史。
SURVIVED 是诚实的现状，比删掉它有用得多。


## 二十三、「能数出来的」不等于「该判的」

判质量时最容易犯的错：**拿最容易数的东西代替判断**。

```
⛔ 「这个模块才 50 行，太空了」        ← 行数
⛔ 「这里有 200 条规则，肯定够全了」    ← 条数
⛔ 「12 个章节都写满了」               ← 结构完整度
⛔ 「自检 55/55 全绿」                 ← 用例数
```

**判据：这个指标能不能靠注水刷高？** 能 → 它不是质量指标。

```
行数     注水能撑满
条数     200 条人人都知道的 = 0 条有用的
章节数   12 个空章节比 3 个写透的差得多
自检数   见第二十二条：全绿 ≠ 覆盖了历史缺陷
```

充实度恰恰是**数不出来的那部分**：
覆盖面 / 规则完善 / 流程规整 / 原理透彻 /
逻辑严密 / 推导真实 / 深度 / **体量与域复杂度的匹配**。
判据见 `craft/substance.md`。

⚠ **体积上限特别容易被误读**：它是**加载成本**上限，不是充实度判据。
两个方向都会错：

| 误读 | 后果 |
|---|---|
| 「还没到上限 = 写够了」 | 空模块一直空着，没人管 |
| 「超了上限 = 写得好」 | **奖励注水** |

超限的正确处置是**拆分**（按需加载），不是表彰。

⛔ 把「精简但充实」误判成「空」会往好内容里注水，
**稀释信息密度**——比留着短内容更糟。


### ⛔ 变体：数「重复次数」不能用关键词，要用语义

建全局块（`common/blocks.md`）时自己踩的（2026-09-25）：

```
grep -rl "反例\|正反双样本" reference/   →  10 个文件
```

按这个数字抽了个全局块。**逐个核实后，「反例」有四种不同含义**：

| 出处 | 这里的「反例」指什么 |
|---|---|
| `craft/techniques.md:78` | 检测判据的正反样本 |
| `craft/taste.md:62` | **文档写作的反例**（写作手法） |
| `howto/knowledge-landing.md:54` | 写法对照表（排版手法） |
| `howto/consolidation-gate.md:32` | **例外情况**（被证伪时可绕开） |

**语义同义的实际只有 2 处**，不是 10 处。

⚠ **这正好是本条讲的那件事的一个更精确的形态**：
不是"拿可数指标代替判断"，而是
**拿"关键词出现"代替"语义是否相同"**。

**判据**：

> **统计"这条内容重复了多少次"时，
> 逐处核实的单位是「语义」，不是「词」。**
> ⛔ 词相同而义不同，会把不相干的内容算成同一类，
> 从而让"重复 ≥3 次"这个门槛**凭空达标**。

ⓘ 与第十四条（判据看语义方向，不看表面特征）同源：
一个是判据认错对象，一个是**统计认错对象**。


## 二十四、每个检查项都要能被**单独**验证（交叉审计）

反哺自 code-audit 的 `rule-registry.py --cross`。

`--test` 只查「tp 被自己命中 / fp 不被自己命中」，**两个方向都有盲区**：

| | 盲区 | 后果 |
|---|---|---|
| **A** | fp（正确写法示例）被**别的**规则命中 | 示例自带真缺陷，**会被人照抄**，文档价值变负的 |
| **B** | tp 没命中自己、却命中了别的 | **「通过」是蹭来的**，样本从没验证过它 |

两种都不影响 `--test` 的结论，**所以长期没人发现**——
实测首次跑出 37 条 A，其中多条是「正确写法」自带的真漏洞。

引擎侧的同构形态：**某个 `check_*` 在自检里一次都没被调用**。
它失效了自检照样全绿，因为**没有任何用例会因它而变红**。
实测：`check_root`（domains 未初始化的守门人）就是这么躺着的。

**判据：能不能把这一个检查项单独关掉，然后看到某条用例变红？**
不能 → 它没有用例，它的绿是白给的。

⚠ **这不是「用例数量」检查**（那是第二十三条批判的注水指标）：
判的是**有没有**覆盖（0 vs ≥1），不是有多少条。
一条能守住就行，十条注水的不如一条真的。

⛔ 实测一个反直觉的事实：
**把一条真断言换成 `chk(True)`，自检总数完全不变**（61/0 → 61/0）。
——数字对注水毫无抵抗力。所以覆盖必须靠**结构**（每个检查项有没有专属用例），
不能靠**总数**。

无法直接调用的检查项（如靠 subprocess 跑真实脚本实测退出码），
必须**显式登记**进 `INDIRECT_COVERAGE` 并写明理由：
⛔ 「找不到就说没有」正是 [EC-01](../common/blocks.md#ec-01-查不到--没有) 批判的失败模式。


### 回放历史缺陷：修过 ≠ 守着

**「修过了」和「有用例守着」是两件事。** 实测差距：

把 `check_size` 的 `rglob` 改回 `glob`（恢复当年修过的那个缺陷），
**自检照样 61/0 全绿**——这个缺陷修过，但**没有任何用例守着**。

(`reference/` 分成五区后，只扫顶层会让子区文档完全不参与体积检查。
同一形态在 code-audit 侧踩过三次：断链检查、扫描器清单、体积检查。)

做法：把修过的缺陷**注入回去**，看有没有用例变红。
引擎侧用 `scripts/mutate.py` + `assets/mutations.json`，
判据见第二十二条。

⛔ **不要因为「当年修过」就认为它不会再犯。**
修过只说明**改过一次代码**，不说明**有东西防止它再犯**。


### ⛔ 变异目标必须是测试套件真的会读到的东西

写变异定义时最容易搞错的一点，实测踩到过：

```
变异目标写成 reference/flow/sequence.md（文档文件）
测试套件是 lint.py --self-test（只测自造样本，不读真库文档）
→ 改文档当然不影响自检 → 报 SURVIVED
```

**这是变异定义写错了，不是真盲区。**
但它的表现形式跟真盲区一模一样（都是 SURVIVED），
于是会误导后面的人去补根本不需要补的用例。

**判据：变异目标必须被测试套件真的读到。**
文档内容类的缺陷只能靠 `lint` 跑真库发现，
⛔ 不能指望自检守住——**自检测的是检查逻辑，不是文档内容**。


## 二十五、验收通过 ≠ 做对了（假完成）

**验收清单能逐条打勾，但那一步其实没做对。**

实例（反哺自 game-dev 成就域）：

> ⚠ 本步最容易"看起来做完了"：**成就列表能显示就行**。
>
> ⛔ 常见假完成：把成就当成一个 `Array` 加几个字符串常量——
> 界面确实能列出成就，
> 但四类成就（一次性/累计/条件/复合）共用一套结构，
> 到做"击杀 100"时才发现**进度无处放**，
> 而此时 id 已经散落在代码各处。

拆成三步看：

```
① 验收清单打勾        ✓（界面能列成就）
② 这一步真的做对了？  ✗（四类结构没分）
③ 什么时候暴露？      做下一步才现形 → 那时 id 已散落各处
```

⚠ **假完成的代价不在"没做对"，而在"发现得太晚"**——
等到下一步才暴露，错误已经扩散，**改起来比重做贵**。

**两条判据，缺一就可能是假完成**：

| # | 判据 |
|---|---|
| 1 | **能不能当场演示？**（⛔ 只说"做了"不算） |
| 2 | **下一步能不能基于它继续？**（⛔ 下一步撞墙 = 这步是假的） |

第 2 条更狠：**假完成只有走到下一步才现形。**
所以「一个做完才进下一个」（`flow/sequence.md` 第三节）
不只是纪律，它同时是**假完成的探测器**。

⛔ **每个功能点都要写清「假完成长什么样」**：
不写这两行，验收清单再详细也可能全是假完成——
**因为没人知道"看起来做完了"长什么样**。
写法见 `flow/acceptance.md` 第四节。

ⓘ 与第八条同源：验收跑在**舒适环境**（局域网 <5ms、只测正常路径）
也是假完成的一种——它证明的是
「在不会出问题的条件下不会出问题」。


## 二十六、排障索引必须按「症状」建，不按注意事项

**出问题的人手里有的是症状，不是注意事项清单。**

实测：game-dev 的 97 个功能点文件里，**60 个**的「常见返工」
用的是三列表：

| 症状 | 原因 | 回到 |
|---|---|---|
| 客户端调 RPC 没反应**也不报错** | 默认 authority | S2 |
| 断线后实体残留 | 没接 `peer_disconnected` | S1 |

⚠ **注意事项只能防，不能查**——它假设读者已经知道问题出在哪一类，
而**不知道才要来查**。按注意事项建的索引，排障时用不上。

**「回到」这一列最常被省，也最有用**：
排障的终点是"去改某个地方"，不是"知道了原因"。

⛔ **最容易过期的是「回到」列**：流程一改（加步/删步/换顺序），
所有指向全错——而**表看起来还是完整的**
（症状对、原因对，只有指向错）。人会被引到一个无关的步上改。

ⓘ 与 [EC-01](../common/blocks.md#ec-01-查不到--没有) 同族：
**表在、内容对、指向错**是最难发现的失效形态。
⛔ 无法自动验证——没有工具知道"S2 现在还是不是那一步"。

写法见 `flow/diagnosis.md`。


## 二十七、查「漏了 B」必须从 A 出发，不能从 B 出发

**[EC-01](../common/blocks.md#ec-01-查不到--没有) 的精确变体，也是最容易搞反方向的一条。**

实测（GA-02 资源没配对）：

```
正向搜：找所有 connect()，逐个确认有 disconnect()
        ✓ 能发现漏了释放的
反向搜：找所有 disconnect()，确认有 connect()
        ✗ 漏掉释放的那次调用，压根没有 disconnect() 可找
```

⛔ **反向搜返回 0 条，而 0 条无法区分**：

```
"0 条 disconnect 找不到配对的 connect"
  → 可能是「都配对了」
  → 也可能是「根本没写 disconnect」
两个方向的**结果相同**，无法区分。
```

**判据（通用化）**：

> **要查「漏了 B」，必须从 A 出发找 B。**
> 从 B 出发时，漏掉的那些**不在搜索结果里**。

同族的三个实例（都是同一个搜索方向）：

| 要查 | 从哪出发 | ⛔ 不能从哪出发 |
|---|---|---|
| 有没有漏 `disconnect` | `connect` 调用点 | `disconnect` |
| 缓存有没有失效路径 | 缓存**写入点** | 失效点 |
| 状态 `exit` 有没有清理 | `enter()` 里创建的 | `exit()` |

⚠ **GA-06 的原话把这个判据说得很清楚**：
判据是 **enter 与 exit 逐个配对**，⛔ 不是"看起来没问题"。

写法与两种反模式表的区分见 `../audit/antipattern-form.md`。


## 二十八、⛔ 变异定义会随代码改动而失效（NOT_APPLIED ≠ 安全）

回放时发现 EV-M10 变成 `NOT_APPLIED`：

```
old 片段在当前文件里找不到 —— 代码改过了，变异定义需要更新
```

**这不是"缺陷不会再犯"，是"变异已经不在测了"。**

⛔ 最危险的读法：把 `NOT_APPLIED` 当成"安全"。
它的真实含义是**这条变异从未跑过**——
既不 KILLED 也不 SURVIVED，**什么都没验证**。

**判据**：

> **`NOT_APPLIED` 与 `SURVIVED` 必须分开统计。**
> 混在一起的话，"KILLED"可能只是因为变异压根没生效
> （第九条已记过这一条，这里是它的**维护期**形态）。

ⓘ 因为检查逻辑被重构（如扩展正则、改基准目录），
变异的 `old` 片段会失配——**这是正常的**，
但必须**立即更新变异定义**，不能放着不管。

判据：**每次回放后，`NOT_APPLIED` 必须为 0**；
不为 0 就说明有变异已经不在守护任何东西了。
