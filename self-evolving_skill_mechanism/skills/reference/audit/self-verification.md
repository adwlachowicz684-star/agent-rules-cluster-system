# 自检协议（索引）

> **本区性质：audit / 不能怎么做（索引）。**
> 本文件是**索引**，不是内容。20 条自检协议按**失效大类**拆成了三份。

ⓘ **为什么按失效大类拆**：原文件 522 行、25 个章节。
更实际的问题是——**查一个失效形态时不必读另外两类**。

| 文件 | 判什么 | 一句话 |
|---|---|---|
| [`self-verification-silent.md`](self-verification-silent.md) | **检查在跑，但没在查** | 有绿色信号，但它根本没执行 |
| [`self-verification-falsepos.md`](self-verification-falsepos.md) | **检查在查，但判据不准** | 把正确写法判成违规 |
| [`self-verification-credibility.md`](self-verification-credibility.md) | **信号有了，但真假难辨** | 无法判断信号是不是真的 |

**判据一句话**：
- 它**有没有在查** → `silent`（最危险：还在输出通过）
- 它在查但**认错了对象** → `falsepos`
- 信号有了但**不知真假** → `credibility`

⚠ **编号是全局的**（一~二十），跨文件引用 `…#十三`、`…#十四` 依然有效。

---

## 为什么单列一节

技能库里的"检查"分两类：查外部对象（代码 / 文档 / 配置）与查库自身。
后者**没有外部反馈**——它说通过了，没人能证伪。
所以必须单列协议，规定"凭什么相信一个检查在真的检查"。

## 怎么用

| 场景 | 去哪 |
|---|---|
| 加了一个检查项 | `silent`（先确认它真能红） |
| 检查报出一堆问题 | `falsepos`（先确认不是误报） |
| 报告看起来正常 | `credibility`（先确认信号是真的） |

## 落地强度对照

| 强度 | 形式 | 例 |
|---|---|---|
| ★★★ | 脚本自动查 | `lint.py` 报死链 / 重复副本 / 标注退化 / 扫描范围 / 豁免未生效 |
| ★★☆ | 流程某一步的判据 | 「加检查项 → 同步加 `--self-test` 坏样例」 |
| ★☆☆ | 可判定的检查项 | 「输出『通过』时附扫描范围」—— 一眼能看出做没做 |
| ☆☆☆ | 「要注意自检有效性」 | ❌ 不合格，不许停在这 |

## 与「知识点落地」的关系

`knowledge-landing.md` 管**知识点有没有改变行为**；
本节管**声称在做的检查是不是真在查**。

一条检查可以写得落地、判据清晰、命令化良好，却**一次也没真正执行过**——
它依然通过前者的检查。所以是两道关，顺序是先落地再自检。
