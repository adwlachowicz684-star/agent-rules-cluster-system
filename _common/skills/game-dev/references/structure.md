# 结构框架总纲

---

## 1. 命名

| 层 | 旧名 | **新名** | 回答 | 组织 | 比喻 |
|---|---|---|---|---|---|
| 流程 | `procedure/` | **`flow/`** | 按什么顺序做、每步产出什么、怎么验收 | 按**功能点** | 施工图（分工序、有验收） |
| 做法 | `flow/` | **`howto/`** | 这个东西怎么做（选型 + 可抄代码） | 按**域** | 工艺手册（查细节） |
| 审核 | `audit/` | `audit/`（不变） | 不能怎么做 | 按**域** | 质检表 |

⚠ **改名理由**：`flow` 在中文语境里直译就是"流程"，而原 `flow/` 装的其实是
"某个域怎么做"的知识，**不是流程**。名字与内容错位，导致每次讨论都要先解释
"你说的 flow 是哪个 flow"。现在名字即动作：

```text
定做什么 → 走 flow（流程·含步骤节点）→ 逐步取用 → 过 audit
              ↓ 每一步按需
          查 howto 的那一段 / 审 audit 的哪几条
```

⚠ **howto 和 audit 不是入口，是被流程调度的资源。**
⛔ 不要一上来就读 howto 全文——先定流程，流程告诉你读哪一段。

三者**正交**，不构成包含关系。⛔ 不要把 howto 塞进 flow，也不要把 audit 混进 howto。

## 1.5 全局层（common/）：多对多，不是一对一

⚠ **三层之外还有一层**：`common/`。它放的是
**"⛔ 不可能每个功能里单独写"**的内容。

| | 三层（flow/howto/audit） | 全局层（common/） |
|---|---|---|
| 组织 | 按**域** | 按**跨功能主题** |
| 被引用 | 域自己用 | **多个域共用** |
| 例 | 战斗怎么做 | 参数类型怎么审 |

### 为什么必须单独一层

ⓘ 统计：缓存出现在 48 个域、状态机 26 个、对象池 12 个、硬编码 11 个。

⛔ **每个域各写一遍 → 改一处要改几十处，且必然漂移。**

### 多对多

```
GC-05 缓存失效 ←── datatable / ui / save / economy   （一块 → 多域）
ui.md ──→ GC-01 GC-02 GC-04 GC-05 GC-06              （一域 → 多块）
```

ⓘ 例：**埋点**的部分功能会被多个不同的埋点系统共用 ——
这就是一个块被多个域引用的典型。

### ⛔ 单向登记不算索引

| 方向 | 判据 |
|---|---|
| 表 → 文档 | 表说"A 域用 GC-01"，A 域文档里**必须真有**该引用 |
| 文档 → 表 | 文档里出现 `GC-01`，表里**必须登记** |

⚠ 只在一边登记 = 做的时候照样找不到。双向由
`scripts/check-common-index.py` 校验。

### 与对称性检查的关系

ⓘ **不要求 howto↔audit 一对一**。
全局性内容（如"参数类型不符"）横跨所有域，
⛔ 不能要求每个 howto 域里都有一份对应内容。
✅ 判定覆盖时，**指向 common 块也算覆盖**。

## 1.6 主观层（craft/）：做到什么程度算好

⚠ **三层 + 全局层之外，还有 `craft/`。** 它放的是
**"没有标准答案，但有行业共识"**的内容。

| | howto / audit | **craft/** |
|---|---|---|
| 回答 | 怎么做 / 会错在哪 | **做到什么程度算好** |
| 性质 | **事实**（可核实） | ⚠ **经验**（主观） |
| 能否引官方 | ✅ | ⛔ **本层不提供官方口径** |
| 接入字段 | 【读】/【审】 | **【品】** |

⛔ **为什么单列一层**：混进 howto 会让"事实"与"经验"无法区分。
实测教训：官方精度表被当成经验值、经验区间被当成官方数值，
两种误用方向相反但**同样有害**。分层是为了让引用者一眼知道该不该信。

ⓘ **【品】是可选字段**（见 4.1.1）：技术性 Step 没有审美维度时不填，
⛔ 硬填是噪音；但**有审美/手感维度的必填** ——
功能全对而没有【品】的产物，会通过所有技术检查，却被评为"像 Demo"。

### 本层的三条禁忌

1. ⛔ **不要把经验区间当官方数值引用** —— 需要官方口径时查 howto
2. ⛔ **不要只抄区间中值** —— 两端对应不同体验，中值两边不讨好
3. ⛔ **不要用堆资源解决廉价感** —— 廉价感来自不协调，不是资源少

## 2. 三层的边界判据

判断一段内容该放哪层，用这三个问题：

| 问题 | 是 → |
|---|---|
| 它描述**时间顺序**（先做什么后做什么）？ | `flow/` |
| 它描述**某个东西本身的构造**（API、参数、代码）？ | `howto/` |
| 它描述**出错的样子 / 禁止事项**？ | `audit/` |

⚠ **"⚠ 注意"类内容容易放错层。** 判据：

- 「这个 API 4.7 才有」→ ⚠ 是**做法的前提** → `howto/`
- 「写成 X 会导致 Y 崩」→ ⛔ 是**错误特征** → `audit/`
- 「这一步做完要先验 X 再进下一步」→ ⚠ 是**工序约束** → `flow/`

⛔ 同一句话不要在三处重复三遍。每层各写各的，靠链接互指。

## 3. 调度模型：需求 → 流程 → 逐步取用

ⓘ **顺序是先定「做什么」，再定流程，最后才按流程逐步取用 howto / audit。**
⚠ 不是先读 howto。howto 和 audit 是**被流程调度的资源**，不是入口。

```
① 定做什么     需求 → 写清楚「做什么 / ⛔不做什么 / 验收标准」
                   ↓
② 定流程        按需求从 flow/ 派生本次流程（细化流程 or 骨架）
                   ↓  ← 这一步决定后面每一步要读哪些 howto、审哪些 audit
③ 逐步执行      每个 Step：读该步的 howto 片段 → 做 → 验 → 审该步条目
                   ↓
④ 功能点收尾    整体过一遍该功能点的 audit 条目
```

⚠ **为什么「定做什么」必须在最前**：流程是从需求派生出来的，不是固定的。
同一个域（比如战斗），"做个伤害结算"和"做一套连招系统"是**两条不同的流程**——
先读 howto 会让你被 howto 的完整内容带着走，做出超出需求的东西。

### 3.1 第 ① 步：定做什么

产出三行（⛔ 缺一不可）：

```text
做什么：<一句话>
不做什么：⛔ <至少两条>
验收标准：<可观测，不是"能跑">
```

⚠ **"不做什么"必须有至少两条。** 边界不清就开工，做出来的是另一个东西。

### 3.2 第 ② 步：定流程

| 情况 | 怎么做 |
|---|---|
| 域有细化流程 | 打开 `flow/<域>/00-域流程总览.md`，按依赖挑**本次需要的功能点** |
| 域无细化流程 | 套 `_骨架.md`，把六步按本次需求具体化 |

ⓘ **挑功能点，不是全做。** 流程总览列的是该域全部功能点，本次需求通常只触及一部分。
⚠ 全做 = 做过头 = 做出需求外的东西 + 浪费。

定流程时同时确定：
- 每个功能点要读的 howto 章节
- 每个功能点末尾要过的 audit 条目

✅ **这一步是"计划"，产出一份本次的执行清单**。后面按清单走，不再回头翻全量文档。

### 3.3 第 ③ 步：逐步取用

每步只加载**该步需要的**那部分：

```
Step N
  【读】howto/godot/<域>.md#<章节>     ← 只这一段
  【做】…
  【产出】…
  【判据】…
  【审】audit/godot/<域>.md#<条目>     ← 只这几条
```

⚠ 这是本框架的核心收益：**一次调用不需要读 537 行**。
以前是"打开 combat.md 自己找"，现在是"流程告诉你读第几节、审第几条"。

## 4. 节点规范：Step 怎么写

ⓘ 每个 Step 是一个**节点**。节点化有两个目的：
一是让每步可独立验收，二是**为后续流程工具预留**——工具要能按节点记录进度。

### 4.1 节点格式

```markdown
### Step 3　加重力　`[character/02#S3]`

【读】howto/godot/character.md#重力
【做】velocity.y += gravity * delta
【产出】角色会下落并停在地面
【判据】落地后完全静止，⛔ 有抖动就是错的
【审】audit/godot/character.md#12
【品】craft/godot/feel-params.md#1. 土狼时间（Coyote Time）
```

| 字段 | 必填 | 说明 |
|---|---|---|
| 节点 ID `[域/文件#S序号]` | ✅ | ⚠ **稳定标识**，流程工具按它记录状态。⛔ 不要中途改 |
| 【读】 | ✅ | howto 锚点。**⛔ 不许指向整个文件**，那等于没指 |
| 【做】 | ✅ | 具体动作 |
| 【产出】 | ✅ | 落在磁盘/场景里，能指认 |
| 【判据】 | ✅ | ⚠ **可观测**。⛔ "感觉对了"不算 |
| 【审】 | ✅ | audit 条目号。该步相关的即时检查 |
| 【品】 | ⚠ 可选 | craft 锚点。**做到什么程度算好**。有审美/手感维度的 Step 必填 |

⚠ 节点 ID 稳定的原因：后续流程工具要存"哪个节点做完了"。ID 一改，进度就断了。

### 4.1.1 【品】字段：第四层

ⓘ 前四层回答"怎么做 / 怎么查错 / 按什么顺序做"。**【品】回答"做到什么程度算好"**。

| | howto【读】 | audit【审】 | craft【品】 |
|---|---|---|---|
| 回答 | 怎么做 | 会错在哪 | 做到什么程度算好 |
| 性质 | 事实 | 事实 | ⚠ **经验（主观）** |
| 不填的后果 | 不知道做法 | 错了发现不了 | ⛔ **做完但很廉价** |

⛔ **【品】不是装饰**：它是"完整"与"高质量"的差别所在。
功能全对但没有【品】的产物，会通过所有技术检查，却被评为"像 Demo"。

**什么时候必填**（满足任一）：

| 信号 | 例子 |
|---|---|
| Step 涉及**手感/节奏** | 土狼时间、顿帧、相机阻尼 |
| Step 涉及**玩家可见的表现** | 命中反馈、UI 过渡、待机动画 |
| Step 的产出是**玩家能感知**的 | 音效、粒子、震动、转场 |

ⓘ 纯技术 Step（数据迁移、协议字段、校验逻辑）**可以不填**，硬填是噪音。

⛔ **两条硬性约束**（与【审】同级）：

1. **不许指向整个文件** —— 必须指到具体条目，与【读】【审】同样判据
2. **填了就要指得准** —— 受零交集检查约束（见 `check-craft.py`）

⚠ **不要从 craft 层找官方口径**。craft 是经验区间与共识，不是可核实的事实。
需要"这个 API 到底是什么行为"时，查 howto。

### 4.2 两级审核

ⓘ 用户明确要求两级都要：

| 级别 | 位置 | 审什么 | 目的 |
|---|---|---|---|
| **步骤级** | 每步【审】 | 该步**相关的具体条目** | ⚠ **即时发现**——做完第 1 步就审，不用等做完 5 步才发现第 1 步错了 |
| **功能点级** | 功能点末尾"整体审核" | 该功能点涉及的**全部条目** | 兜底，防步骤级漏列 |

⛔ **两级不是重复劳动**：步骤级是"做的时候检查"，功能点级是"做完复查"。
步骤级漏掉的条目，功能点级会抓到。

### 4.3 步骤级和功能点级怎么分工

- 步骤级【审】：只列**这一步特有的**坑（如"判定放 _process"只属于移动步）
- 功能点级：列该功能点**全部相关条目**，可重复包含步骤级已审的
  （复查不是浪费——做完再看的视角不同）

## 5. 组合模型：大功能怎么跨多个流程

ⓘ 这是本框架最需要想清楚的部分。"做一个战斗系统"横跨角色控制、战斗结算、
UI、音频、VFX、存档、网络——**不是把几个流程排个序就完事**。

### 5.1 为什么"排序"不够

跨域组合的真正难点不是顺序，是**接缝**：

```text
flow/character/02-跳跃手感  产出：能跳的角色 + 手感参数表
flow/combat/01-伤害结算     依赖：受击方能播放受击、能进硬直
                                    ↑
                            这个"能进硬直"是 character 产出的吗？
                            不一定 —— 两边对"硬直归谁管"没有约定
```

⚠ **A 流程做完的产出，B 流程接不上**，因为接口没约定。
这才是跨域开发返工的主要来源，不是顺序排错。

### 5.2 产物契约（Artifact）

每个功能点必须声明**可指认的产出物**，而不是"做完了"：

```markdown
> **产出物**：`HitResolver.resolve(ctx) -> HitResponse`
> 　　　　　＋ `hit_resolved` 信号（携带 attacker/target/amount/response）
```

⚠ 产出物必须是**能指到具体符号/文件/信号的**，⛔ 不能是"完成了伤害结算"。
理由：下游要按名字对接，上游改接口时下游能立刻发现。

### 5.3 组合的三种关系

| 关系 | 含义 | 处理 |
|---|---|---|
| **依赖** | B 需要 A 的产出物 | 拓扑排序，A 先做 |
| **接缝** | A 的产出与 B 的期望格式不一致 | 加**接线功能点**（glue FP） |
| **共享** | 多个流程都要改同一个东西 | ⛔ 危险信号，见 5.4 |

⚠ **接缝是最容易被忽略的**。判断方法：把两个功能点的产出物/依赖并排写，
如果对不上（命名不同、单位不同、时序不同），就是接缝，需要显式处理。

⛔ **不要在流程内偷偷适配对方的格式**（"反正我这边转一下就行"）——
这个适配会散落在多处，以后改接口时找不到。✅ 单独立一个接线功能点，
它有名字、有验收、以后能被找到。

### 5.4 共享是危险信号

多个流程都要改同一个文件/类/配表 → ⚠ **这是耦合，不是复用**。

处理方式（按优先级）：

1. 抽成独立的功能点，明确归属某一个流程
2. 若真要共享，定义**稳定接口**并写进产出物契约
3. ⛔ 绝不能"两边各改各的，反正跑起来没问题"

### 5.5 组合文档

大功能的组合写成 `flow/_组合/<功能名>.md`，内容：

```markdown
# 战斗系统（跨 5 个流程）

## 涉及流程
| 流程 | 用到的功能点 | 产出物 |
|---|---|---|
| character | 01 02 05 | 可跳可动、带动画的角色 |
| combat | 01–04 | HitResolver + 帧数据 |
| ui | HUD 相关 | 血条 |
…

## 依赖图（按产出物）
character/01 ──┐
               ├→ combat/02（需要受击方能播受击、能进硬直）
character/05 ──┘

## 接缝清单
| 接缝 | 上游产出 | 下游期望 | 处理 |
|---|---|---|---|
| 硬直归谁管 | character 未定义 | combat 需要 | ⚠ 接线 FP：定义 PoiseState |

## 执行顺序（拓扑后）
…

## 集成验收
⛔ 不能只验收各流程自己的清单——要验"拼起来之后"
```

⚠ **最后一条最关键**：各流程自己的验收清单**不能替代集成验收**。
每个部件都合格、拼起来不能用，是跨域开发的典型失败。

## 6. 通用骨架（兜底 110 个域）

ⓘ 只有 2 个域有细化流程，其余 108 个靠 `_骨架.md` 兜底。
骨架是**通用六步**，任何域都能套：

```text
0 定边界      这个域做什么 / ⛔ 不做什么
1 定契约      数据长什么样、对外接口是什么（产出物）
2 最小闭环    跑通最窄的一条路，不做异常不做优化
3 接外部      与已有系统的接线（接缝）
4 异常边界    失败路径、边界值、并发/时序
5 验收        可观测判据 + 过 audit
```

⚠ 六步顺序的理由：

- **0 在前**：边界不清就开工，做出来的是另一个东西
- **2 最小闭环在前**：先证明主干能跑，再补分支。⛔ 反过来会陷入
  "异常处理写了一半，主干还没验证"的泥潭
- **3 接外部在 2 之后**：自己的东西没跑通就去对接，出错时无法定位是谁的问题
- **5 验收含 audit**：⛔ 不能只验"能跑"，要过禁忌表

ⓘ **骨架不等于"随便做做"**。它只是把"细化流程"里的领域特化部分抽掉后剩下的通用部分。
任何域一旦细化，细化的功能点应当**能映射回骨架六步**——映射不上的话，
说明细化时漏了（通常是漏了"异常边界"或"定契约"）。

## 8. 自检应如何随之演进
