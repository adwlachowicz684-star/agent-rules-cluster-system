# 结构框架总纲

ⓘ **本文件是目标结构的设计文档，当前尚未迁移**（见文末「迁移映射」）。
框架定稿后按映射一次性改名，在此之前以下路径名按映射表反向理解。

---

## 1. 命名

| 层 | 旧名 | **新名** | 回答 | 组织 | 比喻 |
|---|---|---|---|---|---|
| 流程 | `procedure/` | **`flow/`** | 按什么顺序做、每步产出什么、怎么验收 | 按**功能点** | 施工图（分工序、有验收） |
| 做法 | `flow/` | **`howto/`** | 这个东西怎么做（选型 + 可抄代码） | 按**域** | 工艺手册（查细节） |
| 审核 | `audit/` | `audit/`（不变） | 不能怎么做 | 按**域** | 质检表 |

⚠ **改名理由**：`flow` 在中文语境里直译就是"流程"，而原 `flow/` 装的其实是
"某个域怎么做"的知识，**不是流程**。名字与内容错位，导致每次讨论都要先解释
"你说的 flow 是哪个 flow"。现在名字即动作：

```text
走 flow  → 查 howto → 过 audit
（顺序）   （细节）    （检查）
```

三者**正交**，不构成包含关系。⛔ 不要把 howto 塞进 flow，也不要把 audit 混进 howto。

---

## 2. 三层的边界判据

判断一段内容该放哪层，用这三个问题：

| 问题 | 是 → |
|---|---|
| 它描述**时间顺序**（先做什么后做什么）？ | `flow/` |
| 它描述**某个东西本身的构造**（API、参数、代码）？ | `howto/` |
| 它描述**出错的样子 / 禁止事项**？ | `audit/` |

⚠ **"⚠ 注意"类内容容易放错层。** 判据：

- 「这个 API 4.7 才有」→ ⚠ 是**做法的前提** → `howto/`
- 「写成 X 会导致 Y 崩」→ ⛔ 是**错误特征** → `audit/`
- 「这一步做完要先验 X 再进下一步」→ ⚠ 是**工序约束** → `flow/`

⛔ 同一句话不要在三处重复三遍。每层各写各的，靠链接互指。

---

## 3. 调度模型：一次调用怎么走

```
需求进来
  │
  ├─ ① 路由：dev-route.py --need="…"  → 命中 N 个域
  │
  ├─ ② 该域有 flow/ 吗？
  │     ├─ 有 → 打开 flow/<域>/00-域流程总览.md
  │     └─ 无 → 套 _骨架.md（见第 6 节），⛔ 不许凭记忆开工
  │
  ├─ ③ 逐个功能点执行（第 4 节的嵌合协议）
  │     ⚠ 一个验收通过才进下一个
  │
  └─ ④ 全部做完 → 过 audit/<域>.md
```

⚠ **第 ② 步的分叉是当前的薄弱环节**：110 个域里只有 2 个有 flow。
所以 `_骨架.md` 不是可选补充，是**兜底设施**——它让"没细化的域"也有章可循，
而不是退回"凭感觉写"。

## 4. 嵌合协议：flow 与 howto 怎么咬合

ⓘ **当前问题是粗粒度**：功能点只写「对应 `howto/godot/combat.md`」，
而该文件有 537 行、11 节——调用方仍要自己翻。

✅ **做法：在 Step 级给出锚点，不是文件级。**

每个 Step 固定四要素（比现在的三要素多一个【查】）：

```markdown
### Step 3　加重力

【查】howto/godot/character.md#重力        ← 具体到章节
【做】velocity.y += gravity * delta
【产出】角色会下落并停在地面
【判据】落地后完全静止，⛔ 有抖动就是错的
```

⚠ **【查】是强制项**（除纯机械步骤外）。理由：

1. 流程不该重复 howto 的代码——重复必然不同步
2. 没有【查】，调用方会跳过 howto 直接按自己记忆写，howto 层就废了
3. 【查】让"这个流程依赖 howto 哪些章节"变成**可检查的依赖**
   → 可加自检：所有 `【查】` 指向的章节必须真实存在

⛔ **【查】不能指向"整个文件"**（`howto/godot/combat.md` 不带 `#`），
那等于没指。ⓘ 例外：该节确实是整体阅读时，锚到 `#0.`

## 5. 组合模型：大功能怎么跨多个流程

ⓘ 这是本框架最需要想清楚的部分。"做一个战斗系统"横跨角色控制、战斗结算、
UI、音频、VFX、存档、网络——**不是把几个流程排个序就完事**。

### 5.1 为什么"排序"不够

跨域组合的真正难点不是顺序，是**接缝**：

```text
flow/character/02-跳跃手感  产出：能跳的角色 + 手感参数表
flow/combat/01-伤害结算     依赖：受击方能播放受击、能进硬直
                                    ↑
                            这个"能进硬直"是 character 产出的吗？
                            不一定 —— 两边对"硬直归谁管"没有约定
```

⚠ **A 流程做完的产出，B 流程接不上**，因为接口没约定。
这才是跨域开发返工的主要来源，不是顺序排错。

### 5.2 产物契约（Artifact）

每个功能点必须声明**可指认的产出物**，而不是"做完了"：

```markdown
> **产出物**：`HitResolver.resolve(ctx) -> HitResponse`
> 　　　　　＋ `hit_resolved` 信号（携带 attacker/target/amount/response）
```

⚠ 产出物必须是**能指到具体符号/文件/信号的**，⛔ 不能是"完成了伤害结算"。
理由：下游要按名字对接，上游改接口时下游能立刻发现。

### 5.3 组合的三种关系

| 关系 | 含义 | 处理 |
|---|---|---|
| **依赖** | B 需要 A 的产出物 | 拓扑排序，A 先做 |
| **接缝** | A 的产出与 B 的期望格式不一致 | 加**接线功能点**（glue FP） |
| **共享** | 多个流程都要改同一个东西 | ⛔ 危险信号，见 5.4 |

⚠ **接缝是最容易被忽略的**。判断方法：把两个功能点的产出物/依赖并排写，
如果对不上（命名不同、单位不同、时序不同），就是接缝，需要显式处理。

⛔ **不要在流程内偷偷适配对方的格式**（"反正我这边转一下就行"）——
这个适配会散落在多处，以后改接口时找不到。✅ 单独立一个接线功能点，
它有名字、有验收、以后能被找到。

### 5.4 共享是危险信号

多个流程都要改同一个文件/类/配表 → ⚠ **这是耦合，不是复用**。

处理方式（按优先级）：

1. 抽成独立的功能点，明确归属某一个流程
2. 若真要共享，定义**稳定接口**并写进产出物契约
3. ⛔ 绝不能"两边各改各的，反正跑起来没问题"

### 5.5 组合文档

大功能的组合写成 `flow/_组合/<功能名>.md`，内容：

```markdown
# 战斗系统（跨 5 个流程）

## 涉及流程
| 流程 | 用到的功能点 | 产出物 |
|---|---|---|
| character | 01 02 05 | 可跳可动、带动画的角色 |
| combat | 01–04 | HitResolver + 帧数据 |
| ui | HUD 相关 | 血条 |
…

## 依赖图（按产出物）
character/01 ──┐
               ├→ combat/02（需要受击方能播受击、能进硬直）
character/05 ──┘

## 接缝清单
| 接缝 | 上游产出 | 下游期望 | 处理 |
|---|---|---|---|
| 硬直归谁管 | character 未定义 | combat 需要 | ⚠ 接线 FP：定义 PoiseState |

## 执行顺序（拓扑后）
…

## 集成验收
⛔ 不能只验收各流程自己的清单——要验"拼起来之后"
```

⚠ **最后一条最关键**：各流程自己的验收清单**不能替代集成验收**。
每个部件都合格、拼起来不能用，是跨域开发的典型失败。

## 6. 通用骨架（兜底 110 个域）

ⓘ 只有 2 个域有细化流程，其余 108 个靠 `_骨架.md` 兜底。
骨架是**通用六步**，任何域都能套：

```text
0 定边界      这个域做什么 / ⛔ 不做什么
1 定契约      数据长什么样、对外接口是什么（产出物）
2 最小闭环    跑通最窄的一条路，不做异常不做优化
3 接外部      与已有系统的接线（接缝）
4 异常边界    失败路径、边界值、并发/时序
5 验收        可观测判据 + 过 audit
```

⚠ 六步顺序的理由：

- **0 在前**：边界不清就开工，做出来的是另一个东西
- **2 最小闭环在前**：先证明主干能跑，再补分支。⛔ 反过来会陷入
  "异常处理写了一半，主干还没验证"的泥潭
- **3 接外部在 2 之后**：自己的东西没跑通就去对接，出错时无法定位是谁的问题
- **5 验收含 audit**：⛔ 不能只验"能跑"，要过禁忌表

ⓘ **骨架不等于"随便做做"**。它只是把"细化流程"里的领域特化部分抽掉后剩下的通用部分。
任何域一旦细化，细化的功能点应当**能映射回骨架六步**——映射不上的话，
说明细化时漏了（通常是漏了"异常边界"或"定契约"）。

## 7. 迁移映射

ⓘ 定稿后执行，一次到位。当前**尚未执行**。

| 现在 | 目标 | 动作 |
|---|---|---|
| `references/procedure/` | `references/flow/` | 目录改名 |
| `references/flow/godot/` | `references/howto/godot/` | 目录改名 |
| `references/audit/godot/` | 不变 | — |
| 265 处 `flow/godot` 引用 | `howto/godot` | 全局替换（⚠ 注意不要误伤已指向新 flow 的引用） |
| 22 处 `procedure` 引用 | `flow` | 全局替换 |

⚠ **迁移的两个风险点**：

1. **替换顺序**：先把 `procedure/` 改名成 `flow/` 会与现有 `flow/` 冲突。
   ✅ 正确顺序：`flow/godot` → 先移到临时名 `howto/` → 再把 `procedure/` 改名 `flow/`。
   ⛔ 反过来会覆盖。
2. **引用替换不能用无脑 sed**：`flow/godot` 这个串里，`flow` 既是旧的做法层
   又是新的流程层。必须先按上下文区分，或先完成目录改名再替换引用。

✅ 迁移完成后的判据：全量自检通过 + 随机抽 10 个域的链接实际打开确认。

## 8. 自检应如何随之演进

ⓘ 迁移后自检需要新增/调整这几条（当前 406 条里的 procedure 相关项需同步改名）：

| 检查 | 目的 |
|---|---|
| 三层目录名正确、无残留旧名 | 防迁移不彻底 |
| `【查】` 锚点指向的 howto 章节真实存在 | 防断链（比文件级更严） |
| 每个功能点声明了产出物 | 防"做完了"这种不可对接的产出 |
| `_组合/*.md` 里的功能点都能找到 | 防组合文档引用不存在的功能点 |
| 骨架六步与细化功能点可映射 | 防细化时漏环节 |

⚠ **所有这些都要做变异测试**——本轮的经验是：规则"看起来对但不触发"
是常态，不造反例验证等于没写。
