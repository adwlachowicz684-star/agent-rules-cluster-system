# 商业化与变现：内购、抽卡、广告（Godot 4.7.2）

"支付""商城""gacha""扭蛋""激励视频""礼包""月卡" 此前 **全部 0 命中**。

## 0. 第一句话：Godot 没有任何 IAP API

⚠ **官方确认：Godot 4.x（含 4.7.2）没有内置跨平台 IAP/支付/广告 API。**

Class DB 里没有 `StoreKit`、`GooglePlayBilling`、`AdMob` 这类类。
商业化必须靠 **GDExtension 原生桥接**（Android / iOS）或第三方插件。

这决定了整个架构：**客户端只是"发起支付的遥控器"**，
所有订单、抽奖、发货、保底、权限**必须在自己的服务器上落地**。

## 1. ⚠ 合规优先于体验

**技术 bug 可以热更修复，下架通知和行政处罚不能撤回。**

### 中国大陆：抽卡是"四件套"，不是一个数字

| 要求 | 内容 |
|---|---|
| ① | 不得要求用户**直接投入法定货币或虚拟货币**参与随机 → 业界通行做法是加一层中间游戏币（钻石/金币） |
| ② | 公示所有可抽取道具的名称、性能、内容、数量及**概率** |
| ③ | 公布抽取结果、**保存记录不少于 90 日** |
| ④ | 必须提供**其他获取途径**（游戏币直接购买/兑换） |

⚠ **漏掉第④条是最常见的"概率公示了但依然不合规"** —— 公示了概率，却没给玩家不靠抽就能拿到同性能物品的等价通道。

### 未成年人充值限额（中国，2019 防沉迷通知）

| 年龄 | 单次 | 每月 |
|---|---|---|
| 未满 8 岁 | **禁止付费** | — |
| 8–16 岁 | 50 | 200 |
| 16–18 岁 | 100 | 400 |

### 其他地区

- **韩国**：2024-03-14 起强制公示，违规可被申请下架
- **中国台湾**：2023 起要求百分比形式公示
- **比利时**：可兑现的开箱认定为赌博
- **Apple 3.1.1**：数字商品必须用 IAP，**战利品箱须在购买前披露概率**；绕开的后果是拒审、下架、账号终止

## 2. 服务端必须校验的清单（漏一项都够致命）

1. IAP 收据真实性（签名、证书链、bundle_id、product_id、transaction_id）
2. **订单是否已发货**（幂等，防重放）
3. 账号是否在未成年限额内、是否宵禁时段
4. 抽奖池是否对该地区开放、道具是否可转移
5. 发货时余额是否足够
6. 月卡/订阅到期时间是否按 **UTC** 计算
7. 所有发放/回滚/退款写**不可变审计日志**

⚠ 客户端说"我付了钱""我抽到了五星""我看了广告"，**一句都不能信**。

## 3. ⚠ 掉单：最容易丢钱的 bug

付了钱没发货。必须：
- **订单号幂等** —— 同一笔订单不能发两次
- **本地单据持久化** —— 付完款但发货前崩溃，重启要能恢复
- 完整流程：本地记录 → 发起支付 → 服务器校验 → 发货 → 标记完成 → 清本地单据

## 4. 抽卡：随机与保底都在服务器

- ⚠ **随机必须在服务器端**（客户端随机会被改）
- ⚠ **保底（pity）必须存服务器** —— 本地存会被清档绕过
- ⚠ **公示的概率必须和实现代码完全一致** —— 单一数据源的概率表，公示页由同一份数据自动生成，
  不能策划填一份 Excel、代码另写一份
- PRD（伪随机分布）与真随机的体验差异：真随机容易连续不出货，PRD 更平滑
- 建议实装**每日抽卡次数上限**（国内常见 50 次）—— 低风险高信号量的合规动作

## 5. 广告与激励视频

⚠ **奖励必须在服务器发** —— 客户端回调可被伪造/断网
⚠ **广告回调时机**：看完了但没回调怎么办（要有超时与查询接口）

## 6. 商城与定价

⚠ **价格本地化与平台价格档位**（各平台有固定档位，不能随便定价）
月卡/订阅的时限计算 ⚠ 必须用 **UTC**（呼应 `economy.md`）

> **反模式清单（不能怎么做，审核用）** → `audit/godot/monetization.md`


## 7. 支付通道的 Godot 侧：HTTPRequest 与导出权限

Godot 没有 IAP，支付必须走自己的 HTTP 通道，`HTTPRequest` 是最常用的节点。
⛔ 它有三条官方限制，全部会表现为"没反应"而不报错：

| 官方事实 | 后果 |
|---|---|
| ⛔ Android 导出必须启用 `INTERNET` 权限 | 官方原话：否则 **任何** 网络通信都会被 Android 阻断 |
| ⛔ 单个 `HTTPRequest` 不要并发请求 | 官方示例注释明写 "Don't make simultaneous requests using a single HTTPRequest node" |
| ⛔ `timeout` 默认 `0.0` | 含义是**不超时**，请求可能永远挂着 |

ⓘ 另两条默认值：`accept_gzip` 默认 `true`（自动解压 gzip 响应）；`max_redirects` 默认 8。

## 8. 订单号、幂等键与设备标识

**订单号**：由服务端下发，或用 `Crypto.generate_random_bytes()` 生成随机分量。
⛔ 不要拿 `Time.get_unix_time_from_system()` 拼 —— 官方明确该系统时钟**用户可手动设置**，且并发下会碰撞。

**幂等键**：在订单表上建**唯一索引**。
⛔ 只在应用层判"有没有处理过" —— 并发下两个请求会同时通过检查。

**设备标识**：`OS.get_unique_id()` 在 Godot 4 **仍然存在**（ⓘ 不要误以为已被移除），
但官方注明两条：
- 重装 / 升级系统 / 更换硬件后**可能变化**，⛔ 不该用来加密持久化数据（此前加密的数据将永久无法解密）
- ⛔ **可被外部程序伪造**，不得用于任何安全目的

**签名与票据比对**：用 `Crypto.constant_time_compare()`。
⛔ 用 `==` 比较签名存在时序侧信道，官方为此专门提供了这个方法（"without leaking timing information in order to prevent timing attacks"）。

## 9. 退款、风控与审计日志

- **审计日志只追加**：发放 / 回滚 / 退款 / 回收四类动作同链，⛔ 不允许 UPDATE / DELETE
- **退款要回收已发物品**：⛔ 只把货币扣成负数，已发道具仍在玩家手里，可被白嫖或转卖
- **风控阈值可热配**：⛔ 硬编码则出事时改一个数字要发版，而攻击窗口在小时级
- ⛔ **不开自有的"撤销订单"接口**：退款走平台侧流程，自有接口一旦存在就是新的攻击面，且会让平台账单与游戏数据对不上
- **对账**：平台订单数 vs 服务端发货数 vs 审计日志条数，每日跑一次并告警
