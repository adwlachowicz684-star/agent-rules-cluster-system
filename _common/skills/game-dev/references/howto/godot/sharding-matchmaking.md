# 分区分服 / 跨服 / 合服 / 匹配机制（Godot 4.7.2）

**此前文档里「分区分服 / 跨服 / 合服 / 匹配机制 / ELO」0 命中。**

> 账号与令牌见 `platform-services.md`；签名与反外挂见 `security.md`；
> 邮件见 `social.md`；指标口径见 `analytics.md`。

⚠ **分服、合服、匹配全部是服务端职责，Godot 不提供任何相关 API。**

> 审核用反模式清单见 `audit/godot/sharding-matchmaking.md`

## 1. 分区分服 / 跨服 / 合服

⚠ **隔离的是服务边界，不是玩家身份。** 全局账号/订单 + 逻辑服角色 + 全局 ID。

### ID 冲突

⚠ **各服自增 ID 会撞** → 跨服（战场、好友）必须用全局唯一 ID：
雪花 ID（时间戳 + 机器位 + 序列）或 `服ID + 自增` 复合。

### 合服

⚠ **必须：快照 → dry-run → 幂等迁移 → 保留回滚。**

要处理：重名（加后缀或让玩家改名）、排行榜合并、重复资产合并、跨服好友与邮件迁移。

## 1.1 资产盘点：不是列数据库表

⚠ **合服前要列全「实体、所有者、外键、业务语义」四件事**，建一张迁移资产清单：
源服/目标服、表/集合、实体主键、所有者字段、引用它的上下游表、是否参与余额、
是否有附件、是否可归档、合服处置、责任人。

⛔ **任何未列进清单的表默认「冻结写入但暂不迁移」，⛔ 不是默认复制。**

| 检查项 | 必须确认 | 错后后果 |
|---|---|---|
| 主键/唯一键 | 目标库是否有同值主键、唯一索引、联合索引 | 插入失败、唯一键冲突、**静默覆盖** |
| 所有者映射 | 角色/邮件/公会归哪个全局账号 | 资产挂到错误玩家或孤儿数据 |
| 服内唯一字段 | 角色名、公会名、队伍名是否服内唯一 | 合服后重名、检索错人 |
| 全局 ID 分配位 | 机器位、数据中心位、服位是否仍够 | ID 生成器耗尽或跨服碰撞 |
| 时间字段 | 创建/过期/登录时间是 UTC 还是本地 | TTL、活动资格和报表错一天 |
| 余额表 | 是否有流水表可反查 | 总额对得上但**明细无法解释** |
| 外键完整性 | 好友、公会、邮件、举报是否双向完整 | 关系单向、邮件找不到收件人 |
| 业务单状态 | 拍卖、匹配、补偿是否处于终态 | 合服后重复结算或卡在中间态 |

⚠ 尤其要检查**状态表**：只有 `status='待领取'` 的订单、正在竞价的拍卖、
跨服进行中的比赛、未到账补偿，**⛔ 不能被简单当作历史数据归档**。

### ID 映射必须提前设计

✅ 理想是上线时即用「服 ID + 服内自增」或 64 位全局 ID，合服无需重写主键。
✅ 存量项目准备不可变 `id_map(source_realm, source_id, target_realm, target_id, entity_type, created_at)`。

⚠ **映射必须按实体类型分命名空间**，否则不同表恰好数值相同也会撞车。
⛔ **禁止只靠「主键整体加一个大偏移量」** —— 若业务主键同时是协议字段、客户端缓存键、
日志 join key 或历史订单引用，简单偏移会破坏外部一致性。
⚠ 映射表本身是**永久审计数据**，⛔ 不因合服完成而删除。

### 冲突枚举要覆盖语义冲突，不只是主键冲突

至少六类：角色/公会名称相同 · 角色 ID、邮件 ID、订单 ID、物品实例 ID 相同 ·
竞技分数或段位相同但赛季版本不同 · 相同账号重复领取新手/回归奖励 ·
好友双向关系中有一方不存在 · 邮件/附件引用已合并或已删除角色

⚠ 公会还要查会长、职位、申请、邀请、公告；拍卖行查托管物品、冻结资金、竞拍中订单；
竞技场查赛季结算、禁用英雄、战绩、奖励领取状态。

## 1.2 dry-run：第一产出是冲突报告，不是「迁移成功」

⚠ **必须在从生产备份恢复的数据副本上执行**，⛔ 禁止连生产只读库直接改状态。
⚠ 副本应来自**同一次一致性快照** —— 否则源服 A/B 备份时间点不同，增量基线失真。

✅ dry-run 与生产脚本**同一代码、同一映射规则、同一批次参数**，唯一区别是目标库为影子库。
顺序：预检查 → 全量迁移 → 增量追平 → 校验 → 冲突报告，**⛔ 不在 dry-run 环境实际切流**。

⚠ **若 dry-run 报「没有冲突」，要反过来检查选择器是否漏表，而不是庆祝。**

### 冲突报告至少八张子表

1. **重名清单**（角色名/公会名、冲突次数、所有冲突主键、建议动作、受影响登录名）
   —— ⚠ 要同时给出「是否影响搜索、排行榜、邮件、日志展示」
2. 主键/唯一键冲突清单
3. ID 映射冲突清单
4. **排行榜重叠**（相同分数、并列规则、赛季版本、有效期）
5. **资产重复**（同一全局账号多角色领取资格、礼包码、回归奖励）
6. **关系断裂**（好友/黑名单/师徒/情侣/公会成员引用到不存在角色）
7. **业务单中间态**（拍卖、邮件附件、订单、比赛、活动任务）
8. 数据规模与耗时（每表行数、迁移时间、最大批次、失败数、校验和不一致）

⚠ **容量与时长必须由 dry-run 实测，⛔ 不能拍脑袋** ——
记录单批下的 CPU、内存、磁盘 IO、复制延迟、日志增长、索引构建时间；
估算后留**至少 2 倍 buffer**，再加备份、缓存预热和验证时间。
ⓘ 具体停服分钟数以最近一次影子迁移的 P50/P95 为基线（**待核实**）。

## 1.3 停服窗口：先冻结写入，再追增量，最后切流

```text
T-7~T-3  发布规则与影响范围
T-1      关闭跨服活动入口、停止发奖、停止影响合服的新付费活动（保留登录和查看）
T0       进入维护，停止逻辑服写入口，等对局结算与异步任务排空，记录全局水位线
T1       建立数据库一致性快照
T2       迁移      T3  多级校验
T4       缓存预热、配置切流、回归
T5       灰度开放  T6  进入观察期
```

⚠ **尤其不能只停客户端入口** —— 后台 GM、客服、定时任务、跨服中心、机器人调度、
消息队列消费者、补偿脚本都可能继续写库，**必须全部进入冻结清单**。

| 阶段 | 必须动作 | 退出条件 | ⛔ 禁止 |
|---|---|---|---|
| 预检查 | 锁版本、备份、校验和、容量、ID 位 | 所有 CHECKLIST 通过 | 跳过无人认领的表 |
| 冻结 | 停写、排空队列、记录水位线 | 无新写入且任务终态 | **先迁移再冻结** |
| 全量迁移 | 按实体顺序、批次迁移 | 行数/总额/校验和对账 | 大事务一次提交 |
| 增量追平 | 从水位线重放增量 | 源目标差集为空 | 手写 SQL 人工补漏 |
| 校验 | 总额、明细、关系、业务规则 | 自动校验 100% 通过 | 只查前 100 条 |
| 切流 | 更新路由、灰度、预热 | 探针与核心链路正常 | 直接全量开放 |
| 观察 | 监控、客服样本、回滚值守 | 观察期无 P0/P1 | 提前释放备份与映射 |

### 迁移脚本必须可重入、可中断续跑

```text
每个批次写入前记录检查点：
  job_id, entity_type, source_realm, last_source_pk, batch_size, status
中断后从最后一个 SUCCESS 检查点之后继续
⚠ 状态为 IN_PROGRESS 的批次要查目标端「已经写到了哪个源主键」
  ⛔ 不能从批次头重做
```

✅ 推荐执行顺序：账号/全局玩家 → 角色 → 基础资产 → 邮件 → 好友/黑名单 →
公会 → 拍卖 → 排行榜/赛季 → 日志索引。
ⓘ 订单、支付、封禁等全局数据若无需合服，则**仅校验引用完整，不复制**。

⚠ **批量与限流以「数据库不受惊吓」为目标** —— 批次事务短、行数小；
批次间 sleep 或令牌桶，限流键按**目标库写压力**⛔ 不是 CPU。
⛔ **禁止百万行一次性 `INSERT ... SELECT` 后重建索引**。
⚠ 若剩余时间超窗口，**必须按预案降级**（缩小范围或改期），⛔ 不能偷偷加大批次。

## 1.4 校验要从总额对账上升到玩家旅程对账

⚠ **总额对账只能证明「没有大规模丢失」，⛔ 不能证明「业务正确」。**

五类对账：角色/公会数量 · 各币种总额 · 装备按类别与实例属性 · 关系数量和双向性 · 活动资格与未领取奖励。
再对**高价值玩家做明细对账**：按流水重建余额，核对附件、限时状态、过期时间、绑定关系。

⚠ **抽样要沿玩家旅程走，⛔ 不是随机点开几张表** ——
登录后角色列表、角色选择、首次读背包、首次写任务、领取旧邮件、发送新邮件、
好友双向展示、公会职位、拍卖创建/竞价、排行榜查询、竞技场进入、充值回调映射、客服查询。

⚠ 还要对**重名玩家、改名玩家、公会会长、被删号、跨服好友、待领附件、过期邮件、拍卖中订单**
分别构造专门样本。⛔ 不能只凭「能登录」就开服。

⚠ **灰度开放解决的是未知风险，⛔ 不是验证正确性** —— 先 1–5% 流量或指定服务器组；
灰度期间所有 GM 补偿、跨服活动、高价商品交易**默认关闭**。
⚠ 核心接口⛔ 不能因灰度比例改变而发生行为差异，否则灰度结果没有意义。

## 1.5 ⚠ 回滚不能回到过去，只能回到「数据仍是内部一致状态」

⚠ **最难的事故不是迁移失败，而是开服后玩家已经继续玩，此时才发现合服错误。**

**切流前校验失败** → 停止切流、保留副本和目标库，从最近全量备份 + 水位线恢复源服写入
（⚠ 源服写入必须在迁移前保留且冻结期间不删除）。

**切流后只有单点错误**（某张表映射错误、某类附件未到账）
→ ✅ **优先「正向补偿 + 单玩家修复 + 审计单」，⛔ 而不是回退整个服。**
⚠ 回退会使已经产生的真实对局、交易、充值和社交行为消失，**构成二次事故**。

⚠ **只有满足「目标状态不可修复」且「未污染源服状态」时才执行全局回滚**：
资产总额不可逆不一致 · 玩家角色被错配 · 订单/充值映射错误 ·
核心功能持续不可用且无法降级 · 数据损坏范围超出自动补偿能力

执行顺序：关闭登录与入口 → 停止所有自动补偿 → 冻结异步任务和跨服通信 →
保存开服后增量水位线 → 评估差异 → 公告 → 若决定回退则把源服恢复为已知一致快照并保留目标服隔离证据
→ 以玩家可理解方式补发或人工处理新数据。

⛔ **任何「简单 restore 到停服时刻」的方案都不应通过评审。**

### 回滚后的新数据分三类处理

| 类 | 内容 | 处理 |
|---|---|---|
| 可重放 | 玩家行为流水、日志、聊天、匹配请求 | 若源端保留且在合法范围内，可重新结算 |
| 需人工裁决 | 跨服比赛、交易、拍卖、纠纷 | ⛔ 不能自动再执行一次 |
| 必须保留 | 充值、封禁、客服承诺 | ⛔ 不能因合服失败而删除 |

⚠ 所以开服后每一笔关键写都必须带**全局事务 ID、服务端接收时间、源事件版本、可重放载荷** ——
⛔ 没有这条，所谓回滚只是把状态一起抹掉。

## 1.6 重名与跨服数据按「身份/社交/经济/竞技」分层处置

⚠ **重名没有零代价的方案：**

| 方案 | 后果 |
|---|---|
| 加后缀（如 `.aa` 两位随机字符） | 玩家失去原名称，搜索结果变；需自动发改名卡并开放免费改名；⚠ 随机后缀可能产生近似冒充 |
| 强制全部重命名 | 最公平但体验最差，仅适合合服范围很小或名称规则重构 |
| 优先保留 | 按「创建最早/累计充值最高/段位最高/最后登录最近」**单一规则**排序并预先公告；⛔ 若采用「原服优先」，被合并服玩家会永久感到降级 |

✅ 最稳妥：冲突方统一追加**可去掉的服标识**，对高价值/早期玩家提供一次优先抢注窗口，其余自动后缀。
⚠ **无论哪种方案，所有显示名、搜索索引、好友备注、邮件收件人、历史日志都要映射同一稳定 ID。**

⚠ **公会冲突比角色名更危险，因为它包含权力与资产** —— 自动后缀 + 给会长改名卡；
校验会长角色是否被合并、职位成员是否重复、申请/邀请是否指向冲突目标。
⚠ **公会资金、仓库、拍卖托管、赛事资格若有服内经济含义，应保留独立账本，
⛔ 禁止在合服脚本里「合并余额」。**

⚠ **好友、邮件、黑名单必须保证双向性** ——
只保存一方时 A 的好友列表有 B 但 B 的没有 A，会造成骚扰、私聊和社交攻击。
✅ 迁移时**以两个方向的边都成功为批次提交条件**；跨服引用存 `target_global_id`，
⛔ 不要存服内角色 ID。

⚠ **拍卖行、排行榜、竞技场赛季有不同时间语义：**
- **拍卖行是经济交易** —— 正在交易中的订单最好合服前进入**禁止上新与结算期**，迁移后再开放，
  ⛔ 否则跨服价格、并发出价、物品归属会造成双重结算
- **排行榜是视图** —— 合服后依据同一赛季、同一规则、同一截止时间**重算**并保留历史快照；
  ⛔ 只把两个榜单上下拼接会制造错误名次
- **竞技场赛季** —— 只应影响下一赛季数据，已结束赛季冻结为快照；
  进行中的赛季要提前结算或延长补偿（**待核实**，取决于比赛公平性）

## 1.7 跨服权威：一次请求只能有一个写者

⚠ **复制模型适合低一致性、高读取的社交数据；远程读取适合必须强一致的资产。**

| 模型 | 适用 | 代价 |
|---|---|---|
| 只读镜像 | 名称、头像、段位、在线状态 | 会读到过期值 |
| 远程读取 | 资产、余额、封禁 | 增加 RTT，原服故障会阻塞 |

⛔ **不要「两边都写一点」**，⛔ 不要让原服和跨服服各自生成资产流水。
✅ 战斗/任务/副本中的状态由战场服权威；结算、背包、货币、订单由中心结算服务或原服权威；
聊天由发送者原服鉴权、中心服务路由。

⚠ **断线、延迟、重复请求要按业务语义分别处理** ——
玩家掉线后⛔ 不能立即消失，⛔ 也不能让客户端继续决定胜负；
结算请求带幂等键，战场服重复提交**必须返回首次结果**而⛔ 不重复入账。
跨服读取失败时用短 TTL 缓存但**标记为「可能过期」**，⛔ 不能把过期值静默当最新值。

### 全局 ID 分配器：三个闸门

⚠ **雪花 ID 的冲突条件是同一时间戳 + 同一机器位 + 同一序列号再次出现。**
⚠ **NTP 可能把时钟往回拨**，导致已使用的时间段和序列被复用；
容器/虚拟机迁移、闰秒、人工校时也是风险源。

✅ 工程对策：
1. **单调时钟生成时间戳**，启动时从持久化高水位恢复
2. 配置最大允许回拨阈值：**小回拨阻塞等待，超限则拒发新 ID、摘流并告警**
3. **机器位通过租约/分布式锁唯一分配**，⛔ 不能把容器名 hash 当绝对唯一
4. 记录时钟守护值、重启次数、生成器版本便于追溯

⚠ **序列号耗尽不是「调大位宽」就够了** —— 同一毫秒耗尽优先等下一毫秒；
确实超位宽先增加生成器实例并验证机器位容量。
⛔ **调整位宽会改变既有 ID 长度与排序语义，属不兼容协议变更，必须灰度**。
⛔ **不要把数据库自增、UUID 和雪花 ID 混在同一个业务主键域**。

## 2. 邮件系统：全服补偿的最后一道可靠性闸门

⚠ **邮件不是站内信，是离线资产交付系统。**

状态至少要有：草稿、未读、已读、**领取中**、已领取、过期、已删除（软删）、历史归档。
⛔ **任何只用一个 boolean 表示「已读」或「已领」的模型，后续都无法支持附件部分领取、
超时并发、审计和回滚。**

ⓘ 玩家看到的「删除」通常只是软删，附件和审计保留；
但**玩家主动销毁的邮件不应再作为活动资格或补偿凭证**。

### 附件领取必须先占状态，再入账

```gdscript
# 服务端用 mail_id + player_id + attachment_id 的唯一约束或条件更新
# UNCLAIMED → CLAIMING
# ⚠ 只有更新成功的一笔执行背包/货币发放，并写入资产流水
# 成功后再置为 CLAIMED
```

⚠ 客户端超时、重复点击、断线重连都**重新查询当前状态**，⛔ 不能让客户端自行重试扣发。
⚠ 资产服务不可用则保留 `CLAIMING` 由补偿任务续跑，⛔ 禁止无状态下让客户端「再点一次」。
⚠ **领取必须整体成功或整体失败** —— 成功但部分物品未到账，**比领取失败更危险**。

### ⚠ 容量满不能让补偿发不出去

| 邮件类型 | 满箱时 |
|---|---|
| 普通活动邮件 | 拒绝新邮件并提示清理 |
| 公告/系统邮件 | 循环覆盖要**明确优先级**，⛔ 不能用新公告覆盖未领取补偿 |
| **维护补偿 / 付费返还 / 官方承诺** | ⛔ **不能被满箱拒绝** —— 转入「待领补偿仓」、保留邮件、让客服可定位 |

⚠ 背包空间不足时：普通奖励提示清理，**高价值奖励转入临时仓库并保留领取记录**，
⛔ 绝不能在客户端弹窗后丢弃附件。
⚠ 容量上限、每类上限、回收策略要由策划/运营明确，⛔ 不能让开发随机返回 `FULL`。

### 全服补偿：模板 + 资格计算 + 分批展开

⛔ **不要一次性插入全量玩家记录。**
✅ 小范围/客服/结算邮件发送时展开；**海量公告采用读取时生成**，
服务端用 `global_mail_id + player_id` 联合唯一键去重，第二次打开不再生成。

⚠ 后台发布前必须展示：内容、目标范围、**附件总价值**、预计人数、开始时间、过期时间；
高价值货币或道具需要审批。

✅ 发送按玩家分片、批次游标、限流器、进度记录执行；每批记录成功/失败/跳过，
**失败项进隔离队列⛔ 而不是中断全量任务**。重发只重放失败批次，⛔ 不能重新向所有玩家插入。

### 过期要分两层

⚠ **邮件生命周期**与**附件有效期**是两件事：

- **领取后相对过期** —— 适合玩家已知道奖励但没及时处理
- **邮件绝对过期** —— 适合活动窗口

⚠ 过期前按玩家活跃度发一次提醒，⛔ 避免在维护窗口提醒。
⚠ 清理任务只删除已达终态且超过保留期的记录，⛔ 不得删除仍在 `CLAIMING` 的附件。

## 3. 匹配与技能分

⚠ **匹配判定必须完全服务端权威。**
客户端只能提交「我要匹配什么模式、什么队伍、什么区域偏好」，
⛔ **不能携带段位、分数或历史战绩**。

✅ 服务端以账号全局 ID 查询技能、信用、惩罚、设备/账号关联、区域、模式、排队版本；
匹配池只在服务端内存或独立匹配集群维护；房间创建、队伍组合、Bot 注入、结果结算**都不信任客户端**。

⚠ 匹配请求必须带**单调递增序号和幂等键**，重复请求返回当前队列状态，⛔ 不能创建第二个排队项。
⚠ 版本不兼容、热更中的匹配规则、房间容量、地图资源都由**服务端拒绝**。

### 等待窗口分级（⛔ 不能无限放宽）

| 累计等待 | 最低质量 | 技能差倍率 | 允许范围 | 运营动作 |
|---:|---:|---:|---|---|
| 0–30s | 0.90 | 1.00x | 同地区同模式 | 严格匹配 |
| 30–60s | 0.80 | 1.40x | 同地区 | 小幅放宽 |
| 60–120s | 0.70 | 2.00x | 同地区 | 明显放宽 |
| 120–180s | 0.60 | 3.00x | 相邻地区 | 人工告警 |
| 180–240s | 0.50 | 5.00x | 相邻地区 | 推荐机器人或提示 |
| >240s | 0.40 | 9.00x | 允许跨区 | 塞机器人/低优先级池 |

ⓘ 上表是**设计起点**，须用在线匹配放弃率、胜率偏差、投诉率校准（**待核实**）。

⚠ **「等待太久就放宽」不是线性关系，而是三条曲线同时恶化**：
技能差上升 → 胜负偏差和投诉；跨区域 → 延迟；机器人填充 → 竞技可信度。
✅ 持续记录「匹配质量、等待时间、平均 RTT、掉线率、投诉率」四联指标，按模式/段位/地区分桶。
⚠ **对高段位或排位模式，宁可延长等待、跨区并明确标注，⛔ 不应无限降低技能门槛。**

### 队伍分数：不能只选平均或最高

| 算法 | 后果 |
|---|---|
| 纯平均 | 高手被低队友拖累，形成「带不动」 |
| **纯最高** | 队伍按最强者定价 → **会被高分带小号操纵** |
| 加权 | 需要校准 |

✅ 推荐「**有界平均 + 方差惩罚 + 组队修正**」：基础分为加权均值，
再按队内分差增加队伍分（使组队协作获得匹配难度），同时给开黑对手同样组队优势补偿。

⚠ **匹配作弊不是玩家自由发挥** —— 平台已公开将故意掉分（Intentional Deranking）、
带人上分（Boosting/Hitchhiking）纳入处罚范围。
✅ 队伍评分不能只追求「均值接近」，还要检测**长期固定开黑、异常胜率、弃赛、账号关联**。

⚠ **恶意退出要区分网络故障和主观违规** —— 断线重连由战斗服记录最后一次可靠状态；
超过最大重连时间才判负，但⛔ 不能给对手既完成对局又拿满收益。
惩罚递增：警告 → 收益保护失效 → 匹配延迟 → 限制排位。
⛔ **单次掉线不能永久封号**；掉线期间服务端必须允许重连且⛔ 不允许重放同一局。

### ⚠ 机器人填充是玩家信任问题，不是纯工程问题

✅ 按模式分层：
- **休闲 PvE / 新手练习** → 可明示「人机/训练对手」
- **非排位休闲 PvP** → 在用户协议和模式说明中披露「可能匹配 AI 替补」，
  ⚠ 但⛔ 避免 AI 进入公开排行榜或付费排位
- **排位和锦标赛** → ⛔ 默认不允许伪装人类

⛔ **不要通过封号式隐藏策略欺骗玩家** —— 一旦曝光风险远大于等待成本。
⚠ Bot 表现模型也应避免故意输、固定套路或可识别行为模式。

### 算法选型：取决于团队结构与信号，不是数学复杂度

| 算法 | 每玩家状态 | 不确定性 | 团队支持 | 典型场景 | 主要成本 |
|---|---|---|---|---|---|
| **Elo** | 评分 | 无原生状态 | 需队伍聚合 | 1v1 原型、透明榜单 | 活跃/回归需额外规则 |
| **Glicko-2** | 评分、RD、波动率 | 有 | 需扩展 | 活跃不均的 1v1 | 周期与参数调优 |
| **TrueSkill 2** | 高斯参数 + 信号 | 有 | 原生支持 | 复杂团队、多人模式 | 实现、解释与校准成本 |

ⓘ Glicko-2 官方建议初始值：评分 1500、RD 350、波动率 0.06；波动率约束参数通常 0.3–1.2 实验选择。
ⓘ TrueSkill 2 在 Halo 5 历史数据上预测准确率 68%，原 TrueSkill 为 52%（微软官方）——
⚠ 这**不证明它在所有游戏上更优**，也⛔ 不意味着应把击杀数直接当排位奖励。

⚠ **评分更新必须和匹配使用不同数据模型** —— 匹配池用当前估计、RD/σ 和区域；
战绩流水保存原始输入；评分服务只从流水重放。
⛔ 禁止战斗结果到达前预先更新段位，⛔ 禁止客户端直接传「我赢了多少分」。

### 赛季重置三种语义

| 方式 | 后果 |
|---|---|
| **全重置** | 实现最简单，但高手与回归玩家会集中在新赛季初期，匹配池失真 |
| **软重置**（保留部分技能估计，只降低暴露分） | ✅ 最稳妥 |
| **衰减**（提高不确定性，让不活跃玩家更快重定位） | 符合「不活跃 = 更不确定」的模型 |

⚠ 段位展示可重置，但**技能估计和匹配混乱风险⛔ 不能靠「把分清零」消除**。
✅ 混乱期通过定级赛、分池、较慢队列开放、每日评估控制（具体系数**待核实**）。

## 4. 运营数据口径

> 技术实现见 `analytics.md`，本文只讲**指标口径**。

- **DAU/MAU**、**留存**（D1/D7/D30）、**漏斗**（新手引导漏斗）、付费转化

### ⚠ 「服务端接收时间」不是字段，是一条事件生命周期规则

✅ 客户端事件必须**同时携带**客户端发生时间、客户端上报时间；
服务端在接入层接收时写入**不可变** `server_received_at`、事件 ID、源服务/版本、接收水位。

⚠ 订单、登录、匹配、战斗、资产变更的**业务时间应是服务端完成事件处理的时间**；
展示活动可按玩家当地时区显示，但**事实表永远保存 UTC 和原始时区**。
⛔ **客户端时间只能用于本地体验，⛔ 不能作为收入、留存和作弊判定的主时间。**

### ⚠ 统一 UTC ≠ 所有「自然日」都用 UTC

必须定义**三种日切**：

| 日切 | 用途 |
|---|---|
| 技术自然日 | UTC |
| 玩家本地日 | 界面和历史查询 |
| 运营活动日切 | 由运营规则定义（如固定北京时间 05:00），⚠ **一旦定义不得随时变化** |

⚠ 日活统计必须同时写清「哪个时区、哪个日切、是否去重、是否包含游客、是否按首登或任意事件」。
⚠ **跨日事件归属到事件发生日，⛔ 不是处理日**；但延迟事件要标注迟报天数。
⚠ 缺这个语义时，不同报表的 DAU、留存和付费会**永远对不上**。

### 数据回溯的默认答案是重算，⛔ 不是更新旧报表缓存

✅ 原始事件落地为**不可变 append-only 流水**；聚合表/宽表从流水重建。
✅ 管道必须有来源版本、ETL 版本、批次 ID、处理时间和重建时间，
所有聚合结果可追溯到 `(event_id, pipeline_version, rebuild_time)`。

⚠ **不要把「消息系统 exactly-once」理解成「业务天然 exactly-once」** ——
Kafka 幂等生产者把重试从 at-least-once 提升到 exactly-once delivery，
⛔ 但前提是应用层不再次发送重复记录，且消费者只读取已提交消息；
事务边界、幂等 sink 和业务主键**仍须设计**。

✅ **报表分 provisional 与 final**：
provisional 标注「数据尚未冻结，可能在补数后变化」；
final 只在事件窗口关闭、迟到数据接受期和重算 SLA 之后发布。
⚠ 运营看板默认显示报表截至时间、最近更新时间、下一重算时间。

### 事件字典版本化要兼容历史，⛔ 不是让旧数据跟着新名字跑

✅ 每个事件写入 `schema_version`、事件名、命名空间。
⚠ 字段重命名时**保留旧 reader**，⛔ 不能把 2025 年的历史 `gold` 在查询层自动翻译成 2026 的 `soft_currency`。
⚠ 删除字段标 deprecated 并保留至少一个兼容版本；新增字段用默认值或显式 unknown；类型变化用新版本和迁移函数。

⚠ **报表指标名与底层字段名要分层** —— 指标 `paid_amount` 可来自多个版本的不同字段，但必须写明版本分支。
