## 0. 一句话：韧性不是"上线前压一次"

⚠ **最危险的不是某次代码缺陷，而是"无超时 + 无限流 + 无熔断 + 无界重试"
把一次局部抖动放大成全链路雪崩。**

另一类是：备份、回滚、扩容预案**只存在于文档而从未验证**。

## 1. 限流：无限流的服务等于裸奔

⚠ 过载从不均匀发生——开服、整点活动、补偿发放、登录排队释放时，
流量可能在**数秒内跃迁一个数量级**。

**算法按"是否允许突发"和"是否允许排队"选**：

| 算法 | 特性 | 适用 |
|---|---|---|
| 固定窗口 | 简单，但**窗口边界出现两倍尖峰** | 粗粒度兜底 |
| 滑动窗口 | 统计准确，代价更高 | 精确配额 |
| **令牌桶** | 平均速率受控 + 短期突发受桶容量约束 | 登录、资源拉取等**用户入口** |
| **漏桶** | 排入有限队列、恒定速率处理 | 批量入库、消息消费、第三方通知等**出口** |

⚠ `burst` 设太大 → 令牌桶退化成"偶尔超售"；队列无限延长 → 漏桶把延迟转成 **OOM**。

| 维度 | 起始阈值（ⓘ 非标准） | 误用风险 |
|---|---:|---|
| 玩家账号 | 10–30 次/分钟，写操作更严 | 家庭 NAT 下多玩家被误杀 |
| 单 IP | 60–300 次/分钟 | 机房/校园网误伤；**不能单独作处罚证据** |
| 单接口 | 按压测拐点反推 | 单接口安全但共享线程池仍被打满 |
| 全局长连接 | 按实例连接数与 SLO 拐点 | 只限 QPS 忽略同时在线与扇出 |
| 单会话消息 | 20–60 条/分钟 | 公会聊天、宏操作误限 |

⚠ **限流响应不能只是 TCP 断开或 HTTP 500。** 要返回状态码 + 业务错误码 +
人类可读提示 + 可选 `Retry-After`。
⚠ **登录限流尤其不能提示"账号或密码错误"** —— 那是给攻击者的**账号枚举能力**。

## 2. 熔断：防持续打击已故障依赖

```
Closed ──(失败率+最少样本达阈值)──▶ Open ──(reset_timeout)──▶ Half-open
   ▲                                                              │
   └────────────(探测连续成功)─────────────────────────────────────┘
```

⚠ **Half-open 的作用是防止刚恢复的依赖被探测请求淹没** —— 只放行少量探测。
⚠ **只统计异常不统计超时，会把"永远不返回"的服务当健康。**
⚠ 只按连续失败计数而不设滑动窗口，会被低频间歇错误误触发。

可测起点（ⓘ 非标准，须校准）：**30 秒内 ≥ 20 个样本、失败率 > 50% → Open 并保持 30 秒**；
Half-open 允许 1–3 个连续成功探测。
⚠ **必须按调用类型拆分** —— 登录、支付、发货、战斗结算的失败代价不同，
不能共用一个"错误率 50%"。

⚠ 要决定是**按 endpoint 熔断还是按逻辑服务熔断**——否则单实例故障可能把整个服务快速失败掉。

## 3. 降级：产品预先批准的可用能力降级，不是隐藏报错

可降三类：**功能**（关掉全服排行榜实时刷新、公会广播）、
**精度**（用 5 分钟前的缓存榜单、返回 100 条降到 20 条）、
**一致性**（异步最终一致发货）。

⚠ 每一档降级必须配置：开关名称、灰度范围、生效/失效时间、负责人、依赖指标、
**玩家可见表现**、数据副作用、自动关闭条件。
⚠ 开关要走正式配置发布，⛔ **"直接 SSH 改生产配置"不应是常规路径**。

## 4. 超时与重试：把瞬时故障扩散成 DDoS 的放大器

⚠ **每个外部调用、DB 查询、连接建立、读写都要有明确超时。**
无限超时会把故障从下游传播到上游线程池，一个慢库拖垮整个接入层。

**从外向内分配预算**：玩家可感知操作总预算 2–3 秒，再给鉴权/缓存/DB/RPC 分更短子超时。

⚠ **重试必须遵守：可重试性、有限次数、总预算、退避、抖动、熔断。**
- 5xx、连接拒绝、限流、超时通常可重试；参数校验失败、权限不足、幂等冲突**不可重试**
- `delay = min(max_delay, base × 2^attempt) + random(0, delay × 0.2)`（ⓘ 起点：base 50ms、cap 2s）
- ⚠ **重试必须携带幂等键** —— 没有幂等键，重试支付只是把重复发货的风险换成一次失败

⚠ **重试风暴是链路上叠加出来的**：网关重试 1 次 + 接入层 2 次 + SDK 2 次
= 单次失败变 **27 倍**下游压力。
⚠ **熔断打开时返回降级结果而不是继续重试。**

⚠ **jitter 必须覆盖首次重连** —— 故障恢复瞬间所有客户端同时按固定周期重连会形成**雷鸣群**。

## 5. 数据层：先证明瓶颈，分片键决定拆分能否长期成立

⚠ **分库分表不是早期优化。** 先排除索引缺失、慢查询、锁竞争、连接池过小、
缓存命中率低、单条记录过大、写入热点；单机扩容、只读副本、表分区、
归档与冷热分层通常应先于水平分片。
⚠ **过早分片会把一次索引优化变成跨库事务、跨片聚合、全局 ID、Schema 迁移与运维平台重构。**

⚠ **分片键的实质是让主要访问路径集中在少数分片，不是让数据"看起来均匀"。**

| 场景 | 常用分片键 |
|---|---|
| 个人背包、任务、好友、邮件 | `user_id` |
| 公会、房间状态 | `guild_id` / `room_id` |
| 日志、流水、对账单 | 时间 |

⚠ 玩家最常按账号查却选了个分布均匀但查询从不带的字段 → **每次扫描全分片**；
低基数枚举分片键 → 严重倾斜。

⚠ **选错分片键的表现是"集群平均很低，但某分片持续报警"** ——
必须**按分片**统计行数、存储、读写 QPS、慢查询、锁等待、连接与复制延迟。

⚠ **扩容方案必须在拆分前确定**：是否允许双写迁移、能否按范围再平衡、
哈希冲突怎么迁移、迁移中旧路由怎么灰度。

### 冷热分离与缓存

温数据按时间分区迁到较慢存储，冷数据进对象存储/列存/归档库。
⚠ 迁移要保留索引、查询计划、批量边界、校验和与回滚点；**删除前先转不可变归档并验证可恢复**。
⚠ 运营、客服、审计、玩家下载的 SLA 不同，不应共用一套"90 天后删除"。

⚠ **读写分离只降读压力，不降写压力，也不消除复制延迟。**
核心支付/发货/战斗结果必须读主库或带版本校验；允许陈旧的要显式标 `stale=true`。

**缓存三类失效要分开治理**：

| 现象 | 解法 |
|---|---|
| **穿透**（查不存在的数据） | 参数/范围/权限校验 → 缓存空标记（短 TTL）或布隆过滤器 |
| **击穿**（热点 key 过期瞬间并发回源） | singleflight / 互斥锁 / 逻辑过期 / 主动刷新 |
| **雪崩**（大批 key 同时过期） | TTL 加**随机抖动** + Redis 高可用 + 多级兜底 + DB 限流 |

⚠ 热点 key 不可用一把大锁（无关请求被串行化）；空值与布隆过滤器可能被恶意键撑爆内存。

⚠ **DDL 风险是元数据锁、复制延迟与隐性锁升级。** 变更前审查算法与锁模式、表大小、
磁盘、活跃事务；变更中监控锁等待、线程池、IOPS、从库延迟；变更后 Schema diff + 采样查询 + 回滚演练。
⛔ **生产禁止手工粘贴未经审核的长 SQL。**

## 6. 容量：从业务事件推到全链路资源

```
峰值 QPS = 峰值同时在线 × 每人在线期间平均请求频率
（消息型还要算连接数、消息条数、大小、扇出倍数）
```

⚠ **压测要测"系统还能否受控失败"，不只是稳态 QPS。** 至少覆盖：
日常稳态 · 开服/整点尖峰 · 实例冷启动 · 缓存击穿 · 单节点故障 ·
依赖降级 · 跨区网络恶化 · 慢查询 · 连接池耗尽 · 队列积压 · **自动扩容全过程**。

⚠ **只跑到"最高 QPS"却不知道此时 P99 是否已不可接受，是无效压测。**

⚠ **扩容要按"检测—决策—申请—启动—预热—注册—验证"计时。**
若自动扩容要 5 分钟而峰值 3 分钟到，**扩容就是事故原因而非解决方案**。
→ 预测性扩容、开服前预热、预留实例应与自动扩容并存。

⚠ 生产压测是受控变更：预批准、专属标签、白名单、**一键停止**、独立监控、回滚负责人。
没有可秒停的开关就不该直接打生产。

## 7. 监控与告警：告警必须有人能立即执行

**RED**（Rate/Errors/Duration）回答"用户是否不高兴"；
**USE**（Utilization/Saturation/Errors）回答"哪里是瓶颈"。
⚠ 只有 CPU/内存的仪表盘**不能证明玩家体验良好**。

⚠ **告警对象应是"当前或即将发生的用户影响"，不是所有异常指标。**
每条 page 级告警至少含：服务/接口、用户影响、影响范围、触发条件、
确认时效、**第一动作**、Runbook 链接、负责人、抑制规则。

SLO 多窗口燃烧率起点（ⓘ 须按自身 SLO 校准）：
快速燃烧 1 小时 + 5 分钟窗口、**14.4×** 燃烧率、耗 2% 月度预算 → 紧急告警；
慢速燃烧 3 天 + 6 小时窗口、1× → 工单。

⚠ **告警必须降噪，否则告警系统本身失去信息价值。**
集群宕机时不要重复 page 所有节点；同根因合并；恢复与触发用同一事件指纹。
⚠ **告警疲劳会直接拉长发现时间** —— 工程师开始静音通知，真事故被埋在几百条里。

**告警评分三条**：代表当前用户影响？必须人 5 分钟内介入？指向唯一一组可执行动作？
**任意一条不满足就降为工单、移到 dashboard 或直接删。**
⛔ 动作只是"登录看看"说明规则层级或自动化不足。

⚠ **值班要可持续**：主岗响应止损、备岗接手调查沟通；每班交接未关闭风险、
活动变更、容量、依赖、近期部署。ⓘ 8 人维持 24/7 双岗是成熟团队经验，
小团队应记录每班 page 数与轮转公平性，**长期夜间 page 应优先偿还可靠性债务，而不是继续加人**。

## 8. 事故响应：第一指标是止损时间

| 级别 | 影响（示例） | 确认 | 止损 |
|---|---|---:|---:|
| **P0** | 全服不可用、登录/支付/核心战斗大范围失败、重大数据风险 | 15 分钟 | 60 分钟 |
| **P1** | 主要玩法或单区严重受损，明显流失/营收影响 | 15 分钟 | 2 小时 |
| **P2** | 局部受损，有替代路径 | 30 分钟 | 4 小时 |
| **P3** | 不影响玩家，内部组件或技术债 | 2 小时 | 5 工作日 |

（ⓘ 起点，须按业务影响、合规与第三方依赖校准）

⚠ **流程是"发现—定级—止损—定位—恢复—复盘"，止损与定位是两个独立目标。**
止损动作按风险从低到高：停止发布 → 关闭最近配置 → 回滚最近版本 → 切流 →
隔离故障实例 → 限流/降级 → 停活动 → 拒绝非核心请求。

⚠ **先恢复再查根因** —— 定位缓慢不能成为继续承受影响的理由。
⚠ **每次操作要有执行人、复核人、预计影响、回退条件和倒计时**；
⛔ 禁止多人同时改配置、扩容、重启和回滚。

⚠ **恢复判断依据是指标回到基线或 SLO 内，不是"告警不响了"。**
故障关闭后仍需观察至少一个完整业务周期（活动结束、登录队列清空、缓存预热完成）。

⚠ **无责复盘不是不问责，是把责任从个人转移到可改进系统。**
⛔ 禁止只写"下次注意""加强监控""提高代码质量"——
每项行动要可验证（"登录网关增加按账号限流，压测达目标值"）。

## 9. 灾备：备份要证明能在目标时间内恢复

⚠ **3-2-1 是副本起点，不是完整方案**（3 份副本、2 种介质、1 份异地）。
还要考虑不可变/离线副本、隔离的删除权限、密钥分离、完整性校验与恢复演练。

⚠ **副本数量不能证明能恢复** —— 备份可能打开失败、表结构缺失、增量链断裂、
权限丢失、回放后应用仍报错。
→ **季度全量恢复（或至少部分恢复）+ 每月随机抽样校验 + 每次重大 Schema 变更后验证**；
验证不只文件可读，还要服务启动、连接、权限、关键表行数、校验和、端到端业务路径。

⚠ **RPO/RTO 必须来自业务容忍度**，不是基础设施团队拍数字：
核心战斗状态可接受秒级回放，但**支付资产不能接受任意丢失**。

⚠ **异地多活不是可靠性的免费升级**：要考虑复制延迟、冲突解决、
全局唯一 ID、跨区调用成本与合规数据边界。
小团队更现实的是**单区高可用 + 定期备份 + 明确停机预案 + 较快单区域恢复**。

⚠ **回滚必须提前写成可执行的逐步预案**，由**不参与事故处理的第二人复核**，
关键命令先在演练环境验证，活动/发布前完成一次桌面推演。

⚠ **数据回滚往往不可行，主路径应是向前修复。**
恢复到旧时间点会创造"部分玩家回到过去"的不公平状态，也会覆盖恢复点之后的合法操作。
替代方案：PITR 到隔离环境审计、按业务对象幂等补偿、差异修复、单表/单玩家修复。
真需要全量回滚时：**先阻断写流量** → 确认恢复点与影响 → 授权人决策。

## 10. Godot 客户端侧

⚠ **客户端重试也要 jitter** —— 否则重连风暴。
⚠ 服务不可用要给明确用户提示，⛔ **不能由客户端判定服务健康或自行切换服务器**。

断线后要恢复的是：战斗状态、房间状态、玩家输入一致性——
⚠ **这些引擎都不管，必须自己设计**（见 `spectate-reconnect.md`、`netsync-advanced.md`）。

## 11. 待核对项（运行时验证）

⚠ 待核对：限流阈值、熔断阈值、超时与重试参数 · 验证：本轮数值均为**可落地起点而非行业标准**，须按压测拐点与 SLO 校准

⚠ 待核对：事故分级与响应分钟数 · 验证：本轮 P0–P3 为示例规范，须按业务 SLO、合规与第三方依赖重定

⚠ 待核对：值班人数与轮换机制 · 验证：8 人 24/7 双岗是成熟团队经验控制目标，小团队应另定指标

⚠ 待核对：RPO/RTO 与备份保留期 · 验证：须由业务容忍度 + 法定义务（税务、争议证据）共同决定
