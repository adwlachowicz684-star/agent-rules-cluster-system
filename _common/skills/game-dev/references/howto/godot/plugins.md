# Godot 插件生态与引入治理

讲"哪些轮子不该自己造"，以及"哪些轮子坚决不能引"。

## 0. 先知道生态的现状

⚠ **官方 Asset Library 已处于维护模式**。官方仓库 README 明确写：
"欢迎提交 bug 修复和小改进，但不要开发大功能，未来 Godot 基金会的 Asset Store 会废弃这个库"。

两条推论：

1. **不能写脚本硬依赖 Asset Library 的 REST 接口或资产 ID**
2. **不能假设今天能搜到的插件明天还在同一 URL**

⚠ **官方收录 ≠ 官方背书**。那是社区提交，只代表流程合规，
不代表质量认证或长期维护承诺。

## 1. 决策口诀

```
侵入数据格式的插件 → 要隔离
侵入场景树的插件   → 要谨慎
只跑编辑器的插件   → 要轻量
涉及 GDExtension   → 要锁 ABI
```

## 2. 按环节的取舍表

| 环节 | 建议 | 不该自己写的触发点 | **不该引入**的触发点 |
|---|---|---|---|
| **对话系统** | 接 Dialogic 2 一类成熟工具 | 有分支、变量、多语言时 | 仅三句以内、无分支 |
| **行为树** | 接 LimboAI / Beehave | 需要可视化调试时 | 几个状态用 FSM 就够时 |
| **DI / 服务定位** | 评估 | 服务成网、需替换实现时 | 只有约五个服务、调用单向时 |
| **瓦片/像素** | 优先内置 TileMap | 需独立编辑器工作流（Pixelorama） | 需求与内置 API 完全重合 |
| **任务/库存** | **自设计** | 极少 | 会强制接管 UI 与存档时 |
| **程序化生成** | 自写 | 需标准化算法库时 | 需求未定型时 |
| **地形/植被** | 评估独立插件 | 需开放世界 LOD 与笔刷 | 引擎新版本已覆盖该能力时 |
| **物理** | 4.4+ 用引擎内置（Jolt 已集成） | 确有精度/性能问题时 | 无实测问题只为"听说更好" |
| **网络** | 先吃透引擎 multiplayer | 需权威服/预测回滚/匹配/断线重连 | 回合制、低频同步 |
| **Steam SDK** | 用 GodotSteam + 一层 wrapper | 需成就/统计/匹配多个能力 | 仅一个 API 调用时 |
| **调试工具** | 引擎自带先用到极致 | 引擎确实没有的能力 | 工具堆叠改变帧时间分布 |

## 3. 几个重点判断

### 对话系统：坚决不要自己写

**真实工作量在格式稳定**，不在显示一行字。需要：打字机、分支跳转、变量插值、
表情立绘切换、本地化占位、条件判断、存档断点。

半年后"对话格式与存档格式互相锁定"是常见结局。

- Dialogic 2：MIT，**要求至少 Godot 4.5**，每次 push/PR 都跑 gdUnit4 单测
- 成熟的标志不是功能多，而是**有明确版本门槛 + 有测试**

⚠ **不该引入的信号**：对话只有三句提示、无分支、无变量、不需要本地化。
一个 `Label` 加 `Timer` 就够。

### 任务/库存：最不该轻率引入

**这类框架会同时侵入**：数据模型（物品、属性、堆叠、装备槽）、UI（格子、拖拽、提示）、
存档（序列化）、游戏逻辑（拾取、掉落、合成）。

⚠ 引入它≈**用一个插件的设计哲学重写整个游戏**。
替换时要重做所有数据文件，**比自写一套数据结构贵得多**。

除非框架支持**纯数据层**、不强制接管 UI 与存档，否则不建议接。
（自写方案见 `game-systems.md`）

### 物理：先看引擎版本

⚠ **Godot 4.4 已把 Jolt Physics 集成进引擎**。
为 4.3 及更早版本写的 Jolt 扩展，在 4.4+ 上可能只是重复加载。

**引入流程**：确认默认物理是否满足 → 确认有可复现问题 → 再评估扩展。
不要"听说某物理更好"就换。

⚠ **换物理引擎是全项目回归测试**，不是改个设置。
碰撞精度、连续碰撞、关节稳定性、射线行为全变，
所有手感调参、关卡碰撞、根运动动画都要重测。

### 网络：先吃透引擎自带

引擎已提供 RPC 与场景复制，且默认不允许解码可能携带脚本的对象
（规避任意代码执行）。

⚠ **网络框架把简单问题变难的比例很高**。
回合制/低频同步用引擎 RPC 几十行就够；
引入框架要理解它的同步模型、生命周期钩子、序列化规则。

框架的甜区是**高频动作游戏的预测与回滚**，不是"能连上就行"。

### DI：Godot autoload 已解决八成问题

⚠ **DI 容器越大越专业是错觉**。只有约五个服务、调用关系单向清晰时，
autoload + 显式构造已经够用。

DI 要求定义接口、绑定规则、作用域 ——
这套仪式在小项目里**比它消除的耦合更贵**。
而 GDScript 是动态类型，"接口绑定"的静态校验价值天然打折。

真正该上的信号：服务互相引用成网、测试需要替换实现、同一接口有多个实现。

> **反模式清单（不能怎么做，审核用）** → `audit/godot/plugins.md`


## 4. 引入前的检查清单

```
1. 许可证 —— 是否允许商用？传递依赖呢？
2. 版本兼容矩阵 —— 有针对 4.x 小版本的明确说明吗？
3. 维护活跃度 —— 最近提交时间、CI 状态、有无测试
4. api_version —— GDExtension 的 ABI 是否对齐当前引擎
5. 侵入范围 —— 改 .tscn 吗？接管存档吗？锁数据格式吗？
6. 替换成本 —— 一年后要换掉，要改多少文件？
7. 操作频率 —— 这个操作每天跑几次？（低频不值得装）
```

**锁定方式**：

```
Git submodule + 固定 commit   ✅
写"兼容 Godot 4.x"版本范围     ❌
```

⚠ **锁 commit 是唯一的复现方式**。
只给版本号、不给 commit 的引入方式，
在 Godot 小版本升级时**必然**变成排查负担。
