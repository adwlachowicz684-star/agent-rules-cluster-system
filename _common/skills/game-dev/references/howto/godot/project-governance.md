# Godot 4.x 性能预算 / CI / 评审 / 技术债

## 0. 性能预算：不能只写"60 FPS"

预算必须按**"目标硬件 × 目标画质 × 代表性场景 × 稳定态指标"**定义。

**每个档位建 3–5 个代表性负载**：空场景/大厅、最大密度战斗、主城/NPC、长时运行、低端机基线。

测量至少覆盖：帧时间、物理帧时间、脚本/渲染分项、对象数、内存、
资源内存、可见对象、draw call、平台特有指标。

⚠ **预算要区分平均值与 P95/P99** ——
平均 16 ms 仍可能每几秒卡顿一次。

**示例台账**（数字仅为示例，非官方阈值，必须由目标设备实测校准）：

| 场景 | 指标 | 示例阈值 | 测量条件 |
|---|---|---|---|
| 战斗 | P95 帧时间 | ≤18.5 ms | 中端机、稳定态 60s |
| 主城 | P99 帧时间 | ≤33.3 ms | 峰值人群 |
| 长时 | 内存增长 | 30 min ≤2% | 固定循环路线 |
| 低端机 | P95 | 不超目标帧预算 | 低画质预设 |

## 1. 测量的三个陷阱

⚠ **Profiler 默认关闭，因为它本身有开销** ——
开启状态下测的结果不能直接给发布包定预算。

⚠ **C# 不受当前 Godot Profiler 支持** —— 要用 Rider/dotTrace。

⚠ **部分 `Performance` 监视器在 release 构建恒返回 0** ——
CI 必须区分 debug 测量、release 测量与基线，不能混为一谈。

⚠ **部分监视器最多每秒更新一次** —— 查再频繁也不更细。

⚠ **headless 无渲染不能代表目标设备渲染性能** ——
它适合逻辑、加载、内存与服务器回归。

⚠ **"帧率不到 60 所以脚本慢"** —— 帧时间包含渲染，
物理、粒子、音频、脚本都可能贡献尖峰。

## 2. CI 判定规则

```gdscript
# 采集：warm-up 后采样，去启动尖峰
samples.append(Performance.get_monitor(Performance.TIME_PROCESS) * 1000.0)
```

⚠ **CI 不应用单次采样判定** —— 至少 warm-up 后收集 N 个样本，
计算均值/P95/P99/最大峰值/内存峰值，再与基线比较。

**门禁两层**：
- 硬阈值突破 → 阻断发布
- 相对基线变化超噪声带 → warning 并要求解释
- 连续多个版本退化 → 升级为 release block

⚠ **不能把"今天随机快 1%"解释为优化有效** ——
要固定进程亲和性、画质、随机种子，允许少量 retest。

⚠ **所有"优化 PR"必须附前后同设备数据** ——
没有基线数据的优化不得标为性能修复。

## 3. 构建流水线

```bash
godot --headless --path "$PROJECT_DIR" --export-release "Windows Desktop" "build/windows/MyGame.exe"
```

⚠ **预设名称区分大小写且必须加引号** ——
`Windows Desktop` 的空格与大小写要与项目导出配置完全一致。

⚠ **CLI 相对输出路径相对 `project.godot` 所在目录**，不是 shell 当前目录。

⚠ **"导出模板只要版本号相同就行"是错的** ——
还要关注 stable/beta/RC、标准/.NET、平台、架构、自定义编译选项、符号匹配。

⚠ **不要只提交 `export_presets.cfg` 却不锁定模板**。

⚠ **版本号要分开** ——
`application/config/version` 是营销版本；构建号由 CI 单调生成。
重构建不会自动递增 `version` 字段。

⚠ **签名密钥/证书/密码只在 CI secret** —— 绝不写进 `export_presets.cfg`。

## 4. 符号与崩溃符号化

⚠ **默认 `debug_symbols=no`** —— 不开则崩溃堆栈没有源码文件和行号。

⚠ **`separate_debug_symbols=yes` 把信息放进独立文件**（Windows/MSVC 生成 `.pdb`）。

⚠ **符号必须与确切构建一一对应保存** ——
自定义编译引擎要为每个发布的 commit/平台/架构/配置保存符号。

⚠ **不能把 debug 构建当发布包**（保留调试、远程调试、未剥离符号）；
也**不能把 release 包直接拿去分析崩溃**（找不到对应符号）。

## 5. 代码评审：不只审 .gd

完整 PR 至少检查：行为、API 边界、节点结构、资源引用、性能影响、
可测试性、平台影响、可回退性。

**GDScript 重点**：类型注解、生命周期、错误路径、`await` 与节点释放、
信号连接与断开、工具脚本副作用、`_process`/`_physics_process` 成本。

**场景 review 核心**：节点为什么存在、如何通信、谁拥有它。

⚠ **不要只审代码行把 `.tscn` 当"非代码"** ——
结果节点泄漏、信号丢失、owner 错误、巨大场景进主干。

⚠ **4.4+ 以后 UID 身份比文件存在更关键** ——
文件在但 UID 错配仍可能异常。检查器要同时看 UID 和路径。

⚠ **reviewer 用自己机器缓存打开项目未执行 `--import`** ——
把陈旧 `.godot/` 当成项目状态。

⚠ **"没有报错"不等于"没有风险"** ——
Godot 常给 push_error/warn，不会使进程立即崩溃。

**大场景 diff 拆分**：节点结构一次 PR、数据/资源一次 PR、外观一次 PR。

## 6. 技术债：可验证、可回退

**风险分层**：
| 层级 | 操作 |
|---|---|
| 低 | 重命名/移动资源 |
| 中 | 抽取数据资源 |
| 高 | 拆分/重组场景 |
| 最高 | 改脚本继承、autoload、信号架构、序列化格式、存档格式 |

⚠ **高影响变更必须分多个 PR**：
先增加兼容读取与迁移测试 → 再切换写入 → 最后清理旧路径。
不要在单个 PR 同时改序列化格式、玩家状态和发布流程。

**资源格式迁移保留版本字段与双读能力**：

```gdscript
class_name PlayerStats extends Resource
const FORMAT_VERSION := 2
```

⚠ **Godot 会丢弃 TRES 注释、省略默认属性** ——
迁移事实不能藏在资源注释里，要用显式版本字段和测试覆盖。

⚠ **不要用"把默认属性写进去"当行为修复** ——
手工加入的默认项保存时会被丢弃。

⚠ **`@tool` 脚本在编辑器执行** —— 可能重排场景、污染缓存或造成保存副作用。

⚠ **只重命名不迁移保存数据** —— 旧存档、配置、热更资源、外部工具仍引用旧字段。

⚠ **重构后只测编辑器不测目标平台与 release 包** ——
发布模板、headless 服务器、debug 构建可能暴露不同问题。

**重构触发条件要可量化**：单场景超约定复杂度、一目录长期多人冲突、
资源重复率上升、场景加载时间增长、bug 集中在继承链、测试无法构造依赖。

⚠ **每次提交保持游戏可启动** —— 避免一次 500 文件"大扫除"。

> **反模式清单（不能怎么做，审核用）** → `audit/godot/project-governance.md`
