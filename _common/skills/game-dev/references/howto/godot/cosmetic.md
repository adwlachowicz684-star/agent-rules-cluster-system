# 外观与个性化：时装 / 称号 / 头像框 / 表情动作 / 染色（Godot 4.7.2）

**此前文档里「捏人 / 时装 / 称号 / 头像框 / 表情动作 / 坐骑皮肤」全部 0 命中。**

> ⚠ **与 `character-customization.md` 的分工**：那篇是**角色外观定制**（捏脸/体型），
> 本篇是**"不改数值、只改外观"这一整类资产**的共同规律：
> 时装、坐骑皮肤、称号、头像框、表情动作、染色、捏人部件。
> 商业化/内购见 `monetization.md`；装备四层分离见 `economy.md`；坐骑移动驱动见 `companion.md`。
>
> ⚠ **与 `character-customization.md` 的分工（两层，不要混）**：
> 那篇是**技术层**（Blend Shape、合并网格、换网格的骨骼兼容、染色实例材质、skeleton 路径）；
> 本篇是**资产系统层**（能不能拥有、优先级、有效期、谁说了算、加载回退、同步、商业化）。
> 换网格与染色的具体做法已在那篇，本篇只在需要时指向。

⚠ **一句话定调**：客户端只持有**可展示缓存**，服务端保存**拥有权、有效期、优先级和授权**；
所有选择、过期、称号赋予、表情播放都回到服务端裁决。

> 审核用反模式清单见 `audit/godot/cosmetic.md`

## 0. 七类外观共享的是"展示状态"，不是资产形态

七类资产技术形态差异很大，但**生命周期高度相似**：获得 → 进库存 → 选槽位 →
判断有效性/优先级/范围 → 客户端加载展示 → 服务端记录并同步 → 过期/卸下/失败回退默认。

统一拆成三层：

| 层级 | 代表数据 | ⛔ 不应混入 | 职责 |
|---|---|---|---|
| **外观模板** `AppearanceTemplate` | ID、类型、槽位、显示名、资产引用、优先级、有效期规则、适用种族/体型、兼容骨骼、染色参数、可见场景 | 玩家拥有状态、具体染色值、动画冷却 | 定义"这是什么、能放哪、怎么展示" |
| **外观实例** `AppearanceInstance` | 实例 ID、模板 ID、来源、获得时间、到期时间、当前染色、锁定 | 网格/材质/动画**资源本体** | 记录"这个玩家拥有的这一份及其使用边界" |
| **生效外观** `ActiveAppearance` | 槽位、实例 ID、校验签名、应用时间、场景/距离/对象范围、版本摘要 | 完整资源对象、完整玩家档案 | 决定"当前显示哪个"，供网络同步 |

⚠ 不抽象的后果是七套互斥、难以审计的逻辑，各写一套"是否拥有/何时到期/能否在战斗用/加载失败显示什么"。

⚠ **"生效范围"不是可有可无的附加字段** —— 至少含：哪个角色、哪个槽位、哪些场景、
哪些观察者距离、是否只对好友或队友可见。
⛔ 没有它，活动外观容易被写成"全游戏任意位置生效"，
结果战斗、竞技场、过场、观战各自取数据 → "服务端允许、客户端拒绝"。

### 槽位冲突按优先级仲裁，不是按点击顺序覆盖

⚠ 优先级比较字段固定为 `(scope_rank, source_rank, obtain_time, instance_id)`。
`scope_rank` 解决全服可见还是仅自己可见，`source_rank` 解决付费与活动的冲突。
⛔ **不能只比较付费与否** —— 一个基础外观可能来自新手任务，也可能是限时回归活动。

### 过期要分三种状态

`unexpired` / `grace_period` / `expired`。
⚠ 到期时服务端要先把槽位从限时外观释放，**再**把 `ActiveAppearance` 设为该槽位的默认/永久外观，
⛔ 不能把槽位留空。

## 1. 换装与染色：技术实现见专门文档

| 需求 | 去哪 |
|---|---|
| 三种换装技术（换贴图 / 换网格 / 骨骼挂点）的成本交换 | → `character-customization.md` |
| ⚠ 骨骼名相同 ≠ 可换网格（层级与 Bone Rest） | → `character-customization.md` §4.5 |
| ⚠ 染色必须实例材质，改共享材质会污染所有同材质对象 | → `character-customization.md` §4.6 |

⚠ **本篇只补那篇没有的两条**：

**① 换装失败的处置是服务端职责。**
`character-customization.md` 讲的是"怎么换上去"，但"换不上去时显示什么"要服务端裁决：
响应码区分 `invalid` / `conflict`（返回权威外观）/ `not_owned`（清缓存）/
`expired`（替换默认）/ `asset_missing`（显示占位）。
⛔ **`asset_missing` 时绝不能把"客户端本地有这个资源"当成拥有**。

**③ ⚠ `SkeletonProfile` 只是提示，不阻止导入。**
Godot 的骨骼配置（`SkeletonProfileHumanoid` 等）用于在导入/绑定阶段
提示骨骼命名与层级问题，⚠ **它不会阻止你把一套不匹配的网格导入进项目**，
也不会在换装时替你校验。

⛔ 后果：编辑器里看着没红字，运行时换上去才发现手臂扭曲。

✅ 要在 **CI 或资产管线里自建指纹校验** —— 对每套换装网格比对
骨骼名集合 / 层级 / Bone Rest，不符即失败。
ⓘ 判据是"导入期失败"，不是"运行时看着不对再去查"。

**② 账号级与角色级外观共存时，所有权要分清。**
跨角色共享的时装仍按角色保存最后选择，**账号共享只是授权范围**，
⛔ 不应让角色 A 的选择直接覆盖角色 B。

## 2. ⚠ 第一道隔离：显示用 A，属性用 B

⚠ **显示链与属性链必须各自独立取数**，这是外观系统最重要的一条隔离。

| | 显示链（A） | 属性链（B） |
|---|---|---|
| 数据 | `ActiveAppearance` + 外观资产 | 装备实例 / 角色数值 / 能力模板 |
| 谁来问 | 渲染、动画、UI 展示 | 战斗、移动、碰撞、经济结算 |
| 失败时 | 回退默认外观，⛔ **不影响任何数值** | 与外观无关 |

⛔ **最常见的越界**：外观挂点被写成"顺便提供碰撞/移速/技能参数"，
于是换一件时装等于改一次战斗数值 —— 而这在功能测试里**完全测不出来**
（测试只验证"穿上后能跑能打"）。

✅ 落地判据（CI 可查）：
- 外观目录/资源**不得**含 `collision_shape`、根运动、移速、伤害、命中范围字段
- 战斗与移动代码**不得**读取外观实例上的任何数值字段
- 外观实例与装备实例**分离存储**：装备交易/分解/回滚不该让时装消失（见 `economy.md`）

ⓘ 反过来说，"外观改数值"的诉求（如坐骑皮肤带移速）应当**显式转成数值系统的一部分**
并纳入平衡与商业化审批，⛔ 不能藏在外观资产里悄悄生效。

## 3. 称号 / 头像框：纯 UI 资产，但仍要服务端权威

⚠ **称号可伪造 → 冒充 GM / 客服。** 这是权限伪造与社会工程攻击的入口。

✅ 服务端签发**白名单、拥有状态、展示签名**；
⛔ 客户端不保存内部称号枚举，只保存可展示文本与脱敏 UI 标记。

⚠ 称号的显示规则要显式定义：同时只显示一个？还是可叠加前缀后缀？
⚠ 高权限称号变更必须**重新签名**。

## 4. 表情动作：动画 + 网络同步，是骚扰与外挂高发点

⚠ 表情/动作是**动画资产 + 网络同步**，常见滥用：卡动作、循环播放刷屏。

✅ 要有：冷却、距离限制、场景过滤、举报入口。
⚠ 服务端可**停止广播并中断动作**；要有频率、距离与举报日志。

## 5. 坐骑皮肤：只改外观，⛔ 不能改碰撞与移速

⚠ 与 `companion.md` 的坐骑移动驱动衔接 —— 皮肤只访问**渲染层和附件层**，
⛔ 不接触移速、碰撞和技能。一旦外观带来移速、碰撞、命中范围或隐藏判定优势，
就**不再是无属性付费**。

✅ 用能力模板，⛔ 丢弃皮肤自带的移动/碰撞参数。
⚠ CI 扫描：是否存在 `collision_shape`、根运动、修改 `scale`、读取动画事件触发战斗结果。

## 6. 加载：必须保留默认外观、超时、令牌、取消

⚠ **外观资产的两难**：大厅要看到所有人的外观，但同屏大量玩家会打爆内存与 I/O。

✅ 策略：默认外观采用**零外部依赖**的基础网格与内置材质（⛔ 回退路径自身不能依赖网络）；
按需异步加载；有 LOD、上限与取消路径。

```gdscript
func apply_or_load(slot, template, target) -> void:
    if template.resource_path.is_empty(): apply_default(slot, target); return
    if asset_cache.acquire(template.resource_path): apply_appearance(...); return
    if _loaders.has(path): _loaders[path].add_waiter(slot, target); return
    start_loader(template)      # ResourceLoader.load_threaded_request

func fail_loader(loader) -> void:
    for item in loader.waiters: apply_default(item.slot, item.target)   # ⚠ 回退默认
    _loaders.erase(loader.path)
    # ⛔ ResourceLoader 没有 cancel API —— "取消"只能是丢弃结果，不是中止加载线程
```

⚠ **取消语义**：从 A 切到 B 而 A 仍在加载时，B 完成后必须**丢弃 A 的结果**，
⛔ 不能出现"最终完成的请求不是最新请求"。用请求令牌或 `slot_version` 校验。

⚠ **卸载不能只看离开视锥** —— 角色可能很快重新进入，要先进低质量状态；
⚠ 同一资产被多个玩家共享时，引用计数要区分"展示引用"与"缓存持有"，
⛔ 避免一个玩家离开就导致其他玩家卸载。

⚠ **"资源已加载完成" ≠ "外观已展示"** —— 要另设 `asset_applied` 状态，显式回调。

### 6.1 ⚠ 官方线程加载的四个坑（与"多玩家等同一件时装"直接冲突）

| 官方口径 | 后果 |
|---|---|
| ⛔ `load_threaded_get()` **会把任务从列表移除**（一次性检索） | 第一个等待者取走后，其余人再查状态得到 `THREAD_LOAD_INVALID_RESOURCE` → 被当成"资源无效"而回退默认 |
| ⛔ 未完成时调 `load_threaded_get()` **会阻塞调用线程** | 在主线程调用可能死锁；官方要求轮询 `load_threaded_get_status()`，⛔ 不要在循环里等 |
| ⛔ **没有 cancel API** | "取消"只能是**丢弃结果 + 令牌校验**，⛔ 不是中止加载线程 |
| ⛔ 资源缓存是**弱引用**，自己不持有会被释放 | 外观"偶尔失效又重新加载"，且重载后是新实例 → 已染色的实例参数丢失 |

⛔ **第一条对本域最致命**：上面的 `add_waiter` 模式（多玩家等同一件时装）
与官方"取走即移除"的语义**直接冲突**。表现为"第一个人穿上正常、后面的人全回退默认"，
而日志里写的是"资源无效" —— 排查必然被引向资源路径或导出设置，
不会想到是**同一次加载被取了两次**。

✅ 正确做法：**取一次，自己缓存，再广播给所有等待者**；
后续请求一律走自己的 `asset_cache`，⛔ 不对同一 path 二次 `load_threaded_get()`。

ⓘ `use_sub_threads = true` 更快但**会影响主线程、造成卡顿** ——
大厅同屏大量外观时，默认的单线程模式（false）反而是对的。

⚠ **加载侧的"独立实例"由 `cache_mode` 决定**：默认 `CACHE_MODE_REUSE`（1）
会复用缓存里的同一个资源实例；需要真独立时用 **`CACHE_MODE_IGNORE`**。
⛔ 只做"材质 `duplicate()`"而不管 `cache_mode` —— 同一路径仍返回同一实例，
染色照样污染所有同材质对象，⛔ 而检查材质时它确实是实例材质（看着完全对）。

### 6.2 ⛔ 导出后运行时加载：默认的二进制转换会让它整体失效

官方：`editor/export/convert_text_resources_to_binary` **默认 `true`**，并明确
*"@GDScript.load will not be able to read converted files in an exported project"*，
同时 *"Some file paths within the exported PCK will also change, such as project.godot becoming project.binary"*。

⛔ 只要依赖运行时加载 PCK 内文件（外观资产、UGC 素材），就必须把该项设为 **`false`**。
表现为"编辑器里一切正常、导出后外观全部回退默认"，⛔ 且不报"路径不存在" ——
因为文件确实在包里，只是读不出来。

## 7. 网络：进场景全量 + 变更增量 + 周期全量校正

⚠ **`MultiplayerSynchronizer` 不能可靠同步 `Object` 类型资源**，
对象实例 ID、RID 等每端不同的值也⛔ 不能直接复制。
✅ 只同步小体积的 **ID、版本、校验摘要**，由客户端查找或异步加载真实资产。

| 事件 | 同步方式 |
|---|---|
| 进入场景 / 首次可见 | **全量 manifest**（槽位、称号、头像框、表情 + 签名） |
| 选择时装 | 增量 + 版本（失败返回当前权威状态） |
| 开始/结束表情 | 事件 + 截止时间（客户端按时间自然结束并支持中断） |
| 称号/头像框选择 | 全量或增量（**高权限称号必须重新签名**） |
| 染色变更 | 实例参数哈希 |
| 移动中重复可见 | **周期性全量** |

⚠ **`appearance_version` 单调递增**，客户端收到增量后比对版本，
只有不存在历史缺口时才应用，否则**请求全量校正**。

⚠ **丢包不会自愈** —— 增量只描述变化，若"卸下帽子"丢失，
本地玩家不会主动知道自己少收到事件（外观没有天然周期性重写）。
✅ 明确全量时机：新端加入、对象重新可见、客户端请求、定期周期、
优先级/有效期变化、连续多个 delta 缺失、玩家打开名片查看角色。

✅ 服务端也可发轻量摘要包（每槽位 `instance_id + asset_version + checksum`），
只有摘要不一致时客户端才请求对应槽位 —— 同时降带宽与"少一个事件永久不一致"的风险。

## 8. 商业化：承诺的核心是明确"外观到底不改什么"

⚠ 只在购买协议写"本商品不影响平衡"**不够** ——
每次热更新增资产都要自动检查外观包是否含移动、碰撞、伤害和判定字段。

⚠ 商城/公告/购买页至少写明：是否永久、是否限时、是否可交易、是否绑定角色、
是否随账号转移、染色是否独立、**到期后是消失还是转永久**、坐骑皮肤是否含移速/碰撞变化。

### 限时时装的六个状态

| 状态 | 含义 | 处理 |
|---|---|---|
| `unused` | 尚未应用 | 可核验来源、有效期、退款政策 |
| `active` | 当前可展示 | 允许选择，持续校验有效期 |
| `expiring_soon` | 即将到期 | ⚠ **向本人提示，⛔ 不向他人泄露** |
| `grace` | 业务宽限 | 是否可继续展示由规则决定 |
| `expired` | 失去展示资格 | 释放槽位并应用默认外观 |
| `granted_again` | 重新获得或补偿 | 重新进入 unused/active，记录来源 |

⚠ "到期后消失但保留展示资格"与"到期自动转永久"是**两种完全不同的产品承诺**，
必须在**购买前**明确。技术系统应支持两种规则，⛔ 但不能默认替运营选择。

⚠ **未使用外观是否可退，⛔ 不能由外观系统自行决定** ——
退款口径与发行地区、支付渠道、是否使用、是否拆封、当地消费者法有关。
✅ 退款决策放到订单和客服服务，外观系统只提供不可变的来源/应用/到期/版本/资产校验与日志。

⚠ **外观包与数值包不能靠资产目录区分** —— 即使放在 `cosmetic/` 下，
只要网格自带碰撞、动画自带根运动，或材质参数被战斗系统读取，就可能产生数值效果。
✅ CI 扫描发现后阻断构建或要求显式风险豁免。

## 9. UGC 外观：责任不因"玩家上传"而转移

⚠ 平台要履行信息内容管理主体责任（含发布审核、巡查、举报入口、处置）。
⛔ 不能只依赖上传时一次关键词检查 —— 模型、贴图、动画、染色和**组合结果**
可能共同构成违规内容。

| 阶段 | 处理 | 必须保留 |
|---|---|---|
| 上传预审核 | 静态资源扫描、恶意内容检测、资产结构检查 | 上传时间、账户、版本、检查结果 |
| 发布审核 | 人工或模型复核，通过后才进可展示白名单 | 审核员、规则版本、通过时间 |
| 发布后巡查 | 抽样检测、举报复核、异常热度监控 | 举报事件、复核结论、处置时间 |

⚠ 染色虽不直接上传贴图，但可用 UGC 资产或自由参数组合 → **也应纳入巡查**。
⚠ 服务端对 UGC 下发**临时访问令牌和过期白名单**，⛔ 客户端不得永久缓存违规资产。
下架时服务端从白名单移除并广播撤销事件，客户端**立即隐藏**，⛔ 不等下次刷新。

## 10. 双仓库：外观业务规则不应混写在节点脚本里

⚠ Godot 节点是运行时组织和可序列化结构，⛔ 不应承担"谁拥有哪件限时时装"的真相。

| 层级 | 存放 | 权威方 |
|---|---|---|
| 内容仓库 | 网格、材质、动画、图集、场景、骨骼 profile | 美术与内容管线 |
| 配置仓库 | ID、槽位、优先级、有效期、兼容关系、染色槽 | **服务端配置** |
| 玩家状态仓库 | 实例、来源、获得时间、到期时间、展示选择 | **服务端** |

⚠ 账号级与角色级外观可共存，但所有权要明确：
跨角色共享的时装仍按角色保存最后选择，**账号共享只是授权范围**，
⛔ 不应让角色 A 的选择直接覆盖角色 B。

ⓘ Godot 4.7 支持多平台 HDR 输出（官方称最高可达 10,000 nits）。
若项目用 HDR 外观，要明确"标准外观"与"HDR 增强"是否同一商品，
避免同一套资产在不同设备上被玩家感知为不同品质。

## 11. 待核对项（运行时验证）

⚠ 待核对：加载预算 `LOAD_BUDGET_MS`、超时 `LOAD_TIMEOUT_SECONDS`、同屏外观预算 · 验证：**项目实测**，与平台和目标机型相关

⚠ 待核对：表情动作的冷却、距离、场景过滤阈值 · 验证：项目实测；须有举报与服务端中断能力

⚠ 待核对：全量校正周期、增量摘要频率、观战/外观的可见性过滤字段 · 验证：项目实测，与同屏人数和带宽相关

⚠ 待核对：限时时装的宽限期与退款口径 · 验证：**不由外观系统决定**，须按发行地区、支付渠道与当地消费者法确认

⚠ 待核对：UGC 外观的审核流程、保留期限与临时令牌有效期 · 验证：按合规要求与运营成本确认

⚠ 待核对：账号级与角色级外观的具体归属规则 · 验证：按项目设计确认，须避免角色间选择互相覆盖
