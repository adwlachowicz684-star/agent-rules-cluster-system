# 待核对项：运行时录入与验证

## 为什么有这套机制

技能文档里写着大量**"我没有在目标版本/真机上实测过"**的结论。

这些结论如果和已验证结论混在一起，读者无法区分
"可以直接信"和"要先测一下"——而后者被当成前者用，
正是最难排查的一类问题：**代码写对了、逻辑想通了，但前提是错的。**

## 标记格式

写在 Godot 开发文档里，**一行一条**：

```
⚠ 待核对：{结论} · 验证：{怎么验证}
```

例：

```
⚠ 待核对：ArcCast3D 节点是否存在 · 验证：4.7.2 编辑器节点搜索框输入 ArcCast3D
```

⚠ **`验证：` 后面那句是必须的** —— 它决定了这条能不能被验证。
只写"待核对"不写方法的，`verify.py` 会报出来要求补。

## 用法

```bash
python3 scripts/verify.py                # 只看还没验证的（默认）
python3 scripts/verify.py --all           # 含已验证的
python3 scripts/verify.py --stats         # 统计概览
python3 scripts/verify.py --doc=xr-deep.md
python3 scripts/verify.py --grep=手部
```

### 运行时录入

在真机 / 目标版本上验证之后，把结果记下来：

```bash
python3 scripts/verify.py --verify=V5001 --result=ok
python3 scripts/verify.py --verify=V5001 --result=failed \
        --note="4.7.2 编辑器确实没有该节点，需手动实现"
python3 scripts/verify.py --verify=V5004 --result=skipped \
        --note="无头显设备，无法验证"
```

| result | 含义 |
|---|---|
| `ok` | 验证通过，结论成立 |
| `failed` | 验证推翻，结论错了 |
| `skipped` | 无条件验证（缺设备/版本） |

`--result=failed` 的记录特别有价值：它保留"当时以为是这样、后来发现不是"的痕迹，
避免同一个坑被重新踩一遍。

## 设计取舍

**ID 用「文档序号 + 条序号」，不用内容哈希。**
哈希的话改一个字 ID 就变，之前录入的验证结果会全部失配。

**状态不写回文档，放独立文件 `.verify-state.json`。**
多窗口并行改文档会互相覆盖（已发生过两次），状态放外面不参与冲突。

**ID 会在文档列表变化时漂移**，所以录入前先跑一次 `--verify` 时脚本会校验 ID 存在，
ID 不存在会直接报错而不是静默写错。

## 什么时候该标"待核对"（判定标准）

⚠ 这套机制的价值取决于**标得准不准**。
标多了会稀释可信度，标少了等于没标。

### ✅ 该标的三类

| 类型 | 例 |
|---|---|
| **版本/平台相关，我没在目标上实测** | "4.7.2 编辑器是否有某节点" |
| **数字来自二手来源，权威性不足** | 社区复现的内存数字 |
| **官方口径有争议或正在变动** | 某法规阈值存在废止争议 |

### ⛔ 不该标的三类

| 类型 | 为什么 |
|---|---|
| **已引官方原文且明确** | 那就是已验证 |
| **纯逻辑推导/数学结论** | 不需要真机 |
| ⚠ **"我不确定但懒得查"** | 这是没查，不是待核对 |

⚠ 最后一条是机制退化的主因：把"没查清楚"记成"待核对"，
条目会无限膨胀，最终没人再信这个清单。

## 条目拆解：一条只能包含一个待定结论

ⓘ **反例**（⚠ 下面必须放代码块，裸写会被 `verify.py` 当成真条目收集）：

```
⚠ 待核对：FSR2 在 Mobile 与 Compatibility 下的表现 · 验证：两个渲染器下分别导出实测画质与帧率
```

⚠ 这是**两个**结论（两个渲染器），但它们可能**一个对一个错**。
合成一条 → 只能整体标 ok 或 failed，**丢失一半信息**。

✅ 拆成两条，各自独立验证。

ⓘ 判据：**一条只能有一个 `result`**。
如果你发现"部分对了"，说明该拆。

## `--result=failed` 为什么特别有价值

⚠ **它保留"当时以为是这样、后来发现不是"的痕迹。**

ⓘ 这类记录的价值不在当下，而在**三个月后**：
有人重新遇到同一个问题时，如果只有"结论"，他会**重新踩一遍**；
有 failed 记录，他能看到"这条路试过，不通"。

✅ 所以 failed 时 **`--note` 要写清"实际是什么"**，
⛔ 不能只写"不对" —— 那等于没记。

## skipped 不是"跳过"，是有信息量的结论

ⓘ `skipped` 的语义是**"无条件验证"**（缺设备/版本）。

⚠ 它与 `failed` 的区别必须清楚：

| result | 含义 | 对结论的影响 |
|---|---|---|
| `ok` | 成立 | 可以信 |
| `failed` | ⛔ **被推翻** | **不能再信，要改文档** |
| `skipped` | 没验证 | ⚠ **仍然不确定**，保持待核对 |

⛔ 把"测不了"记成 `ok` 是这套机制最严重的滥用 ——
它会把一个从未验证过的结论变成"已验证"。

## failed 之后必须做的事：改文档

⚠ **录入 failed 不等于处理完了。**

⛔ 常见错误：记一条 failed 就结束，文档里那条错误结论**还原样躺着**。
下一个人读到的还是错的，只是系统里多了一条没人看的记录。

✅ 流程：
```
记 failed → 改文档（纠正或删除该结论） → 该条目归档
```

ⓘ 判据：**failed 的条目在文档里应该已经找不到对应错误结论**。
如果还在，说明没处理完。

## 与 `scan-gaps.py` 的分工

ⓘ 两个工具都在找"不足"，但找的东西不同：

| 工具 | 找什么 | 粒度 |
|---|---|---|
| `verify.py` | **具体结论**是否可信 | 一条断言 |
| `scan-gaps.py` | **域/主题**是否覆盖 | 一个概念 |

⛔ 不要混用：
- "这个 API 到底存不存在" → `verify.py`
- "这个功能域有没有文档" → `scan-gaps.py`

## 自检

```bash
python3 scripts/verify.py --self-test
```

覆盖：能收集到条目、ID 无重复、每条都有验证方法、
能检出"只写待核对没写验证方法"的条目（造坏样例）、状态读写往返。
