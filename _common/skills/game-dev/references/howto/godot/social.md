# 多人社交：大厅、匹配、好友、聊天（Godot 4.7.2）

"matchmaking""大厅""lobby""组队""公会""邮件""公告""举报""敏感词" 此前 **几乎全部 0 命中**。

⚠ **这不是遗漏，是这些功能本就不在 Godot 引擎职责内。**

## 0. ⚠ Godot 不内置任何社交服务

**Godot 不内置匹配服务、好友关系、持久公会、邮件、公告或聊天服务器。**

⚠ **ENet 也不是完整的 P2P 服务网络，而是基于 UDP 的传输层。**

官方类参考写明：ENet 只用 UDP；公开服务器只需转发 UDP 端口；
`create_server` / `create_client` / `create_mesh` 分别对应监听、连接、网状模式。

这能让你在两台机器间建立连接，**但不能替你解决**：
陌生玩家怎么报名、两个对称 NAT 后的玩家如何会合、**房主关机后历史记录去哪**。

⚠ "P2P"也要区分：ENet 的 client/server 模型里服务器仍是中心权威节点；
mesh 才是所有节点彼此连接，但**仍需你自己用信令服务交换地址与端口**。

## 1. 三层架构（推荐）

| 层 | 走什么 | 内容 |
|---|---|---|
| **认证与会话** | HTTPS | ⚠ 不以 Godot peer ID 作为玩家身份 |
| **社交控制面** | HTTPS/WebSocket | 大厅、匹配、好友、组队、聊天、公会、邮件、公告、举报 |
| **战斗数据面** | ENet/WebSocket | 进房间后的实时同步 |

⚠ 这样玩家掉线、崩溃、本地主机退出时，**社交元状态仍然存在**。

Web 端无法直接用 ENet → 切 `WebRTCMultiplayerPeer` 或 WebSocket。

## 2. ⚠ 房主不是"房间主人"

`owner_id`（可改设置的人）与 `host_endpoint`（负责战斗 RPC 的进程）
**是两回事，都要能更换**。

⚠ **把房主永久等同于创建者，会导致创建者退出后房间设置永远锁死。**

推荐迁移顺序：**创建者 → 副房主/队长 → 剩余最早加入者**。
用户主动退出时显式交接，断线时按心跳超时交接。

## 3. 匹配

⚠ Godot **不提供匹配服务**，需自建或接第三方。
匹配维度：MMR、地区、延迟、模式。⚠ 要有等待与超时处理。

## 4. 聊天是合规重灾区

- 频道划分（世界/队伍/私聊/系统）
- ⚠ **客户端过滤是不够的**（改包就能绕过），**必须服务器过滤**
- ⚠ **聊天内容要留存**配合举报取证
- ⚠ UGC 风险：玩家名、公会名、头像都要过审

⚠ 中国监管要求平台建立跟帖评论审核、实时巡查、举报和记录保存制度，
但**未给出游戏私聊的统一保存天数** —— 实际期限由运营与法务按最小必要原则制定（**待核对**）。

## 5. 举报与审核

⚠ **举报必须能定位到具体内容** —— 要存**证据快照**，不能只存"某人被举报了"。

> **反模式清单（不能怎么做，审核用）** → `audit/godot/social.md`


## 6. ⚠ 阵营 / 势力 / 声望 / 战力 / 战报

> 扫描确认 `阵营 / 势力 / 声望 / 荣誉 / 战力 / 战报 / 师徒 / 婚姻 / 结拜 / 聊天频道`
> 此前**全部 0 命中**。
>
> ⚠ **这套系统的核心不是"多几张表"，而是把「关系状态」与「战斗结果」拆成
> 两个边界清晰、服务端权威的域。**

| 层 | 数据 | 更新频率 | 谁可写 | 典型误用 |
|---|---|---:|---|---|
| **关系事实** | 主阵营、声望、关系、冷却 | 低 | 服务端事务 | ⛔ 客户端提交关系成功 |
| **规则** | 关系矩阵、解锁、衰减 | 配置 | 运维/热更 | ⛔ 热更后旧战报直接重算 |
| **派生指标** | 战力、活跃、排名 | 中 | 服务端重算 | ⛔ 客户端算并上传总分 |
| **事件** | 战斗 / 关系事件 | 高 | 房间与结算服务 | ⛔ 用最终快照冒充完整回放 |

⚠ **四层混写是绝大多数后期灾难的起点**：客户端为显示方便直接改总分、
服务端为性能缓存关系、战报为还原结果又存了最终状态，最后三者互相矛盾。

### 6.1 阵营关系是有向图，不是角色表上的一个枚举

⚠ **一个玩家可同时属于多个组织，但同一语义层级必须只有一个"作战身份"。**

| 字段 | 用途 |
|---|---|
| `main_faction_id` | PvP、占领、赛季积分 |
| `memberships` | 公会、国家、职业组织、剧情派系（可多个） |
| `temporary_affiliations` | 剧情临时效忠、租借、俘虏（**必须有过期时间**） |

⚠ 混成一个"阵营"会出现"剧情让我叛变但 PvP 仍算原阵营"的矛盾。
主阵营决定 **PvP 身份**，剧情阵营只触发任务条件，
⛔ 临时身份不得绕过 PvP 身份校验。

⚠ **阵营关系必须是非对称的：A 对 B 友好 ≠ B 对 A 友好。**
存 `faction_relation(from, to, relation, valid_from, valid_to, rule_version)`。
⛔ **不要把有向行自动镜像**。查询时先找有向边，找不到再取阵营默认关系。

⚠ **"同阵营不能互相攻击"只是战斗规则，不是数据库唯一约束。**
公会战、演习、混战可能允许友伤，剧情背叛可能临时允许。
⛔ 直接写 `if a.faction == b.faction: return false`，
后续每种例外都会变成在战斗层打补丁。
✅ 用房间级 `PvpContext`，**服务端开房时冻结**阵营关系、友伤、占领规则与配置版本，
⚠ **战斗中的切换请求不能回溯修改已冻结的上下文**。

⚠ **势力不能只存"人数"，要存可作战人口**：
`member_count / active_7d / match_ready_count / current_online / war_commitment / power_band_estimate`。
人数多但上线少、胜率高但从不守点的势力会被误判为强势。
⚠ 势力积分要分**控制分、战斗分、贡献分**，避免单一排名制造虚假失衡。

### 6.2 阵营切换必须付出时间、关系和经济三重代价

⚠ **主要风险不是数值损失，是身份套利**：开战前转入防守方领奖、战后转回优势方；
用同一角色跨阵营搬运情报；退出后立即加入敌对势力刷新任务；复制关系拿双边解锁。

✅ 切换是一次**不可撤销的事务**：加锁 → 校验冷却与未决绑定 →
更新主阵营 → **清理旧阵营专属状态** → 算惩罚 → 写冷却 → 发事件。

⚠ 清理时要**保留**永久剧情标记与已购外观，⚠ **清除** vendor 解锁、日常占领标记、待领奖励。
最低限度要有：切换冷却 · 赛季切换次数上限 · 退出时未领奖励作废 ·
声望衰减或转换 · 阵营 Buff 清除 · 已报名阵营战退出 · **师徒/婚姻/结拜在切换期间挂起**。

⚠ "一次免费转阵营"不是免费，只是把代价从经济资源移到冷却、切换窗口或新阵营审批。

### 6.3 GVG 的基本单位是有生命周期的战役实例，不是房间

```
CampaignSeason → Campaign → Battle → Objective → CapturePoint → GuildAssignment
```

⚠ **不要把据点控制权写进角色表**，也不要把当前控制者当作永久历史。
据点用"占进度 + 抗衰减"：进入区域增分，离开或敌方干扰时**按服务端时钟衰减**，
达阈值才设控制权。写 `CapturedBy / CapturedAt / LastContestedAt / ControlVersion`，
⚠ 避免客户端预测时产生瞬时反复横跳。

⚠ **赛季结束必须保存冻结快照，并用该赛季的配置版本生成最终奖励**，
⛔ 不能拿下一赛季的新平衡参数重新解释旧战役。

### 6.4 阵营平衡：奖励要补偿"参与解决失衡的人"

⚠ **"人多的一方奖励更多"会变成正反馈**：人多 → 更活跃 → 奖励更多 →
观望玩家转入 → 优势方继续扩张；弱势方奖励更少还承受更多失败 → 继续流失。

✅ 动态奖励应优先补偿**对弱势方目标有直接贡献的行为**：守点、反攻、护送、资源运输、新人组队。
⛔ 不要简单按阵营身份给全阵营 Buff；若必须给，要限定持续时间并同时观察转阵营率。

干预顺序（由弱到强）：提示推荐弱势方 → 限时双倍贡献/专属任务/匹配优先 →
按可作战人口平衡报名 → **最后才限制自由切换**。
⚠ 所有干预必须向玩家解释"补偿什么、持续多久、依据哪个赛季"，否则像黑箱操纵。

⚠ 平衡数据按 15–60 秒采样并保存 5 分钟 / 1 小时 / 24 小时三个平滑窗口，
⛔ 每分钟读全量会压垮数据库。

### 6.5 声望：连续值负责策略，分档负责体验

⚠ **声望必须能掉，否则只是一根上涨的线。**
要同时支持衰减、负值（恶名 / 通缉）与解除锁定。
⚠ **衰减不能惩罚活跃玩家** —— 衰减应从"上次获得后"计时，
且活跃行为要能抵消衰减，否则老玩家被系统惩罚、新玩家追不上。

⚠ 连续值与分档**不能互相替代**：连续值给策略（差 30 点能不能买），
分档给体验（"崇敬"是个可读的身份）。

### 6.6 战力：总分只负责直觉，匹配必须另建技能估计

⚠ **战力测的是配置和养成，不是操作。** 四个具体陷阱：
① 高分低操作玩家污染队伍 ② 跨职业排序无意义（坦克生存高输出低）
③ 玩家为总分牺牲真正有用的属性 → **堆无用词条** ④ 装备版本变化让旧号集体虚高。

✅ 展示优先级：**分维度雷达/条形 + 职业百分位 + 装备建议 + 总分**，
⛔ 不是只显示一个大数字。
⚠ 总分由**服务端计算并缓存**，⛔ 客户端不得上传；
缓存键含角色/装备/属性/**公式**版本，任一项变化必须失效。

⚠ **战力只适合新手推荐、装备成长、排行榜展示。**
真正匹配用独立 MMR/Elo/Glicko + 近期表现 + 角色熟练度 + 位置 + 延迟，
战力最多作为 `role_fit` 或解释性展示，⛔ **不进主匹配分**。

⚠ 虚高用"有效属性白名单 + 场景惩罚 + 实测回归"处理：
词条映射到实际伤害/有效生命/增益覆盖/实战贡献；重复属性边际递减；
**对当前职业完全无效的属性不得进总分**。
⚠ 公式版本必须随战报保存，否则玩家会质疑旧战绩。

### 6.7 战报：保存能重建事实的最小事件集，不保存每个像素

```
最稳组合 = 初始状态哈希 + 固定步长输入序列 + 确定性随机种子 + 配置版本 + 关键事件摘要
```

| 存法 | 优点 | 缺点 |
|---|---|---|
| 输入序列 | 最小、可完整重放 | 必须完全确定性重放 |
| 状态快照 | 易定位、可快进 | 体积大，不能证明中间结果 |
| 事件日志 | 适合结算与审计 | 不能高保真回放过程 |

⚠ **确定性不是把 `float` 换成 `double` 就够。** IEEE 754 规定基本运算结果，
但**不保证跨编译器、优化选项、平台、CPU 扩展精度、数学库、线程调度和物理求解器一致**。
浮点累积顺序、三角函数、碰撞迭代次数、哈希容器遍历、异步加载都可能发散。
⚠ **Godot 默认物理、节点顺序和平台差异不应被假定为跨平台确定**（待核实）。

必须冻结：固定逻辑步长 / 物理步长 / 最大步长与子步策略 ·
单一授权随机源及每次随机调用的序号 · 无平台或硬件条件分支 ·
确定性容器与排序 · 碰撞回调顺序 · 技能计时器 · 初始种子。
⛔ 不要用系统时钟、对象 ID、字典遍历、GUI 时间或浮点误差做游戏逻辑；
⛔ `is_close` 要换成确定性容差或整数定点；
⛔ 视觉抖动、粒子、镜头、音效不得参与逻辑。

⚠ **版本兼容要在写入时隔离，不是读取时"尽力兼容"。**
回放头保存 `engine_build / data_version / balance_version / rule_set_id`，
旧回放用旧快照重放。ⓘ 商业产品也明确限定回放只能按当前实装版本观看——
**跨版本不兼容是真实产品约束，不是实现偷懒**。

### 6.8 战报隐私：默认最小展示

⚠ **"战绩本来就是公开的"不能成为默认逻辑。**
PIPL 要求处理个人信息合法正当必要诚信、限于最小范围；
除取得单独同意外不得公开处理的个人信息；
**不满十四周岁未成年人的个人信息属敏感个人信息**。

战报至少分五档：`SELF / PARTY / FACTION_OFFICER / WAR_REPORT / PUBLIC_LEADERBOARD`。

| 默认公开 | 默认隐藏 |
|---|---|
| 角色名/化名、赛季、阵营、分数、时间戳、非精确地图 | 真实姓名、精确对局时间、IP、设备、好友列表、聊天、位置、未成年人标识、可反查账号 |

⚠ 精确对局时间可能结合其他数据形成**行踪**；
⚠ 不建议公开原始输入序列。
⚠ 分享前做脱敏投影，服务端保留一份**可验证但不可公开**的证据。
⚠ 用户应能在隐私设置里关闭公开，除法规或平台要求外**关闭不应影响核心匹配**。
⚠ 团队规模小、无法建立删除请求与导出机制时，⛔ **不应做跨服战绩榜**。

### 6.9 关系型社交（师徒 / 结拜 / 婚姻）

⚠ **本质是"绑定 + 共享收益 + 解除代价"，三者缺一不可。**

⚠ **解除必须冷却**，否则可以反复建立/解除来刷奖励。
⚠ **关系加成要有硬上限**，否则叠满所有关系会破坏数值。
⚠ 批量解除要限流。

⚠ **合规重点是未成年人、诱导与权力不对称**：
避免诱导加好友、诱导充值绑定、定位式社交、跨代际私聊。
（详见 `compliance.md`）

### 6.10 聊天频道：频道、成员资格、扇出三者分离

⚠ **不要把成员列表塞进频道对象**，热点频道会拖垮战斗服。
扇出要单独限流（见 `backend-stability.md` 的单会话消息维度）。

⚠ 世界频道的刷屏要用**发言道具 / 冷却**控制（经济手段），
⛔ 不是只靠限流（技术手段）—— 限流会误伤正常玩家。
