# 时间推进系统：离线结算 / 生产队列 / 体力 / 周期重置（Godot 4.7.2）

**此前「建造 / 生产队列 / 挂机离线收益 / 体力恢复 / 领地家园」几乎全部 0 命中。**

> 经济与养成见 `economy.md`；运营活动时间见 `ops.md`；
> 合规的时间口径见 `compliance.md`；存档见 `io-network.md`。
>
> ⚠ **与 `genres-idle-sim.md` 的分工**：那篇是**放置/模拟经营品类**（TickEngine、建筑放置、每建筑 \_process 性能）。
> 本篇是**跨品类的时间推进内核**——体力恢复、建造/生产队列、每日与赛季重置，
> 这些在非放置游戏（RPG、策略、竞技）里同样存在。品类视角看前者，结算内核看本篇。

**这类系统表面完全不同**（建造队列要知道"第几个完工"，体力要知道"什么时候回满一格"，
挂机要知道"累计产出多少"），但⚠ **技术内核只有一个：用一个不可伪造的绝对时间戳做锚，
把「上次结算时刻」到「本次结算时刻」的流逝换算成状态增量。**

> 审核用反模式清单见 `audit/godot/time-progression.md`

## 0. 一句话模型

```
elapsed = clamp(now - last_settled_at, 0, CAP)   # 锚点差，封顶
cycles  = elapsed / tick_ms                       # 整型除法
产出    = cycles * output_per_cycle
锚点    = last_settled_at + cycles * tick_ms      # ⚠ 只推进"已完整结算"的部分
```

⚠ **锚点只推进已完整结算的部分，余数留在区间里。** 这一句是全篇最关键的。

## 1. 三种时间源，用错层级是万恶之源

| 时间源 | 会跳变吗 | 适合 | 严禁 |
|---|---|---|---|
| 服务器 UTC 时间戳 | **会**（改表、NTP、时区、夏令时） | 存档锚点、每日/赛季重置边界 | 帧间 delta、短间隔测量 |
| `Time.get_ticks_msec()` | **不会**（官方保证单调） | 帧间 delta、性能打点、本地倒计时预测 | **存档**（进程重启归零）、跨设备 |
| `get_datetime_dict_from_system()` | 会 | UI 显示、把服务器时刻换算成本地几点 | 任何数值结算 |

⚠ **Godot 官方文档原话**：`_from_system` 方法使用用户可手动设置的系统时钟，
**永远不要用于精确时间计算**；精确计算用 `get_ticks_usec` / `get_ticks_msec`（保证单调）。

⚠ 这里的"精确"应读作"**可重复、可差分**"：单次读取可能完全正确，
但**两次读取的差**不可信。

⚠ **`get_unix_time_from_system()` 返回 float**，`int(x * 1000.0)` 在数值大时有浮点尾误差。
→ **落库与计费必须用服务端的 int64 毫秒**，客户端预测差几毫秒无所谓。

### 客户端怎么拿到可信时间

登录时服务端下发 `server_time_utc_ms`，客户端算一次偏移：

```gdscript
var _mono_offset := 0
func on_server_time(server_utc_ms: int) -> void:
    _mono_offset = server_utc_ms - Time.get_ticks_msec()

func now_utc_ms() -> int:
    return _mono_offset + Time.get_ticks_msec()
```

⚠ **这个估计值只允许向前**：若小于已持久化的 `last_settled_at`（系统钟回拨、睡眠唤醒漂移），
**钳制到 `last_settled_at`，绝不结算负值。**

## 2. 存档存什么：绝对锚点，不是剩余秒数

```
✅ 正确
{ "last_settled_at_ms": 1726900000000,     # int64 UTC，唯一时间锚
  "started_at_ms": ..., "base_duration_ms": ...,
  "speed_timeline": [...],                  # 速率变更日志，不是"当前速率"
  "valid_through_ms": ..., "schema_version": 3 }

❌ 错误
{ "building_remaining_sec": 1234 }          # 被杀进程 / 加成变化 / 暂停后全失真
```

⚠ **剩余秒数是派生值。** 一旦暂停、加成变化、速率调整，它就失真；
绝对锚点加上"当时生效的速率"可以复算任意时刻的进度。

⚠ **`_process(delta)` 累加不会跨会话** —— 关机、杀进程、被挂起后 delta 就没了。
正确结构：在线时用 delta 做高频小幅更新（体验），**同时持久化绝对锚点**（保真）；
离线归来只用时间戳差做一次性结算，**不补模拟**。

## 3. 余数：三种安全处理，一种禁止

| 方式 | 长期偏差 | 评价 |
|---|---|---|
| **锚点回拨**（只推进已结算部分） | 无 | ✅ 首选，无需额外字段 |
| 余数累加器（**int64 定点**） | 无 | ✅ 可用，回档时字段要一起恢复 |
| `float` 累加器 | **长期漂移，对账失败** | ⛔ 禁止 |
| 直接 `floor` 并推进完整 elapsed | **系统性偏低**，且偏差与速率成反比 | ⛔ 禁止 |

⚠ **不写回余数** → 玩家的挂机收益长期低于设计值，且**速率越高丢得越多**，
数值调整后玩家感知会突变。
⚠ **反过来把零头四舍五入补成一次产出** → 玩家频繁进出场景就能反复触发向上取整，凭空产出。

## 4. 分段：离线期间的速率不能按"回来那一刻"倒推

⚠ **这是第二普遍的实现错误。** 玩家离线 8 小时，期间可能 VIP 到期、活动结束、
加成卡激活、建筑升级、赛季重置。此时 `R(t)` 不是常数，**不能整体乘一个速率**。

```
segments = build_segments(P, N, rate_timeline, cap_timeline, reset_timeline)
for seg in segments:
    cyc = seg.elapsed_ms / seg.tick_ms
    产出 += cyc * seg.output_per_cycle
    consumed += cyc * seg.tick_ms
    if seg.is_reset_boundary: apply_reset(seg.reset_kind)
```

⚠ **速率时间线是"按生效时间排序的事件日志"，不是"玩家当前的速率快照"。**
重建 `R(t)` 时从日志二分查找。

⚠ **重置是时间轴上的硬边界**，必须在边界处落库一次中间状态再进下一段。

## 5. 封顶：是留存节奏，不是功能缺陷

⚠ **不封顶的挂机等于奖励长时间离线** —— 玩家发现"挂三天比玩三小时划算"，
在线行为被瓦解。行业常见 **4–24 小时**，取值是产品决策。

| 封顶 | 玩家行为含义 |
|---|---|
| 2 小时 | 午饭前必须回来 |
| 8 小时 | 一天两次，符合上班节奏 |
| 24 小时 | 一天不上线无损 |

⚠ **三个数必须分开**：`max_offline_ms`（系统硬上限，防经济崩盘）·
`offline_cap_ms`（玩家当前生效上限，受 VIP/加成延展）· `catch_up_granted_ms`（补签解锁）。
`granted = clamp(实际离线 - cap, 0, 硬上限 - cap)`
→ 保证补签叠加加成也**不越过系统硬上限**，否则一次活动就能击穿经济。

⚠ **速率加成与上限加成是两个字段**：`rate_multiplier`（产出 +50%）
和 `cap_extension_ms`（挂机时长 +4 小时）语义不同，塞进同一个 multiplier 会出现
"买了时长加成结果速率也变高"的配置错乱。

⚠ **封顶后产出停止，不产生"欠账"**。维护期间把维护起止作为时间线事件，
区间内跳过结算、结束后从维护开始时刻重算——玩家不亏也不赚。

## 6. 生产 / 建造队列

⚠ **槽位并行规则必须配置化，不能硬编码**：严格串行 / 有限并行（K 槽）/ 全局共享池。

⚠ **加速（立即完成）计费必须服务端**：客户端 `remaining * price` 是典型计费漏洞。
- 剩余时长要在服务端用**当时生效的速率**重算（客户端缓存的"还剩 3 分钟"可能因加成变动失准）
- **扣款与产出落库必须原子化**，否则"扣了钱没完成"或"产出了没扣钱"
- ⚠ **立即完成本质是一次"结算到 now"，应复用同一套结算管线**，另写路径必然在
  分段/封顶/重置边界上出现行为分叉

⚠ **红点判定要实时查询**（是否存在 `started_at + duration <= now` 的条目），
**不能靠"到达时刻推送通知"** —— 关机、杀进程、挂起都会漏通知。

⚠ **离线期间队列是否继续走是产品决策**，但**只要选"继续走"，完成判定就必须用绝对锚点**。

## 7. 体力：三个边界

```
stamina = { amount, last_settled_at_ms, restore_interval_ms, cap }
```

恢复公式与挂机产出**是同一个模型**（速率 = 1点/interval）：

```
cycles = elapsed / restore_interval_ms
amount = clamp(amount + cycles, 0, cap)
last_settled_at += cycles * restore_interval_ms   # 余数留在区间
```

⚠ **溢出额度绝不产生利息、绝不受加成放大、绝不跨重置累积。**

⚠ **购买体力能否超上限，必须在产品文档写死** —— 技术上没有自然答案。
若允许超上限，必须显式存 `hard_cap` 与 `bonus_pool`，否则玩家升到更高 cap 时
"超出旧上限的部分"无法被恢复系统识别。

⚠ **"每日购买次数"与"自然恢复"是两套独立时钟，绝不能共享一个 `last_settled_at`**
——否则买一次体力会顺带重置恢复时间戳，等于白赚一段恢复时间。

⚠ **升级导致 cap 增大时怎么处理**（只扩容器 / 补满 / 全额发放一次）
差异巨大，必须配置化且服务端执行。

## 8. 周期重置：硬边界，不是定时任务

⚠ **重置必须能在任意时刻被补算** —— 玩家断网三天后上线，要把这三天里
**每一个**重置边界都跑一遍，而不是"只在 05:00 发一次事件"。

⚠ **重置时间点用服务器时区定义**（推荐 UTC 整点），不用玩家时区。
- 玩家跨时区旅行后，"本地午夜重置"会让他的"一天"变长或变短
- 夏令时切换那天，本地 02:00 会消失一次或重复一次，基于本地日期字符串的重置表会**跳过或重复触发**
- UTC 不实行夏令时，边界恒定

⚠ **重置时正在进行的队列**要逐类约定：建造/生产队列**跨重置继续推进**；
每日任务清 0 并发放未领奖励；赛季排行结算后清空。

⚠ **最危险组合是"重置清 0 + 用剩余秒数存档"** —— 队列在重置边界附近被杀进程，
恢复时既不知道该被清掉也不知道该继续。
解法：给条目加 `valid_through_ms` 字段，把**生命周期与进度解耦**。

⚠ **周期标识由服务端算好下发**（`current_daily_cycle_id` 等）。
客户端自己算周期会因时区偏差制造"我已领过 / 我还没领过"的冲突。

## 9. Godot 侧：挂起回调只做持久化

⚠ **`NOTIFICATION_APPLICATION_PAUSED` 是"最后一次机会持久化"，不是计时器。**
官方：Android/iOS 上挂起的应用随时可能被杀死，iOS 上你只有约 **5 秒**完成该信号启动的任务，
超时会被**杀死而非挂起**。

所以 PAUSED 里：✅ 写 `last_settled_at` 与状态到持久化 ·
⛔ 不做网络请求（挂起后不可靠）· ⛔ 不跑大批量结算（会超时）·
⛔ **不要在 PAUSED 里结算**（网络不可用，结果无法上链，且挂起期间时间无法被诚实测量）

`RESUMED` 的职责：校准本地单调偏移 → 触发一次完整离线结算 → 刷新倒计时显示。

⚠ **`FOCUS_OUT` ≠ `PAUSED`** —— 切桌面、第三方弹窗触发 FOCUS_OUT 但未必挂起。
持久化挂在 FOCUS_OUT 会导致高频 I/O 与重复结算。

⚠ **`SceneTree.paused` 停掉 `_process`，但单调钟不停。**
`SceneTreeTimer.create_timer` 受场景树暂停影响、`Engine.time_scale` 影响帧间 delta
→ **两者都只能用于视觉与玩法表现，绝不能用于存档时间轴。**
