# 存档迁移（Godot 4.7.2）

⚠ **这与"云存档/冲突"是两回事** ——
迁移是"**存档格式变了怎么办**"，云存档是"多设备之间怎么同步"（见 `cloud-save.md`）。

## 0. 格式必然要变

新增字段、改字段类型、删除字段、扩展枚举、重排数组都会发生。
**真正的问题不是"要不要迁移"，而是能否从旧存档无损到达当前格式。**

⚠ **`VERSION` 字段要从第一天就写进去** ——
第一天没写格式版本，日后就只能**猜**，而猜错的代价是**玩家进度消失**。

### 三个"版本"要分开

⚠ **存档格式版本 ≠ 游戏版本号 ≠ 构建号** —— 三者常被混为一谈。

存档格式版本应设计为**单调递增整数**，与另外两者完全分开。

### 版本字段的位置

必须位于**所有迁移逻辑都能读到的稳定位置**：

| 格式 | 放哪 |
|---|---|
| JSON | 顶层 `schema_version` |
| ConfigFile | 固定节（如 `[meta]` 下的 `schema_version`） |
| 自定义二进制 | **解密后**、可预测的头部 |

⚠ 不要埋在实体子结构里，也不要依赖不同节的读取顺序。

⚠ **加密存档必须先解密才能读到版本号** ——
所以版本号只能放在**解密边界内**，不能依赖密文之外的位置。
⚠ **加密元数据不能替代自己的版本字段。**

## 1. 三种失败必须区分

| 类型 | 表现 | 处理 |
|---|---|---|
| **损坏** | 无法解密 / HMAC 失败 / JSON 断裂 / 关键字段缺失 | 备份恢复，或用户可见的"存档损坏" |
| **降级** | 旧程序读新存档 | **明确拒绝或提示升级**，不能默默覆盖 |
| **未知未来版本** | 版本高于当前 | **拒绝**，不要硬塞进迁移链 |

⚠ 区分开的意义：日志才能准确回答"是文件坏了、程序旧了，还是迁移写错了"。

⚠ **降级尤其危险**：`ConfigFile.get_value` 对缺失键**返回默认值**，
旧程序遇到未知字段**往往不报错**，却把新状态**静默填成默认值**。

## 2. 迁移的执行

```
备份 → 逐级迁移 → 校验 → 重算 HMAC → 原子替换
```

⚠ **迁移前必须备份** —— 迁移是**不可逆操作**，失败即丢失玩家进度。

⚠ **迁移后必须重算 HMAC/校验值** ——
否则**旧签名会给新数据披上"已验签"的假象**。

**写盘**：先落临时文件，校验并备份后再**原子替换**（写一半崩会损坏存档）。

**逐级迁移 vs 一次性迁移**：逐级更好维护，但要保证链条完整。

## 3. 字段级兼容

| 变更 | 注意 |
|---|---|
| 新增字段 | 默认值从哪来（不能依赖"缺失即 0"） |
| 删除字段 | 旧数据要不要留（回滚需要） |
| 类型变更 | int → float 等，要显式转换 |
| ⚠ 枚举扩展 | 旧存档存的是数字，新增项**会不会错位** |
| 嵌套/数组 | 重排与长度变化 |

（详见 `cloud-save.md`，此处只讲边界）
- 要先定**迁移与冲突的先后顺序**
- ⚠ **多设备可能处于不同版本** —— 同步过来的可能是旧格式

⚠ **要保留各版本的历史存档样本**做回归测试 ——
没有历史样本，迁移代码等于没验证过。

## 6. 迁移链怎么写（可照做的结构）

⚠ **迁移不是"一个大函数按版本 switch"，是一条链。**
大 switch 的问题：版本一多就变成几百行的分支体，
且**无法单独测试"从 3 到 4"这一步**。

```gdscript
# 每个迁移是一个纯函数：只吃旧结构，吐新结构
static func m3_to_4(d: Dictionary) -> Dictionary:
    d["stamina"] = d.get("stamina", 100)     # ⚠ 显式默认值
    return d

const CHAIN := [
    null,           # 索引 = 源版本，0 不用
    null,
    callable(m2_to_3),
    callable(m3_to_4),
]

static func migrate(data: Dictionary, from: int, to: int) -> Dictionary:
    var v := from
    while v < to:
        data = CHAIN[v].call(data)
        v += 1
    data["schema_version"] = to
    return data
```

ⓘ 三个好处：
- 每一步可**单独测试**（喂一个 v3 的字典，检查输出）
- 链条有缺口时**立刻暴露**（`CHAIN[v]` 为 null 会报错，⛔ 不是静默跳过）
- 新版本只需**追加**，⛔ 不改已有函数

⚠ **逐级迁移的代价是老存档要跑很多步** ——
版本极多时可加"快照版本"（如每 10 版一个直达函数），
但 ⛔ 直达函数与逐级链必须**结果一致**，要有对拍测试。

## 7. 删字段是四个阶段，不是一个动作

⚠ "删除字段"最常见的错误是**一次性删干净**，
后果是"回滚到旧版本时旧程序读不到数据"。

| 阶段 | 做什么 | 何时 |
|---|---|---|
| ① 停用 | 不再**写入**新值，仍**读取**兼容 | 决定删除时 |
| ② 保留 | 读写都在，但标记为 deprecated | 至少跨一个发布周期 |
| ③ 只留不读 | 序列化时仍写出，代码不再读 | 确认无回滚需求 |
| ④ 移除 | 从结构里删除 | ⚠ 需要"最后支持版本"已过期 |

ⓘ 判据：**能回滚到的最旧版本仍需能读，就不能进阶段 ④。**

## 8. ⚠ 迁移失败必须用户可见

⚠ **迁移失败静默回落到"新档"，等于删除玩家全部进度。**
这是存档系统里最严重的一类事故——不崩溃、不报错，只是进度没了。

✅ 正确流程：

```text
迁移失败
  → 保留原始文件（⛔ 不覆盖、不删除）
  → 尝试从迁移前备份恢复
  → 恢复成功：提示"已回退到上次存档"
  → 恢复失败：明确告知"存档损坏"，并提供"联系客服/导出诊断包"
```

⚠ **绝不能把损坏的存档当成空档重新开局** ——
玩家会以为是自己忘了存，而实际是数据丢失。

⚠ 还要区分**"存档损坏"**与**"存档过新"**：
后者应提示"请更新游戏"，⛔ 不是"存档损坏"。

## 9. 历史样本库怎么建

⚠ 第 5 节说"要保留历史存档样本"，这里给具体做法。

⚠ **没有样本库，迁移代码就是没测过的代码。**
而它一旦出错是**不可逆的玩家资产损失**。

```text
tests/fixtures/saves/
  v1_minimal.json        # 最简：刚开局就存
  v1_full.json           # 最全：所有系统都用过
  v1_edge.json           # 边界：空背包、满背包、极端数值
  v2_*.json
  ...
```

ⓘ 三种必备：**最简 / 最全 / 边界**。
⛔ 只有"正常玩下来"的样本，会漏掉空容器、零值、极限值这些最容易炸的输入。

⚠ **样本要在格式定稿的那一刻就生成并入库**，⛔ 不能事后补造。
事后补造的样本是"按当前代码猜出来的"，验证不了真实历史数据。

✅ 每次加迁移函数，CI 里跑一遍全样本：
`for 样本 in 全部: migrate(样本) 不得抛错 且 结果通过校验`

## 10. 迁移要可观测

⚠ **线上迁移失败如果只在玩家本地发生，你永远不会知道。**
症状是"玩家默默流失"，后台看不出任何异常。

ⓘ 至少上报这些（在用户同意与隐私政策范围内）：

| 字段 | 用途 |
|---|---|
| 源版本 → 目标版本 | 知道玩家卡在哪些版本 |
| 成功 / 失败 / 失败类型 | 区分损坏、降级、未知版本 |
| 是否走了备份恢复 | 衡量事故严重度 |
| ⚠ **不含存档内容** | ⛔ 存档含个人信息，不能上报 |

⚠ **不要上报存档文件本身** —— 存档可能含昵称、位置、聊天记录等个人信息。

ⓘ 有了这个数据才能回答"这次改格式影响了多少玩家"。
