# 转职 / 觉醒系统（Godot 4.7.2）

ⓘ **"转职""觉醒""职业进阶"在全部 howto 里此前 0 命中** —— 本篇是新建域。
⛔ 但它**不是**孤立的：它与 `economy.md`（天赋树、装备养成）、`build-affix.md`
（词条）、`save-migration`（存档）有强接缝，本篇只写本域特有的部分。

---

## 0. 先分清三件事：转职、觉醒、多职业

ⓘ 这三个词常被混用，但它们的**数据模型完全不同**。先定是哪一个，
否则做到一半会发现结构撑不住。

| | 语义 | 状态 | 典型 |
|---|---|---|---|
| **转职** | 替换职业 | 单职业持有，旧职业消失 | 战士→骑士 |
| **觉醒** | 在原职业上追加 | 原职业保留 + 觉醒层 | 战士→狂战士 |
| **多职业** | 同时持有多个 | N 套职业状态并存，可切换 | 骑士/法师双修 |

⚠ **判据**：转职后玩家还能不能变回原职业、原职业的技能还在不在。
- 不能 → 转职
- 在，且被增强 → 觉醒
- 两套独立 → 多职业

⛔ **最贵的错误**：用"转职"的数据模型去做"多职业"。
单职业模型只能存一份状态，做到切换功能时才发现要存 N 份 —— 那时
存档格式、UI、技能系统全都按单份写完了，改动面是**全系统级**的。

## 1. 职业是模板，玩家职业状态是实例

ⓘ 与 `economy.md` 的 `EquipmentBase / EquipmentInstance` **同构**，
不要另发明一套。

```gdscript
# 模板：不可变，配表导入
class_name ClassTemplate extends Resource
@export var class_id: StringName
@export var display_name: String
@export var prev_class: StringName        # 前置职业（转职链）
@export var next_classes: Array[StringName]
@export var growth: Dictionary           # 属性成长系数（每级）
@export var skill_ids: Array[StringName] # 本职业可用技能
@export var equip_types: Array[StringName]  # 可穿戴装备类型
@export var awake_only: bool             # 是否只能由觉醒获得

# 实例：玩家当前状态，进存档
class_name ClassState extends Resource
@export var class_id: StringName
@export var level: int
@export var exp: int
@export var awake_level: int = 0         # 觉醒层数
@export var history: Array[StringName]   # 转职历史（不可删）
```

⚠ **`history` 必须只增不删。** 它是排查"这个玩家为什么有这个技能"的
唯一依据。删了之后客服面对申诉只能靠猜。

⚠ **成长系数存"每级增量"而不是"满级终值"。** 存终值的话，改了等级
上限就要改所有职业的整张表，而且**看不出中间等级怎么长**。

## 2. 转职是事务：三个动作的顺序不能错

转职涉及三件事：**扣消耗**（道具/货币/任务完成）、**改职业**、**重置派生状态**
（技能点、天赋、装备适配）。

⛔ **两个直觉顺序都会丢东西**：

| 顺序 | 失败时的后果 |
|---|---|
| 先扣消耗 → 再转职 | 扣了没转成，**玩家资产凭空消失** |
| 先转职 → 再扣消耗 | 转了没扣成，**白嫖**（且难以追回） |

✅ 正确顺序是**试算 → 扣费 → 提交 → 失败则整体回滚**：

```gdscript
func try_change_class(p, target_id) -> Dictionary:
    # ① 试算：不产生任何副作用，只回答"能不能、会变成什么样"
    if not _meets_requirement(p, target_id):
        return {"ok": false, "reason": "未满足转职条件"}
    var preview = _simulate(p, target_id)     # 纯函数，返回变更清单
    if not _cost_affordable(p, target_id):
        return {"ok": false, "reason": "消耗不足"}

    # ② 扣费：唯一有外部副作用的一步
    var tx = _begin_cost(p, target_id)

    # ③ 提交：改职业 + 重置派生状态
    var before = p.class_state.duplicate(true)
    if not _apply(p, preview):
        _rollback_cost(tx)                   # ④ 回滚
        p.class_state = before
        return {"ok": false, "reason": "应用失败，已回滚"}
    _commit_cost(tx)
    return {"ok": true, "preview": preview}
```

⚠ **`preview` 必须能直接给 UI 展示。** 玩家点转职前要看到"转完之后
技能变这样、属性变这样、这些装备会失效"。⛔ 没有预览的话，"转职后
发现装备全穿不上"会变成**差评和客服工单**，而不是一个 bug。

ⓘ 试算与实际提交**必须走同一个函数**，只是提交多一步写回。
⛔ 预览算一遍、提交再算一遍，两边漂移是这类系统的经典 bug ——
表现为"预览说能穿，转完穿不上"。

## 3. 转职后的装备兼容：最伤玩家的一环

⚠ **转职后原装备穿不上 = 玩家瞬间裸装。** 这是转职系统**最高频的
严重体验事故**：不崩溃、不报错，只是战斗力断崖式下跌。

三种解法，必须**明示选了哪一种**：

| 方案 | 做法 | 代价 |
|---|---|---|
| 装备通用 | 装备不绑职业 | 职业差异感弱 |
| 转职保留（降级） | 旧装备保留但属性打折/禁用特效 | 要写降级规则 |
| 提供过渡装 | 转职即赠一套可用装备 | 经济系统被绕过 |

⛔ **不要"静默卸下"**。玩家看到装备栏空了却不知道为什么，会认为
是 bug 或丢装备。

⚠ 装备兼容判定要**在试算阶段就跑完**，把"哪些会失效"列进 preview。
判定只看 `equip_types`，⛔ 不要在渲染/穿戴时才判 —— 那时已经晚了。

## 4. 属性重算：职业成长系数变了

ⓘ 属性计算**必须只有一个入口**，与 `economy.md` 第 2 节一致：

```
基础模板 → 等级缩放 → 职业成长 → 品阶 → 词条 → 强化 → 镶嵌 → 外部 buff
```

⚠ **转职改的是"职业成长"这一环**，但它会让**整条链的结果全变**。

⛔ 常见错误：转职时直接改 `attack` 这类最终值。
后果是下次重算（换装备、升级、进战斗）时，这次的修改被覆盖 ——
表现为"转职后攻击力变高了，打一场又变回去了"。

⚠ **缓存的面板属性必须在转职提交后立刻失效。**
⛔ 只改职业不刷缓存，UI 显示的还是旧职业的面板，玩家会以为没转成。

---

## 5. 技能与天赋：重置还是继承

⚠ **重置后不返还投入 = 玩家资产损失。** 技能点、天赋点通常是付费或
长线积累的，清零而不返还，与"删档"性质相同。

三种处理，同样要明示：

| 方案 | 适用 | 注意 |
|---|---|---|
| 全继承 | 觉醒（原职业还在） | 技能 ID 冲突要有映射表 |
| 全额返还 | 转职（新职业重置） | ⚠ 返还的是投入量，不是当前值 |
| 部分返还 | 有损耗的设计 | 损耗比例必须明示 |

ⓘ **"返还"要返还当时的投入量，不是当前剩余。**
⛔ 返还"剩余"（投入 - 已用）会让玩家先点满再转职来套利；
返还"投入"则配合重置是等价交换。

⚠ **跨职业技能 ID 必须有一张映射表**（旧技能 → 新技能）。
⛔ 没有映射表时，转职后旧技能既不能用也不显示，玩家看到技能栏
少了一半 —— 而且**无法恢复**，因为不知道原来是什么。

## 6. 不可逆性与后悔机制

⚠ **"转职不可逆"本身不是问题，"不可逆且没有确认"才是。**

必做的三层：

1. **预览**：转完什么样（见 §2）
2. **显式确认**：二次确认，且确认文案要包含**关键代价**（哪些装备失效、
   技能是否重置）
3. **后悔期**：限时内可撤销一次

ⓘ 后悔期的实现是**保存转职前快照**，不是"反向再转一次"。
⛔ 反向转职会**污染 `history`**，且不满足原职业的前置条件时会失败 ——
表现为"撤销失败，玩家被卡在新职业"。

⚠ 后悔期快照要**限制数量**（只存最近一次），否则存档无限增长。

## 7. 存档与迁移

ⓘ 职业状态进存档的三件套，与 `save-migration.md` 一致：
`class_state` + `history` + `version`。

⚠ **`class_id` 存 ID 不存引用。** 存 Resource 引用的话，改配表时
旧存档会指向已删除的职业 —— 表现为"读档后职业变成空"。

ⓘ 职业配表**只能增不能改 ID**。要调整就新增一个 ID，旧的标废弃。
与 `datatable.md` 的"删字段四阶段"同源。

⚠ **读到未知 `class_id` 时不能静默回落到默认职业。**
⛔ 那会让玩家的转职进度凭空消失，且没有报错。正确做法是保档 +
明确提示"职业数据异常，请联系客服"。

---

## 8. 服务端权威

⚠ 转职必须由服务端判定并广播，客户端**只发意图**。

⛔ 客户端判定的话，改内存就能白嫖高阶职业 —— 而且**没有任何日志**，
事后无法追查谁转了、什么时候转的。

ⓘ 与 `netsync-advanced.md` 一致：客户端发 `request_class_change(target_id)`，
服务端校验条件、扣费、提交、广播结果。**预览可以在客户端算，但
提交必须以服务端结果为准。**

⚠ **预览与服务端结果不一致时要以服务端为准并提示。**
⛔ 静默采用客户端预览，玩家会看到"预览能穿的装备，转完穿不上"。

---

## 9. 待核对项（运行时验证）

- ⚠ 待核对：后悔期时长（无统一值，按项目定）· 验证：定一个值后实测"转职→撤销→再转职"三次，确认 history 未被污染
- ⚠ 待核对：装备降级比例（若采用降级方案）· 验证：选 3 件跨职业装备实测降级后面板，确认不会出现负属性
- ⚠ 待核对：技能映射表覆盖率 · 验证：遍历全部职业对，确认每一条"旧→新"都有映射，无孤儿技能
- ⓘ 待核对：觉醒层数上限 · 验证：达到上限后确认 UI 不再显示觉醒入口，且服务端拒绝
