# Godot 4.x 宝石 / 符文（镶嵌系统）

> **适用**：装备有插槽、可镶嵌宝石/符文，或符文自成套组的项目。
> **不适用**：把属性直接写死在装备上的项目（那就只是数值表）。
> ⚠ 本域是 `economy.md` 装备四层的**子系统**：`economy` 讲"装备实例怎么长"，
> 本域讲"插在装备里的那一层怎么长"。两者是同一套模板/实例思想的两次应用。

## 0. 先分清三件事

⚠ **"宝石""符文""镶嵌"在中文项目里经常混用，但结构不同。**

| 说法 | 结构 | 关键差异 |
|---|---|---|
| **宝石** | 插进装备插槽，可拆 | 属于**装备实例**的一层 |
| **符文** | 自成一组（符文页/符文槽），可整套切换 | 属于**角色**而非某件装备 |
| **附魔** | 覆盖式，新的替换旧的 | ⛔ 不并存，所以没有"插槽数"概念 |

ⓘ 判据是**挂在谁身上**：宝石挂在装备上（换装备就没了），符文挂在角色上（换装备还在）。
⛔ 混用会导致"换了武器，符文组跟着没了"这类难以归因的 bug。

## 1. 宝石是 Resource，不是 Node

⚠ **宝石必须是 `Resource`，绝不能是 `Node`。**

⛔ 做成 Node 的后果：宝石要进背包、进存档、进网络包，而 Node 带
`_process` / 树路径 / 父子关系——序列化会带上整棵子树，
且 `Node` 不能被 `ResourceSaver` 直接存。

```gdscript
# ✅ 模板（配表，运行时只读）
class_name GemBase extends Resource
@export var gem_id: StringName
@export var tier: int                  # 宝石等级
@export var mods: Array[Dictionary]    # [{stat, value, op}]  op: add/mul
@export var socket_type: StringName    # 可插入的插槽类型

# ✅ 实例（进存档）
class_name GemInstance extends Resource
@export var gem_id: StringName
@export var instance_id: int
@export var tier: int                  # 实例自己的等级（可合成升过）
```

ⓘ 与 `economy.md` 的 `EquipmentBase / EquipmentInstance` **同构**。
⛔ 不要另发明第三套——做"宝石与装备联动"时要写两份适配。

## 2. 插槽：数量来自装备，类型来自配表

⚠ **插槽数是装备实例的属性，插槽类型由配表约束。**

⛔ 把插槽数做成全局常量（所有装备一样）会让"高级装备孔多"这条设计无法实现；
⛔ 把插槽类型也塞进实例，则配表改了旧装备不跟随——两边漂移。

```gdscript
class_name SocketSlot extends Resource
@export var index: int
@export var socket_type: StringName    # 红/蓝/黄… 或 "任意"
@export var gem_instance_id: int = -1  # -1 = 空
```

ⓘ **`socket_type` 的匹配规则要写死在一处**。
⚠ 常见坑：装备说"红槽"、宝石说"可插红槽"，两边字符串不一致 → 永远插不进去，
而且**没有报错**（只是列表为空）。

**判据**：⚠ 全项目搜索 `socket_type` 的赋值处，只允许**配表导入**与**实例反序列化**两处。

## 3. 镶嵌是事务：顺序不能错

⚠ **与转职同源：先扣后插 或 先插后扣，都会丢资产。**

```
① 校验（纯判断，无副作用）
   ├ 插槽存在且为空 / 或允许覆盖
   ├ socket_type 匹配
   ├ 宝石未被绑定给他人
   └ 未超过该装备的镶嵌上限
② 试算：产出变更清单（属性变化预览）
③ 扣费（唯一外部副作用：消耗宝石、扣金币）
④ 提交：写 EquipmentInstance.sockets
⑤ 失败 → 回滚 ② 的清单、退还 ③ 的消耗
```

⛔ **绝不能"先删宝石再插新的"**——中间态失败则宝石**凭空消失**。
覆盖镶嵌必须是**一次原子替换**：算出新数组 → 校验 → 整体写回。

ⓘ 与 `inventory.md` 的移动事务是同一套：试算 → 提交，零脏数据。

## 4. 拆卸与损耗

⚠ **拆卸要不要损耗，是经济系统的决策，不是技术细节。**

| 方案 | 后果 |
|---|---|
| 免费无损 | 宝石可无限复用 → 一套宝石全服通用，养成深度消失 |
| 付费无损 | 可控，但要给明确价格 |
| 有损耗（降级/销毁） | 养成压力最大，⛔ 必须**明示概率或明示规则** |

⚠ **损耗必须在 UI 上明示**。⛔ 不明示的话，玩家拆出一颗降级宝石会认为是 bug，
且这类投诉**无法自证清白**（没有日志能证明"这是设计如此"）。

**判据**：⚠ 拆卸确认弹窗里能直接读到损耗规则。

## 5. 合成：等级与数量

⚠ **合成要防"合成后又可拆回"的套利环。**

若 `3 颗 Lv1 → 1 颗 Lv2`，且 `1 颗 Lv2 → 3 颗 Lv1` 无损，
则合成/拆卸可以无限刷（若存在任何与等级相关的任务/成就）。

⛔ 更隐蔽的是**非整数比**：`5 颗 → 1 颗` 而拆卸返回 `3 颗`，
玩家会以"材料变少了"为由投诉，而这其实是设计——**必须写进文案**。

ⓘ 合成成功率若非 100%：
⚠ **失败时材料必须明确去向**（全损 / 保留 / 返还部分），
⛔ "没说"会按全损处理，玩家认为被吞。

## 6. 套装与共鸣

⚠ **"全身镶满红宝石触发额外效果"这类规则，判定要看装备槽位，不是看数量。**

⛔ 只数"红宝石数量"的话，玩家把 6 颗红宝石全插在一把武器上也会触发——
而设计意图通常是"分布在多件装备上"。

**判据**：⚠ 套装判定按 `(装备槽位, 宝石类型)` 的去重集合算，不是按总数。

⚠ 还有一类是**相邻插槽共鸣**（插槽连成特定形状）。
它的判定必须在**装备定义里存邻接表**，⛔ 不能靠 index 加减推导
（`index+1` 在换装备后指向的插槽形状完全不同）。

## 7. 属性并入统一管线

⛔ **宝石属性绝不能单独累加到最终面板。**

```
基础模板 → 等级缩放 → 品阶缩放 → 词条 → 强化 → 镶嵌 → 外部 buff
                                              ↑
                                          宝石在这里
```

⚠ 镶嵌是**管线中的一环**，不是管线之后的补丁。
⛔ 在管线外直接 `attack += gem.attack` → 下次重算被覆盖，
表现为"刚镶上变强了，打一场又变回去"。

**判据**：⚠ 卸下宝石后调用一次重算，结果与"从未镶过"**逐字段相等**。

## 8. 存档：存 ID，不存引用

⚠ 与 `economy.md` 同源：**存档只写 `gem_id` + 实例可变字段**。

⛔ 存 Resource 引用的话，配表删掉某颗宝石后旧存档会指向空——
表现为"读档后装备上的宝石变成空白图标"，且**没有报错**。

ⓘ 加载时用 `GemRegistry.get_base(gem_id)` 解析；
⚠ **解析失败要进隔离区**，⛔ 不能静默用默认宝石替换
（玩家会看到属性变了但不知道为什么）。

## 9. 服务端权威

⚠ 镶嵌结果与消耗必须服务端裁决。

| 客户端能做 | 客户端不能做 |
|---|---|
| 本地预览属性变化 | 决定宝石是否消耗 |
| 校验格式、提前置灰 | 决定合成是否成功 |
| 展示套装触发状态 | 决定拆卸损耗比例 |

⛔ 合成成功率在客户端算 = 玩家可以改内存必成。

ⓘ 与 `netsync-advanced.md` 同源：客户端只发**意图**，结果以服务端为准。

## 10. 待核对项（运行时验证）

> ⚠ 以下为本域**尚无统一法定数值/口径**的项，落地时必须实测确认。
> ⛔ 不要凭印象填数值——这些恰恰是各项目差异最大的地方。

- ⚠ 待核对：宝石合成比例（3→1 还是 5→1）与拆卸返还比 · 验证：查目标项目的经济策划案，与 `economy.md` 的产出/消耗表对齐，确认无套利环
- ⚠ 待核对：拆卸损耗的具体规则（降级 / 销毁 / 付费无损） · 验证：查策划案并在 UI 文案中逐字确认已明示
- ⚠ 待核对：符文页是否允许战斗中切换 · 验证：查目标项目的战斗系统设计，与 `combat.md` 的硬直/施法规则对齐
- ⚠ 待核对：套装判定是按装备槽位去重还是按宝石总数 · 验证：查策划案；若两处描述不一致，以配表实际字段为准并回写文档
