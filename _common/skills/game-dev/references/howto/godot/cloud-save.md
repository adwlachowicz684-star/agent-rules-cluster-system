# 云存档与跨平台进度同步（Godot 4.7.2）

"云存档""云同步" 此前 **0 命中**。跨平台商业项目的硬需求。

## 0. 本质不是"把文件传上去"

⚠ **核心难题是冲突**，不是传输。

必须当作正常路径（而非边缘异常）的四种场景：
1. 同一设备离线玩后上线
2. 多设备交替玩（PC 玩一半，手机接着玩）
3. 云存档与本地不一致
4. ⚠ **旧版程序读取新版存档**（版本降级）

⚠ **最危险的策略是"网络成功或本地较新就静默覆盖"** —— 玩家进度直接没了。

## 1. Godot 没有内置云存档

⚠ 官方只有 `user://`、FileAccess/DirAccess、JSON 与低级网络。
**没有统一远程存储、账号、版本控制或冲突解决模块。**

生产方案通常是：

```
Godot 负责可校验的本地存档
Steam / EOS / Play Games / 主机服务 / 自建后端 负责远程存储
游戏侧用 单调递增版本号 + 逻辑时钟 + 校验和 + 迁移表 + 显式冲突界面 接起来
```

### 平台 SDK 现状

| 方案 | 状态 |
|---|---|
| **GodotSteam** | 4.22.1 明确列出 **Godot 4.7.2** 变体，当前最成熟的社区路径 |
| **EOSG** | 官方写 Godot 4.2+，有 Player/Title Data Storage；**需按 4.7.2 重新验证** |
| **Godot Play Game Services** | 第三方方案，要核对 4.7.2 + AGP + SDK + 包名签名 |

⚠ **引擎 API 的"正式版"与插件的"兼容"必须分开声明** ——
不能只看到 README 写"支持 Godot 4.x"就当成已验证。

## 2. `user://` 的实际位置

| 平台 | 位置 |
|---|---|
| 桌面端 | 标准应用数据目录 |
| 移动端 | 应用私有沙盒 |
| HTML5 | **IndexedDB** |

ⓘ `user://` 的实际路径可用 `OS.get_user_data_dir()` 拿到。
官方说明：该路径取决于**项目名称**与
`ProjectSettings.application/config/use_custom_user_dir`；
Windows 上为 `%AppData%\Godot\app_userdata\[project_name]`。

⚠ **别与 `OS.get_data_dir()` 混淆** —— 官方原话：后者返回的是
**全局（非项目特定）**的用户主目录。用错会把存档写到共享位置，
导致**不同项目互相覆盖**。

⚠ **iOS**：Documents 与 Application Support 通常**参与备份**，
Caches/Temporary **不备份** —— 这是选择本地缓存与临时写入目录的直接依据。

## 3. 冲突判据：不能用文件修改时间

⚠ **"时间戳较新"只能用于界面解释，不能单独成为权威证据** ——
PC 时钟可被改、手机跨时区、两台设备都不校时、夏令时改变字符串顺序。

**最小元数据**：模式/游戏版本 · 存档格式版本 · 用户账户 ID · 存档槽 ·
**逻辑版本号** · 上一次源端逻辑版本 · 写入端标识 · 写入时间（仅展示） ·
游玩时长（仅辅助） · 内容哈希 · 可合并字段标记

⚠ **版本号不能复用构建号**（一个构建内可能多次写入）。
⚠ **时钟不能复用设备时间**，要用每个槽**单调递增**的计数器。

### 逻辑版本 + 历史线

```
若云端 42、本地 41 且 parents 含 42 → 本地从云端继续，可直接上传
若两者共同来自 40 → 构成分支，进入合并或人工选择
```

Lamport 时钟是轻量补充（读到远端事件就推到 `max(local, remote)+1`），
但**不适合独立生成完整因果图** —— 真正防丢失仍需领域层合并或显式选择。

⚠ **冲突 UI 要让玩家看懂**：显示"PC 大约 2 小时前 / 手机 大约 10 分钟前"，
**而不是时间戳**。

## 4. 跨平台兼容

⚠ **同一份存档在 PC 和手机上的内容可能不同**（画质设置、操作偏好、已购内容）
→ 要分清**哪些该同步、哪些不该**。

注意字节序、编码、路径分隔符的平台差异。

> **反模式清单（不能怎么做，审核用）** → `audit/godot/cloud-save.md`


## 5. 同步主流程（可照做的顺序）

⚠ **顺序写错会导致可恢复的冲突变成不可逆丢失。**
下面是唯一安全的顺序：

```text
启动
 1. 读本地存档 → 校验（HMAC/解析）→ 本地可用？
      ├ 不可用 → 本地损坏流程（见 save-migration.md 第 8 节）
      └ 可用 → 2
 2. 拉取云端元数据（⛔ 不先拉整份存档）
 3. 比较逻辑版本 + 历史线（见第 3 节）
      ├ 云端是本地的祖先 → 直接上传本地
      ├ 本地是云端的祖先 → 直接下载云端
      ├ 同一祖先的分支   → ⚠ 冲突流程（第 6 节）
      └ 无法判断         → ⚠ 按"冲突"处理（⛔ 不要猜）
 4. 落地后**再跑一次迁移链**（云端可能是旧格式）
 5. 启动成功，进入正常游玩
```

⚠ **第 4 步最容易被漏。** 云端存档可能是**旧格式**（别的设备装的是旧版），
只做冲突判断不做迁移 → 启动崩溃或数据错乱。

⚠ **第 2 步只拉元数据。** 先整份下载再比对，
等于用流量换一次"大概率要重下"的下载。

### ⚠ 上传时机：存档时不能立刻上传

⚠ **同步是异步的，且必然有失败。**
在"写入本地成功"后**必须立刻返回成功**给玩家，
⛔ 不能让玩家等着云端返回——否则断网就存不了档。

```text
写本地成功 → 立刻告诉玩家"已保存"
          → 入同步队列 → 后台重试（带退避）
          → 失败保留队列，下次启动/联网时继续
```

⚠ **队列要持久化。** 只在内存里排队 → 玩家关掉游戏再开就丢了，
表现为"我以为存档同步了"。

### ⚠ 离线游玩的时长上限

⚠ 长时间离线后上线，**冲突概率与离线时长成正比**。
若游戏允许离线玩很久，要有**"长时间未同步"的温和提醒**，
⛔ 不能只在冲突时才弹窗——那时已经晚了。

## 6. 冲突流程：三种可执行的解法

⚠ **"自动选一个"不是解法。**
自动选 = 静默丢弃玩家在某个设备上的进度。

| 解法 | 适用 | 代价 |
|---|---|---|
| **① 玩家选择** | 通用兜底 | 打断体验，但**永不丢数据** |
| **② 领域层合并** | 字段可独立合并（如成就、统计） | 要逐字段定合并规则 |
| **③ 槽位并存** | 玩家愿意手动管理 | 要 UI 展示多个槽 |

ⓘ **① 是必须有的**——②③ 都做不到时它是唯一的安全网。

### 合并的前提：区分"可合并"与"不可合并"

⚠ **不是所有字段都能合并。** 混在一起做"字段级 last-write-wins"
会得到"金币取了新的、任务进度取了旧的"这种**逻辑上不可能的状态**。

| 类型 | 例子 | 策略 |
|---|---|---|
| ✅ 单调可加 | 成就、击杀数、累计时长 | 取 max / 求和 |
| ✅ 集合可并 | 已解锁内容、图鉴 | 并集 |
| ⛔ 不可合并 | 当前关卡进度、背包、任务状态 | **整体取一份** |

⚠ **第 3 节元数据里的"可合并字段标记"就是为这个服务的** ——
没有它，合并代码只能靠猜字段语义。

### 冲突 UI 的三条硬要求

⚠ 显示**相对时间 + 设备**，⛔ 不显示时间戳（第 3 节已述）
⚠ **必须能预览内容**（等级、进度、时长），⛔ 不能只给两个按钮盲选
⚠ **选完要能反悔** —— ⛔ 覆盖前把落选的那份**备份到本地**

ⓘ 第三条常被漏：玩家选错了就永久丢失，而"备份落选项"成本极低。

## 7. 该同步什么：三分类表

⚠ **"全部都同步"和"全部不同步"都是错的。**
第 4 节说要分清，这里给可执行的分类：

| 类别 | 例子 | 是否同步 |
|---|---|---|
| **进度类** | 关卡、任务、背包、角色 | ✅ 同步 |
| **跨端偏好** | 音量、语言、已购内容 | ✅ 同步（但要处理平台差异） |
| **本机偏好** | 画质、分辨率、操作偏好、按键映射 | ⛔ **不同步** |
| **本机状态** | 相机位置、UI 折叠、临时缓存 | ⛔ 不同步 |

ⓘ 判据：**"换一台设备，这个设置还合理吗？"**
不合理 → 本机专属，不同步。

⚠ **画质设置同步是最典型的错误** ——
手机同步到 PC 会把 PC 画质拉到最低，反之会让手机卡死。

## 8. 配额与容量：云不是无限大

⚠ **云端有配额，且配额满了通常"不报错、只是同步失败"。**

ⓘ 各平台配额策略不同（⚠ 待核对：Steam 对个人游戏的配额与超限行为 ·
验证：查 Steamworks 文档的 Cloud 配额章节并在目标 AppID 实测），
但**共同点是**：满了之后新存档写不进去。

✅ 工程上的应对（与平台无关）：

| 措施 | 说明 |
|---|---|
| **存档体积上限** | 单档要设硬上限，超了要报错而非静默失败 |
| **本地保留代数** | 只同步当前档，历史档留本地 |
| ⚠ **主动检测失败** | 上传失败要**可见**，⛔ 不能只在日志里 |

ⓘ 常见诱因：截图、回放、日志被写进存档 → 单个存档几 MB。
✅ 二进制大块内容应**与存档分离**存。

### Web（IndexedDB）额外两条

⚠ **浏览器可以主动清除数据**（尤其是移动端）。
可用 `navigator.storage.persist()` 申请持久化，但**不保证被授予**。

⚠ **隐私模式下配额可能为 0。** 此时写入直接失败，
⛔ 不能表现为"存档成功但下次没了"。

✅ Web 端必须**捕获配额异常并明确提示**，
且关键进度**不应只存在本地**（要有服务端副本）。

## 9. 可观测：同步失败必须能看见

⚠ **云存档失败的典型表现是"玩家换了设备发现进度没了"** ——
此时已无法挽回，且后台看不出任何异常。

ⓘ 最少要能回答三个问题：

| 问题 | 上报字段 |
|---|---|
| 同步成功了吗 | 结果（成功/失败/冲突/跳过） |
| 失败在哪一步 | 阶段（拉元数据/上传/下载/迁移） |
| 影响多少人 | 失败类型计数（⛔ **不含存档内容**） |

⚠ **同样不能上报存档内容**（与 `save-migration.md` 第 10 节同一条约束）。

ⓘ 有了这个数据，"换了设备进度没了"这类差评才能被定位到具体阶段。
