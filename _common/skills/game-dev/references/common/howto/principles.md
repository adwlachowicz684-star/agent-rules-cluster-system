# 全局做法：跨功能域通用块（多对多可被索引）

> 本文件的每个块都有**稳定锚点 ID**（`GC-xx`），可被任意功能域引用。
> 一个块可以被**多个域**引用；一个域也可以引用**多个块**。
> 索引表见 `../index.md`。

⚠ **为什么单独放这里**：这些内容在几十个域里重复出现
（缓存 48 个、状态机 26 个、对象池 12 个、硬编码 11 个）。
⛔ 每个域各写一遍 → 改一处要改几十处，且必然漂移。
✅ 写在这里，各域用锚点引用。

ⓘ **引用写法**：`【读】common/howto/principles.md#GC-01`

---

## GC-01 状态机优于 if 嵌套

**适用**：角色状态、AI 行为、流程阶段、UI 面板、任务状态、交易状态……

⚠ 状态一多（idle/run/jump/fall/attack/hurt/dash），if 嵌套会变成灾难。

```
状态枚举 → 每个状态一个 enter/update/exit → 明确的转换条件
```

**三条硬性要求**：

1. ⚠ **每个状态必须明确 exit() 做什么** —— 只写 enter 的状态机一定会泄漏
   （残留 Tween、已连接信号、未完成的计时器）
2. ⚠ **转换条件必须是数据，不是"当前在第几行代码"** ——
   否则重放/存档/网络同步全都做不了
3. ⚠ **状态数要有上限并写进设计文档** ——
   状态爆炸的表现是"加一个新行为要改 5 个状态"

ⓘ Godot 侧可用 `AnimationTree` 的 StateMachine，或 `match state:`。

## GC-02 频繁生成/销毁的东西要池化

**适用**：子弹、粒子、伤害数字、列表项、投射物、特效……

⚠ 每帧 new 会产生 GC 压力，表现为**周期性卡顿**
（⛔ 不是持续低帧，是一阵一阵的）—— 这个特征很容易误判成"渲染问题"。

**回池前必须清理的四类状态**（漏一类就会复用出 bug）：

| 状态 | ⛔ 不清理的后果 |
|---|---|
| 速度/方向残留 | 从池里取出就往旧方向飞 |
| 已命中集合 | 第二发打不中 |
| 已连接的信号 | 回调打到旧目标 |
| 视觉残留（拖尾/粒子） | 残影出现在新对象上 |

⚠ **池不是"用 queue_free 换成 hide"就完事** ——
不做状态重置的池比不池化更糟，因为它把偶发 bug 变成必现 bug。

## GC-03 数据与逻辑分离（不硬编码易变值）

**适用**：数值、路径、动画名、ID、阈值……

```gdscript
# 反例：数值散落在代码里
velocity.y = -400.0
health -= 25

# 正例：可配置
@export var jump_velocity: float = -400.0
@export var damage: int = 25
```

⚠ **判据不是"能不能改"，而是"谁改"** ——
如果调一个数值需要程序员改代码重新打包，那就是硬编码。

ⓘ 好处：策划能自己调，便于做难度曲线，也便于 A/B。

⚠ **但不要走极端**：把"每帧都变的运行时状态"也塞进配置表是错误的，
配置表只放**启动时确定、运行期不变**的输入。

## GC-04 事件解耦 vs 直接引用

**适用**：跨系统通信（战斗→UI、战斗→音频、经济→任务）……

A 直接持有 B 的引用 → A 和 B 绑死，改一个另一个要跟着改。
用事件总线：A 发信号，谁关心谁订阅。

ⓘ **代价必须知道**：信号连了要记得断。

⚠ **这是跨所有域的头号泄漏源**，判据是"订阅与退订必须成对出现在同一生命周期层"
（`_enter_tree`/`_exit_tree` 或 `ready`/`tree_exiting`，⛔ 不能混层）。

⚠ **事件解耦不适用于强顺序依赖的场景** ——
"A 必须等 B 完成后才能继续"用信号会退化成回调地狱，那时应该显式调用。

## GC-05 缓存：必须有失效路径

**适用**：资源缓存、查询结果缓存、派生数据缓存、UI 缓存……

⚠ **48 个域都提到缓存，但失效路径是最常被漏写的一半。**

ⓘ 缓存的风险**不是"占内存"**，而是**脏读** —— 拿到旧数据而没有任何迹象。

**三个必答问题**（写缓存时逐条回答）：

| 问题 | ⛔ 答不出的后果 |
|---|---|
| 什么时候失效？ | 永远不失效 = 读到陈旧数据 |
| 谁是权威源？ | 两份真相，改一处漏一处 |
| 失效是推还是拉？ | 推漏一个订阅者 = 永久脏 |

⚠ **缓存 key 必须包含影响结果的全部输入** ——
漏一个维度（如语言、难度、赛季版本）会让不同配置互相污染。

ⓘ **"先加缓存再优化"是本末倒置**：缓存引入的一致性成本通常高于它省的时间。

## GC-06 性能：先定位再优化

⚠ **不要凭感觉优化**。常见误判：

| 直觉 | 实际 |
|---|---|
| "节点太多了所以卡" | 节点数量本身很少是瓶颈，DrawCall 和脚本逻辑才是 |
| "贴图太大" | 通常是材质切换次数（合批被打断）而非单张尺寸 |
| "物理太重" | 先确认是不是每帧在做空间查询 |

✅ **正确顺序**：跑 Profiler → 看是 Script / Render / Physics 哪一栏高 → 针对性优化。

⚠ **搞反了会白优化**，而且更糟：优化完仍然卡，会让人怀疑工具不准，
转而去改"看起来可疑"的地方，越改越乱。

## GC-07 手感优先于（物理）正确性

**适用**：平台跳跃、射击手感、操作反馈……

平台跳跃的手感来自几个**物理上不正确**的小机制：

| 机制 | 作用 |
|---|---|
| 土狼时间（Coyote Time） | 离开平台后 0.1s 内仍可跳，容忍玩家反应延迟 |
| 跳跃缓冲（Jump Buffer） | 落地前按的跳会在落地瞬间生效 |
| 可变跳跃高度 | 松开跳键立刻削减上升速度，短按=小跳 |
| 加速度/摩擦分离 | 起停有过渡，不是瞬间到达最高速 |

⚠ 没有这些，手感就是"黏" —— 而玩家不会说"缺土狼时间"，只会说"不好玩"。

ⓘ **这条也解释了为什么"照物理公式实现"往往手感差**：
正确的物理 ≠ 正确的手感。

## GC-08 常见架构模式速查

| 模式 | 用途 | Godot 实现 |
|---|---|---|
| 单例/管理器 | 全局唯一（存档、音频、场景管理） | Autoload |
| 事件总线 | 跨系统解耦（见 GC-04） | Autoload + signal |
| 状态机 | 角色/AI/流程状态（见 GC-01） | `match` 或 AnimationTree |
| 对象池 | 频繁生成销毁（见 GC-02） | 见各域文档 |
| 组件组合 | 能力拼装（可移动+可受伤+可交互） | 子节点 + 接口约定 |
