# 全局审查：跨功能域通用块（多对多可被索引）

> 本文件的每个块都有**稳定锚点 ID**（`GA-xx`），可被任意功能域引用。
> 这些是"⛔ 不可能每个功能里单独写"的审查项 —— 它们横跨所有域。
> 索引表见 `../index.md`。

⚠ **为什么单独放这里**：在 100+ 个域里各写一遍"参数类型要检查"，
结果是每个域写得都不一样，且必然有域漏掉。

ⓘ **引用写法**：`【审】common/audit/global.md#GA-01`

---

## GA-01 参数类型不符 / 类型不匹配

**适用**：所有函数入口、RPC 参数、配置表字段、存档字段、外部输入。

⚠ **动态语言里这类错误不会在编译期暴露**，表现为运行到某条分支才崩，
或者**更糟：不崩，只是算出错误结果**。

必查四类：

| 类型 | ⛔ 典型错误 |
|---|---|
| 数值 vs 字符串 | 配置表里写 `"100"`，读到 `int` 字段变成 0 |
| 整数 vs 浮点 | 除法在两边都是 int 时**截断**（`7/2 == 3`） |
| 可空 vs 非空 | 外部输入缺失时拿默认值，⛔ 不要静默吞掉 |
| 枚举 vs 魔数 | 用 1/2/3 表示状态，改表后全部错位 |

⚠ **外部输入（网络、存档、配置表、玩家输入）必须显式校验类型与范围**，
⛔ 不能依赖"上游保证是对的"。

ⓘ **RPC 参数尤其危险**：远端发的类型与本地声明不符时，
错误发生在**对端**，本地日志里只有一句不明确的报错。

## GA-02 资源没配对（申请/释放、连接/断开）

**适用**：文件句柄、信号连接、Tween、Timer、网络连接、对象池借用、锁。

⚠ **这是跨所有域出现频率最高的缺陷类。**

必查六对：

| 申请 | 释放 | ⛔ 漏掉的后果 |
|---|---|---|
| `connect` | `disconnect` | 回调打到已释放对象 |
| `create_tween` | `kill` / 超时兜底 | 跨场景泄漏 |
| 池 `acquire` | 池 `release` | 池耗尽后永远借不到 |
| 打开文件 | 关闭 | 句柄泄漏 |
| 加锁 | 解锁 | 死锁 |
| 注册监听 | 注销 | 重复触发 |

⚠ **配对必须发生在同一生命周期层**（`_enter_tree`/`_exit_tree` 或 `ready`/`tree_exiting`），
⛔ 混层会在场景切换时漏掉一半。

ⓘ **判据**：搜索 "申请" 的调用点，逐个确认有对应的释放点。
⛔ 反过来搜（找释放点确认有申请）是无效的 —— 漏掉的根本没写释放。

## GA-03 硬编码易变值

**适用**：数值、路径、动画名、ID、阈值、URL、版本号。

⚠ 判据不是"能不能改"，而是"**改它要不要重新打包**"。

⛔ 尤其危险的四种：

1. **路径硬编码** —— 换平台/导出后路径失效（导出后资源被转换是常见原因）
2. **动画名硬编码** —— 改动画名后静默失效（⛔ 不报错，只是不播）
3. **ID / 主键硬编码** —— 数据表重排后指向错误对象
4. **时间与汇率等外部值硬编码** —— 无法热更

ⓘ 对应做法见 `../howto/principles.md#GC-03`。

## GA-04 每帧做本该事件驱动的事

**适用**：`_process` / `_physics_process` 里的一切。

⛔ 三类典型：

| 每帧做 | 应该 |
|---|---|
| 轮询输入 | 用输入事件 / `_input` |
| 查找节点（`get_node`） | 缓存引用 |
| 重建文本 / 重排 UI | 只在数据变化时做 |

⚠ **UI 文本尤其致命**：每次赋值都触发重排，
表现为"数据没变但帧率就是上不去"。

ⓘ 判据：**数据不变的帧里，赋值次数应为 0**。
不是"大概不会每帧改"—— 要实测。

---

## GA-05 缓存无失效路径

**适用**：一切缓存（资源、查询结果、派生数据、UI）。

⚠ 缓存的风险**不是占内存，是脏读** —— 拿到旧数据而**没有任何迹象**。

必答三问（答不出 = 缺陷）：

1. 什么时候失效？→ ⛔ 答"不需要"通常意味着永不失效
2. 谁是权威源？→ ⛔ 两份真相必漂移
3. 失效是推还是拉？→ ⛔ 推漏一个订阅者 = 永久脏

⚠ **缓存 key 必须包含影响结果的全部输入** ——
漏一个维度（语言、难度、赛季版本）会让不同配置互相污染。

ⓘ 对应做法见 `../howto/principles.md#GC-05`。

---

## GA-06 状态机只写 enter 不写 exit

**适用**：一切状态机（角色、AI、流程、UI 面板、任务）。

⚠ **这是"状态机泄漏"的头号来源**：退出状态时不做清理，
残留 Tween、已连接信号、未完成计时器、未归还的池对象。

⛔ 表现：切换状态几次后行为逐渐异常，且**难以复现**。

必查：每个状态的 `exit()` 是否清理了它在 `enter()` 里创建的一切。
⚠ 判据是 **enter 与 exit 逐个配对**，⛔ 不是"看起来没问题"。

ⓘ 对应做法见 `../howto/principles.md#GC-01`。

---

## GA-07 错误处理吞掉异常

**适用**：一切 `try/except`、错误码分支、空值判断。

⚠ **吞异常的代价是错误信号被当成正常结果** ——
这是最难排查的缺陷类，因为**没有任何日志**。

⛔ 三类典型：

| 写法 | 后果 |
|---|---|
| `except: pass` | 失败静默，后续逻辑基于错误前提继续跑 |
| 错误码不检查 | 同上 |
| 空值不判 | 空对象后续调用崩在**离根因很远**的地方 |

✅ 至少要有日志或计数；关键路径必须显式失败。

⚠ **"但要保证流程不中断"不是吞掉的理由** ——
正确做法是降级 + 记录，⛔ 不是假装没发生。
