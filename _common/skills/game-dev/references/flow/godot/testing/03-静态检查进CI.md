# 03 静态检查进 CI（测试域）

> **本步交付**：工具链版本对齐 + 抑制规范 + 收紧节奏
> **对应**：流程 `howto/godot/testing.md` · 审核 `audit/godot/testing.md`

## 0. 交付物定义

1. 工具链大版本与 Godot 大版本**已对齐并锁定**
2. 已跑一次建立基线，⛔ 不是一上来要求 0 问题
3. 每处抑制都写了原因，⛔ 没有批量关规则
4. 项目自身的审查脚本也进流水线
5. 流水线分层：快的先跑，慢的不阻塞快速反馈

## 1. 前置检查清单

- [ ] `gdtoolkit` 大版本 == Godot 大版本，且版本已锁定（不随 latest 漂移）
- [ ] 已记录当前基线问题数，且有明确的收紧计划
- [ ] 每处行内抑制旁都有原因文字
- [ ] `godot-audit.py`（或等价脚本）在流水线里且有 P0 判据
- [ ] 静态检查与慢测试分成两个 job，静态在前

## 2. 工序

### Step 1　⛔ 工具链大版本必须与 Godot 对齐并锁定　`[testing/03#S1]`

【读】`howto/godot/testing.md#4. 静态检查进 CI`

【做】
`gdtoolkit` 用 `4.*`（Godot 4 项目），并在 CI 里**写死版本**。
⛔ 用 `latest` 或不锁版本 —— 规则集会随工具升级变化，
表现为"某天 CI 突然红了几十处，而代码一行没改"，
⛔ 排查被引向"谁提交了什么"，实际是工具自己升级了。

ⓘ 版本不一致时**规则全错**（不是少报几条），
表现为"本地全绿、CI 全红"或反过来，
⛔ 而两边的代码与配置看起来完全一致。

【产出】锁定的工具版本清单

【判据】在 CI 配置里能直接读到版本号，⛔ 没有 `latest`。

【审】`audit/godot/testing.md#4`

### Step 2　先跑一次建基线，⛔ 不能一上来要求 0 问题　`[testing/03#S2]`

【读】`howto/godot/testing.md#6. 我们自己的审查脚本`

【做】
先完整跑一次并记录基线问题数，
对**新改动的文件**严格、历史文件逐步收紧。
⛔ 一上来要求 0 —— 老项目会直接被 CI 卡死，
⛔ 而卡死之后团队的唯一出路是**绕过 CI**（加排除、加抑制、直接 merge），
于是这套检查从此作废，且没人会记得它曾经有效过。

ⓘ 这条的本质是：检查的**严格度**必须与其**可执行性**匹配。
⛔ 一个立即无法通过的门禁，最终结果是门禁被拆除，而不是代码变好。

【产出】基线问题数 + 收紧节奏（如"每月收紧一档"）

【判据】能说出当前基线与下一次收紧的目标值。

【审】`audit/godot/testing.md#7`

### Step 3　抑制必须写原因，⛔ 不能批量关规则　`[testing/03#S3]`

【读】`howto/godot/testing.md#4. 静态检查进 CI`

【做】
每处行内抑制旁写明"为什么这里必须例外"。
⛔ 批量关掉某条规则 —— 真问题也被一起关掉，
⛔ 表现为"这条规则明明开着，相关 bug 却从来没被抓到"，
而排查时看到规则是启用的，就会去别处找原因。

ⓘ 典型正当例外：引擎回调签名要求的未使用参数。
ⓘ 典型不正当例外："这个项目历史原因比较多" ——
这不是原因，是放弃。

【产出】抑制清单（含每条原因）

【判据】随机挑 3 处抑制，都能读出一句话的具体原因。

【审】`audit/godot/testing.md#5`

### Step 4　项目自己的审查脚本也要进流水线　`[testing/03#S4]`

【读】`howto/godot/testing.md#6. 我们自己的审查脚本`

【做】
把 `godot-audit.py`（或项目自建的检查脚本）作为流水线一步，
并以 P0 问题为失败判据。
⛔ 只在本地偶尔跑 —— 脚本的有效性与"是否有人跑"完全绑定，
⛔ 三个月后它检查的东西早已与代码脱节，
而所有人仍以为"我们有检查"。

ⓘ 这与 S2 是配套的：脚本进流水线同样要先建基线，
⛔ 用 P0 全量清零做首日目标，结果同样是门禁被绕过。

【产出】流水线步骤 + P0 判据 + 当前基线

【判据】故意引入一处 P0 问题，该步骤报红。

【审】`audit/godot/testing.md#7`、`audit/godot/testing.md#16`

### Step 5　流水线分层：快的先跑，⛔ 别让慢任务挡住反馈　`[testing/03#S5]`

【读】`howto/godot/testing.md#7. 上线前检查`

【做】
把静态检查（秒级）与慢测试（分钟级）分成两个 job，静态在前，
慢测试不阻塞静态反馈。
⛔ 全塞一个 job —— 每次提交都要等十几分钟才知道结果，
⛔ 而人对慢反馈的反应是"先合了再说，红了再看"，
反馈越慢，门禁的实际约束力越弱。

ⓘ 配套：每步都要有超时上限（见 01/S5），
⛔ 挂死的任务会让整条流水线无限等待。

【产出】流水线 job 划分 + 各步超时上限

【判据】一次提交能在 1 分钟内拿到静态检查结果。

【审】`audit/godot/testing.md#15`、`audit/godot/testing.md#19`

## 3. 参考实现

```yaml
# ⓘ 承接本步产出：版本锁定 + 分层 + 超时 + P0 判据
name: Godot CI
on: [push, pull_request]

jobs:
  static:                      # ⛔ 快的先跑，不跟慢测试混在一个 job
    runs-on: ubuntu-latest
    timeout-minutes: 10        # ⛔ 无上限时挂死会让流水线无限等待
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-python@v5
        with: { python-version: '3.11' }
      # ⛔ 不写 latest：工具升级会让规则集静默变化
      - run: pip install "gdtoolkit==4.3.*"
      - run: gdformat --check .
      - run: gdlint .          # ⛔ tests/ 目录不排除（见 02/S5）
      - run: python3 godot-audit.py --src=. --format=json > audit.json
      - run: python3 check_p0.py audit.json   # P0 判据，先建基线后收紧

  test:
    runs-on: ubuntu-latest
    needs: static
    timeout-minutes: 30
    steps:
      - run: godot --headless -s addons/gut/gut_cmdln.gd -gtest=tests/ -gexit
      # ⛔ 退出码是否生效必须实测（见 01/S2），兜底读文件判成败
      - run: test -f user://test_result.txt && head -1 user://test_result.txt | grep -q '^0 '
```

## 4. 验收清单

- [ ] 工具版本已锁定且与 Godot 大版本一致
- [ ] 已建基线，有收紧计划
- [ ] 抑制都写了原因，无批量关规则
- [ ] 自建审查脚本进流水线且有 P0 判据
- [ ] 流水线分层，每步有超时上限

## 5. 常见返工

| 症状 | 原因 | 回到 |
|---|---|---|
| 某天突然红了几十处，代码没改 | 工具版本没锁 | S1 |
| CI 卡死团队，最后被绕过 | 一上来要求 0 问题 | S2 |
| 规则开着但 bug 从没被抓到 | 批量关了规则 | S3 |
| 自建脚本与代码脱节 | 没进流水线 | S4 |
| 提交后要等十几分钟 | 快慢任务没分层 | S5 |
