# 测试与 CI —— 域流程总览

> ⚠ **第 0 步：先定"哪些不测、测了怎么算失败"。**
> 本域有 7 个功能点，⛔ **不是全做** —— 按本次需求挑。

## 0. 先定做什么

| 本次要做的 | 走哪些功能点 |
|---|---|
| 刚起步，先有纯逻辑测试 | 01 → 02 → 07 |
| 静态检查进 CI | 01 → 03 → 07 |
| 存档格式要改，怕老档读不了 | 01 → 02 → 04 → 07 |
| 随机 / 回放 / 抽卡类玩法 | 01 → 02 → 05 → 07 |
| 画面改动怕视觉劣化 | 01 → 06 → 07 |
| 完整测试体系 | 01 → 02 → 03 → 04 → 05 → 06 → 07 |

⛔ **01 不能跳过** ——
测试分层与"失败怎么表达"决定了后面每一步的有效性。
⛔ 不先定，就会写成"测试跑完打印一行通过"，
而**这行通过什么都没证明**：断言可能根本没执行（见 01/S1），
失败信号也可能没传到 CI（见 01/S2）。

⛔ **02 的失败信号必须真能打断 CI** ——
这是本域与其他域最大的区别：别的域交付功能，
本域交付的是**"功能坏了会立刻被人知道"这件事本身**。
⛔ 测试写了、跑了、绿了，但坏了不红 = 等于没有测试，
而且比没有更糟，因为它给出了虚假的安全感。

⛔ **04 的存档样本要在格式变更之前存** ——
改完格式再补样本，样本已经是新格式，回归网从未真正覆盖旧档。
⛔ 表现为"上线后老玩家存档读不了"，而此时没有样本可复现。

ⓘ 若本次只是**补两个单元测试**，那是编码，不套本域。
ⓘ 若只是**排查某个测试为什么偶发红**，先看 05（随机性与确定性）。

ⓘ 分工：
- `howto/godot/testing.md` 讲**基础做法**（分层、GUT、静态检查、上线前检查）
- `howto/godot/testing-advanced.md` 讲**进阶做法**（属性测试、模糊、视觉回归、性能基准、确定性）
- 本域讲**这两篇按什么顺序做、怎么保证测试真的在验证东西**

⛔ 若本域某步需要"覆盖率目标""p99 阈值""模糊迭代次数"这类数字，
指向项目实测，⛔ 不在这里编数字。

## 1. 功能点拆解（按依赖，不可颠倒）

| # | 功能点 | 依赖 | 交付物 |
|---|---|---|---|
| 01 | 测试分层与失败信号地基 | — | 分层清单 + 断言可执行口径 + 退出码实测结论 |
| 02 | 单元与集成测试 | 01 | 纯逻辑测试集 + 隔离口径 + 失败即红的链路 |
| 03 | 静态检查进 CI | 01 | 工具链版本对齐 + 抑制规范 + 收紧节奏 |
| 04 | 存档回归与兼容性 | 01, 02 | 历史版本样本库 + 往返测试 + 迁移路径 |
| 05 | 随机性、确定性与模糊测试 | 01, 02 | 固定种子口径 + 不变量判定器 + 畸形输入存活测试 |
| 06 | 视觉回归与性能基准 | 01, 02 | 基线管理 + 阈值断言 + 分位数判据 |
| 07 | 测试验收 | 全部 | 故意注入失败 + release 导出包实测 |

⚠ **01 必须在写第一个测试之前**：
断言机制与退出码是"测试是否有效"的地基，
⛔ 先写一堆测试再发现断言在 release 下不执行，等于全部重写一遍断言方式。

⚠ **03 的工具链版本要在第一次装 CI 时定死**：
`gdtoolkit` 大版本与 Godot 大版本不一致时规则全错，
⛔ 表现为"本地全绿 CI 全红"，而排查必然被引向 CI 配置。

⚠ **05 的确定性口径要在引入随机玩法时同步定**，不能事后补：
补的时候代码里已到处是 `randi()`，⛔ 改不完就只能把测试写成"跑一次看对不对"。

## 2. 与其他域的接缝

> ⚠ **组合的真正难点不是单个测试，是接缝。**
> 下面每条都必须能指认到具体符号或字段，⛔ 不能是"做完了"。

| 接缝 | 契约 |
|---|---|
| `save` 域 存档 | 存档格式与迁移见 `save`，⛔ 本域只定**样本怎么存、怎么回归** |
| `perf` 域 性能 | 帧预算与剖析见 `perf`，⛔ 本域只定基准**怎么测、怎么看分位数** |
| `procgen` 域 程序化生成 | 种子可复现契约见 `procgen`，⛔ 本域只定**怎么验它复现** |
| `security` 域 安全 | 改包与篡改检测见 `security`，⛔ 本域只定模糊/畸形输入的存活判据 |
| `economy` 域 经济 | 纯逻辑测试优先测什么见 `economy`，⛔ 本域不另定业务口径 |
| `compliance` 域 合规 | 上线前检查的合规项见 `compliance`，⛔ 本域只定检查**怎么进流水线** |
| `cicd-publish` | ⓘ howto 层，暂无 flow 域 —— 出包与发布流水线见该篇 |
| `devtools` | ⓘ howto 层，暂无 flow 域 —— 调试开关与开发期工具见该篇 |
| `gdextension-deep` | ⓘ howto 层，暂无 flow 域 —— C# / GDExtension 侧的测试见该篇 |

## 3. 参数登记

| 参数 | 所在功能点 | 初始值 | 实测值 | 状态 |
|---|---|---|---|---|
| `DIFF_THRESHOLD` 视觉差异阈值 | 06 | — | — | 待实测（与抗锯齿与 GPU 驱动相关，⛔ 不能设 0） |
| `WARMUP_FRAMES` 预热帧数 | 06 | — | — | 待实测（与首帧加载开销相关） |
| `MEASURE_FRAMES` 采样帧数 | 06 | — | — | 待实测（与可接受的 CI 时长相关） |
| `P99_BUDGET_MS` p99 帧时间上限 | 06 | — | — | 待实测（与目标帧率和目标硬件相关） |
| `FUZZ_ITERATIONS` 模糊迭代次数 | 05 | — | — | 待实测（与 CI 时长预算相关） |
| 存档样本保留的历史版本数 | 04 | — | — | 待实测（⛔ 少于 1 等于没有回归网） |
| CI 单轮超时上限 | 03 | — | — | 待实测（⛔ 太长等于没设，故障要几小时才暴露） |

⛔ 上表"待实测"项**不得凭行业惯例填** ——
填错不会报错，只会表现为"阈值形同虚设"或"永远红但没人看"，
⛔ 而后者会让团队养成绕过 CI 的习惯。
