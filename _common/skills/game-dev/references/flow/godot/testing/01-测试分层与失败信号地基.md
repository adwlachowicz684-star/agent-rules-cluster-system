# 01 测试分层与失败信号地基（测试域）

> **本步交付**：分层清单 + 断言可执行口径 + 退出码实测结论
> **对应**：流程 `howto/godot/testing.md` · 审核 `audit/godot/testing.md`

## 0. 交付物定义

1. 测试分层已写下，且**明确写下哪些不测**
2. 断言机制已定：**能证明它在导出包里真的执行**
3. 退出码链路已实测：**故意让一个测试失败，CI 真的红**
4. `assert()` 内无副作用表达式，已成团队公约
5. release 导出包跑测试已进流水线，⛔ 不是只在编辑器里跑

## 1. 前置检查清单

- [ ] 能一句话说清本项目的四层测试各自测什么、哪些不测
- [ ] 已验证断言在 **release 导出模板**下确实执行（或已改用不依赖 assert 的机制）
- [ ] 已实测：让一个测试失败 → 进程退出码非 0 → CI 报红
- [ ] `assert()` 内没有函数调用等副作用
- [ ] 流水线里有一轮跑的是**导出后的产物**，不是编辑器

## 2. 工序

### Step 1　⛔ 先确认断言在 release 下还会执行 —— 否则测试全过但什么都没测　`[testing/01#S1]`

【读】`howto/godot/testing.md#8. 断言与退出码：测试有效的两个前提`

【做】
先定断言机制，再写测试。
官方对 `assert` 的警告（单行引用）：*`"the code inside assert() is only executed in debug builds or when running the project from the editor"*`。
⛔ 用 `assert` 写断言、却在 release 导出包里跑测试 ——
断言**整段被跳过**，测试输出"通过 100 / 失败 0"，
而实际**一次都没验证**，且没有任何报错。

ⓘ 这条最危险的地方在于它是**自洽的**：
本地编辑器里跑，assert 执行、失败会红，看起来完全正常；
只有换到 release 模板才失效，而那时没人会怀疑"测试是不是没跑"。

⛔ 修法不是"改用 push_error"（那不会失败、只会打日志），
而是改用**自己统计并 `quit(非0)`** 的判定函数（见 `howto` §3 最小方案），
或明确约定：测试**只能在 debug 模板下跑**并写进流水线。

【产出】断言机制结论（三种口径之一）+ 写进 CI 的模板类型

【判据】在 release 导出包里故意断言一个假命题，⛔ 必须真的失败；
如果只是"通过"，说明该机制在本项目无效。

【审】`audit/godot/testing.md#9`

### Step 2　⛔ 退出码要实测，不能假设 —— `quit(1)` 可能不生效　`[testing/01#S2]`

【读】`howto/godot/testing.md#8. 断言与退出码：测试有效的两个前提`

【做】
让一个测试**故意失败**，从命令行跑，用 `echo $?` 确认退出码非 0。
⛔ 假设 `quit(1)` 一定生效 —— 官方仓库有 issue 记录
`--headless --script` 下 `quit(1)` **返回 0**（GH-88055，4.2.1 / 4.2.2 可复现）。
⛔ 表现为"测试全红但 CI 全绿"，而这是**灾难级**的：
流水线给出的信号与事实相反，团队会一直以为代码是好的。

ⓘ 该 issue 已关闭，**修复版本需实测确认** ——
所以本步的交付物不是"记得写 quit(1)"，而是**实测结论**。
⛔ 不要凭文档或记忆认定它已修好。

ⓘ 兜底写法：把失败数写进一个文件，CI 步骤读该文件判断，
⛔ 不单纯依赖进程退出码。

【产出】退出码实测结论 + 兜底判据（文件 / 日志关键字）

【判据】故意失败一次，CI 步骤确实报红且能被看到。

【审】`audit/godot/testing.md#11`、`audit/godot/testing.md#3`

### Step 3　⛔ `assert()` 里不能放有副作用的表达式　`[testing/01#S3]`

【读】`howto/godot/testing.md#8. 断言与退出码：测试有效的两个前提`

【做】
把"调用被测函数"与"断言结果"分成两行。
⛔ `assert(take_damage(30) == 70)` 这类写法 ——
官方警告 *"Don't include code that has side effects in an assert() call"*：
release 下整个表达式不求值，**被测函数根本没被调用**，
表现为"测试通过但功能没跑"，而 debug 下完全正常。

ⓘ 这与 S1 是同一机制的两个面：
S1 关注"断言没执行"，本步关注"被断言的**动作**没执行"。
⛔ 后者更隐蔽，因为断言本身可能是通过的。

【产出】断言书写公约（先调用取结果 → 再断言）

【判据】所有 `assert(...)` 括号内不含函数调用、赋值、`await`。

【审】`audit/godot/testing.md#10`

### Step 4　分层先定"不测什么" —— 覆盖率不是目标　`[testing/01#S4]`

【读】`howto/godot/testing.md#1. 测试分层`

【做】
写下四层（单元 / 集成 / 冒烟 / 回归）各自测什么，
并**明确写下哪些不测**（UI 布局、渲染表现、手感 —— 靠人工）。
⛔ 追求覆盖率数字 —— 游戏项目里 UI 与渲染的测试维护成本极高，
收益最低；把人力压在那里，⛔ 结果是"覆盖率达标但核心逻辑没人测"。

ⓘ 优先级判据：**先测纯逻辑**（伤害、经济、背包、寻路、存档），
它们可测、易测、出 bug 代价最高。

【产出】分层清单 + 明确的不测清单

【判据】能指出任意一处纯逻辑，它都有对应测试；
⛔ 不需要给出覆盖率数字。

【审】`audit/godot/testing.md#8`

### Step 5　失败信号要能打断流水线 —— 且要能看到是哪个用例　`[testing/01#S5]`

【读】`howto/godot/testing.md#7. 上线前检查`

【做】
失败时打印**失败用例名 + 期望值 + 实际值**，并让流水线中断。
⛔ 只打印"测试失败" —— CI 日志几百行时，
没人知道是哪个用例，⛔ 常见结果是先 retry 一次、再跳过。

ⓘ 配套两条：
流水线要有**超时上限**（⛔ 无上限时挂死的测试会让 CI 卡几小时，
表现为"CI 很慢"，团队的第一反应是加机器而不是查挂死）；
测试⛔ 不依赖联网或外部服务（网络抖动造成的红会被忽略，
久而久之所有红都被当成抖动）。

【产出】失败输出格式 + 流水线超时上限

【判据】注入一个失败，日志里能直接看到用例名，且流水线在限定时间内报红。

【审】`audit/godot/testing.md#16`、`audit/godot/testing.md#15`、`audit/godot/testing.md#19`

## 3. 参考实现

```gdscript
# ⓘ 承接本步产出：不依赖 assert 的判定 + 显式退出码 + 副作用外置
extends SceneTree

var _pass := 0
var _fail := 0
var _failed_cases: Array[String] = []

func _init() -> void:
    _test_damage()
    _test_save_roundtrip()
    # ⛔ 兜底：把结论写文件，CI 读文件判成败
    var f := FileAccess.open("user://test_result.txt", FileAccess.WRITE)
    if f:
        f.store_string("%d %d" % [_fail, _pass])
        f.close()
    print("通过 %d / 失败 %d" % [_pass, _fail])
    for c in _failed_cases:
        print("  ✗ %s" % c)
    quit(1 if _fail > 0 else 0)

func check(cond: bool, label: String, expected := "", actual := "") -> void:
    if cond:
        _pass += 1
    else:
        _fail += 1
        _failed_cases.push_back("%s（期望 %s 实际 %s）" % [label, expected, actual])

func _test_damage() -> void:
    # ⛔ 先调用取结果，再断言 —— 不在断言里放副作用
    var hp := 100
    hp -= 30
    check(hp == 70, "伤害计算", "70", str(hp))
```

ⓘ `quit()` 的退出码是否生效**必须实测**（见 S2），
⛔ 不要因为写了 `quit(1)` 就认为 CI 一定会红。

## 4. 验收清单

- [ ] release 模板下断言确实执行（或已约定只在 debug 下跑）
- [ ] 故意失败时退出码非 0，且 CI 报红
- [ ] `assert()` 内无副作用表达式
- [ ] 分层清单含明确的"不测什么"
- [ ] 失败日志含用例名；流水线有超时上限

## 5. 常见返工

| 症状 | 原因 | 回到 |
|---|---|---|
| release 包里测试"全过"但功能坏了 | assert 在 release 不执行 | S1 |
| 测试全红 CI 全绿 | quit(非0) 未生效 / 未实测 | S2 |
| 测试通过但被测函数没跑 | assert 内放了副作用 | S3 |
| 覆盖率达标但核心逻辑出 bug | 测了 UI 没测逻辑 | S4 |
| 只知道 CI 红了不知道哪红 | 失败不打用例名 | S5 |
