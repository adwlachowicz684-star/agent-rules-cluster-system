# 07 测试验收（测试域）

> **本步交付**：故意注入失败 + release 导出包实测
> **对应**：流程 `howto/godot/testing.md` · 审核 `audit/godot/testing.md`

## 0. 交付物定义

1. 每一类测试都**注入过一次失败**，并确认它真的报红
2. 测试在 **release 导出产物**上跑过，⛔ 不是只在编辑器里跑
3. 断言机制在本项目的导出模板下确实执行（01/S1 结论复核）
4. 退出码链路实测通过（01/S2 结论复核）
5. 各类基线（存档样本 / 视觉 / 性能）都经确认是对的

## 2. 工序

### Step 1　⛔ 注入失败法：逐个破坏，确认测试真的会红　`[testing/07#S1]`

【读】`howto/godot/testing.md#7. 上线前检查`

【做】
对每一类测试，改一处被测代码让它**变错**，
跑一遍，确认对应用例报红，然后还原。
⛔ 只看"当前全绿" —— 全绿什么都证明不了：
它可能因为断言没执行（01/S1）、退出码没生效（01/S2）、
基线是错的（06/S2）而**虚假地绿**。

ⓘ 这是本域唯一真正能证明"测试有效"的手段。
⛔ 没做过注入的测试套件，其绿色与没有测试不可区分。

ⓘ 最少覆盖：纯逻辑、存档往返、迁移、随机不变量、
模糊存活、性能阈值、视觉差异 —— 各注入一次。

【产出】注入清单（破坏点 × 预期报红的用例 × 实测结果）

【判据】每一次注入都让**预期中的那个**用例变红；
⛔ 若注入后全绿，说明该用例从未真正验证过它。

【审】`audit/godot/testing.md#9`、`audit/godot/testing.md#11`

### Step 2　⛔ 必须在 release 导出产物上跑一遍 —— 编辑器不算　`[testing/07#S2]`

【读】`howto/godot/testing.md#7. 上线前检查`

【做】
导出 release 模板，在上面跑完整测试套件。
⛔ 只在编辑器里跑 ——
编辑器是 debug 构建，断言会执行、回溯可用、
部分资源以原始形态加载，
⛔ 而玩家拿到的是 release 产物，
⛔ 表现为"编辑器里全过、出包后行为不同"，
且这类差异**通常不报错**。

ⓘ 与 `hotupdate` 域的分工：
热更产物的加载与校验见 `hotupdate`，
⛔ 本域只定"测试必须覆盖导出产物"这一条。

【产出】release 产物上的测试结果记录

【判据】release 与 debug 两侧结果一致；若不一致，差异已记录并解释。

【审】`audit/godot/testing.md#12`、`audit/godot/testing.md#9`

### Step 3　断言机制复核：在项目实际模板下再验一次　`[testing/07#S3]`

【读】`howto/godot/testing.md#7. 上线前检查`

【做】
把 01/S1 的结论在本项目**当前使用的导出模板**上复核一遍：
故意断言一个假命题，确认真的失败。
⛔ 只在立项时验过一次 ——
模板类型、CI 镜像、Godot 版本都可能变，
⛔ 表现为"以前是好的，不知从什么时候起测试不再验证东西"，
而这种退化**没有任何信号**。

ⓘ 配套复核 `assert()` 内是否混入了副作用（01/S3）：
这类写法往往是在后续迭代中**被慢慢加进去**的。

【产出】断言机制复核结论（含模板类型与 Godot 版本）

【判据】在 release 模板下断言假命题 → 测试报红。

【审】`audit/godot/testing.md#9`、`audit/godot/testing.md#10`

### Step 4　退出码链路复核：失败时 CI 真的红　`[testing/07#S4]`

【读】`howto/godot/testing.md#7. 上线前检查`

【做】
让一个用例失败，确认流水线报红、且能在日志里看到用例名。
⛔ 假设"上次测过就是好的" ——
CI 镜像、runner、Godot 版本变化都可能让退出码链路失效，
⛔ 而它失效的表现是"测试全红但流水线全绿"，
⛔ 这是本域**最严重**的失败模式：信号与事实相反。

ⓘ 兜底判据（文件 / 日志关键字）也要一并复核，
⛔ 只依赖退出码的链路在退出码被忽略时没有第二道防线。

【产出】退出码与兜底判据的复核记录

【判据】注入一次失败，流水线在超时上限内报红且能看到用例名。

【审】`audit/godot/testing.md#11`、`audit/godot/testing.md#16`、`audit/godot/testing.md#15`

### Step 5　基线复核：存档样本 / 视觉 / 性能基线都得是对的　`[testing/07#S5]`

【读】`howto/godot/testing.md#7. 上线前检查`

【做】
清点三类基线：存档样本覆盖全部历史版本（04/S2）、
视觉基线经人工确认且非全黑（06/S1、S2）、
性能基线是在目标硬件上取的（06/S5）。
⛔ 只清点数量不看内容 ——
基线可以是"存在但错的"，
⛔ 而错的基线让整套回归**持续给出通过信号**，
这是比没有基线更糟的状态。

ⓘ 与 `compliance` 域的分工：
上线前的合规项见 `compliance`，
⛔ 本域只定"基线本身要定期复核"这一条。

【产出】三类基线的复核记录（版本号 / 确认人 / 取值环境）

【判据】任意一条基线都能说清：谁、何时、在什么环境确认过。

【审】`audit/godot/testing.md#6`、`audit/godot/testing.md#20`、`audit/godot/testing.md#12`

## 3. 验收清单

- [ ] 七类测试各注入过一次失败，且都真的报红
- [ ] release 导出产物上跑过完整套件
- [ ] 断言机制在当前模板下复核通过
- [ ] 退出码 + 兜底判据复核通过
- [ ] 三类基线经复核为"存在且正确"

## 4. 常见返工

| 症状 | 原因 | 回到 |
|---|---|---|
| 测试一直绿，但 bug 从没被抓到 | 从未注入失败验证 | S1 |
| 编辑器全过、出包后行为不同 | 没在 release 产物上跑 | S2 |
| 不知从何时起测试不再验证 | 断言机制未随环境复核 | S3 |
| 测试全红但流水线全绿 | 退出码链路失效 | S4 |
| 基线齐全但回归持续放行 | 基线是错的（含全黑图） | S5 |
