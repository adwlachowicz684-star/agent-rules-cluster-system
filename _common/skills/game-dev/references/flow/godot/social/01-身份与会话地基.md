# 01 身份与会话地基（社交域）

> **本步交付**：独立于 peer ID 的玩家身份 + 控制面 / 数据面分离
> **对应**：流程 `howto/godot/social.md` · 审核 `audit/godot/social.md`

## 0. 交付物定义

1. 玩家身份由认证服务下发，⛔ 与 Godot 的 peer ID 无关
2. 社交控制面走 HTTPS / WebSocket，战斗数据面走 ENet / WebSocket
3. 权威推导自"两端一致的东西"，⛔ 不用本地 peer ID 自证

## 1. 前置检查清单

- [ ] 已选定认证方式（平台账号 / 自建）
- [ ] 服务端有会话令牌与过期策略
- [ ] ⚠ 已确认社交状态存服务端，不存客户端
- [ ] 已确认控制面与数据面的进程可以分开部署

## 2. 工序

### Step 1　先确认 Godot 不内置任何社交服务　`[social/01#S1]`

【读】`howto/godot/social.md#0. ⚠ Godot 不内置任何社交服务`

【做】
在设计文档开头写明：Godot **不内置**匹配服务、好友关系、持久公会、邮件、公告或聊天服务器。
ENet 也只是**基于 UDP 的传输层**，不是完整的 P2P 服务网络 ——
它解决不了"陌生玩家怎么报名""两个对称 NAT 后的玩家如何会合""房主关机后历史记录去哪"。
⛔ 在 GDScript 里找 `Matchmaking` / `Lobby` 节点 —— 不存在，且不会有报错提示。

【产出】架构约束：这些能力**全部自建或接第三方**，不由引擎提供

【判据】指着大厅、好友、聊天任一功能，能说出它由哪个服务提供。

【审】`audit/godot/social.md#1`

### Step 2　peer ID 不能当玩家身份　`[social/01#S2]`

【读】`howto/godot/social.md#1. 三层架构（推荐）`

【做】
服务端 ID **恒为 1**、客户端是随机正整数，每次重连都变。
所以身份必须由**认证与会话层**（HTTPS）下发，社交状态以玩家 ID 为键。
⛔ 拿 `multiplayer.get_unique_id()` 当"这个玩家是谁" ——
断线重连后 id 变了，好友关系、战绩、邮件全断。
⛔ 把好友列表存本地 —— 换设备就没了，且可被改。

【产出】玩家 ID 与 peer ID 的映射表（服务端持有）+ 社交状态以玩家 ID 为键

【判据】杀掉客户端重连，好友列表、邮件、战绩与断线前完全一致。

【审】`audit/godot/social.md#11`

### Step 3　权威必须推导自两端一致的东西　`[social/01#S3]`

【读】`howto/godot/social.md#2.1 ⚠ 权威与身份的三条官方语义（多人）`

【做】
spawner 把 avatar 命名为所属 peer id，各端用 `name.to_int()` 推出同一个答案。
⛔ 在 `_ready()` 里写 `set_multiplayer_authority(multiplayer.get_unique_id())` ——
该脚本在**每个 peer 上、对每个 avatar 都跑一遍**，
于是每个 peer 都在本地声称拥有全部角色，
表现为"每个客户端都在驱动所有角色"，而本地 authority 检查全是绿的。
⛔ 以为 `recursive` 能让后加入的子节点也继承 ——
它只对**调用时已存在的子树**生效。
⛔ 以为改了 authority 别人就知道 —— 该调用**不会自我复制**，
必须经 `spawn_function` / RPC / `MultiplayerSynchronizer` 告知。

【产出】权威推导规则（来自节点名）+ 后加子节点的补设规则

【判据】中途 `add_child()` 一个新子节点，它上面的 authority RPC 仍能被正确路由。

【审】`audit/godot/social.md#45`

### Step 4　控制面与数据面分离　`[social/01#S4]`

【读】`howto/godot/social.md#1. 三层架构（推荐）`

【做】
认证与会话、社交控制面（大厅 / 匹配 / 好友 / 组队 / 聊天 / 公会 / 邮件 / 公告 / 举报）
走 HTTPS / WebSocket；进房间后的实时同步走 ENet / WebSocket。
⛔ 把好友关系、邮件、公告塞进战斗进程 ——
房主关机 / 崩溃之后这些状态**随之消失**。
⚠ Web 端无法直接用 ENet，须切 `WebRTCMultiplayerPeer` 或 WebSocket。

【产出】三层职责表 + 各层的部署形态

【判据】杀掉战斗进程甚至换一台机器，好友、邮件、公会公告仍在。

【审】`audit/godot/social.md#13`

### Step 5　UDP 端口转发与 NAT　`[social/01#S5]`

【读】`howto/godot/social.md#0. ⚠ Godot 不内置任何社交服务`

【做】
Godot 高层多人 API **只用 UDP**，对外开服必须转发 **UDP** 端口，不能只转 TCP；
对称 NAT 后的玩家会合要**自建信令服务**，WebRTC 也只是"能穿透"，
⛔ 信令服务器**引擎不提供**，得自己搭。
监听前检查 `create_server()` 的返回值（`ERR_ALREADY_IN_USE` / `ERR_CANT_CREATE`）。
⛔ 只转 TCP —— 表现为"服务端在跑、外网连不上"，且不报错。
⛔ 不看返回值 —— 表现为"服务端看着在跑，但一个连接都接不进来"。

【产出】部署检查清单（UDP 转发 + 返回值检查）+ 信令服务形态

【判据】端口被占用时启动立即失败并给出可区分错误；外网客户端能连入。

【审】`audit/godot/social.md#46`

## 3. 参考实现

```gdscript
# ⓘ 承接本步产出：两端一致的权威推导 + 监听返回值检查
# ⛔ 官方：set_multiplayer_authority 不会自我复制，且 recursive 不覆盖后加子节点
const PORT := 7000
const MAX_PLAYERS := 8

func host() -> Error:
    var peer := ENetMultiplayerPeer.new()
    var err := peer.create_server(PORT, MAX_PLAYERS)
    if err != OK:                       # ⛔ 不检查则"在跑但接不进"
        push_error("监听失败: %d" % err)
        return err
    multiplayer.multiplayer_peer = peer
    return OK

func _on_avatar_ready() -> void:
    # ✅ 从两端一致的节点名推导，而不是本地 peer id
    set_multiplayer_authority(name.to_int())
```

## 4. 验收清单

- [ ] 没有任何一处把 peer ID 当作玩家身份
- [ ] 权威推导自两端一致的节点名
- [ ] 后加子节点的 authority 有补设
- [ ] 杀掉战斗进程后社交状态仍在
- [ ] 开服前有 UDP 端口转发与返回值检查

## 5. 常见返工

| 症状 | 原因 | 回到 |
|---|---|---|
| 每个客户端都能开别人的车 | `_ready()` 里用本地 peer id 设 authority | S3 |
| 重连后好友与战绩全断 | 社交状态以 peer ID 为键 | S2 |
| 外网连不上、本地正常 | 只转了 TCP 或未看返回值 | S5 |
