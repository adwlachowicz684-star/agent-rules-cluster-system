# 03 匹配与排队（社交域）

> **本步交付**：独立匹配分 + 等待超时 + 匹配成功后进房的交接
> **对应**：流程 `howto/godot/social.md` · 审核 `audit/godot/social.md`

## 0. 交付物定义

1. 匹配服务自建或接第三方，⛔ 不由 Godot 提供
2. 匹配分与展示用的战力是两套数，战力**不进**主匹配分
3. 等待有超时与扩展策略，匹配成功后进房有明确交接

## 1. 前置检查清单

- [ ] 已完成 01（身份与会话地基）
- [ ] 已选定匹配维度（MMR / 地区 / 延迟 / 模式）
- [ ] 已确认匹配分存服务端
- [ ] 已定义等待超时与放宽策略

## 2. 工序

### Step 1　先确认 Godot 不提供匹配服务　`[social/03#S1]`

【读】`howto/godot/social.md#3. 匹配`

【做】
匹配要自建或接第三方平台服务（Steam / EOS 等）。
⛔ 指望 ENet 自带撮合 —— 它只是传输层，
表现为"能连上但没有陌生人可连"。
匹配维度先定死：MMR、地区、延迟、模式。

【产出】匹配服务选型 + 维度定义

【判据】两个陌生玩家无需交换 IP 即可被撮合进同一房间。

【审】`audit/godot/social.md#12`

### Step 2　等待与超时：不能让玩家无限等　`[social/03#S2]`

【读】`howto/godot/social.md#3. 匹配`

【做】
给等待设上限，超时后**放宽条件**（地区 → 延迟 → 分数区间）并最终兜底。
⛔ 无限等待 —— 表现为"排队 20 分钟没反应"，玩家已流失。
⛔ 超时后直接判失败而不放宽 —— 低峰期永远排不到人。
⛔ 放宽了不告知玩家 —— 表现为"怎么匹配到这么远的服"，像黑箱。

【产出】超时阈值 + 分档放宽策略 + 对玩家的可见提示

【判据】低峰期单人排队也能在阈值内开局，且玩家看得到放宽提示。

【审】`audit/godot/social.md#52`

### Step 3　战力不进主匹配分　`[social/03#S3]`

【读】`howto/godot/social.md#6.6 战力：总分只负责直觉，匹配必须另建技能估计`

【做】
战力测的是**配置和养成**，不是操作；它只适合新手推荐、装备成长、排行榜展示。
真正匹配用独立 MMR / Elo / Glicko + 近期表现 + 角色熟练度 + 位置 + 延迟。
⛔ 拿战力当匹配分 —— 高分低操作玩家污染队伍，
表现为"队友分数很高但打得极差"，玩家会归因为"匹配有毒"。

【产出】两套数：展示用战力（服务端算并缓存）/ 匹配用 MMR

【判据】改一个只堆无用词条的角色，战力飙升而 MMR 不变。

【审】`audit/godot/social.md#53`

### Step 4　匹配成功到进房的交接　`[social/03#S4]`

【读】`howto/godot/social.md#1. 三层架构（推荐）`

【做】
匹配成功 → 服务端预留房间 → 下发连接票据 → 客户端持票进房 → 核对票据与房间成员一致。
⛔ 把房间号直接给客户端让它自己连 —— 可被猜到并挤进别人的房间。
⛔ 票据不含房间标识 —— 服务端无法判断"这个人是不是这间房的"。

【产出】一次性连接票据 + 进房时的票据核对

【判据】拿别人的票据进房被拒；票据用过一次即失效。

【审】`audit/godot/social.md#54`

### Step 5　组队整体报名，不是各自排队再合房　`[social/03#S5]`

【读】`howto/godot/social.md#3. 匹配`

【做】
组队以**队伍为单位**报名，匹配分取队伍的综合值（不是平均分）。
⛔ 各自排队再尝试合房 —— 五人队可能永远凑不齐同一局。
⛔ 用平均分 —— 一个大带四个新手会持续摧毁对手体验。

【产出】队伍级报名 + 队伍综合分算法（登记在参数表）

【判据】五人队能被整体撮合进同一局；大带小的队伍分数偏向高段。

【审】`audit/godot/social.md#55`

## 4. 验收清单

- [ ] 匹配服务已选定（非引擎提供）
- [ ] 等待有超时与分档放宽，且对玩家可见

## 5. 常见返工

| 症状 | 原因 | 回到 |
|---|---|---|
| 排队很久没反应 | 无超时也无放宽 | S2 |
| 队友分数高但打得差 | 用战力当匹配分 | S3 |
| 陌生人挤进房间 | 房间号可猜、无票据 | S4 |
