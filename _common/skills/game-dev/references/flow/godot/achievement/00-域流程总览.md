# 成就系统 —— 域流程总览

> ⚠ **第 0 步：先定做什么。**
> 本域有 7 个功能点，⛔ **不是全做** —— 按本次需求挑。

## 0. 先定做什么

| 本次要做的 | 走哪些功能点 |
|---|---|
| 只要几个一次性成就 | **不要套本域** → 见下 |
| 成就 + 存进度 | 01 → 02 → 07 |
| 有累计型（击杀 100） | 01 → 02 → 03 → 07 |
| 成就发奖励 | 01 → 02 → 03 → 04 → 07 |
| 有隐藏成就 | 01 → 02 → 05 → 07 |
| 接 Steam / Epic 成就 | 01 → 02 → 04 → 06 → 07 |
| 已上线、新增成就 | 01 → 03 → 07 |
| 全套 | 01 → 02 → 03 → 04 → 05 → 06 → 07 |

⛔ **只在代码里写死几个 `if` 判定的项目不要套本域。**
⚠ 那属于 `howto/godot/onboarding-meta.md#4` 的范围——
本域处理的是**要存档、要发奖、要对接平台、要回溯老号**的复杂度。

ⓘ 分工：
- `howto/godot/achievement.md` 讲**单个要素怎么做**（定义/进度/事件/奖励/展示/平台）
- 本域讲**这些要素按什么顺序做、怎么管状态**

⛔ 若本域某步需要"GodotSteam 怎么初始化"这类细节，
指向 `platform-services.md`，**不在这里重复**。

## 1. 功能点拆解（按依赖，不可颠倒）

| # | 功能点 | 依赖 | 交付物 |
|---|---|---|---|
| 01 | 成就模型定性 | — | 四类成就定型 + id 规则 |
| 02 | 定义与状态分离 | 01 | 定义 Resource + 状态存档两层 |
| 03 | 事件与进度追踪 | 02 | 事件驱动 + 跨会话累计进度 |
| 04 | 解锁与奖励发放 | 03 | 判达成→标记→发奖→通知 事务 |
| 05 | 隐藏成就与展示 | 02 | 标题/进度/是否解锁可见，描述受控 |
| 06 | 平台成就对接 | 04 | 平台 ID 映射 + 失败可重试 |
| 07 | 成就验收 | 全部 | 老号/重放/崩溃/平台失败 实测 |

⚠ **01 必须在一切之前**：类型没定性，02 的进度字段和 04 的判定方式都无从定。
⚠ **02 必须在 03 之前**：没有状态层，进度无处落盘。
⚠ **03 必须在 04 之前**：没有进度与达成判定，发奖没有触发依据。
⚠ **04 必须在 06 之前**：本地解锁都不幂等，推给平台只会放大不一致。

## 2. 与其他域的接缝

| 接缝 | 契约 |
|---|---|
| `narrative` 域 任务链 | 任务完成事件是成就的常见来源 |
| `economy` 域 奖励 | 奖励走经济通道，见 04 |
| `save` 域 存档 | 成就状态进存档，见 02 |
| `netsync` 域 同步 | 进度权威在服务端时客户端只展示 |
| `vip` 域 时间源 | 每日/每周重置类成就同受 `Time` 官方禁令约束 |
| `onboarding-meta` 统计 | 进度常派生自统计，见 03 |

⛔ **若某条接缝对不上，要单独立一个接线功能点**。

## 3. 本域最容易做反的顺序

⛔ **先做解锁弹窗（04）再做定义与状态分离（02）。**

弹窗是最直观的"成就"反馈，
于是先做 UI、先弹通知，
⚠ 而此时成就还是写死在代码里的 `if` →
**读档后进度丢失、改数值后旧存档覆盖新定义**，
⛔ 且不报错，只在更新配置后才暴露。

✅ 正确顺序：先定类型与 id（01），再立定义/状态两层（02），
再让进度跨会话累计（03），最后才谈解锁与发奖（04）。
