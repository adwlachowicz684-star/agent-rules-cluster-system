# 01 交付边界与平台矩阵（CI/CD 与导出发布域）

> **本步交付**：平台矩阵 + 产物清单 + 版本单一数据源
> **对应**：流程 `howto/godot/cicd-publish.md` · 审核 `audit/godot/cicd-publish.md`

## 0. 交付物定义

1. 目标平台矩阵已定，且**写明每个平台的产物形态**
2. 主语言与渲染后端已按平台矩阵确定（⛔ 不是"先写了再说"）
3. 每个平台的产物清单已列出，并指定**谁校验**
4. debug 与 release 被当成**两种产物**分别对待
5. 版本号有**单一数据源**

## 1. 前置检查清单

- [ ] 能用一句话列出目标平台与各平台产物
- [ ] 主语言与渲染后端已按矩阵确定
- [ ] 产物清单里有"校验人"一列，⛔ 不是只写"导出成功"
- [ ] debug 与 release 分开跑，⛔ 不是只测 debug
- [ ] 版本号只有一处定义

## 2. 工序

### Step 1　先定平台矩阵，⛔ 不是先配导出预设　`[cicd-publish/01#S1]`

【读】`howto/godot/cicd-publish.md#3.2 各平台要点`

【做】
先写出平台矩阵：每个平台、产物形态、是否需要签名、是否有商店门槛。
⛔ 先配预设 —— 矩阵一变，语言、渲染后端、纹理格式全部跟着变，
⛔ 表现为"每个平台预设都要重配一遍"，而每次单看都是"加一个新平台"。

ⓘ 矩阵还要写清**谁负责校验产物**：
"导出成功"是命令层面的判断，"产物能启动"是另一个判断，
⛔ 两者在 Godot 里会给出相反的结论（见 06）。

【产出】平台矩阵表（平台 / 产物形态 / 签名需求 / 校验人）

【判据】指着任一平台能说出产物是什么、谁确认它能启动。

【审】`audit/godot/cicd-publish.md#15`

### Step 2　平台矩阵决定主语言与渲染后端，⛔ 这是立项级决定　`[cicd-publish/01#S2]`

【读】`howto/godot/cicd-publish.md#3.4 Web 的限制`

【做】
按矩阵确定主语言与渲染后端：目标是 Web 就不能用 C# 作主语言，
且 WebGL2 没有 normal-roughness buffer，依赖它的后处理在 Web 上不成立。
⛔ 等到渲染阶段才发现 —— 这个决定**后期无法低成本更改**，
⛔ 表现为"桌面版效果做完了，Web 版要整套重做或砍掉"。

ⓘ 判据不是"Web 能不能跑"，是"**Web 上的观感是否可接受**"：
可接受 / 降级后可接受 / 只对桌面发布，⛔ 三者必须明确选一个，
含糊过去会在发布当天变成争论。

【产出】语言与渲染后端决策记录（含 Web 观感的明确结论）

【判据】每个目标平台的渲染特性依赖都有明确结论，无"待定"。

【审】`audit/godot/cicd-publish.md#16`

### Step 3　产物清单要指定校验人，⛔ 不是"导出成功"就结案　`[cicd-publish/01#S3]`

【读】`howto/godot/cicd-publish.md#发布检查清单`

【做】
产物清单里每个平台写清**产物路径、预期形态、校验人与校验方式**。
⛔ 只记"导出命令成功" —— Godot 导出失败仍返回 0，
⛔ 表现为"构建记录全绿，发版当天才发现根本没有产物"。

ⓘ 校验方式要能自动化：至少包含**存在且非空**，
这一步能在 CI 里跑，而"能启动"通常需要人（见 06）。

【产出】产物清单（含每项的自动校验与人工校验分工）

【判据】CI 里有一条对每个产物做存在性与体积校验的步骤。

【审】`audit/godot/cicd-publish.md#17`

### Step 4　debug 与 release 是两种产物，⛔ 不能只测 debug　`[cicd-publish/01#S4]`

【读】`howto/godot/cicd-publish.md#2. CI 流水线`

【做】
把 debug 与 release 当成两条独立产物链：
`--export-debug` 带调试符号与远程调试，`--export-release` 才是要发的。
⛔ 只测 debug —— release 下 `assert` 被剥离、优化行为不同，
⛔ 表现为"debug 一切正常，release 崩溃"，而崩溃点通常不在出问题的代码里。

ⓘ 两条链的差异还包括：release 的导入与导出路径可能不同，
⛔ 用同一份缓存跑两条链会拿到互相污染的结果。

【产出】两条产物链的定义（命令、产物路径、各自的验证方式）

【判据】发布前 release 产物被实际启动过至少一次。

【审】`audit/godot/cicd-publish.md#12`

### Step 5　版本号只有一个数据源　`[cicd-publish/01#S5]`

【读】`howto/godot/cicd-publish.md#版本号`

【做】
版本号只在 `project.godot` 的 `application/config/version` 里定义，
CI 与商店后台都从这里读。
⛔ 散落三处 —— 必然不同步，且**不报错**，
表现为"包里显示 1.2.3、商店写 1.2.4、崩溃日志报 1.2.2"。

ⓘ 代码里用 `ProjectSettings.get_setting("application/config/version")` 读，
⛔ 不要在 CI 里用另一个常量再写一遍 —— 那就是第二处数据源。

【产出】版本号的单一定义与读取方式

【判据】包内、CI 日志、商店后台三处版本号一致。

【审】`audit/godot/cicd-publish.md#14`

## 3. 参考实现

```gdscript
# ⓘ 承接本步产出：版本单一数据源
const VERSION_SETTING := "application/config/version"

static func app_version() -> String:
    return str(ProjectSettings.get_setting(VERSION_SETTING, "0.0.0"))

# ⛔ 不要在 CI 脚本、商店元数据里再各写一份版本号常量
```

```bash
# ⓘ 承接本步产出：两条产物链分开
godot --headless --export-debug   "Windows Desktop" build/debug/game.exe
godot --headless --export-release "Windows Desktop" build/release/game.exe
# ⛔ 两条链不要共用同一个导入缓存目录
```

## 4. 验收清单

- [ ] 平台矩阵已定，各平台产物形态明确
- [ ] 语言与渲染后端按矩阵确定，Web 观感有明确结论
- [ ] 产物清单含校验人与自动校验步骤
- [ ] debug / release 两条链分开，release 被启动过
- [ ] 版本号三处一致

## 5. 常见返工

| 症状 | 原因 | 回到 |
|---|---|---|
| 加一个平台要重配所有预设 | 先配预设后定矩阵 | S1 |
| 桌面做完了 Web 要重做 | 立项没定平台 | S2 |
| CI 全绿但发版没产物 | 只验命令成功 | S3 |
| debug 好、release 崩 | 只测 debug | S4 |
| 包内与商店版本号不一致 | 版本号散落多处 | S5 |
