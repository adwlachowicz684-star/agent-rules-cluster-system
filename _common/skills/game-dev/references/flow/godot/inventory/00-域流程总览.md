# 背包与物品域 — 流程总览

> **本域交付**：一个能装、能取、能堆叠、能移动、能存档、UI 能正确显示的库存系统。
> **对应**：做法 `howto/godot/game-systems.md` `economy.md` `ui.md`
> 　　　审核 `audit/godot/game-systems.md` `ui.md`

---

## 0. 先定做什么（⛔ 没写这三行不许开工）

⚠ 同在背包域，"做一个能装东西的背包"和"做一套支持玩家交易、带负重、可扩容的库存"
是**两条不同流程**。

```text
做什么：<谁持有、装什么、有没有上限>
不做什么：⛔ <至少两条>
验收标准：<可观测的>
```

示例（本次只做基础背包）：

```text
做什么：主角持有一个 20 格背包，能放入/取出/堆叠物品，能存档回读
不做什么：⛔ 不做负重与扩容（见 03 的取舍说明）
         ⛔ 不做玩家交易（见 player-trading）
验收标准：放满后再放会返回实际放入数量而非静默丢弃；
         存档回读后耐久、附魔、堆叠数量全部一致；
         同一 instance_id 在任何时刻只存在于一个槽
```

### 然后挑功能点

| 本次要做的 | 需要的功能点 |
|---|---|
| 只是"能装能取" | 01 → 02 → 07 |
| 要堆叠 / 唯一物品 / 容量策略 | 01 → 02 → 03 → 07 |
| 要拖拽、交换、跨容器移动 | 01 → 02 → 03 → 04 → 07 |
| 要存档 | 01 → 02 → 05 → 07 |
| 要有界面 | 01 → 02 → 06 → 07 |

⛔ **不要全做。**

## 1. 功能点拆解与依赖顺序

```text
01 物品定义与实例 ── 02 库存容器 ──┬── 03 堆叠/唯一/容量 ──┐
                                   ├── 04 移动与原子性 ────┼── 07 背包验收
                                   ├── 05 存档序列化 ──────┤
                                   └── 06 UI 绑定 ─────────┘
```

| # | 功能点 | 前置 | 为什么这个顺序 |
|---|---|---|---|
| 01 | 物品定义与实例 | 无 | ⚠ 模板/实例分离是**整个域的地基**；不做分离，后面每次移动都在复制数据 |
| 02 | 库存容器 | 01 | 容器装的是实例 id，先有实例才有容器 |
| 03 | 堆叠/唯一/容量 | 02 | 堆叠是放入算法的分支，先有 `add()` 才有分支可加 |
| 04 | 移动与原子性 | 02 03 | ⚠ 移动的"试算再提交"依赖放入算法的返回值 |
| 05 | 存档序列化 | 02 | slots 与 instances **两个都要存** |
| 06 | UI 绑定 | 02 | UI 订阅容器信号，先有信号才有订阅 |
| 07 | 背包验收 | 01–06 | 链路完整才谈得上验收 |

## 2. ⚠ 四个最容易做反的顺序

**① 槽位直接存物品对象。**
最诱人也最致命。`InventorySlot` 存整个 `ItemInstance`，
移动和交换时深拷贝，**耐久和附魔被复制出多份且不再同步**——
玩家会看到"同一把剑在两个格子里，一个耐久 80% 一个耐久 30%"。
✅ 槽位只存 `instance_id + count`。

**② 先做 UI 再做容器。**
UI 一做出来，所有逻辑都会被塞进 UI 的按钮回调里，
之后想加服务端校验就发现逻辑全在视图层。
✅ 容器先能跑通（用 `print` 验证），再接 UI。

**③ 先加堆叠分支再定"什么能堆"。**
`max_stack = 1` 的装备、唯一物品（`is_unique`）
若走了通用堆叠分支，就会出现两把同 id 神器。
✅ 堆叠规则是**物品定义的一部分**，不是放入算法的特判。

**④ 交易/移动边改边判定。**
先扣 A 再加 B，中途失败 → 物品既在原处又在新处，或两边都没了。
⚠ **这是不可逆的脏数据**。✅ 先试算、全部通过再提交。

## 3. 每做完一个功能点必做

1. 跑一遍该步的**验收清单**，逐条打勾
2. ⛔ 有没过的，不进下一步
3. 过该步【审】列的 audit 条目
4. 过功能点末尾的「整体审核」节
5. ⚠ 实测参数已回填，⛔ 不留示例值
