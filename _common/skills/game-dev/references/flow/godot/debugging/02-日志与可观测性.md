# 02 日志与可观测性（调试域）

> **本步交付**：分级日志 + 一个在 release 下也活着的自定义监视器 + 埋点可关
> **对应**：流程 `howto/godot/debugging.md` · 审核 `audit/godot/debugging.md`

## 0. 交付物定义

1. 日志按级别走，发布版不打调试级
2. 自定义监视器已注册，**名字带斜杠分类**
3. 取值函数**足够轻**（它每次查询都会被调用）
4. 埋点有统一开关，能一次性关掉
5. 已知哪些内建监视器在 release 下**恒为 0**

## 1. 前置检查清单

- [ ] 全局搜裸 `print(`（参与逻辑的部分）结果为 0
- [ ] 自定义监视器名字都带 `/`
- [ ] 监视器取值函数里没有 `get_nodes_in_group` 一类的全树扫描
- [ ] 有一个开关能关掉全部业务埋点
- [ ] 已书面记下 release 下恒为 0 的内建项

## 2. 工序

### Step 1　日志分级，别满屏 print　`[debugging/02#S1]`

【读】``howto/godot/debugging.md#2. 日志``

【做】
按级别走日志，`print` 只留给临时排查且**不留进提交**。
⛔ 不要用 `print` 当日志系统 —— 它没有级别，发布版里照样打，
⛔ 而每帧 `print` 会**让性能数据失真**（audit #6），
于是"加了日志之后变卡"和"本来就卡"分不开。

ⓘ 分级还有一层：
⛔ **`print` 未刷新时崩溃，最后一行日志会骗人**（audit #1） ——
它指向的是崩之前的某处，不是崩溃点。
⛔ 所以崩溃场景要么用即时刷新，要么就别信最后一行。

【产出】日志分级函数 + 级别常量

【判据】发布版构建里调试级日志条数为 0。

【审】``audit/godot/debugging.md#6``

### Step 2　自定义监视器：这是 release 下唯一活着的指标　`[debugging/02#S2]`

【读】``howto/godot/debugging.md#4.5 自定义性能监视器（官方机制，可带进发布版）``

【做】
用 `Performance.add_custom_monitor()` 注册业务指标，**名字带斜杠**决定分类。
⛔ 不要用无斜杠的名字 —— 官方明确无斜杠一律归入泛化 `Custom` 类，
⛔ 与别人的埋点混在一起，排查时找不到自己的那一条。

ⓘ 这条是本域最有价值的一条：
官方明确 `get_custom_monitor()` **在 debug 与 release 下都可用**，
而 `MEMORY_STATIC` 一类内建项**在 release 恒为 0**（audit #4）。
⛔ 所以在导出版上靠内建项查泄漏，得到的是"没问题"的假象。

【产出】`add_custom_monitor` 注册点（带分类前缀）

【判据】release 导出版里能读到该指标；⛔ 名字含 `/`。

【审】``audit/godot/debugging.md#14``

### Step 3　取值函数必须轻：它每次查询都会跑　`[debugging/02#S3]`

【读】``howto/godot/debugging.md#4.5 自定义性能监视器（官方机制，可带进发布版）``

【做】
取值函数只做 O(1) 读取，⛔ 不要在里面做全树扫描或 IO。
⛔ 官方明确：该函数**每次查询监视器时都会被调用**（编辑器内约每秒一次）。
在里面放 `get_nodes_in_group().size()` 这类操作，
监视器本身就成为性能问题 —— ⛔ 而它只在开了监视器时才卡，
于是"开着调试就卡"被当成"调试器 overhead"，不会想到是自己写的取值函数。

ⓘ 计数类指标**自己维护计数器**，不要每次去数：
⛔ 数出来的是"当前值"，自维护的也是"当前值"，
后者 O(1)，前者随场景规模线性增长。

【产出】O(1) 取值函数（自维护计数器）

【判据】取值函数里无循环、无 `get_nodes_in_*`、无文件 IO。

【审】``audit/godot/debugging.md#15``

### Step 4　负值会被静默钳成 0　`[debugging/02#S4]`

【读】``howto/godot/debugging.md#4.5 自定义性能监视器（官方机制，可带进发布版）``

【做】
跟踪"增量 / 差值"这类可正可负的量时，**拆成两个非负监视器**，
或加一个固定偏移让它恒为正。
⛔ 不要直接把差值丢给自定义监视器 —— 官方明确
**custom monitors 不支持负值，负值会被静默钳到 0**。
⛔ 表现是"资源一直在泄漏，但监视器图上是一条平稳的 0"，
而它**不报错**，是最像"没问题"的一种错。

ⓘ 这条与"钳到 0"的另一半也有关：
⛔ 0 还是个**看着完全正常的值**，不像 `null` 或负数那样会引人怀疑，
所以它是静默失败里最难被察觉的一类。

【产出】差值指标的拆分或偏移方案（书面的）

【判据】构造一次负向变化，监视器上能看到它（不是 0）。

【审】``audit/godot/debugging.md#13``

### Step 5　埋点有统一开关，能一次性关掉　`[debugging/02#S5]`

【读】``howto/godot/debugging.md#3.3 自定义埋点``

【做】
业务埋点挂在一个总开关下，测完能整体关掉。
⛔ 不要埋完就留着 —— **埋点本身会成为性能问题**（audit #11），
⛔ 而它是在"测量"的名义下加进去的，最容易被默认保留到发布版。

ⓘ 采样窗口也要定：
⛔ 窗口过短读不到周期性抖动，过长又会把尖峰平均掉。
`MONITOR_SAMPLE_WINDOW` 要按"想看多长周期的现象"来定，
⛔ 而不是随手取 60 或 100。

【产出】埋点总开关 + 采样窗口常量

【判据】关掉开关后，埋点相关调用数为 0。

【审】``audit/godot/debugging.md#11``


## 3. 参考实现

```gdscript
# ⓘ 本块内自足：常量在此声明，承接上文即可直接用
const MONITOR_SAMPLE_WINDOW := 120    # 采样窗口（帧）（02 参数表登记）
const LOG_FLUSH_INTERVAL := 1.0       # 日志刷盘间隔（秒）（02 参数表登记）
const DELTA_OFFSET := 1000000         # 差值偏移：保证恒为正（02 参数表登记）

var _enemy_count := 0                 # ⓘ 自维护计数器，取值函数 O(1)
var _spawned_total := 0
var _freed_total := 0
var _probe_enabled := true

func _ready() -> void:
    # ⛔ 名字必须带斜杠：斜杠决定分类，无斜杠归入泛化 Custom 类
    Performance.add_custom_monitor("game/enemies", _get_enemy_count)
    # ⛔ 差值类指标：拆成两个非负量，不直接喂差值（负值会被钳到 0）
    Performance.add_custom_monitor("game/spawned", _get_spawned)
    Performance.add_custom_monitor("game/freed", _get_freed)

func _get_enemy_count() -> int:
    return _enemy_count               # ⛔ O(1)：不在这里做全树扫描

func _get_spawned() -> int:
    return _spawned_total + DELTA_OFFSET

func _get_freed() -> int:
    return _freed_total + DELTA_OFFSET

func log_at(level: int, msg: String) -> void:
    if not _probe_enabled and level > 1:
        return                        # ⛔ 总开关：测完能整体关掉
    match level:
        0: print(msg)
        1: push_warning(msg)          # ⓘ 进调试器 Errors 标签，带栈帧
        _: push_error(msg)
```

## 5. 常见返工

| 现象 | 返工到 |
|---|---|
| 加了日志之后变卡，分不清真假 | 返工 Step 1（每帧 print） |
| 导出版查泄漏得到"没问题" | 返工 Step 2（用了 release 下恒 0 的内建项） |
| 开着调试就卡 | 返工 Step 3（取值函数做了全树扫描） |
| 泄漏很久但监视器一直是 0 | 返工 Step 4（差值被钳成 0） |
| 埋点留到发布版 | 返工 Step 5（没有总开关） |
