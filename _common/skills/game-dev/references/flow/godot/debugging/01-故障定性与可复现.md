# 01 故障定性与可复现（调试域）

> **本步交付**：故障归入正确的类 + 一份最小复现 + 一份环境记录
> **对应**：流程 `howto/godot/debugging.md` · 审核 `audit/godot/debugging.md`

## 0. 交付物定义

1. 故障被归入四类之一：崩溃 / 卡死 / 性能 / 仅在导出版出现
2. 有一份**别人照着做就能复现**的步骤（≤ `REPRO_MAX_STEPS` 步）
3. 环境记录：引擎版本、渲染器、平台、是否 debug 模板
4. 已知"什么情况下不复现"也写下来了
5. 定性结论有**证据**，不是"看着像"

## 1. 前置检查清单

- [ ] 已确认是崩溃、卡死、掉帧，还是只在导出版出现
- [ ] 能在**干净启动**（不带上次存档/缓存）下复现
- [ ] 已记录引擎版本与渲染方法（Forward+ / Mobile / Compatibility）
- [ ] 已确认 debug 模板下是否同样复现
- [ ] "不复现的条件"已写下来（⛔ 它比复现条件更容易被忽略）

## 2. 工序

### Step 1　先分四类，别急着下断点　`[debugging/01#S1]`

【读】``howto/godot/debugging.md#0. 先分清故障类型``

【做】
先给故障归类，再选工具：
**崩溃**看栈；**卡死**看执行权在谁手上；**掉帧**看帧时间分解；
**仅在导出版出现**看编辑器替你做了什么。
⛔ 不要四类都从下断点开始 —— 断点在线程代码里**根本不会命中**（官方），
于是得到"这段代码没执行"这个**错误结论**，⛔ 且不报任何错。

ⓘ 归类还有一层容易漏的：
⛔ **"偶发"本身就是信息** —— 偶发通常指向时序、线程、或未初始化内存，
而必然复现多指向逻辑。把偶发当必然去查，会一直在逻辑里找不存在的分支。

【产出】故障分类（书面）+ 打算用的工具

【判据】能说清"为什么不是另外三类"，而不只是"看着像这一类"。

【审】``audit/godot/debugging.md#12``

### Step 2　收敛到最小复现　`[debugging/01#S2]`

【读】``howto/godot/debugging.md#0. 先分清故障类型``

【做】
把复现步骤砍到 ≤ `REPRO_MAX_STEPS` 步，且**每一步都是必需的**。
⛔ 不要停在"进游戏玩一会儿就崩" —— 这种描述无法验证修没修好，
也无法变成回归用例，⛔ 于是修完只能靠"多玩一会儿没崩"来判断。

ⓘ 砍步骤的过程本身常常就是定位过程：
⛔ 砍到某一步发现不复现了，那一步就是成因线索，
跳过它直接去猜成因会丢掉这条最省力的证据。

【产出】最小复现步骤（可交给别人执行）

【判据】换一个人照着做也能复现；⛔ 步骤数 ≤ `REPRO_MAX_STEPS`。

【审】``audit/godot/debugging.md#12``

### Step 3　记录环境：版本、渲染器、平台、模板　`[debugging/01#S3]`

【读】``howto/godot/debugging.md#4.7 Visual Profiler 的四条读数前提``

【做】
记下引擎版本、渲染方法（Forward+ / Mobile / Compatibility）、
导出模板类型（debug / release）、目标平台。
⛔ 不要只记"我这儿能复现" —— 官方明确 Visual Profiler 的
**分类项随渲染方法不同而不同**，⛔ 换渲染器后横比出来的"改善"没有意义。

ⓘ 同一条还有另一半：官方注明结果**随视口分辨率剧烈变化**，
⛔ 所以不同次运行要对比，必须锁定同一视口尺寸 ——
否则会得出"优化后反而更差"或"优化大成功"两种**同样不可信**的结论。

【产出】环境记录表（一次填写，后续每步复用）

【判据】别人按这份记录能搭出等价环境。

【审】``audit/godot/debugging.md#21``

### Step 4　把"什么情况下不复现"也写下来　`[debugging/01#S4]`

【读】``howto/godot/debugging.md#4. 常见故障的定位流程``

【做】
显式记录不复现的条件（新档不复现、窗口化不复现、关掉某开关不复现）。
⛔ 不要只记复现条件 —— "关掉某开关就不复现"往往是**最直接的定位线索**，
而它因为"不是 bug 的表现"被当成无关信息丢掉。

ⓘ 这条还有防甩锅的作用：
⛔ 卡死与掉帧在玩家视角都是"游戏不动了"，
记录不清就会两边各查一遍，而**两者的排查路径完全不同**。

【产出】不复现条件清单

【判据】每条不复现条件都能对应到一个可开关的变量。

【审】``audit/godot/debugging.md#12``

### Step 5　定性要有证据，不是"看着像"　`[debugging/01#S5]`

【读】``howto/godot/debugging.md#3.4 区分 CPU 瓶颈还是 GPU 瓶颈``

【做】
用**可复现的测量**支撑定性结论，而不是凭手感。
⛔ 不要把"感觉卡"直接写成"性能问题" —— 官方明确
**只看 FPS 无法区分 CPU 瓶颈还是 GPU 瓶颈**，
⛔ 而两者的优化方向**完全相反**，方向错了会做一堆无效优化。

ⓘ 最快的判别法是官方那条：
⛔ **降渲染缩放** —— 帧率明显上升是 GPU 瓶颈，几乎不变是 CPU 瓶颈。
这一步几乎零成本，却能避免后面走错整条路。

【产出】定性结论 + 支撑它的测量数据

【判据】结论能被一次独立测量复现；⛔ 定性为性能后**转到 `perf` 域**，本域到此为止。

【审】``audit/godot/debugging.md#5``


## 3. 参考实现

```gdscript
# ⓘ 本块内自足：常量在此声明，承接上文即可直接用
const REPRO_MAX_STEPS := 7          # 最小复现步骤上限（01 参数表登记）
const ENV_KEYS := ["engine_version", "renderer", "template", "platform"]

var _env: Dictionary = {}
var _repro_steps: Array = []
var _not_repro: Array = []

func record_env() -> void:
    _env["engine_version"] = Engine.get_version_info().get("string", "")
    # 渲染方法：project.godot 的 rendering/renderer/rendering_method
    _env["renderer"] = ProjectSettings.get_setting(
        "rendering/renderer/rendering_method", "forward_plus")
    _env["template"] = "debug" if OS.is_debug_build() else "release"
    _env["platform"] = OS.get_name()

func add_repro_step(what: String) -> void:
    _repro_steps.append(what)
    # ⛔ 超过上限说明还没收敛到最小，继续砍而不是继续记
    assert(_repro_steps.size() <= REPRO_MAX_STEPS)

func add_not_repro(condition: String) -> void:
    _not_repro.append(condition)

func dump() -> String:
    return JSON.stringify({
        "env": _env,
        "repro": _repro_steps,
        "not_repro": _not_repro,
    }, "  ")
```

## 4. 验收清单

- [ ] 故障已归入四类之一，且能说清为什么不是另外三类
- [ ] 复现步骤 ≤ `REPRO_MAX_STEPS` 步，换人可复现
- [ ] 环境记录含版本、渲染器、模板、平台
- [ ] 不复现条件已记录
- [ ] 定性结论有测量支撑（不是"看着像"）

## 5. 常见返工

| 现象 | 返工到 |
|---|---|
| 断点没命中，以为代码没执行 | 返工 Step 1（很可能跑在线程里） |
| 修完说不清修没修好 | 返工 Step 2（没有最小复现） |
| 换台机器结论就反了 | 返工 Step 3（渲染器/视口未锁定） |
| 卡死与掉帧来回甩锅 | 返工 Step 4（未记录不复现条件） |
| 优化做了一堆没效果 | 返工 Step 5（CPU/GPU 没分清） |
