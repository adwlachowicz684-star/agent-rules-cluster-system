# 05 导出版专属故障（调试域）

> **本步交付**：编辑器与导出包的差异清单 + 每个动态路径都有存在性检查
> **对应**：流程 `howto/godot/debugging.md` · 审核 `audit/godot/debugging.md`

## 0. 交付物定义

1. 已知哪些内建监视器在 release 下恒为 0
2. 动态 `load()` 路径全部有存在性检查
3. 已知导出期资源转换会影响运行时读取
4. `assert` 不用于 release 期校验
5. 有一份"只在导出版做"的检查清单

## 1. 前置检查清单

- [ ] 全局搜 `load(` 的动态路径都有 `ResourceLoader.exists` 前置
- [ ] 无依赖 `MEMORY_STATIC` 一类 debug-only 指标的发布逻辑
- [ ] 无依赖 `assert` 做发布期校验
- [ ] 已知文本资源转二进制的导出设置状态
- [ ] 导出版跑过一次完整流程（不是只跑主菜单）

## 2. 工序

### Step 1　先建差异清单，别猜　`[debugging/05#S1]`

【读】``howto/godot/debugging.md#只在导出版出现``

【做】
书面列出编辑器与导出包的所有已知差异，逐项过。
⛔ 不要凭"编辑器正常"推断导出版也正常 ——
⛔ 编辑器会替你做导入、转换、缓存，
而导出包里这些**都不发生**，⛔ 且不报错，只表现为"功能没了"。

ⓘ 这份清单是**可复用资产**：
⛔ 每次只在出问题时临时列一遍，列的内容会随当时印象而变，
⛔ 于是同一个坑会在不同人手里重复踩。

【产出】差异清单（书面，可持续补充）

【判据】清单里的每一项都在导出版实测过一次。

【审】``audit/godot/debugging.md#8``

### Step 2　动态 load 路径必须有存在性检查　`[debugging/05#S2]`

【读】``howto/godot/debugging.md#只在导出版出现``

【做】
每个运行时拼出来的路径，先 `ResourceLoader.exists()` 再 `load()`。
⛔ 不要直接 `load(res://... % name)` ——
编辑器里文件在，导出包里**可能根本没有被包含进去**
（未被任何场景静态引用的资源不一定进包），
⛔ 表现为"编辑器完美、出包后这块功能没了"，⛔ 且不报"路径不存在"之外的任何错，
而那条错常常被 try 吞掉。

ⓘ 还有同源的一条：
⛔ 导出期**文本资源转二进制**的开关会影响运行时读取 ——
文件确实在包里，只是**读不出来**，⛔ 这种比"文件不在"更难查，
因为 `exists()` 会返回 `true`。

【产出】动态加载的存在性检查 + 失败时的明确提示

【判据】构造一个不存在的路径，能看到明确报错而不是静默回退。

【审】``audit/godot/debugging.md#8``

### Step 3　release 下恒为 0 的指标不能用来判健康　`[debugging/05#S3]`

【读】``howto/godot/debugging.md#3.1 用 Monitor 看总量``

【做】
把 release 下恒为 0 的内建项列出来，发布逻辑一律不依赖它们。
⛔ 不要用 `MEMORY_STATIC` / `OBJECT_ORPHAN_NODE_COUNT` 在发布版查泄漏 ——
官方明确这些是**debug-only，在 release 导出后恒返回 0**（audit #4）。
⛔ 表现是"查了，没问题"，而泄漏一直在发生，
⛔ 这是最坏的一种错：**测量手段本身在目标环境里失效**。

ⓘ 替代方案就是 02 那条：
⛔ 自定义监视器（`add_custom_monitor`）官方明确**在 release 下也可用**，
这才是导出版上唯一活着的指标来源。

【产出】debug-only 指标清单（书面）

【判据】发布逻辑里对这些项的引用数为 0。

【审】``audit/godot/debugging.md#4``

### Step 4　assert 不能当发布期校验　`[debugging/05#S4]`

【读】``howto/godot/debugging.md#2. 日志``

【做】
`assert` 只用于开发期不变量，发布期校验走显式分支 + 日志。
⛔ 不要用 `assert` 校验运行时数据 —— **它在 release 里被剥离**（audit #2），
⛔ 校验**静默消失**，表现是"开发期拦得住的错误，发布版全都放过去了"。

ⓘ 这条的隐蔽之处在于：
⛔ 剥离是**静默**的，不会报"assert 不可用"，
⛔ 于是开发期看到的严格校验给人一种"这里有保护"的安全感，
而发布版里那道门根本不存在。

【产出】`assert` 使用约定（只用于不变量）+ 发布期校验分支

【判据】发布版里触发一次该错误，能看到日志且走了降级分支。

【审】``audit/godot/debugging.md#2``

### Step 5　导出版跑完整流程，不是只跑主菜单　`[debugging/05#S5]`

【读】``howto/godot/debugging.md#只在导出版出现``

【做】
出包后跑一遍**完整**流程，包含存档、读档、切场景、动态加载。
⛔ 不要只跑到主菜单就认为导出成功 ——
绝大多数导出专属故障发生在**动态加载与持久化**路径上，
⛔ 而这些路径在主菜单阶段**一次都不会执行**。

ⓘ 完整跑一遍还有个额外收益：
⛔ 它同时覆盖了"权限"与"工作目录"这类平台差异，
这些在编辑器里**永远不发生**，只在真机/导出版出现（audit #12）。

【产出】导出版冒烟清单

【判据】清单每项在真机导出版上通过；⛔ 不只在编辑器通过。

【审】``audit/godot/debugging.md#12``


## 3. 参考实现

```gdscript
# ⓘ 本块内自足：常量在此声明，承接上文即可直接用
const RELEASE_ONLY_ZERO := ["MEMORY_STATIC", "MEMORY_STATIC_MAX",
                            "OBJECT_ORPHAN_NODE_COUNT"]

func load_dynamic(path: String) -> Resource:
    # ⛔ 先查存在性：导出包里未被引用的资源可能根本没进包
    if not ResourceLoader.exists(path):
        push_error("资源不存在（导出包可能未包含）：%s" % path)
        return null
    var r := load(path)
    if r == null:
        # ⛔ exists() 为 true 仍可能读不出：文本资源转二进制后读不了
        push_error("资源存在但加载失败（检查导出期文本转二进制设置）：%s" % path)
    return r

func check_health_release() -> void:
    # ⛔ 不能用 debug-only 指标判健康：release 下恒为 0（audit #4）
    # ⓘ 改用自己的自定义监视器：官方明确 release 下也可用
    var enemies := Performance.get_custom_monitor("game/enemies")
    if enemies == 0:
        push_warning("自定义监视器未注册或返回 0，检查分类名是否带斜杠")
    # ⛔ assert 在 release 被剥离，发布期校验必须走显式分支
    if not is_instance_valid(_critical_node):
        push_error("关键节点失效（发布期校验，非 assert）")
```

## 4. 验收清单

- [ ] 差异清单每项都在导出版实测过
- [ ] 构造不存在路径能看到明确报错
- [ ] 发布逻辑对 debug-only 指标的引用数为 0
- [ ] 发布版触发一次错误能看到日志且走降级
- [ ] 导出版冒烟清单覆盖存档/读档/切场景/动态加载

## 5. 常见返工

| 现象 | 返工到 |
|---|---|
| 编辑器完美、出包后功能没了 | 返工 Step 2（动态 load 无检查） |
| 查了泄漏说没问题，但一直在涨 | 返工 Step 3（用了 release 恒 0 的指标） |
| 开发期拦得住、发布版全放过 | 返工 Step 4（用 assert 做发布校验） |
| 主菜单正常就算导出通过 | 返工 Step 5（没跑完整流程） |
