# 03 断点与远程调试（调试域）

> **本步交付**：断点能命中 + 远程能连上 + 已知线程里断点不生效
> **对应**：流程 `howto/godot/debugging.md` · 审核 `audit/godot/debugging.md`

## 0. 交付物定义

1. 断点能命中，且**已确认目标代码不在线程里**
2. 远程调试连得上（端口格式正确）
3. 两种断点的持久化范围已分清
4. 命令行调试开关至少用过一次
5. 断点未命中时知道该往哪查，而不是改判"代码没跑"

## 1. 前置检查清单

- [ ] 目标代码确认不在 `Thread` / 子线程组里
- [ ] 远程调试地址带 `tcp://` 前缀
- [ ] 已知 gutter 断点与 `breakpoint` 关键字的持久化范围不同
- [ ] 用过一次 `--debug-collisions` 之类的可视化开关
- [ ] 断点未命中时不直接下"代码没执行"的结论

## 2. 工序

### Step 1　先确认目标代码不在线程里　`[debugging/03#S1]`

【读】``howto/godot/debugging.md#1. 断点``

【做】
下断点前先确认这段代码跑在哪个线程。
⛔ 不要在线程代码里下断点 —— 官方 Warning 明确：
**GDScript 调试器不会在线程中运行的代码上中断**。
⛔ 表现是断点永远不命中，于是得出"这段代码没执行"的**错误结论**，
而实际它一直在跑，⛔ 且不报任何错。

ⓘ 这条的排查成本特别高：
⛔ 断点不命中以后，人会去查"是不是条件没满足""是不是函数没被调用"，
走进逻辑排查的死路，而真因在**执行环境**上。

【产出】目标代码的执行线程（书面的）

【判据】断点命中一次；⛔ 未命中时先排除线程，再怀疑逻辑。

【审】``audit/godot/debugging.md#24``

### Step 2　远程调试：`tcp://` 前缀不能省　`[debugging/03#S2]`

【读】``howto/godot/debugging.md#远程调试``

【做】
用 `--remote-debug tcp://127.0.0.1:6007` 起进程再连调试器。
⛔ 不要写成裸 `127.0.0.1:6007` —— 官方的格式是
`--remote-debug < remote debug (://[:]) >`，即 `tcp://` 是协议部分。
⛔ 少了前缀连不上，而症状是"调试器一直等连接"，
⛔ 排查会被引向防火墙和端口占用，不会想到是格式。

ⓘ 端口本身也有坑：
⛔ 多实例同时开会**撞端口**（`REMOTE_DEBUG_PORT`），
表现为"连上了但断点是别人那个进程的"。

【产出】可用的远程调试启动命令（记进项目文档）

【判据】真机/另一进程上能连回本机调试器。

【审】``audit/godot/debugging.md#3``

### Step 3　两种断点，持久化范围不同　`[debugging/03#S3]`

【读】``howto/godot/debugging.md#两种断点，用途不同``

【做】
分清两种断点：点 gutter 建的**跨编辑器重启保留**，
`breakpoint` 关键字写的**随脚本进版本控制、跨机器保留**。
⛔ 不要把两者当一回事 —— 需要团队共用或长期保留的断点用关键字，
⛔ 用 gutter 的会**只存在于自己机器上**，别人打开项目看不到，
于是"我这儿能断，他那儿不能"被当成环境差异排查一遍。

ⓘ 反过来也有一条：
⛔ 关键字断点写进脚本就有**被提交到发布版**的风险，
⛔ 而 gutter 断点不会。所以临时断点优先用 gutter。

【产出】断点使用约定（书面）

【判据】需要跨机器复用的断点在脚本里；⛔ 临时断点不在脚本里。

【审】``audit/godot/debugging.md#25``

### Step 4　命令行开关：不改代码就注入条件　`[debugging/03#S4]`

【读】``howto/godot/debugging.md#4.6 命令行调试开关（不用改代码就能注入条件）``

【做】
优先用命令行开关造条件，而不是临时改代码。
⛔ 不要为了看一眼碰撞体就去改代码加 `draw` ——
用 `--debug-collisions` / `--debug-paths` / `--debug-navigation` / `--debug-avoidance`。
⛔ 改代码造条件的代价是**测完还要改回去**，
而忘了改回去的调试代码经常一路进发布版。

ⓘ 模拟低端机用 `--frame-delay`：
⛔ 但官方明确它用于**模拟高 CPU 负载**，**不要当帧率限制用**，限帧是 `--max-fps`。
⛔ 用前者限帧会把 CPU 时间一起算进去，性能数据失真。

【产出】常用命令行开关清单（记进项目文档）

【判据】造这些条件不需要改代码。

【审】``audit/godot/debugging.md#22``

### Step 5　Visual Profiler 的读数前提　`[debugging/03#S5]`

【读】``howto/godot/debugging.md#4.7 Visual Profiler 的四条读数前提``

【做】
读 Visual Profiler 前先满足四个前提：目标帧率、视口尺寸、Fit to Frame、渲染器。
⛔ 不要直接读百分比列 —— 官方明确目标帧时间
**硬编码为 16.67ms（60FPS）**，⛔ 非 60 目标的项目（VR 90fps、移动端锁 30）
百分比**全部失真**，只能看毫秒值。

ⓘ 另外三条同样会得出"可信的错误结论"：
⛔ 视口尺寸不同则不可比；⛔ 有尖峰要关 Fit to Frame；
⛔ 分类项随渲染器不同而不同，跨渲染器横比无意义；
⛔ 停止运行后结果还在，**退出编辑器就没了** —— 要留证先截图。

⛔ 还有一条最容易被误读：Visual Profiler **只测渲染相关的 CPU 时间**，
**不含脚本与物理**（audit #7）—— 脚本耗时要看 Profiler 标签。

【产出】Visual Profiler 读数检查表

【判据】每次读数前四项前提都勾选过。

【审】``audit/godot/debugging.md#18``


## 3. 参考实现

```gdscript
# ⓘ 本块内自足：常量在此声明，承接上文即可直接用
const REMOTE_DEBUG_PORT := 6007       # 远程调试端口（03 参数表登记）

func remote_debug_cmd() -> String:
    # ⛔ 协议前缀不能省：官方格式是 tcp://host:port
    return "godot --remote-debug tcp://127.0.0.1:%d --path ." % REMOTE_DEBUG_PORT
```

```bash
# 常用命令行调试开关（不改代码造条件）
godot --debug-collisions --path .        # 显示碰撞体
godot --debug-navigation --path .        # 显示导航多边形
godot --frame-delay 8 --path .           # ⛔ 模拟高 CPU 负载；限帧用 --max-fps
godot --max-fps 30 --path .              # 限帧（0 = 不限）
godot --single-threaded-scene --path .   # 场景树单线程（排查线程相关）
godot --print-fps --path .               # 帧率打到 stdout
```

## 4. 验收清单

- [ ] 断点命中一次，且已确认目标不在线程里
- [ ] 远程调试命令带 `tcp://`，能连上
- [ ] 跨机器复用的断点用关键字，临时的用 gutter
- [ ] 造常用调试条件不需要改代码
- [ ] Visual Profiler 读数前四项前提都过过

## 5. 常见返工

| 现象 | 返工到 |
|---|---|
| 断点永不命中，以为代码没跑 | 返工 Step 1（跑在线程里） |
| 调试器一直等连接 | 返工 Step 2（地址缺 `tcp://`） |
| 我这儿能断、别人那儿不能 | 返工 Step 3（用了 gutter 断点） |
| 调试代码进了发布版 | 返工 Step 4（没用命令行开关） |
| 优化前后对比结论不可信 | 返工 Step 5（四项前提未满足） |
