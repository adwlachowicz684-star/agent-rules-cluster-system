# 07 调试验收与防复发（调试域）

> **本步交付**：回归用例 + 判据固化 + 观测不残留
> **对应**：流程 `howto/godot/debugging.md` · 审核 `audit/godot/debugging.md`

## 0. 交付物定义

1. 至少 `REGRESSION_CASE_MIN` 条回归用例，且**修复前跑过并失败**
2. 验收判据写成"执行什么、期望什么"，含环境约束
3. 排查期加的日志 / 埋点 / 可视化已清理或挂总开关
4. 编辑器 / 导出版 / 真机三处都跑过完整流程
5. 本次成因已写进差异清单，且带判别特征

## 2. 工序

### Step 1　回归用例要先在修复前失败　`[debugging/07#S1]`

【读】``howto/godot/debugging.md#0. 先分清故障类型``

【做】
把最小复现变成可自动跑的用例，**先在修复前跑一次确认它失败**。
⛔ 不要修完才写用例 —— 修完写的用例**永远通过**，
⛔ 于是它证明不了任何事，却给人一种"这里有保护"的安全感。
这是最难发现的无效用例：**它绿着，但什么都没测**。

ⓘ "修复前失败"还有第二重作用：
⛔ 它能确认用例**真的碰到了那个成因**，
⛔ 否则可能出现"用例通过但根本没走到出错路径"，
这种用例在回归里是纯噪声。

【产出】≥ `REGRESSION_CASE_MIN` 条用例 + 修复前的失败记录

【判据】用例在**故意回退修复**后会失败。

【审】``audit/godot/debugging.md#26``

### Step 2　判据要能复跑，不是"看着没问题"　`[debugging/07#S2]`

【读】``howto/godot/debugging.md#3.4 区分 CPU 瓶颈还是 GPU 瓶颈``

【做】
把验收判据写成"执行什么、期望什么"，并写明环境约束。
⛔ 不要把"跑起来不卡了"当判据 —— 它不可复跑、不可比对，
⛔ 而"卡不卡"在不同机器、不同视口尺寸下**可以完全相反**
（官方：Visual Profiler 结果随分辨率剧烈变化）。

ⓘ 判据里要**写明环境**：
⛔ 不写视口尺寸与渲染器的性能判据，在别人机器上跑出来的是**另一个结论**，
⛔ 而这会被误读成"优化效果不稳定"，而不是"判据没写全"。

【产出】可复跑判据（含环境约束）

【判据】换一台机器按判据执行，得到同一结论。

【审】``audit/godot/debugging.md#19``

### Step 3　临时观测要清理或挂开关　`[debugging/07#S3]`

【读】``howto/godot/debugging.md#3.3 自定义埋点``

【做】
排查期加的日志、埋点、可视化，收尾时清理或挂总开关。
⛔ 不要留着不管 —— **埋点本身会成为性能问题**（audit #11），
⛔ 而它是以"调试需要"的名义加的，最容易被默认保留，
⛔ 于是上线后带着一批没人再看的观测在跑。

ⓘ 清理也要覆盖**命令行开关**那一类：
⛔ 用 `--debug-collisions` 造的条件不会留在代码里（这正是它的价值），
⛔ 而为看效果临时改的代码会 —— 所以优先用开关就是为了少一处要清理的。

【产出】临时观测清单（已清理或已挂开关）

【判据】关闭总开关后，调试期新增调用数为 0。

【审】``audit/godot/debugging.md#11``

### Step 4　编辑器 / 导出版 / 真机各验一次　`[debugging/07#S4]`

【读】``howto/godot/debugging.md#只在导出版出现``

【做】
在导出版与真机上各跑一遍完整流程，顺序是编辑器 → 导出版 → 真机。
⛔ 不要只在编辑器验证就收尾 —— **真机不复现不代表没问题**（audit #12），
真机有性能、权限、平台差异，⛔ 而这些差异在编辑器里**永远不出现**。

ⓘ 顺序也有讲究：
⛔ 跳过中间层直接上真机，出问题会分不清是**导出配置**还是**平台差异**，
⛔ 而这两者的修法完全不同。

【产出】三处验证记录

【判据】三处都通过；⛔ 任一处不通过则回到对应功能点。

【审】``audit/godot/debugging.md#12``

### Step 5　把成因写进差异清单，带判别特征　`[debugging/07#S5]`

【读】``howto/godot/debugging.md#4. 常见故障的定位流程``

【做】
把本次成因补充进 05 的差异清单与项目文档，**带判别特征**。
⛔ 不要修完就结束 —— 同一类坑会在不同人手里重复踩，
⛔ 而"我踩过但没写下来"等于别人还要再踩一次，
⛔ 更糟的是**自己也会再踩**，因为印象会随项目切换而淡掉。

ⓘ 写的时候要带**判别特征**，不只是结论：
⛔ 只写"记得检查 X"没有可操作性，
⛔ 而"表现为 A、排查会被引向 B、真因是 C"才会在下次被认出来。

【产出】清单更新（含判别特征）

【判据】清单里能按"表现症状"反查到成因。

【审】``audit/godot/debugging.md#12``


## 3. 验收清单

- [ ] 用例在故意回退修复后会失败（不是"修完才写的永远绿的用例"）
- [ ] 判据含环境约束，换机执行得到同一结论
- [ ] 关闭总开关后调试期新增调用数为 0
- [ ] 编辑器 / 导出版 / 真机三处完整流程都通过
- [ ] 成因已写进差异清单，且能按"表现症状"反查
- [ ] 本次定性结论有测量支撑，不是"看着像"

## 4. 常见返工

| 现象 | 返工到 |
|---|---|
| 用例一直绿但 bug 又出现 | → `07#S1`（修后写的用例） |
| 换台机器结论就变 | → `07#S2`（判据没写环境） |
| 上线后带着一堆观测在跑 | → `07#S3`（临时埋点没清） |
| 编辑器过、真机炸 | → `07#S4`（跳过中间层） |
| 同一个坑第二次踩 | → `07#S5`（没写进清单） |
| 断点没命中以为代码没跑 | → `03#S1`（跑在线程里） |
| 导出版查泄漏得到"没问题" | → `05#S3`（用了 release 恒 0 的指标） |
| 崩溃栈里找不到成因 | → `06#S1`（get_node 静默返回 null） |
