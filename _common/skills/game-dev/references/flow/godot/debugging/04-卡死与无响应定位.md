# 04 卡死与无响应定位（调试域）

> **本步交付**：执行权归属清楚 + 死循环与 await 悬挂已区分 + 有超时兜底
> **对应**：流程 `howto/godot/debugging.md` · 审核 `audit/godot/debugging.md`

## 0. 交付物定义

1. 卡死时能说清执行权在谁手上
2. 死循环与 `await` 悬挂**已明确区分**
3. 所有 `await` 都有超时或已知信号源
4. 有看门狗能在卡住时留下证据
5. 主线程被占满的情形能被识别

## 1. 前置检查清单

- [ ] 全局搜 `await` 的每个调用点都有明确的信号源
- [ ] 无 `while true` 一类无出口循环（或有明确出口条件）
- [ ] 有超时兜底的 `await` 已列出
- [ ] 看门狗能在 `HANG_WATCHDOG_SEC` 后留下记录
- [ ] 已知哪些操作会占满主线程

## 2. 工序

### Step 1　先分死循环还是悬挂　`[debugging/04#S1]`

【读】``howto/godot/debugging.md#卡死不报错``

【做】
先看 CPU：占满是死循环，躺平是 `await` 悬挂。
⛔ 不要两类都用"加日志"去查 —— 死循环下日志会**刷屏到看不清**，
悬挂下则**一条新日志都没有**，
⛔ 两种情形下加日志都得不到信息，还把现场污染了。

ⓘ 这个区分之所以重要：
⛔ 两者的修法完全相反 —— 死循环要加出口条件，
悬挂要保证信号一定会发。判错了会往没有 bug 的那边一直改。

【产出】卡死类型（书面）+ CPU 占用证据

【判据】能用一次 CPU 观测区分两者；⛔ 不靠猜。

【审】``audit/godot/debugging.md#9``

### Step 2　`await` 必须知道等的是谁　`[debugging/04#S2]`

【读】``howto/godot/debugging.md#卡死不报错``

【做】
每个 `await` 都写清等的是哪个信号、谁会发它。
⛔ 不要 `await` 一个可能永远不来的信号 —— 官方/audit 明确：
**`await` 无信号源会永久悬挂，且不报错**（audit #9）。
⛔ 表现是"这一步之后就没有任何反应了"，
而排查时代码看着完全正常，因为 `await` 本来就是合法的。

ⓘ 最隐蔽的一种：
⛔ 信号源节点在 `await` 期间被 `queue_free()` 了 ——
信号永远不会来，⛔ 而没有任何东西提示"你在等一个已经没了的对象"。

【产出】`await` 清单（含信号源与发送者）

【判据】每个 `await` 都能指出"谁保证这个信号一定会发"。

【审】``audit/godot/debugging.md#9``

### Step 3　给悬挂加超时兜底　`[debugging/04#S3]`

【读】``howto/godot/debugging.md#卡死不报错``

【做】
关键路径的 `await` 用 `AWAIT_TIMEOUT_SEC` 加超时分支。
⛔ 不要裸 `await` 关键流程 —— 悬挂时**没有任何提示**，
玩家侧表现为"卡在加载界面"，⛔ 而服务端/日志侧**一切正常**，
这类问题几乎只能靠玩家反馈发现。

ⓘ 超时分支要**走降级而不是假装成功**：
⛔ 超时后继续往下走，会把"没等到"当成"等到了但没数据"，
⛔ 而这正是 audit #10 那条 —— 失败与空数据走了同一分支。

【产出】带超时的 `await` 封装 + 降级路径

【判据】人为让信号不来，能在 `AWAIT_TIMEOUT_SEC` 后走到降级分支。

【审】``audit/godot/debugging.md#10``

### Step 4　看门狗：卡住时要留下证据　`[debugging/04#S4]`

【读】``howto/godot/debugging.md#3.3 自定义埋点``

【做】
挂一个独立计时，超过 `HANG_WATCHDOG_SEC` 就记录当前阶段标记。
⛔ 不要卡住之后才想办法观测 —— **复现场即消失**，
⛔ 事后再查只剩"它卡住了"这个事实，没有任何指向成因的线索。

ⓘ 看门狗要记的是**阶段标记**，不是栈：
⛔ 卡死时取栈本身可能就取不到（主线程被占满），
而阶段标记是**在卡之前**写下的，一定能拿到。

【产出】看门狗 + 阶段标记写入点

【判据】人为注入一次长耗时，看门狗能留下最后一个阶段标记。

【审】``audit/godot/debugging.md#11``

### Step 5　主线程被占满要能识别　`[debugging/04#S5]`

【读】``howto/godot/debugging.md#3.2 帧时间分解``

【做】
能区分"主线程被自己的代码占满"与"在等外部"。
⛔ 不要把"主线程在跑重活"当成卡死 —— 帧时间分解里它显示为
`process` 项异常高，⛔ 而死循环会让它**无限高**，
两者在玩家视角都是"不动了"，但**修法完全不同**。

ⓘ 还有一条容易混：
⛔ 同步 `load()` 大资源会造成**一次性长卡顿**，
它在帧时间分解里是一个孤立尖峰，**不是持续增长**，
⛔ 当成泄漏去查会白查一整轮。

【产出】主线程占用情形的判别表

【判据】给出一次卡死，能说清是无限循环、一次性长任务，还是悬挂。

【审】``audit/godot/debugging.md#5``


## 3. 参考实现

```gdscript
# ⓘ 本块内自足：常量在此声明，承接上文即可直接用
const HANG_WATCHDOG_SEC := 5.0      # 卡死看门狗阈值（秒）（04 参数表登记）
const AWAIT_TIMEOUT_SEC := 10.0     # 悬挂探测超时（秒）（04 参数表登记）

var _stage := "init"
var _watchdog_t := 0.0
var _timed_out := false

func set_stage(s: String) -> void:
    # ⓘ 阶段标记是在"卡之前"写下的，卡死后一定拿得到（栈不一定）
    _stage = s
    _watchdog_t = 0.0

func _process(delta: float) -> void:
    _watchdog_t += delta
    if _watchdog_t > HANG_WATCHDOG_SEC:
        push_warning("watchdog: 阶段 %s 已 %.1fs 未推进" % [_stage, _watchdog_t])
        _watchdog_t = 0.0            # ⛔ 重置避免刷屏，但不丢失阶段名

# ⛔ 关键路径不要裸 await：永久悬挂不报错（audit #9）
func await_with_timeout(sig: Signal, timeout_sec: float = AWAIT_TIMEOUT_SEC) -> bool:
    var t := 0.0
    while not _timed_out and t < timeout_sec:
        if sig.get_connections().is_empty():
            push_error("await 目标无任何连接，信号永不会来")
            return false
        await get_tree().process_frame
        t += get_process_delta_time()
    _timed_out = t >= timeout_sec
    return not _timed_out             # ⛔ 超时走降级，不能当成"等到了但没数据"
```

## 4. 验收清单

- [ ] 能用 CPU 占用区分死循环与悬挂
- [ ] 每个 `await` 都能指出信号由谁保证发出
- [ ] 人为让信号不来，能走到超时降级分支
- [ ] 人为注入长耗时，看门狗留下最后阶段标记
- [ ] 能区分无限循环、一次性长任务、悬挂

## 5. 常见返工

| 现象 | 返工到 |
|---|---|
| 加日志后刷屏或一条都没有 | 返工 Step 1（没先分死循环/悬挂） |
| 卡在加载界面但日志一切正常 | 返工 Step 2（await 无信号源） |
| 超时后当成空数据继续走 | 返工 Step 3（降级与成功混同） |
| 卡住后只剩"它卡住了" | 返工 Step 4（没装看门狗） |
| 一次性长卡顿被当泄漏查 | 返工 Step 5（没看帧时间分解） |
