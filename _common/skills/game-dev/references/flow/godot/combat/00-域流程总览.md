# 战斗结算域 — 流程总览

> **本域交付**：一次攻击从"发起"到"伤害落地、状态改变、反馈播完"的完整链路。
> **对应**：做法 `howto/godot/combat.md` `vfx-feel.md` `projectile.md`
> 　　　审核 `audit/godot/combat.md`

---

## 0. 先定做什么（⛔ 没写这三行不许开工）

⚠ **流程是从需求派生的，不是固定的。** 同在战斗域，
"给主角加一个能打怪的攻击"和"做一套有格挡招架的对抗系统"
是**两条完全不同的流程**，走的功能点集合不一样。

开工前写下：

```text
做什么：<一句话，说清"谁对谁、在什么时机、造成什么结果">
不做什么：⛔ <至少两条>
验收标准：<可观测的，不是"能打">
```

示例（本次只做基础攻击）：

```text
做什么：主角按攻击键 → 挥剑 → 命中范围内敌人 → 扣血 + 受击反馈
不做什么：⛔ 不做格挡/招架/处决（对抗层，见 06）
         ⛔ 不做联网（见 netsync-advanced）
验收标准：一次按键只造成一次伤害，命中同帧多个敌人各结算一次，
         帧率从 30 到 240 判定结果完全一致
```

### 然后挑功能点

| 本次要做的 | 需要的功能点 |
|---|---|
| 只是"能打中、能扣血" | 01 → 02 → 07 |
| 有前后摇、要手感 | 01 → 02 → 03 → 05 → 07 |
| 有 buff / 中毒 / 灼烧 | 01 → 02 → 04 → 07 |
| 有格挡 / 霸体 / 处决 | 01 → 02 → 06 → 07 |

⛔ **不要全做。** 全做 = 做出需求外的东西 + 浪费。

## 1. 功能点拆解与依赖顺序

```text
01 命中判定 ──┬── 02 伤害结算 ──┬── 03 帧数据与判定窗 ──┐
              │                 ├── 04 Buff 与状态 ─────┼── 07 战斗验收
              │                 ├── 05 打击感反馈 ──────┤
              │                 └── 06 对抗层 ──────────┘
```

| # | 功能点 | 前置 | 为什么这个顺序 |
|---|---|---|---|
| 01 | 命中判定 | 无 | ⚠ **先有"命中事件"才有后面一切**。没有 AttackContext，02–06 全是在各自形状上重复造轮子 |
| 02 | 伤害结算 | 01 | 结算的输入就是 01 产出的 AttackContext |
| 03 | 帧数据与判定窗 | 01 02 | 判定窗是"什么时候开 hitbox"，要先有 hitbox |
| 04 | Buff 与状态 | 02 | buff 改的是结算输入；顺序反了会出现"改了数值却没生效" |
| 05 | 打击感反馈 | 02 | 反馈由"结算结果"驱动，先有结果才有反馈 |
| 06 | 对抗层 | 02 04 | ⚠ 硬直/霸体/格挡都是**改写结算结果**，必须建立在结算管线之上 |
| 07 | 战斗验收 | 01–06 | 只有链路完整才谈得上验收 |

## 2. ⚠ 四个最容易做反的顺序

**① 在碰撞回调里直接写伤害。**
最常见也最致命。`Area2D.body_entered` 里扣血、播特效、发死亡广播——
当时最快，等策划加一条"被格挡时不耗蓝、触发弹反且不进冷却"，
你要把**所有武器的回调改一遍**。
✅ 回调只做一件事：把几何结果包成 `AttackContext` 交给结算层。

**② 先调数值再定结算顺序。**
结算顺序（闪避→格挡→暴击→乘区→抗性→应用）没定死就调数值，
顺序一改全部作废。✅ 顺序是骨架，数值是皮肉。

**③ 先做打击感再做结算。**
hitstop、震屏、粒子都依赖"这一击到底是什么结果"（普通/暴击/格挡/闪避）。
结果还没定就做反馈，做完发现每个结果分支都要重做一遍。

**④ 用计时器对齐动画和判定。**
"第 0.3 秒开 hitbox" —— 动画一改时长，时间点全错。
✅ 用 **Call Method Track** 在 active 帧开判定。

## 3. 每做完一个功能点必做

1. 跑一遍该步的**验收清单**（第 4 节），逐条打勾
2. ⛔ 有没过的，不进下一步
3. 过该步【审】列的 audit 条目（步骤级即时检查）
4. 过功能点末尾的「整体审核」节（功能点级复查）
5. ⚠ 数值参数实测后**回填**，⛔ 不留文档示例值
