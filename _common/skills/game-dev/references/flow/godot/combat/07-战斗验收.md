做完这一步，应该能**当场演示**：

1. 一次完整战斗：发起 → 命中 → 结算 → 反馈 → 状态变化 → 死亡，全程无异常
2. ⚠ 极端帧率（30 / 240）下行为一致
3. ⚠ 连续战斗 5 分钟后不泄漏、不卡死、数值不漂移

## 2. 工序

### Step 1　串一遍完整链路　`[combat/07#S1]`

【读】`howto/godot/combat.md#0. 四层分离` 的事件流

【做】从输入到死亡完整走一遍，逐段确认：

```
Input → Brain → StateMachine → Ability.try_cast()
  → 播动画 → Call Method Track 开 hitbox/发射线
    → 收集候选目标 → CombatResolver.resolve_hit()
      → 属性与状态 → 伤害信号 → 受击反馈
```

⚠ 在**每一段之间**加临时日志，确认数据形态符合预期。
⛔ 只看最终血量——中间哪一段变形了看不出来。

【产出】完整链路的日志，每段输出可核对

【判据】⚠ 一次攻击的日志里，`attack_id` 全程一致，`resolve_hit` 调用次数 == 命中目标数

【审】`audit/godot/combat.md#5`（attack_id 去重）

### Step 2　帧率一致性　`[combat/07#S2]`

【读】`howto/godot/combat.md#3. 帧数据` 的固定步长原则

【做】把帧率上限设成 **30**，跑一遍固定连招；再设成 **240**，跑同一段。

⚠ 三处最容易跟渲染帧走：命中判定（01）、DoT 扣血（04）、硬直衰减（06）。

【产出】两组结果记录

【判据】⚠ **命中结果、DoT 总伤害、硬直总时长，三项在 30 与 240 下完全一致**
（任何一项不一致就是有逻辑挂在 `_process` 上）

【审】`audit/godot/combat.md#3` `#8`

### Step 3　长时间稳定性　`[combat/07#S3]`

【读】`howto/godot/combat.md#5. Buff / Debuff` 与 `#8.2 霸体 / 韧性`

【做】连续战斗 5 分钟（或用脚本模拟 5000 次攻击），观察：

- 内存/节点数是否单调增长（状态、特效没清理）
- `Engine.time_scale` 是否始终是 1.0（hitstop 泄漏）
- 数值是否漂移（float 累加、衰减没 floor）

⚠ 这三类问题**短时间测试看不出来**，是最典型的"上线后才炸"。

【产出】5 分钟前后的对比数据

【判据】⚠ 节点数不单调增长；结束时 `time_scale == 1.0`；数值无漂移

【审】`audit/godot/combat.md#9`（状态残留）`#13`（hitstop 不恢复）

### Step 4　可扩展性验证　`[combat/07#S4]`

【读】`howto/godot/combat.md#6. 技能系统` 与 `#8.7 Godot 实现`

【做】**只通过 Inspector**（不改代码）加：
1. 一个新武器（不同帧数据、不同伤害）
2. 一个新状态（不同叠加规则）

⚠ 这条是"解耦做得对不对"的**硬指标**——
做不到说明有逻辑写死在代码里，以后每次加内容都要改核心。

【产出】两个新内容可用，且 diff 里**没有**核心文件改动

【判据】⚠ `git diff` 里只多了两个 `.tres`，⛔ 没有 `.gd` 改动

【审】`audit/godot/combat.md#10` `#36` `#39`

### Step 5　接缝复查（跨域）　`[combat/07#S5]`

【读】`structure.md#5. 组合模型`

【做】若本域是更大功能的一部分（如"完整战斗系统"含 AI、UI、音频），
列出接缝清单并逐条确认：

| 接缝 | 上游产出 | 下游期望 | 一致? |
|---|---|---|---|
| 伤害数值 → 血条 | `damage_applied` 信号 | UI 订阅 | |
| 受击 → 受击动画 | `response` 返回码 | 动画状态机 | |
| 死亡 → 掉落/结算 | `HitResponse.DEAD` | 其他系统 | |

⚠ **各域合格 ≠ 拼起来能用。** 接缝对不上要单独立适配步骤，
⛔ 不要在各处偷偷转格式（那些转换以后找不到）。

【产出】接缝清单，每行标注"一致"或"已适配"

【判据】⚠ 每行都有明确结论，⛔ 没有"应该没问题"

【审】`audit/godot/combat.md#39`（靠事件解耦）
