# 经济系统与长线进度（Godot 4.7.2）

"天赋树""养成"此前 **0 命中**。本文讲大型项目的经济与长线系统。

## 0. 地基：货币不能只是一个 int

⚠ **多货币、来源追踪、上限** —— 后期加货币种类时，单 int 要改所有调用点。

⚠ **单一数据源**：所有改货币的地方必须走同一个入口，否则对不上账。

⚠ **浮点不能碰货币**（精度问题），但加成计算又绕不开浮点。
解法不是"全程用 int"，而是**把两层彻底分开**：

```
货币与计数 = 整数域
加成的乘区管线 = 浮点域
两者只在一个明确的转换点相接
```

事务与日志：出问题要能查账。

## 1. 掉落系统

**核心不是"抽一个"，而是"如何定义一次抽取"** ——
权重、保底、条件过滤、次数限制共同决定输入（表、上下文、历史）与输出（结果、状态变更）。
边界没划清，代码会退化成敌人脚本里的一堆 `if`。

### 保底（pity）

⚠ **掉落最大的坑不是随机算法，是保底状态的存储与重置。**

- 引擎不会帮你维护"连续未中次数" —— **必须随存档持久化**
- ⚠ **必须与抽卡池绑定**，不能全局共用一个计数器
- `RandomPCG::rand_weighted` **明确禁止负权重**

**期望值要算出来验证** —— 配表时确认概率对不对，而不是靠玩家反馈。

⚠ **客户端算掉落 = 可篡改**。有联机时掉落必须在服务端。

## 2. 商店

⚠ **购买校验放服务端**（如果联机）。
⚠ **失败原因要能区分**：货币不足 / 已达上限 / 已下架 —— 统一报"购买失败"会无从排查。

**限购的本质是"计数 + 周期重置"**。
⚠ 最难的是重置：日按哪时区、周从周几开始、跨周期旧计数怎么处理。
⚠ **限购计数必须容忍"玩家跨周期不在线"**。

## 3. 养成与天赋树

### 崩坏点集中在三处

**① 洗点** —— 必须按「取消分配 → 校验 → 扣点」三步，**且在同一事务内完成**。

**② 依赖检查** ——
⚠ **"最大等级"不是"做多个节点"**，而是节点内部的 `current_rank` / `max_rank` 状态。
拆成 I/II/III 三个节点会导致：前置关系爆炸 + 洗点要按依赖逐级回退极易出错。

**③ 叠加法** —— 见下。

### 加成计算：数值崩坏的头号来源

一个"攻击力 +20%"会因实现方式不同而给出完全不同的结果，
**而策划配表时默认它只有一个含义。**

| 方式 | 公式 | 上例（基础100，两个+20%） |
|---|---|---|
| **加法叠加**（同加区求和） | `Base × (1 + Σb)` | `100 × 1.4 = 140` |
| **乘法叠加**（独立因子相乘） | `Base × Π(1+b)` | `100 × 1.2 × 1.2 = 144` |
| **独立乘区**（不同维度） | `Base × A × C × D × …` | 按区相乘 |

**加法的边际收益递减**：已有 +200% 时再 +20%，提升只有约 6.7%。
→ 适合**投放量大、玩家容易堆高**的基础属性，膨胀可控。

**独立乘区的边际收益恒定**：提升比例永远是 20%，加得越多膨胀越快。
→ **必须严格限制投放渠道与数量上限**，否则后期数值失控。

⚠ **叠加顺序必须固定**：`加区 → 乘区 → 独立乘区`，
否则同样的词条组合会因**重算顺序不同**给出不同结果。

## 4. 装备养成：模板 / 实例 / 词条 / 养成状态四层分离

"强化""升星""洗练""重铸""品阶""词条""分解"此前 **0 命中**。

⚠ **核心不是"属性字段更多"，而是把稳定定义、可变实例、随机结果、经济责任拆成四条互不污染的链路。**

```
EquipmentBase       # 模板：不可变（基础属性范围、槽位、允许的 affix）
EquipmentInstance   # 实例：base_id + instance_id + 词条快照 + 强化 + 镶嵌 + 绑定
AffixSnapshot       # 词条生成后冻结：affix_id + roll（不是最终数值）
BindingState        # 绑定策略 + 所有者 + 来源追溯
```

⚠ **模板不能内嵌进存档。** Godot 的 Resource 会被共享加载，一旦背包存档把模板内联，
两个玩家、两把武器、甚至同一把武器的两次加载可能引用**不同副本**。
→ 存档只写 `base_id` + 可变实例字段，加载时用 `EquipmentRegistry.get_base(base_id)` 解析。
→ **模板 ID 缺失要进隔离区，不能静默用默认武器替换玩家装备。**

⚠ **`instance_id` 必须由服务端生成**（单调递增或雪花 ID），**不能客户端 `randi()`**。
创建装备与写入 `owner_index` 要在**同一事务**内——否则断线重试会造出两件相同装备。

⚠ **词条一旦生成就冻结，只存 `affix_id + roll`，不存最终数值。**
策划改了词条上限后，存最终值的历史装备无法重算；存 roll + `generation_version`
才能区分"故意保留的旧超模装备"与"Bug 装备"。

### 强化：面板成功率 ≠ 玩家总投入

⚠ **失败回退会非线性放大成本。** 同一案例下 12 级强化的期望次数：

| 失败规则 | 期望次数 |
|---|---:|
| 失败等级不变 | 约 31 |
| 50% 回退 1 级 | 约 205 |
| 100% 回退 1 级 | 约 2557 |

→ **"失败掉一级"对普通玩家实质上近似不可达**，不要凭直觉配。

⚠ **保底必须持久化在实例/账号/活动上下文中，并随角色存档。**
"进程变量""内存缓存""每日清零字段"都不是保底。
⚠ **等级、保底计数、材料与货币余额必须在同一事务提交**——先改等级后存保底，崩溃会造成状态撕裂。

⚠ **保护符是替换失败后果，不是叠加概率。** 且不可同时获得"不掉级"和"材料返还"。

⚠ **不能只看均值**：上线前蒙特卡洛 10 万次，输出 P50/P90/P99 材料消耗、最大连续失败、目标等级覆盖率。
（15% 概率下连续 10 次失败约 19.7%——玩家记住的是连败，不是期望。）

⚠ **"幸运值"别这么叫。** 若它是"失败后概率递增"，应命名为**保底进度**，
否则玩家会把它误解为独立概率；且递增概率与硬保底叠加后，就不能再宣称遵守面板概率。

### 洗练 / 重铸：先冻结旧快照，扣费后再切指针

| | 洗练 | 重铸 |
|---|---|---|
| 保留 | 实例 ID、强化等级、镶嵌、锁定词条 | 实例 ID（基础 ID 与强化等级通常也保留） |
| 重投 | 指定槽或全部未锁定词条 | 品阶、词条数量、全部词条 |

⚠ **不能在扣费前覆盖旧数据**，也**不允许客户端无限次"试洗后取消"**——
那等于把服务端随机结果免费预览。预览可接受极少量消耗或一次性令牌。

⚠ **装备数值只能走一个计算器**：
`基础模板 → 等级缩放 → 品阶缩放 → 词条 → 强化 → 镶嵌 → 外部 buff`。
⚠ 最容易崩的是同一词条受两套规则控制（面板显示 12%，实际又乘了品阶和等级）。

### 品阶：约束词条数与上限，不是写死某条属性

品阶分三层，不要混用：
`模板.quality_tier`（可参与的品阶分布）· `实例.quality`（掉落时的生成结果）· `enhance/star`（养成层）。

⚠ **不能因为"升品"就直接把 `quality` 字段改高** —— 同一模板的旧实例会产生不同行为。
品阶升级是**有冷却、材料、失败/保底的事务**；若新槽数少于旧槽数，必须明确"删哪条"
（优先删不能锁定的低优先级词条）。

⚠ 品阶 → 词条槽数是**设计惯例，不是行业标准**，各档槽数以本项目配置为准。

### 掉落表：互斥权重 ≠ 独立概率

⚠ **把 0.5% / 0.3% / 0.2% 当互斥权重填**，实际概率会小于配置；
⚠ **把互斥权重表当独立概率**，玩家可能一次拿到多件。

| 模式 | 语义 | 适用 |
|---|---|---|
| 互斥权重 | `weight / total`，一次出一个 | "这次掉什么基础物品" |
| 独立概率 | 每个入口各自判定 | "每个奖励各自是否命中"，可多命中 |

推荐把"掉不掉"与"掉什么"分开：基础物品池（互斥权重）→ 品质表定品阶 → 词条池生成词条 → 稀有入口再嵌套额外池。

⚠ **权重不需要人工归一化到 100**，但**池内权重改错会让某物品长期消失**——改表后要模拟验证。

### 分解：防通胀边界

⚠ **分解返还是最容易算错的通胀源**：返还 ≥ 获取成本会让玩家刷分解套利。

- 明确**什么能分解**：绑定物品、已装备物品、活动物品通常不能
- 返还按**当前养成状态**折算，不是按模板原价
- ⚠ 分解与强化/洗练共用同一事务与审计日志

## 5. 任务/成就与长线

⚠ **任务条件不要每帧轮询** —— 事件驱动。

⚠ **长线系统唯一可靠的时间源是服务器 UTC** ——

> **每日/每周/赛季重置的边界怎么定**（服务器时区、夏令时、补算、周期标识下发）
> 见 `time-progression.md`。
客户端本地时间不可信（可改系统时钟、跨时区、夏令时切换会让"每天 5 点重置"缺一天或多一天）。
`Time.get_unix_time_from_system()` 返回 UTC 时间戳，应作为唯一依据。
