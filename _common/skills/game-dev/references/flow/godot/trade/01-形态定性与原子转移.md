## 0. 交付物定义

⚠ **本步最容易"看起来做完了"：能发一个 RPC 把东西从 A 挪到 B 就行。**

⛔ 常见假完成：每种形态各写一套转移代码（摆摊一份、拍卖一份、邮件一份）——
⚠ 功能全对、界面也正常，
⛔ 但**五套背包五种漏洞**，修一个 bug 要改五处，且总有漏改的。

做完这一步，应该能**当场演示**：

1. 加一种新交易形态（如"赠礼"）**不改转移逻辑**
2. ⛔ 钱包、挂单、邮件的权威**全在服务端**，客户端改不动
3. ⛔ 同一笔写操作重发两次，**只生效一次**
4. ⚠ 客户端断线重连后，本地缓存被服务端状态**整体替换**
5. ⛔ 客户端**没有**"先扣物品再等确认"的半权威路径

**产出物**（下游按名字对接）：

```text
TransferAsset(source_owner, source_location,
              destination_owner, destination_location,
              asset_ref, expected_version, reason, trace_id)
MarketService / MailService / GuildVaultService  ← 共享同一 owner
```

## 2. 工序

### Step 1　⛔ 先选形态；"支持直接交易"不是"省一个拍卖行"　`[trade/01#S1]`

【读】`howto/godot/player-trading.md#0. 五种形态：先选形态，再谈实现`

【做】按项目选形态，并把**不做的理由**写进设计文档。

⛔ 把"开放直接交易"理解成"省一个拍卖行" →
两者是不同取舍：拍卖行给**价格发现与异步流动性**，
直接交易给**议价、以物易物、赠与与即时交付**。
⚠ 表现为"有了拍卖行，玩家还是抱怨不能当面送装备"。

【产出】形态清单 + 未选形态的理由

【判据】⛔ 每个未做的形态都有一条**明确理由**，不是"以后再说"

【审】`audit/godot/player-trading.md#3`

### Step 2　⛔ 五种形态共用一个原子转移操作　`[trade/01#S2]`

【读】`howto/godot/player-trading.md#0. 五种形态：先选形态，再谈实现`

【做】只写一个 `TransferAsset()`，所有形态都调它；
同一实例**同时只能有一个权威位置**，任何新状态先建不可变历史记录再更新索引。

⛔ 各写一套 → 五套背包五种漏洞，修一处漏四处；
⚠ 且"双卖""重复发货"这类 bug 会在**形态交界处**集中出现（如邮件取的货又挂单）。

【产出】`TransferAsset()` + 不可变历史记录

【判据】⛔ 全局只有一个资产转移函数；跨形态转移也走它

【审】`audit/godot/player-trading.md#1`

### Step 3　⚠ 交易代码不直接改背包表，要共享服务化 owner　`[trade/01#S3]`

【读】`howto/godot/player-trading.md#0. 五种形态：先选形态，再谈实现`

【做】交易逻辑通过统一的 `owner` 服务访问库存，⛔ 不直接读写背包数据结构。

⛔ 直接改背包表 → 托管、锁定、版本校验各写各的，
表现为"从公会仓库取出的物品还能被原主人装备"。

【产出】共享 owner 服务（背包 / 托管 / 邮件 / 公会统一入口）

【判据】⛔ 交易代码里搜不到对背包内部字段的直接赋值

【审】`audit/godot/player-trading.md#2`

### Step 4　⛔ 客户端只发请求；钱包、挂单、邮件权威留服务端　`[trade/01#S4]`

【读】`howto/godot/player-trading.md#10. Godot 实现：只发请求和显示服务端状态`

【做】UI 收集意向 → `any_peer` 命令 RPC → 服务端校验 → `authority` 推状态 → 客户端替换本地缓存。

⛔ 客户端先扣物品、先改货币再等确认 → **没有"半权威"的便利做法**，
断线或被拒时表现为"东西没了但没成交"，且**日志里没有这笔**。
⛔ 即使让玩家权威自己的角色移动，⛔ 也**不能顺带让他权威钱包、挂单或邮件**。

【产出】"客户端请求 / 服务端决定"的单向数据流

【判据】⛔ 客户端不存在"先扣后确认"路径；钱包权威字段在服务端

【审】`audit/godot/player-trading.md#53`

### Step 5　⛔ 写操作 RPC 用 reliable，且必须另加幂等键与结算令牌　`[trade/01#S5]`

【读】`howto/godot/player-trading.md#10. Godot 实现：只发请求和显示服务端状态`

【做】全部写操作 RPC 用 `reliable`；服务端用挂单版本 + 唯一请求 ID + 结算令牌防重。

⛔ 用 `unreliable` 求速度 → 重复扣款、乱序成交、**一次出价应用两次**，全部**不可逆**。
⚠ 但 `reliable` **只保证到达与顺序，不保证幂等**——把它当幂等是最常见的一类误判。
⛔ `client_nonce` 只是**客户端去重键**，⛔ 不能替代服务端 `idempotency_key`。

【产出】`reliable` 写 RPC + 服务端幂等键 + 结算令牌

【判据】⛔ 同一 `idempotency_key` 重发两次，只结算一次

【审】`audit/godot/player-trading.md#47`

## 5. 常见返工

**① 五种都做。** 每种一套代码，漏洞 ×5。

**② 各写一套转移。** 修一处漏四处。

**③ 客户端先扣后确认。** 断线即丢资产。

**④ 玩家权威自己的钱包。** 可直接改余额。

**⑤ 把 reliable 当幂等。** 一次出价应用两次。
