## 0. 交付物定义

⚠ **等级 = f(累充额度)，是派生值。**

⛔ 单独存一份等级 = 两份真相。
表现为"累充够了等级没涨"或"退款了等级还在"——
⛔ 而这类不一致**不报错**，只在玩家投诉时才暴露。

做完这一步，应该能**当场演示**：

1. 增加累充 → 等级**自动**升
2. ⚠ 退款扣回 → 等级**正确回落**（不是不变）
3. ⛔ 存档里**没有**等级字段（只有额度）
4. 改阈值配置 → 等级重算一致
5. ⚠ 重算链**只有一条**（扣回与增加走同一处）

**产出物**（下游按名字对接）：

```text
total_recharge: int         # 唯一真相，存档只存这个
level_of(total) -> int      # 纯函数，由阈值表算
_recompute_level()          # 唯一的重算入口
```

## 2. 工序

### Step 1　⛔ 存档只存额度，不存等级　`[vip/03#S1]`

【读】`howto/godot/vip-subscription.md#5. 等级是派生值，⛔ 不单独存`

【做】只存 `total_recharge`，等级每次由阈值表算出。

⛔ 存两份 → "累充够了等级没涨"，且不报错。

【产出】存档字段（只有额度）

【判据】⚠ 存档里**搜不到**等级字段

【审】`audit/godot/vip-subscription.md#13`

### Step 2　⚠ level_of 是纯函数　`[vip/03#S2]`

【读】`howto/godot/vip-subscription.md#5. 等级是派生值，⛔ 不单独存`

【做】`level_of(total)` 只读阈值表，无副作用。

⛔ 带副作用 → 重算会重复计数，
表现为"每查一次等级，等级就涨一次"。

【产出】`level_of()`

【判据】⚠ 连续调用 10 次**结果不变**

【审】`audit/godot/vip-subscription.md#13`

### Step 3　⛔ 扣回与增加走同一条重算链　`[vip/03#S3]`

【读】`howto/godot/vip-subscription.md#5. 等级是派生值，⛔ 不单独存`

【做】增减额度后都调同一个 `_recompute_level()`。

⛔ 只减额度不重算 → 等级不变；
⛔ 只降等级不减额度 → 下次重算**又升回去**。

【产出】唯一重算入口

【判据】⚠ 退款后等级**正确回落**且再重算不回升

【审】`audit/godot/vip-subscription.md#13` `audit/godot/vip-subscription.md#14`

### Step 4　⚠ 阈值改了要能重算全部玩家　`[vip/03#S4]`

【读】`howto/godot/vip-subscription.md#9. 待核对项（运行时验证）`

【做】阈值变更时按 `total_recharge` 重算，⛔ 不做增量调整。

⛔ 增量调整（"给所有人 +1 级"）会破坏 `level = f(total)` 的等价关系，
之后退款就再也算不对了。

【产出】重算方式（全量）

【判据】⚠ 改阈值后，重算结果与 `level_of(total)` **逐个一致**

【审】`audit/godot/vip-subscription.md#23`

### Step 5　⚠ 旧档迁移要能补出等级　`[vip/03#S5]`

【读】`howto/godot/vip-subscription.md#10. 相关文档`

【做】旧档若只有等级没有额度，迁移时给出额度或标记待定。

⛔ 直接丢弃旧等级 → 老玩家**掉级**，
⛔ 直接用旧等级当真相 → 又回到两份真相。

【产出】迁移策略

【判据】⚠ 老档加载后等级**不低于**迁移前

【审】`audit/godot/vip-subscription.md#14`

## 5. 常见返工

**① 存两份。** 不一致且不报错。

**② 只降等级不减额度。** 重算又回升。

**③ 增量调等级。** 破坏等价关系。

**④ 旧档丢弃。** 老玩家掉级。
