# VIP / 订阅 / 累充 —— 域流程总览

> ⚠ **第 0 步：先定做什么。**
> 本域有 7 个功能点，⛔ **不是全做** —— 按本次需求挑。

## 0. 先定做什么

| 本次要做的 | 走哪些功能点 |
|---|---|
| 只是"有个 VIP 标志，能多领点东西" | 01 → 02 → 07 |
| 有等级（累充分段） | 01 → 02 → 03 → 07 |
| 有月卡/订阅（会到期） | 01 → 04 → 07 |
| 月卡可以续期 | 01 → 04 → 05 → 07 |
| 权益要给多个系统用（掉落/扫荡/商城） | 01 → 06 → 07 |
| 全套 | 01 → 02 → 03 → 04 → 05 → 06 → 07 |

⛔ **不要因为"商业化项目都有"就全做。**
⚠ 04（订阅到期）是复杂度分水岭——
一旦有到期，就要引入服务器时间、硬边界判定、续期叠加，
⛔ 而这些在"只有等级没有到期"时完全不需要。

ⓘ 若本次只是**单次内购**（买一次金币），
那是 `monetization.md` 的事，⛔ 不要套本域——
本域的前提是"有持续状态"。

## 1. 功能点拆解（按依赖，不可颠倒）

| # | 功能点 | 依赖 | 交付物 |
|---|---|---|---|
| 01 | 时间源与到期基准 | — | 服务器权威时间戳 + UTC 约定 |
| 02 | 权益定义与取值 | 01 | 一处定义的权益表 + `get_benefit()` |
| 03 | 累充与等级 | 02 | 只存额度、等级派生的重算链 |
| 04 | 订阅与到期 | 01 | 硬边界判定 + 只改状态不删数据 |
| 05 | 续期与补时 | 04 | `max(end, now) + duration` |
| 06 | 权益接入其他系统 | 02 | 只读接入，不各自判断 |
| 07 | VIP 验收 | 全部 | 改系统时间/时区实测 + 接缝复查 |

⚠ **01 必须在一切之前**：时间基准错了，后面全错，且**症状延迟暴露**。
⚠ **02 必须在 03 之前**：权益没有统一入口，等级只能靠散落的 if 表达。
⚠ **05 依赖 04**：没有到期概念就谈不上续期。

## 2. 与其他域的接缝

> ⚠ **组合的真正难点不是排序，是接缝。**
> 下面每条都必须能指认到具体符号或字段，⛔ 不能是"做完了"。

| 接缝 | 契约 |
|---|---|
| `monetization.md` 支付 | 那篇管**扣款与掉单**；本域只消费"到账后"的状态 |
| `economy.md` 货币 | 累充额度用的货币类型与 economy 一致 |
| `time-progression.md` 时间源 | 三种时间源在那篇；本域只讲**到期用哪个** |
| `datatable.md` 配置 | 等级阈值与权益表进配置，不硬编码 |
| `systems.md` 存档 | 只存额度与到期时刻，⛔ 不存派生等级 |
| `save-migration.md` 迁移 | 阈值结构变更时旧档要能读 |
| `auto-battle.md` 扫荡 | 扫荡次数走 06 的 `get_benefit()`，不自己判等级 |

⛔ **若某条接缝对不上，要单独立一个接线功能点**，
⛔ 不许在各处偷偷转格式（那些转换会散落多处，改接口时找不到）。

⚠ **各功能点自己的验收不能替代集成验收** ——
部件全合格、拼起来不能用，是跨域开发的典型失败。

## 3. 本域最容易做反的顺序

⛔ **先做权益展示（02）再做时间基准（01）。**

"充值后 VIP 图标亮起来"是最直观的验收点，
于是先在客户端写 `if is_vip(): 显示图标`，
而到期判定**先按本地时钟凑合**。

⚠ 后果链：
本地时钟能改 → 玩家改时间图标就亮 →
为了修它又加"上次服务器时间"缓存 →
缓存没有失效路径 → 权益**永久停在旧值**。

⛔ 这些补丁会让 01 再也没法正确落地——
因为到处都已经有了"本地算的 VIP 状态"。

✅ 正确顺序：先把服务器时间基准（01）钉死，再谈权益怎么读（02）。
