# 02 触控事件与多点触控（移动端域）

> **本步交付**：事件流分工 + 手指 index 管理机制
> **对应**：流程 `howto/godot/mobile.md` · 审核 `audit/godot/mobile.md`

## 0. 交付物定义

1. `ScreenTouch` / `ScreenDrag` / 鼠标三类事件的分工已明确
2. 每根手指用 `index` 独立跟踪，⛔ 不共享状态
3. 拖拽与按下抬起的区分逻辑已写清（`is_pressed()` 只在非拖拽时有意义）
4. 多指不重复触发同一全局动作
5. `use_accumulated_input` 的取舍已按玩法定下

## 1. 前置检查清单

- [ ] 三个事件类的职责已分清，无重复消费
- [ ] 手指 `index` 独立跟踪，抬起时能正确回收
- [ ] `is_pressed()` 只在非拖拽事件上使用
- [ ] 已确认多指不会各自触发同一全局动作
- [ ] ⚠ `use_accumulated_input` 已按玩法决定开关
- [ ] 手指抬起在控件外的情况已处理（不会状态泄漏）

## 2. 工序

### Step 1　三个事件类分工，别在同一个处理器里混着判　`[mobile/02#S1]`

【读】`howto/godot/mobile.md#1. 触控事件`

【做】
分清楚 `InputEventScreenTouch`（按下 / 抬起）与 `InputEventScreenDrag`（移动），
各自在独立的分支里处理。
⛔ 把三者混在一个 `if` 链里判断 —— `is_pressed()` **只在非拖拽时才有意义**，
在拖拽事件上读它得到的是无意义的值。

⛔ 表现为"拖动过程中状态反复跳变"，
而排查会被引向逻辑写错，实际只是读了一个不该读的字段。

【产出】事件流分工表：哪个类负责按下、哪个负责移动、哪个负责抬起

【判据】指着每个分支，能说出它只处理哪一类事件、读了哪些字段。

【审】`audit/godot/mobile.md#1`

### Step 2　每根手指用 index 独立跟踪　`[mobile/02#S2]`

【读】`howto/godot/mobile.md#1. 触控事件`

【做】
用 `event.get_index()` 区分手指，每根手指一份独立状态。
⛔ 用单一变量记录"当前触摸点" —— 第二根手指按下时会覆盖第一根的状态，
抬起时又清掉，⛔ 表现为"两指操作时第一指莫名失效"，且不报错。

ⓘ 鼠标没有 index，统一视为 0 即可让两套逻辑共用一条路径。

【产出】以 index 为键的手指状态表

【判据】两指同时按下再依次抬起，两次抬起各自清掉自己的状态、互不影响。

【审】`audit/godot/mobile.md#18`、`audit/godot/mobile.md#30`

### Step 3　手指在控件外抬起要能回收状态　`[mobile/02#S3]`

【读】`howto/godot/mobile.md#1. 触控事件`

【做】
在全局 `_input()` 里监听抬起，不只在该控件的 `_gui_input()` 里处理。
⛔ 只在控件内处理抬起 —— 手指按下后拖到控件外再抬起，
控件永远收不到抬起事件，⛔ 状态卡在"按下"，表现为"松手了还在动"。

⛔ 这类泄漏在一次操作后不会自愈，要下一次按下才被覆盖，
于是 bug 表现为"偶尔卡住"，极难复现。

【产出】抬起事件的兜底回收路径（全局监听）

【判据】按下后拖出控件再松开，状态能被正确回收。

【审】`audit/godot/mobile.md#18`

### Step 4　多指不重复触发同一全局动作　`[mobile/02#S4]`

【读】`howto/godot/mobile.md#多点触控`

【做】
明确哪些动作是"全局只认一次"的（如打开菜单、释放技能），并对 index 做裁决。
⛔ 每个手指都触发一遍全局动作 —— 双指缩放的同时会放两次技能，
⛔ 表现为"缩放时莫名其妙放了技能"，而单指测试完全正常。

ⓘ 裁决规则要写死：通常是"只认第一个按下的手指"或"只认落在特定区域的手指"。

【产出】全局动作的 index 裁决规则

【判据】双指操作时全局动作只触发一次。

【审】`audit/godot/mobile.md#30`

### Step 5　精细拖拽要关掉输入累积　`[mobile/02#S5]`

【读】`howto/godot/mobile.md#1. 触控事件`

【做】
对画线、精确拖拽这类玩法，关闭 `use_accumulated_input`。
⛔ 它是**默认开启**的：引擎会把一帧内的相似输入事件合并，
于是输入回调频率被**限制在渲染帧率**。

⛔ 后果是低帧率下拖拽精度明显下降 —— 而这恰恰发生在最需要精度的低端机上。
表现为"低端机上画不准"，排查会被引向触控屏硬件质量。

【产出】按玩法分档的累积开关说明（哪些界面开、哪些关）

【判据】能说清哪些界面必须关、关了之后低端机上的轨迹是否变密。

【审】`audit/godot/mobile.md#29`

## 3. 参考实现

```gdscript
# ⓘ 承接本步产出：index 独立跟踪 + 全局兜底回收 + 累积按玩法关闭
extends Node

# ⓘ 手指状态以 index 为键，互不覆盖（见 S2）
var _touches: Dictionary = {}

func _ready() -> void:
    # ⓘ 精确拖拽玩法必须关闭累积，否则输入频率被限制到渲染帧率（见 S5）
    Input.use_accumulated_input = false

func _input(event: InputEvent) -> void:
    var idx := 0
    if not (event is InputEventMouse):
        idx = event.get_index()

    var is_drag := event is InputEventScreenDrag or event is InputEventMouseMotion
    var is_press := not is_drag and event.is_pressed()
    var is_release := not is_drag and not event.is_pressed()

    if is_press:
        _touches[idx] = event.position
    elif is_drag:
        if _touches.has(idx):
            _touches[idx] = event.position
    elif is_release:
        # ⛔ 兜底：即使拖出控件外，也要在全局回收（见 S3）
        _touches.erase(idx)
```
