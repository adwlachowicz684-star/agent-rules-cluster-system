# 01 输入架构定性（移动端域）

> **本步交付**：输入形态定死 + 目标设备档位 + 桌面端共存方案
> **对应**：流程 `howto/godot/mobile.md` · 审核 `audit/godot/mobile.md`

## 0. 交付物定义

1. 输入形态已定死（摇杆 / 点触 / 拖拽 / 手势 / 按键），不打算中途改
2. 目标最低设备档位已明确，⛔ 不是"尽量兼容"
3. 桌面端与移动端的共存方式已定，玩家代码里⛔ 没有分平台分支
4. `emulate_mouse_from_touch` 的取舍已明确，不会两套事件重复消费
5. 真机验证设备清单已列出（至少含一台低端机）

## 1. 前置检查清单

- [ ] 输入形态能一句话说清，且能说出为什么不是另一种
- [ ] 最低设备档位已写下（不是"尽量兼容"）
- [ ] 已确认玩家代码里不出现 `OS.get_name()` 之类的分平台输入分支
- [ ] `emulate_mouse_from_touch` 的开关结论已记录，含理由
- [ ] 真机清单已列出，含至少一台低端 Android
- [ ] ⚠ 桌面端是否复用同一套 Input Map 已定

## 2. 工序

### Step 1　先定输入形态，它决定后面所有事件怎么消费　`[mobile/01#S1]`

【读】`howto/godot/mobile.md#0. 先决定输入架构`

【做】
一句话说清玩家用什么操作：虚拟摇杆走位、点触选中、拖拽移动物体、双指缩放、固定按键释放技能。
⛔ 先写摇杆再去想"这游戏该用哪种输入" —— 四种形态的事件消费方式完全不同：
摇杆吃连续方向、点触吃按下抬起、拖拽吃移动轨迹、手势吃多指关系。
⛔ 中途换形态不是改几行，是所有输入代码重写。

⛔ 更要命的是混搭不定性：摇杆和点触同时存在却没定优先级，
玩家拇指放在摇杆上时点触也触发，表现为"技能莫名其妙放出来了"。

【产出】一句话的输入形态描述 + 各形态的优先级顺序

【判据】指着屏幕上每个可触摸区域，能说出它归哪种形态、冲突时谁优先。

【审】`audit/godot/mobile.md#9`

### Step 2　目标设备档位先写死，不写"尽量兼容"　`[mobile/01#S2]`

【读】`howto/godot/mobile.md#8. 移动端性能`

【做】
写下最低支持的设备档位（如"骁龙 6 系 / 4GB 内存 / Android 10"），并据此定渲染后端与画质基线。
⛔ 用"尽量兼容"代替具体档位 —— 没有档位就没有预算，
后面每个"这个效果要不要加"都会变成拍脑袋，最后在低端机上一起爆发。

ⓘ 档位同时决定渲染后端选择：中低端走 `gl_compatibility`，有独显需求走 `mobile`。
⛔ 桌面端 60fps 不代表移动端能跑 —— 这两件事之间没有换算关系。

【产出】最低设备档位 + 对应渲染后端 + 画质基线

【判据】能说出"这个效果要不要加"时，判断依据能追溯到档位表里的一行。

【审】`audit/godot/mobile.md#10`、`audit/godot/mobile.md#41`

### Step 3　桌面端与移动端共用一套 Input Map，玩家代码不分平台　`[mobile/01#S3]`

【读】`howto/godot/mobile.md#4. 输入管理器（推荐架构）`

【做】
把摇杆绑到与键盘、手柄相同的 Input Map 动作上，玩家逻辑统一走 `Input.get_vector()`。
⛔ 在玩家代码里写 `if OS.has_feature("mobile")` 再分两套分支 ——
⛔ 这是后续维护灾难：每加一个操作要改两处，而两边的手感会不知不觉地分叉。

ⓘ 正确分层是：差异只存在于"输入采集层"（摇杆 / 键盘 / 手柄各自产动作），
"输入消费层"（玩家移动、技能释放）永远只有一份。

【产出】输入管理器分层说明：采集层分设备、消费层唯一

【判据】玩家移动代码里 grep 不到任何平台判断。

【审】`audit/godot/mobile.md#9`

### Step 4　`emulate_mouse_from_touch` 的取舍要写下来，不能默认开着不管　`[mobile/01#S4]`

【读】`howto/godot/mobile.md#1. 触控事件`

【做】
明确这个开关是开还是关，并在代码里注明理由。
⛔ 开着它又另外处理触控事件 —— 一次触摸会同时产生鼠标事件和触控事件，
动作**触发两次**，而表现为"点一下放了俩技能"，排查时不会想到是开关问题。

⛔ 反过来，指望用它支撑多点触控也不行 ——
该仿真不是为多点触控设计的，第二指起行为不可靠。

【产出】开关结论（开 / 关）+ 一句话理由 + 代码中已注明

【判据】能说清"为什么开"或"为什么关"，且代码里找得到这个注释。

【审】`audit/godot/mobile.md#1`、`audit/godot/mobile.md#40`

### Step 5　真机验证清单先列，必须含一台低端机　`[mobile/01#S5]`

【读】`howto/godot/mobile.md#8. 移动端性能`

【做】
列出要实测的设备，至少一台低端 Android，并写明每项测多久。
⛔ 只在编辑器里用鼠标测 —— 鼠标是单指、是精确指针、是无遮挡，
而拇指是粗的、会挡住屏幕、会误触。⛔ 这三件事在编辑器里一个都暴露不出来。

ⓘ 发热导致的降频掉帧通常在 10 分钟后才出现，⛔ 只测前 2 分钟等于没测。

【产出】设备清单（含档位）+ 每项的测试时长

【判据】清单里存在至少一台明确属于"最低档位"的设备。

【审】`audit/godot/mobile.md#10`、`audit/godot/mobile.md#33`、`audit/godot/mobile.md#37`

## 3. 参考实现

```gdscript
# ⓘ 承接本步产出：采集层分设备、消费层唯一
# autoload: mobile_input.gd
extends Node

# ⓘ 开关结论：本项目关闭 emulate_mouse_from_touch，全部走触控事件
#    理由：需要双指缩放，该仿真不是为多点触控设计的（见 S4）
var _joystick: VirtualJoystick

func _ready() -> void:
    Input.emulate_mouse_from_touch = false
    _joystick = $UI/VirtualJoystick
    _joystick.visible = OS.has_feature("mobile")

# ⓘ 消费层唯一入口 —— 玩家代码只调这个，不含任何平台判断
func get_move_vector() -> Vector2:
    if _joystick.is_pressed():
        return _joystick_output
    return Input.get_vector("move_left", "move_right", "move_up", "move_down")
```

## 5. 常见返工

| 症状 | 原因 | 回到 |
|---|---|---|
| 技能莫名其妙放出来 | 摇杆与点触未定优先级 | S1 |
| 低端机上一起爆发 | 没有档位就没有预算 | S2 |
| 加个操作要改两处 | 玩家代码里分了平台 | S3 |
| 点一下触发两次 | 仿真开着又处理触控 | S4 |
