# 01 配表边界与格式选型（配置表域）

> **前置**：已列出现有硬编码数值（见 `00-域流程总览.md` 第 0 节）
> **本步交付**：一份"什么进表、什么留代码"的清单，以及选定的数据源格式
> **对应**：做法 `howto/godot/datatable.md` · 审核 `audit/godot/datatable.md`

## 0. 交付物定义

做完这一步，应该能**当场说清**：

1. 哪些数值进表（⛔ 不是"全都搬"）
2. 选了哪个数据源格式及理由
3. ⚠ 已确认**不用** `ConfigFile` 当配表
4. 已确认导出的 CSV 是 **UTF-8 无 BOM**

**产出物**（下游按名字对接）：

```text
进表 / 留代码 的清单
数据源格式：CSV / JSON / .tres / SQLite
CSV 编码约定：UTF-8 无 BOM
```

⚠ 数值写死在代码里：**改一个数值要改代码、要重新导出，程序员成为瓶颈**。

## 1. 前置检查清单

- [ ] 已列出所有现存硬编码数值
- [ ] ⚠ 已确认哪些是策划会调的
- [ ] 已确认表的大致规模（行数、表数）
- [ ] 已确认谁来编辑（策划 / 程序 / 程序生成）

## 2. 工序

### Step 1　划清配表 vs 硬编码的边界　`[datatable/01#S1]`

【读】`howto/godot/datatable.md#0. 为什么必须把数据搬出代码`

【做】三条判据：

| 进表 | 留代码 |
|---|---|
| 策划需要调的 | 结构性逻辑 |
| 会频繁变的 | 算法 |
| 需要批量对比的 | 引擎常量 |

⚠ 常见误判：把"引擎常量"（物理层掩码、输入动作名）也搬进表，
结果改一个掩码要改 CSV，比改代码还麻烦。

【产出】清单覆盖所有现存数值，每项标"进表/留代码"

【判据】⚠ 随机抽 5 个"留代码"的项，都能说出"为什么不该进表"

【审】`audit/godot/datatable.md` 第 1 条（数值写代码里也行 → 改一次就要重新导出）

### Step 2　选数据源格式　`[datatable/01#S2]`

【读】`howto/godot/datatable.md#1. 数据源格式对比`

【做】五选一：

| 格式 | 适合 | 不适合 |
|---|---|---|
| **CSV / Excel** | 策划直接编辑、多人协作、diff 友好 | 嵌套结构 |
| **JSON** | 纯外部交换、程序生成 | 人工编辑易错、无注释 |
| **`.tres` / `.res`（Resource）** | 运行时载体、类型安全 | 手工编辑大量数据 |
| **SQLite** | 千表级、复杂查询、多人同时写 | 小项目杀鸡用牛刀 |
| ⚠ `ConfigFile` | 简单设置 | **不适合当配表** |

⚠ **`ConfigFile` 不适合当配表** —— 无 schema、无校验、无类型，
只是"能读能写的键值对"。

【产出】格式已选定，理由落在"谁来编辑"上

【判据】⚠ 能说出"因为策划要用 Excel 编辑，所以选 CSV"这类因果

【审】`audit/godot/datatable.md` 第 2 条（ConfigFile 能当配表 → 不适合）

### Step 3　确认推荐管线　`[datatable/01#S3]`

【读】`howto/godot/datatable.md#1. 数据源格式对比` 的 ⚠ 推荐方案

【做】⚠ **推荐方案（中大型）**：

```
策划编辑 Excel/CSV → 提交 UTF-8 无 BOM 的 CSV
   → 自定义导入器生成带 schema 的 .tres，同时生成 ID 常量
   → 运行时只持有只读模板，运行时实例必须 duplicate(true)
```

⚠ 三个关键节点缺一不可：
- **UTF-8 无 BOM** —— 有 BOM 的话第一行表头会带不可见字符，列名永远匹配不上
- **生成 ID 常量** —— 否则字符串 ID 拼错只能在运行时发现
- **运行时实例必须拷贝** —— 直接改模板会全改

【产出】管线图已确认，三个节点都有负责人

【判据】⚠ 用十六进制看 CSV 前 3 字节，**不是** `EF BB BF`（BOM）

【审】`audit/godot/datatable.md` 第 7/11 条

### Step 4　嵌套结构怎么处理　`[datatable/01#S4]`

【读】`howto/godot/datatable.md#1. 数据源格式对比`

【做】⚠ CSV **不适合嵌套结构**（技能的多段伤害、掉落表的多级权重）。

三种解法：
- 扁平化（加后缀列：`dmg_1` `dmg_2`）
- 拆成子表 + 外键
- 该表改用 JSON / `.tres` 手写

⛔ 不要试图在单个 CSV 单元格里塞 JSON——
策划改起来痛苦，而且导入器要再做一次解析，出错更难查。

【产出】每张有嵌套的表都选了一种解法

【判据】⚠ CSV 里**没有**任何单元格内容是 JSON/数组文本

【审】`audit/godot/datatable.md` 第 2 条

## 3. 参考实现

ⓘ 本步是**决策步**，产出是一张清单：

```text
【进表】技能伤害/冷却/消耗、物品价格/堆叠上限、怪物血量/掉落权重
       → 理由：策划每周调
【留代码】物理层掩码、输入动作名、枚举值、常量公式
       → 理由：改了会破坏代码结构，且策划不关心

数据源：CSV（策划用 Excel 编辑）
编码：UTF-8 无 BOM（导出时确认）
嵌套：掉落表拆成 drop_group + drop_entry 两张表，用外键关联
```

⚠ 这张清单要在写导入器**之前**定稿——
它决定了 schema，而 schema 决定了导入器。

## 5. 常见返工

| 症状 | 原因 | 回到 |
|---|---|---|
| 改数值还要改代码 | 该进表的没进 | S1 |
| 表名列名永远匹配不上 | CSV 带 BOM | S3 |
| 策划改表经常把游戏改崩 | 用了 ConfigFile 无校验 | S2 |
| 嵌套数据改不动 | 硬塞进单元格 | S4 |
