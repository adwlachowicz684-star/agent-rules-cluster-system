# 01 排序与深度地基（2D 渲染域）

> **本步交付**：排序父节点结构 + 原点口径 + z_index 约定
> **对应**：流程 `howto/godot/2d-rendering.md` · 审核 `audit/godot/2d-rendering.md`

## 0. 交付物定义

1. 排序父节点结构已定，可排序对象**全部**在同一父节点下
2. 精灵原点口径统一（脚底在原点），⛔ 不是靠 `y_sort_origin` 逐个补偿
3. `z_index` 约定已写下：哪些层参与互排，哪些层固定
4. 运行时动态生成的实例有明确的挂载点（会进排序父节点）
5. UI 层与世界层的 z_index 边界已划清

## 1. 前置检查清单

- [ ] 能用一句话说清"哪些节点互排、挂在谁下面"
- [ ] 所有角色/物体的精灵原点在脚底，且碰撞体与之对齐
- [ ] `z_index` 约定已写下（不是"默认 0 就行"）
- [ ] 运行时 `add_child` 的位置已确定，会落进排序父节点
- [ ] UI `CanvasLayer` 不参与世界层的 z_index 竞争

## 2. 工序

### Step 1　排序父节点结构先定，`y_sort_enabled` 开在父上　`[2d-rendering/01#S1]`

【读】`howto/godot/2d-rendering.md#1. Y-Sort：俯视角 2D 的地基`

【做】
确定一个排序父节点，所有需要互排的对象作为它的直接子节点，`y_sort_enabled` 开在这个父节点上。
⛔ 把 `y_sort_enabled` 开在每个子节点自己身上 —— 子节点自己开只影响它自己的子树，
对同级关系**不起作用**，表现为"全都勾了但完全没排序"。

⛔ 更要命的是**排序对象不在同一父节点下**：玩家挂在 `Entities`、树挂在 `Scenery`，
两者不互排，表现为"走到树前/树后的遮挡关系时有时无"，
⛔ 而这种时有时无会被当成随机的渲染 bug 去查，不会想到是父节点。

【产出】排序父节点名 + 参与互排的节点清单

【判据】指着任意两个可互排对象，能说出它们共同的直接父节点是谁。

【审】`audit/godot/2d-rendering.md#1`、`audit/godot/2d-rendering.md#2`

### Step 2　原点统一在脚底，不用 `y_sort_origin` 逐个补　`[2d-rendering/01#S2]`

【读】`howto/godot/2d-rendering.md#脚底对齐`

【做】
统一用 `sprite.offset.y = -texture.get_height() / 2.0` 把精灵下移，让节点原点落在脚底。
⛔ 用 `y_sort_origin` 逐个调数值去"看起来对" ——
那是**治标**：排序对了，碰撞体和射线检测仍然按错误原点算，
表现为"看着站在树前、实际判定在树后"。

ⓘ 统一口径的收益是连锁的：碰撞体、Y 排序、射线、落点特效**共用同一个原点**，
后面加任何依赖位置的功能都不用再问一次"这里该用哪个坐标"。

【产出】精灵 offset 设置（统一写在基类或工具函数里）+ 碰撞体与之对齐的说明

【判据】换一张高度不同的贴图，排序与碰撞**都不需要改数值**。

【审】`audit/godot/2d-rendering.md#3`、`audit/godot/2d-rendering.md#34`

### Step 3　`z_index` 约定写下来：官方口径是"只有同一值才互排"　`[2d-rendering/01#S3]`

【读】`howto/godot/2d-rendering.md#官方排序语义：传播 + z_index 约束`

【做】
写下每类对象的 `z_index`，并确认**需要互排的对象取值相同**。
⛔ 官方口径：*"Nodes sort relative to each other only if they are on the same `z_index`."*
给玩家 `z_index = 1`、给树 `z_index = 0` → 两者**不互排**，角色永远画在前面。

⛔ 这是最难查的一类失效：检查面板时 `y_sort_enabled` 处处是 `true`、
父子结构也完全正确，⛔ 于是每一处单看都对，而排序整体不生效且不报错。

ⓘ 反过来，官方那条"父开、子关则子树塌成同一 Y"是**可用特性**：
做多层建筑、载具这种"整组一起排"的东西时，给组节点关掉即可，⛔ 但要知道这是刻意用的。

【产出】z_index 分配表（含"哪些层参与互排"）

【判据】互排对象两两 `z_index` 相等；不互排的层有写明理由。

【审】`audit/godot/2d-rendering.md#19`

### Step 4　运行时生成的实例必须挂进排序父节点　`[2d-rendering/01#S4]`

【读】`howto/godot/2d-rendering.md#1. Y-Sort：俯视角 2D 的地基`

【做】
确定所有 `add_child` / `instantiate()` 的挂载点，让动态实例落进排序父节点。
⛔ 运行时刷怪、掉落物、特效直接挂到根节点或当前场景根 ——
编辑器里手摆的那批排序正常，⛔ **运行时刷出来的全部不参与排序**，
表现为"手摆的对、刷出来的错"，而排查必然被引向生成逻辑。

ⓘ 分块加载的关卡尤其要注意：块的根节点挂在哪，决定块内所有物体是否进入排序域。
这与 `level` 域的分块策略直接相关，⛔ 接缝在"挂载点"这个具体符号上。

【产出】动态实例的挂载点说明（含分块关卡的块根挂载）

【判据】刷一波怪后，新怪与手摆物体之间遮挡关系正确。

【审】`audit/godot/2d-rendering.md#35`

### Step 5　UI 层与世界层的 z_index 边界划清　`[2d-rendering/01#S5]`

【读】`howto/godot/2d-rendering.md#1. Y-Sort：俯视角 2D 的地基`

【做】
UI 走独立 `CanvasLayer`，⛔ 不靠调大 `z_index` 压在世界之上。
⛔ 混用会让层内外的排序互相穿透：世界里的高 `z_index` 物体盖住 UI，
或 UI 的层级被世界物体的 `z_index` 打乱，表现为"偶尔有个血条被树挡住"。

ⓘ 判定边界很简单：**世界层内部**用 `z_index` 与 Y 排序，**层与层之间**用 `CanvasLayer.layer`。
⛔ 这两套机制不要交叉使用。

【产出】层划分说明（哪几个 CanvasLayer、各自 layer 值）

【判据】世界物体无论 z_index 多高，都不会盖住 UI 层。

【审】`audit/godot/2d-rendering.md#37`

## 3. 参考实现

```gdscript
# ⓘ 承接本步产出：统一原点 + 统一挂载点 + z_index 约定
# sort_root.gd —— 挂在排序父节点上
extends Node2D

# ⓘ z_index 约定：互排对象一律 0；地面层 -1（不参与互排），飞行单位 2（不参与互排）
const Z_GROUND := -1
const Z_SORTABLE := 0
const Z_AIRBORNE := 2

func _ready() -> void:
    y_sort_enabled = true

# ⓘ 运行时实例统一走这里，⛔ 不要各自 add_child 到场景根
func spawn(scene: PackedScene, pos: Vector2) -> Node2D:
    var n := scene.instantiate() as Node2D
    n.position = pos
    n.z_index = Z_SORTABLE
    add_child(n)
    return n
```

```gdscript
# ⓘ 脚底对齐统一入口（基类或工具函数），⛔ 不用 y_sort_origin 逐个补
static func align_feet(sprite: Sprite2D) -> void:
    var tex := sprite.texture
    if tex == null:
        return
    sprite.offset.y = -tex.get_height() / 2.0
```

## 4. 验收清单

- [ ] 排序父节点唯一，互排对象都在其下
- [ ] 换贴图高度后排序与碰撞都不用改数值
- [ ] 互排对象 `z_index` 两两相等，非互排层写明理由
- [ ] 运行时生成的实例排序正确

## 5. 常见返工

| 症状 | 原因 | 回到 |
|---|---|---|
| 全都勾了但没排序 | `y_sort_enabled` 开在子节点 | S1 |
| 遮挡关系时有时无 | 排序对象不在同一父节点 | S1 |
| 看着在树前、判定在树后 | 用 `y_sort_origin` 治标 | S2 |
| 配置全对但排序整体失效 | 互排对象 `z_index` 不同 | S3 |
| 手摆的对、刷出来的错 | 动态实例挂错父节点 | S4 |
| 血条偶尔被树挡住 | UI 与世界层混用 z_index | S5 |
