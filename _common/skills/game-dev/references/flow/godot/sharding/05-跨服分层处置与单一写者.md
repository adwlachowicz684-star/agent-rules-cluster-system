# 05 跨服分层处置与单一写者（分服合服域）

> **本步交付**：分层处置表 + 单一写者约定 + 镜像过期标记
> **对应**：流程 `howto/godot/sharding-matchmaking.md` · 审核 `audit/godot/sharding-matchmaking.md`

## 0. 交付物定义

1. 重名与跨服数据按"身份 / 社交 / 经济 / 竞技"分层处置
2. 公会保留独立账本，⛔ 不合并余额
3. 好友双向成功才算批次提交
4. 排行榜按同一赛季 / 规则 / 截止时间重算
5. 拍卖行先进入禁止上新与结算期
6. ⛔ 一次请求只能有一个写者
7. 过期镜像值被标记"可能过期"，⛔ 不静默当最新

## 1. 前置检查清单

- [ ] 重名方案已预先公告，且配改名卡
- [ ] 公会账本独立，余额未合并
- [ ] ⛔ 好友关系双向校验通过才提交批次
- [ ] 排行榜已重算，⛔ 不是上下拼接
- [ ] 拍卖行已进入禁止上新与结算期
- [ ] 跨服调用有单一写者约定
- [ ] 镜像值带"可能过期"标记

## 2. 工序

### Step 1　重名按"身份 / 社交 / 经济 / 竞技"分层，加后缀有代价　`[sharding/05#S1]`

【读】`howto/godot/sharding-matchmaking.md#1.6 重名与跨服数据按「身份/社交/经济/竞技」分层处置`

【做】
重名加后缀是最省事的方案，⚠ 但玩家会**失去原名**、搜索行为改变、
还可能被近似名冒充。
⛔ 处置要按四层分别定：身份（显示名 / 索引 / 备注 / 收件人都映射同一稳定 ID）、
社交（好友 / 黑名单）、经济（订单 / 邮件）、竞技（战绩 / 段位）。

【产出】重名分层处置表（含改名卡与预先公告）

【判据】所有显示名、索引、备注、收件人都指向同一稳定 ID

【审】`audit/godot/sharding-matchmaking.md#22`


### Step 2　⛔ "原服优先"保留名字会让被合并服感到永久降级　`[sharding/05#S2]`

【读】`howto/godot/sharding-matchmaking.md#1.6 重名与跨服数据按「身份/社交/经济/竞技」分层处置`

【做】
"保留原服玩家的名字"看似公平，⛔ 对被合并服来说是**永久的降级感**——
他们会在每一次看到自己名字带后缀时重新体验一次。
⚠ 公平方案通常是双方都改 + 各发改名卡，而不是一方保留。

【产出】重名归属规则（含补偿方案）

【判据】规则中不存在"某一服优先"的表述

【审】`audit/godot/sharding-matchmaking.md#23`


### Step 3　⛔ 公会保留独立账本，不合并余额　`[sharding/05#S3]`

【读】`howto/godot/sharding-matchmaking.md#1.6 重名与跨服数据按「身份/社交/经济/竞技」分层处置`

【做】
公会不只是人数集合，它同时含**权力与资产**。
⛔ 合并余额等于把两个组织的资产强行并账，
表现为"公会资金突然变多"——而这笔钱没有任何来源记录。

【产出】公会处置规则（成员合并 / 账本独立 / 权限重定）

【判据】合并后每个公会仍有独立余额与独立审计流水

【审】`audit/godot/sharding-matchmaking.md#24`


### Step 4　⛔ 好友存单向边会导致骚扰与社交攻击　`[sharding/05#S4]`

【读】`howto/godot/sharding-matchmaking.md#1.6 重名与跨服数据按「身份/社交/经济/竞技」分层处置`

【做】
只写一条 A→B 的边，会出现"**A 有 B 但 B 没有 A**"：
A 能看到 B 在线、能给 B 发消息，而 B 侧毫无记录也无法屏蔽。
⛔ 这是骚扰与社交攻击的直接入口。
⚠ **双向都写成功才算批次提交**，单向失败要整批回滚而不是留半条边。

【产出】好友迁移批次规则（双向原子）

【判据】不存在单向边；单向写入失败时批次整体回滚

【审】`audit/godot/sharding-matchmaking.md#25`


### Step 5　⛔ 排行榜不能上下拼接，要按同一赛季重算　`[sharding/05#S5]`

【读】`howto/godot/sharding-matchmaking.md#1.6 重名与跨服数据按「身份/社交/经济/竞技」分层处置`

【做】
把两个榜上下拼起来，会造出**错误名次**：
两个服的赛季开始时间、规则、截止时间都不同，分数本就不可比。
⛔ 拼接出来的榜既不公平也无法解释，而它看起来"有数据、能显示"。

【产出】排行榜重算规则（同一赛季 / 规则 / 截止时间）

【判据】合并后的榜是重算结果，不是拼接结果

【审】`audit/godot/sharding-matchmaking.md#26`


### Step 6　⛔ 拍卖行订单不能一起迁移：先进入禁止上新与结算期　`[sharding/05#S6]`

【读】`howto/godot/sharding-matchmaking.md#1.6 重名与跨服数据按「身份/社交/经济/竞技」分层处置`

【做】
进行中的挂单直接迁移会造成**双重结算**：
原服结算一次、目标服再结算一次。
⛔ 必须先进入禁止上新与结算期，让所有在途订单走完，
再迁移已完成状态。

【产出】拍卖行迁移前置条件（禁止上新 + 结算期 + 在途清零）

【判据】迁移开始时在途订单数为 0

【审】`audit/godot/sharding-matchmaking.md#27`


### Step 7　⛔ 跨服一次请求只能有一个写者　`[sharding/05#S7]`

【读】`howto/godot/sharding-matchmaking.md#1.7 跨服权威：一次请求只能有一个写者`

【做】
跨服场景下本能是"两边都写一份保持一致"。
⛔ 两边都写意味着两个写者，必然出现顺序竞争与部分成功，
⚠ 而部分成功在跨服里最难被发现——因为两边各自看都是自洽的。

【产出】单一写者约定（哪个服写、谁补偿、谁对账）

【判据】任一跨服写路径都能指出唯一的写者

【审】`audit/godot/sharding-matchmaking.md#28`


### Step 8　⛔ 过期镜像值要标记"可能过期"，不能静默当最新　`[sharding/05#S8]`

【读】`howto/godot/sharding-matchmaking.md#1.7 跨服权威：一次请求只能有一个写者`

【做】
跨服读取常走镜像。镜像过期时若直接返回，
⛔ **资产、封禁状态、比赛资格**这三类会被静默判错——
玩家看到的是"我没钱 / 我被封了 / 我不能参赛"，而真实值并非如此。
⚠ 正确做法是带上"可能过期"标记，并在关键判定前回源确认。

【产出】镜像值契约（含 stale 标记与回源规则）

【判据】资产 / 封禁 / 资格三类判定前必回源

【审】`audit/godot/sharding-matchmaking.md#29`


## 3. 参考实现

```gdscript
# ⓘ 承接本步产出：跨服调用要有超时，镜像要带过期标记
const CROSS_SHARD_TIMEOUT_MS := 800
const MIRROR_MAX_STALE_SEC := 60

# ⛔ HTTPRequest.timeout 默认 0.0 = 永不超时；必须显式设置。
# ⓘ 超过容忍过期就必须回源，⛔ 不能把旧值当最新值用。
func need_revalidate(stale_sec: int, is_critical: bool) -> bool:
	if is_critical:
		return true
	return stale_sec > MIRROR_MAX_STALE_SEC
```

## 5. 常见返工

| 症状 | 原因 | 回到 |
|---|---|---|
| 改名后玩家投诉 | 加后缀无补偿 | S1 |
| 被合并服流失 | 原服优先 | S2 |
| 公会资金对不上 | 合并了余额 | S3 |
| 单向好友骚扰 | 单向边 | S4 |
| 名次明显不合理 | 拼接了榜 | S5 |
| 一笔订单结算两次 | 在途订单迁移 | S6 |
| 两边数据不一致 | 两个写者 | S7 |
| 玩家看到错误的封禁状态 | 镜像过期未标记 | S8 |
