# 06 邮件与全服补偿（分服合服域）

> **本步交付**：附件状态机 + 补偿模板 + 分批展开
> **对应**：流程 `howto/godot/sharding-matchmaking.md` · 审核 `audit/godot/sharding-matchmaking.md`

## 0. 交付物定义

1. ⛔ 附件已领不是一个 boolean，是状态机
2. 领取先占状态再入账
3. 客户端超时后重新查询状态，⛔ 不是直接重试
4. 满箱不阻断维护补偿 / 付费返还 / 官方承诺
5. 全服补偿走模板 + 资格计算 + 分批展开
6. 重发只重放失败批次
7. 过期分两层：领取后相对过期 + 邮件绝对过期

## 1. 前置检查清单

- [ ] 附件状态至少 `UNCLAIMED / CLAIMING / CLAIMED`
- [ ] ⛔ 只有状态更新成功的那笔执行入账
- [ ] 超时路径是"重查状态"而不是"重试发放"
- [ ] ⛔ 官方承诺类补偿不被满箱阻断
- [ ] 补偿是模板 + 分批，不是一次性插全量记录
- [ ] 重放范围限定为失败批次
- [ ] 过期规则有两层且各自可查

## 2. 工序

### Step 1　⛔ 附件"已领"不能用一个 boolean　`[sharding/06#S1]`

【读】`howto/godot/sharding-matchmaking.md#2. 邮件系统：全服补偿的最后一道可靠性闸门`

【做】
一个 boolean 无法表达**部分领取**：一封邮件三个附件，领了第一个就断了。
⛔ 它也无法支持并发、审计与回滚——
出问题时只能知道"领过 / 没领过"，不知道领了哪个、领了几次。

【产出】附件状态机（每个附件独立状态）

【判据】一封多附件邮件可以只领其中一个，且状态可查

【审】`audit/godot/sharding-matchmaking.md#39`


### Step 2　⛔ 附件领取必须先占状态，再入账　`[sharding/06#S2]`

【读】`howto/godot/sharding-matchmaking.md#附件领取必须先占状态，再入账`

【做】
正确顺序是 `UNCLAIMED → CLAIMING`（条件更新占住），
**只有更新成功的那笔**才执行背包 / 货币发放并写资产流水，成功后置 `CLAIMED`。
⛔ 反过来（先发奖再置位）在并发下会双发，
⚠ 而表现为"偶尔多发一次"，长期被当成数据异常而不是顺序错误。

【产出】领取事务（`mail_id + player_id + attachment_id` 唯一约束）

【判据】并发领取同一附件时只有一笔入账

【审】`audit/godot/sharding-matchmaking.md#40`


### Step 3　⛔ 客户端超时要重新查询状态，不是直接重试发放　`[sharding/06#S3]`

【读】`howto/godot/sharding-matchmaking.md#2. 邮件系统：全服补偿的最后一道可靠性闸门`

【做】
超时只说明"不知道结果"，不说明"没发"。
⛔ 直接重试会造成部分到账——而**部分到账比领取失败更危险**，
因为玩家拿到了东西但订单状态可能仍是未领，形成可重复利用的漏洞。

【产出】超时处置流程（先查状态，再决定）

【判据】超时路径的第一步是查询，不是重放

【审】`audit/godot/sharding-matchmaking.md#41`


### Step 4　⛔ 满箱不能让补偿发不出去　`[sharding/06#S4]`

【读】`howto/godot/sharding-matchmaking.md#⚠ 容量满不能让补偿发不出去`

【做】
背包满就拒绝，会让**维护补偿、付费返还、官方承诺**全部发不出去。
⛔ 这三类被阻断是运营事故，不是"玩家自己整理背包"能解决的：
玩家可能长期不在线，等他上线时邮件已过期。

【产出】满箱处置规则（三类必达邮件不受满箱阻断）

【判据】维护补偿在背包满时仍能到账（如入暂存 / 延长有效期）

【审】`audit/godot/sharding-matchmaking.md#42`


### Step 5　⛔ 全服补偿是模板 + 资格计算 + 分批展开　`[sharding/06#S5]`

【读】`howto/godot/sharding-matchmaking.md#全服补偿：模板 + 资格计算 + 分批展开`

【做】
一次性给全量玩家插记录，会在瞬间打爆写入并拖垮从库。
⛔ 正解是存**模板**，读取时按资格计算展开，写入走分批，
并用唯一键去重——这样重入也安全。

【产出】补偿模板 + 分批展开任务（含唯一键）

【判据】补偿执行期间从库延迟可控，且重入不产生重复

【审】`audit/godot/sharding-matchmaking.md#43`


### Step 6　⛔ 重发只重放失败批次　`[sharding/06#S6]`

【读】`howto/godot/sharding-matchmaking.md#全服补偿：模板 + 资格计算 + 分批展开`

【做】
重发时重新向所有人插入，会让已经领过的玩家**再收到一份**。
⛔ 依赖"已领标记"也不够——因为失败批次里有些玩家可能已经部分到账。
⚠ 只对**明确失败的批次**重放，并保持唯一键约束。

【产出】失败批次清单 + 重放记录

【判据】重放后无玩家收到两份，且有重放审计记录

【审】`audit/godot/sharding-matchmaking.md#44`


### Step 7　⚠ 邮件过期要分两层　`[sharding/06#S7]`

【读】`howto/godot/sharding-matchmaking.md#过期要分两层`

【做】
只有一条过期规则时，会出现"领了之后附件还在有效期但邮件已消失"这类矛盾。
⛔ 要分两层：**领取后相对过期**（领了才计时）与**邮件绝对过期**（到点整封消失）。
⚠ 两层口径都要对玩家可见，否则客服无法解释。

【产出】两层过期规则（各自可查、对玩家可见）

【判据】能回答"这封邮件什么时候消失"和"领到的道具什么时候过期"

【审】`audit/godot/sharding-matchmaking.md#45`


## 3. 参考实现

```gdscript
# ⓘ 承接本步产出：分批展开 + 两层过期
const MAIL_BATCH_SIZE := 5000
const MAIL_EXPIRE_DAYS := 30

# ⛔ 客户端只展示；占位与入账由服务端事务完成。
# ⓘ claimed 是每附件独立状态，⛔ 不是整封邮件一个 boolean。
func is_claimable(state: String, expired: bool) -> bool:
	if expired:
		return false
	return state == "UNCLAIMED"
```

## 4. 验收清单

- [ ] 多附件邮件可只领其中一个
- [ ] ⛔ 并发领取只有一笔入账
- [ ] 超时路径先查状态
- [ ] ⛔ 维护补偿 / 付费返还不被满箱阻断
- [ ] 补偿是模板 + 分批，重入无重复
- [ ] 重放只针对失败批次
- [ ] 两层过期各自可查

## 5. 常见返工

| 症状 | 原因 | 回到 |
|---|---|---|
| 多附件领一半就断 | 用了 boolean | S1 |
| 偶尔多领一次 | 先发奖后置位 | S2 |
| 部分到账可重复利用 | 超时直接重试 | S3 |
| 维护补偿发不出去 | 满箱阻断 | S4 |
| 补偿时从库被打爆 | 一次性插全量 | S5 |
| 重发后玩家收到两份 | 重放了所有人 | S6 |
| 客服无法解释过期 | 只有一层规则 | S7 |
