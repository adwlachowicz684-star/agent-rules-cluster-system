# 分服 / 跨服 / 合服 / 匹配 —— 域流程总览

> ⚠ **第 0 步：先定"隔离的是什么"。**
> 本域有 8 个功能点，⛔ **不是全做** —— 按本次要扛什么形态挑。
> ⛔ 顺序错了比不做更糟：先调匹配算法会得到"分服 ID 已撞车"的线上事故。

## 0. 先定做什么

| 本次要做的 | 走哪些功能点 |
|---|---|
| 还没开服，只是怕以后合服 | 01 → 02 → 08 |
| 要合服（真要搬数据） | 01 → 02 → 03 → 04 → 05 → 08 |
| 要做跨服玩法（跨服匹配 / 跨服战场） | 01 → 05 → 07 → 08 |
| 要做全服补偿 / 系统邮件 | 06 → 08 |
| 只做匹配与排位 | 01 → 07 → 08 |
| 全套 | 01 → 02 → 03 → 04 → 05 → 06 → 07 → 08 |

⛔ **01 无论如何不能跳过** ——
它是唯一决定"后面 7 个功能点该投多少预算"的一步。
⛔ 跳过 01 直接做 07（匹配）是最常见的错：
匹配能立刻给出"排队多久、对手强不强"这些直观反馈，
⚠ 而此时**各服 ID 生成器仍是各服自增**——
跨服一开，玩家 ID、角色 ID、公会 ID 全线撞车，
⛔ 于是团队去改匹配分，撞车问题却在每次跨服时重新出现。

ⓘ 分工：
- `howto/godot/sharding-matchmaking.md` 讲**单个机制怎么实现**（全局 ID、dry-run、冻结清单、邮件状态机、匹配分）
- 本域讲**这些机制按什么顺序做、哪些必须在服务端、怎么验收**

## 2. 接缝

| 接缝 | 说明 |
|---|---|
| `netsync` 域 同步 | 跨服同步的权威判定在服务端，见 05 |
| `security` 域 服务端权威 | 匹配分更不能客户端算，见 `security/02#S5`、`security/01#S3` |
| `social` 域 公会好友 | 公会独立账本、好友双向，见 05 |
| `trade` 域 拍卖行 | 合服前要进禁止上新与结算期，见 05 |
| `ops` 域 运营 | 全服补偿的流水号幂等，见 `ops/05#S1` |
| `analytics` 域 埋点 | 运营数据口径与日切定义，见 08 |
| `economy` 域 账本 | 资产迁移进同一账本，⛔ 不另开计数 |
| `backend-stability` 域 稳定性 | 跨服调用的超时与熔断，见 `backend-stability/03` |

⛔ **若某条接缝对不上，要单独立一个接线功能点**。

⚠ **各功能点自己的验收不能替代集成验收** ——
部件全合格、拼起来不能用，是跨域开发的典型失败。

## 3. 本域最容易做反的顺序

⛔ **先做匹配与排队界面（07），再做全局 ID 地基（01）。**

"能看到排队秒数、能打上一局"是最直观的验收点，
于是先接匹配算法、先画等待界面、先在客户端算段位，
⚠ 而此时 ID 仍是各服自增、跨服还没有单一写者约定。

⛔ 后果链：
各服自增 ID → 跨服撞车 → 为了修它加映射表 →
但映射表是运行时才补的 → 历史订单与日志 join 全断 →
于是加偏移量 → **破坏协议字段与缓存键**。

⚠ 这些补丁会让 01 再也没法正确落地——
因为到处都已经有了"某个服本地生成的 ID"。

⛔ 同类第二条：**先接邮件 UI（06），再定附件状态机。**
"能看到邮件列表、能点领取"同样直观，
而附件直接发资产、已领用一个 boolean，
⛔ 表现为"功能正常"，直到并发领取与补偿重发才暴露双发。

✅ 正确顺序：先把全局 ID 与边界（01）钉死，
再谈盘点（02）、迁移（03）、跨服（05）、匹配（07）。
