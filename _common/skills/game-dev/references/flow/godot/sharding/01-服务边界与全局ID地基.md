# 01 服务边界与全局 ID 地基（分服合服域）

> **本步交付**：隔离边界清单 + 全局唯一 ID 方案 + 位宽契约
> **对应**：流程 `howto/godot/sharding-matchmaking.md` · 审核 `audit/godot/sharding-matchmaking.md`

## 0. 交付物定义

1. "隔离的是什么"两栏清单已写下，不是凭感觉
2. 已确认引擎不提供任何分服 / 跨服 / 匹配能力
3. 全局 ID 方案已定，⛔ 不依赖各服自增
4. ID 生成器抗时钟回拨，机器位有租约
5. 位宽变更被当作不兼容协议变更处理

## 1. 前置检查清单

- [ ] 已写明"隔离的是服务边界，不是玩家身份"
- [ ] 已确认账号 / 订单 / 支付是**全局**的，不随服隔离
- [ ] 全局 ID 生成器已就位，⛔ 各服自增已停用
- [ ] ⛔ 已验证 NTP 回拨场景下不复用已用时间段
- [ ] 机器位由租约分配，⛔ 不是各服自己填

## 2. 工序

### Step 1　先写"隔离的是什么"两栏清单　`[sharding/01#S1]`

【读】`howto/godot/sharding-matchmaking.md#1. 分区分服 / 跨服 / 合服`

【做】
本能以为分服隔离的是**玩家身份**，实际隔离的是**服务边界**。
账号、订单、支付、客服工单都是全局的——玩家换服不应换账号。
⛔ 不写这两栏清单直接开工，"这个是不是全局的"会在每个新系统被重新争论，
⛔ 而争论的结论通常取决于当时谁在写，最后形成一半全局一半分服的烂摊子。

【产出】隔离边界两栏清单（分服隔离 / 全局共享）

【判据】指着任一实体能说出它属于哪一栏，且理由不是"应该跟着服走"

【审】`audit/godot/sharding-matchmaking.md#2`


### Step 2　Godot 不提供分服 / 跨服 / 匹配：一个都没有　`[sharding/01#S2]`

【读】`howto/godot/sharding-matchmaking.md#1. 分区分服 / 跨服 / 合服`

【做】
不要去 `ProjectSettings` 里找"分服开关"，不要指望 `ENetMultiplayerPeer` 自带路由，
不要找内置的匹配队列或技能分系统。
⚠ 引擎**一个都没有**，全部要自建后端。
⛔ 把它们当成"引擎应该有的功能"去找，会浪费大量时间，
并导向"Godot 不适合做大服"这个错误结论。

【产出】自建清单（后端各模块分别承担什么）

【判据】清单里每项都写明了由谁提供，不存在"引擎自带"

【审】`audit/godot/sharding-matchmaking.md#1`


### Step 3　⛔ 各服自增 ID 会撞车，必须换全局唯一 ID　`[sharding/01#S3]`

【读】`howto/godot/sharding-matchmaking.md#ID 冲突`

【做】
各服 `AUTO_INCREMENT` 独立计数，合服或跨服时**必然撞车**。
⛔ 撞车不止发生在主键上：缓存键、日志 join、历史订单引用会一起错，
而报错信息通常只是"唯一约束冲突"，看起来像脏数据而不是设计缺陷。

【产出】全局 ID 方案（生成器 + 位宽 + 部署方式）

【判据】任两个服各生成 10 万个 ID，合并后无重复

【审】`audit/godot/sharding-matchmaking.md#3`


### Step 4　⛔ 雪花 ID 的抗回拨与机器位租约　`[sharding/01#S4]`

【读】`howto/godot/sharding-matchmaking.md#全局 ID 分配器：三个闸门`

【做】
配好雪花 ID 不等于安全：⚠ **NTP 回拨会复用已用时间段**，
机器位若各服自己填则会重复。
⛔ 机器位必须租约分配（用完归还），时间戳回拨要有明确处置（等待 / 报错 / 借用序号位），
且**不能静默继续发号**。

【产出】ID 生成器契约（回拨处置 + 机器位租约）

【判据】人为回拨系统时钟后，生成器不产出已用过的 ID，且有可观测告警

【审】`audit/godot/sharding-matchmaking.md#4`


### Step 5　⛔ 序列号耗尽：改位宽是不兼容协议变更　`[sharding/01#S5]`

【读】`howto/godot/sharding-matchmaking.md#全局 ID 分配器：三个闸门`

【做】
序列号位宽用尽时，本能是"调大位宽"。
⛔ 但位宽是**协议的一部分**：客户端解析、缓存键长度、日志格式都依赖它。
⚠ 正确做法是把位宽变更当作不兼容协议变更，走灰度与双读，
而不是一次上线全量切换。

【产出】位宽变更灰度方案（新旧双读窗口）

【判据】位宽变更期间新旧两种 ID 都能被正确解析

【审】`audit/godot/sharding-matchmaking.md#5`


## 3. 参考实现

```gdscript
# ⓘ 承接本步产出：位宽是协议的一部分，改它必须灰度
const MACHINE_ID_BITS := 10
const SEQ_BITS := 12
const SNOWFLAKE_EPOCH_MS := 0

# ⛔ 客户端只做解析与展示，⛔ 不生成 ID
func decode_snowflake(id: int) -> Dictionary:
	var seq_mask := (1 << SEQ_BITS) - 1
	var machine_mask := (1 << MACHINE_ID_BITS) - 1
	return {
		"seq": id & seq_mask,
		"machine": (id >> SEQ_BITS) & machine_mask,
		"ts": (id >> (SEQ_BITS + MACHINE_ID_BITS)) + SNOWFLAKE_EPOCH_MS,
	}
```

## 5. 常见返工

| 症状 | 原因 | 回到 |
|---|---|---|
| 一半全局一半分服 | 没定边界 | S1 |
| 花时间找"分服开关" | 以为引擎内置 | S2 |
| 合服时唯一约束冲突 | 各服自增 | S3 |
| 回拨后 ID 重复 | 生成器不抗回拨 | S4 |
| 改位宽后日志全错 | 当成内部实现改 | S5 |
