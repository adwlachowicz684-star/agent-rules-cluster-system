# 07 匹配与技能分（分服合服域）

> **本步交付**：服务端权威分数 + 窗口分级 + 赛季重置语义
> **对应**：流程 `howto/godot/sharding-matchmaking.md` · 审核 `audit/godot/sharding-matchmaking.md`

## 0. 交付物定义

1. ⛔ 匹配分数只来自服务端，客户端不携带段位 / 分数 / 战绩
2. 重复入队返回当前队列状态
3. 等待窗口分级，⛔ 不无限放宽
4. 队伍分不取最高，也不取平均
5. ⛔ 排位不塞伪装人类的 Bot
6. 故意掉分按操控处理
7. 掉线惩罚递增且允许重连
8. 赛季重置用软重置，⛔ 不清零

## 1. 前置检查清单

- [ ] ⛔ 客户端请求里不含段位 / 分数 / 战绩字段
- [ ] 重复入队返回已有队列状态
- [ ] 窗口分级表已定，且定义了放弃条件
- [ ] 队伍分规则已定并公示
- [ ] ⛔ 排位无伪装人类的 Bot
- [ ] 掉分操控有检测与处罚梯度
- [ ] 掉线可重连，且同一局不允许重放
- [ ] 赛季重置是软重置 / 衰减

## 2. 工序

### Step 1　⛔ 匹配必须服务端，客户端不能携带段位 / 分数 / 战绩　`[sharding/07#S1]`

【读】`howto/godot/sharding-matchmaking.md#3. 匹配与技能分`

【做】
客户端上报分数等于把匹配结果交给玩家决定。
⛔ 请求体里**不能出现**段位、分数、战绩字段——
不是"服务端校验一下"，而是**根本不传**。
⚠ 只传"我要排队"和身份，其余全部服务端查。

【产出】入队请求字段表（不含任何分数相关字段）

【判据】请求体里搜不到 score / rank / mmr 类字段

【审】`audit/godot/sharding-matchmaking.md#30`


### Step 2　⛔ 重复入队不能创建第二个排队项　`[sharding/07#S2]`

【读】`howto/godot/sharding-matchmaking.md#3. 匹配与技能分`

【做】
网络重试或玩家连点会创建第二个排队项，
⛔ 表现为"同时在两个队列里"，随后被两个房间同时拉走，
产生一个永远无法结算的对局。
⚠ 正确做法是重复入队返回**当前队列状态**（幂等）。

【产出】入队幂等约定（同玩家只有一个排队项）

【判据】连续入队 10 次，队列里仍只有一个排队项

【审】`audit/godot/sharding-matchmaking.md#31`


### Step 3　⛔ 等待太久不能无限放宽：三条曲线同时恶化　`[sharding/07#S3]`

【读】`howto/godot/sharding-matchmaking.md#等待窗口分级（⛔ 不能无限放宽）`

【做】
放宽窗口能立刻降低排队时长，⚠ 但同时恶化**匹配偏差、对局延迟、结果可信度**三条曲线。
⛔ 无限放宽的最终状态是"秒进房、局面完全不可玩"，
而监控上只看得到排队时长这一条在变好。
⚠ 要定义**放弃条件**（放宽到某级后 bot 填充或直接提示重试）。

【产出】窗口分级表（每级的分差上限 + 放弃条件）

【判据】每一级都写明了再放宽就放弃的条件

【审】`audit/godot/sharding-matchmaking.md#32`


### Step 4　⛔ 队伍分取最高会被高分带小号操纵　`[sharding/07#S4]`

【读】`howto/godot/sharding-matchmaking.md#队伍分数：不能只选平均或最高`

【做】
取最高分，一个高手可以带四个新号打进低分段，
⛔ 这是**可被规模化利用**的漏洞，而不只是"有点不公平"。

【产出】队伍分规则（含组队跨度限制）

【判据】存在组队分差上限，超出无法一起排队

【审】`audit/godot/sharding-matchmaking.md#33`


### Step 5　⚠ 队伍分取平均会让高手觉得带不动　`[sharding/07#S5]`

【读】`howto/godot/sharding-matchmaking.md#队伍分数：不能只选平均或最高`

【做】
取平均则高手被拖累，表现为"带不动"，
⚠ 这是**体验问题**，不会报错，只体现在留存上。
⛔ 因此不能用"取平均看起来更公平"来取舍——
两者都不可用，正解通常是加权 + 跨度限制。

【产出】队伍分加权公式 + 公示文案

【判据】公式已公示，且高手与新手组队时双方体验均有数据支撑

【审】`audit/godot/sharding-matchmaking.md#34`


### Step 6　⛔ 排位塞伪装人类的 Bot 是玩家信任问题　`[sharding/07#S6]`

【读】`howto/godot/sharding-matchmaking.md#⚠ 机器人填充是玩家信任问题，不是纯工程问题`

【做】
用 Bot 填补队列能立刻解决排队时长，
⛔ 但在排位 / 锦标赛里这是**玩家信任问题**：
一旦被发现，玩家会怀疑自己所有对局的真实性，包括赢的那些。
⚠ 排位与锦标赛默认不允许伪装人类的 Bot。

【产出】Bot 使用范围（哪些模式允许、是否明示）

【判据】排位 / 锦标赛明确为不允许，且写明是否明示

【审】`audit/godot/sharding-matchmaking.md#35`


### Step 7　⛔ 故意掉分不是玩家自由，是 ranked manipulation　`[sharding/07#S7]`

【读】`howto/godot/sharding-matchmaking.md#3. 匹配与技能分`

【做】
故意连败把分打下去再在低分段碾压，
⛔ 平台已明确按 **ranked manipulation** 处罚，不是"玩法自由"。
⚠ 检测要区分真新手与掉分号（看历史峰值与波动形态），
⛔ 直接按当前分判会误伤。

【产出】掉分操控检测规则（含误伤规避）

【判据】规则中明确区分真新手与掉分号

【审】`audit/godot/sharding-matchmaking.md#36`


### Step 8　⛔ 单次掉线不能封号：惩罚要递增，且必须允许重连　`[sharding/07#S8]`

【读】`howto/godot/sharding-matchmaking.md#3. 匹配与技能分`

【做】
一次掉线就封号会误伤所有网络不稳的玩家。
⛔ 惩罚要递增，且**掉线期间必须允许重连**——
不允许重连会把可挽救的对局直接判负。
⚠ 同时要保证重连**不允许重放同一局**（防止反复进出刷结果）。

【产出】掉线惩罚梯度 + 重连规则（含防重放）

【判据】首次掉线可重连；重连后同一局结果不被重放

【审】`audit/godot/sharding-matchmaking.md#37`


### Step 9　⛔ 赛季重置把分清零不能消除混乱　`[sharding/07#S9]`

【读】`howto/godot/sharding-matchmaking.md#赛季重置三种语义`

【做】
清零看起来是"重新开始"，⛔ 但技能估计与匹配混乱**不会因为清零而消失**——
重置后所有人挤在同一分段，前若干局必定极度混乱。
⚠ 正解是**软重置 / 向均值衰减**，保留估计的不确定性。

【产出】赛季重置语义（软重置公式 + 衰减比例）

【判据】重置后玩家分数向均值收敛，而不是全部归零

【审】`audit/godot/sharding-matchmaking.md#38`


## 3. 参考实现

```gdscript
# ⓘ 承接本步产出：窗口有上限，赛季用软重置
const MATCH_WINDOW_SEC := 120
const MATCH_SCORE_SPREAD_MAX := 200
const SEASON_SOFT_RESET_RATIO := 0.5

# ⛔ 客户端只显示排队时长，⛔ 不参与任何分数计算。
# ⓘ 软重置：向均值收敛，⛔ 不是清零。
func soft_reset(score: int, mean_score: int) -> int:
	return int(round(score + (mean_score - score) * SEASON_SOFT_RESET_RATIO))
```
