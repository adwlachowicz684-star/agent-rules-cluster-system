# 02 2D 纹理三开关与像素清晰度（美术资产域）

> **本步交付**：Filter/Repeat/Mipmap 三个开关定档 + 压缩模式按用途分层 + 像素美术不糊
> **对应**：流程 `howto/godot/art-assets.md` · 审核 `audit/godot/art-assets.md`

## 0. 交付物定义

1. 三类资产（像素 / 高清 2D / UI）各自的三开关取值已定档，写进速查表
2. 压缩模式按**用途**分层，不是统一无损
3. 像素糊的排查按顺序走过一遍，结论有证据
4. Basis Universal 只在发布前 A/B，开发期不铺开
5. `MIPMAP_MEM_HEADROOM` 已算进内存预算

## 2. 工序

### Step 1　Filter 在两处，先分清改哪一处　`[art-assets/02#S1]`

【读】``howto/godot/art-assets.md#Filter``

【做】
4.x 的 Filter / Repeat 在 **CanvasItem 属性**里设，项目设置只是**默认值**。
⛔ 不要只在纹理导入页找 —— 那里没有这两个开关，
⛔ 于是"明明关了过滤却还在糊"会被归因成引擎 bug，而真相是改错了地方。

ⓘ 两层还有个顺序问题：
⛔ 项目设置改了默认，只影响**之后新建**的 CanvasItem，
⛔ 已经摆在场景里的那些仍是旧值，表现为"有的糊有的不糊"。

【产出】三开关速查表（按资产类型分行）

【判据】新场景里放一个精灵，不用手动改就已是目标 Filter。

【审】``audit/godot/art-assets.md#1``

### Step 2　像素糊了，按五个原因顺序查　`[art-assets/02#S2]`

【读】``howto/godot/art-assets.md#1. 像素美术``

【做】
按 Filter → 整数缩放 → 0.5 像素偏移 → 窗口整数缩放 → 后处理/抗锯齿 的顺序查。
⛔ 不要一开始就怀疑源 PNG —— 经典误区，
⛔ 而"让美术重出一遍图"成本极高且**查完也还是糊**，
于是会连着返工两轮才回到真正的原因上。

ⓘ 排查要**冻结相机变换**再比对：
⛔ 相机在动的时候，糊的原因无法归因，
⛔ 因为"糊"本身在动，人会本能地把它归给运动模糊。

【产出】五步排查记录（每步结论 + 截图）

【判据】能指出是哪一步造成的，且改它之后糊消失。

【审】``audit/godot/art-assets.md#2``

### Step 3　Repeat 只对"需要连续铺开"的资产开　`[art-assets/02#S3]`

【读】``howto/godot/art-assets.md#Repeat``

【做】
只给地面、墙壁、噪声、可滚动背景开 Repeat；UI 图标、头像、立绘、NinePatch 一律关。
⛔ 不要"开着更省事" —— 关掉的收益是**采样不会跨到相邻像素**，
而开了之后出问题表现为"边缘出现不该有的像素"，⛔ 排查被引向图集或缩放。

ⓘ **图集资源的 Repeat 判定对象是整个图集纹理**，不是图集内的逻辑区域：
⛔ 图集里只要有一个切片需要 Repeat，整张图集开了就会让**所有切片**都受影响，
⛔ 表现为"只有一两个图标边缘脏了"，看起来像那几个图坏了。

【产出】Repeat 开关清单（逐资产）

【判据】UI 与图标类资产 Repeat 全为关；需要平铺的已开且无脏边。

【审】``audit/godot/art-assets.md#3``

### Step 4　Mipmap 是"缩小稳定性"，不是高清选项　`[art-assets/02#S4]`

【读】``howto/godot/art-assets.md#Mipmap``

【做】
只在相机**显著缩小**或 3D 远距离时开；2D 若相机从不缩小就不要开。
⛔ 不要把它当画质选项 —— 官方口径：相机从不显著缩小时
**没有任何收益，但内存照涨**（约 +33%）。

⛔ 还有一条官方口径别踩：**`mipmaps/limit` 标注为 Unimplemented**，
改它**没有任何效果且不报错**。
⛔ 于是"设了 limit 以为省了内存"是最典型的假优化：数字写进去了，显存一分没少。

【产出】Mipmap 开关清单 + 内存增量已计入预算

【判据】`MIPMAP_MEM_HEADROOM` 已算进 `TEXTURE_BUDGET_MB`。

【审】``audit/godot/art-assets.md#4``

### Step 5　压缩按用途分层，不是"无损最好"　`[art-assets/02#S5]`

【读】``howto/godot/art-assets.md#2. 纹理压缩``

【做】
像素/UI/含 1px 细节用 Lossless；数量多尺寸大的照片背景与立绘用 VRAM Compressed。
⛔ 不要统一无损 —— 无损在 3D 与大图上直接把显存与包体顶满，
⛔ 而它在小图上**看起来完全正常**，于是爆内存时没人怀疑是它。

ⓘ 分层的依据要写进文档：
⛔ 没有写下来就会出现"这张也无损吧"的逐张破例，
⛔ 而破例是**增量**的，出包时才发现总账超了。

【产出】压缩模式分层表 + 每层的预算占比

【判据】任一张图能按表查出它该用什么模式，不需要问人。

【审】``audit/godot/art-assets.md#6``

### Step 6　Basis Universal 只在发布前 A/B　`[art-assets/02#S6]`

【读】``howto/godot/art-assets.md#Basis Universal``

【做】
开发期用 Lossless / VRAM Compressed，发布前把候选纹理批量转 Basis 做 A/B 验收。
⛔ 不要一开始就用 Basis —— 官方口径它的质量**较低**（块状伪影、颜色偏移、法线方向异常）
且**编码时间长**，⛔ 开发期用它等于每次改图都多等一次编码。

⛔ 另外两条要写进清单：
**显存并不比普通 GPU 压缩低**；**不支持浮点图像**（Godot 内部回退到 VRAM Compressed）。
⛔ 于是"用 Basis 是为了省显存"这个理由不成立，而它是被引用最多的理由。

【产出】Basis 候选清单（含"不适合"的四类：面部/小字 UI/像素硬边/法线）

【判据】候选清单里不含"不适合"的四类；A/B 结论有截图。

【审】``audit/godot/art-assets.md#7``


## 3. 参考实现

```gdscript
# ⓘ 本块内自足：常量在此声明，承接上文即可直接用
const MIPMAP_MEM_HEADROOM := 0.33   # 官方：mipmap 约 +33% 内存
const TEXTURE_BUDGET_MB := 256.0    # 单场景纹理显存上限（01 参数表登记）

# ⛔ 只算未压缩 RGBA8 的粗略占用，压缩格式的实测值以渲染器统计为准
func estimate_mb(w: int, h: int, with_mipmaps: bool) -> float:
    var bytes := float(w * h * 4)
    if with_mipmaps:
        bytes *= (1.0 + MIPMAP_MEM_HEADROOM)
    return bytes / 1048576.0

func fits_budget(items: Array) -> bool:
    var total := 0.0
    for it in items:
        total += estimate_mb(it.w, it.h, it.mipmaps)
    return total <= TEXTURE_BUDGET_MB
```

## 5. 常见返工

| 现象 | 返工到 |
|---|---|
| 关了过滤还在糊 | 返工 Step 1（改的是导入页不是 CanvasItem） |
| 让美术重出图后仍糊 | 返工 Step 2（没按顺序查） |
| 图标边缘出现邻图像素 | 返工 Step 3（Repeat 误开） |
| 设了 mipmaps/limit 显存没降 | 返工 Step 4（官方标注未实现） |
| 出包后显存爆 | 返工 Step 5（压缩没分层） |
| 每次改图都要等很久 | 返工 Step 6（开发期用了 Basis） |
