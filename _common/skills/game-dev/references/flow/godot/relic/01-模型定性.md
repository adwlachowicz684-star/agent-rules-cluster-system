## 0. 交付物定义

⚠ **这一步不写业务代码，但它是全域地基。**
⛔ 跳过它直接建数据结构，做到一半会发现"换装备后遗物没了"或
"局外解锁被局末清空"，改动面是**全系统级**的。

做完这一步，应该能**当场回答三句话**：

1. 是 **遗物**（局内整局保留）/ **词条**（换装即失效）/ **局外解锁**（永久）中的哪一个
2. ⚠ **它什么时候消失** —— 这是三者唯一可靠的区别
3. 一局结束后，它还在不在存档里

**产出物**（下游按名字对接）：

```text
RelicBase.relic_id / rarity / effects[{stat,value,op}] / tags
RelicInstance.relic_id / instance_id / stacks
```

⚠ 两层都要有。⛔ 只做一层 = 默认选了"遗物不可叠加、无实例状态"。

## 2. 工序

### Step 1　⚠ 用"什么时候消失"定性　`[relic/01#S1]`

【读】`howto/godot/relic-build.md#0. 先分清三件事`

【做】回答一个问题：**一局结束后，它还在不在**。
- 不在，局内整局保留 → **遗物**
- 换装备就没 → **词条**
- 存档里一直在 → **局外解锁**

ⓘ 判据不是"游戏里叫什么名字"。
⚠ 很多叫"词条"的系统实际是遗物（局内三选一拿到后整局生效）。

【产出】一句话定性 + 一条原始需求依据

【判据】⚠ 能指出**需求文档里哪一条**支持这个判断

【审】`audit/godot/relic-build.md#1`

### Step 2　⛔ 显式排除另外两种　`[relic/01#S2]`

【读】`howto/godot/relic-build.md#0. 先分清三件事`

【做】把排除的两种**写下来，附业务需求理由**。

ⓘ 三个月后有人提"能不能让遗物永久保留"时，这条记录是唯一能说明
"当时的结构为什么不支持"的东西。

【产出】两条"本次不做 X，因为 Y"

【判据】每条都指向**具体业务需求**，⛔ 不是"太复杂"

【审】`audit/godot/relic-build.md#1`

### Step 3　⚠ 效果可共用、来源不可共用　`[relic/01#S3]`

【读】`howto/godot/relic-build.md#0. 先分清三件事`

【做】三者可以共用 `{stat, value, op}` 的**效果**结构，
⛔ 但**来源**结构必须分开。

⚠ 原因：失效时机完全不同。共用来源会导致
"换装备把遗物一起清了"或"局末把局外解锁一起清了"。

【产出】效果结构统一 + 来源结构分离

【判据】⚠ 清空局内状态的操作，**不会**影响局外解锁

【审】`audit/godot/relic-build.md#1`

### Step 4　⚠ 确认是否可叠加　`[relic/01#S4]`

【读】`howto/godot/relic-build.md#1. 遗物池三层：池 / 稀有度 / 实例`

【做】若可叠加，用 `RelicInstance.stacks`，
⛔ 不要"重复持有多个实例"。

ⓘ 用多实例表达的话，协同判定（04）要处理"同一 id 出现多次"，
UI 要合并显示——两处都会变复杂。

【产出】`stacks` 字段（若可叠加）

【判据】⚠ 同一遗物拿 3 次，**实例只有一个且 stacks=3**

【审】`audit/godot/relic-build.md#3`

### Step 5　⚠ 写下验证这三者的最小场景　`[relic/01#S5]`

【读】`howto/godot/relic-build.md#0. 先分清三件事`

【做】写三个可演示的场景：

| 定性为 | 证明场景 |
|---|---|
| 遗物 | 一局结束后**清空**，但局内换装备**仍在** |
| 词条 | 换一件装备，**该效果立即消失** |
| 局外解锁 | 退出重进，**仍在** |

ⓘ 这三个场景是 07 验收的输入。⛔ 现在不定，到 07 只能凭感觉。

【产出】三个可演示场景（写进 00 总览第 0 节）

【判据】⚠ 每个场景都能在 10 分钟内手工跑完

【审】`audit/godot/relic-build.md#1`

## 5. 常见返工

**① 定性时看名词不看失效时机。** 叫"词条"的实际整局生效。

**② 来源结构共用。** 换装备把遗物一起清了。

**③ 叠加用多实例。** 协同与 UI 两处变复杂。
