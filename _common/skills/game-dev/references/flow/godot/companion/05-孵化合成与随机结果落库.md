# 05 孵化合成与随机结果落库（伴侣物域）

> **本步交付**：开始时 roll 并落库 + 扣材料时序 + 并发串行
> **对应**：流程 `howto/godot/companion.md` · 审核 `audit/godot/companion.md`

## 0. 交付物定义

1. 随机结果在**开始时**就 roll 并**落库**，⛔ 不在领取时随机
2. 材料在**开始时**立即扣除，⛔ 不等完成时
3. 多槽孵化遍历**全部槽**
4. 取消返还考虑了背包已满（检查空间或存临时区）
5. 多合成台并发在服务端串行或加互斥；队列上限查总数

## 1. 前置检查清单

- [ ] 结果是开始时 roll 的，且已持久化
- [ ] 材料是开始时扣的
- [ ] 多槽全部都会推进
- [ ] 取消返还不会凭空消失
- [ ] 并发请求在服务端串行

## 2. 工序

### Step 1　结果在开始时就 roll 并落库　`[companion/05#S1]`

【读】`howto/godot/companion.md#4. 孵化与合成`

【做】
孵化 / 合成**开始时**就 roll 出结果，并把结果**持久化**。
⛔ 在领取时才随机 —— 玩家可以**反复读档或重发请求刷稀有度**，
⛔ 这是本域唯一一个"发版后靠补日志无法定位"的漏洞：
日志里每一次都是"正常随机"，没有任何异常痕迹。

ⓘ 落库这半步同样关键：只存在内存里 —— 重连后重 roll，
⛔ 等于又变回"领取时随机"，可以反复刷。

【产出】结果字段（含稀有度与具体条目）+ 落库时机说明

【判据】同一订单读档重发 10 次，结果完全一致。

【审】`audit/godot/companion.md#20`、`audit/godot/companion.md#38`

### Step 2　材料在开始时立即扣，⛔ 不等完成　`[companion/05#S2]`

【读】`howto/godot/companion.md#4. 孵化与合成`

【做】
合成开始时立即扣材料。
⛔ 等完成时再扣 —— 同一批材料被**多个合成台重复利用**，
表现为"一份材料出了两份产物"，
⛔ 而每个合成台的单条流程单看都正确（都检查了、都扣了）。

ⓘ 与 `economy` 域的接缝：材料与产出走**同一账本**，
⛔ 本域不另定货币口径，但扣减必须走同一个事务。

【产出】扣减时序（开始即扣）+ 与 `economy` 账本的事务契约

【判据】两台合成台同时用同一批材料，只有一台成功。

【审】`audit/godot/companion.md#21`

### Step 3　多槽孵化要遍历全部槽　`[companion/05#S3]`

【读】`howto/godot/companion.md#4. 孵化与合成`

【做】
多槽孵化每次推进都**遍历全部槽**。
⛔ 只更新第一个（比如提前 `return` 或找到第一个就 `break`）——
其他槽**永远不完成**，
表现为"第二个孵化槽点了没反应"，⛔ 而第一个槽完全正常，
于是排查被引向"第二个槽的 UI 没绑上"。

ⓘ 这条在单槽测试时 100% 通过，
⛔ 只有开放多槽后才暴露，而那时玩家已经用一段时间了。

【产出】槽位推进的遍历实现（⛔ 无提前退出）

【判据】三个槽同时孵化，三个都按时完成。

【审】`audit/godot/companion.md#22`

### Step 4　取消返还要考虑背包已满　`[companion/05#S4]`

【读】`howto/godot/companion.md#4. 孵化与合成`

【做】
取消合成返还材料时，先检查背包空间，不够就**存临时区**。
⛔ 直接返还 —— 背包满时返还失败，材料**凭空消失**，
⛔ 而日志里"已返还"，玩家却没拿到，
这是典型的"两边都自洽"的问题，客服无法判责。

ⓘ 与 `inventory` 域的接缝：临时区的存取事务走 `inventory` 口径，
⛔ 本域只保证"不凭空消失"。

【产出】返还流程（含背包满时的临时区分支）

【判据】背包满时取消合成，材料进入临时区且可领取。

【审】`audit/godot/companion.md#23`

### Step 5　并发串行，队列上限查总数　`[companion/05#S5]`

【读】`howto/godot/companion.md#5. 服务端权威边界`

【做】
多台合成台的并发请求在**服务端串行**或加互斥；
队列上限检查算 `queue + active` 的**总数**。
⛔ 依赖"玩家点不了那么快" —— 客户端脚本同时点两台**必然**出问题。
⛔ 只算其中一个 —— 队列溢出，
表现为"队列显示 3/3，实际排了 5 个"，而 UI 显示确实是对的。

ⓘ 与 `ops` 域的接缝：活动期多倍掉落会放大这条，
⛔ 本域只保证服务端串行，不另定活动规则。

【产出】服务端串行化实现 + 队列上限的计数口径

【判据】脚本同时提交 10 个请求，队列不越界、无重复产出。

【审】`audit/godot/companion.md#24`、`audit/godot/companion.md#39`

## 3. 参考实现

```gdscript
# ⓘ 承接本步产出：开始时 roll 并落库 + 开始即扣 + 全槽遍历
class_name HatchOrder extends Resource
@export var order_id: StringName
@export var result_id: StringName      # ⛔ 开始时 roll，领取时只读
@export var result_rarity: int
@export var started_at: int            # 服务端时间戳
@export var ready_at: int

func start_hatch(slots: Array) -> void:
    for s in slots:                    # ⛔ 遍历全部槽，不要提前 return
        if s.is_empty():
            continue
        consume_materials(s)           # ⛔ 开始即扣，不等完成
        s.result_id = roll(s)          # ⛔ 开始时 roll
        s.ready_at = server_now() + s.duration
        persist(s)                     # ⛔ 必须落库，否则重连重 roll
```

## 4. 验收清单

- [ ] 读档重发结果一致
- [ ] 一台成功、另一台材料不足
- [ ] 三个槽全部完成
- [ ] 背包满时材料进临时区
- [ ] 并发不越界、无重复产出

## 5. 常见返工

| 症状 | 原因 | 回到 |
|---|---|---|
| 玩家能刷出稀有度 | 领取时才随机 / 没落库 | S1 |
| 一份材料出两份产物 | 完成时才扣 | S2 |
| 第二个孵化槽没反应 | 只更新第一个 | S3 |
| 取消后材料没了 | 背包满直接返还 | S4 |
| 队列显示 3/3 实际 5 个 | 上限只算其一 | S5 |
