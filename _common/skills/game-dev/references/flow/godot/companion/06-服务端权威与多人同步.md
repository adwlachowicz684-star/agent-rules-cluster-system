# 06 服务端权威与多人同步（伴侣物域）

> **本步交付**：权威边界清单 + 两阶段确认 + 归属清理
> **对应**：流程 `howto/godot/companion.md` · 审核 `audit/godot/companion.md`

## 0. 交付物定义

1. 权威边界清单已写下（哪些必须服务端、哪些只能客户端预测）
2. 上下马的判定由服务端校验距离与地形条件
3. 骑手与坐骑作为**两个实体**各自同步，authority 一致
4. 上马走**两阶段确认协议**
5. 召唤物的 `caster_id` 已存，释放时仇恨表已清理

## 1. 前置检查清单

- [ ] 成长/进化/死亡/复活判定在服务端
- [ ] 上下马判定在服务端
- [ ] 骑手与坐骑的 authority 均已转移
- [ ] 上马有两阶段确认
- [ ] 召唤物有 caster_id 且释放即清仇恨

## 2. 工序

### Step 1　先写权威边界清单，⛔ 不最后统一补　`[companion/06#S1]`

【读】`howto/godot/companion.md#5. 服务端权威边界`

【做】
写下边界清单。必须服务端：宠物成长/进化、忠诚度与饱食度衰减、
死亡与复活判定、上下马判定（距离、条件）、召唤物创建/销毁/数量上限、
召唤物伤害与归属、孵化计时与结果、合成材料与结果、合成队列。
客户端只能预测：宠物跟随动画（纯表现）、坐骑移动输入（服务端校验最终位置）、UI 进度条。
⛔ 把成长/进化判定放在客户端 —— 改包即可直接满级，
⛔ 而服务端日志里"从未发生过升级"，两边都自洽。

ⓘ 这条要**随功能点同步写**，不能最后统一补：
补的时候会顺手把"客户端预测"也划进权威，
表现为"手感变钝"但没人敢改回去。

【产出】权威边界清单（含"客户端只能预测"三项）

【判据】改包把宠物等级改成满级，服务端拒绝且不入库。

【审】`audit/godot/companion.md#43`

### Step 2　上下马由服务端校验距离与条件　`[companion/06#S2]`

【读】`howto/godot/companion.md#2. 坐骑：核心是"谁在驱动移动"`

【做】
上下马的判定放服务端，校验**距离与地形条件**。
⛔ 只做客户端距离判定 —— 可**瞬移上马 / 穿墙上马**，
表现为"角色卡在屋顶却骑上了马"，
⛔ 而客户端的距离检查在它自己看来是通过的。

ⓘ 与 03 的接缝：03 定"驱动权怎么转移"，本步定"**谁批准转移**"。
⛔ 顺序是先批准、再转移，⛔ 反过来会出现"驱动已转移但服务端不认"的中间态。

【产出】上下马的服务端校验项（距离、地形、状态、坐骑归属）

【判据】客户端改坐标后请求上马，服务端拒绝。

【审】`audit/godot/companion.md#44`

### Step 3　骑手与坐骑是两个实体，authority 都要转　`[companion/06#S3]`

【读】`howto/godot/companion.md#多人同步`

【做】
把骑手与坐骑当作**两个需要同步的实体**分别处理 authority。
⛔ 假设"同步了骑手位置就等于同步了坐骑" ——
只转一个的 authority，延迟期间**骑手和坐骑各自移动**，
表现为"上马后人和马分离漂移"，⛔ 而两边的同步代码单看都正确。

ⓘ 另有一条官方边界（见 `social` 域）：
`set_multiplayer_authority()` 的 `recursive` 只对**调用时已存在的子树**生效，
⛔ 后加入的子节点不继承，其 authority RPC 会被静默拒绝。

【产出】两个实体的 authority 归属表（含转入/转出时机）

【判据】上马后任意时刻，两端看到的骑手与坐骑相对位置一致。

【审】`audit/godot/companion.md#41`

### Step 4　上马走两阶段确认，⛔ 不等 authority 落定　`[companion/06#S4]`

【读】`howto/godot/companion.md#多人同步`

【做】
用**两阶段确认协议**：请求上马 → 服务端转移 authority → 确认后才切换到骑乘状态机。
⛔ 认为"authority 转了就能骑" —— 转移有延迟，
延迟期间骑手与坐骑会**各自移动**，
表现为"上马瞬间人和马短暂分离"，⛔ 而这个窗口极短，测试时容易被当成偶发抖动忽略。

ⓘ 客户端可以立刻播放上马动画（纯表现），
⛔ 但状态机切换必须等确认 —— 这是"客户端只能预测表现"那条边界的具体落点。

【产出】两阶段确认的时序（含请求 / 转移 / 确认 / 回退四个分支）

【判据】人为延迟服务端响应，客户端不会提前进入骑乘状态机。

【审】`audit/godot/companion.md#12`

### Step 5　召唤物存 caster_id，释放时清仇恨　`[companion/06#S5]`

【读】`howto/godot/companion.md#3. 召唤物：数量是性能死穴`

【做】
伤害归属存 `caster_id`，并在释放时清理仇恨表。
⛔ 不存归属 —— 召唤物消失后目标仍向**召唤者**报仇恨，
表现为"召唤物没了，怪还在追主人"，
⛔ 而仇恨系统本身完全正常，排查被引向仇恨逻辑。

ⓘ 归属同时决定**伤害统计与掉落归属**，
⛔ 缺失会让统计口径对不上（击杀数有、掉落无）。

【产出】`caster_id` 字段 + 释放时的清理项清单

【判据】召唤物消失后，目标立即停止向召唤者报仇恨。

【审】`audit/godot/companion.md#19`

### Step 6　客户端只能预测的三项，⛔ 不许扩列　`[companion/06#S6]`

【读】`howto/godot/companion.md#5. 服务端权威边界`

【做】
明确只允许三项客户端预测：宠物跟随动画、坐骑移动输入、UI 进度条。
⛔ 扩列到"宠物伤害结算""孵化完成判定" ——
前者可改包改伤害，后者可改包提前领取，
⛔ 两者在单机测试里表现完美。

ⓘ 判定方法很简单：把这一项放到服务端跑，手感会不会明显变钝？
⛔ 不会变钝却还在客户端的，就是扩列。

【产出】预测项白名单（三项）+ 每项的"为什么可以"一句话

【判据】白名单外没有任何伴侣物判定跑在客户端。

【审】`audit/godot/companion.md#43`

## 3. 参考实现

```gdscript
# ⓘ 承接本步产出：两阶段确认 + 双实体 authority + caster_id
# ⛔ 客户端只播放表现，状态机切换必须等服务端的 confirm_mount
@rpc("any_peer", "reliable")
func request_mount(mount_id: int) -> void:
    var sender := multiplayer.get_remote_sender_id()
    if not server_check_distance(sender, mount_id):   # ⛔ 服务端校验距离与地形
        return
    var m := get_mount(mount_id)
    m.set_multiplayer_authority(sender)               # 坐骑 authority
    get_rider(sender).set_multiplayer_authority(sender) # ⛔ 骑手是第二个实体，也要转
    confirm_mount.rpc_id(sender, mount_id)

@rpc("authority", "reliable")
func confirm_mount(mount_id: int) -> void:
    enter_mounted_state(mount_id)   # ⛔ 只有确认后才切状态机
```

## 4. 验收清单

- [ ] 改包满级被拒
- [ ] 改坐标上马被拒

- [ ] 延迟确认不会提前进状态机

- [ ] 白名单外无客户端判定

## 5. 常见返工

| 症状 | 原因 | 回到 |
|---|---|---|
| 有人宠物满级 | 成长判定在客户端 | S1 |
| 卡在屋顶却骑上马 | 只做客户端距离判定 | S2 |
| 上马后人和马分离漂移 | 只转了一个 authority | S3 |
| 上马瞬间短暂分离 | 没走两阶段确认 | S4 |
| 召唤物没了怪还追主人 | 仇恨未清 | S5 |
