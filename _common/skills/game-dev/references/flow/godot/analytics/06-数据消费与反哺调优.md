# 06 数据消费与反哺调优（分析域）

> **本步交付**：流失曲线 + 热力图 + 远程配置闭环
> **对应**：流程 `howto/godot/analytics.md` · 审核 `audit/godot/analytics.md`

## 0. 交付物定义

1. 能输出**每一步流失多少**的曲线
2. 能区分"太难"与"太无聊 / 迷路"
3. 难度参数可由服务端下发，⛔ 不必发版
4. 每次调参都有**可回溯的记录**（改了什么、何时生效）
5. 数据变化能归因到具体改动

## 1. 前置检查清单

- [ ] 已有流失曲线（按步）
- [ ] ⚠ 已能同时看到**时长分布**与**重试次数**
- [ ] 已确定哪些参数走远程配置
- [ ] ⚠ 已有调参记录（参数快照 + 生效时间）

## 2. 工序

### Step 1　先画流失曲线，再看单点指标　`[analytics/06#S1]`

【读】`howto/godot/analytics.md#4. 关卡难度调优（怎么把数据用起来）`

【做】
输出按步的流失曲线：每一步流失多少，**陡降处就是卡点**。
⛔ 只看整体通关率——它告诉你"有问题"，
但说不出问题在第几步，于是只能笼统地"降低整体难度"，
⛔ 而真正的卡点可能只是某一处交互没提示。

【产出】按步流失曲线（可定位到具体步骤）

【判据】能指出流失最陡的那一步，并说出它对应的游戏内容。

【审】`audit/godot/analytics.md#33`

### Step 2　⛔ 区分"太难"和"太无聊"　`[analytics/06#S2]`

【读】`howto/godot/analytics.md#4. 关卡难度调优（怎么把数据用起来）`

【做】
死亡次数高 + 反复重试 = **太难**；
停留时间长 + 无死亡 = **迷路或无聊**。
两者的改法完全相反（前者降难度，后者加指引或节奏）。
⛔ 只看通关率低就判定"太难"——若真实原因是迷路，
调低难度不会提高通关率，⛔ 于是得出"调了没用"的错误结论，
并把数值改到一个更难恢复的位置。

【产出】联合判据：死亡次数 × 重试次数 × 停留时长

【判据】给出一个关卡的数据，能判定属于"太难"还是"迷路"。

【审】`audit/godot/analytics.md#11`

### Step 3　难度参数走远程配置　`[analytics/06#S3]`

【读】`howto/godot/analytics.md#4.1 远程配置与闭环`

【做】
把可调数值放在服务端，客户端启动时拉取。
⛔ 每次调参都要发版——调一次等一周，
反馈周期长到无法做 A/B，也就谈不上"用数据调优"。

【产出】远程配置项清单 + 客户端拉取与本地兜底（取不到时用内置默认）

【判据】改服务端数值后客户端重启即生效，且服务端不可达时仍能玩。

【审】`audit/godot/analytics.md#38`

### Step 4　每次调参都要留可回溯记录　`[analytics/06#S4]`

【读】`howto/godot/analytics.md#4.1 远程配置与闭环`

【做】
记录：改了哪个参数、旧值、新值、生效时间。
⛔ 只改不留痕——数据变化了却不知道是哪个改动引起的，
下次只能凭印象重试一遍，⛔ 于是"调优"退化成反复试。

【产出】参数变更日志（参数名 / 旧值 / 新值 / 生效时间）

【判据】任意一天的数据波动，都能查到当天生效的参数变更。

【审】`audit/godot/analytics.md#1`

### Step 5　结论必须落到具体改动　`[analytics/06#S5]`

【读】`howto/godot/analytics.md#4. 关卡难度调优（怎么把数据用起来）`

【做】
分析产出的是**要改什么**（哪个步骤、加什么提示、调哪个数值），
不是"这一关偏难"这类无法行动的描述。
⛔ 只出结论不出行动项——数据看完了但没人知道下一步做什么，
埋点投入就白费了。

【产出】结论 → 行动项映射（含负责的功能点与验收方式）

【判据】每份分析结论都能对上一个具体的待改项。

【审】`audit/godot/analytics.md#12`

## 5. 常见返工

| 症状 | 原因 | 回到 |
|---|---|---|
| 调低难度没用 | 真实原因是迷路，不是太难 | S2 |
| 数据波动查不到原因 | 调参没留记录 | S4 |
| 调一次参数等一周 | 数值写死在包里 | S3 |
