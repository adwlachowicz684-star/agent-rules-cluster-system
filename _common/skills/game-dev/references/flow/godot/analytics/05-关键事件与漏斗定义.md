# 05 关键事件与漏斗定义（分析域）

> **本步交付**：付费 / 通关 / 流失点 + 立即上报通道
> **对应**：流程 `howto/godot/analytics.md` · 审核 `audit/godot/analytics.md`

## 0. 交付物定义

1. 已列出**关键事件**清单（付费、通关、注册转化等不可逆节点）
2. 关键事件走**立即上报**通道，⛔ 不等批量
3. 漏斗每一步都有明确的上一步与进入条件
4. 流失点埋在**真实的流失位置**，不是"关卡开始"
5. 枚举值用稳定字符串
6. 死亡点 / 热力图有对应的数据来源

## 1. 前置检查清单

- [ ] 已列出关键事件清单
- [ ] ⚠ 已确认关键事件不走批量延迟通道
- [ ] 已定义至少一个完整漏斗（含每一步进入条件）
- [ ] 已确认枚举用稳定字符串

## 2. 工序

### Step 1　先分清哪些是关键事件　`[analytics/05#S1]`

【读】`howto/godot/analytics.md#常用事件清单`

【做】
关键事件 = 不可逆且要对账的节点：付费、通关、注册、领取不可逆奖励。
其余（移动、点击、打开面板）是普通事件，走批量。
⛔ 不做区分、全部一视同仁——关键事件被埋没在海普通事件里，
要么一起延迟（对账差），要么一起立即发（请求风暴）。

【产出】关键事件清单（明确列出，可评审）

【判据】指着付费与通关，能确认它们都在关键事件清单里。

【审】`audit/godot/analytics.md#32`

### Step 2　⛔ 关键事件必须立即上报，不走批量　`[analytics/05#S2]`

【读】`howto/godot/analytics.md#2. 实现：离线优先`

【做】
付费、通关等节点**立即 flush**，不等 `BATCH_SIZE` / `FLUSH_INTERVAL_SEC`。
⛔ 付费事件走批量——玩家付费后强杀进程退出，
事件还在队列里没发出去，⛔ 于是"付费成功但后台无记录"，
对账时表现为**服务端有订单、分析后台无事件**，且排查方向会被引到后端。

【产出】`track_critical()`：入队后立即触发 flush

【判据】付费后立即强杀进程，服务端仍能收到该付费事件。

【审】`audit/godot/analytics.md#31`

### Step 3　漏斗每一步要有明确进入条件　`[analytics/05#S3]`

【读】`howto/godot/analytics.md#4. 关卡难度调优（怎么把数据用起来）`

【做】
漏斗不是"几个事件的列表"，而是**有序的、每步有明确进入条件的序列**。
⛔ 只记录事件不定义顺序——事后只能靠时间戳猜先后，
而时间戳又依赖客户端时钟（见 01/S4），一步错整条漏斗错。

【产出】漏斗定义（步骤序 + 每步进入条件 + 超时判定）

【判据】给出一个玩家的行为序列，能 unambiguous 地算出他走到第几步。

【审】`audit/godot/analytics.md#14`

### Step 4　流失点埋在真实流失位置　`[analytics/05#S4]`

【读】`howto/godot/analytics.md#4. 关卡难度调优（怎么把数据用起来）`

【做】
流失点应对应"玩家实际放弃的那一步"（死亡、卡关退出、支付页返回）。
⛔ 只在关卡开始处打点——只能看到"来了多少人"，
看不出人在**哪里**走掉，也就无从判断该改哪里。

【产出】流失点事件（含位置标识：关卡 / 步骤 / 子区域）

【判据】能画出一条"每一步流失多少"的曲线，而不是只有一个总数。

【审】`audit/godot/analytics.md#33`

### Step 5　枚举用稳定字符串，不用数字　`[analytics/05#S5]`

【读】`howto/godot/analytics.md#命名规范（可直接抄）`

【做】
取值域写成稳定的英文字符串（如 `"sword"` / `"potion"`），不用数字下标。
⛔ 用数字省空间——后续无法解读，
且一旦有人往枚举中间插入一项，**所有历史数据的语义全部错位**，
⛔ 这种错位不报错，看报表的人只会觉得"数据变了"。

【产出】枚举取值域表（字符串常量）+ 说明"中间不可插入"

【判据】任一条历史数据，其枚举值能在当前取值域表中找到对应含义。

【审】`audit/godot/analytics.md#9`

### Step 6　死亡点与热力图要有数据来源　`[analytics/05#S6]`

【读】`howto/godot/analytics.md#4. 关卡难度调优（怎么把数据用起来）`

【做】
死亡点事件带坐标或区域标识，供热力图聚合。
⛔ 只记"死了"不记"死在哪"——热力图画不出来，
只能退回"这一关整体太难"这种无法行动的结论。

【产出】死亡点事件（含区域 / 坐标字段）

【判据】能按区域聚合死亡次数并排序。

【审】`audit/godot/analytics.md#11`


## 3. 参考实现

```gdscript
# ⓘ 承接本步产出：关键事件立即 flush
func track_critical(event: String, params := {}) -> void:
    track(event, params)
    flush()      # ⛔ 不等攒够批量、也不等定时触发
```

## 4. 验收清单

- [ ] 付费与通关都在关键事件清单里
- [ ] 付费后立即强杀进程，服务端仍能收到

- [ ] 死亡事件带区域 / 坐标，能按区域聚合排序

## 5. 常见返工

| 症状 | 原因 | 回到 |
|---|---|---|
| 付费成功但后台无记录 | 付费事件走批量后强杀 | S2 |
| 历史枚举对不上 | 往枚举中间插入了一项 | S5 |
| 说不出玩家在哪流失 | 只在关卡开始处打点 | S4 |
