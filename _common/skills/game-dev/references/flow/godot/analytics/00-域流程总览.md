# 数据分析与埋点（事件契约 / 采集 / 上报 / 合规 / 消费）—— 域流程总览

> ⚠ **第 0 步：先定做什么。**
> 本域有 7 个功能点，⛔ **不是全做** —— 按本次需求挑。

## 0. 先定做什么

| 本次要做的 | 走哪些功能点 |
|---|---|
| 只要"有个埋点，能看日活" | 01 → 02 → 03 → 04 → 07 |
| 要付费 / 通关等关键事件与漏斗 | 01 → 02 → 03 → 04 → 05 → 07 |
| 要用来调关卡难度、做流失分析 | 01 → 02 → 03 → 04 → 05 → 06 → 07 |
| 全套数据分析 | 01 → 02 → 03 → 04 → 05 → 06 → 07 |

⛔ **只要"能发出去"的项目，02 也不能跳过** ——
"同意之前不采集"是合规硬约束，不是可选优化。

ⓘ 若本次只是**"调试期打日志、看变量"**，
那是 `debugging.md` 的事，⛔ 不要套本域——
本域管的是**上线后仍在运行、要跨版本可比的数据管道**。

ⓘ 分工：
- `howto/godot/analytics.md` 讲**单个要素怎么实现**（事件模型、离线优先、后端选型、难度调优）
- 本域讲**这些要素按什么顺序做、怎么保证数据不丢、怎么保证能用来做决策**

⛔ 若本域某步需要"各地法规的具体保存期限"这类细节，
指向 `compliance` 域，**不在这里重复**（库里没有的就是没有，⛔ 不许编一个天数出来）。

## 1. 功能点拆解（按依赖，不可颠倒）

| # | 功能点 | 依赖 | 交付物 |
|---|---|---|---|
| 01 | 埋点契约与事件字典 | — | 命名规范 + 不可变承诺 + 事件字典落文档 |
| 02 | 身份会话与合规边界 | 01 | 可重置 player_id + 同意开关 + 同意前零采集 |
| 03 | 采集与离线缓存 | 01, 02 | 本地队列 + 持久化 + 退出保存 + 上限 |
| 04 | 上报通道与失败重试 | 03 | 批量 + 幂等 + 退避重试 + 超时 |
| 05 | 关键事件与漏斗定义 | 01, 03, 04 | 付费 / 通关 / 流失点 + 立即上报通道 |
| 06 | 数据消费与反哺调优 | 05 | 流失曲线 + 热力图 + 远程配置闭环 |

⚠ **01 必须在一切之前**：事件字典是**接口契约**。
先写代码后补字典，等于先发货后签合同——
⛔ 上线后改事件名，历史数据立刻不可比（见 01）。

⚠ **02 必须在 03 之前**：采集一旦开始，
"同意前不采集"就已经被破坏过一次，⛔ 且无法追溯哪些数据是违规采的。

## 2. 与其他域的接缝

> ⚠ **组合的真正难点不是排序，是接缝。**
> 下面每条都必须能指认到具体符号或字段，⛔ 不能是"做完了"。

| 接缝 | 契约 |
|---|---|
| `monetization` 域 商业化 | 付费是 analytics 的**关键事件源**，见 05；⛔ 付费事件不走批量延迟 |
| `compliance` 域 合规 | 同意状态、最小必要、可删除，见 02 |
| `save` 域 存档 | `player_id` 与同意状态持久化走同一套落盘，见 02 |
| `level` 域 关卡流程 | 关卡流失点与检查点即埋点位置，见 05 / 06 |
| `economy` 域 经济 | 货币产出 / 消耗事件进同一事件流，⛔ 不开第二套 |
| `netsync` 域 网络同步 | `session_id` 由会话层下发，⛔ 不用 peer ID 当会话键 |
| `social` 域 社交 | 匹配质量与治理效果即埋点源 |
| `perf` 域 性能 | 帧率 / 卡顿采样进同一管道，但⛔ 采样率要单独控制（高频） |
| `hotupdate` 域 热更 | 事件须带 `app.version`，否则热更前后数据不可比，见 01 |

⛔ **若某条接缝对不上，要单独立一个接线功能点**，
⛔ 不许在各处偷偷转格式（那些转换会散落多处，改接口时找不到）。

⚠ **各功能点自己的验收不能替代集成验收** ——
部件全合格、拼起来不能用，是跨域开发的典型失败。

## 3. 本域最容易做反的顺序

⛔ **先把埋点发出去（03 / 04），后补事件字典与合规（01 / 02）。**

"能看到数据了"是最直观的验收点，
于是先接后端、先让曲线跑起来，
⚠ 而此时事件名是随手起的、player_id 用的是设备 ID、同意开关还没做。

⛔ 后果链：
事件名随手起 → 三个月后发现同名不同义 → 改事件名 → 历史数据断层 →
为修补它加映射层 → 但 player_id 还是设备 ID（合规风险 + 重装即断） →
换 player_id → 老用户的历史全部接不上 →
再补丁加双写 → 而同意开关仍未做 → 违规采集已发生且无法追溯。

⚠ 这些补丁会让 01 / 02 再也没法正确落地——
因为到处都已经有了"以旧事件名 / 设备 ID 为键"的数据。

✅ 正确顺序：先钉死事件契约（01）与合规边界（02），
再谈采集（03）、上报（04）。
