# 01 同步模型选型（网络同步域）

> **前置**：已定死玩法类型与延迟容忍度（见 `00-域流程总览.md` 第 0 节）
> **本步交付**：选定同步模型并写清"内置能做什么、必须自建什么"
> **对应**：做法 `howto/godot/netsync-advanced.md` · 审核 `audit/godot/netsync-advanced.md`

## 0. 交付物定义

⚠ **一句话定位**：Godot 解决"把状态送到对端"，但**不替你消除网络往返**。

`MultiplayerSpawner` / `MultiplayerSynchronizer` 只是**状态同步的自动复制器**。
预测、回滚、插值、锁步、时钟同步——**全部没有内置**，要自己写。

做完这一步，应该能**当场说清**：

1. 选了哪个模型，为什么（⛔ 不是"大家都在用"）
2. 该模型下，**哪些是内置的、哪些必须自建**
3. ⚠ 若选锁步：已确认**引擎不保证确定性**
4. 已确认内置组件同步不了的东西（Resource / RID / 实例 ID）

**产出物**（下游按名字对接）：

```text
同步模型：权威状态同步 / 确定性锁步 / 输入同步+预测回滚 / 纯事件 RPC
"内置能做"与"要自建"的分界表
需要拆成可序列化 ID 的属性清单
```

## 1. 前置检查清单

- [ ] 已定死玩法类型（FPS / RTS / MOBA / 休闲合作 / 回合制）
- [ ] 已定死目标平台（⛔ Web 平台 ENet 不可用，见 02）
- [ ] 已确认要不要回放/观战（锁步天生自带，状态同步要另做）
- [ ] ⚠ 已确认**不能**选客户端权威（除非同机/纯休闲合作）

## 2. 工序

### Step 1　在四种模型里选一个　`[netsync/01#S1]`

【读】`howto/godot/netsync-advanced.md#1. 同步模型选型`

【做】四选一：

| 模型 | 传什么 | 适合 | 代价 |
|---|---|---|---|
| **权威状态同步** | 位置/朝向/血量等结果 | FPS、MMO、生存、大世界 | 快照带宽、纠错 |
| **确定性锁步** | 每 tick 输入 + 种子 | RTS、回合制、棋牌 | 等最慢玩家、浮点极敏感 |
| **输入同步 + 预测回滚** | 输入 + 序号 + 确认 | FPS、MOBA、格斗 | 历史保存、重放、调试成本 |
| **客户端权威** | 角色状态 | 同机、休闲合作 | **极易被篡改**，不适合竞技 |

⚠ **模型名称只是架构缩写，实际项目经常是混合体**：
服务器权威计算 + 客户端本地预测 + 远端实体插值 + 技能按固定 tick + 生成事件用可靠 RPC。

【产出】模型已选定并写进设计文档（含选型理由）

【判据】⚠ 能说出"为什么不是另外三种"——⛔ 不能只说"大家都用这个"

【审】`audit/godot/netsync-advanced.md` 全部条目

### Step 2　RTS 用锁步、FPS 用状态同步的原因　`[netsync/01#S2]`

【读】`howto/godot/netsync-advanced.md#1. 同步模型选型` 的「为什么 RTS 用锁步而 FPS 用状态同步」

【做】理解这两个典型：

**RTS**：单位成百上千，逐属性发位置会吃光带宽；只发输入包量极小。
而且 RTS 常需要回放/观战，确定性模拟天生提供。

**FPS**：等最慢玩家 = 快玩家替慢玩家卡顿。
玩家更容忍"看到的快照略微过期"，所以服务器持有权威世界、客户端预测自己、远端插值。

【产出】选型理由里包含"单位数量/等待容忍度"两项

【判据】⚠ 若选锁步：能说明"我们单位多到发不动位置"；
　　　若选状态同步：能说明"我们不能让快玩家等慢玩家"

【审】`audit/godot/netsync-advanced.md`

### Step 3　⚠ 引擎不保证确定性　`[netsync/01#S3]`

【读】`howto/godot/netsync-advanced.md#1. 同步模型选型` 的 ⚠ 提示

【做】⚠ **Godot 没有承诺跨平台跨版本逐帧确定性。**
浮点、容器遍历顺序、加载顺序、`_process` 与 `_physics_process` 差异、
信号触发顺序都可能改变结果。

**锁步要自己做确定性保证**，引擎不会帮你。

⛔ 若选锁步但没做确定性处理，**上线后各端必然分叉**，
而且分叉是渐进的——前 30 秒看起来完全正常。

【产出】若锁步：已有确定性清单（定长步、不用浮点随机、固定遍历顺序）

【判据】⚠ 同一段输入在两个不同机器上跑 10 分钟，**结果完全一致**

【审】`audit/godot/netsync-advanced.md`

### Step 4　内置组件的硬限制　`[netsync/01#S4]`

【读】`howto/godot/netsync-advanced.md#1. 同步模型选型` 的「内置组件的硬限制」

【做】⚠ `MultiplayerSynchronizer` **不能同步 `Resource` 等 `Object` 类型属性**，
也不能同步每端唯一的实例 ID 或 `RID`。

要把背包 Resource、另一个 Node、物理 RID 拆成**可序列化 ID / 字典 / 数组**，
让两端各自查回来。

【产出】一份"需要拆成 ID 的属性"清单

【判据】⚠ 同步配置里**没有任何** Resource / Node / RID 类型的属性

【审】`audit/godot/netsync-advanced.md`

### Step 5　写出"要自建什么"　`[netsync/01#S5]`

【读】`howto/godot/netsync-advanced.md#0. 一句话定位`

【做】把下表抄进设计文档，逐行标注"我们做不做"：

| 需求 | 内置能做 | 要自建 |
|---|---|---|
| 生成/销毁同步 | ✅ | 权限、白名单、断线清理 |
| 同步已配置属性 | ✅ | tick、压缩、增量、插值 |
| **本地玩家零等待移动** | ❌ | 客户端预测 + 输入历史 |
| **服务器纠正错误预测** | ❌ | 序号、确认、回滚重放 |
| **远端玩家平滑** | ❌ | 固定延迟缓冲 + 插值 |
| **命中回滚判定** | ❌ | 历史快照 + 延迟估计 |
| 客户端输入收集 | ❌ | 输入快照、序号、节流 |

【产出】分界表每行有"做/不做"结论

【判据】⚠ 标"做"的行，在后续功能点里**都能找到对应实现**

【审】`audit/godot/netsync-advanced.md`

## 3. 参考实现

ⓘ 本步是**决策步**，不产代码。产出是一张写进设计文档的表：

```text
同步模型：权威状态同步 + 客户端预测（本地玩家）+ 快照插值（远端玩家）
选型理由：单位 <50，不能让快玩家等慢玩家；需要观战但可另做回放
内置：生成同步 ✅ / 属性同步 ✅
自建：输入序号 + 未确认队列 + 回滚重放 + 快照缓冲 + 插值
不做：锁步（单位少、且引擎不保证确定性）
```

⚠ 这张表要在**写第一行网络代码之前**定稿——
中途换模型的成本等于重写整个网络层。

## 5. 常见返工

| 症状 | 原因 | 回到 |
|---|---|---|
| 上线后各端结果分叉 | 选了锁步但没做确定性 | S3 |
| 快玩家被慢玩家拖卡 | 该用状态同步却用了锁步 | S1 |
| 同步配置加了 Resource 无效 | 内置同步不了 Object | S4 |
| 做到一半发现要重写 | 模型中途换 | S1 |
