## 0. 交付物定义

⚠ **本步最容易"看起来做完了"：后加载的覆盖先加载的，能覆盖就行。**

⛔ 常见假完成：认为"顺序即优先级"已经够用，
⚠ 换贴图也确实生效了，
⛔ 但**登记的是"包声明了哪些路径"，不等于运行时最终解析结果** ——
调试 UI 把它当成"当前生效来源"显示，玩家报告"这个贴图不对"时**查不到真凶**。

做完这一步，应该能**当场演示**：

1. 覆盖链模型已建立（后来者压过先前）
2. ⛔ `replace_files=false` 是"不覆盖"，已被正确理解
3. ⛔ 调试 UI 区分**声明来源**与**解析结果**
4. ⚠ 记录了 `pack_id -> source_path / sha256 / version / load_time`
5. ⚠ 玩家能在 UI 里调整顺序（顺序即优先级）

**产出物**（下游按名字对接）：

```text
覆盖链模型
pack 来源登记表
Mod 顺序调整 UI
```

## 2. 工序

### Step 1　⛔ 覆盖语义：`replace_files=false` 是不覆盖，不是后来者优先　`[04#S1]`

【读】`howto/godot/modding.md#1. 第一条正路：资源包覆盖`

【做】默认传 `true` 让后来者接管；传 `false` 时明确知道同名文件会被**忽略**。

【产出】`replace_files` 使用约定

【判据】⛔ 传 `false` 时，后加载的同名文件**确实被忽略**（不是"后者优先"）

【审】`audit/godot/modding.md#3`

### Step 2　⛔ 声明来源 ≠ 运行时解析结果　`[04#S2]`

【读】`howto/godot/modding.md#8. 冲突检测：声明来源 ≠ 运行时解析结果`

【做】登记每个 pack 声明的路径；另建"实际解析结果"的查询，二者分开存储与展示。

【产出】声明来源表 + 解析结果查询

【判据】⛔ 调试 UI 上两者**分列显示**，标注哪个是声明、哪个是生效

【审】`audit/godot/modding.md#11`

### Step 3　⚠ 记录 pack 来源与 sha256，能区分原版/补丁/DLC/Mod　`[04#S3]`

【读】`howto/godot/modding.md#8. 冲突检测：声明来源 ≠ 运行时解析结果`

【做】维护 `pack_id -> source_path / sha256 / version / load_time` 表。

【产出】来源登记表

【判据】⚠ 玩家报告贴图错误时，能**当场查出**来自哪个包

【审】`audit/godot/modding.md#31`

### Step 4　⚠ 玩家可调整顺序，顺序即优先级　`[04#S4]`

【读】`howto/godot/modding.md#1. 第一条正路：资源包覆盖`

【做】提供 UI 让玩家拖拽调整顺序，顺序变化后按新序重新加载。

【产出】顺序调整 UI + 重载流程

【判据】⚠ 调整顺序后**冲突结果随之改变**（证明顺序真的影响优先级）

【审】`audit/godot/modding.md#30`

### Step 5　⛔ 加载失败要显式记录，不静默继续　`[04#S5]`

【读】`howto/godot/modding.md#8. 冲突检测：声明来源 ≠ 运行时解析结果`

【做】`load_resource_pack()` 返回 false 时记录并提示玩家，不是跳过。

【产出】失败记录 + 提示

【判据】⛔ 故意给一个损坏包，玩家**看到明确提示**（而不是"装了没变化"）

【审】`audit/godot/modding.md#29`

## 3. 参考实现

```text
# 声明来源 vs 解析结果
declared[path] = pack_id          # 包声明了什么

# UI 上两列并排，不能混为一谈
```

## 5. 常见返工

⛔ **返工：调试 UI 把声明来源当生效来源** —— 玩家报告"贴图不对"时查不到真凶，
因为覆盖链上后面的包改了它，而 UI 显示的是最早声明的那个。
