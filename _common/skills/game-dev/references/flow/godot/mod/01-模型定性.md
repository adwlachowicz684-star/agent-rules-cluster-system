# 01 模型定性（mod 域）

> **前置**：无（本域地基）
> **本步交付**：**Mod 类型定型 + 玩家 Mod 与编辑器插件划清界限 + 官方两条路选定**
> **对应**：做法 `howto/godot/modding.md#0. 先定性：玩家 Mod ≠ 编辑器插件`
> 　　　审核 `audit/godot/modding.md`

## 0. 交付物定义

⚠ **本步最容易"看起来做完了"：能加载一个 PCK 就算支持 Mod 了。**

⛔ 常见假完成：照着教程调一次 `load_resource_pack()`，
⚠ 确实能把一个自定义贴图换进去，
⛔ 但 Mod 类型（纯资源 / 数据 / 脚本 / 关卡）没定型，
到做"脚本型 Mod"时才发现没有接口约定与安全边界，
而此时目录结构已经散落在各处。

做完这一步，应该能**当场演示**：

1. 四类 Mod 各有明确边界（资源替换 / 数据 / 脚本 / 关卡）
2. ⛔ 玩家 Mod 与编辑器插件**路径已划清**（不是同一件事）
3. ⚠ 官方两条路已选定（文档化结构 vs 自带 GUI 工具）
4. ⛔ 游戏本体**不用 tool build**（官方安全要求）
5. ⚠ 是否要支持脚本型已决策（决定 05 的深度）

**产出物**（下游按名字对接）：

```text
Mod 类型表（资源/数据/脚本/关卡）
官方两条路的选择结论
tool build 分离约定
```

## 2. 工序

### Step 1　⛔ 先划清：玩家 Mod ≠ 编辑器插件　`[01#S1]`

【读】`howto/godot/modding.md#0. 先定性：玩家 Mod ≠ 编辑器插件`

【做】明确玩家 Mod 走 `load_resource_pack()` 覆盖链；编辑器插件（`EditorPlugin`）只用于扩展 Godot 自身，两者不混用。

【产出】路径划分结论（玩家侧 / 开发者侧）

【判据】⛔ 代码里**不存在**用 `EditorPlugin` 实现玩家 Mod 的路径

【审】`audit/godot/modding.md#1`

### Step 2　⚠ 四类 Mod 分别定型，不共用一套结构　`[01#S2]`

【读】`howto/godot/modding.md#0. 先定性：玩家 Mod ≠ 编辑器插件`

【做】资源替换型走覆盖链；数据型走独立数据目录 + 校验；脚本型走接口约定；关卡型走场景约定。

【产出】四类 Mod 的结构定义

【判据】⛔ 新增一类 Mod 时**不需要改**已有三类的加载逻辑

【审】`audit/godot/modding.md#14`

### Step 3　⛔ 官方两条路要选定，不能骑墙　`[01#S3]`

【读】`howto/godot/modding.md#0. 先定性：玩家 Mod ≠ 编辑器插件`

【做】二选一：文档化资源结构 + 让玩家装 Godot 自建 PCK；或开发者提供 GUI 工具（跑在 tools-enabled build，用 `OS.execute()` 导出）。

【产出】选定结论 + 该路的配套清单

【判据】⚠ 文档里写明了**资源结构约定与脚本接口**，玩家能照着做出可用的包

【审】`audit/godot/modding.md#4`

### Step 4　⛔ 游戏本体不用 tool build，Mod 工具与游戏分离　`[01#S4]`

【读】`howto/godot/modding.md#0. 先定性：玩家 Mod ≠ 编辑器插件`

【做】游戏本体用普通导出模板；Mod 工具单独发布，用 `OS.execute()` 调 Godot 命令行导出 PCK。

【产出】工具与游戏分离的构建约定

【判据】⛔ 发布出去的游戏本体**不含导出能力**（`OS.has_feature("editor")` 为假）

【审】`audit/godot/modding.md#23`

### Step 5　⚠ 决策是否支持脚本型，它决定安全投入　`[01#S5]`

【读】`howto/godot/modding.md#6. ⚠ 安全：Mod 等于给玩家执行任意代码的能力`

【做】明确是否允许 Mod 带脚本；若允许，则 05 必须做完整的风险告知与边界。

【产出】脚本型支持决策（是/否 + 理由）

【判据】⚠ 该决策**已写进文档**，而非隐含在"当然支持"的假设里

【审】`audit/godot/modding.md#6`
