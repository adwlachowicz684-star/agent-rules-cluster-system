# 03 清单与依赖求解（mod 域）

> **前置**：`02-包格式与加载时机.md`

> **对应**：做法 `howto/godot/modding.md#7. 清单、依赖与加载顺序`
> 　　　审核 `audit/godot/modding.md`

## 0. 交付物定义

⚠ **本步最容易"看起来做完了"：读目录顺序加载，能用就行。**

⛔ 常见假完成：按 `DirAccess` 返回顺序或文件名字面序加载，
⚠ 单 Mod 场景完全正常，
⛔ 到有依赖的第二个 Mod 出现时，**依赖者先于依赖加载**，
报错指向依赖者而不是真正的缺失项 —— 排查方向被带偏。

做完这一步，应该能**当场演示**：

1. 清单含 id / 版本 / 依赖 / 加载顺序 / 作者
2. ⛔ 加载顺序由**拓扑排序**产生，不是目录顺序
3. ⛔ 循环依赖**主动检测**并报明确错误
4. ⚠ 清单校验在加载前完成（不是"文件存在即合法"）
5. ⚠ 加载顺序配置进存档（换机器不丢）

**产出物**（下游按名字对接）：

```text
mod.json 清单格式
依赖图 + 拓扑排序
循环依赖检测器
```

## 2. 工序

### Step 1　⛔ 清单字段一次定够，别回头加　`[03#S1]`

【读】`howto/godot/modding.md#7. 清单、依赖与加载顺序`

【做】清单含 id、名称、版本、依赖、加载顺序、作者；缺字段即判非法。

【产出】`mod.json` 格式定义 + 校验器

【判据】⛔ 缺 id 或版本的清单**被拒绝**，而不是"先加载再说"

【审】`audit/godot/modding.md#35`

### Step 2　⛔ 加载顺序由拓扑排序产生，不是目录顺序　`[03#S2]`

【读】`howto/godot/modding.md#7. 清单、依赖与加载顺序`

【做】按依赖图做拓扑排序，被依赖者排在依赖者之前。

【产出】拓扑排序后的加载序列

【判据】⛔ 有依赖的两个 Mod，**依赖者加载时不报错**

【审】`audit/godot/modding.md#20`

### Step 3　⛔ 循环依赖主动检测，报明确错误　`[03#S3]`

【读】`howto/godot/modding.md#7. 清单、依赖与加载顺序`

【做】拓扑排序遇到环时中断，报出环上的具体 Mod id 列表。

【产出】循环依赖检测器 + 错误提示

【判据】⛔ 构造 A→B→A，**报出环上的 id**，而不是"两个都加载失败"

【审】`audit/godot/modding.md#21`

### Step 4　⚠ 清单校验在加载前完成　`[03#S4]`

【读】`howto/godot/modding.md#7. 清单、依赖与加载顺序`

【做】用 `PCKDirAccess`（PCK）或 `ZIPReader.get_files()`（ZIP）在挂载前检查条目，校验清单合法性。

【产出】挂载前预检流程

【判据】⚠ 非法包**在挂载前被拒**，不需要挂载后再回滚

【审】`audit/godot/modding.md#35`

### Step 5　⚠ 加载顺序配置进存档，换机器不丢　`[03#S5]`

【读】`howto/godot/modding.md#7. 清单、依赖与加载顺序`

【做】把玩家调整后的顺序持久化，随存档或 `user://` 配置保存。

【产出】顺序持久化

【判据】⚠ 换一台机器加载同一批 Mod，**顺序一致**（冲突可复现）

【审】`audit/godot/modding.md#36`

## 3. 参考实现

```text
# 拓扑排序：被依赖者先加载
order := topo_sort(deps)          # 环 → 报错并列出环上 id
for id in order:
    load_resource_pack(manifest[id].path, true)
```

## 5. 常见返工

⛔ **返工：按目录顺序加载** —— 单 Mod 时测不出来，
有依赖后才暴露，且**报错指向依赖者**，很容易误判成"依赖者的代码有问题"。
