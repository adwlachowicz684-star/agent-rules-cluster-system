# 00 域流程总览 · 性能分析工作流（perf 域）

## 0. 先定做什么

⚠ **本域的核心不是"怎么优化"，而是"按什么顺序量、以及怎么证明改完之后确实变好了"。**

性能工作有个共同特征：**优化做了很多，但没人说得清有没有变好。**
改动本身会改变测量环境（着色器已编译、缓存已热、机器温度已升），
⛔ 于是"优化完 FPS 高了"这个观察**本身不可信**。

本域把"测量"当成一件需要被交付的工程产物，而不是随手看一眼。

## 1. 功能点拆解（按依赖，不可颠倒）

| # | 功能点 | Step | 交付物 |
|---|---|---:|---|

| 02 | 剖析定位 | 5 | 瓶颈定位结论（不是猜测） |
| 03 | 优化顺序 | 6 | 按性价比排序的优化清单 |
| 04 | 预算与质量分档 | 5 | 帧预算 + 运行时降级链 |
| 05 | 回归防护 | 5 | 基线快照 + 复测入口 |
| 06 | 发布前专项 | 6 | 首帧 / 内存 / 热节流实测 |
| 07 | 性能验收 | 5 | 可签核报告 |

## 2. 与其他域的接缝

| 域 | 接缝 |
|---|---|
| physics | 物理插值缺失导致的拖影；TPS 与渲染帧率不匹配 |
| vegetation | 实例化 draw call 与 MultiMesh 分块 |
| level | 流式加载的首帧与加载屏 |
| ui | 每帧改 `text` 触发重排 |
| save | 同步 IO 卡主线程 |
| destruction | 碎片池化与 `reset_physics_interpolation()` |

## 3. 本域最容易做反的顺序

⛔ **先优化，再补基线。** 基线此时已被改动污染，
补出来的数字既不能证明"改之前多差"，也不能证明"改之后多好"。

⛔ **一次改多个变量。** 有效果不知道归谁的功，
出问题则要全量回滚——而全量回滚通常意味着这次优化整体作废。

⛔ **只在编辑器里测。** 编辑器跑在桌面 GPU 上，
且带 gizmo、热重载、远程调试器。只优化编辑器里的尖峰，
等于把问题推迟到发布前。

## 4. 入口

做法 `howto/godot/perf-profiling.md`（怎么量、平台差异）
　　`howto/godot/performance.md`（优化手段、预算、上线前检查）
审核 `audit/godot/perf-profiling.md`

⚠ **两篇 howto 的分工**：`perf-profiling.md` 讲**怎么测量与各平台差多少**，
`performance.md` 讲**定位之后具体怎么改**。本域讲**按什么顺序做**。
