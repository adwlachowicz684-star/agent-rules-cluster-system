# 转职 / 觉醒域 — 流程总览

> **本域交付**：一套"转得动、转得明白、转错了能回头"的职业系统。
> **对应**：做法 `howto/godot/class-awaken.md` · 审核 `audit/godot/class-awaken.md`
> 　　　接缝：`economy.md`（天赋树/装备养成）、`build-affix.md`（词条）、
> 　　　　　　`save-migration.md`（存档）、`netsync-advanced.md`（服务端权威）

---

## 0. 先定做什么（⛔ 没写这三行不许开工）

⚠ 同在职业域，"换个称号和技能组"和"带转职链、条件、消耗、装备兼容、
后悔期的完整转职系统"是**两条不同流程**——后者的复杂度几乎全在
**事务与兼容**上，而不是在职业数据本身。

```text
做什么：<转职 / 觉醒 / 多职业，职业链，条件与消耗>
不做什么：⛔ <至少两条>
验收标准：<可观测的>
```

示例（本次只做基础转职）：

```text
做什么：单一职业链 战士→骑士，等级+任务+道具作为条件，转职后技能重置并全额返还
不做什么：⛔ 不做多职业切换（只持有一套职业状态）
         ⛔ 不做跨职业技能映射（本次新旧职业技能完全独立）
验收标准：条件不满足时点不动且不扣消耗；扣费后提交失败能整体回滚；
         转职后失效装备在预览里就列出来；撤销一次后 history 未被污染
```

### 然后挑功能点

| 本次要做的 | 需要的功能点 |
|---|---|
| 只是"能换职业" | 01 → 02 → 07 |
| 有消耗（道具/货币/任务） | 01 → 02 → 03 → 07 |
| 转职后装备会失效 | 01 → 02 → 03 → 04 → 07 |
| 有技能/天赋要处理 | 01 → 02 → 03 → 05 → 07 |
| 要后悔期 / 预览 | 01 → 02 → 03 → 06 → 07 |
| 联网项目 | 01 → 02 → 03 → 07，且 **03/06 必须服务端判定** |

⛔ **不要全做。** 觉醒（原职业保留）不需要 05 的"返还"逻辑。

## 1. 功能点拆解与依赖顺序

```text
01 职业模型定性 ── 02 模板与实例 ── 03 转职事务 ──┬── 04 装备兼容 ──┐
                                                  ├── 05 技能与天赋 ─┼── 07 验收
                                                  └── 06 预览与后悔 ─┘
```

⚠ 06 在图里排在后面，但**只要有消耗就应提前做预览**——
没有预览的转职，"转完发现装备全穿不上"会变成差评和客服工单，
而不是一个能被发现的 bug。

| # | 功能点 | 前置 | 为什么这个顺序 |
|---|---|---|---|
| 01 | 定性：转职/觉醒/多职业 | 无 | ⚠ 三者数据模型不同，定错了后面全改 |
| 02 | 职业模板与状态实例 | 01 | 先有数据结构，才有事务可谈 |
| 03 | 转职事务（试算→扣费→提交→回滚） | 02 | ⚠ 唯一有外部副作用的一步，必须最先定型 |
| 04 | 装备兼容与降级 | 03 | 兼容清单要进预览，所以必须在试算里 |
| 05 | 技能与天赋的继承/返还 | 03 | 同样是提交阶段的一部分 |
| 06 | 预览、确认、后悔期 | 03 04 05 | ⚠ 依赖前三者才能列出"转完什么样" |
| 07 | 转职验收 | 01–06 | 含失败路径与资产保全实测 |

## 2. ⚠ 六个最容易做反的顺序

**① 不区分转职/觉醒/多职业就开工。**
⛔ 用转职模型做多职业，做到切换时才发现要存 N 份状态——
那时存档格式、UI、技能系统全都按单份写完了，改动面是**全系统级**的。

**② 先写 UI 和流程，再想事务。**
"先扣后转"和"先转后扣"都会丢东西。⛔ 顺序写死之后再补事务，
等于要把整条流程拆开重接。

**③ 把转职当成改几个字段。**
转职改的是"职业成长"这一环，但会让**整条属性链的结果全变**。
⛔ 直接改 `attack` 这类最终值，下次重算就被覆盖——
表现为"转职后攻击力变高了，打一场又变回去了"。

**④ 装备兼容放到穿戴时才判。**
那时玩家已经转完了。⚠ 兼容清单必须在**试算阶段**跑完并进预览。

**⑤ 技能点清零不返还。**
⚠ 技能点通常是付费或长线积累的，清零而不返还**等同删档**。
且返还的是**当时投入量**，不是当前剩余（否则可先点满再转职套利）。

**⑥ 后悔期用"反向再转一次"实现。**
⛔ 会污染 `history`，且可能不满足原职业的前置条件——
表现为"撤销失败，玩家被卡在新职业"。正确做法是**保存转职前快照**。

## 3. 与其它域的接缝

⚠ 转职是**典型的跨域功能**，做完本域不代表能上线。

| 接缝对象 | 契约 | 谁负责 |
|---|---|---|
| `economy.md` 天赋树 | 转职提交时调用统一的重置入口 | ⛔ 转职侧不自己改天赋数据 |
| `economy.md` 属性计算 | 只改"职业成长"这一环，**不碰最终值** | 属性计算器单一入口 |
| `build-affix.md` 词条 | 装备词条不随职业改；受职业影响的只有可用装备类型 | 兼容判定只看 `equip_types` |
| `save-migration.md` | `class_state` + `history` + `version` 三件套进存档 | 存 ID 不存引用 |
| `netsync-advanced.md` | 客户端只发意图，服务端判定并广播 | 预览可本地算，结果以服务端为准 |
| `datatable.md` | 职业配表只增不改 ID | 改数值另起 ID，旧的标废弃 |

⛔ **各功能点自己的验收不能替代集成验收**：
部件全合格、拼起来不能用，是跨域开发的典型失败。
