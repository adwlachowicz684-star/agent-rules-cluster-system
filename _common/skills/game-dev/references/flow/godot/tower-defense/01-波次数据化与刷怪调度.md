# 01 波次数据化与刷怪调度（塔防域）

> **本步交付**：波次是数据不是代码 + 刷怪用累加器显式结算 + 生成走对象池
> **对应**：流程 `howto/godot/genres-tower-defense.md` · 审核 `audit/godot/genres-tower-defense.md`

## 0. 交付物定义

1. `Wave` / `SpawnGroup` 已定义为 `Resource`，波次表里没有任何硬编码数组
2. 刷怪时序由**累加器显式结算**，全文件无"用 Timer 串密集刷怪"
3. 敌人生成走对象池，归还与复用路径唯一
4. 休眠敌人用 `set_physics_process(false)`，不是 `if not active: return`
5. 敌人节点类型已按"是否需要相互推挤"定下（不是一律 `CharacterBody2D`）

## 2. 工序

### Step 1　先分三层：波次层 / 调度层 / 战场层　`[tower-defense/01#S1]`

【读】``howto/godot/genres-tower-defense.md#0. 三层分离``

【做】
把 `WaveRunner`（什么时候刷什么）、`MobDirector`（生成、池、路径分配）、
`TowerGrid`（建塔、格子、索敌、结算）三层的职责各写一行，
并写下**每层不负责什么**。
⛔ 先写"怪物怎么走"再回头分层 —— 一旦 `MobDirector` 里混进了波次判定，
后面所有"这波到底清了没有"都要靠猜，
而 `get_nodes_in_group("enemies").is_empty()` 会被池里的休眠怪污染。

ⓘ 这条定性决定后面所有步：波次完成判定在**波次层**，
怪的生死计数在**调度层**，塔只管打 —— ⛔ 三层各记一份计数就是三套真相。

【产出】三层职责表（含每层的不负责项）

【判据】指着任意一处计数代码能说出它属于哪一层；⛔ 同一件事没有第二处计数。

【审】``audit/godot/genres-tower-defense.md#4``

### Step 2　波次配置用 Resource，不硬编码数组　`[tower-defense/01#S2]`

【读】``howto/godot/genres-tower-defense.md#1. 波次配置用 Resource，不要硬编码数组``

【做】
`Wave` 持有 `Array[SpawnGroup]` + `delay_before`，
`SpawnGroup` 持有 `enemy_scene / count / interval / path_id`。
⛔ 不要把波次写成 `_wave_3 := [10, 0.5, 0]` 这种数组字面量 ——
改一个数要读代码才知道第几位是什么，而策划改波次是**每次迭代都发生**的事。

ⓘ `path_id` 要在这一步就定下：它是 02 的路径缓存键，
⛔ 等到寻路时再补"这只怪走哪条路"，会出现同一个 `path_id` 有两种含义。

【产出】`wave.gd` + `spawn_group.gd` 两个 Resource 脚本

【判据】加一波只需在资源里加一行，⛔ 不改任何 .gd 文件。

【审】``audit/godot/genres-tower-defense.md#21``

### Step 3　刷怪时序用累加器显式结算，不用 Timer 串　`[tower-defense/01#S3]`

【读】``howto/godot/genres-tower-defense.md#1. 波次配置用 Resource，不要硬编码数组``

【做】
用 `_acc += delta` + `while _acc >= interval` 的循环显式结算本帧该刷几只。
⛔ 不要用 `Timer` 串"间隔 0.05 秒刷 50 只" —— `Timer` 每帧/每 tick
最多处理一次超时，密集刷怪会**依赖帧率**：
开发机上 60 FPS 正常，低端机 30 FPS 时一波要花两倍时间刷完，
⛔ 而波次完成判定看着仍然"正常通过"。

ⓘ `while` 而不是 `if`：一帧内可能要刷多只（掉帧后补刷），
⛔ 写成 `if` 会永久少刷，且计数器对不上时不报错。

【产出】累加器刷怪函数（含一帧多只的 while 分支）

【判据】把帧率锁到 30 FPS 跑同一波，⛔ 刷完的**总时长**与 60 FPS 一致（不是总只数一致）。

【审】``audit/godot/genres-tower-defense.md#6``

### Step 4　敌人生成走对象池，休眠用 set_physics_process(false)　`[tower-defense/01#S4]`

【读】``howto/godot/genres-tower-defense.md#7. 性能预算``

【做】
池子的取/还收敛到唯一入口，归还时重置全部状态（血量、路径下标、buff）。
⛔ 休眠用 `set_physics_process(false)`，**不是**在函数开头 `if not active: return` ——
后者节点仍在树里、仍参与遍历与信号，200 只怪的开销一分没省，
而 CPU 占用看着"已经优化过了"。

ⓘ 归还时**必须**重置路径下标与 `NavigationAgent` 的目标，
⛔ 复用时残留的旧目标会让怪先朝上一个目标走一帧，
表现为"新怪偶尔反向冲一下"。

【产出】对象池（含归还重置清单）

【判据】池子命中率可观测；⛔ 复用出的怪不会朝上一只的目标移动。

【审】``audit/godot/genres-tower-defense.md#10``

### Step 5　敌人节点类型按是否推挤选型，不是一律 CharacterBody2D　`[tower-defense/01#S5]`

【读】``howto/godot/genres-tower-defense.md#0. 三层分离``

【做】
需要相互推挤才用 `CharacterBody2D` + `NavigationAgent2D`；
纯路径插值用普通 `Node2D` 沿路径移动即可。
⛔ 一律 `CharacterBody2D` 会给几百只怪各挂一套物理体与 agent，
而这笔开销换来的只有「怪会互相挤」这一个效果 ——
如果玩法根本不在乎挤，这笔开销**纯亏**，且看不出来是亏在这里。

ⓘ 这条要在这一步定死：⛔ 到 03 才发现「其实不用推挤」，
等于把整套移动实现重写一遍。

【产出】敌人节点类型选型结论（含理由）

【判据】选 `Node2D` 时能说清「不需要推挤」；选 `CharacterBody2D` 时能说清哪个玩法依赖推挤。

【审】``audit/godot/genres-tower-defense.md#11``


## 3. 参考实现

```gdscript
# ⓘ 本块内自足：常量在此声明，承接上文即可直接用
const POOL_INIT := 64          # 池子初始容量
const MAX_ACTIVE := 256        # 同屏怪物硬上限

var _acc: float = 0.0
var _pool: Array[Node2D] = []
var _active: Array[Node2D] = []

func _process(delta: float) -> void:
    _acc += delta
    # ⛔ while 不是 if：掉帧后一帧要补刷多只
    while _acc >= _cur_interval and _spawned < _cur_count:
        spawn_one()
        _acc -= _cur_interval
        _spawned += 1

func spawn_one() -> void:
    if _active.size() >= MAX_ACTIVE:
        return
    var m := _take()
    m.reset_state()               # ⛔ 归还/复用时的状态重置
    _active.append(m)

func _take() -> Node2D:
    if _pool.is_empty():
        var m := _enemy_scene.instantiate()
        return m
    return _pool.pop_back()

func release(m: Node2D) -> void:
    _active.erase(m)
    m.set_physics_process(false)  # ⛔ 不是 if not active: return
    _pool.append(m)
```
