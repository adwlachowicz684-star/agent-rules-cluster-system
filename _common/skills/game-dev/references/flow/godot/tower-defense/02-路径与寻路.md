# 02 路径与寻路（塔防域）

> **本步交付**：同起终点路径只算一次 + `optimize` 按玩法选型 + 建塔后的同步时机已定 + 频繁改建筑走 A* 图
> **对应**：流程 `howto/godot/genres-tower-defense.md` · 审核 `audit/godot/genres-tower-defense.md`

## 0. 交付物定义

1. 路径缓存以 `path_id` 为键，同起终点的路径只算一次
2. `optimize` 的取值有书面理由（不是抄默认值）
3. 建塔后路径失效的处理时机已定，且 `map_force_update()` 的调用点**唯一**
4. 频繁增删建筑改的是 `AStarGrid2D` 点权重，不是 carving 切导航网格
5. 路径失效与重算的触发条件写下来了

## 1. 前置检查清单

- [ ] 200 只怪同时在场时，寻路调用次数是常数级不是 200 次/帧
- [ ] `optimize` 的取值能说出对应哪种玩法
- [ ] 全项目 `map_force_update` 的调用点 ≤ 1 处
- [ ] 建塔/拆塔走的是 A* 点权重

## 2. 工序

### Step 1　路径缓存以 path_id 为键，同起终点只算一次　`[tower-defense/02#S1]`

【读】``howto/godot/genres-tower-defense.md#2. 路径缓存，不要每只怪独立寻路``

【做】
`_path_cache: Dictionary` 以 `path_id` 为键缓存 `PackedVector2Array`，
怪物只在路径上插值。
⛔ 不要每只怪各自 `target_position = goal` 去寻路 ——
同一起终点算出的路径**完全一样**，而 A* 是实打实的开销；
200 只怪每帧各算一次，帧预算会被引擎的寻路吃掉，
⛔ 排查时却会被引向"渲染"或"脚本逻辑"，因为 profiler 上寻路成本常被归到别的条目。

ⓘ 缓存失效条件要写死：**只有路径被破坏才重算**，
⛔ 每帧无条件重算等于没缓存，而代码里确实有 `_path_cache`。

【产出】`_path_cache` 与 `get_path(pid)`

【判据】200 只怪在场时 `map_get_path` 的调用次数与怪数**无关**。

【审】``audit/godot/genres-tower-defense.md#5``

### Step 2　optimize 按玩法选型：等大网格 + 纯格子移动才用 false　`[tower-defense/02#S2]`

【读】``howto/godot/genres-tower-defense.md#8. ⛔ 官方口径：路径查询、避让默认值与 force_update 的代价``

【做】
官方：
`true` 走 funnel 沿拐角收缩 —— 但**小格子网格会产生难看的拐角路径**；
`false` 路径点落多边形边中点 —— 但**网格之外**单条长边覆盖开阔区时
会产生**不必要的绕远**。
⛔ 只记「网格用 false」会在混合地形关卡上得到绕远路径，
而路径看着"确实连着"，检查时查不出问题。

ⓘ 判据是玩法：**等大网格 + 纯格子移动**用 `false`；**自由移动**用 `true`。
⛔ 填完要在地图上目视走一遍拐角，不能只看路径连不连得上。

【产出】`optimize` 取值与玩法理由

【判据】能说出取值对应的玩法；⛔ 地图上目视无绕远、无贴角。

【审】``audit/godot/genres-tower-defense.md#12`　`audit/godot/genres-tower-defense.md#15``

### Step 3　建塔后的同步时机：地图默认只在物理帧末同步　`[tower-defense/02#S3]`

【读】``howto/godot/genres-tower-defense.md#8. ⛔ 官方口径：路径查询、避让默认值与 force_update 的代价``

【做】
官方原话：导航地图**默认只在每个物理帧末同步**。
建塔后同一帧立刻 `map_get_path()` 拿到的是**旧数据**。
要立即生效可 `map_force_update()`，但官方明确警告：
它会**flush 整个 NavigationServer 命令队列**（含其他地图、区域、代理），
且 *"should only be used by users that really know what they are doing"*。

⛔ 所以正确用法是**只在"一帧内建/拆一批塔之后"调一次**，
不是每放一座塔调一次 —— 后者是本项目最容易自己造出的性能悬崖，
⛔ 而它表现为"建塔时偶发卡顿"，排查必然被引向塔的特效或音效。

【产出】路径失效与重算的触发条件表（含 `map_force_update` 唯一调用点）

【判据】全项目 `map_force_update` 调用点 ≤ 1；⛔ 一帧内建 10 座塔只触发一次同步。

【审】``audit/godot/genres-tower-defense.md#2`　`audit/godot/genres-tower-defense.md#14``

### Step 4　频繁增删建筑改 A* 点权重，不用 carving 切导航网格　`[tower-defense/02#S4]`

【读】``howto/godot/genres-tower-defense.md#7. 性能预算``

【做】
官方与社区口径一致：运行时频繁改建筑的场景，
用 `NavigationObstacle2D` 切导航网格的代价**远高于**改 `AStarGrid2D` 点权重。
重算一张 100×60 的网格比重新切割导航网格便宜得多。
⛔ 按"塔是障碍物所以该用 Obstacle"的直觉选 carving，
会在塔多的关卡末期**每次建造都卡一下**，
而单看一次建造的耗时完全正常。

ⓘ 两种方式可以并存：静态地形用导航网格，
**可建造格子**用 A* 图 —— ⛔ 但两者必须有一个明确的归属表，
否则同一个格子被两套系统各判一次。

【产出】建筑可通行性的实现归属表（A* 点权重 vs carving）

【判据】建/拆一座塔的耗时与塔的数量**无关**。

【审】``audit/godot/genres-tower-defense.md#9``

### Step 5　写下路径失效与重算的触发条件　`[tower-defense/02#S5]`

【读】``howto/godot/genres-tower-defense.md#2. 路径缓存，不要每只怪独立寻路``

【做】
把"什么时候缓存作废"写成一张表：建塔、拆塔、地形变化、路径点被占。
⛔ 不写这张表，缓存就会在两个地方各判一次失效条件，
最终表现为"有时候重算了有时候没重算"，
而这类**间歇性**问题在开发期几乎必然被当成偶发 bug 放过去。

ⓘ 已出发的怪要不要立即改道，是**玩法决定**不是技术决定：
立即改道更公平但会让怪原地抖动；走完当前段再改更稳但玩家觉得"塔白建了"。
⛔ 这个选择必须写下来，不能靠默认值滑过去。

【产出】缓存失效条件表 + 已出发怪的改道策略

【判据】改一张塔之后，路径缓存的命中/失效次数可观测且符合预期。

【审】``audit/godot/genres-tower-defense.md#5``


## 3. 参考实现

```gdscript
# ⓘ 本块内自足：常量在此声明，承接上文即可直接用
const MAP_RID_UNKNOWN := 0

var _path_cache: Dictionary = {}      # path_id -> PackedVector2Array
var _dirty_paths: Array[int] = []     # 本帧内失效的 path_id

func get_path(pid: int) -> PackedVector2Array:
    if not _path_cache.has(pid):
        _path_cache[pid] = NavigationServer2D.map_get_path(
            _map, _start[pid], _goal[pid], false, 1)  # ⛔ optimize 按玩法选
    return _path_cache[pid]

func on_build_batch_done() -> void:
    # ⛔ 批量建拆后只调一次，不是每座塔调一次
    for pid in _dirty_paths:
        _path_cache.erase(pid)
    _dirty_paths.clear()
    NavigationServer2D.map_force_update(_map)
```
