# 04 建塔与格子（塔防域）

> **本步交付**：格子归属唯一 + ⛔ 建塔前验证路径仍可达 + 建塔后的路径失效批量处理
> **对应**：流程 `howto/godot/genres-tower-defense.md` · 审核 `audit/godot/genres-tower-defense.md`

## 0. 交付物定义

1. 格子的占用状态只有一处真相（不是格子表与塔实例各记一份）
2. ⛔ **建塔前**用同一张图验证「放下后所有出生点仍可达」，不通过则拒绝建造
3. 建塔/拆塔后的路径失效走批量同步（02 已定的唯一 `map_force_update` 调用点）
4. 「允许封路 / 禁止封路」的玩法决定已写下来
5. 迷宫类玩法若允许改道，已出发怪的改道策略已定（02/S5 定下的口径）

## 1. 前置检查清单

- [ ] 格子占用状态只有一个来源
- [ ] 存在"建塔前置可达性校验"函数
- [ ] 用塔把路封死时，建造被**拒绝**（不是怪卡住）
- [ ] 允许封路的玩法有书面的说明
- [ ] 建塔不直接调 `map_force_update`

## 2. 工序

### Step 1　先定玩法：允许封路还是禁止封路　`[tower-defense/04#S1]`

【读】``howto/godot/genres-tower-defense.md#0. 三层分离``

【做】
这是**玩法决定**，不是技术决定，且必须在写建造逻辑之前定：
- **禁止封路**（多数塔防）：建塔时校验，堵死则拒绝
- **允许改道**（迷宫塔防）：允许封死，但必须重算全部路径并让已出发的怪改道
- **完全允许封死**：那就不该有寻路，怪走固定轨道即可

⛔ 不定就开工，等于默认接受「玩家把路堵死后怪卡住不动」这个结果。
而它在开发期几乎测不出来 —— 关卡设计者自己不会去堵路。

【产出】封路口径（三选一，含理由）

【判据】能指着一行说明本作允许哪种；⛔ 没有「没想过」这种状态。

【审】``audit/godot/genres-tower-defense.md#20``

### Step 2　格子占用只有一处真相　`[tower-defense/04#S2]`

【读】``howto/godot/genres-tower-defense.md#0. 三层分离``

【做】
格子的占用状态要么由 `TowerGrid` 的表持有，要么由塔实例自己报，
⛔ **不能两边各记一份** —— 拆塔时漏清一边就会出现「格子显示为空但建不上」，
而检查两个数据源时它们**各自都是自洽的**。

ⓘ 选中哪个都行，但要在这一步写死，并在 05 的索敌里统一用它。

【产出】格子占用状态的唯一来源（含清理路径）

【判据】建了再拆，格子状态回到初始值；⛔ 无「显示为空但建不上」。

【审】``audit/godot/genres-tower-defense.md#20``

### Step 3　⛔ 建塔前验证路径仍可达（本域最关键的一步）　`[tower-defense/04#S3]`

【读】``howto/godot/genres-tower-defense.md#8. ⛔ 官方口径：路径查询、避让默认值与 force_update 的代价``

【做】
`AStarGrid2D.get_id_path(from, to, allow_partial_path = false)` ——
**`allow_partial_path` 默认是 `false`**，
⛔ 目标不可达时返回**空数组**，而不是「走到最接近的点」。

所以在禁止封路的玩法里：**放下这座塔之后**，从**每个**出生点到终点仍需有解；
任一条无解就**拒绝这次建造**。
⛔ 事后才发现封死，等于接受「怪原地不动」这个已发生状态 ——
它**不报错**：`is_point_solid` 全绿、路径缓存全绿、怪也"还在场上"，
⛔ 排查会被引向「这只怪是不是被冰冻了」。

【产出】`can_build_at(cell) -> bool` 前置可达性校验

【判据】用塔把路封死的那一刻，建造被拒绝并给出提示；⛔ 不会出现在场怪原地不动的情况。

【审】``audit/godot/genres-tower-defense.md#19`　`audit/godot/genres-tower-defense.md#20``

### Step 4　校验要用与寻路同一张图　`[tower-defense/04#S4]`

【读】``howto/godot/genres-tower-defense.md#2. 路径缓存，不要每只怪独立寻路``

【做】
⛔ 前置校验**必须**用怪物实际寻路用的那张图（同一个 `AStarGrid2D` 实例、
同一套 solid / weight 规则）。
⛔ 为了「快一点」另建一张简化的校验图，会得到「校验通过但实际走不通」，
而这是最难查的一类：两套逻辑各自正确，只有它们不一致时才出错。

ⓘ 校验开销不够就**降频或缓存**，⛔ 不是换一张图。

【产出】校验与寻路共用同一张图的证据（同一实例引用）

【判据】临时把寻路图的某点设为 solid，⛔ 校验结果同步变化。

【审】``audit/godot/genres-tower-defense.md#19``

### Step 5　建塔后的失效走批量，不直接调 map_force_update　`[tower-defense/04#S5]`

【读】``howto/godot/genres-tower-defense.md#8. ⛔ 官方口径：路径查询、避让默认值与 force_update 的代价``

【做】
建塔只往 02 定的 `_dirty_paths` 里登记失效的 `path_id`，
由批处理器在帧末统一清缓存 + 唯一一次 `map_force_update()`。
⛔ 在建造回调里直接调，等于把官方警告的那把刀交给了每一次点击。

【产出】建造回调 → 失效登记 → 批量同步 的链路

【判据】一帧内建 10 座塔，`map_force_update` 只被调用 1 次。

【审】``audit/godot/genres-tower-defense.md#14``


## 3. 参考实现

```gdscript
# ⓘ 本块内自足：常量在此声明，承接上文即可直接用
const ALLOW_BLOCKING := false   # ⛔ 玩法决定：false = 禁止封路

func can_build_at(cell: Vector2i) -> bool:
    if _occupied.has(cell):
        return false
    if ALLOW_BLOCKING:
        return true
    # ⛔ 用与寻路同一张图试放，再验证每个出生点仍可达
    _grid.set_point_solid(cell, true)
    var ok := true
    for spawn in _spawn_cells:
        var p := _grid.get_id_path(spawn, _goal_cell)   # allow_partial_path 默认 false
        if p.is_empty():
            ok = false
            break
    _grid.set_point_solid(cell, false)                  # ⛔ 一定回滚
    return ok
```

## 5. 常见返工

| 现象 | 返工到 |
|---|---|
| 玩家堵路后怪站着不动 | 返工 Step 3（缺前置可达性校验） |
| 格子显示空但建不上 | 返工 Step 2（两处各记一份占用） |
| 校验通过但实际走不通 | 返工 Step 4（另建了简化校验图） |
| 建塔时偶发卡顿 | 返工 Step 5（每塔一次 `map_force_update`） |
