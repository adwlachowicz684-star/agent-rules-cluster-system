# 03 离线结算分段与封顶（时间推进域）

> **本步交付**：速率事件日志 + 分段结算 + 三个封顶字段分开
> **对应**：流程 `howto/godot/time-progression.md` · 审核 `audit/godot/time-progression.md`

## 0. 交付物定义

1. 离线期间按**事件日志分段**，⛔ 不按"回来那一刻"的速率整体乘
2. 速率时间线是**按生效时间排序的事件日志**，⛔ 不是当前速率快照
3. `rate_multiplier` 与 `cap_extension_ms` 是**两个字段**
4. 三个封顶数分开：硬上限 / 生效上限 / 补签额度
5. 封顶后**不产生欠账**

## 1. 前置检查清单

- [ ] 离线结算走分段循环，不是单次乘法
- [ ] 速率变更以日志留存且可二分查找
- [ ] 速率加成与上限加成是两个独立字段
- [ ] 补签叠加加成后不越过系统硬上限
- [ ] 维护区间跳过结算且不留欠账

## 2. 工序

### Step 1　离线速率按事件日志分段，⛔ 不按回来那一刻倒推　`[time-progression/03#S1]`

【读】`howto/godot/time-progression.md#4. 分段：离线期间的速率不能按"回来那一刻"倒推`

【做】
离线 8 小时内可能 VIP 到期、活动结束、加成卡激活、建筑升级、赛季重置。
此时速率 `R(t)` **不是常数**，必须按事件边界切段逐段结算：

```gdscript
# ⓘ 本块内声明：MAX_OFFLINE_MS 见 00 参数登记，待实测
const MAX_OFFLINE_MS := 86_400_000

# segments 按生效时间排序；⛔ 不能用"回来那一刻"的速率整体乘
func settle_offline(segments: Array) -> int:
	var produced := 0
	for seg in segments:
		var cyc: int = seg["elapsed_ms"] / seg["tick_ms"]
		produced += cyc * seg["output_per_cycle"]
		if seg.get("is_reset_boundary", false):
			apply_reset(seg["reset_kind"])   # 边界处落库一次中间状态
	return produced
```

⛔ 用当前速率整体乘离线时长 ——
这是**第二普遍的实现错误**。表现为"VIP 到期后那几小时仍按 VIP 速率发收益"，
⛔ 而玩家收益看起来"多了"，没人会去查。

【产出】分段构造函数（输入锚点区间与时间线，输出 segments）

【判据】VIP 中途到期时，到期前后两段速率不同。

【审】`audit/godot/time-progression.md#9`

### Step 2　速率时间线是事件日志，⛔ 不是当前速率快照　`[time-progression/03#S2]`

【读】`howto/godot/time-progression.md#4. 分段：离线期间的速率不能按"回来那一刻"倒推`

【做】
`speed_timeline` 存**按生效时间排序的变更事件**，重建 `R(t)` 时二分查找。
⛔ 只存一个"当前速率"字段 —— 无法得知离线期间某时刻生效的是哪条。

⛔ 表现为"热调速率后，正在离线的玩家收益按新速率算"，
而运营预期是"调整只对新时段生效"，
⛔ 且这个偏差**只对当时离线的那批玩家生效**，报表上看不出来。

ⓘ 重置是时间轴上的**硬边界**，必须在边界处**落库一次中间状态**再进下一段，
⛔ 否则跨边界的那一段结算会用到边界前的字段。

【产出】`speed_timeline` 结构定义 + 二分查找的 `R(t)` 重建函数

【判据】热调速率不影响已离线玩家的既有分段。

【审】`audit/godot/time-progression.md#30`

### Step 3　速率加成与上限加成是两个字段　`[time-progression/03#S3]`

【读】`howto/godot/time-progression.md#5. 封顶：是留存节奏，不是功能缺陷`

【做】
`rate_multiplier`（产出 +50%）与 `cap_extension_ms`（挂机时长 +4 小时）
**语义不同，必须是两个字段**。

⛔ 塞进同一个 multiplier ——
会出现"买了时长加成结果速率也变高"的配置错乱。
表现为"某个 VIP 档位的收益远超设计"，
⛔ 而配置表里那个数字**看着完全合理**（它就是个倍数）。

ⓘ 这类错的排查成本极高：它只在**同时存在两种加成**时才显现，
而验收时通常分别测"速率加成对不对""时长加成对不对"。

【产出】加成字段定义（速率 / 上限 分开）+ 配置校验脚本

【判据】只加时长时速率不变；只加速率时时长不变。

【审】`audit/godot/time-progression.md#10`

### Step 4　三个封顶数必须分开　`[time-progression/03#S4]`

【读】`howto/godot/time-progression.md#5. 封顶：是留存节奏，不是功能缺陷`

【做】
`max_offline_ms`（系统硬上限，防经济崩盘）·
`offline_cap_ms`（玩家当前生效上限，受 VIP 延展）·
`catch_up_granted_ms`（补签解锁）三者分开：

```
granted = clamp(实际离线 - cap, 0, 硬上限 - cap)
```

⛔ 只设一个封顶字段 —— 补签叠加加成后**会击穿系统硬上限**。
表现为"一次活动就让产出翻几十倍"，
⛔ 而每个加成单独看都没超过自己的限额。

ⓘ **不封顶的挂机等于奖励长时间离线**：
玩家发现"挂三天比玩三小时划算"，在线行为被瓦解。
⛔ 这是产品决策，⛔ 不是技术缺陷 —— 取值不由本域决定。

【产出】三个封顶字段 + `granted` 计算与硬上限校验

【判据】补签 + VIP 时长加成叠加后仍不超过系统硬上限。

【审】`audit/godot/time-progression.md#11`

### Step 5　封顶后停止产出，⛔ 不产生欠账　`[time-progression/03#S5]`

【读】`howto/godot/time-progression.md#5. 封顶：是留存节奏，不是功能缺陷`

【做】
封顶后**直接停止**，⛔ 不把超出的部分记成"欠账"后续补发。
维护期间把维护起止作为时间线事件，区间内**跳过结算**，结束后从维护开始时刻重算。

⛔ 封顶后累积欠账 ——
断网或维护数小时后会产出**天量补偿**，难解释、难对账，
且会一次性注入大量资源冲击经济。
表现为"维护补偿发出去之后物价崩了"，
⛔ 而发放逻辑本身完全正确，问题在"该不该发"。

【产出】封顶后的行为定义 + 维护时间线事件的处理约定

【判据】维护 6 小时后上线，玩家不亏也不赚，无一次性天量补偿。

【审】`audit/godot/time-progression.md#12`

## 3. 参考实现

```gdscript
# ⓘ 本块内声明：OFFLINE_CAP_MS / MAX_OFFLINE_MS 见 00 参数登记，待实测
const OFFLINE_CAP_MS := 28_800_000
const MAX_OFFLINE_MS := 86_400_000

# ⛔ 补签叠加后不得越过系统硬上限；封顶后不欠账
func granted_ms(offline_ms: int, cap_ms: int) -> int:
	return clampi(offline_ms - cap_ms, 0, MAX_OFFLINE_MS - cap_ms)
```
