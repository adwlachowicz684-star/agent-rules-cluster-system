# 05 体力与溢出额度（时间推进域）

> **本步交付**：双锚点（自然恢复 / 每日购买）+ 溢出三"绝不" + cap 变化配置化
> **对应**：流程 `howto/godot/time-progression.md` · 审核 `audit/godot/time-progression.md`

## 0. 交付物定义

1. 体力恢复与挂机产出**共用同一内核**
2. 溢出额度**三"绝不"**：不生息、不受加成放大、不跨重置累积
3. 自然恢复与**每日购买次数**是两套**独立时钟**
4. 允许超上限时必须显式存 `hard_cap` 与 `bonus_pool`
5. cap 增大时的处理**配置化且服务端执行**

## 1. 前置检查清单

- [ ] 体力恢复走统一结算内核，未另写倒计时
- [ ] 溢出额度不参与任何加成计算
- [ ] 购买体力不重置自然恢复时钟
- [ ] 超上限部分有独立字段承载
- [ ] cap 变化的处理来自配置

## 2. 工序

### Step 1　体力恢复与挂机产出是同一内核　`[time-progression/05#S1]`

【读】`howto/godot/time-progression.md#7. 体力：三个边界`

【做】
恢复公式与挂机产出**同一个模型**（速率 = 1 点 / interval）：

```gdscript
# ⓘ 本块内声明：RESTORE_INTERVAL_MS / STAMINA_CAP 见 00 参数登记，待实测
const RESTORE_INTERVAL_MS := 300_000
const STAMINA_CAP := 120

# ⛔ 与挂机同一内核：锚点只推进已完整结算的部分
func restore(cur: int, last_ms: int, now_ms: int) -> Dictionary:
	var cycles: int = maxi(now_ms - last_ms, 0) / RESTORE_INTERVAL_MS
	return {
		"amount": clampi(cur + cycles, 0, STAMINA_CAP),
		"new_anchor": last_ms + cycles * RESTORE_INTERVAL_MS,
	}
```

⛔ 另写一套"每 N 分钟 +1"的定时器 ——
它不会跨会话，且与挂机在封顶 / 重置上的行为必然分叉。
表现为"体力恢复和挂机收益对同一份加成的理解不一样"。

【产出】体力恢复函数（复用统一内核）

【判据】体力与挂机走同一函数，无两份封顶逻辑。

【审】`audit/godot/time-progression.md#1`

### Step 2　溢出额度三"绝不"　`[time-progression/05#S2]`

【读】`howto/godot/time-progression.md#7. 体力：三个边界`

【做】
超出上限的体力：**绝不产生利息、绝不受加成放大、绝不跨重置累积**。

⛔ 让溢出部分参与加成或累积 ——
玩家可以通过"卡满体力 + 等活动加成"把溢出堆成天量资源。
表现为"某次活动后部分玩家资源异常高"，
⛔ 而每一笔溢出**单独看都是合法获得的**。

ⓘ 这条属于"正常流程测不出"的典型：
需要玩家**刻意配合时间窗口**才会触发，
⛔ 自动化测试不会这么玩。

【产出】溢出额度的处理定义（三"绝不"）+ 服务端校验

【判据】卡满体力吃加成后，溢出部分不变多。

【审】`audit/godot/time-progression.md#26`

### Step 3　购买体力与自然恢复是两套独立时钟　`[time-progression/05#S3]`

【读】`howto/godot/time-progression.md#7. 体力：三个边界`

【做】
"每日购买次数"与"自然恢复"**绝不能共享一个 `last_settled_at`**。

⛔ 共用一个锚点 —— 买一次体力会**顺带重置恢复时间戳**，
等于白赚一段恢复时间。
表现为"体力恢复得比设计快一点"，
⛔ 而"快一点"在验收时极易被放过，直到数值策划发现产出曲线对不上。

【产出】两套独立锚点（恢复锚点 / 每日购买周期锚点）

【判据】连续购买 5 次体力后，自然恢复进度未被重置。

【审】`audit/godot/time-progression.md#17`

### Step 4　允许超上限时必须显式存 hard_cap 与 bonus_pool　`[time-progression/05#S4]`

【读】`howto/godot/time-progression.md#7. 体力：三个边界`

【做】
若产品允许购买体力超过自然上限，必须显式存 `hard_cap` 与 `bonus_pool`。

⛔ 只存一个 `amount` —— 玩家升到更高 cap 时，
"超出旧上限的部分"无法被恢复系统识别，
表现为"升级后体力上限反而变低了"或"溢出部分凭空消失"。

ⓘ **购买体力能否超上限，技术上没有自然答案**，
必须在产品文档写死 —— ⛔ 本域不替产品做这个决定。

【产出】`amount` / `hard_cap` / `bonus_pool` 三段式结构

【判据】升级扩 cap 后，超上限部分仍可被正确识别与消耗。

【审】`audit/godot/time-progression.md#27`

### Step 5　cap 增大时的处理配置化且服务端执行　`[time-progression/05#S5]`

【读】`howto/godot/time-progression.md#7. 体力：三个边界`

【做】
升级导致 cap 增大时的处理（只扩容器 / 补满 / 全额发放一次）**配置化**，且**服务端执行**。

⛔ 客户端自己补 —— 改包即可无限补满。
⛔ 且三种处理方式的差异巨大，写死在代码里等于替产品做了决定。

ⓘ 这条与 S4 是配套的：
先有 `hard_cap` / `bonus_pool` 能表达"超出旧上限的部分"（S4），
再谈"扩 cap 时怎么处理"（S5），
⛔ 顺序反了会写出无法表达的补偿逻辑。

【产出】cap 变化处理配置表 + 服务端执行入口

【判据】改配置切换三种处理方式，无需发版；改包无法自行补满。

【审】`audit/godot/time-progression.md#28`

## 3. 参考实现

```gdscript
# ⓘ 本块内声明：STAMINA_CAP 见 00 参数登记，待实测
const STAMINA_CAP := 120

# 三段式：⛔ 不把溢出塞进 amount，否则扩 cap 后无法识别
var amount := 0        # 自然恢复可承载的部分
var bonus_pool := 0    # 购买获得的超上限部分，⛔ 不生息不受加成
var hard_cap := STAMINA_CAP

func total() -> int:
	return amount + bonus_pool
```
