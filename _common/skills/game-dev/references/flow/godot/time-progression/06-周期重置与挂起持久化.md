# 06 周期重置与挂起持久化（时间推进域）

> **本步交付**：服务端时区硬边界 + 任意时刻补算 + PAUSED 只持久化
> **对应**：流程 `howto/godot/time-progression.md` · 审核 `audit/godot/time-progression.md`

## 0. 交付物定义

1. 重置时间点用**服务器时区**（推荐 UTC 整点）
2. 重置必须能在**任意时刻补算**，⛔ 不是定时任务
3. 重置时正在进行的队列**逐类约定**
4. 周期标识由**服务端下发**
5. `PAUSED` 回调用**只做持久化**
6. `FOCUS_OUT` ≠ `PAUSED`

## 1. 前置检查清单

- [ ] 重置边界由服务器时区定义，无本地午夜逻辑
- [ ] 断网三天后上线能补算每一个边界
- [ ] 队列 / 每日任务 / 赛季排行各有明确的重置约定
- [ ] 周期 ID 来自服务端
- [ ] PAUSED 里无网络请求、无大批量结算

## 2. 工序

### Step 1　重置时间点用服务器时区，⛔ 不用玩家本地午夜　`[time-progression/06#S1]`

【读】`howto/godot/time-progression.md#8. 周期重置：硬边界，不是定时任务`

【做】
重置时间点用**服务器时区**定义（推荐 UTC 整点）。

⛔ 按玩家本地午夜重置 ——
玩家跨时区旅行后，他的"一天"会变长或变短；
夏令时切换那天，本地 02:00 会**消失一次或重复一次**，
基于本地日期字符串的重置表会**跳过或重复触发**。
表现为"少数玩家偶尔少领一次或多领一次"，
⛔ 而这种偶发只在特定日期的特定时区出现，几乎无法复现。

ⓘ UTC 不实行夏令时，边界恒定 —— 这是选它的**唯一且充分的理由**。

【产出】重置时区定义 + 边界计算函数（UTC 整点）

【判据】模拟跨时区与夏令时切换，重置边界不跳不重。

【审】`audit/godot/time-progression.md#18`

### Step 2　重置必须能补算任意时刻的每个边界　`[time-progression/06#S2]`

【读】`howto/godot/time-progression.md#8. 周期重置：硬边界，不是定时任务`

【做】
玩家断网三天后上线，要把这三天里**每一个**重置边界都跑一遍。

⛔ 只在 05:00 发一次事件 ——
断网期间的事件全部丢失，表现为"三天没上线，回来只重置了一次"。
⛔ 而且丢失是**静默的**：事件系统显示"已发送"，只是那时玩家不在线。

【产出】`apply_resets(from_ms, to_ms)` 补算函数（遍历区间内所有边界）

【判据】断网三天上线，三天的每日重置各执行一次。

【审】`audit/godot/time-progression.md#19`

### Step 3　重置时正在进行的队列逐类约定　`[time-progression/06#S3]`

【读】`howto/godot/time-progression.md#8. 周期重置：硬边界，不是定时任务`

【做】
逐类约定：建造 / 生产队列**跨重置继续推进**；
每日任务清 0 并发放未领奖励；赛季排行结算后清空。

⛔ **最危险的组合是"重置清 0 + 用剩余秒数存档"** ——
队列在重置边界附近被杀进程，恢复时**既不知道该被清掉也不知道该继续**。
解法是给条目加 `valid_through_ms`，把**生命周期与进度解耦**。

【产出】各类条目的重置行为表 + `valid_through_ms` 字段

【判据】在重置边界前后 1 秒杀进程，恢复行为确定且一致。

【审】`audit/godot/time-progression.md#20`

### Step 4　周期标识由服务端下发　`[time-progression/06#S4]`

【读】`howto/godot/time-progression.md#8. 周期重置：硬边界，不是定时任务`

【做】
`current_daily_cycle_id` 等周期标识由**服务端算好下发**。

⛔ 客户端自己算"今天是第几周期" ——
时区偏差会造成"我已领过 / 我还没领过"的冲突。
表现为"客服收到玩家投诉说奖励没发，日志却显示已发"，
⛔ 而两边**各自都是正确的**，只是算的不是同一个周期。

【产出】周期 ID 下发接口 + 客户端⛔禁止本地计算周期

【判据】跨时区玩家与服务端对"今天"的判定一致。

【审】`audit/godot/time-progression.md#21`

### Step 5　PAUSED 回调只做持久化，⛔ 不做结算　`[time-progression/06#S5]`

【读】`howto/godot/time-progression.md#9. Godot 侧：挂起回调只做持久化`

【做】
`NOTIFICATION_APPLICATION_PAUSED` 是**最后一次机会持久化**，不是计时器。
iOS 上只有约 **5 秒**完成该信号启动的任务，超时会被**杀死而非挂起**。

⛔ 在 PAUSED 里做结算 ——
网络不可用（结果无法上链）、挂起期间时间无法被诚实测量，
且大批量结算会超时被杀。
表现为"iOS 上切后台回来闪退或进度没了"，
⛔ 排查必然被引向崩溃 SDK 或内存，⛔ 不会想到是暂停回调太慢。

ⓘ `RESUMED` 的职责才是：校准本地单调偏移 → 触发一次完整离线结算 → 刷新显示。

【产出】PAUSED 处理器（只写锚点与状态）+ RESUMED 处理器（校准 + 结算）

【判据】PAUSED 处理耗时 < 5 秒；真机切后台不丢进度。

【审】`audit/godot/time-progression.md#22`

### Step 6　⛔ FOCUS_OUT 不等于 PAUSED　`[time-progression/06#S6]`

【读】`howto/godot/time-progression.md#9. Godot 侧：挂起回调只做持久化`

【做】
持久化挂在 **`NOTIFICATION_APPLICATION_PAUSED`**，⛔ 不挂 `FOCUS_OUT`。

⛔ 挂在 `FOCUS_OUT` ——
切桌面、第三方弹窗也会触发它，但未必真的挂起，
结果是**高频 I/O 与重复结算**。
表现为"切个窗口回来发现收益算多了"，
⛔ 而每次结算单看都是正确的（只是被触发了太多次）。

【产出】回调挂载点清单（明确区分 FOCUS_OUT / PAUSED / RESUMED）

【判据】连续切窗口 20 次，结算只在实际挂起时发生。

【审】`audit/godot/time-progression.md#23`

## 3. 参考实现

```gdscript
# ⓘ 本块内声明：RESET_HOUR_UTC 见 00 参数登记，待实测
const RESET_HOUR_UTC := 0

# ⓘ 承接 Node 内置常量：NOTIFICATION_APPLICATION_PAUSED / NOTIFICATION_APPLICATION_RESUMED
# ⛔ 只做持久化；网络请求与大批量结算会超时（iOS 约 5 秒后被杀）
func _notification(what: int) -> void:
	if what == NOTIFICATION_APPLICATION_PAUSED:
		save_anchor_only()
	elif what == NOTIFICATION_APPLICATION_RESUMED:
		calibrate_offset()
		settle_offline_full()
```

## 4. 验收清单

- [ ] 模拟夏令时切换，重置不跳不重
- [ ] 断网三天上线补算三天边界
- [ ] 重置边界前后杀进程行为确定
- [ ] 跨时区玩家与服务端周期判定一致
- [ ] 真机切后台 PAUSED 耗时 < 5 秒
- [ ] 连续切窗口不产生重复结算

## 5. 常见返工

| 症状 | 原因 | 回到 |
|---|---|---|
| 少数玩家偶尔少领一次 | 本地午夜 + 夏令时 | S1 |
| 三天没上线只重置一次 | 重置靠定时事件 | S2 |
| 边界附近杀进程行为不定 | 清 0 + 剩余秒数组合 | S3 |
| 玩家说没发、日志说发了 | 客户端自算周期 | S4 |
| iOS 切后台回来闪退 | PAUSED 里做结算 | S5 |
| 切窗口回来收益变多 | 持久化挂 FOCUS_OUT | S6 |
