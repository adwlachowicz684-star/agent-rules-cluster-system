# 01 时间源与可信时钟地基（时间推进域）

> **本步交付**：三种时间源分工表 + 服务端 int64 UTC 锚点 + 客户端单调偏移
> **对应**：流程 `howto/godot/time-progression.md` · 审核 `audit/godot/time-progression.md`

## 0. 交付物定义

1. 三种时间源各司其职，⛔ 不混用层级
2. 存档锚点是**服务端 int64 UTC 毫秒**，⛔ 不存 `get_ticks_msec()`
3. 客户端本地估计值**只允许向前**，⛔ 绝不结算负值
4. 表现层计时（倒计时动画、过场）与存档时间轴**彻底分开**
5. 与 `economy` / `ops` / `save` 域的接缝已指认到具体字段

## 1. 前置检查清单

- [ ] 没有任何一处用 `_from_system` 系列做数值差分
- [ ] 存档里没有 `get_ticks_msec()` 结果
- [ ] 客户端估计时间有向前钳制
- [ ] `SceneTreeTimer` / `time_scale` 未出现在任何结算路径
- [ ] 服务端时间偏移在登录时取一次并有校准入口

## 2. 工序

### Step 1　三种计时系统是同一个内核，⛔ 不做三套　`[time-progression/01#S1]`

【读】`howto/godot/time-progression.md#0. 一句话模型`

【做】
把建造、挂机、体力统一成**同一个内核**：

```
elapsed = clamp(now - last_settled_at, 0, CAP)
cycles  = elapsed / tick_ms
锚点    = last_settled_at + cycles * tick_ms   # ⚠ 只推进已完整结算的部分
```

⛔ 三个系统各写一套倒计时 ——
每套都会各自实现一遍封顶、重置、加成，然后**在边界上出现三份不同行为**。
表现为"建造加速和体力恢复对同一份 VIP 加成的理解不一样"，
⛔ 而每个系统的单测都是绿的，因为测的是各自那条路径。

ⓘ 统一内核的收益在加第四个系统时才显现：
那时只需要提供 `tick_ms` 与 `output_per_cycle`，
⛔ 三套独立实现则要重新决定"它算不算挂机"。

【产出】统一结算内核（输入锚点与时间线，输出 cycles 与新锚点）

【判据】建造 / 挂机 / 体力走同一函数，无三份封顶逻辑。

【审】`audit/godot/time-progression.md#1`

### Step 2　⛔ 系统时钟可读，但两次的差不可信　`[time-progression/01#S2]`

【读】`howto/godot/time-progression.md#1. 三种时间源，用错层级是万恶之源`

【做】
确立分层：**服务器 UTC 时间戳**用于存档锚点与重置边界，
`Time.get_ticks_msec()` 用于帧间差分与性能打点，
`get_datetime_dict_from_system()` 只用于 UI 显示。

⛔ 用 `_from_system` 系列算 elapsed ——
单次读取可能完全正确，但**两次读取的差**不可信：
玩家改表、NTP 校时、跨时区、夏令时都会让差值为负或跳变。
表现为"部分玩家收益莫名少几小时或变成负数"，
⛔ 而日志里每一次结算**都是按当时读到的值正确算出来的** —— 无从报错。

ⓘ 官方原话用的是"永远不要用于**精确**时间计算"。
这里的"精确"应读作"**可重复、可差分**"：
⛔ 不要因为"我读一次是准的"就认为它能做差分。

【产出】三种时间源分工表（会跳变吗 / 适合 / 严禁）

【判据】全局无一处用系统时钟做数值差分。

【审】`audit/godot/time-progression.md#2`

### Step 3　存档锚点用服务端 int64 UTC 毫秒　`[time-progression/01#S3]`

【读】`howto/godot/time-progression.md#客户端怎么拿到可信时间`

【做】
登录时服务端下发 `server_time_utc_ms`，客户端算一次偏移后本地预测：

```gdscript
# ⓘ 本块内声明：偏移只在登录/校准时更新，运行期只读
var _mono_offset := 0

func on_server_time(server_utc_ms: int) -> void:
	_mono_offset = server_utc_ms - Time.get_ticks_msec()

func now_utc_ms() -> int:
	return _mono_offset + Time.get_ticks_msec()
```

⛔ 把 `Time.get_ticks_msec()` 存进存档 ——
它保证单调但**进程重启归零**，跨会话存它等于存了一个与真实时间无关的数。
表现为"重开游戏后所有计时归零或暴增"。

⛔ 用 `get_unix_time_from_system()` 落库 ——
它返回 **float**，`int(x * 1000.0)` 在数值大时有浮点尾误差。
计费与落库必须用服务端的 **int64 毫秒**，客户端预测差几毫秒无所谓。

【产出】`server_time_utc_ms` 下发接口 + 本地 `now_utc_ms()` 预测函数

【判据】杀进程重启后倒计时正确；计费字段全程为 int64。

【审】`audit/godot/time-progression.md#4`

### Step 4　客户端估计值只允许向前，⛔ 绝不结算负值　`[time-progression/01#S4]`

【读】`howto/godot/time-progression.md#客户端怎么拿到可信时间`

【做】
`now_utc_ms()` 的结果若小于已持久化的 `last_settled_at`
（系统钟回拨、睡眠唤醒漂移、NTP 反向校时），**钳制到 `last_settled_at`**。

⛔ 信任本地估计值直接算 `now - last_settled_at` ——
差值为负时要么产出负数（扣玩家资源），要么被 `max(0, ...)` 静默吞掉
表现为"这一次上线什么都没结算，且没有任何提示"。

ⓘ 更危险的是它**间歇出现**：
只在玩家改过时钟或设备休眠唤醒后才触发，
⛔ 测试环境里永远复现不出，于是长期被归为"偶发数据异常"。

【产出】向前钳制函数 + 钳制命中时的上报埋点

【判据】人为把系统时间回调 2 小时，上线不产生负结算、不静默跳过。

【审】`audit/godot/time-progression.md#25`

### Step 5　表现层计时与存档时间轴彻底分开　`[time-progression/01#S5]`

【读】`howto/godot/time-progression.md#9. Godot 侧：挂起回调只做持久化`

【做】
`SceneTreeTimer.create_timer` 与 `Engine.time_scale` **只用于视觉与玩法表现**。

⛔ 用 `SceneTreeTimer` 驱动结算 —— 它受场景树暂停影响，
暂停期间"时间停了但玩家以为在走"，表现为"暂停后收益少了一段"。
⛔ 用 `time_scale` 做加速 —— 它影响帧间 delta，
⛔ 而 `SceneTree.paused` 停掉 `_process` 时**单调钟并不停**，两者就此分叉。

ⓘ 判据很直接：**把 time_scale 拉到 0，真实时间轴必须照常推进**。
⛔ 只要结算跟着停了，就是混用了表现层时间。

【产出】表现层计时清单（哪些用 tree timer），全部标注"不参与结算"

【判据】`time_scale = 0` 时挂机收益按真实时间照常累计。

【审】`audit/godot/time-progression.md#24`

## 3. 参考实现

```gdscript
# ⓘ 本块内声明：TICK_MS 见 00 参数登记，待实测
const TICK_MS := 60_000

# 服务端 int64 UTC 毫秒是唯一时间锚；本地只做预测且只允许向前
func elapsed_ms(last_settled_at_ms: int, now_ms: int, cap_ms: int) -> int:
	var now_clamped: int = maxi(now_ms, last_settled_at_ms)  # ⛔ 绝不结算负值
	return clampi(now_clamped - last_settled_at_ms, 0, cap_ms)

# 表现层：⛔ 不参与结算，只驱动倒计时显示
func start_countdown_display(sec: float) -> void:
	get_tree().create_timer(sec).timeout.connect(_on_display_tick)
```
