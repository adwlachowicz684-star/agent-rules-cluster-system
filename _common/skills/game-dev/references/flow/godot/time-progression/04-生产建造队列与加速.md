# 04 生产 / 建造队列与加速（时间推进域）

> **本步交付**：槽位规则配置化 + 服务端计费 + 原子落库 + 实时红点
> **对应**：流程 `howto/godot/time-progression.md` · 审核 `audit/godot/time-progression.md`

## 0. 交付物定义

1. 槽位并行规则**配置化**，⛔ 不硬编码
2. 加速（立即完成）计费**服务端算**，⛔ 客户端不算价
3. 扣款与产出**原子化**
4. 立即完成**复用同一套结算管线**，⛔ 不另写路径
5. 红点**实时查询**，⛔ 不靠到达时刻推送

## 1. 前置检查清单

- [ ] 槽位规则来自配置，改配置不需要改代码
- [ ] 加速价格由服务端按当时速率重算
- [ ] 扣款与产出在同一事务
- [ ] 立即完成与正常完成共用结算函数
- [ ] 红点查询的是"是否存在已完成条目"

## 2. 工序

### Step 1　槽位并行规则配置化，⛔ 不硬编码　`[time-progression/04#S1]`

【读】`howto/godot/time-progression.md#6. 生产 / 建造队列`

【做】
槽位并行规则（严格串行 / 有限并行 K 槽 / 全局共享池）来自配置。

⛔ 把"最多 2 个并行"写进代码 ——
改规则要发版，且不同建筑类型往往规则不同。
表现为"运营想开一个 3 槽位的活动建筑，技术说要下个版本"，
⛔ 而这个改动本身**没有任何技术难度**，纯粹是被硬编码挡住了。

【产出】槽位规则配置结构 + 各建筑类型的规则表

【判据】改配置文件即可切换串行 / K 并行 / 共享池。

【审】`audit/godot/time-progression.md#29`

### Step 2　加速计费必须服务端算　`[time-progression/04#S2]`

【读】`howto/godot/time-progression.md#6. 生产 / 建造队列`

【做】
剩余时长由服务端用**当时生效的速率**重算，价格也由服务端出。

⛔ 客户端 `remaining * price` —— 这是**典型计费漏洞**，
改包即可把价格改成 0。
⛔ 而且客户端缓存的"还剩 3 分钟"可能因加成变动而失准，
即使没有恶意玩家，也会出现"价格与实际剩余不匹配"的投诉。

【产出】服务端加速计价接口（入参条目 ID，出参价格与重算后的剩余时长）

【判据】改包伪造价格被服务端拒绝；加成变动后价格随之变化。

【审】`audit/godot/time-progression.md#13`

### Step 3　扣款与产出落库必须原子化　`[time-progression/04#S3]`

【读】`howto/godot/time-progression.md#6. 生产 / 建造队列`

【做】
扣款与产出**在同一事务**内完成。

⛔ 分两步 —— 中间任意一步失败就产出"扣了钱没完成"或"产出了没扣钱"。
表现为"玩家投诉扣费没到账"，
⛔ 而日志里两个操作**各自都成功过**，只是不在同一次里。

ⓘ 这条的排查难点在于**它是概率性的**：
只在进程被杀、网络超时、服务重启时触发，
⛔ 测试环境的正常流程永远走不到中间态。

【产出】原子事务封装 + 中途失败的对账补偿脚本

【判据】注入故障时，要么两者都发生，要么都不发生。

【审】`audit/godot/time-progression.md#14`

### Step 4　立即完成复用结算管线，⛔ 不另写路径　`[time-progression/04#S4]`

【读】`howto/godot/time-progression.md#6. 生产 / 建造队列`

【做】
"立即完成"本质是一次**结算到 now**，必须复用同一套结算管线。

⛔ 另写一条"直接标记完成"的路径 ——
必然在**分段 / 封顶 / 重置**三个边界上出现行为分叉。
表现为"用加速完成的建筑，跨重置后的表现和正常完成的不一样"，
⛔ 而两条路径单测都通过，因为测的是各自的正常流程。

【产出】立即完成 = 以 now 为终点调用统一结算函数的实现

【判据】加速完成与正常等待完成，跨重置后的状态完全一致。

【审】`audit/godot/time-progression.md#15`

### Step 5　红点实时查询，⛔ 不靠到达时刻推送　`[time-progression/04#S5]`

【读】`howto/godot/time-progression.md#6. 生产 / 建造队列`

【做】
红点判定**实时查询是否存在 `started_at + duration <= now` 的条目**。

⛔ 靠"到达时刻推送通知" ——
关机、杀进程、挂起**都会漏通知**，玩家上线后看不到红点。
表现为"玩家说东西早该好了但没提示"，
⛔ 而推送服务日志显示"推送成功"（它确实推了，只是设备没收到）。

ⓘ 判据很直接：**杀进程后重开，红点必须正确**。
⛔ 只要重开后红点丢了，就是依赖了推送。

【产出】红点实时查询函数（不依赖任何通知通道）

【判据】强杀进程重开后，已完成条目的红点正确显示。

【审】`audit/godot/time-progression.md#16`

## 3. 参考实现

```gdscript
# ⓘ 本块内声明：MAX_QUEUE_SLOTS 见 00 参数登记，待实测
const MAX_QUEUE_SLOTS := 2

# 红点：⛔ 实时查询，不依赖到达时刻的推送（杀进程会漏）
func has_ready_item(items: Array, now_ms: int) -> bool:
	return items.any(func(it): return it["started_at_ms"] + it["duration_ms"] <= now_ms)
```
