# 时间推进 —— 域流程总览

> ⚠ **第 0 步：先定"时间从哪来、存档存什么"。**
> 本域有 7 个功能点，⛔ **不是全做** —— 按本次需求挑。

## 0. 先定做什么

| 本次要做的 | 走哪些功能点 |
|---|---|
| 挂机 / 离线收益 | 01 → 02 → 03 → 07 |
| 建造 / 生产队列与加速 | 01 → 02 → 04 → 07 |
| 体力 | 01 → 02 → 05 → 07 |
| 每日 / 周 / 赛季重置 | 01 → 02 → 06 → 07 |
| 全套时间系统 | 01 → 02 → 03 → 04 → 05 → 06 → 07 |

⛔ **01 不能跳过** ——
服务器 UTC 时间戳、`Time.get_ticks_msec()`、`_from_system` 系列
看起来都是"取当前时间"，但**只有第一类能存进存档、只有第二类能做差分**。
⛔ 选错层级在开发期完全正常，表现为"上线后部分玩家收益差几小时"，
而日志里每一次结算都是**按当时读到的值正确算出来的**。

⛔ **02 不能跳过** ——
存"剩余秒数"是最直觉的写法，且在小龙套流程里表现完美。
它的失效条件是**杀进程 / 加成变化 / 暂停**，也就是"正常测试碰不到的那几条路径"。

⛔ **03 不能等经济数值铺开再补** ——
离线分段要按"离线期间真实生效的规则"重算，
而那时 VIP 到期、活动结束、赛季重置的边界已经写死在各处配置里，
⛔ 补分段等于把每条配置的生效时间反查一遍。

ⓘ 若本次只是"加一个每日任务、配一张周期表"，那是资源配置，不套本域。
ⓘ 若只是排查"倒计时不准"，先看 01 确认时间源层级，再回 02 看锚点。

ⓘ 分工：
- `howto/godot/time-progression.md` 讲**三种时间源与挂机/队列/体力/重置各自的算法**
- 本域讲**这些系统按什么顺序做、怎么保证杀进程与改时钟后仍然对**

⛔ 若本域某步需要"封顶几小时""体力上限多少"这类细节，
指向项目实测，⛔ 不在这里编数字 —— 行业区间不是本项目设计值。

## 1. 功能点拆解（按依赖，不可颠倒）

| # | 功能点 | 依赖 | 交付物 |
|---|---|---|---|
| 01 | 时间源与可信时钟地基 | — | 三种时间源分工表 + 服务端 int64 UTC 锚点 + 客户端单调偏移 |
| 02 | 存档锚点与余数处理 | 01 | 绝对锚点存档结构 + 余数回拨 + ⛔ 禁用 float 累加 |
| 03 | 离线结算分段与封顶 | 01, 02 | 速率事件日志 + 分段结算 + 三个封顶字段分开 |
| 04 | 生产 / 建造队列与加速 | 02, 03 | 槽位规则配置化 + 服务端计费 + 原子落库 |
| 05 | 体力与溢出额度 | 02 | 双锚点（自然恢复 / 每日购买）+ 溢出三"绝不" |
| 06 | 周期重置与挂起持久化 | 01, 02 | 服务端时区硬边界 + 任意时刻补算 + PAUSED 只持久化 |
| 07 | 时间推进验收 | 全部 | 改时钟 / 杀进程 / 断网三天 / 真机挂起 实测 |

⚠ **01 要在第一个计时功能之前** ——
那时每个系统各按各的取时间，统一时间源意味着每处都改一次。

⚠ **05 的双锚点要在第一个"购买体力"入口之前** ——
共用一个锚点会让买一次体力顺带重置恢复时钟，
⛔ 而这个漏洞在功能验收时表现为"体力恢复得比设计快一点"，极易被放过。

⚠ **06 的挂起持久化要在真机测试之前** ——
桌面环境下 `FOCUS_OUT` 与 `PAUSED` 的差异不明显，
⛔ 到 iOS 上才暴露时，已经分不清是持久化慢还是结算逻辑慢。

## 2. 与其他域的接缝

> ⚠ **组合的真正难点不是单个计时器，是接缝。**
> 下面每条都必须能指认到具体符号或字段，⛔ 不能是"做完了"。

| 接缝 | 契约 |
|---|---|
| `ops` 域 运营活动 | 活动五态与配置生效期见 `ops`，⛔ 本域只定**离线期间按事件日志分段结算** |
| `economy` 域 经济 | 产出的入账与账本口径见 `economy`，⛔ 本域只定"产出多少"不定"怎么记账" |
| `save` 域 存档 | `schema_version` 与迁移见 `save`，⛔ 本域只定锚点字段必须可迁移 |
| `netsync` 域 网络同步 | 服务端时间下发通道见 `netsync`，⛔ 本域只定"登录时取一次偏移" |
| `security` 域 安全 | 改系统时钟的作弊检测见 `security`，⛔ 本域只定"估计值只允许向前" |
| `companion` 域 伴侣物 | 宠物复活冷却 / 孵化计时复用本域锚点，⛔ 不另写一套倒计时 |
| `lifeskill` 域 生活玩法 | 生产队列的物料与产出见 `lifeskill`，⛔ 本域只定队列推进与加速计费 |
| `monetization` 域 商业化 | VIP 速率加成与上限加成的取值见 `monetization`，⛔ 本域只定"这是两个字段" |
| `mobile` 域 移动端 | iOS 挂起约 5 秒预算见 `mobile`，⛔ 本域只定 PAUSED 里做什么 |

## 3. 参数登记

| 参数 | 所在功能点 | 初始值 | 实测值 | 状态 |
|---|---|---|---|---|
| `TICK_MS` 结算 tick 间隔 | 02 | — | — | 待实测（与产出节奏相关） |
| `MAX_OFFLINE_MS` 系统硬上限 | 03 | — | — | 待实测（⛔ 防经济崩盘，不由本域定） |
| `OFFLINE_CAP_MS` 玩家生效上限 | 03 | — | — | 待实测（受 VIP / 加成延展） |
| `CATCH_UP_GRANTED_MS` 补签额度 | 03 | — | — | 待实测（⛔ 叠加后不得越过硬上限） |
| `RESTORE_INTERVAL_MS` 体力恢复间隔 | 05 | — | — | 待实测（与体力上限共同决定节奏） |
| `STAMINA_CAP` 体力上限 | 05 | — | — | 待实测（⛔ 升级扩 cap 的处理要配置化） |
| `RESET_HOUR_UTC` 重置整点 | 06 | — | — | 待实测（⛔ 服务器时区，非玩家本地） |

⛔ 上表"待实测"项**不得凭行业惯例填** ——
4–24 小时挂机封顶是行业区间，**不是本项目设计值**。
填错不会报错，只会表现为"玩家在线行为被瓦解"，⛔ 且要等留存数据出来才发现。
