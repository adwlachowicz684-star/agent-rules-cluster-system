# 02 存档锚点与余数处理（时间推进域）

> **本步交付**：绝对锚点存档结构 + 余数回拨 + ⛔ 禁用 float 累加
> **对应**：流程 `howto/godot/time-progression.md` · 审核 `audit/godot/time-progression.md`

## 0. 交付物定义

1. 存档存**绝对锚点 + 当时生效的速率时间线**，⛔ 不存剩余秒数
2. 在线 delta 只做体验，持久化靠锚点，⛔ 不补模拟
3. 锚点**只推进已完整结算的部分**，余数留在区间
4. ⛔ 禁止 float 累加器，余数累加必须 int64 定点
5. 与 `save` 域的 `schema_version` 迁移契约已指认

## 1. 前置检查清单

- [ ] 存档里没有任何"剩余秒数"字段
- [ ] 没有 float 类型的产出累加器
- [ ] 结算后锚点被写回（余数留在区间）
- [ ] 杀进程后进度不丢、不重复
- [ ] 速率变更以事件日志形式留存，不是当前值快照

## 2. 工序

### Step 1　存绝对锚点，⛔ 不存剩余秒数　`[time-progression/02#S1]`

【读】`howto/godot/time-progression.md#2. 存档存什么：绝对锚点，不是剩余秒数`

【做】
存档结构改为 **`last_settled_at_ms` + 速率时间线**，而不是 `remaining_sec`：

```gdscript
# ⓘ 本块内声明：TICK_MS / RATE_TIMELINE 见 00 参数登记，待实测
const TICK_MS := 60_000
var last_settled_at_ms: int = 0
var speed_timeline: Array = []   # ⛔ 是"变更日志"，不是"当前速率"
```

⛔ 存"剩余秒数" —— 它是**派生值**。
一旦暂停、加成变化、速率热调，它就失真，且无法反推应该是什么。
表现为"玩家买了加速卡，倒计时反而变长了"，
⛔ 而每一处单看都在正确地读写自己的字段。

ⓘ 绝对锚点的收益在于**能复算任意时刻的进度**：
配上"当时生效的速率"就能重放，⛔ 剩余秒数做不到这一点。

【产出】存档结构定义（锚点 / 起始时刻 / 基础时长 / 速率时间线 / schema_version）

【判据】暂停与加成变化后，进度可由锚点完整复算。

【审】`audit/godot/time-progression.md#3`

### Step 2　在线 delta 只做体验，⛔ 不补模拟　`[time-progression/02#S2]`

【读】`howto/godot/time-progression.md#2. 存档存什么：绝对锚点，不是剩余秒数`

【做】
在线时用 `_process(delta)` 做**高频小幅更新**（体验），
**同时持久化绝对锚点**（保真）；离线归来只用时间戳差做**一次性结算**。

⛔ 离线归来用 delta 逐帧补模拟 ——
关机、杀进程、被挂起之后 delta 根本不存在，补模拟既慢又必然对不上。
表现为"离线 8 小时回来，进度比预期少一点"，
⛔ 而在线挂机测试完全正常，因为那条路径根本没走过补模拟。

ⓘ 正确的结构让两条路径共用同一个内核：
在线是"频繁调用结算函数"，离线是"用大 elapsed 调用一次"，
⛔ 两条路径各写一遍 = 边界行为必然分叉。

【产出】在线 / 离线两条路径的统一结算入口

【判据】离线 8 小时与在线挂机 8 小时的产出一致（误差在 tick 内）。

【审】`audit/godot/time-progression.md#5`

### Step 3　锚点只推进已完整结算的部分　`[time-progression/02#S3]`

【读】`howto/godot/time-progression.md#3. 余数：三种安全处理，一种禁止`

【做】
结算后把锚点推进 **`cycles * tick_ms`**，把不足一个 tick 的余数**留在区间里**。

⛔ 直接把完整 elapsed 推进锚点（`floor` 后不管余数）——
玩家的挂机收益**系统性偏低**，而且**速率越高丢得越多**：
每次结算丢掉的部分随 tick 缩短而占比升高。
表现为"数值策划调快产出速率后，玩家实收反而低于设计值"，
⛔ 排查方向必然被引向配置表，而不是结算函数。

【产出】结算函数（返回 cycles 与新锚点）+ 余数处理方式的显式选择

【判据】高频结算与低频结算的长期累计产出一致。

【审】`audit/godot/time-progression.md#6`

### Step 4　⛔ 禁止用四舍五入补零头　`[time-progression/02#S4]`

【读】`howto/godot/time-progression.md#3. 余数：三种安全处理，一种禁止`

【做】
零头**留在区间**，⛔ 不做"差一点就补成一次产出"的向上取整。

⛔ 把零头四舍五入补一次 ——
玩家频繁进出场景就能**反复触发向上取整**，凭空产出。
表现为"总产出高于设计值，且活跃玩家偏高更多"，
⛔ 而单次结算看不出问题（每次只补了一点）。

ⓘ 这与 S3 是**同一枚硬币的两面**：
S3 丢余数会系统性偏低，S4 补余数会系统性偏高，
⛔ 两者都通过"能算出数"这个判据。

【产出】余数处理方式的显式声明（回拨 / int64 定点累加器 二选一）

【判据】反复进出场景 100 次，产出不超过按真实时间应得的量。

【审】`audit/godot/time-progression.md#7`

### Step 5　⛔ 禁止 float 累加器，用 int64 定点　`[time-progression/02#S5]`

【读】`howto/godot/time-progression.md#3. 余数：三种安全处理，一种禁止`

【做】
余数累加器必须是 **int64 定点**，⛔ 不用 float。

⛔ float 累加器 —— 长期漂移，**对账失败**。
表现为"运行几个月后玩家数据对不上，且无法复现"，
⛔ 而短期测试完全一致，于是被认为"没问题"。

ⓘ 若用累加器方案，回档时**该字段必须一起恢复**，
⛔ 只恢复锚点不恢复累加器 = 余数凭空消失，等于退化成 S3 的丢余数。

【产出】累加器类型定义 + 存档迁移时该字段的恢复约定

【判据】连续结算 10 万次后累计误差为 0。

【审】`audit/godot/time-progression.md#8`

## 3. 参考实现

```gdscript
# ⓘ 本块内声明：TICK_MS 见 00 参数登记，待实测
const TICK_MS := 60_000

# ⛔ 锚点只推进已完整结算的部分；余数留在区间，不四舍五入
func settle(last_settled_at_ms: int, now_ms: int) -> Dictionary:
	var elapsed: int = maxi(now_ms - last_settled_at_ms, 0)
	var cycles: int = elapsed / TICK_MS
	var consumed: int = cycles * TICK_MS
	return {
		"cycles": cycles,
		"new_anchor": last_settled_at_ms + consumed,  # ⛔ 不推进余数部分
	}
```

## 5. 常见返工

| 症状 | 原因 | 回到 |
|---|---|---|
| 买了加速倒计时反而变长 | 存了剩余秒数 | S1 |
| 离线回来进度少一点 | 用 delta 补模拟 | S2 |
| 调快速率后实收反而更低 | floor 后丢余数 | S3 |
| 活跃玩家产出偏高 | 四舍五入补零头 | S4 |
| 运行数月后对不上账 | float 累加漂移 | S5 |
