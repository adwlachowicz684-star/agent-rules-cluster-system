# UI 域 — 流程总览

> **本域交付**：一套在任意分辨率下不错位、键盘手柄都能操作、长列表不卡、文本不注入的界面。
> **对应**：做法 `howto/godot/ui.md` `ui-advanced.md` `i18n.md`
> 　　　审核 `audit/godot/ui.md` `ui-advanced.md`

---

## 0. 先定做什么（⛔ 没写这三行不许开工）

⚠ 同在 UI 域，"给游戏加个血条"和"做一套完整菜单 + 设置 + 存档界面"
是**两条不同流程**。

```text
做什么：<哪几个界面、面向什么输入设备、目标分辨率范围>
不做什么：⛔ <至少两条>
验收标准：<可观测的>
```

示例（本次只做 HUD）：

```text
做什么：一个血条 + 分数，跟随玩家数值变化，任意分辨率下贴边不错位
不做什么：⛔ 不做菜单（见 04）
         ⛔ 不做手柄导航（见 05，本次只键鼠）
验收标准：1280×720 与 2560×1440 下元素都不出屏；
         分数变化时才改 Label.text（不是每帧赋值）；
         相机移动时 HUD 不动
```

### 然后挑功能点

| 本次要做的 | 需要的功能点 |
|---|---|
| 只是血条/分数 | 01 → 02 → 07 |
| 有完整菜单 | 01 → 02 → 04 → 05 → 07 |
| 有对话/长文本 | 01 → 02 → 03 → 07 |
| 有大量列表（>200 项） | 01 → 02 → 06 → 07 |
| 要适配多分辨率 | 01 → 02 → 07（07 的 S1 必做） |

⛔ **不要全做。**

## 1. 功能点拆解与依赖顺序

```text
01 布局地基（锚点与容器）── 02 数据绑定与刷新 ──┬── 03 文本与长内容 ──┐
                                               ├── 04 菜单与面板 ────┼── 07 UI 验收
                                               ├── 05 焦点与导航 ────┤
                                               └── 06 大列表性能 ────┘
```

| # | 功能点 | 前置 | 为什么这个顺序 |
|---|---|---|---|
| 01 | 布局地基 | 无 | ⚠ 锚点错了，后面所有界面在别的分辨率下都要重做 |
| 02 | 数据绑定与刷新 | 01 | 先有稳定的布局，再往里填会变的数据 |
| 03 | 文本与长内容 | 01 02 | 打字机依赖文本节点，且"只在变化时赋值"是 02 的原则 |
| 04 | 菜单与面板 | 01 | 菜单是布局组合，不依赖数据绑定 |
| 05 | 焦点与导航 | 04 | ⚠ 先有可聚焦控件，才谈得上"默认焦点是谁" |
| 06 | 大列表性能 | 01 02 | 列表是"大量控件的绑定"，要先懂绑定与重建 |
| 07 | UI 验收 | 01–06 | 链路完整才谈得上验收 |

---

## 2. ⚠ 四个最容易做反的顺序

**① 先摆控件再想分辨率。**
用鼠标拖出来的位置在 1280×720 下完美，换个比例就错位。
✅ 先定锚点预设（`PRESET_*`），再摆位置。

**② 先做界面再补手柄。**
键鼠做完再补焦点链，会发现整个交互模型要重来
（哪些控件可聚焦、Tab 顺序、返回键归属）。
✅ 即使本次只支持键鼠，控件也要标清 `focus_mode`。

**③ 用计时器控制文本动画。**
"每 0.03 秒加一个字"用 `_process` 累加判断，和动画/暂停系统脱节。
✅ 用 `await` + 判 `is_instance_valid`。

**④ 列表直接用 `Tree`/大量 `instantiate`。**
⚠ **Godot 没有内置虚拟列表，而且 `Tree` 也不虚拟化**（见 06）。
先按小数据量写，会等到上线前才发现扛不住。

## 3. 每做完一个功能点必做

1. 跑一遍该步的**验收清单**，逐条打勾
2. ⛔ 有没过的，不进下一步
3. 过该步【审】列的 audit 条目
4. 过功能点末尾的「整体审核」节
5. ⚠ 实测参数已回填，⛔ 不留示例值
