# 04 变体与编译预热（着色器域）

> **本步交付**：变体数可控 + 预热清单 + 首帧无新增卡顿
> **对应**：流程 `howto/godot/shaders.md` · 审核 `audit/godot/shaders.md`

## 0. 交付物定义

1. 变体数可控，⛔ 不以代码行数衡量复杂度
2. 运行时差异用 **uniform**，不是编译期宏
3. 预热执行了**代表性 draw**，不只是创建资源
4. 覆盖目标渲染器与质量档位
5. 已知"缓存会失效"，⛔ 不假定一次预热永久有效

## 1. 前置检查清单

- [ ] 最小闭环已跑通（03）
- [ ] 已列出所有编译期宏开关
- [ ] ⚠ 已确定目标渲染器与最低质量档位
- [ ] 已确定会出现的所有材质 / 灯光组合
- [ ] 已准备加载界面作为预热窗口

## 2. 工序

### Step 1　代码短不等于变体少　`[shaders/04#S1]`

【读】`howto/godot/shaders.md#变体爆炸`

【做】
用**变体数**衡量复杂度，不用代码行数。管线由渲染器、功能开关、纹理提示、
`render_mode`、透明度状态、灯光阴影、特化常量共同决定。
⛔ 用行数评估成本 —— 一个 20 行的 shader 可能产生几十个管线，
而"代码很短"会让人彻底放弃对变体的控制。

⚠ N 个独立编译期宏开关，最坏组合数是 2^N。

【产出】变体来源清单（每个开关 → 是否必需）

【判据】能说出当前 shader 大致的变体量级，以及它由哪几个开关决定。

【审】`audit/godot/shaders.md#16`

### Step 2　运行时差异用 uniform，不用宏　`[shaders/04#S2]`

【读】`howto/godot/shaders.md#变体爆炸`

【做】
把"运行时会变的东西"做成 uniform 而不是编译期宏。
⛔ 用宏做运行时差异（方便是方便）—— N 个开关最坏 2^N 个变体，
每个变体都要单独编译，⛔ 编译时卡顿与磁盘缓存体积一起爆炸。

ⓘ uniform 控制的分支通常不产生新 shader 版本，
这也是为什么 uniform 分支在性能上通常也是划算的。

【产出】开关分类表：哪些改成 uniform，哪些必须留在编译期

【判据】每个宏开关都能说出"为什么它必须留在编译期"。

【审】`audit/godot/shaders.md#34`

### Step 3　preload 不等于预热，要执行代表性 draw　`[shaders/04#S3]`

【读】`howto/godot/shaders.md#预热`

【做】
预热必须让 GPU **真的画一次**，不只是把资源加载进内存。
⛔ 只 `preload()` 或创建 RID 就当预热过了 —— 首帧仍会编译，
表现为"第一次出现这个效果时顿一下"，⛔ 而它只在玩家第一次遇到时发生，
开发时反复跑同一段路根本测不出来。

ⓘ 预热要在加载界面做，并保持加载状态，⛔ 不假定单帧能完成。

【产出】预热清单（组合 → 是否执行了代表性 draw）

【判据】清掉管线缓存后重跑，首次出现该效果时无新增卡顿。

【审】`audit/godot/shaders.md#17`

### Step 4　换材质、改分辨率、动态灯也会生成新管线　`[shaders/04#S4]`

【读】`howto/godot/shaders.md#预热`

【做】
预热清单要覆盖：目标渲染器、阴影设置、常见分辨率、
运行时动态创建的材质、以及所有材质与灯光组合。
⛔ 只覆盖"启动时会用到的组合" —— 玩家改分辨率、首次进新区域、
动态灯光配置变化、运行时换材质，⛔ 都会生成新管线，
而这些都是"玩了一阵才开始卡"的典型来源。

⛔ 特别一条：在主菜单测 Compatibility、游戏里却切 Forward+，
等于预热了一组根本用不到的管线。

【产出】覆盖矩阵：渲染器 × 质量档 × 分辨率 × 材质灯光组合

【判据】矩阵里每一格都做过一次代表性 draw。

【审】`audit/godot/shaders.md#32`、`audit/godot/shaders.md#27`

### Step 5　缓存会失效，别假定一次预热永久有效　`[shaders/04#S5]`

【读】`howto/godot/shaders.md#预热`

【做】
把管线缓存当作"可以失效的东西"来设计：换设备、升驱动后缓存失效，
需要重新编译。⛔ 假定预热一次永久有效 ——
表现为"换了台机器又开始卡"，而没人会想到是缓存没了。

ⓘ 具体缓存位置与失效条件见 `perf` 域，⛔ 本域不给未经实测的路径与数值。
ⓘ 官方明确该问题"远未解决"，缓存只是缓解，不是根治。

【产出】缓存失效时的降级策略（加载界面保持 + 分批预热）

【判据】删掉缓存目录后重跑，仍能通过加载界面完成预热而不卡在首帧。

【审】`audit/godot/shaders.md#33`

## 3. 参考实现

```gdscript
# ⓘ 承接本步产出：预热要执行代表性 draw，且覆盖目标渲染器
const PREWARM_COMBOS := [
    {"mesh": "res://art/dummy_mesh.tres", "mat": "res://art/mat_toon.tres"},
    {"mesh": "res://art/dummy_mesh.tres", "mat": "res://art/mat_rim.tres"},
]

func _prewarm() -> void:
    for combo in PREWARM_COMBOS:
        var mi := MeshInstance3D.new()
        mi.mesh = load(combo["mesh"])
        mi.material_override = load(combo["mat"])
        add_child(mi)          # ⛔ 只 load 不算预热，必须真的进渲染树画一次
        await RenderingServer.frame_post_draw
        mi.queue_free()
```

- [ ] 运行时差异已改为 uniform

- [ ] 覆盖矩阵涵盖渲染器 × 质量档 × 分辨率 × 材质灯光组合

## 5. 常见返工

| 症状 | 原因 | 回到 |
|---|---|---|
| 首次出现效果时顿一下 | 只 load 没 draw | S3 |
| 玩了一阵才开始卡 | 换材质 / 改分辨率生成新管线 | S4 |
| 换了台机器又开始卡 | 缓存失效 | S5 |
| 变体数量失控 | 用宏做运行时差异 | S2 |
| 缓存体积爆炸 | 变体没控制 | S1 |
