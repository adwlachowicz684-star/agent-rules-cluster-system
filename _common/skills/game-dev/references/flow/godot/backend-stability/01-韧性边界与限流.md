# 01 韧性边界与限流（服务端稳定性域）

> **本步交付**：四层能力清单 + 限流维度表 + 限流响应契约
> **对应**：流程 `howto/godot/backend-stability.md` · 审核 `audit/godot/backend-stability.md`

## 0. 交付物定义

1. "超时 / 限流 / 熔断 / 有界重试"四层能力逐条写下现状（有 / 没有）
2. 已确认韧性不是"上线前压一次"
3. 限流算法按"允许突发 / 允许排队"选定，不是随便挑
4. burst 与队列长度已设上界
5. 限流响应能被客户端区分（安全风控 / 容量限流 / 服务故障）

## 1. 前置检查清单

- [ ] 四层能力清单已写下，每项有"有 / 没有"结论
- [ ] 已确认最危险的是四个"无"叠加，而不是某个代码缺陷
- [ ] 限流算法的选择理由写的是"是否允许突发 / 排队"
- [ ] ⛔ burst 与队列长度有明确上界数字
- [ ] 限流返回含状态码 + 业务错误码 + 提示 + `Retry-After`

## 2. 工序

### Step 1　先写四层能力清单：超时、限流、熔断、有界重试　`[backend-stability/01#S1]`

【读】`howto/godot/backend-stability.md#0. 一句话：韧性不是"上线前压一次"`

【做】
最危险的不是某次代码缺陷，而是**无超时 + 无限流 + 无熔断 + 无界重试**
把一次局部抖动放大成全链路雪崩。
逐条写下当前现状（有 / 没有 / 部分），⛔ 不能凭"应该有"下结论。
⚠ 另一类是备份、回滚、扩容预案**只存在于文档而从未验证**——
清单里要单列"已演练 / 仅文档"两栏。
⛔ 只有"上线前压一次"的团队，通常四层里三层是"没有"，且自己不知道。

【产出】四层能力清单（每项含"有 / 没有"与"已演练 / 仅文档"）

【判据】指着任一层能说出当前是否有，且证据不是"代码里写过"

【审】`audit/godot/backend-stability.md#1`


### Step 2　限流算法按"是否允许突发"和"是否允许排队"选　`[backend-stability/01#S2]`

【读】`howto/godot/backend-stability.md#1. 限流：无限流的服务等于裸奔`

【做】
令牌桶 = 平均速率受控 + 短期突发受桶容量约束，适合**用户入口**（登录、资源拉取）；
漏桶 = 排入有限队列 + 恒定速率处理，适合**出口**（批量入库、消息消费、第三方通知）。
固定窗口简单但**窗口边界出现两倍尖峰**；滑动窗口准确但代价更高。
⛔ 选型理由必须写成"允许不允许突发、允许不允许排队"，
⛔ 不能写成"大家都用令牌桶"——两者放错位置会同时失去突发控制与排队保护。

【产出】限流算法选型表（含每类适用位置与理由）

【判据】每个入口 / 出口位置都能说出为什么是这个算法

【审】`audit/godot/backend-stability.md#2`


### Step 3　⛔ burst 与队列长度必须有上界　`[backend-stability/01#S3]`

【读】`howto/godot/backend-stability.md#1. 限流：无限流的服务等于裸奔`

【做】
`burst` 设太大 → 令牌桶退化成"偶尔超售"；
队列无限延长 → 漏桶把延迟转成 **OOM**。
两个值都要有明确数字，且要写"到达上界时丢弃什么"。
⛔ 只设速率不设上界，等于把有限流做成无限流：
速率生效的那部分会让仪表盘看起来正常，而被超售 / 积压的部分没有任何图表会显示。

【产出】burst 与队列长度上界（含到达上界时的丢弃策略）

【判据】两个值都是数字，且丢弃策略已写明

【审】`audit/godot/backend-stability.md#3`


### Step 4　限流响应契约：状态码 + 业务码 + 提示 + Retry-After　`[backend-stability/01#S4]`

【读】`howto/godot/backend-stability.md#1. 限流：无限流的服务等于裸奔`

【做】
⛔ 限流响应不能只是 TCP 断开或 HTTP 500。
要返回状态码 + 业务错误码 + 人类可读提示 + 可选 `Retry-After`，
让客户端能决定是稍后重试还是提示玩家。
⛔ 只断开连接，客户端只能一律立即重连——这正是雷鸣群的来源，
而且是**由限流本身触发的**雷鸣群。

【产出】限流响应契约（三类返回各自的字段）

【判据】客户端能区分"稍后重试"与"不要再试"

【审】`audit/godot/backend-stability.md#4`


### Step 5　⛔ 登录限流不能提示"账号或密码错误"，且要能与安全风控区分　`[backend-stability/01#S5]`

【读】`howto/godot/backend-stability.md#1. 限流：无限流的服务等于裸奔`

【做】
登录被限流时提示"账号或密码错误"，等于给攻击者**账号枚举能力**。
同时限流与安全风控是两类返回，⛔ 不能共用一个错误码，
否则客户端无法区分"稍后再来"与"你被封了"，玩家看到的表现也是错的。

【产出】登录限流返回规范（与安全风控返回并列对比）

【判据】限流与安全风控业务码不同，且限流提示不含账号是否存在的信息

【审】`audit/godot/backend-stability.md#5`


## 3. 参考实现

```gdscript
# ⓘ 承接本步产出：三类限流返回必须能被客户端区分
const LIMIT_CODE_CAPACITY := 1001      # 容量限流：稍后重试
const LIMIT_CODE_SECURITY := 1002      # 安全风控：不要再试
const LIMIT_CODE_DEGRADED := 1003      # 服务降级：部分能力不可用

func _is_retryable(code: int) -> bool:
	# ⛔ 只有容量限流可重试；安全风控与降级重试只会加重打击
	return code == LIMIT_CODE_CAPACITY
```

## 5. 常见返工

| 症状 | 原因 | 回到 |
|---|---|---|
| 抖动被放大成雪崩 | 四层里有"无" | S1 |
| 边界出现两倍尖峰 | 固定窗口未换 | S2 |
| 延迟变成 OOM | 队列无上界 | S3 |
| 客户端一律立即重连 | 限流只断开 | S4 |
| 被做账号枚举 | 限流提示泄露 | S5 |
