# 服务端稳定性、容量与事故响应 —— 域流程总览

> ⚠ **第 0 步：先定"最坏情况下怎么失败"。**
> 本域有 7 个功能点，⛔ **不是全做** —— 按本次要扛什么量级挑。
> ⛔ 顺序错了比不做更糟：先上监控会得到一堆没有止损动作的图表。

## 0. 先定做什么

| 本次要做的 | 走哪些功能点 |
|---|---|
| 只想防住被突发流量打垮 | 01 → 07 |
| 有外部依赖（第三方登录 / 支付 / 推送） | 01 → 02 → 03 → 07 |
| 数据量开始撑不住单机 | 01 → 04 → 07 |
| 要扛开服 / 整点活动尖峰 | 01 → 05 → 07 |
| 已有线上服务，要能快速止损 | 01 → 06 → 07 |
| 全套 | 01 → 02 → 03 → 04 → 05 → 06 → 07 |

⛔ **01 无论如何不能跳过** ——
它是唯一决定"后面 6 个功能点该投多少预算"的一步。
⛔ 跳过 01 直接做 05（容量压测）是最常见的错：
压测能立刻给出"能扛多少 QPS"这个直观数字，
⚠ 而此时**每个外部调用仍无超时、无熔断**——
压测曲线看起来是"容量不足"，实际是"一次慢依赖把线程池拖垮"，
⛔ 于是团队去扩容，扩容后拐点几乎不变，且没人怀疑方向错了。

ⓘ 分工：
- `howto/godot/backend-stability.md` 讲**单个机制怎么实现**（限流算法、熔断三态、分片键、SLO 燃烧率）
- 本域讲**这些机制按什么顺序做、哪些必须在服务端、怎么验收**

## 1. 功能点拆解（按依赖，不可颠倒）

| # | 功能点 | 依赖 | 交付物 |
|---|---|---|---|
| 01 | 韧性边界与限流 | — | 四层能力清单 + 限流维度表 + 限流响应契约 |
| 02 | 熔断与降级 | 01 | 三态机 + 按调用类型阈值 + 降级档位配置 |
| 03 | 超时重试与客户端侧 | 01, 02 | 超时预算表 + 退避抖动幂等键 + 客户端 jitter |
| 04 | 数据层与分片 | 01 | 瓶颈证明 + 分片键 + 缓存三失效治理 |
| 05 | 容量与压测 | 01, 04 | 容量模型 + 受控失败压测 + 扩容计时 |
| 06 | 监控告警事故响应与灾备 | 全部 | 可执行告警 + 分级止损 + 恢复演练记录 |
| 07 | 稳定性验收 | 全部 | 敌意环境实测（依赖永不返回 / 雪崩 / 分片倾斜 / 恢复演练） |

⚠ **02、03 必须在 05 之前**：
压测的前提是"系统能受控失败"，
⛔ 没有超时与熔断就去压测，测出来的拐点是**雪崩点**而不是容量上限。

## 2. 与其他域的接缝

> ⚠ **组合的真正难点不是排序，是接缝。**
> 下面每条都必须能指认到具体符号或字段，⛔ 不能是"做完了"。

| 接缝 | 契约 |
|---|---|
| `ops` 域 运营 | 配置下发是降级的执行通道，⛔ SSH 改生产不是（见 02/S5） |
| `security` 域 安全 | 限流与安全风控的返回必须能被客户端区分（见 01/S5） |
| `analytics` 域 埋点 | SLO 与告警依赖埋点口径，指标名要对齐（见 06/S1） |
| `netsync` 域 网络同步 | 断线重连 jitter 与雷鸣群，客户端不判定服务健康（见 03/S6） |
| `monetization` 域 商业化 | 支付重试必须携带同一套幂等键（见 03/S4） |
| `save` 域 存档 | 数据回滚不可行时按存档版本向前修复（见 06/S7） |
| `sharding-matchmaking` 分服合服 | ⓘ howto 层，暂无 flow 域 |

⛔ **若某条接缝对不上，要单独立一个接线功能点**，
⛔ 不许在各处偷偷转格式。

## 3. 本域最容易做反的顺序

⛔ **先上监控仪表盘与限流，把超时与熔断排到最后（01、05、06 提前，02、03 靠后）。**

"QPS 被压住了""告警都配好了"是最直观的验收点，
于是先搭仪表盘、先配限流规则、先做压测报告，
⚠ 而此时外部调用既无超时也无熔断。

⛔ 后果链：
开服尖峰到来 → 限流把多余请求挡在外面，仪表盘显示"系统稳定" →
一次慢依赖让线程池逐渐挂满 →
⚠ 而"永不返回"不计入任何失败统计，熔断永远不会打开 →
故障表现为"整体变慢"而不是"报错" →
⛔ 所有图表都在正常范围内，值班看到的是"没有告警"。

✅ 正确顺序：先定韧性边界与限流（01），
再做熔断与降级（02）与超时重试（03），
然后数据层（04）、容量压测（05），最后监控告警与事故响应（06）。
