# 07 稳定性验收（服务端稳定性域）

> **本步交付**：敌意环境实测记录（依赖永不返回 / 雪崩 / 分片倾斜 / 恢复演练）
> **对应**：流程 `howto/godot/backend-stability.md` · 审核 `audit/godot/backend-stability.md`

## 0. 交付物定义

1. ⛔ 让一个依赖"永不返回"，确认超时与熔断真的生效
2. 缓存雪崩实测：一批 key 同时过期
3. 分片倾斜实测：制造访问分布不均
4. 恢复演练：备份能恢复到 RTO 内
5. ⛔ 数据回滚不可行已验证，主路径是向前修复

## 2. 工序

### Step 1　⛔ 让一个依赖"永不返回"，看超时与熔断是否真的生效　`[backend-stability/07#S1]`

【读】`howto/godot/backend-stability.md#4. 超时与重试：把瞬时故障扩散成 DDoS 的放大器`

【做】
正常压测里依赖总是会返回，于是**“永不返回”这条路径从未执行**。
⛔ 而它正是故障的真实形态：不抛异常、不返回错误码，
在统计里表现为"既没成功也没失败"。
验证方法：让依赖挂起（不返回也不拒绝），确认
调用侧超时触发、该超时被计为失败、熔断在预期时间内打开。
⚠ 只测"依赖返回 500"，走的是另一条代码路径。

【产出】依赖挂起测试记录（超时触发 → 计为失败 → 熔断打开）

【判据】熔断在预期时间内打开，且失败统计里包含超时

【审】`audit/godot/backend-stability.md#6`


### Step 2　缓存雪崩实测：让一批 key 同时过期　`[backend-stability/07#S2]`

【读】`howto/godot/backend-stability.md#5. 数据层：先证明瓶颈，分片键决定拆分能否长期成立`

【做】
TTL 固定值时，过期时刻是确定的、尖峰也是确定的。
⛔ 日常监控看不到它，因为日常没有"大批 key 恰好同时过期"这个条件。
验证方法：批量写入同 TTL 的 key，等待同时过期，观察回源 QPS 与 DB 负载。
⛔ 只加 Redis 高可用不能解决雪崩——高可用防的是节点挂，不是同时回源。

【产出】雪崩测试记录（回源 QPS 曲线 + DB 负载）

【判据】同时过期时的回源量在 DB 可承受范围内

【审】`audit/godot/backend-stability.md#21`


### Step 3　分片倾斜实测：制造访问分布不均　`[backend-stability/07#S3]`

【读】`howto/godot/backend-stability.md#5. 数据层：先证明瓶颈，分片键决定拆分能否长期成立`

【做】
倾斜在均值视图下不可见。验证方法：让大部分访问落到少数分片，
确认面板能定位到具体分片，而不是只显示集群均值。
⛔ 只有一行集群汇总的面板，会在倾斜已经很严重时仍然全绿。

【产出】倾斜测试记录（按分片的行数 / QPS / 慢查询）

【判据】面板能指出是哪几个分片在报警

【审】`audit/godot/backend-stability.md#18`


### Step 4　⛔ 恢复演练：副本数量不能证明能恢复　`[backend-stability/07#S4]`

【读】`howto/godot/backend-stability.md#9. 灾备：备份要证明能在目标时间内恢复`

【做】
备份可能打开失败、表结构缺失、增量链断裂、权限丢失、回放后应用仍报错。
⛔ **副本数量不能证明能恢复**。
验证要超出"文件可读"：服务能否启动、连接、权限、关键表行数、
校验和、端到端业务路径。
⛔ 只验证文件可读，是最常见的假通过——
它证明的是备份工具正常，不是系统能恢复。

【产出】恢复演练记录（含实测 RTO 数字）

【判据】端到端业务路径跑通，且 RTO 有实测数字

【审】`audit/godot/backend-stability.md#33`


### Step 5　RPO/RTO 必须来自业务容忍度，⛔ 不是基础设施拍数字　`[backend-stability/07#S5]`

【读】`howto/godot/backend-stability.md#9. 灾备：备份要证明能在目标时间内恢复`

【做】
核心战斗状态可接受秒级回放，但**支付资产不能接受任意丢失**。
⛔ 用同一个 RPO 覆盖所有数据，会让最不能丢的那一类被最宽松的口径保护。
验证要按数据类型分行，并逐行确认业务方签字。
⚠ 异地多活不是可靠性的免费升级：要考虑复制延迟、冲突解决、
全局唯一 ID、跨区调用成本与合规数据边界。

【产出】RPO/RTO 表（按数据类型分行 + 业务方确认）

【判据】每类数据的 RPO/RTO 都有业务方确认，不是技术侧定的

【审】`audit/godot/backend-stability.md#34`


### Step 6　⛔ 数据回滚往往不可行，主路径是向前修复　`[backend-stability/07#S6]`

【读】`howto/godot/backend-stability.md#9. 灾备：备份要证明能在目标时间内恢复`

【做】
恢复到旧时间点会创造"部分玩家回到过去"的不公平状态，
也会覆盖恢复点之后的合法操作。
替代方案：PITR 到隔离环境审计、按业务对象幂等补偿、差异修复、单表 / 单玩家修复。
⛔ 把"回滚数据库"写进预案，等于准备了一个大概率不可执行的动作——
而它在演练中永远不会被真的执行到，所以永远不会暴露。
⚠ 真需要全量回滚时：**先阻断写流量** → 确认恢复点与影响 → 授权人决策。

【产出】向前修复方案（含存档版本协同，见 `save` 域接缝）

【判据】预案的主路径是向前修复，回滚是特例且有授权步骤

【审】`audit/godot/backend-stability.md#36`


## 3. 验收清单

- [ ] ⛔ 依赖永不返回时熔断能打开
- [ ] 一批 key 同时过期的回源量已实测
- [ ] 面板能定位到具体分片
- [ ] ⛔ 恢复演练跑通端到端，RTO 有数字
- [ ] RPO/RTO 按数据类型分行且有业务方确认
- [ ] 预案主路径是向前修复，不是回滚

## 4. 常见返工

| 症状 | 原因 | 回到 |
|---|---|---|
| 永不返回却从不熔断 | 只测返回 500 | S1 |
| 回源打垮 DB | TTL 固定值 | S2 |
| 均值全绿但某分片报警 | 只有集群汇总 | S3 |
| 备份可读但恢复不起来 | 只验证文件 | S4 |
| 最不能丢的数据丢了 | RPO 一刀切 | S5 |
| 预案执行不了 | 主路径是回滚 | S6 |
