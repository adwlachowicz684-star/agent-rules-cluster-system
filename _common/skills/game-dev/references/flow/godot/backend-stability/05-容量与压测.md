# 05 容量与压测（服务端稳定性域）

> **本步交付**：容量模型 + 受控失败压测 + 扩容计时
> **对应**：流程 `howto/godot/backend-stability.md` · 审核 `audit/godot/backend-stability.md`

## 0. 交付物定义

1. 容量由业务事件推到全链路，不是拍一个 QPS
2. ⛔ 压测覆盖"受控失败"，不只稳态 QPS
3. 扩容全过程已计时，且短于峰值到达时间
4. 生产压测有可秒停的开关
5. 压测结果给出 P99 与拐点，是可复现的数字

## 1. 前置检查清单

- [ ] 容量模型含连接数、消息条数与扇出倍数
- [ ] 压测场景表含冷启动、击穿、单节点故障、扩容全程
- [ ] ⛔ 扩容计时有实测数字，不是"应该很快"
- [ ] 生产压测有一键停止与回滚负责人
- [ ] 压测报告同时记录 P99 与拐点

## 2. 工序

### Step 1　容量从业务事件推，⛔ 不是拍一个 QPS　`[backend-stability/05#S1]`

【读】`howto/godot/backend-stability.md#6. 容量：从业务事件推到全链路资源`

【做】
`峰值 QPS = 峰值同时在线 × 每人在线期间平均请求频率`；
消息型还要算连接数、消息条数、大小、扇出倍数。
⛔ 只按历史 QPS 乘一个系数，会漏掉扇出——
一次公会广播的写放大可能是几百倍，
而它在 QPS 曲线上只表现为"一个请求"。

【产出】容量模型（QPS + 连接数 + 扇出倍数）

【判据】任一业务事件都能算出它对下游的放大倍数

【审】`audit/godot/backend-stability.md#23`


### Step 2　⛔ 压测要测"系统还能否受控失败"，不只稳态 QPS　`[backend-stability/05#S2]`

【读】`howto/godot/backend-stability.md#6. 容量：从业务事件推到全链路资源`

【做】
至少覆盖：日常稳态 · 开服 / 整点尖峰 · 实例冷启动 · 缓存击穿 · 单节点故障 ·
依赖降级 · 跨区网络恶化 · 慢查询 · 连接池耗尽 · 队列积压 · **自动扩容全过程**。
⚠ 稳态跑得很好而冷启动直接崩，是最常见的落差：
冷启动时缓存是空的、连接池是空的、JIT 还没热，
⛔ 而稳态压测永远走不到这条路径。

【产出】压测场景表（十一类场景 × 预期表现）

【判据】每类场景都有实测记录，不是"应该能扛"

【审】`audit/godot/backend-stability.md#24`


### Step 3　⛔ 扩容要全链路计时：扩容可能就是事故原因　`[backend-stability/05#S3]`

【读】`howto/godot/backend-stability.md#6. 容量：从业务事件推到全链路资源`

【做】
扩容按"检测—决策—申请—启动—预热—注册—验证"计时。
若自动扩容要 5 分钟而峰值 3 分钟到，**扩容就是事故原因而非解决方案**。
→ 预测性扩容、开服前预热、预留实例应与自动扩容并存。
⛔ 只看"扩容最终成功了"，会漏掉中间那 3 分钟——
而玩家正是在那 3 分钟里流失的。

【产出】扩容计时表（七段各自的耗时）

【判据】总耗时短于峰值到达时间，否则有预热与预留方案

【审】`audit/godot/backend-stability.md#25`


### Step 4　生产压测是受控变更：⛔ 没有可秒停的开关就不该打生产　`[backend-stability/05#S4]`

【读】`howto/godot/backend-stability.md#6. 容量：从业务事件推到全链路资源`

【做】
预批准、专属标签、白名单、**一键停止**、独立监控、回滚负责人。
⛔ 没有可秒停的开关，压测本身就成了一个没有止损手段的变更——
一旦流量超出预期，唯一的停止方式是等它自己结束。

【产出】生产压测方案（含一键停止与回滚负责人）

【判据】停止开关已实测可用，且有人能在 1 分钟内执行

【审】`audit/godot/backend-stability.md#44`


### Step 5　⛔ 只知道最高 QPS 不算压测完，要同时看 P99　`[backend-stability/05#S5]`

【读】`howto/godot/backend-stability.md#6. 容量：从业务事件推到全链路资源`

【做】
只跑到"最高 QPS"却不知道此时 P99 是否已不可接受，是无效压测。
⛔ 峰值 QPS 与可接受 P99 通常不在同一个点上：
能扛住的 QPS 往往比"体验可接受的 QPS"高不少，
⛔ 而报告里那个更大的数字会自然成为对外口径。

【产出】压测报告（拐点 + 该点 P99）

【判据】报告给出的是成对数字，不是单个最大 QPS

【审】`audit/godot/backend-stability.md#45`


## 3. 参考实现

```gdscript
# ⓘ 承接本步产出：容量由业务事件推，且扩容计时短于峰值到达
const SCALE_UP_BUDGET_SEC := 180.0
const PEAK_CCU := 10000
const REQ_PER_MIN_PER_PLAYER := 6.0
const FANOUT_GUILD_BROADCAST := 200.0

func _peak_qps(ccu: int, req_per_min: float) -> float:
	return ccu * req_per_min / 60.0

func _write_amplification(fanout: float) -> float:
	# ⛔ 扇出不体现在 QPS 曲线上：一次广播在曲线上只有"一个请求"
	return fanout
```

## 4. 验收清单

- [ ] 容量模型含扇出与连接数
- [ ] ⛔ 十一类压测场景有实测记录
- [ ] 扩容计时短于峰值到达时间
- [ ] ⛔ 生产压测有一键停止开关
- [ ] 压测报告是拐点 + P99 成对数字

## 5. 常见返工

| 症状 | 原因 | 回到 |
|---|---|---|
| 广播打垮下游 | 没算扇出 | S1 |
| 冷启动直接崩 | 只测稳态 | S2 |
| 峰值到了还没扩完 | 扩容计时过长 | S3 |
| 压测停不下来 | 无一键停止 | S4 |
| 报告数字与体验不符 | 只报最大 QPS | S5 |
