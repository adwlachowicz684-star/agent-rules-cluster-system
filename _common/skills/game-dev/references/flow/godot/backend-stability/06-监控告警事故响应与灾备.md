# 06 监控告警事故响应与灾备（服务端稳定性域）

> **本步交付**：可执行告警 + 分级止损 + 恢复演练记录
> **对应**：流程 `howto/godot/backend-stability.md` · 审核 `audit/godot/backend-stability.md`

## 0. 交付物定义

1. 告警对象是"当前或即将发生的用户影响"，不是所有异常指标
2. ⛔ 告警已降噪，且每条指向唯一一组可执行动作
3. 事故分级是写死的触发条件，不是靠人判断
4. 止损与定位分离：先恢复再查根因
5. 恢复判据是指标回到 SLO 内，不是"告警不响了"

## 1. 前置检查清单

- [ ] 面板同时有 RED（用户是否不高兴）与 USE（哪里是瓶颈）
- [ ] ⛔ 告警疲劳指标被跟踪（每班 page 数）
- [ ] 每条 page 告警含九项字段，第一动作不是"登录看看"
- [ ] 事故等级有触发条件与自动升级规则
- [ ] 恢复后观察窗口覆盖一个完整业务周期

## 2. 工序

### Step 1　告警对象是用户影响；⛔ 只有 CPU/内存仪表盘不能证明体验良好　`[backend-stability/06#S1]`

【读】`howto/godot/backend-stability.md#7. 监控与告警：告警必须有人能立即执行`

【做】
**RED**（Rate / Errors / Duration）回答"用户是否不高兴"；
**USE**（Utilization / Saturation / Errors）回答"哪里是瓶颈"。
⛔ 只有 CPU / 内存的仪表盘**不能证明玩家体验良好**——
它是资源视图，而资源空闲时用户可能正在排队、正在超时、正在看到旧数据。
⚠ 埋点口径要与告警指标对齐（见 `analytics` 域接缝），
否则"用户不高兴"这件事在数据上根本不存在。

【产出】RED + USE 面板（两类指标齐全）

【判据】能回答"现在用户是否不高兴"与"瓶颈在哪里"两个问题

【审】`audit/godot/backend-stability.md#26`


### Step 2　⛔ 告警必须降噪：告警疲劳会直接拉长发现时间　`[backend-stability/06#S2]`

【读】`howto/godot/backend-stability.md#7. 监控与告警：告警必须有人能立即执行`

【做】
集群宕机时不要重复 page 所有节点；同根因合并；
恢复与触发用同一事件指纹。
⚠ **告警疲劳会直接拉长发现时间**——工程师开始静音通知，
真事故被埋在几百条里。
ⓘ 要跟踪"每班 page 数"这个元指标：
⛔ 它上升时，告警系统的信息价值正在下降，而这件事没有任何告警会报。

【产出】告警降噪规则（合并 / 抑制 / 指纹）+ 每班 page 数跟踪

【判据】同根因只产生一条 page，且 page 数有趋势记录

【审】`audit/godot/backend-stability.md#27`


### Step 3　每条 page 告警都要有唯一一组可执行动作　`[backend-stability/06#S3]`

【读】`howto/godot/backend-stability.md#7. 监控与告警：告警必须有人能立即执行`

【做】
每条 page 级告警至少含：服务 / 接口、用户影响、影响范围、触发条件、
确认时效、**第一动作**、Runbook 链接、负责人、抑制规则。
⛔ **动作只是"登录看看"说明规则层级或自动化不足**，
应降为工单、移到 dashboard 或直接删。
三条评分：代表当前用户影响？必须人 5 分钟内介入？指向唯一一组可执行动作？
**任意一条不满足就降级。**

【产出】告警规则表（九项字段齐全 + 评分结果）

【判据】任一 page 的第一动作都不是"登录看看"

【审】`audit/godot/backend-stability.md#28`


### Step 4　⛔ 事故分级要写死触发条件，不能靠人判断　`[backend-stability/06#S4]`

【读】`howto/godot/backend-stability.md#8. 事故响应：第一指标是止损时间`

【做】
P0–P3 各级要有明确的触发条件与自动升级规则
（影响范围、受影响能力、持续时间）。
⛔ 靠领导判断定级，会让定级发生在"有人注意到"之后——
而"有人注意到"本身就是发现时间的主要组成部分。
⚠ 确认时效与止损时效要写成数字，⛔ "尽快处理"不是承诺。

【产出】事故分级表（P0–P3 触发条件 + 确认 / 止损时效）

【判据】任一线上现象都能不经过讨论定出等级

【审】`audit/godot/backend-stability.md#29`


### Step 5　⛔ 先恢复再查根因；止损与定位是两个独立目标　`[backend-stability/06#S5]`

【读】`howto/godot/backend-stability.md#8. 事故响应：第一指标是止损时间`

【做】
流程是"发现—定级—止损—定位—恢复—复盘"。
止损动作按风险从低到高：停止发布 → 关闭最近配置 → 回滚最近版本 → 切流 →
隔离故障实例 → 限流 / 降级 → 停活动 → 拒绝非核心请求。
⚠ **先恢复再查根因**——定位缓慢不能成为继续承受影响的理由。
⛔ **禁止多人同时改配置、扩容、重启和回滚**：
并发的止损动作会互相掩盖效果，让"哪个动作起了作用"无法回答。

【产出】止损动作序列（含执行人 / 复核人 / 回退条件）

【判据】每次操作有执行人、复核人与回退条件

【审】`audit/godot/backend-stability.md#30`


### Step 6　⛔ 恢复判据是指标回到 SLO 内，不是"告警不响了"　`[backend-stability/06#S6]`

【读】`howto/godot/backend-stability.md#8. 事故响应：第一指标是止损时间`

【做】
恢复判断依据是指标回到基线或 SLO 内。
故障关闭后仍需观察至少一个完整业务周期
（活动结束、登录队列清空、缓存预热完成）。
⛔ "告警不响了"可能只是触发条件被顺手调宽了，
也可能是流量自然回落——两者都不等于系统恢复了。

【产出】恢复判据清单（指标 + 基线 + 观察窗口）

【判据】关闭事故时能给出指标截图或数字，不是"看起来好了"

【审】`audit/godot/backend-stability.md#31`


### Step 7　复盘每项行动都要可验证，⛔ 禁止"下次注意"　`[backend-stability/06#S7]`

【读】`howto/godot/backend-stability.md#8. 事故响应：第一指标是止损时间`

【做】
无责复盘不是不问责，是把责任从个人转移到可改进系统。
⛔ 禁止只写"下次注意""加强监控""提高代码质量"——
每项行动要可验证（"登录网关增加按账号限流，压测达目标值"），
且有人、有期限。
ⓘ 长期夜间 page 应优先偿还可靠性债务，而不是继续加人。

【产出】复盘行动项表（每项含可验证判据 + 负责人 + 期限）

【判据】每项行动在期限到达时能判定完成与否

【审】`audit/godot/backend-stability.md#32`

## 5. 常见返工

| 症状 | 原因 | 回到 |
|---|---|---|
| 资源空闲但用户排队 | 只有资源视图 | S1 |
| 真事故被埋没 | 告警疲劳 | S2 |
| 收到告警不知道干嘛 | 动作是"登录看看" | S3 |
| 定级发生在注意到之后 | 靠人判断 | S4 |
| 定位久、影响持续 | 没有先止损 | S5 |
| "看起来好了"又复发 | 判据不是指标 | S6 |
| 复盘后没有改变 | 行动不可验证 | S7 |
