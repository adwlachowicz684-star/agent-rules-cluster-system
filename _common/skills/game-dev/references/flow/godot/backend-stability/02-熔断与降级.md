# 02 熔断与降级（服务端稳定性域）

> **本步交付**：三态机 + 按调用类型阈值 + 降级档位配置
> **对应**：流程 `howto/godot/backend-stability.md` · 审核 `audit/godot/backend-stability.md`

## 0. 交付物定义

1. 三态机（Closed / Open / Half-open）已实现，且有最少样本约束
2. ⛔ 超时计入失败统计，不是只统计异常
3. 熔断阈值按调用类型拆分（登录 / 支付 / 发货 / 战斗结算）
4. Half-open 只放行少量探测
5. 每档降级都有玩家可见表现，且开关走正式发布

## 1. 前置检查清单

- [ ] 三态转移条件写成了可判定的数字（样本数、失败率、保持时长）
- [ ] ⛔ 统计口径里包含超时
- [ ] 阈值表按调用类型分行，不是全局一个值
- [ ] Half-open 的探测数量是数字
- [ ] 降级档位含"玩家可见表现"与"自动关闭条件"

## 2. 工序

### Step 1　三态机 + 最少样本，⛔ 统计里必须包含超时　`[backend-stability/02#S1]`

【读】`howto/godot/backend-stability.md#2. 熔断：防持续打击已故障依赖`

【做】
`Closed ──(失败率 + 最少样本达阈值)──▶ Open ──(reset_timeout)──▶ Half-open`。
⛔ **只统计异常不统计超时，会把"永远不返回"的服务当健康**——
这类依赖不会抛异常、不会返回错误码，在统计里表现为"既没成功也没失败"，
于是失败率始终为零，熔断永远不打开。
同时要有**最少样本**：只按连续失败计数而不设滑动窗口，
会被低频间歇错误误触发。
⚠ 这里的"失败"必须显式定义为 `超时 or 异常 or 业务错误码` 三者之一。

【产出】三态机实现 + 失败定义（超时 / 异常 / 错误码三类）

【判据】让一个依赖永不返回，熔断能在预期时间内打开

【审】`audit/godot/backend-stability.md#6`


### Step 2　⛔ 阈值按调用类型拆分，不能全局共用一个失败率　`[backend-stability/02#S2]`

【读】`howto/godot/backend-stability.md#2. 熔断：防持续打击已故障依赖`

【做】
登录、支付、发货、战斗结算的失败代价完全不同，
⛔ 共用一个"错误率 50%"会让代价最高的那一类被最宽松的阈值保护。
同时要决定是**按 endpoint 熔断还是按逻辑服务熔断**——
按 endpoint 会让单实例故障把整个服务快速失败掉；
按逻辑服务则会放过"只有一个 endpoint 坏了"的情况。

【产出】按调用类型的阈值表（含熔断粒度的选择）

【判据】支付与登录的阈值不同，且粒度选择有明确理由

【审】`audit/godot/backend-stability.md#7`


### Step 3　Half-open 只放行少量探测　`[backend-stability/02#S3]`

【读】`howto/godot/backend-stability.md#2. 熔断：防持续打击已故障依赖`

【做】
Half-open 的作用是**防止刚恢复的依赖被探测请求淹没**——
只放行少量探测，连续成功才回 Closed。
⛔ 全量放行等于把刚刚缓过来的依赖再打挂一次，
而且第二次打击通常比第一次更彻底（此时它的缓存与连接池都还是冷的）。

【产出】Half-open 探测策略（数量 + 成功判据）

【判据】探测数量是数字，且连续成功才回 Closed

【审】`audit/godot/backend-stability.md#8`


### Step 4　降级是产品预先批准的可用能力降级，不是隐藏报错　`[backend-stability/02#S4]`

【读】`howto/godot/backend-stability.md#3. 降级：产品预先批准的可用能力降级，不是隐藏报错`

【做】
可降三类：**功能**（关掉全服排行榜实时刷新、公会广播）、
**精度**（用 5 分钟前的缓存榜单、返回 100 条降到 20 条）、
**一致性**（异步最终一致发货）。
⛔ 每一档必须配置：开关名称、灰度范围、生效 / 失效时间、负责人、依赖指标、
**玩家可见表现**、数据副作用、自动关闭条件。
⛔ 缺了"自动关闭条件"，降级会永久留在线上——
因为没有人敢在没确认恢复的情况下手动关掉它。

【产出】降级档位配置表（八项字段齐全）

【判据】每档都能说出玩家会看到什么，且有关闭条件

【审】`audit/godot/backend-stability.md#9`


### Step 5　⛔ 开关走正式配置发布，SSH 改生产不是常规路径　`[backend-stability/02#S5]`

【读】`howto/godot/backend-stability.md#3. 降级：产品预先批准的可用能力降级，不是隐藏报错`

【做】
降级开关要走正式的配置发布通道（见 `ops` 域 02 的配置下发），
⛔ "直接 SSH 改生产配置"不应是常规路径：
它没有审批、没有灰度、没有回滚点，也留不下"谁在什么时候改了什么"的记录。
事故中临时改过的配置，事后往往忘了改回去，
⛔ 而那份"临时改动"正是下一次故障的初始条件。

【产出】开关发布与回滚流程（含改动记录）

【判据】任一开关的变更都能查到执行人与时间

【审】`audit/godot/backend-stability.md#10`


## 3. 参考实现

```gdscript
# ⓘ 承接本步产出：失败必须包含超时，不只是异常
const CB_MIN_SAMPLES := 20
const CB_ERROR_RATIO := 0.5
const CB_OPEN_SEC := 30.0
const CB_HALF_OPEN_PROBES := 3

enum CBState { CLOSED, OPEN, HALF_OPEN }

# ⛔ timed_out 与 threw 都要计成失败，否则"永不返回"永远打不开熔断
func _is_failure(timed_out: bool, threw: bool, bad_code: bool) -> bool:
	return timed_out or threw or bad_code
```

## 5. 常见返工

| 症状 | 原因 | 回到 |
|---|---|---|
| 依赖永不返回却从不熔断 | 只统计异常 | S1 |
| 支付被宽松阈值保护 | 全局一个阈值 | S2 |
| 刚恢复又被打挂 | Half-open 全量放行 | S3 |
| 降级永久留在线上 | 缺自动关闭条件 | S4 |
| 临时改动忘了改回 | SSH 改生产 | S5 |
