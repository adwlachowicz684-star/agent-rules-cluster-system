# 04 数据层与分片（服务端稳定性域）

> **本步交付**：瓶颈证明 + 分片键 + 缓存三失效治理
> **对应**：流程 `howto/godot/backend-stability.md` · 审核 `audit/godot/backend-stability.md`

## 0. 交付物定义

1. 已证明瓶颈在数据层，不是先分片再找理由
2. 分片键贴合主要访问路径
3. ⛔ 指标按分片看，不看集群均值
4. 读写分离只降读压力这件事已被写进结论
5. 缓存穿透 / 击穿 / 雪崩三类分开治理，TTL 带抖动

## 1. 前置检查清单

- [ ] 已排除索引缺失、慢查询、锁竞争、连接池过小、缓存命中率低、写入热点
- [ ] 分片键的选择理由是"主要查询带不带它"
- [ ] 监控面板按分片分行，不是只有一个集群均值
- [ ] 核心支付 / 发货 / 战斗结果明确读主库或带版本校验
- [ ] TTL 生成时带随机抖动

## 2. 工序

### Step 1　⛔ 先证明瓶颈在数据层，分片不是早期优化　`[backend-stability/04#S1]`

【读】`howto/godot/backend-stability.md#5. 数据层：先证明瓶颈，分片键决定拆分能否长期成立`

【做】
先排除索引缺失、慢查询、锁竞争、连接池过小、缓存命中率低、单条记录过大、写入热点；
单机扩容、只读副本、表分区、归档与冷热分层通常应先于水平分片。
⛔ **过早分片会把一次索引优化变成跨库事务、跨片聚合、全局 ID、
Schema 迁移与运维平台重构**——
而它换来的性能，往往一次索引优化就能拿到。
⚠ 判据是"能不能指出瓶颈的单点"，不是"数据量看起来很大"。

【产出】瓶颈证明（慢查询 / 锁等待 / IOPS 等实测数据）

【判据】能指出具体是哪一类瓶颈，且排除项已逐个过一遍

【审】`audit/godot/backend-stability.md#16`


### Step 2　分片键要贴合访问路径，不是看起来均匀　`[backend-stability/04#S2]`

【读】`howto/godot/backend-stability.md#5. 数据层：先证明瓶颈，分片键决定拆分能否长期成立`

【做】
分片键的实质是**让主要访问路径集中在少数分片**，不是让数据"看起来均匀"。
玩家最常按账号查却选了个分布均匀但查询从不带的字段 → **每次扫描全分片**；
低基数枚举分片键 → 严重倾斜。
⛔ 还要在拆分**之前**确定扩容方案：是否允许双写迁移、能否按范围再平衡、
哈希冲突怎么迁移、迁移中旧路由怎么灰度——
⛔ 这些在拆完后再补，等于第二次拆分。

【产出】分片键选择表（含扩容与迁移方案）

【判据】主要查询都带分片键，且迁移路径已写明

【审】`audit/godot/backend-stability.md#17`


### Step 3　⛔ 按分片看指标，集群均值会掩盖倾斜　`[backend-stability/04#S3]`

【读】`howto/godot/backend-stability.md#5. 数据层：先证明瓶颈，分片键决定拆分能否长期成立`

【做】
选错分片键的表现是"集群平均很低，但某分片持续报警"。
必须**按分片**统计行数、存储、读写 QPS、慢查询、锁等待、连接与复制延迟。
⛔ 只看均值的面板，会在倾斜已经很严重时仍然全绿——
均值本身就是设计来掩盖离群值的。

【产出】按分片的监控面板（六项指标 × 分片数）

【判据】面板能定位到具体分片，而不是只有一行集群汇总

【审】`audit/godot/backend-stability.md#18`


### Step 4　读写分离只降读压力，⛔ 不消除复制延迟　`[backend-stability/04#S4]`

【读】`howto/godot/backend-stability.md#5. 数据层：先证明瓶颈，分片键决定拆分能否长期成立`

【做】
读写分离不降写压力，也不消除复制延迟。
核心支付 / 发货 / 战斗结果必须读主库或带版本校验；
允许陈旧的要显式标 `stale=true`。
⛔ 不标 `stale=true` 的陈旧读，会让下游把它当权威值继续写入——
于是延迟被固化成数据，且无法回滚。

【产出】读路径分类表（哪些必须读主库，哪些允许陈旧）

【判据】每个读路径都标了是否允许陈旧

【审】`audit/godot/backend-stability.md#19`


### Step 5　缓存三类失效分开治理，⛔ TTL 必须带抖动　`[backend-stability/04#S5]`

【读】`howto/godot/backend-stability.md#5. 数据层：先证明瓶颈，分片键决定拆分能否长期成立`

【做】
**穿透**（查不存在的数据）→ 参数校验 + 缓存空标记（短 TTL）或布隆过滤器；
**击穿**（热点 key 过期瞬间并发回源）→ singleflight / 互斥锁 / 逻辑过期 / 主动刷新；
**雪崩**（大批 key 同时过期）→ TTL 加**随机抖动** + 多级兜底 + DB 限流。
⛔ TTL 用固定值，等于预约了一次雪崩：
过期时刻是确定的，流量尖峰也是确定的。
⚠ 热点 key 不可用一把大锁（无关请求被串行化）；
空值与布隆过滤器可能被恶意键撑爆内存。

【产出】三类失效各自的治理方案 + TTL 生成函数

【判据】TTL 生成带随机量，且三类现象有各自的解法

【审】`audit/godot/backend-stability.md#20`


### Step 6　DDL 是元数据锁与复制延迟风险，⛔ 禁止手工粘长 SQL　`[backend-stability/04#S6]`

【读】`howto/godot/backend-stability.md#5. 数据层：先证明瓶颈，分片键决定拆分能否长期成立`

【做】
变更前审查算法与锁模式、表大小、磁盘、活跃事务；
变更中监控锁等待、线程池、IOPS、从库延迟；
变更后 Schema diff + 采样查询 + 回滚演练。
⛔ **生产禁止手工粘贴未经审核的长 SQL**——
手工执行的变更没有回滚点，也没有"谁在什么时候改了什么"的记录。

【产出】DDL 变更流程（前 / 中 / 后三段检查项）

【判据】任一 DDL 都能查到审核记录与回滚步骤

【审】`audit/godot/backend-stability.md#22`


## 3. 参考实现

```gdscript
# ⓘ 承接本步产出：TTL 必须带随机抖动，且分片数默认不分片
const CACHE_TTL_JITTER_RATIO := 0.1
const SHARD_COUNT := 1   # ⛔ 先证明瓶颈再分，不是默认就分

func _ttl_with_jitter(base_ttl: float) -> float:
	# ⛔ 固定 TTL 等于预约一次雪崩：过期时刻确定，尖峰也确定
	return base_ttl * (1.0 + randf() * CACHE_TTL_JITTER_RATIO)

func _shard_of(key: int) -> int:
	# ⛔ SHARD_COUNT 为 1 时此函数不应参与路由
	return key % SHARD_COUNT
```

## 5. 常见返工

| 症状 | 原因 | 回到 |
|---|---|---|
| 分片后问题更多 | 过早分片 | S1 |
| 每次扫描全分片 | 分片键不带查询 | S2 |
| 均值全绿但某分片报警 | 只看均值 | S3 |
| 陈旧读被当权威值写入 | 没标 stale | S4 |
| 预约了一次雪崩 | TTL 固定值 | S5 |
| DDL 锁住全表 | 手工执行未审查 | S6 |
