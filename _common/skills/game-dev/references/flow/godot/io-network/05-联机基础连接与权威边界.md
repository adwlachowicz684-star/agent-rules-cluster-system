# 05 联机基础：连接与权威边界（资源与网络域）

> **本步交付**：权威清单 + 稳定身份 + 错误码处理 + RPC 校验 + 重连路径
> **对应**：流程 `howto/godot/io-network.md` · 审核 `audit/godot/io-network.md`

## 0. 交付物定义

1. 权威边界清单已写（哪些判定只在服务端）
2. 玩家有**稳定身份**，⛔ 不是 `peer_id`
3. `create_server` / `create_client` 的错误码被判
4. 每个 `any_peer` RPC 都校验了发送者
5. RPC 两端 NodePath / 签名一致
6. 断线与重连是**两条路径**都实现

## 1. 前置检查清单

- [ ] 能一句话说清哪些判定只在服务端
- [ ] 身份字段与连接序号分开
- [ ] 连接失败有明确错误提示
- [ ] `any_peer` 的 RPC 全部校验了 `get_remote_sender_id()`
- [ ] 重连后 RPC 关系已重建

## 2. 工序

### Step 1　先写权威边界清单，再写第一行 RPC　`[io-network/05#S1]`

【读】`howto/godot/io-network.md#4. 多人联机`

【做】
先列出"哪些判定只跑服务端"（伤害、掉落、交易、冷却、位置合法性），再写代码。
⛔ 先写业务最后补清单 —— 补的时候会顺手把客户端预测也划进权威，
表现为"手感变钝"，⛔ 而没人敢改回去（怕改坏同步）。

ⓘ 本域只到"连上、能同步"，⛔ 预测与回滚见 `netsync` 域，
不要在这里发明同步算法。

【产出】权威边界清单（判定项 → 只在服务端 / 可客户端）

【判据】指着任一判定项能说出它在哪一侧执行。

【审】`audit/godot/io-network.md#6`

### Step 2　peer_id 不是玩家身份：重连会变号　`[io-network/05#S2]`

【读】`howto/godot/io-network.md#建立连接`

【做】
引入**稳定身份**（账号 ID / 角色 ID），`peer_id` 只当**当前连接的地址**。
⛔ 用 `peer_id` 当数据库主键 —— 重连后号码变了，
数据串到别人身上，⛔ 而本地单机测试**永远正确**（每次都是 1）。

ⓘ 这条与"存档用什么做 key"是同一个问题：
⛔ 任何**会变**的东西都不能当主键，而 `peer_id` 恰好只在多人时才暴露它会变。

【产出】身份字段定义（稳定 ID + 当前 peer_id 的映射表）

【判据】同一账号断线重连，拿到的是同一份数据。

【审】`audit/godot/io-network.md#31`

### Step 3　连接失败要判错误码，"在跑"不等于"能接"　`[io-network/05#S3]`

【读】`howto/godot/io-network.md#建立连接`

【做】
判 `create_server` / `create_client` 的返回值，区分
`ERR_ALREADY_IN_USE`（端口占用）与 `ERR_CANT_CREATE`。
⛔ 只判 `!= OK` —— 表现为"服务端在跑但一个连接都接不进来"，
⛔ 而进程、端口监听看着都正常。

【产出】连接错误处理（错误码 → 用户可见提示）

【判据】端口被占用时给出明确提示，而不是静默启动。

【审】`audit/godot/io-network.md#32`

### Step 4　any_peer 是不可信输入边界：必须校验发送者　`[io-network/05#S4]`

【读】`howto/godot/io-network.md#RPC`

【做】
每个 `any_peer` RPC 第一行就 `get_remote_sender_id()` 校验权限，
再校验**参数范围**（数量、取值、冷却）。
⛔ 只校验"是不是合法玩家" —— 合法玩家也能传 99999 或负数。
⛔ 表现为"有人刷了道具但日志里每次调用都合法"。

ⓘ 官方还有一条：RPC 只校验函数名与参数**个数**匹配，
⛔ 参数取值完全不校验，所以校验必须自己写。

【产出】RPC 校验清单（每个 any_peer → 校验了哪些）

【判据】构造越权调用，被拒绝且不会执行副作用。

【审】`audit/godot/io-network.md#6`、`audit/godot/io-network.md#33`

### Step 5　RPC 两端签名与 NodePath 必须一致　`[io-network/05#S5]`

【读】`howto/godot/io-network.md#RPC`

【做】
保证两端脚本的 RPC 签名一致、节点路径一致（动态节点用 `force_readable_name`）。
⛔ 路径不一致 —— **RPC 静默不调用**，既不执行也不报错，
⛔ 表现为"点了没反应"，排查被引向逻辑分支。

ⓘ 动态生成的节点尤其容易中招：
`add_child` 不带 `true` 会得到 `Enemy` 与 `@Enemy@2` 这类自动名，两端不同。

【产出】节点命名约定（动态节点强制可读名）+ 签名检查

【判据】动态生成的节点上的 RPC 能被对端收到。

【审】`audit/godot/io-network.md#33`

### Step 6　断线与重连是两条路径，不能只测"点退出"　`[io-network/05#S6]`

【读】`howto/godot/io-network.md#建立连接`

【做】
实现**两条**路径：正常登出（走清理）与超时断线（走服务端补算）。
⛔ 只实现正常登出 —— 强杀进程/拔网线的玩家数据停在中间态，
⛔ 表现为"重连后状态不对"，而每次点退出测试都正常。

ⓘ 这与存档域的"强杀不是点退出"是同一条原则：
⛔ 两条路径在代码上完全不同，测一条等于没测。

【产出】断线检测（心跳超时）+ 重连恢复流程（重建 RPC 与同步关系）

【判据】强杀客户端后重连，状态与断线前一致。

【审】`audit/godot/io-network.md#36`

## 3. 参考实现

```gdscript
# ⓘ 承接本步产出：稳定身份 + 错误码判定 + any_peer 校验
# ⓘ 常量出处：PORT / MAX_PLAYERS 由参数表登记（待实测）
const PORT := 7000
const MAX_PLAYERS := 4
const MAX_AMOUNT := 999

var _account_by_peer: Dictionary = {}    # peer_id -> 稳定账号 ID

func host() -> Error:
    var err := _peer.create_server(PORT, MAX_PLAYERS)
    if err == ERR_ALREADY_IN_USE:
        push_error("端口被占用: %d" % PORT)   # ⛔ 不细分就只会看到"在跑但接不进"
        return err
    if err != OK:
        push_error("创建服务端失败: %d" % err)
        return err
    multiplayer.multiplayer_peer = _peer
    return OK

@rpc("any_peer", "call_local", "reliable")
func request_buy(item_id: StringName, amount: int) -> void:
    var sender := multiplayer.get_remote_sender_id()   # ⛔ 不可信输入边界
    if not _account_by_peer.has(sender):
        return
    # ⛔ 官方不校验参数取值：范围必须自己判
    if amount <= 0 or amount > MAX_AMOUNT:
        return
    _buy(_account_by_peer[sender], item_id, amount)
```

## 5. 常见返工

| 症状 | 原因 | 回到 |
|---|---|---|
| 手感变钝没人敢改 | 权威边界是补写的 | S1 |
| 重连后数据串号 | 用 peer_id 当主键 | S2 |
| 服务端在跑接不进 | 错误码没细分 | S3 |
| 有人刷道具但日志合法 | any_peer 只校验身份不校验范围 | S4 |
| 点到动态节点没反应 | NodePath 两端不一致 | S5 |
| 重连后状态不对 | 只实现了正常登出 | S6 |
