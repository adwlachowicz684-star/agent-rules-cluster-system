# 06 联机基础：同步与生成（资源与网络域）

> **本步交付**：replication 配置 + 生成契约 + 上限口径 + 同步内容清单
> **对应**：流程 `howto/godot/io-network.md` · 审核 `audit/godot/io-network.md`

## 0. 交付物定义

1. 同步属性已配进 replication 列表（⛔ 不只是 `@export`）
2. 生成走 `MultiplayerSpawner`，两端 NodePath 一致
3. 数量上限由**服务端**强制，⛔ 不依赖 `spawn_limit`
4. 同步**内容**与同步**频率**分开定
5. 客户端预测边界已指向 `netsync`，本域不发明算法
6. 本地多实例调试能区分身份

## 1. 前置检查清单

- [ ] replication 列表里有本次要同步的属性
- [ ] 生成节点的名字两端一致
- [ ] 上限是服务端数的
- [ ] 高频属性设了同步间隔
- [ ] 本地开了两个实例能区分

## 2. 工序

### Step 1　@export 不会自动同步：必须配 replication 列表　`[io-network/06#S1]`

【读】`howto/godot/io-network.md#MultiplayerSpawner / Synchronizer`

【做】
把要同步的属性**显式**加进 `MultiplayerSynchronizer` 的 replication 列表。
⛔ 只写 `@export` —— 属性不同步，
⛔ 而**面板上看不出差别**（`@export` 该显示的都显示了），
排查被引向"同步器没生效"。

ⓘ 这与"配了同步器就等于全同步"是相反的两句话：
同步器只同步**你列出来的**东西。

【产出】replication 列表（属性 → 是否同步 → 频率）

【判据】改一个属性，对端在画面上跟着变。

【审】`audit/godot/io-network.md#34`

### Step 2　生成走 Spawner，且节点名两端一致　`[io-network/06#S2]`

【读】`howto/godot/io-network.md#MultiplayerSpawner / Synchronizer`

【做】
服务端 `add_child(node, true)` 强制可读名，生成走 `MultiplayerSpawner`。
⛔ 手写 RPC 生成 —— 两端 NodePath 不一致时**静默失败**，
⛔ 表现为"服务端有、客户端没有"，而不报任何错。

ⓘ `spawn_function` 返回的节点必须**不在场景树中**，
⛔ 自己 `add_child` 会导致重复入树（见 `companion` 域同一条）。

【产出】生成契约（谁生成 → 名字规则 → 谁校验）

【判据】服务端生成后客户端在预期时间内出现同名节点。

【审】`audit/godot/io-network.md#33`

### Step 3　spawn_limit 不是权威上限：服务端要自己数　`[io-network/06#S3]`

【读】`howto/godot/io-network.md#MultiplayerSpawner / Synchronizer`

【做】
服务端维护自己的计数并强制上限，`spawn_limit` 只当**客户端复制保护**。
⛔ 把 `spawn_limit` 当权威 —— 它是客户端侧设置，
改包即可绕过，⛔ 表现为"设了 20 偶尔能出 23"，而服务端日志一切正常。

ⓘ 这条与"客户端校验只是提示"是同一条原则：
⛔ 客户端的任何限制都只是**体验优化**，不是约束。

【产出】服务端计数逻辑 + 超限拒绝路径

【判据】改包绕过客户端限制，服务端仍拒绝。

【审】`audit/godot/io-network.md#35`

### Step 4　同步内容与同步频率分开定　`[io-network/06#S4]`

【读】`howto/godot/io-network.md#MultiplayerSpawner / Synchronizer`

【做】
先定**同步什么**（位置、血量、状态机态），再定**多久同步一次**
（高频属性设间隔）。
⛔ 全部按默认最高频 —— 带宽打满，
⛔ 表现为"越玩越卡"，排查被引向渲染或逻辑性能。

ⓘ 反向也成立：血量这类低频但关键的属性若设了太长间隔，
会出现"血条跳变"，⛔ 排查被引向动画插值。

【产出】同步表（属性 → 频率档位 → 理由）

【判据】多人同屏时带宽与帧率在预算内。

【审】`audit/godot/io-network.md#42`

### Step 5　预测与回滚不在这里做：指向 netsync　`[io-network/06#S5]`

【读】`howto/godot/io-network.md#4. 多人联机`

【做】
本域只保证"状态能同步到"，⛔ **不定义**预测、回滚、插值算法 ——
那些见 `netsync` 域。
⛔ 在这里发明同步算法 —— 会与 `netsync` 的既有口径冲突，
⛔ 表现为"两套同步逻辑互相覆盖"，而每一套单看都合理。

ⓘ 分工口径：本域解决**通不通**，`netsync` 解决**顺不顺**。
⛔ 先做顺不顺再做通不通，会在连不上时完全无法定位。

【产出】指向 `netsync` 的接缝说明（本域不做什么）

【判据】本域文件里搜不到自创的插值 / 回滚实现。

【审】`audit/godot/io-network.md#37`

### Step 6　本地多实例调试要能区分身份　`[io-network/06#S6]`

【读】`howto/godot/io-network.md#建立连接`

【做】
本地开两个实例时，用命令行参数或窗口标题区分服务端/客户端与身份。
⛔ 不做区分 —— 两个窗口长得一样，
⛔ 表现为"改了一个窗口以为改的是服务端"，排查时间翻倍。

ⓘ 这与"peer_id 不是身份"（05/S2）呼应：
本地调试时两个实例的 peer_id 是稳定的，
⛔ 于是那些只在重连才暴露的问题**在本地永远测不出来**。

【产出】多实例启动脚本（含身份标记）

【判据】两个窗口能一眼分清谁是服务端。

【审】`audit/godot/io-network.md#31`

## 3. 参考实现

```gdscript
# ⓘ 承接本步产出：服务端计数上限 + 强制可读名 + 走 Spawner
# ⓘ 常量出处：MAX_ENTITIES 由参数表登记（待实测）
const MAX_ENTITIES := 64

var _count: int = 0

@rpc("any_peer", "call_local", "reliable")
func request_spawn(kind: StringName, pos: Vector3) -> void:
    if not multiplayer.is_server():
        return                              # ⛔ 权威在服务端
    if _count >= MAX_ENTITIES:              # ⛔ spawn_limit 不是权威上限
        push_warning("已达上限")
        return
    var n := _make(kind)
    n.position = pos
    _count += 1
    _spawn_root.add_child(n, true)          # ⛔ true = 强制可读名，两端一致
```

ⓘ 同步属性必须配进 `MultiplayerSynchronizer` 的 replication 列表，
⛔ 只写 `@export` 不会同步。
