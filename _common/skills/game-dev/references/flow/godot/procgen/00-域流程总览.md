# 程序化生成 —— 域流程总览

> ⚠ **第 0 步：先定做什么。**
> 本域有 7 个功能点，⛔ **不是全做** —— 按本次需求挑。

## 0. 先定做什么

| 本次要做的 | 走哪些功能点 |
|---|---|
| 只是要几张随机地图 | **不要套本域** → 见下 |
| 要能复现（种子能重放） | 01 → 02 → 07 |
| 地牢 / 房间型布局 | 01 → 02 → 03 → 07 |
| 洞穴 / 有机地形 | 01 → 02 → 03 → 04 → 07 |
| 有敌人 / 奖励投放 | 03 → 04 → 07 |
| 有锁与钥匙、要保证能通关 | 03 → 05 → 07 |
| 大世界地形、要存档 | 01 → 02 → 06 → 07 |
| 全套 | 01 → 02 → 03 → 04 → 05 → 06 → 07 |

⛔ **一次性生成、不打算复现、不要存档的项目不要套本域。**
⚠ 那属于 `howto/godot/procedural-generation.md` 的基础用法范围 ——
本域处理的是**要能复现、要能校验、要能存档、要能修 bug** 的复杂度。

ⓘ 分工：
- `howto/godot/procedural-generation.md` 讲**单个算法与 API 怎么用**
- `howto/godot/genres-roguelike.md` 讲**关卡生成管线与房间图**
- 本域讲**这些按什么顺序做、怎么保证可复现与可验收**

⛔ 若本域某步需要"WFC 的约束怎么定义"这类细节，指向那篇，**不在这里重复**。

## 1. 功能点拆解（按依赖，不可颠倒）

| # | 功能点 | 依赖 | 交付物 |
|---|---|---|---|
| 01 | 生成物与种子契约 | — | 边界清单 + 种子来源 + 生成器版本 |
| 02 | 随机源与可复现 | 01 | 实例隔离 + 种子质量 + 调用顺序锁定 |
| 03 | 布局算法与连通性 | 02 | 布局数据 + flood fill 校验 |
| 04 | 内容投放与密度 | 03 | 合法子区域 + 密度预算 |
| 05 | 约束求解与可解性 | 03 | 约束集 + 可解性校验 + 兜底 |
| 06 | 分帧实例化与版本迁移 | 03 | 一次性提交 + 生成器版本入档 |
| 07 | 生成验收 | 全部 | 同种子复现 + 边缘精度 + 可解性实测 |

⚠ **01 必须在一切之前**：不先定"哪些是生成物"，02 的隔离边界和 06 的迁移范围都无从划分。
⚠ **02 必须在 03 之前**：随机源不隔离，布局的复现性无从谈起。
⚠ **03 必须在 04 之前**：没有布局数据，投放没有合法位置可算。
⚠ **05 依赖 03 但不依赖 04**：可解性校验的是布局与锁的关系。

## 2. 与其他域的接缝

| 接缝 | 契约 |
|---|---|
| `relic` 域 局内构筑 | 同为"种子必须可复现"，共用同一套 RNG 契约 |
| `openworld` 域 开放世界 | 大坐标精度与分块，见 06 |
| `level` 域 关卡 | 手工件与生成物的风格统一，见 04 |
| `vegetation` 域 植被 | 泊松采样是共用的布点算法，见 04 |
| `save` 域 存档 | 存种子与生成器版本，不存生成结果，见 06 |
| `perf` 域 性能 | 生成耗时与内存峰值要进预算，见 07 |
| `ai` 域 导航 | 生成后要重烘导航，见 06 |

⛔ **若某条接缝对不上，要单独立一个接线功能点**。

## 3. 本域最容易做反的顺序

⛔ **先把画面生成出来（03/04），再回头补种子契约（01/02）。**

地形和房间是最直观的"生成"需求，于是先撒瓦片、先调噪声，
⚠ 而此时随机源是各写各的 →
**"这关有问题"无法复述、无法修、无法分享**，
⛔ 且不报错，只在要修 bug 或要做每日挑战时才暴露 —— 那时整个生成器已经定型。

✅ 正确顺序：先立种子契约与随机源隔离（01/02），再生成布局（03）。
