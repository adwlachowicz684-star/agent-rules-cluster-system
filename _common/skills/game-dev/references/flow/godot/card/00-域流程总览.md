# 卡牌 / 桌游（Card）—— 域流程总览

> ⚠ **第 0 步：先定"卡牌是定义还是实例、随机走哪个源、连锁由谁收口"。**
> 本域有 7 个功能点，⛔ **不是全做** —— 按本次需求挑。

## 0. 先定做什么

| 本次要做的 | 走哪些功能点 |
|---|---|
| 最小可玩：抽牌、打牌、结算 | 01 → 02 → 03 → 04 → 05 → 07 |
| 已经有牌与 UI，只补连锁 | 03 → 04 → 07 |
| 抽牌/洗牌对不上、回放不一致 | 01 → 02 → 06 → 07 |
| 效果互相触发、栈爆了 | 03 → 04 → 07 |
| 卡面数值改一张全变 | 01 → 07 |
| 多存档槽互相覆盖 | 06 → 07 |
| 手牌多了拖拽掉帧 | 05 → 07 |

⛔ **01 不能跳过** —— 卡牌、词条、赛制的形态差异很大，
但**"定义是共享的只读模板、对局里用的是复制出来的实例"**这一条完全统一。
⛔ 不先定这条，就会直接改 `CardData` 的字段当"这张牌本回合减费"，
而 `load()` 是带缓存的：牌库、手牌、弃牌堆里所有同名卡**是同一个对象**，
改一处全变，**且不报错**。
表现是"减费效果一开，牌库里剩下的火球全变 0 费"，
排查时 `Array[CardData]`、`Resource`、`@export` 全部检查都对。

⛔ **02 的随机源不能在 06 才统一**：回放与服务器校验都建立在"只有一个 rng"上，
到要复现时才发现洗牌走实例、AI 走全局，等于把整局随机重做一遍 ——
而它**不报错**，只表现为"同种子不同结果"。

ⓘ 03 与 04 是本域最容易互相甩锅的两步：
连锁顺序不对时，成因可能在"没入栈"也可能在"时机枚举没覆盖这个触发点"。
⛔ 所以 03 只定**栈与深度**，04 只定**谁在什么时候把东西放进去**，两边不许各判一次。

## 1. 功能点拆解与依赖

| # | 功能点 | 交付 | 依赖 |
|---|---|---|---|
| 01 | 卡牌数据与实例隔离 | `CardData` 是定义、对局内用实例、改动边界只有一处 | — |
| 02 | 牌堆、洗牌与随机源 | Deck/Hand/Pile 各自持有、单一 rng、同帧回抽保护 | 01 |
| 03 | 效果栈与连锁结算 | 显式栈、深度上限、事件入栈、结果驱动表现 | 01 |
| 04 | 回合、时机与目标合法性 | Timing 覆盖全部触发点、结算前校验目标仍合法 | 03 |
| 05 | 表现层、拖拽与手牌池 | `CardView` 纯观察者、固定容量池、重排预算 | 01 / 04 |
| 06 | 存档与回放复现 | `.res` 存档、槽位路径显式、种子与日志可复现 | 02 / 04 |
| 07 | 卡牌验收 | 同种子复现、连锁深度、读档一致、满手牌帧率 | 全部 |

⛔ **依赖是硬的**：04 的目标合法性校验要用 03 那份上下文，
⛔ 另建一份"当前目标列表"会得到"校验通过但结算时目标已经没了"，
而两份数据各自正确，只有不一致时才出错。

⛔ **06 依赖 02 而不是反过来**：先有单一随机源才有可复现，
先做存档再补随机源，存档里存的种子是**没有意义的数字**。

## 2. 域边界与接缝

| 邻域 | 分工 |
|---|---|
| `combat` 域 战斗结算 | 伤害公式与 Buff 见 `combat`，⛔ 本域只定"伤害要变成事件入栈" |
| `inventory` 域 背包 | 卡牌收藏与牌组持有见 `inventory`，⛔ 本域只管**对局内**的牌堆三态 |
| `ui` 域 UI | 布局与焦点导航见 `ui`，⛔ 本域只定 `CardView` 是观察者、不持有状态 |
| `save` 域 存档 | 持久化机制与云存档见 `save`，⛔ 本域只定"对局状态要能整体序列化" |
| `economy` 域 经济 | 货币与奖励账本见 `economy`，⛔ 本域只产出"这局赢了发多少" |
| `2d-rendering` 域 2D 渲染 | 排序与图层见 `2d-rendering`，⛔ 本域不另定手牌排序口径 |
| `netsync` 域 网络同步 | 传输与预测见 `netsync`，⛔ 本域只定"随机必须由一端决定" |
| `build-affix` | ⓘ howto 层，暂无 flow 域 —— 构筑合法性、禁用表、词条组合语义见该篇 |

## 3. 参数登记

| 参数 | 所在功能点 | 初始值 | 实测值 | 状态 |
|---|---|---|---|---|
| `MAX_DEPTH` 连锁深度上限 | 03 | 32 | — | 待实测（⛔ 不设就是无限递归） |
| `HAND_CAP` 手牌上限 | 02 | 10 | — | 待实测（⛔ 也是 05 池子容量，两处必须同一个数） |
| `HAND_POOL` 手牌视图池容量 | 05 | 12 | — | 待实测（⛔ 要 ≥ HAND_CAP + 动画中的 surplus） |
| `RESOLVE_GUARD` 单回合结算步数上限 | 04 | 512 | — | 待实测（⛔ 防"互相触发"式死循环） |
| `RESHUFFLE_MODE` 同帧回抽口径 | 02 | skip | — | 待实测（⛔ 玩法决定，不是技术默认） |
| `SAVE_SLOTS` 存档槽数量 | 06 | 3 | — | 待实测（⛔ 与 FLAG_CHANGE_PATH 口径绑定） |
| `DRAG_REDRAW_BUDGET` 拖拽期每帧重排上限 | 05 | 1 | — | 待实测（⛔ 不设就是每帧全量重排） |

⛔ 上表"待实测"项**不得凭行业惯例填** ——
填错不会报错，只会表现为"偶发连锁栈爆""偶发抽到刚洗进去的同一张"，
⛔ 而这类偶发在测试环境几乎不出现。

⛔ `HAND_CAP` 与 `HAND_POOL` 是**同一个约束的两处表达**：
只改一处会出现"手牌满了但视图池不够，抽到的牌没有卡面"，
而池子取不到时通常返回 `null`，表现为"偶发打出空牌"。
