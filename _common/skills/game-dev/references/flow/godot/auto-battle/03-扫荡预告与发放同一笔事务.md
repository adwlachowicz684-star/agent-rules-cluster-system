# 03 扫荡：预告与发放同一笔事务（自动战斗域）

> **本步交付**：简化结算函数 + `preview_id` + 同一事务发放 + 业务语义层幂等
> **对应**：流程 `howto/godot/auto-battle.md` · 审核 `audit/godot/auto-battle.md`

## 0. 交付物定义

1. 扫荡是结算函数，不是加速播放的战斗
2. 结果算法选型有明确口径（简化规则 vs 战力推算）
3. 预告是服务端审批过的结果，发放复用同一个 `preview_id`
4. 扣次数与发奖在同一事务内
5. 幂等在业务语义层，重复请求返回首次结果

## 1. 前置检查清单

- [ ] 扫荡不跑位置 / 碰撞 / 动画
- [ ] 只保留会影响产出的变量
- [ ] 预览与发放是同一笔事务
- [ ] 奖励有 source 幂等键
- [ ] 次数 / 体力 / 倍率全部服务端算

## 2. 工序

### Step 1　扫荡是结算函数，⛔ 不是把战斗加速 1000 倍　`[auto-battle/03#S1]`

【读】`howto/godot/auto-battle.md#3. 扫荡`

【做】
扫荡只保留**会影响产出的变量**：阵容 / 战力、敌人阵容、关卡配置版本、随机种子、次数、倍率、掉落规则。
⛔ 真的跑完整战斗 —— 大量单位持续寻路 / 碰撞 / 技能模拟，逐场等动画物理渲染，
每场都产生 RNG、事件和录像。⛔ 更重要的是**实时战斗的结果无法被客户端低成本稳定预测**，
表现为"同样阵容有时过有时不过"，而每次单看都是"正常战斗结果"。

【产出】`sweep_resolve()` 结算函数签名 + 入参清单

【判据】同样输入跑 100 次得到相同结果；且不产生任何寻路 / 动画开销。

【审】`audit/godot/auto-battle.md#3`

### Step 2　结果算法选型：简化战斗规则 vs 战力推算　`[auto-battle/03#S2]`

【读】`howto/godot/auto-battle.md#两种结果算法`

【做】
两种算法各自的风险相反，必须**先选再写**：
简化战斗公式——与玩家体验过的战斗同一套规则子集，⛔ 但不能漏掉破防、部位破坏、处决、抗性、仇恨、目标切换、连击；
战力推算——稳定快速，⛔ 但战力不是真实技能表达，养成虚高与克制关系会让"数值说该赢"而玩家复现不了。

✅ 推荐口径：**已通关且已解锁扫荡的关卡用简化战斗规则**；
未通关、特殊机制关、活动关必须手动通过后再开放；
战力曲线只用于失败惩罚、奖励降级或排队匹配，⛔ 不替代战斗结果。

【产出】算法选型结论 + 例外关卡清单

【判据】不存在"明明能过却扫失败"的关卡类型。

【审】`audit/godot/auto-battle.md#12`

### Step 3　预告是服务端审批过的结果，发放必须复用它　`[auto-battle/03#S3]`

【读】`howto/godot/auto-battle.md#预告不是`

【做】
预告 = 服务端把**审批过的结果摘要**先发给客户端；确认时**复用同一个 `preview_id`**。
`preview_id` 要绑定舞台、次数、配置版本、倍率、种子与玩家快照 —— 任何关键变量变化都使旧预览作废。
⛔ 预览与发放各算一遍 —— 玩家"看到一项奖励、到账另一项"，
⛔ 而日志里两次都是成功调用，是最难排查的一类客诉。

ⓘ 有效期（见 00 参数登记）是产品取舍：太短玩家点不到确认，太长等于允许"看完再改难度再领"。

【产出】`SweepPreview` / `SweepCommit` 接口 + `preview_id` 绑定字段表

【判据】改任何绑定字段后旧预览被拒；发放结果与预告逐项一致。

【审】`audit/godot/auto-battle.md#7`

### Step 4　扣次数与发奖在同一事务内　`[auto-battle/03#S4]`

【读】`howto/godot/auto-battle.md#3. 扫荡`

【做】
同一事务内完成：扣体力 / 次数 → 按 source 键发奖 → 标记 committed。
⛔ 分成两步 —— 中断时留下"扣了次数没发奖"或"发了奖没扣次数"，
⛔ 而两者在日志里都是部分成功的正常记录。

⚠ 次数 / 体力 / 票券、VIP、活动、首通、广告、公会等**所有倍率与上限全部服务端权威**；
客户端可提前拉规则做费用面板，但⛔ 面板不是结算结果。

【产出】扫荡事务边界定义（含失败回滚口径）

【判据】任意时刻中断，次数与奖励始终一致，无中间态。

【审】`audit/godot/auto-battle.md#8`

### Step 5　幂等在业务语义层，⛔ 不是 HTTP 去重　`[auto-battle/03#S5]`

【读】`howto/godot/auto-battle.md#3. 扫荡`

【做】
奖励每一项用 `source_type:source_id:player:item:seq` 幂等键；
重复投递**只返回首次结果**，⛔ 不能重新抽掉落。
⛔ 靠 HTTP 层去重 —— 重试、超时、客户端连点都会绕过去，
表现为"掉了两次同样的东西"，而网关日志显示只有一次请求。

【产出】幂等键定义 + 首次结果缓存

【判据】同一 `request_id` 连点 10 次，奖励与首次完全一致。

【审】`audit/godot/auto-battle.md#9`、`audit/godot/auto-battle.md#10`

## 3. 参考实现

```gdscript
# ⓘ 承接本步产出：preview_id 绑定 + 同一事务 + 幂等键
# SWEEP_PREVIEW_TTL_SEC 见 00 参数登记，待实测
const SWEEP_PREVIEW_TTL_SEC := 300

func commit(preview_id: String, ticket_id: String) -> Dictionary:
    var key := "sweep:%s:%s" % [preview_id, ticket_id]
    if _first_result.has(key):
        return _first_result[key]      # ⛔ 不能重新抽掉落
    var r := _txn_consume_and_grant(preview_id)   # 同一事务：扣次数 → 发奖 → 标记
    _first_result[key] = r
    return r
```

## 5. 常见返工

| 症状 | 原因 | 回到 |
|---|---|---|
| 同样阵容有时过有时不过 | 真跑了完整战斗 | S1 |
| 明明能过却扫失败 | 简化模型漏了机制 | S2 |
| 看到一项、到账另一项 | 预览发放各算一遍 | S3 |
| 扣了次数没发奖 | 两步非事务 | S4 |
| 掉了两次同样东西 | 幂等在 HTTP 层 | S5 |
