# 自动战斗 / 扫荡 / 离线挂机 / 回放观战 —— 域流程总览

> ⚠ **第 0 步：先定"这是不是一个模拟器"。**
> 本域有 7 个功能点，⛔ **不是全做** —— 按本次需求挑。

## 0. 先定做什么

| 本次要做的 | 走哪些功能点 |
|---|---|
| 自动战斗 / 一键托管 | 01 → 02 → 06 → 07 |
| 扫荡 / 快速战斗 | 01 → 03 → 06 → 07 |
| 离线挂机收益 | 01 → 04 → 06 → 07 |
| 回放 / 观战 | 01 → 05 → 06 → 07 |
| 全套（放置 / 卡牌常见） | 01 → 02 → 03 → 04 → 05 → 06 → 07 |

⛔ **01 不能跳过** ——
自动战斗、扫荡、离线、回放**是同一个战斗模拟器在四种输入源下的复用**，
不是四个播放功能。⛔ 先做其中一个（通常是扫荡，因为它最像"一个接口"），
会写出四套互斥逻辑，表现为"手动能过、扫荡说你打不过"，
⛔ 而每一套单看都合理、都能跑通。

⛔ **03 的核心不是"把战斗加速 1000 倍"** ——
扫荡是**不带位置 / 碰撞 / 动画的结算函数**。先做加速再改成结算函数，
等于把已经写好的战斗循环整块推翻。

⛔ **04 不能等客户端计时器写完再补**：
按真实时间跑循环在单人测试里完全正常，
⛔ 只在服务端有 N 个离线玩家时才爆 CPU，那时返工的是整个结算结构。

⛔ **05 的确定性要跨构建验，不能只在编辑器跑一遍**：
Debug / Release、x86 / ARM、不同帧率下浮点会漂移，
⛔ 编辑器里跑通是这类 bug 最典型的假通过。

ⓘ 若本次只是"加一个可扫荡关卡、配一张掉落表"，那是资源配置，不套本域。
ⓘ 若只是排查"托管打不过"，先看 `combat` 域确认战斗数值，再回本域 02。

ⓘ 分工：
- `howto/godot/auto-battle.md` 讲**四种模式各自的技术做法**（模拟器合同、AI 策略、扫荡事务、离线推导、固定 tick）
- 本域讲**这些模式按什么顺序做、怎么保证换输入源换版本后结果仍然对**

⛔ 若本域某步需要"离线封顶时长""扫荡概率""观战延迟"这类细节，
指向项目实测，⛔ 不在这里编数字。

## 1. 功能点拆解（按依赖，不可颠倒）

| # | 功能点 | 依赖 | 交付物 |
|---|---|---|---|
| 01 | 模拟器合同与四种输入源 | — | 模拟器接口 + `Intent` 语义 + 固定 tick 与 RNG bank |
| 02 | 自动战斗：AI 策略适配器与可见性 | 01 | `Observation` 边界 + 决策三件套 + 运行时可配 |
| 03 | 扫荡：预告与发放同一笔事务 | 01 | 简化结算函数 + `preview_id` + 同一事务发放 |
| 04 | 离线挂机：一次性分段推导 | 01 | 分段推导 + 服务端锚点 + 结构化事件日志 |
| 05 | 回放与观战：确定性接口 | 01 | 固定 tick 重放 + 版本元数据 + 观战可见性过滤 |
| 06 | 服务端权威与幂等边界 | 01–05 | 权威清单 + 同一套幂等键 + 带目标 tick 的命令 |
| 07 | 自动战斗验收 | 全部 | 跨构建黄金集 + 敌意环境实测 |

⚠ **01 要在任何一个模式开工之前**：
那时改"谁喂输入"只需要改一处；
⛔ 等四个模式各写各的，再统一就是四套数据各改一次。

⚠ **04 的分段推导要在接体力 / 离线 UI 之前**：
分段结构决定了锚点、封顶与事件日志三个字段的形状，
⛔ 先写 UI 再补，等于把展示层与结算层一起返工。

⚠ **06 的权威边界要随功能点同步写，不能最后统一补**：
补的时候会顺手把"客户端预算面板"也划进权威，
表现为"预览永远算不对"，但没人敢改回去。

## 2. 与其他域的接缝

> ⚠ **组合的真正难点不是单个模式，是接缝。**
> 下面每条都必须能指认到具体符号或字段，⛔ 不能是"做完了"。

| 接缝 | 契约 |
|---|---|
| `combat` 域 战斗结算 | 一次战斗怎么打（命中、帧数据、伤害、Buff）见 `combat`，⛔ 本域只定**输入源怎么换** |
| `netsync` 域 网络同步 | 传输与 authority 见 `netsync`；ⓘ 观战与重连、确定性回放的 howto 层篇目 `replay.md` / `spectate-reconnect.md` 挂在它的接缝下 |
| `ops` 域 运营服务端 | 补偿发放与幂等见 `ops`，⛔ 本域的扫荡 / 离线发奖必须复用**同一套 source 幂等键** |
| `security` 域 安全 | 改包伪造与服务端权威判定见 `security`，⛔ 本域只定"客户端提交结果必须被拒" |
| `economy` 域 经济 | 掉落、货币与账本见 `economy`，⛔ 本域不另定货币口径 |
| `vip` 域 VIP / 订阅 | 扫荡次数加成走 `vip` 的 `get_benefit()`，⛔ 本域不自己判等级 |
| `save` 域 存档 | 离线锚点与未领取结算单的持久化见 `save`，⛔ 本域只定"锚点必须落库" |
| `testing` 域 测试与 CI | 确定性模糊测试与基准见 `testing`，⛔ 本域只定黄金集要跨构建比对 |
| `time-progression` | ⓘ howto 层，暂无 flow 域 —— 离线结算与封顶原则见该篇 |
| `genres-idle-sim` | ⓘ howto 层，暂无 flow 域 —— 放置品类挂机收益见该篇 |

## 3. 参数登记

| 参数 | 所在功能点 | 初始值 | 实测值 | 状态 |
|---|---|---|---|---|
| `SIM_STEP_MS` 模拟步长 | 01 | — | — | 待实测（与 `physics_ticks_per_second` 绑定，改它要同步改步数上限） |
| `AUTO_AI_DECIDE_EVERY_N_TICKS` 托管决策间隔 | 02 | — | — | 待实测（与技能数、单位数、帧预算相关） |
| `SWEEP_PREVIEW_TTL_SEC` 预告有效期 | 03 | — | — | 待实测（太短玩家点不到确认，太长允许"看完再改难度"） |
| `OFFLINE_CAP_HOURS` 离线封顶时长 | 04 | — | — | 待实测（⛔ 封顶太短等于惩罚下线） |
| `OFFLINE_BATTLE_INTERVAL_MS` 离线场次间隔 | 04 | — | — | 待实测（整数毫秒，⛔ 不用浮点累加） |
| `REPLAY_CHECKPOINT_TICKS` 回放检查点间隔 | 05 | — | — | 待实测（与跳转体验和文件大小相关） |
| `SPECTATE_DELAY_SEC` 观战延迟 | 05 | — | — | 待实测（按"观众能影响对局的时间"定，⛔ 30 秒只是经验值） |

⛔ 上表"待实测"项**不得凭行业惯例填** ——
填错不会报错，只会表现为"偶发结果不一致""偶发重复发奖""偶发卡结算"，
⛔ 而这类偶发在测试环境几乎不出现。
