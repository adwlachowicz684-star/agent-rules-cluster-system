# 04 离线挂机：一次性分段推导（自动战斗域）

> **本步交付**：分段推导 + 服务端锚点 + 结构化事件日志 + 派生种子先 hash
> **对应**：流程 `howto/godot/auto-battle.md` · 审核 `audit/godot/auto-battle.md`

## 0. 交付物定义

1. 离线按**一次性分段推导**，不按真实时间跑循环
2. 锚点与时长以服务端 `now` 为准
3. 场次数用整数毫秒 / 定点，满一场才结算
4. 有结构化事件日志，能审计
5. 派生种子先 hash 再喂 RNG

## 1. 前置检查清单

- [ ] 服务端不会为每个离线玩家跑寻路 / 碰撞 / 渲染
- [ ] 客户端不算"离线了多久"
- [ ] 场次数不是浮点累加
- [ ] 日志含 `config_version`、`seed`、`prev/next_anchor`
- [ ] 派生种子经过 hash

## 2. 工序

### Step 1　一次性分段推导，⛔ 不按真实时间跑循环　`[auto-battle/04#S1]`

【读】`howto/godot/auto-battle.md#4. 离线挂机`

【做】
把速率变化写成**事件日志**，离线时长切成若干段，每段用该段的速率积分，一次性推导到底。
⛔ 按真实时间跑循环 —— N 个离线玩家线性放大 CPU，
且重启、扩容、补算、跨日活动会**重复或遗漏**，
⛔ 表现为"玩家说收益少了/多了"，而每笔结算单看都正确。

ⓘ 余数处理要显式：不满一场的**留在当前未结算周期**，
⛔ 不要因为"不足一场"就丢掉，也不要凑整。

【产出】分段推导函数 + 事件日志结构（时间、场景、战力、速率）

【判据】同一段离线区间算两次结果一致；且 CPU 与离线玩家数无关。

【审】`audit/godot/auto-battle.md#13`

### Step 2　锚点与时长以服务端 `now` 为准　`[auto-battle/04#S2]`

【读】`howto/godot/auto-battle.md#4. 离线挂机`

【做】
`last_settled_at` 与 `now` 全部取服务端；时长先 `clamp` 到封顶（见 00 参数登记）。
⛔ 客户端用本地时间算"离线了多久" ——
设备时钟可改、后台进程会被杀、热更会改变规则，
⛔ 表现为"改系统时间就能刷收益"，而服务端日志里每一次都是"正常结算"。

ⓘ 客户端可展示"预计离线收益"，但**到账数量以服务端结算单为准**。

【产出】锚点字段（`prev_anchor` / `next_anchor`）+ 封顶规则

【判据】改客户端系统时间 1 年，收益与正常情况完全相同。

【审】`audit/godot/auto-battle.md#14`

### Step 3　场次数用整数毫秒 / 定点，⛔ 不浮点累加　`[auto-battle/04#S3]`

【读】`howto/godot/auto-battle.md#4. 离线挂机`

【做】
场次数按**连续产出率积分**；必须离散化时用整数毫秒或定点，
边界统一采用"**满一场才结算，余数留给下次**"。
⛔ 在每次 tick 用 `if acc >= interval: spawn_battle()` —— 累积浮点误差，
表现为"长时间离线后场次数差一两场"，
⛔ 而短时长测试完全对得上，只有挂机一整天的玩家会投诉。

【产出】积分 / 离散化口径 + 余数处理约定

【判据】离线 24 小时与 24 次 1 小时的场次数之和一致。

【审】`audit/godot/auto-battle.md#15`

### Step 4　结构化事件日志，⛔ 不只存总金币　`[auto-battle/04#S4]`

【读】`howto/godot/auto-battle.md#4. 离线挂机`

【做】
每笔离线结算记录须含字段：`event_id` · `player` · `scene` · `start` · `end` · `config_version` · `seed` · `formula_version` · `snapshots[]` · `rewards{}` · `reason` · `prev_anchor` · `next_anchor` · `request_id`。
⛔ 只存总金币 —— 客诉无法复现，运营无法回答"为什么是这些"，
⛔ 而补日志要等下一次离线，等于承认这笔永远查不清。

⚠ `config_version` 这条尤其关键：重大配置热更必须绑定版本，
⛔ 否则回补离线时会用**新规则改写旧时间窗**（见 07 验收 S6）。

【产出】离线结算单结构 + 审计查询入口

【判据】任一笔离线收益都能凭日志复算出相同数字。

【审】`audit/godot/auto-battle.md#16`

### Step 5　派生种子先 hash 再喂 RNG　`[auto-battle/04#S5]`

【读】`howto/godot/auto-battle.md#扫荡派生种子必须先 hash`

【做】
扫荡与离线的派生种子（`master_seed + i`、`master_seed + 场次序号`）**先过一次 hash** 再设给 RNG。
⛔ 直接把相近整数当种子 —— 官方明确 RNG **没有 avalanche effect**，
相近种子会产生**相近的随机序列**，
表现为"连续扫荡的出货有肉眼可见规律""第 3、7 次总出同一个东西"，
⛔ 而单次抽样的概率统计完全正常，用统计工具查不出来。

ⓘ 同源两条：官方说底层算法是**实现细节**，⛔ 不能依赖跨版本复现；
`state` 只应设回**从 `state` 取出来的值**，⛔ 不要设任意值。

【产出】`derive_seed()` 实现（含 hash 步骤）+ 用途分配

【判据】连续 10 次扫荡的结果序列无明显规律。

【审】`audit/godot/auto-battle.md#36`

## 3. 参考实现

```gdscript
# ⓘ 承接本步产出：分段推导 + 整数毫秒 + hash 派生种子
# OFFLINE_CAP_HOURS / OFFLINE_BATTLE_INTERVAL_MS 见 00 参数登记，待实测
const OFFLINE_BATTLE_INTERVAL_MS := 600_000

func settle_offline(now_ms: int, last_ms: int, events: Array) -> Dictionary:
    var cut := mini(now_ms - last_ms, OFFLINE_CAP_HOURS * 3_600_000)
    var cursor := 0
    var rewards := {}
    while cursor < cut:
        var dur := mini(_seg_end(events, cursor), cut) - cursor
        _accumulate(rewards, _rate_at(last_ms + cursor), dur)
        cursor += dur
    return {"rewards": rewards, "prev_anchor": last_ms, "next_anchor": last_ms + cursor}

# ⛔ 相近种子会产生相近序列：先 hash 再喂 RNG
func derive_seed(master: int, seq: int) -> int:
    return hash("%d:%d" % [master, seq])
```
