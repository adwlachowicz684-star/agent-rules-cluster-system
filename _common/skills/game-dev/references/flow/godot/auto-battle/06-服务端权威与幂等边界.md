# 06 服务端权威与幂等边界（自动战斗域）

> **本步交付**：权威清单 + 同一套幂等键 + 输入摘要留存 + 带目标 tick 的命令
> **对应**：流程 `howto/godot/auto-battle.md` · 审核 `audit/godot/auto-battle.md`

## 0. 交付物定义

1. 客户端"提交战斗结果"必须被拒绝
2. 次数 / 体力 / 倍率全部服务端算
3. 扫荡与离线的发奖复用 `ops` 域同一套 source 幂等键
4. 保存输入摘要 / seed / 版本 / 关键事件，供异常时确定性校验
5. 网络包转成带目标 tick 的命令

## 1. 前置检查清单

- [ ] 资产、进度、公平、跨端一致性四类量都不由客户端最终决定
- [ ] 客户端改内存后"提交结果"被拒
- [ ] 幂等键与补偿发放同源
- [ ] 异常时能做确定性校验
- [ ] 网络命令带目标 tick

## 2. 工序

### Step 1　客户端提交结果必须被拒绝　`[auto-battle/06#S1]`

【读】`howto/godot/auto-battle.md#8. 服务端权威清单`

【做】
凡影响**资产、进度、公平或跨端一致性**的量，⛔ 都不能由客户端最终决定：
胜负、评价、掉落、金币、经验、物品、次数、体力、所有倍率与上限、
离线锚点与时长、竞技录像的种子与校验和、AI 是否有权用某技能。
客户端可缓存配置并算预览，**但结果必须服务端重新评估**。

⛔ 接受客户端"提交结果" —— 改内存即可刷，
表现为"排行榜出现不可能的战绩"，而服务端日志里那是一次正常提交。

【产出】权威边界清单（按四类量分组）+ 拒绝码

【判据】伪造的提交被拒，且客户端回退无中间态。

【审】`audit/godot/auto-battle.md#30`

### Step 2　次数 / 体力 / 倍率全部服务端算　`[auto-battle/06#S2]`

【读】`howto/godot/auto-battle.md#8. 服务端权威清单`

【做】
扫荡次数、剩余次数、体力 / 票券 / 能量消耗与恢复、
VIP、活动、首通、新手、广告、公会等**所有倍率与上限**由服务端算。
⛔ 客户端算完报上来 —— 改内存即得，
表现为"有人的扫荡次数永远用不完"，而每次请求格式完全合法。

ⓘ 与 `vip` 域的接缝：次数加成走 `vip` 的 `get_benefit()`，
⛔ 本域不自己判等级 —— 否则两套等级口径会给出不同次数。

【产出】次数与倍率的取值口径（含 `vip` 域调用点）

【判据】改客户端内存中的倍率不影响实际发放。

【审】`audit/godot/auto-battle.md#11`

### Step 3　发奖复用 `ops` 域同一套 source 幂等键　`[auto-battle/06#S3]`

【读】`howto/godot/auto-battle.md#3. 扫荡`

【做】
扫荡与离线的奖励发放，与 `ops` 域的**补偿发放共用同一套 source 幂等键**
（`source_type:source_id:player:item:seq`）。
⛔ 自己造一套 —— 两套幂等互相绕过，
表现为"补偿 + 扫荡各发了一次"，而两边各自的去重日志都显示"只发了一次"。

【产出】幂等键归属说明（指向 `ops` 域）+ 本域调用点

【判据】补偿与扫荡指向同一 source 时只发一次。

【审】`audit/godot/auto-battle.md#40`

### Step 4　保存输入摘要 / seed / 版本 / 关键事件　`[auto-battle/06#S4]`

【读】`howto/godot/auto-battle.md#5. 回放与观战`

【做】
服务端**不必完整重放**每场自动战斗，但应保存输入摘要、seed、版本和关键事件，
在异常或举报时做确定性校验。
⛔ 什么都不存 —— 举报无法判定，只能人工看录像，
⛔ 而录像只是表现层，证明不了逻辑层是否异常。

【产出】自动战斗留存记录结构 + 确定性校验脚本入口

【判据】任一举报都能凭留存记录复算出当时的结果。

【审】`audit/godot/auto-battle.md#31`

### Step 5　网络包转成带目标 tick 的命令　`[auto-battle/06#S5]`

【读】`howto/godot/auto-battle.md#8. 服务端权威清单`

【做】
网络包先转成**带目标 tick 的命令**再进模拟器。
⛔ 直接改模拟状态 —— 不同机器到达时的 tick 不同，
表现为"同样的操作在两台机器上结果不同"，
⛔ 而两台机器的网络包内容完全一致，排查被引向序列化。

【产出】命令结构（含 `target_tick`）+ 到达时的丢弃 / 排队口径

【判据】人为打乱包序后，按 `target_tick` 重排结果不变。

【审】`audit/godot/auto-battle.md#22`

## 3. 参考实现

```gdscript
# ⓘ 承接本步产出：带目标 tick 的命令 + 同源幂等键
func on_cmd(cmd: Dictionary) -> void:
    # ⛔ 不接受客户端提交的结果，只接受带 tick 的命令
    if cmd.has("result"):
        reject(cmd, "CLIENT_RESULT_NOT_ALLOWED"); return
    if cmd["target_tick"] <= sim_tick:
        reject(cmd, "LATE_CMD"); return
    pending_cmds[cmd["target_tick"]].append(cmd)
```

## 4. 验收清单

- [ ] 伪造提交被拒且无中间态
- [ ] 改内存倍率不影响发放
- [ ] 补偿与扫荡同源只发一次
- [ ] 举报可凭留存记录复算
- [ ] 打乱包序后结果不变

## 5. 常见返工

| 症状 | 原因 | 回到 |
|---|---|---|
| 排行榜出现不可能战绩 | 接受客户端结果 | S1 |
| 有人次数永远用不完 | 客户端算次数 | S2 |
| 补偿 + 扫荡各发一次 | 两套幂等键 | S3 |
| 举报无法判定 | 没留存输入摘要 | S4 |
| 两台机器结果不同 | 直接改模拟状态 | S5 |
