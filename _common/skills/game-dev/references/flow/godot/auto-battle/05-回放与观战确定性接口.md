# 05 回放与观战：确定性接口（自动战斗域）

> **本步交付**：固定 tick 重放 + 版本元数据 + 观战可见性过滤 + 倍速不改步长
> **对应**：流程 `howto/godot/auto-battle.md` · 审核 `audit/godot/auto-battle.md`

## 0. 交付物定义

1. 回放走固定 tick，不用 `_process(delta)`
2. RNG bank 可快照，不依赖跨版本一致
3. 行动顺序用 ID 全序，不依赖 `Dictionary`
4. 明确只支持同版本，并保存四类版本元数据
5. 倍速只放大真实时间，不改 `STEP`、不用 `time_scale`
6. 观战有可见性过滤与延迟

## 1. 前置检查清单

- [ ] 回放与实时共用同一套 `step()`
- [ ] 随机来自 seeded bank 且可保存 / 恢复 `state`
- [ ] 行动顺序不依赖字典或节点树顺序
- [ ] 录像头含 `app_version / content_version / rules_hash / config_digest`
- [ ] `physics_jitter_fix` 为 0
- [ ] 观战输出的是统一的"观战可见事件"

## 2. 工序

### Step 1　回放走固定 tick，且 jitter 设为 0　`[auto-battle/05#S1]`

【读】`howto/godot/auto-battle.md#7. Godot 实现`

【做】
回放推进只认 `sim_tick`，⛔ 不用 `_process(delta)`；
同时把 `Engine.physics_jitter_fix` 设为 **0**。
⛔ 用 `delta` 推进 —— 帧率一变，输入映射与碰撞时序就漂移，
表现为"回放和当时打得不一样""高刷屏上回放更快"，
⛔ 而每一段回放单看都是连续的、没有明显跳帧。

ⓘ jitter 那条是同源的：默认 `0.5` 会让 tick **偏离**真实时钟，
官方明确 0 或更小才完全同步，且**推荐网络游戏用 0**；
⛔ 沿用默认会让同一段输入在不同帧率机器上推进到不同 tick。

【产出】回放推进器（按 tick）+ 项目设置项（jitter = 0）

【判据】同一录像在 30 / 60 / 144 FPS 下重演结果一致。

【审】`audit/godot/auto-battle.md#17`、`audit/godot/auto-battle.md#35`

### Step 2　RNG bank 可快照，⛔ 不依赖跨版本一致　`[auto-battle/05#S2]`

【读】`howto/godot/auto-battle.md#7. Godot 实现`

【做】
保存 / 恢复 `state` 来实现检查点与跳转。
⛔ 假设 `RandomNumberGenerator` 跨版本给出相同序列 ——
官方明确底层算法是**实现细节**，⛔ 不能依赖，
表现为"引擎升级后所有老录像对不上"，而录像文件本身完好无损。

⚠ `state` 只应设回**从 `state` 取出来的值**，⛔ 不要设任意值。

【产出】RngBank 快照 / 恢复接口 + 检查点结构

【判据】从任一检查点恢复后，后续序列与原回放完全一致。

【审】`audit/godot/auto-battle.md#19`

### Step 3　行动顺序用 ID 全序，⛔ 不依赖 `Dictionary`　`[auto-battle/05#S3]`

【读】`howto/godot/auto-battle.md#9. 待核对项`

【做】
单位行动顺序按**稳定 ID 全序**排定。
⛔ 依赖 `Dictionary` 迭代顺序或节点树顺序 —— 官方警告迭代时删除**不可预测**，
表现为"本地测试全过、正式环境偶发顺序不同"，
⛔ 而这类偶发在单测里几乎不可复现，是最典型的"只在发布后漂移"。

【产出】行动顺序排序规则（ID 全序）

【判据】打乱插入顺序后，行动顺序不变。

【审】`audit/godot/auto-battle.md#20`

### Step 4　只支持同版本，并保存四类版本元数据　`[auto-battle/05#S4]`

【读】`howto/godot/auto-battle.md#5. 回放与观战`

【做】
录像头保存 `app_version / content_version / rules_hash / config_digest`，
播放前校验；不匹配就**拒绝播放并说明原因**。
⛔ 允许跨版本播放 —— 规则变了但录像还在按旧规则演，
表现为"回放里出现了当前版本不存在的技能效果"，
⛔ 而玩家会当成"作弊视频"投诉，排查方向完全跑偏。

ⓘ 商业产品也只支持同版本，**这不是实现偷懒**，是确定性的前提。

【产出】录像头结构 + 版本校验与拒绝提示

【判据】版本不匹配的录像被拒播，且提示中写明哪个字段不符。

【审】`audit/godot/auto-battle.md#23`

### Step 5　倍速只放大真实时间，⛔ 不改 `STEP`、不用 `time_scale`　`[auto-battle/05#S5]`

【读】`howto/godot/auto-battle.md#6. 加速与暂停`

【做】
倍速改的是**每帧跑几个 tick**，⛔ 不是改 `STEP_MS`；
⛔ 也不要用 `Engine.time_scale` —— 官方明确它缩放的是 **delta** 并影响 `_physics_process()`，
tick 数不变，于是"倍速下的轨迹"与"跑满 480 个 tick"完全不同，
表现为"倍速下结果与 1 倍速不一致、回放对不上"。

⛔ 官方还有一条 Note：建议 `time_scale` **保持大于 0**，
所以用它做暂停（含顿帧 hitstop）**不被推荐**，行为未定义。

【产出】倍速实现（放大每帧迭代数）+ 暂停实现（停迭代而非改 time_scale）

【判据】8 倍速跑完的结果与 1 倍速逐 tick 一致。

【审】`audit/godot/auto-battle.md#32`、`audit/godot/auto-battle.md#33`

### Step 6　观战有可见性过滤与延迟　`[auto-battle/05#S6]`

【读】`howto/godot/auto-battle.md#5. 回放与观战`

【做】
观战输出**统一的"观战可见事件"**，并加延迟（见 00 参数登记）。
⛔ 把内部状态直接推给观众 —— 镜头、高亮、命中数字会**隐式泄露隐藏状态**，
表现为"观众能看到选手看不到的东西"，而每个字段单看都只是"展示更丰富"。
⛔ 零延迟观战尤其危险：可能泄露对手行动形成**上帝视角**。

ⓘ 延迟按"观众能影响对局的时间"定，⛔ 30 秒只是经验值，不是标准。

【产出】观战可见事件白名单 + 延迟配置

【判据】观众端拿不到任何选手不可见的字段；延迟可配。

【审】`audit/godot/auto-battle.md#26`、`audit/godot/auto-battle.md#28`

## 3. 参考实现

```gdscript
# ⓘ 承接本步产出：按 tick 重放 + 倍速放大迭代数（不放大 delta）
# REPLAY_CHECKPOINT_TICKS / SPECTATE_DELAY_SEC 见 00 参数登记，待实测
const REPLAY_CHECKPOINT_TICKS := 600

func advance(ticks: int, speed: int) -> void:
    for _i in range(ticks * speed):   # ⛔ 不是改 SIM_STEP_MS，也不是 time_scale
        sim_tick += 1
        simulation.step(replay.pull(sim_tick), rng_bank)
        if sim_tick % REPLAY_CHECKPOINT_TICKS == 0:
            checkpoint.save(sim_tick, rng_bank.state)
```

## 5. 常见返工

| 症状 | 原因 | 回到 |
|---|---|---|
| 高刷屏上回放更快 | 用 delta 推进 | S1 |
| 升级后老录像对不上 | 依赖 RNG 跨版本 | S2 |
| 发布后偶发顺序不同 | 依赖 Dictionary | S3 |
| 回放里出现已删除技能 | 允许跨版本播放 | S4 |
| 倍速结果对不上 | 改 STEP 或 time_scale | S5 |
| 观众有上帝视角 | 无可见性过滤 | S6 |
