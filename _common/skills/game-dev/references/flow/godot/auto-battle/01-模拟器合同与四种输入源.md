# 01 模拟器合同与四种输入源（自动战斗域）

> **本步交付**：模拟器接口 + `Intent` 语义 + 固定 tick 与 RNG bank + 结果元数据
> **对应**：流程 `howto/godot/auto-battle.md` · 审核 `audit/godot/auto-battle.md`

## 0. 交付物定义

1. 四个模式共用**同一个模拟器**，只有输入源不同
2. `Intent` 是领域动作语义，不含按键 / 坐标 / UI 索引 / 节点路径
3. 时间只从 `sim_tick` 与固定 `STEP` 推出
4. 随机来自独立 seeded RNG bank，可快照
5. 每次模拟结果自带版本与 seed 元数据

## 1. 前置检查清单

- [ ] 四个模式的 `step()` 是同一个函数
- [ ] `Intent` 里没有 `Input.is_action_pressed` 之类的设备语义
- [ ] 模拟器里读不到 `delta`、系统时间、渲染帧
- [ ] RNG 按用途分开（战斗 / 掉落 / 生成 / 表现）
- [ ] 结果记录含 `config_version` 与 seed

## 2. 工序

### Step 1　四个模式共用一个模拟器，⛔ 不是四套实现　`[auto-battle/01#S1]`

【读】`howto/godot/auto-battle.md#0. 四种模式`

【做】
把四种模式统一成**同一个模拟器**的四种输入源：
`LIVE_PLAYER`（手动）/ `AUTO_AI`（托管）/ `REPLAY`（回放）/ `NULL`（扫荡）。
差异只体现在三处：**输入源、时间尺度、权威域**。
⛔ 给每个模式各写一套战斗逻辑 —— 四套规则会各自漂移，
表现为"手动能过、扫荡说你打不过""回放里这一刀没暴击"，
⛔ 而每一套单看都能跑通、都能自圆其说。

ⓘ 扫荡是这套逻辑的**极限形态**：它连位置、碰撞、动画都不跑，
但仍然复用同一套规则子集 —— 这是判断"是不是真共用"的最快检验。

【产出】模拟器接口定义（含四种 `IntentSource` 枚举）

【判据】改一次伤害公式，四个模式的结果同时变化。

【审】`audit/godot/auto-battle.md#1`

### Step 2　`Intent` 必须是领域动作语义　`[auto-battle/01#S2]`

【读】`howto/godot/auto-battle.md#1. 模拟器合同`

【做】
`Intent` 只携带**领域动作**（`MOVE / SELECT_TARGET / BASIC_ATTACK / SKILL / CANCEL / GUARD / ITEM / RETREAT`）
与目标、技能 ID、tick。
⛔ 塞进 `Input.is_action_pressed("jump")`、鼠标坐标、UI 按钮索引或节点路径 ——
回放会**绑死当时的分辨率、设备与节点树**，
表现为"换了分辨率回放就乱走""重构节点后老录像全部失效"，
⛔ 而这些老录像在出问题前一直播放正常，没人会怀疑它们。

ⓘ 玩家输入、AI 决策、回放录制、测试脚本**全部转成同一个结构** ——
这同时是自动化测试的接入点，测试脚本不用再模拟真实设备。

【产出】`Intent` 结构定义 + 四种输入源的转换函数

【判据】把节点树整体改名后，回放仍能正确重演。

【审】`audit/godot/auto-battle.md#2`

### Step 3　时间源只从 `sim_tick` 与固定 `STEP` 推出　`[auto-battle/01#S3]`

【读】`howto/godot/auto-battle.md#7. Godot 实现`

【做】
模拟器内部**只有 tick 计数**，⛔ 不读 `delta`、`Time.get_unix_time_from_system()`、渲染帧号。
用固定步长累加器推进：`_physics_process` 里累加 —— 超过 `STEP_MS` 就跑一次 `step()` 并 `sim_tick += 1`。

⛔ 两个官方约束必须同时记住：
① 提高 `physics_ticks_per_second` 时**必须同步提高** `max_physics_steps_per_frame`（默认 `8`），
否则"变慢阈值"从 7.5 FPS 升到 15 FPS —— **模拟会变慢而不是变快**，且不报错；
② 联网与回放场景要把 `physics_jitter_fix` 设为 **0**，
⛔ 默认 `0.5` 会让 tick 偏离真实时钟，各机器推进到不同 tick。

【产出】固定步长循环 + 项目设置清单（tick 率 / 步数上限 / jitter）

【判据】同一段输入在 30 / 60 / 144 FPS 下推进到相同 tick。

【审】`audit/godot/auto-battle.md#21`、`audit/godot/auto-battle.md#34`

### Step 4　随机走独立 seeded RNG bank，⛔ 不用全局 `randf()`　`[auto-battle/01#S4]`

【读】`howto/godot/auto-battle.md#7. Godot 实现`

【做】
按用途分开：`combat_rng`（命中暴击）/ `drop_rng`（掉落）/ `spawn_rng`（生成）/ `cosmetic_rng`（表现，可本地实时）。
每个 bank 可保存 / 恢复 `state`。
⛔ 用 `randf()` / 全局 `RandomNumberGenerator` / 时间戳 / 节点 ID 当随机源 ——
回放与扫荡都**无法复现**，表现为"重连一次换一个稀有度""客服复现不了客诉的那次扫荡"，
⛔ 而日志里每一次都是"正常随机"，看不出问题。

【产出】RngBank 定义（含 `state` 快照接口）+ 用途分配表

【判据】同 seed 两次运行的状态哈希完全一致。

【审】`audit/godot/auto-battle.md#18`

### Step 5　结果与版本、seed 元数据一起落库　`[auto-battle/01#S5]`

【读】`howto/godot/auto-battle.md#5. 回放与观战`

【做】
每次模拟（含扫荡与离线结算）都要留下**可复算的最小元数据**：
`config_version / rules_hash / seed / 输入摘要 / 关键事件`。
⛔ 只存结果 —— 运营无法回答"当时为什么发这些奖励"，
客诉只能靠人工翻日志，⛔ 而翻到的每一条都是成功记录。

ⓘ 服务端**不必完整重放**每场自动战斗，
但必须能在异常或举报时做**确定性校验** —— 这就是元数据的最小用途。

【产出】模拟结果记录结构（含版本与 seed 字段）+ 复算脚本入口

【判据】拿一条三个月前的扫荡记录，能用当时的参数算出一致结果。

【审】`audit/godot/auto-battle.md#31`

## 3. 参考实现

```gdscript
# ⓘ 承接本步产出：固定步长 + 四种输入源 + RngBank
# SIM_STEP_MS 见 00 参数登记，待实测；⛔ 改它必须同步改 max_physics_steps_per_frame
const SIM_STEP_MS := 1000.0 / 60.0

enum IntentSource { LIVE_PLAYER, AUTO_AI, REPLAY, SWEEP }
enum IntentType   { MOVE, SELECT_TARGET, BASIC_ATTACK, SKILL,
                    CANCEL, GUARD, ITEM, RETREAT }

var accumulator_ms := 0.0
var sim_tick := 0
var source: IntentSource = IntentSource.LIVE_PLAYER

func _physics_process(delta: float) -> void:
    accumulator_ms += delta * 1000.0
    while accumulator_ms >= SIM_STEP_MS:
        accumulator_ms -= SIM_STEP_MS
        sim_tick += 1
        simulation.step(input_port.pull(sim_tick), rng_bank)
```

## 5. 常见返工

| 症状 | 原因 | 回到 |
|---|---|---|
| 手动能过、扫荡打不过 | 四套逻辑 | S1 |
| 换分辨率回放乱走 | Intent 含设备语义 | S2 |
| 自动战斗有时候很慢 | 只提 tick 率没提步数上限 | S3 |
| 重连一次换一个稀有度 | 全局随机 | S4 |
| 客服复现不了客诉 | 没存版本与 seed | S5 |
