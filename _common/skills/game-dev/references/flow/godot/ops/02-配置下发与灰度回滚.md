# 02 配置下发与灰度回滚（运营域）

> **本步交付**：六件套管线 + 解析规范 + 秒级回滚
> **对应**：流程 `howto/godot/ops.md` · 审核 `audit/godot/ops.md`

## 0. 交付物定义

1. 配置管线六件套齐全（版本、灰度、校验、重试、默认值、回滚）
2. 已处理 JSON 数值全为 float 与大整数失真
3. 已处理 `ConfigFile` 空格静默截断
4. 分桶逻辑在服务端，客户端不重建
5. 已认清 PCK 热更不等于配置热更

## 1. 前置检查清单

- [ ] 配置有版本号与灰度规则
- [ ] ⛔ 已处理"解析失败"与"内容为空"的区分
- [ ] 64 位 ID 不走 JSON 数值
- [ ] 分桶结果由服务端返回
- [ ] 回滚路径不需要发版

## 2. 工序

### Step 1　配置下发的六件套：版本、灰度规则、校验签名、失败重试、本地默认值、可回滚　`[ops/02#S1]`

【读】`howto/godot/ops.md#2. 配置下发不是"下载个 JSON"`

【做】
下载只是第一步。
⛔ 把配置下发等同于"下载个 JSON"，是最常见也最晚被发现的错误——
**它在本地测试里永远正常**，只在灰度、断网、回滚时才暴露。
缺任一项的后果：无版本=无法判定新旧；无灰度=全量生效；无校验=中间人可改；
无重试=弱网即失败；无默认值=断网白屏；无回滚=改错只能发版。

【产出】配置管线清单（六项逐条打勾）

【判据】六项齐全，且能说出缺任一项的具体后果

【审】`audit/godot/ops.md#6`


### Step 2　⛔ JSON 解析出的数字全是 float，且失败与 null 无法区分　`[ops/02#S2]`

【读】`howto/godot/ops.md#8.7 传输与存储的能力边界`

【做】
官方说明：JSON 规范只有 number 类型，`stringify` 会把所有数值转成 float。
因此配置里的活动 ID、玩家 ID、订单号经 JSON 往返后是 **float**，
⛔ 超过 2^53 的 64 位 ID 会**静默失真**——不报错、不抛异常，只是值变了。
另：`JSON.parse_string()` 解析失败返回 `null`，
⛔ 与"内容本身就是 null"无法区分；生产要用 `JSON.new().parse()` 走 `error != OK` 分支。

【产出】配置解析规范（ID 字段按字符串传递，或解析后显式 `int()`）

【判据】配置解析处不存在对 64 位 ID 的直接 `==` 比较

【审】`audit/godot/ops.md#7`、`audit/godot/ops.md#8`


### Step 3　⛔ ConfigFile 的 section/key 含空格：空格之后会被静默忽略　`[ops/02#S3]`

【读】`howto/godot/ops.md#8.7 传输与存储的能力边界`

【做】
官方原话：section 与 property 名不能含空格，
**"Anything after a space will be ignored on save and on load"**。
⛔ 这不是报错，是**静默截断**——
`set_value("activity", "daily reset", 1)` 存进去变成 `daily`，读出来也是 `daily`，
全程无警告，表现为"配置读不到"。
另外 `ConfigFile` 是 INI 风格，**不支持原生嵌套**，`;` 注释保存时丢失。
→ 嵌套配置用 `JSON.stringify()` + `FileAccess`，或自定义 `Resource`。

【产出】配置存储选型说明（嵌套走 JSON / Resource）

【判据】不存在 section / key 名含空格的 `ConfigFile` 调用

【审】`audit/godot/ops.md#9`


### Step 4　分桶必须服务端算，客户端不能自己 randf　`[ops/02#S4]`

【读】`howto/godot/ops.md#1. A/B 测试与灰度：分组必须服务端算`

【做】
客户端 `randf()` 分桶：每次启动 / 闪退重启 / 切场景都可能重新分组，
**实验样本瞬间污染**；更糟的是攻击者能选对自己最有利的一组。
服务端用"不可猜测的玩家主键 + 实验版本盐 + 层标识"算，
返回 `experiment_id / group / assigned_at / config_version`。
⛔ 客户端只保存结果并附在埋点里，不能重建分组逻辑。

【产出】分组接口字段定义

【判据】客户端代码中不存在本地分桶逻辑

【审】`audit/godot/ops.md#10`


### Step 5　⛔ PCK 热更不等于配置热更：已加载资源不会被替换　`[ops/02#S5]`

【读】`howto/godot/ops.md#8.6 PCK 热更 ≠ 配置热更`

【做】
`load_resource_pack()` 返回 true **只说明包进了 VFS**，
不代表任何已加载资源被替换；默认 `CACHE_MODE_REUSE` 会返回旧对象。
→ 对新路径用 `REPLACE` 重新 load，或让新版本资源走新路径。
⚠ `Resource.take_over_path()` 只在编辑器上下文实现，生产没用。
⛔ PCK 不能换 GDScript 逻辑（脚本导出时已编译进主包）——
所以"改活动规则"永远走配置通道，不走 PCK。

【产出】热更策略（配置走网络，资源走新路径）

【判据】不存在"换 PCK 就能改活动逻辑"的预期

【审】`audit/godot/ops.md#11`


## 3. 参考实现

```gdscript
# ⓘ 承接本步产出：配置解析必须能区分"解析失败"与"内容为空"
const CONFIG_TIMEOUT_SEC := 10
const CONFIG_RETRY_MAX := 3
const ID_MAX_SAFE := 9007199254740992

func parse_config(text: String) -> Dictionary:
	var json := JSON.new()
	if json.parse(text) != OK:
		push_warning("配置解析失败：%s @ %d" % [json.get_error_message(), json.get_error_line()])
		return {}
	return json.data
```
