# 05 移动、空间 UI 与舒适度（XR 域）

> **本步交付**：移动方式已选型 + 传送四重判定 + 舒适度设置可配
> **对应**：流程 `howto/godot/xr.md` · 审核 `audit/godot/xr.md`

## 0. 交付物定义

1. 移动方式已选型，且**传送优先**于持续平移
2. 传送有**四重**有效性判定
3. 位移必带淡入淡出（vignette），⛔ 不是瞬移
4. 平滑移动配隧道视野，且舒适度设置**暴露给玩家**
5. 转向提供 snap turn 选项
6. 空间 UI 同时解决深度、命中、可读性三件事

## 1. 前置检查清单

- [ ] 移动方式选型已写进参数表
- [ ] 传送判定正好四重
- [ ] 每次位移都有 vignette
- [ ] 舒适度设置项可在游戏内改
- [ ] 有 snap turn 开关
- [ ] 空间 UI 的射线碰撞层已配

## 2. 工序

### Step 1　先选移动方式：持续平移优先传送，不是先做平滑移动　`[xr/05#S1]`

【读】`howto/godot/xr-deep.md#3. 移动与舒适度`

【做】
在做任何移动代码之前先选型：房间规模 / 传送 / 臂摆 / 平滑移动，
并默认把**传送**作为持续平移的实现。
⛔ 先做平滑移动再补传送 —— 平滑移动最易致晕，
而"先做出来看着能走"会让它成为事实标准，
⛔ 表现为"上线后玩家反馈晕"，那时传送已是新功能而不是默认项。

ⓘ 晕动症的成因是**前庭冲突**，不是"有些人容易晕"，
所以它是可设计规避的，⛔ 不是用户体质问题。

【产出】移动方式选型（传送优先）+ 理由

【判据】参数表里有选型结论；⛔ 不是"先做着看"。

【审】`audit/godot/xr-deep.md#10`

### Step 2　传送要四重判定，命中不等于合法落点　`[xr/05#S2]`

【读】`howto/godot/xr.md#4. 传送`

【做】
依次判：① 射线/抛物线是否命中；② 命中点法线是否朝上；
③ 落点头顶是否有足够空间；④ 是否在允许区域内。
⛔ 只判命中 —— 会传到墙里、斜面外沿或虚空，
表现为"偶尔掉出地图"，
⛔ 而绝大多数传送点合法，这个问题只在少数位置复现。

【产出】四重判定函数 + 非法时的反馈

【判据】对斜面、墙角、天花板下方、区域边界四类位置判定均拒绝。

【审】`audit/godot/xr.md#8`

### Step 3　位移必须淡入淡出，瞬移是晕动症头号成因　`[xr/05#S3]`

【读】`howto/godot/xr.md#4. 传送`

【做】
所有位移（含传送、重生、关卡切换）都配 vignette 淡入淡出。
⛔ 直接改 `XROrigin3D.global_position` 瞬移 ——
这是晕动症的头号成因，
表现为"玩十分钟就难受"，⛔ 而开发者自己反复暴露会产生耐受，
⛔ **主观感受不能当判据**（见 07/S5）。

ⓘ 移动的一定是 `XROrigin3D`，⛔ 不是相机（见 01/S1）。

【产出】位移封装（内部必带 vignette）

【判据】全局搜位移调用，全部经过封装；⛔ 无裸改 origin 位置。

【审】`audit/godot/xr.md#9`

### Step 4　平滑移动配隧道视野，且强度必须暴露给玩家　`[xr/05#S4]`

【读】`howto/godot/xr-deep.md#3. 移动与舒适度`

【做】
保留平滑移动时配隧道视野（移动时收缩视野），
并把移动方式、转向方式、隧道视野强度**做成设置项**。
⛔ 把强度写死 —— 隧道视野是**舒适度设置**不是美术效果，
写死等于替玩家决定他能承受多晕，
⛔ 表现为"一部分人怎么调都不舒服、另一部分人嫌挡视线"，
而两组反馈互相矛盾，看不出是缺一个滑块。

【产出】舒适度设置项（三项）+ 默认值

【判据】三项都能在游戏内改并立即生效。

【审】`audit/godot/xr-deep.md#19`

### Step 5　转向要提供 snap turn 选项，⛔ 不只有平滑旋转　`[xr/05#S5]`

【读】`howto/godot/xr.md#5. 晕动症（VR 特有，最重要）`

【做】
实现 snap turn（瞬时角度）并作为默认或可选项，⛔ 不只提供平滑旋转。
⛔ 只有平滑旋转 —— 一部分玩家会直接晕，
⛔ 而开发机上自己转两下没事，
这个问题**只在真实用户身上出现**且不会被报成 bug。

ⓘ 同时提供固定参考系（座舱 / 静止 HUD 元素）有助于缓解，
⛔ 但它是辅助手段，不能替代转向方式的选择。

【产出】snap turn 实现 + 开关（含角度档位登记）

【判据】设置里可切换到 snap turn；两种模式各有一次真人实测记录。

【审】`audit/godot/xr.md#22`

### Step 6　空间 UI 要同时解决深度、命中、可读性　`[xr/05#S6]`

【读】`howto/godot/xr-deep.md#4. 空间 UI`

【做】
用 3D 面板 + 指针射线，并同时处理三件事：
面板能被指针射线点中（射线与 UI 的碰撞层）、
世界空间 UI 的分辨率足够（太远会糊）、
文本输入有虚拟键盘。
⛔ 沿用 2D 控件 —— 在 VR 里没有正确的深度与命中，
表现为"看得见点不着"，
⛔ 而控件本身工作正常，排查被引向输入事件或焦点。

【产出】空间 UI 面板（含碰撞层配置）+ 可读性距离登记

【判据】在最近与最远可用距离上都能点中且文字清晰。

【审】`audit/godot/xr.md#14`

## 3. 参考实现

```gdscript
# ⓘ 承接本步产出：四重判定 + 必带 vignette + snap turn 档位
# ⛔ SNAP_ANGLE / VIGNETTE_MS / MIN_HEADROOM 由 00 参数表实测回填
const MIN_HEADROOM := 1.2          # 落点头顶最小净空（米）
const MAX_SLOPE_DOT := 0.7         # 法线朝上阈值
const SNAP_ANGLE := deg_to_rad(30.0)
const VIGNETTE_MS := 180

func try_teleport(hit: Dictionary) -> bool:
    if hit.is_empty():                      return false   # ① 命中
    if hit["normal"].dot(Vector3.UP) < MAX_SLOPE_DOT: return false  # ② 法线朝上
    if not _has_headroom(hit["position"], MIN_HEADROOM): return false  # ③ 头顶空间
    if not _in_allowed_zone(hit["position"]): return false  # ④ 允许区域
    return true

func move_origin(to: Vector3) -> void:
    yield_vignette(VIGNETTE_MS)             # ⛔ 瞬移是晕动症头号成因
    global_position = to
```

ⓘ 上例只示范判定与位移封装，
⛔ 移动的是 origin 不是相机（见 01/S1），隧道视野见 S4。
