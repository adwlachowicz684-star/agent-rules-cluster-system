# 06 渲染选型与帧预算（XR 域）

> **本步交付**：渲染器已按 foveation 需求选型 + 设置时机正确 + 帧预算已换算
> **对应**：流程 `howto/godot/xr-deep.md` · 审核 `audit/godot/xr-deep.md`

## 0. 交付物定义

1. 渲染器已选型，且选型**先于** foveation 需求定下来
2. `render_target_size_multiplier` 在接口初始化**之前**设
3. 刷新率读 API，⛔ 不写死 90
4. foveation / VRS 在初始化**之后**设，Vulkan 下配 `VRS_XR`
5. 帧预算按刷新率换算（看双眼总量）+ 降负载顺序已定

## 1. 前置检查清单

- [ ] 渲染器选型与 foveation 需求一致
- [ ] 分辨率倍率的设置点早于接口初始化
- [ ] 刷新率来自 `get_available_display_refresh_rates()`
- [ ] foveation 设置点晚于接口初始化
- [ ] 帧预算表按目标刷新率换算

## 2. 工序

### Step 1　先定要不要动态 foveation，再选渲染器　`[xr/06#S1]`

【读】`howto/godot/xr-deep.md#6. ⛔ 官方口径：渲染器、foveation 与设置时机`

【做】
先回答"要不要动态注视点渲染"，**再**定渲染器。
官方 `foveation_dynamic` 注明 *"Only works on the Compatibility renderer."*，
而"XR 必须用 Mobile 或 Forward+"是另一条常见口径 ——
⛔ 两者**直接冲突**：想要动态 foveation 就必须 Compatibility。

⛔ 先选渲染器再补 foveation ——
补的时候才发现渲染器要换，
⛔ 而换渲染器会连带重测材质、后处理与阴影，属于中期整体返工。

【产出】渲染器选型 + 是否启用动态 foveation（写进参数表）

【判据】参数表里能查到"为什么是这个渲染器"，且与 foveation 需求自洽。

【审】`audit/godot/xr-deep.md#20`

### Step 2　分辨率倍率必须在接口初始化之前设，⛔ 不在 _ready 里　`[xr/06#S2]`

【读】`howto/godot/xr-deep.md#6. ⛔ 官方口径：渲染器、foveation 与设置时机`

【做】
把 `render_target_size_multiplier` 的设置放在 OpenXR 接口初始化**之前**。
⛔ 官方原话是 *"Must be set before the interface has been initialized."* ——
在 `_ready()` 里设通常已太晚，
表现为"设了没效果"，⛔ 而属性面板上值确实是你写的那个，
排查被引向"是不是被别处覆盖了"。

ⓘ 注意它与下一条的时机要求**相反**，
两者不能写在同一段初始化代码里而不加区分。

【产出】倍率设置点（早于初始化）+ 注释标明时机

【判据】改倍率后渲染目标尺寸确实变化（可用调试叠加层确认）。

【审】`audit/godot/xr-deep.md#21`

### Step 3　刷新率由运行时决定，读 API 不写死；延迟预算单独登记　`[xr/06#S3]`

【读】`howto/godot/xr-deep.md#5. 性能`

【做】
用 `get_available_display_refresh_rates()` 读可用档位、
`display_refresh_rate` 读当前值，⛔ 不在代码里写死 90。
⛔ 写死 —— 在只支持 72Hz 或支持 120Hz 的设备上，
要么白丢性能要么被合成层重投影，
表现为"有的设备上画面拖影、有的设备上性能过剩"，
⛔ 而开发机只有一种刷新率，这个问题**永远发现不了**。

同时把**输入到画面的延迟预算**单独登记：
⛔ 只盯帧率不看延迟 —— 帧率达标但延迟超预算时，
玩家会感到"手和画面不同步"，
⛔ 而性能面板上一切正常。

【产出】刷新率读取代码 + 延迟预算登记

【判据】在两种刷新率设备上都能读到正确档位；延迟预算有数字。

【审】`audit/godot/xr-deep.md#13`

【品】`craft/godot/feel-params.md#6. 输入到画面的延迟预算`

### Step 4　foveation 与 VRS 在初始化之后设，Vulkan 下要 VRS_XR　`[xr/06#S4]`

【读】`howto/godot/xr-deep.md#6. ⛔ 官方口径：渲染器、foveation 与设置时机`

【做】
`foveation_level`（0–3）与 `foveation_dynamic` 放在接口初始化**之后**设；
若走 Vulkan 驱动，还要把 `Viewport.vrs_mode` 设为 `VRS_XR`。
⛔ 沿用上一步的"初始化前"写法 ——
这两个属性的要求恰好相反（*"The interface must be initialized before
this is accessible."*），
⛔ 设早了拿到的不是报错而是无效值，表现为"开了 foveation 没收益"。

ⓘ `is_foveation_supported()` 同样要求初始化后才返回有效值，
⛔ 初始化前查会拿到 false 而误判"设备不支持"。

【产出】foveation 设置点（晚于初始化）+ VRS 模式配置

【判据】开启后 GPU 时间可测地下降；关闭后恢复。

【审】`audit/godot/xr-deep.md#22`

### Step 5　帧预算按刷新率换算并看双眼总量，降负载有固定顺序　`[xr/06#S5]`

【读】`howto/godot/xr-deep.md#5. 性能`

【做】
按目标刷新率换算单帧预算（72Hz ≈ 13.89ms / 90Hz ≈ 11.11ms / 120Hz ≈ 8.33ms），
并且**按双眼总量**算，⛔ 不是按单眼。
同时定下降负载顺序：动态分辨率 → LOD / 遮挡 / 远处阴影 → 才减对象与材质。
⛔ 一上来就减对象 —— 会先毁掉画面，
⛔ 而"画面变差了但帧率上去了"会被当成优化成功，
真正的瓶颈（fillrate 还是命令提交）从未被定位过。

ⓘ 判别方法：降内部分辨率立刻恢复 → fillrate 为主；
GPU 时间几乎不变 → 查命令提交。

【产出】帧预算表（按目标刷新率）+ 降负载顺序

【判据】参数表里有目标刷新率对应的毫秒数；降负载按序执行有记录。

【审】`audit/godot/xr-deep.md#12`、`audit/godot/xr-deep.md#23`

## 3. 参考实现

```gdscript
# ⓘ 承接本步产出：两个相反的时机 + 刷新率读 API + 预算换算
# ⛔ TARGET_HZ / RENDER_SCALE / FOVEATION_LEVEL 由 00 参数表实测回填
const RENDER_SCALE := 1.0      # ⛔ 必须早于接口初始化设置
const FOVEATION_LEVEL := 2     # ⛔ 必须晚于接口初始化设置
const TARGET_HZ := 90.0

func pre_init() -> void:
    var oxr := XRServer.find_interface("OpenXR") as OpenXRInterface
    oxr.render_target_size_multiplier = RENDER_SCALE   # ⛔ 早

func post_init() -> void:
    var oxr := XRServer.find_interface("OpenXR") as OpenXRInterface
    if not oxr.is_foveation_supported():
        return
    oxr.foveation_level = FOVEATION_LEVEL              # ⛔ 晚
    oxr.foveation_dynamic = true
    var rates := oxr.get_available_display_refresh_rates()
    print("可用刷新率：", rates)                        # ⛔ 不写死 90

static func frame_budget_ms(hz: float) -> float:
    return 1000.0 / hz                                 # ⓘ 双眼总量，不是单眼
```

ⓘ 上例只示范时机与换算，
⛔ Vulkan 下还要 `Viewport.vrs_mode = Viewport.VRS_XR`（见 S4）。
