# 01 外观模型与拥有权地基（外观域）

> **本步交付**：三层模型 + 生效范围字段 + 服务端权威口径
> **对应**：流程 `howto/godot/cosmetic.md` · 审核 `audit/godot/cosmetic.md`

## 0. 交付物定义

1. `AppearanceTemplate` / `AppearanceInstance` / `ActiveAppearance` 三层已定义
2. 每层的"⛔ 不应混入"字段已写下（不是只写正向定义）
3. **生效范围**字段已存在（角色 / 槽位 / 场景 / 观察者距离 / 可见对象）
4. "客户端选择成功 ≠ 拥有"的口径已确立，客户端只有本地预览
5. 外观业务规则不写在节点脚本里（双仓库）

## 1. 前置检查清单

- [ ] 能用一句话说清三层各自的职责与不混入什么
- [ ] 生效范围字段已存在，⛔ 不是"全游戏生效"
- [ ] 服务端持有拥有权、有效期、优先级、授权
- [ ] 客户端只持有可展示缓存
- [ ] 外观规则与节点脚本分离

## 2. 工序

### Step 1　七类外观统一成三层，先写"不混入什么"　`[cosmetic/01#S1]`

【读】`howto/godot/cosmetic.md#0. 七类外观共享的是"展示状态"，不是资产形态`

【做】
定义 `AppearanceTemplate`（这是什么）、`AppearanceInstance`（这个玩家拥有的这一份）、
`ActiveAppearance`（当前显示哪个）三层，并**逐层写下"⛔ 不应混入"的字段**。
⛔ 只写正向定义、不写禁止项 —— 三层会**悄悄长成一层**：
玩家拥有状态混进模板、资源对象混进实例，
表现为"改一个模板，所有人的外观都变了"，且不报错。

ⓘ 三层分开的收益在审计时才显现：
出问题时能直接问"是模板错了、实例错了、还是生效状态错了"，
⛔ 混成一层就只能全量排查。

【产出】三层数据结构定义（含各层禁止字段清单）

【判据】指着任意字段，能说出它属于哪一层；⛔ 没有字段跨层重复出现。

【审】`audit/godot/cosmetic.md#1`、`audit/godot/cosmetic.md#33`

### Step 2　生效范围字段必须有，⛔ 不能是"全游戏生效"　`[cosmetic/01#S2]`

【读】`howto/godot/cosmetic.md#0. 七类外观共享的是"展示状态"，不是资产形态`

【做】
在 `ActiveAppearance` 上定义生效范围：哪个角色、哪个槽位、哪些场景、
观察者距离、是否只对好友/队友可见。
⛔ 省掉这个字段、写成"全游戏任意位置生效" ——
战斗、竞技场、过场、观战会各自取数据，
表现为"服务端允许、客户端拒绝"，而两边日志都自洽。

ⓘ 活动外观尤其容易踩：它天然是"限时 + 限场景"的，
⛔ 做成全局生效后要回收，得同时改四个模块的取数逻辑。

【产出】生效范围字段定义 + 各场景的取数口径

【判据】指着任一外观，能说出它在竞技场与在过场里分别取哪份数据。

【审】`audit/godot/cosmetic.md#2`

### Step 3　服务端权威：客户端"选择成功"只是本地预览　`[cosmetic/01#S3]`

【读】`howto/godot/cosmetic.md#1. 换装与染色：技术实现见专门文档`

【做】
确立口径：**拥有权、有效期、优先级、授权只在服务端**；
客户端的"换装成功"只更新本地展示，等服务端确认后才算生效。
⛔ 客户端选成功就写进库存 —— 改内存就能凭空造限定时装，
表现为"有人穿着没发售的时装"，⛔ 而服务端日志里这个人"从未获得过"。

ⓘ 服务端拒绝后要能**撤销预览**并回退上一组已验证外观，
⛔ 不能停在"显示着但没有拥有"的中间态。

【产出】服务端响应码表（含 `not_owned` 时清缓存、`conflict` 时返回权威外观）

【判据】伪造一个客户端请求，服务端拒绝且客户端回退，无任何中间态。

【审】`audit/godot/cosmetic.md#7`、`audit/godot/cosmetic.md#11`

### Step 4　称号 / 头像框：纯 UI 资产也要服务端签发　`[cosmetic/01#S4]`

【读】`howto/godot/cosmetic.md#3. 称号 / 头像框：纯 UI 资产，但仍要服务端权威`

【做】
称号由服务端签发白名单、拥有状态与展示签名；客户端只存可展示文本。
⛔ 客户端保存内部称号枚举 —— 可伪造出 GM / 客服称号，
这是**社会工程攻击的入口**，后果远超"显示不对"。
⚠ 高权限称号变更必须重新签名。

【产出】称号签发表 + 客户端只存展示文本的说明

【判据】改客户端内存无法让称号变成未拥有的高权限称号。

【审】`audit/godot/cosmetic.md#14`、`audit/godot/cosmetic.md#15`

### Step 5　外观业务规则不写进节点脚本（双仓库）　`[cosmetic/01#S5]`

【读】`howto/godot/cosmetic.md#10. 双仓库：外观业务规则不应混写在节点脚本里`

【做】
把"谁拥有哪件限时时装"的规则放在独立的数据/服务层，节点脚本只负责展示。
⛔ 写在节点脚本里 —— 节点是运行时结构，
表现为"切场景后拥有状态丢了"，而排查必然被引向存档或网络。

ⓘ 判据很简单：**把渲染节点整个删掉，拥有权数据应该仍然完整**。

【产出】规则层与展示层的目录/职责划分

【判据】删掉全部展示节点后，拥有权与有效期数据仍可完整读出。

【审】`audit/godot/cosmetic.md#33`

## 3. 参考实现

```gdscript
# ⓘ 承接本步产出：三层分离 + 生效范围 + 服务端权威
class_name AppearanceTemplate extends Resource
# ⛔ 不混入：玩家拥有状态、具体染色值、动画冷却
@export var id: StringName
@export var slot: StringName
@export var display_name: String
@export var asset_ref: String          # 资产路径，⛔ 不是资源对象
@export var scope_rank: int
@export var source_rank: int
@export var valid_scenes: PackedStringArray

class_name AppearanceInstance extends Resource
# ⛔ 不混入：网格 / 材质 / 动画资源本体
@export var instance_id: StringName
@export var template_id: StringName
@export var obtain_time: int
@export var expire_time: int          # 0 表示永久
@export var dye_params: PackedColorArray

class_name ActiveAppearance extends Resource
# ⛔ 不混入：完整资源对象、完整玩家档案
@export var slot: StringName
@export var instance_id: StringName
@export var signature: String         # 服务端签发
@export var version: int              # appearance_version，单调递增
@export var scope: Dictionary         # 角色 / 场景 / 观察者距离 / 可见对象
```

## 4. 验收清单

- [ ] 三层各自职责明确，禁止字段已写下
- [ ] 生效范围存在，非"全游戏生效"
- [ ] 客户端选择成功只是预览，服务端可拒绝并撤销
- [ ] 称号服务端签发，客户端无内部枚举
- [ ] 规则层与展示层分离，删节点不丢数据

## 5. 常见返工

| 症状 | 原因 | 回到 |
|---|---|---|
| 改一个模板所有人外观都变 | 三层悄悄长成一层 | S1 |
| 服务端允许、客户端拒绝 | 缺生效范围字段 | S2 |
| 有人穿着未发售的时装 | 客户端选择即写入库存 | S3 |
| 冒充 GM / 客服 | 客户端保存称号枚举 | S4 |
| 切场景后拥有状态丢失 | 规则写在节点脚本里 | S5 |
