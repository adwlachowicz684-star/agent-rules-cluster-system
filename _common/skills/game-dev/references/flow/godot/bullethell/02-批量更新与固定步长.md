# 02 批量更新与固定步长（弹幕域）

> **本步交付**：固定逻辑步长 + 有上限累加器 + tick 计数基准
> **对应**：流程 `howto/godot/genres-bullet-hell.md` · 审核 `audit/godot/genres-bullet-hell.md`

## 0. 交付物定义

1. 弹幕逻辑跑在固定步长上，⛔ 不用渲染 `delta`
2. 累加器有**明确上限**
3. 图案时间轴以**逻辑 tick 计数**为基准
4. 一次遍历先算后写，回收在遍历之后
5. 逻辑步长与 `physics_ticks_per_second` 的关系已登记

## 1. 前置检查清单

- [ ] 存在 `_step(LOGIC_STEP)` 且只被累加器驱动
- [ ] 累加器有最大追帧步数
- [ ] 时间轴用 tick 计数，不是秒
- [ ] 遍历中不改活跃表
- [ ] 步长与物理 TPS 的取值已分别登记

## 2. 工序

### Step 1　弹幕逻辑用固定步长，⛔ 不能吃渲染 delta　`[bullethell/02#S1]`

【读】`howto/godot/genres-bullet-hell.md#4. 弹幕逻辑用固定步长，不是 delta`

【做】
用累加器把渲染 `delta` 攒成固定步长的 `_step()` 调用，
⛔ 不要在 `_physics_process` 里直接用 `delta` 推进弹幕 ——
弹幕图案对帧率敏感且要求确定性回放，
表现为"60Hz 与 144Hz 下弹幕密度不同"。

ⓘ 固定步长的收益不只是回放：
它让图案参数（间隔、速度）有**稳定单位**，
⛔ 用 delta 时所有参数都要按帧率重新解释一遍。

【产出】`_process` 累加器 + `_step(LOGIC_STEP)`

【判据】锁 30 / 60 / 144 FPS 三档跑同一图案，弹幕数量与分布一致。

【审】`audit/godot/genres-bullet-hell.md#7`

### Step 2　累加器必须有上限，⛔ 无上限会 spiral of death　`[bullethell/02#S2]`

【读】`howto/godot/genres-bullet-hell.md#9. ⛔ 固定步长累加器必须有上限`

【做】
给累加器设最大追帧步数（超过就丢弃剩余时间），
⛔ 不设上限 —— 官方 `Engine.max_physics_steps_per_frame` 默认 `8`
的存在理由就是避免 *"spiral of death"*
（昂贵的模拟触发更多模拟，无限循环）。
表现为"偶尔掉一次帧后游戏再也回不到正常速度"。

ⓘ 丢弃剩余时间会让弹幕**变慢一瞬**，
⛔ 但这是正确取舍：追帧导致的是**永久卡死**。

【产出】`MAX_CATCHUP_STEPS` 与丢弃策略

【判据】人为卡顿 500ms 后，游戏能在 1 秒内回到正常速度。

【审】`audit/godot/genres-bullet-hell.md#14`

### Step 3　逻辑步长与 physics_ticks_per_second 分开登记，⛔ 不混用　`[bullethell/02#S3]`

【读】`howto/godot/genres-bullet-hell.md#9. ⛔ 固定步长累加器必须有上限`

【做】
弹幕逻辑步长是**自己的常量**，⛔ 不等于 `physics_ticks_per_second`，
改物理 TPS 时也不连带改它。
⛔ 把 `physics_ticks_per_second` 提到 240 以上求"更准" ——
官方明确：渲染帧率一旦低于 30 FPS，游戏会**整体变慢**，
（即使物理计算里一直正确使用 `delta`），
除非同步把 `max_physics_steps_per_frame` 一起改。

ⓘ 弹幕不需要更高的物理 TPS：
弹幕碰撞是**解析判定**（距离比较），不是物理求解，
⛔ 提高 TPS 只会增加开销而不提升手感。

【产出】两处取值的分别登记与改动的连带检查项

【判据】改物理 TPS 后弹幕密度不变；改弹幕步长后物理行为不变。

【审】`audit/godot/genres-bullet-hell.md#15`

### Step 4　一次遍历先算后写，回收统一在遍历之后　`[bullethell/02#S4]`

【读】`howto/godot/genres-bullet-hell.md#1. MultiMesh 定容量，运行时只改可见数`

【做】
单趟遍历内只做"读旧值 → 算新值 → 写回"，
越界与 lifetime 到期的索引**先记到待回收表**，遍历结束后统一回收。
⛔ 边遍历边改活跃表 —— 索引会整体错位，
表现为"偶尔少一颗 / 多一颗"，且不报错。

ⓘ 这条与分裂弹叠加时最容易出问题：
分裂会在遍历中**新增**弹幕，同样要进待处理表，⛔ 不能当场 spawn。

【产出】单趟更新函数 + 待回收 / 待 spawn 两张表

【判据】打满上限并持续分裂 10 秒，活跃数从不越界、从不丢索引。

【审】`audit/godot/genres-bullet-hell.md#16`

### Step 5　图案时间轴以 tick 计数为基准，⛔ 不用秒　`[bullethell/02#S5]`

【读】`howto/godot/genres-bullet-hell.md#5. 图案是数据，不是代码`

【做】
时间轴上的触发时刻存**逻辑 tick 序号**，不是秒数。
⛔ 用秒 —— 浮点累加会让长时间回放的触发点漂移，
表现为"回放第 3 分钟开始弹幕密度和原局不一样"。

ⓘ tick 计数还带来两个免费能力：
图案可**跳转到任意 tick**预览（见 04），
以及回放校验只需比对 tick 序列而不必比对浮点。

【产出】`EmitCommand.tick` 字段定义

【判据】同一图案跑两遍，触发 tick 序列完全相同。

【审】`audit/godot/genres-bullet-hell.md#17`

## 3. 参考实现

```gdscript
# ⓘ 承接 01：定容量世界 + 累加器
# ⛔ LOGIC_STEP / MAX_CATCHUP_STEPS 由 00 参数表回填
const LOGIC_STEP := 1.0 / 60.0
const MAX_CATCHUP_STEPS := 8      # ⛔ 与 Engine.max_physics_steps_per_frame 同思路
var _acc := 0.0
var _tick := 0

func _process(delta: float) -> void:
    _acc += delta
    var n := 0
    while _acc >= LOGIC_STEP and n < MAX_CATCHUP_STEPS:
        _step(LOGIC_STEP)
        _tick += 1
        _acc -= LOGIC_STEP
        n += 1
    if n >= MAX_CATCHUP_STEPS:
        _acc = 0.0                # ⛔ 丢弃剩余，宁可慢一瞬也不要追到卡死

func _step(dt: float) -> void:
    for i in _active:
        _x[i] += _vx[i] * dt
        _y[i] += _vy[i] * dt
    # ⛔ 回收在遍历之后统一做，不在 _step 内改 _active
```

## 4. 验收清单

- [ ] 锁 30/60/144 FPS 弹幕分布一致
- [ ] 人为卡顿后能恢复到正常速度
- [ ] 改物理 TPS 不影响弹幕密度

## 5. 常见返工

| 症状 | 原因 | 回到 |
|---|---|---|
| 不同刷新率弹幕密度不同 | 吃了渲染 delta | S1 |
| 掉一次帧后再也回不去 | 累加器无上限 | S2 |
| 提高 TPS 后低帧率时变慢 | 没同步改追帧上限 | S3 |
| 弹幕偶尔少一颗 | 遍历中改活跃表 | S4 |
| 回放几分钟后不一样 | 时间轴用秒 | S5 |
