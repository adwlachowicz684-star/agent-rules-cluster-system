# 玩家交易 / 拍卖行 / C2C 经济流通（Godot 4.7.2）

**此前文档里「拍卖行 / 摆摊 / 玩家交易 / 交易行 / 市场」全部 0 命中。**

> ⚠ **与 `economy.md` 的分工**：那篇回答"货币和物品**从哪里来、被什么消耗**"
> （产出与消耗侧，含养成与天赋树、装备四层分离）；
> 本篇只回答"**已存在的某份资产如何从一方到达另一方**"，以及这一转移
> **是否可逆、可审计、可风控**。两者共享货币与物品定义，但必须共享服务化 owner，
> ⛔ 不是让交易代码直接改背包表。
> 商业化/支付见 `monetization.md`。

⚠ **一句话定调**：**客户端请求交易，服务端决定一切；
任何资产离开一个位置时，必须先建立另一个位置的权威暂存状态。**

> 审核用反模式清单见 `audit/godot/player-trading.md`

## 0. 五种形态：先选形态，再谈实现

| 形态 | 适用 | 时间特性 | 主要代价 | 兜底 |
|---|---|---|---|---|
| **面对面直接交易** | 双方同时在线、需当面谈价 | 同步 | 欺诈、机器人、确认复杂 | 锁定—双方确认—短延迟—冷却 |
| **摆摊 / 寄售** | 强调"逛店"与社交 | 卖家在线或代理在线 | 发现成本高、掉线影响 | 代理托管、离线关闭、撤销冷却 |
| **拍卖行** | 异步、全服、长尾与高价值 | 分钟~天 | 刷价、机器人、托管复杂 | 状态机、保证金、延迟到账、快照日志 |
| **邮件附件** | 异步、异地、跨时区、大额 | 发送即等待领取 | 不可见资产、附件过期 | 服务端权威领取、延迟、过期回退 |
| **公会仓库** | 组织内部共享、贡献与借还 | 同步/异步混合 | 会长权限、批量洗金、纠纷 | 权限、流水、取出冷却、审批队列 |

⚠ **"支持直接交易"通常是降低社交门槛的让步，不是功能缺失。**
拍卖行提供价格发现与异步流动性，却牺牲了面对面议价、以物易物、赠与与即时交付。
⛔ 不要把"开放直接交易"理解成"省一个拍卖行"。

⚠ **所有形态必须共用一个资产转移原子操作**，否则会变成五套背包写法和五种漏洞：

```gdscript
TransferAsset(source_owner, source_location,
              destination_owner, destination_location,
              asset_ref, expected_version, reason, trace_id)
```

同一物品实例**同时只能有一个权威位置**；任何新状态先创建不可变历史记录，再更新索引。

## 1. 流转的是实例，不是模板

⚠ 唯一装备即使由同一模板生成，也必须有**不可复用**的 `item_instance_id`。

| 字段 | 唯一装备 | 可堆叠材料 | 说明 |
|---|---|---|---|
| `item_instance_id` | 必填 | 建议必填 | **服务端生成，不可复用** |
| `template_id` | 必填 | 必填 | 用于展示和搜索，⛔ 不是成交依据 |
| `affix_snapshot` | 必填 | 空 | 成交时锁定，**不重新随机** |
| `durability` | 必填 | 0/不适用 | 必须随实例迁移 |
| `bind_state` | 必填 | 按设计 | 成交前与确认时**双检** |
| `stack_id` | 空 | 必填 | 代表"这一堆" |
| `quantity` | 1 | 1..max_stack | 拆分后总量守恒 |
| `parent_stack_id` | 空 | 拆分时可填 | 用于追溯，⛔ 不是所有权链 |

⚠ **绑定不是显示标签，而是资产迁移函数的输入。**
服务端维护 `trade_policy`，为每种来源/绑定类型/角色/接收者组合返回：
`ALLOWED` / `DENIED` / `CONVERT_BIND_ON_RECEIVE` / `DELAYED`。
⚠ 任何交易前**用物品当前状态和版本重新求值**，⛔ 不能缓存客户端发来的"可交易"。

⚠ **拆分要生成新 `stack_id`，保留血缘但⛔ 永不复用旧实例 ID。**
旧堆 50 拆成 20+30：原 `stack_id` 退出，服务端建两个新实例，数量合计仍 50。
⛔ 若沿用旧 ID → 外部缓存、挂单快照、邮件附件会指向一个已不存在的"20 份实例"；
⛔ 若把 30 写成"原实例+数量"却没生成新 ID → 撤销原挂单时可能**错误释放同一份资产**。

## 2. 挂单：先用托管把"可卖物品"从背包拿走

⚠ **上架那一刻就把实例位置改成市场托管，
⛔ 不是等成交时再检查"是否还在背包"** —— 否则卖家可以继续装备、销毁、邮寄、再挂（双卖）。

```gdscript
func request_listing(player, client_ref, qty, price_type, price, duration, idem_key):
    if not player.trade_eligible: return reject()
    if not rate_limiter.allow("list", player, item): return reject()
    var inst = inventory.lock_and_load(client_ref, true)   # 版本锁
    if inst.owner != player or not inst.tradable or inst.locked: return reject()
    if qty > inst.quantity or qty < 1: return reject()
    if not price.within_policy(item, market_reference): return reject()
    var deposit = fee_calculator.listing_deposit(item, duration)
    currency.reserve_or_charge(player, deposit, idem_key)
    var listing = market.create_listing(player, inst, qty, price_type, price, duration)
    escrow.place(listing.id, inst, qty, inst.version)     # 托管
    inventory.mark_market_listed(client_ref, listing.id)
    audit.write(LIST, inst, escrow, price)                # 快照
    return listing.public_view
```

⚠ 客户端可以在请求前显示**预估**费用，⛔ 不得决定实际扣费
（余额、VIP 折扣、费率都可能在请求途中变化）。

**挂单状态机（⚠ "正在结算"与"已成交"必须互斥）：**

```
PENDING → ACTIVE → BUYOUT_PENDING / BID_WIN_PENDING → SETTLING → COMPLETED
                 ↘ CANCELLED / EXPIRED / DISPUTED
```

| 事件 | 前 → 后 | 必做 |
|---|---|---|
| 上架成功 | PENDING → ACTIVE | 扣/冻结保证金，物品托管 |
| 一口价购买 | ACTIVE → BUYOUT_PENDING | 冻结货款与税，**二次读价格** |
| 竞价出价 | ACTIVE → ACTIVE | 冻结新领先资金，释放旧领先资金 |
| 到时成交 | ACTIVE → BID_WIN_PENDING | 冻结货款，准备结算 |
| 令牌结算 | *_PENDING → SETTLING → COMPLETED | 发货、扣税、付卖家、审计 |
| 撤销 | ACTIVE → CANCELLED | 按规则扣费/释放保证金，返还物品 |
| 无人成交 | ACTIVE → EXPIRED | 返还物品，处理保证金 |

⚠ 两个请求竞争最后一件时，只有**先拿到挂单版本**的行能完成，失败方退款并收到幂等错误码。
⛔ **绝不能先给双方客户端返回成功，再后台"尽量结算"**。

## 3. 一口价是同步成交，竞价是条件订单 + 延时结算

⚠ **一口价**：服务端从最新挂单**重新读取价格**，⛔ 不相信客户端附带的单价。
价格仍有效且买家资金够 → 冻结货款与税 → 一次性结算。

⚠ **竞价的本质不是"显示当前最高价"，而是把领先者资金冻结到拍卖结束。**

```gdscript
func place_bid(player, listing_id, amount, idem_key):
    var l = market.lock_listing(listing_id, true)
    if l.status != ACTIVE: return reject()
    if amount <= l.effective_price or amount < l.min_next_bid: return reject()
    if player.funds < amount + expected_tax: return reject()
    var previous = l.leading_bid
    l.current_price = amount
    l.leading_bidder = player
    l.version += 1
    l.save()
    if previous: funds.release(previous.hold_id)   # 先持久化新领先，再异步释放
    funds.hold(player, amount, idem_key, listing_id)
    audit.write(BID, l, previous, amount)
    anti_snipe.apply(l)                             # ⚠ 仅服务端决定延期
```

⚠ 定时器只负责把 `ACTIVE` 转成待结算，**结算本身仍由唯一令牌执行**。
否则"截止前一毫秒出价"会因网络时钟差与并发产生争议。

⚠ **"代拍/顶价"应建模为服务端订单，⛔ 不是客户端自动点价。**
客户端只设绝对上限与可选增量策略，服务端只出价到"当前最低可领先额"，绝不超过上限。

⚠ **价格显示只是缓存**：排序可异步，**成交必须实时**。
点击购买时服务端重查最新挂单与价格；界面显示"价格待确认"，
⛔ 不要显示客户端缓存价就允许连点。

## 4. 玩家定价 + 服务端软边界（不是二选一）

⚠ **玩家定价**提供流动性与商人玩法，代价是起拍战、虚假压价、扫货抬价、低价陷阱。
⚠ **系统定价**适合新手引导、稳定材料、高通胀资源、RMT 高风险物品，但会让稀缺性失真。

✅ 推荐：**玩家市场价格发现 + 服务端软边界 + 风险处置。**
每个物品维护可配置 `price_policy`：无边界 / 只限绝对上下界 / 限近期成交分布 / 按系统锚价浮动。
⚠ 服务端**拒绝**明显超界的订单，⛔ 但**不自动改成"合理价格"**（卖家会抱怨系统偷改）。

| 指标 | 优点 | 缺陷 | 用途 |
|---|---|---|---|
| 成交中位数 | 抗极端价 | 低成交量时不稳 | 稳定材料指导价 |
| 成交量加权均价 | 反映成交结构 | 易被大单拉动 | 补充 |
| 时间衰减加权中位数 | 重视近期 | 参数需调 | 高波动装备 |
| NPC / 合成成本锚 | 稳定可预测 | 不代表需求 | **兜底与防崩溃价** |
| 分位数区间 | 可识别低价扫货 | 实现复杂 | 风控与市场 UI |

⚠ **近期成交中位数必须剔除异常值和未真正成交的记录**：
样本 = 有效窗口内**成功结算且未被撤销/回滚**的成交；排序后排除首尾风险比例（**待核实**）；
⚠ 来源关联订单、自买自卖、机器人循环交易要单独剔除或降权。
⛔ **不要把全服最低挂单价当成交价** —— 那可能是诱饵、误操作或被脚本抢走的临时价。

## 5. 税：既改变行为，也决定货币去哪

⚠ 三种模式**不可混用**（UI 缓存、历史邮件、税率配置会不一致）：

| 模式 | 现金流 | 特点 |
|---|---|---|
| **买家付税** | 买家付"成交价+税"，卖家收成交价 | 税最显眼，玩家比较报价直观 |
| **卖家付税** | 买家付成交价，卖家收"成交价-税" | 可抑制挂过高价 |
| 双方各付 | 复杂 | ⛔ 除非有社交/阵营需求，否则不建议 |

⚠ **阶梯税按本次交易的 taxable base 算，⛔ 不让客户端选档位：**
`fee = min(price, b1)*r1 + max(0, min(price, b2) - b1)*r2 + ...`
⚠ 阶梯税可能诱使把交易拆成多笔小额 → **必须同时限制拆分与短期上架频率**。

⚠ **销毁比回到系统钱包更可控** —— 销毁直接减少货币存量；
进系统钱包后那笔钱再怎么花仍是货币回流。
⚠ 公会仓库捐赠、跨服中转、机器人代售应视为普通市场收入或另设 sink，
⛔ 不能因为是系统账户就不计税。

⚠ 客户端的"预计到手"要注明公式版本与结算时重算，
⛔ 不要向卖家显示成"保证获得"（撤销、争议、回滚都会改变最终收入）。

## 6. 面对面交易用锁定确认，公会仓库是权限化库存

⚠ 直接交易的核心是防"我一边加物品一边撤回，同时对方已点确认"：

```
PENDING → ACTIVE → LOCKED_A / LOCKED_B → CONFIRMED → SETTLING → COMPLETED
             ↑ 任一方改 offer，双方回到 ACTIVE
```

⚠ 任何边距、赠礼、以物易物、货币与手续费**均服务端计算**；
确认后对双方 offer 加版本锁，⛔ 任一方物品失效则整个交易取消，**不做部分成交**。
⚠ 距离校验要**服务端测距**，⛔ 不可信客户端位置。

⚠ **公会仓库不是"共享背包"的快捷方式，而是带 ACL 的库存服务。**
⚠ 会长⛔ 不能从经济规则中豁免；高风险取出、非成员转交、凌晨批量取走要更长冷却。
⚠ 若允许直接取出后转卖，**公会就成了洗号中转站** ——
要区分个人暂存区、公会公共区、审批区。

⚠ **摆摊**：玩家在线摊位掉线应立即停止新成交并把存量商品放入结算/回收队列；
⚠ 摊位中的物品⛔ 不再是"玩家背包中的可装备品"。

## 7. 延迟到账与撤销：盗号止损的唯一窗口

⚠ **若货款立即到账、附件立即可领、物品立即可再卖，
盗号者的最优路径就是：登录 → 批量挂单 → 低价扫给同伙 → 快速转服。**

⚠ 二次密码、设备提示、登录风控**都只是提高门槛，不能撤销已完成盗窃**。
必须在高风险资产转移上把"交易发生"与"资产完全可用"**分开**。

**推荐分级延迟**：普通小额直接结算 · 可交易贵重品按保护等级延迟 ·
异常账号与异常关系链延迟并人工复核。
ⓘ 公开资料中某游戏对直接交易/摆摊/玩家商店所得设 24/48 小时使用限制（**旁证，非通用标准**），
本项目的时长、额度、白名单与验证方式**待安全设计复核**。

⚠ 延迟策略要放进**热更新策略表**，⛔ 不要写死在客户端常量；
⚠ 策略变化**只作用于新交易**，⛔ 不追溯改旧订单。

⚠ **延迟期结束后不应自动"发到背包"** —— 背包满、账号离线、资产上限会造成隐形丢失。
应进入**可领取状态**，玩家主动领取；领取请求重新检查封禁、所有权、上限与撤销状态。
⚠ 附件到期要先转待回收任务，再由服务端返还或销毁，⛔ 不能只删记录。

⚠ **撤销必须全有或全无。** 争议撤销要同时冻结后续转移，并从**当前持有人**回滚，
⚠ **不能只看"当前货币余额"** —— 盗号成交后买家可能把货款用于强化或转给第三人，
只追回货币无法恢复装备。设计上优先冻结可撤销链路，无法回滚时人工补偿。
⚠ **补偿金走独立系统账**，⛔ 不能伪装成正常交易收入。

## 8. 防刷：目标是发现关系链，不是惩罚单一交易

⚠ 小号刷金典型模式：批量注册 → 相同/关联设备与网络 → 快速完成新手产出 →
资源集中给少数大号 → 原号弃用。
⚠ **单看一笔交易往往正常**，风控必须从"这笔是否异常"升级为
"**账号、设备、网络、行为、资金图**"的综合判断。

| 风险 | 前置信号 | 服务端响应 |
|---|---|---|
| 小号刷金 | 批量注册、同设备/网络、短生命周期、单向集中转移 | 交易资格延迟、上架数量限制、风险评分 |
| 盗号转移 | 异地/新设备、突发清空、低价大单、新关联收款方 | 延长延迟、强验证、**冻结关联链** |
| 绑定洗白 | 绑定状态变化、跨形态转移、白名单命中 | 拒绝交易；高危资产进**隔离库存** |
| 扫货垄断 | 超短反应时间、批量同参数购买、单账号垄断 | 行为挑战、慢速队列、品类购买上限 |
| 跨服套利 | 同账号跨服资产同向集中、搬运速度异常 | 跨服冷却、附加费、独立账本 |
| 货币套利 | 两货币价格长期偏离、循环转账闭环 | 汇率差阈值、税、人工审查 |
| 虚假成交 | 同集团循环买卖、自买自卖、成交后快速回售 | 从价格统计剔除、风险标记 |

⚠ **绑定物品永远不能经交易变"干净"。** 处理顺序：
① 发送前检查实例当前绑定 ② 创建转移记录时记录**原绑定快照**
③ 接收端按来源决定继承/转为接收者绑定/不允许接收 ④ 回滚时按快照恢复。
⛔ 只检查 `is_bound = true/false` 会漏掉"绑定于 A、本应不可转、却被客户端改成可交易"。
⚠ 所有绑定解除必须来自**服务端事件**（使用时绑定、赠送许可、官方解绑券）并生成独立流水。

⚠ **邮件附件是天然的审计化载体，但不能变成无摩擦洗钱通道。**
每封邮件有唯一 ID、发件人、收件人、附件清单、税/运费、创建时间、可领取时间、过期时间、状态。
⚠ 附件必须服务端冻结，客户端只收**脱敏视图**；高价值附件延迟可领取；
⚠ 大附件要限制同设备、同 IP、同账户群的总流入。

## 9. 日志：交易日志是客服和回滚的唯一真相源

⚠ 只记录"玩家 A 交易 1000 金给玩家 B"**不够** —— 交易前双方余额、价格、
物品模板与实例快照、绑定、税费、挂单版本、风险标签都可能改变处置结论。

⚠ **日志要写"请求前快照 + 意图 + 结果"，⛔ 不能只写结果。**
每次状态迁移写**两个事件**：

| 事件 | 存什么 |
|---|---|
| `DECISION` | 校验结果、价格、**策略版本** |
| `EFFECT` | 转移后的新余额与库存版本 |
| `REVERSAL_REQUEST` / `REVERSAL_EFFECT` | 撤销的意图与结果 |

这样客服才能判断"客户端请求的是 500 还是 5000""当时物品是否已锁定"
"撤销是因为玩家申诉还是风控自动触发"。
⛔ 只保存最后余额 → 误扣和误发变成**无法定责的黑箱**。

| 字段组 | 必记 |
|---|---|
| 标识 | `event_id`、`trace_id`、`actor_id`、目标角色 |
| 资产 | 物品实例快照、数量、价格、币种、前后余额 |
| 位置 | 源位置、目标位置、挂单/邮件/仓库 ID |
| 风控 | 规则版本、风险分、设备/IP **摘要** |
| 结果 | 状态迁移、失败码、撤销/补偿关系 |

⚠ 保留期限分三层：原始不可变账本长期保存 · 玩家个人历史可配月数 · 风控聚合特征到期删除或脱敏。
⚠ **日志只写哈希 ID 与设备/IP 摘要**，⛔ 不要把完整凭据、聊天原文或精确定位混入经济日志。

## 10. Godot 实现：只发请求和显示服务端状态

⛔ **Godot 端没有"半权威"的便利做法** ——
客户端⛔ 不能因为预测体验好就先扣物品、先改货币再等服务端确认。

```
UI 收集意向 → any_peer 命令 RPC → 服务端认证/限流/版本锁/业务校验
            → 可靠账本事务 → authority 推送状态与库存变更 → 客户端替换本地缓存
```

⚠ **全部写操作 RPC 用 `reliable`。** 直接交易不是位置同步——
重复扣款、乱序成交、一次出价应用两次都是**不可逆**伤害。
⚠ `reliable` 保证到达与顺序，但**不保证幂等**，
所以服务端必须用挂单版本 + 唯一请求 ID + **结算令牌**防重。

```gdscript
# 客户端 → 服务端
@rpc("any_peer", "reliable")
func request_buyout(listing_public_id: int, client_nonce: String) -> void:
    if not multiplayer.is_server(): return
    MarketService.on_buyout_request(peer_id, listing_public_id, client_nonce, request_id)

# 服务端 → 客户端
@rpc("authority", "reliable")
func receive_buyout_result(result: Dictionary) -> void:
    if multiplayer.is_server(): return
    UI_Trade.update_listing(result)
```

⚠ **`client_nonce` 只是客户端去重键，⛔ 不能替代服务端 `idempotency_key`** ——
服务端键应结合会话、玩家、操作、挂单版本与请求哈希。
⚠ 返回结构只放服务端算出的价格、税、前后余额哈希、挂单状态、错误码；
⛔ **绝不返回"已成交，请客户端扣款"**。

⚠ **RPC 不能序列化 `Object` 或 `Callable`**（官方明确），
且发送方与接收方节点必须有相同 `NodePath`。
⚠ **物品序列化只传稳定 ID 与显示摘要**，服务端按 ID 重新加载真实实例：
客户端只发 `item_instance_id` + 版本。
⛔ 禁止用 `Object`、`Resource` 实例、脚本引用或函数句柄当网络参数；
⛔ 禁止把服务端库存表直接赋给客户端场景节点。

⚠ **`set_multiplayer_authority()` 不会自动把新权威复制到其他端**（官方明确警告），
开发者必须自己通过 spawn 函数、RPC 或同步器复制。
⚠ 本项目可将场景对象权威保留给服务端，客户端只显示；
⛔ 即使未来允许玩家权威移动自己的角色，也不能顺带让他权威自己的**钱包、挂单或邮件**。
