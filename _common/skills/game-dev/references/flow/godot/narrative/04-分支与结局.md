# 04 分支与结局 `[narrative/04]`


⚠ 本功能点的核心风险不是"判错"，而是**"判对了但玩家永远到不了"**。

## 2. 工序

### Step 1　结局用判定表，不用 if elif　`[narrative/04#S1]`

【读】`howto/godot/narrative.md#3. 分支与多结局（核心）`

【做】
结局定义为数据记录：
`id` / `priority` / `conditions` / `flags_to_set` / `required_flags` / `incompatible_with`。

⛔ **`if elif` 链在分支少时看似清晰**，很快出现
优先级、重复条件、测试覆盖、策划改表四类问题。

【产出】
结局数据资源 + 判定器（先找全部满足 → 按优先级排序 → 处理冲突）。

【判据】
新增一个结局**不需要改判定器代码**，只加一条数据。

【审】`audit/godot/narrative.md#5`（结局写 if elif → 要判定表）

---

### Step 2　优先级显式配置　`[narrative/04#S2]`

【读】`howto/godot/narrative.md#3. 分支与多结局（核心）`

【做】
优先级必须显式配置，⛔ **不能依赖资源数组顺序**。
编辑器应检查**重复优先级**并提醒策划。
⚠ 优先级相同时按**稳定 ID 排序**，消除未定义行为。

【产出】
带 `priority` 字段的结局表 + 重复优先级检查。

【判据】
把两个结局的 priority 设成相同 → 判定结果**在多次运行中一致**（不抖动）。

【审】`audit/godot/narrative.md#6`（结局靠数组顺序 → 要显式优先级） `audit/godot/narrative.md#7`

---

### Step 3　冲突关系双向对称　`[narrative/04#S3]`

【读】`howto/godot/narrative.md#10. ⚠ 分支可达性要能自动验证`

【做】
`incompatible_with` 要检查**双向一致**：
A 写了排斥 B 但 B 没写排斥 A → 判定顺序不同会得到不同结果。

✅ 要么校验器补全为对称，要么**报出来要求显式写全**。

【产出】
对称性检查（或自动补全）。

【判据】
造一组单向冲突 → 校验器报出，或自动补全为双向。

【审】`audit/godot/narrative.md#27`（incompatible_with 单向写就行 → 要对称）

---

### Step 4　可达性验证　`[narrative/04#S4]`

【读】`howto/godot/narrative.md#10. ⚠ 分支可达性要能自动验证`

【做】
⚠ **"数据合法"不等于"玩家能到达"**：
所有 ID 都存在、条件语法正确，但某结局被另一个**永远先满足**的结局挡住
→ 玩家永远看不到它，而所有常规检查都是绿的。

两种验证：

| 方法 | 做法 | 能发现 |
|---|---|---|
| 静态遍历 | 枚举**影响结局的 flag** 全组合（其余取默认值），按判定器跑一遍 | 结局**从未命中** → 不可达 |
| 随机走查 | 模拟玩家随机选择跑 N 次，统计分布 | 结局**概率异常**（过难/过易） |

ⓘ 静态遍历在 flag 多时组合爆炸 →
✅ 只对影响结局的 flag 做全组合。

【产出】
可达性校验器，输出每个结局的命中次数。

【判据】
**每个结局至少有一条可达路径**。
⛔ 命中 0 次的结局要当 bug 处理，不是"玩家运气不好"。

【审】`audit/godot/narrative.md#8`（数据合法就能达成 → 还要查可达性）

---

### Step 5　"真结局"的可发现性　`[narrative/04#S5]`

【读】`howto/godot/narrative.md#3. 分支与多结局（核心）`

【做】
评估真结局**不看攻略能否触发**。

⚠ 这不一定是缺陷（有些设计就要这个效果），
⛔ 但必须是**有意识的决定**，不是"做完才发现没人能触发"。

【产出】
一份结论：真结局是"刻意隐藏"还是"需要补线索"，并写明理由。

【判据】
【审】`audit/godot/narrative.md#26`
对真结局的每个前置条件，都能指出**游戏内何处给了玩家线索**。
指不出 → 需要补线索。
