# 03 概率抽取与合规公示（商业化域）

> **本步交付**：服务端随机 + 保底持久化 + 概率同源公示
> **对应**：流程 `howto/godot/monetization.md` · 审核 `audit/godot/monetization.md`

## 0. 交付物定义

1. 随机与保底都在**服务端**，客户端只展示结果
2. 概率表与公示页**同源**，改一处两边同时变
3. 中国地区四件套齐全，抽取结果留存 ≥90 日

## 1. 前置检查清单

- [ ] 01 已完成（服务端权威）
- [ ] 已确认发行地区清单（决定适用哪套法规）
- [ ] 概率表已作为**单一数据源**存在（不是 Excel 一份、代码一份）

## 2. 工序

### Step 1　随机必须在服务器，客户端只展示　`[monetization/03#S1]`

【读】`howto/godot/monetization.md#4. 抽卡：随机与保底都在服务器`

【做】
抽取在服务端执行，客户端收到结果后播放表现。
⛔ 客户端 `RandomNumberGenerator` 算完再上报 —— 可被改，
且表现为"出货率异常高"，等运营发现时已经扩散。
⛔ 出货与未出货用同一套表现、同一强度的反馈 —— 玩家感知不到稀有度差异，
抽卡的全部意义在于**强度差异**，所有事件同一强度反馈会把最稀有的结果做得和平常一样。

【产出】抽取接口（入参：池 ID / 次数；出参：结果列表 + 保底计数）

【判据】断网时点抽卡，明确提示无法进行，⛔ 而不是先出结果再上报失败。

【审】`audit/godot/monetization.md#3`
【品】`craft/godot/cheapness.md#2. 反馈类廉价感`

### Step 2　保底（pity）计数存服务端　`[monetization/03#S2]`

【读】`howto/godot/monetization.md#4. 抽卡：随机与保底都在服务器`

【做】
保底计数与订单一样落在服务端存储，随账号不随设备。
⛔ 保底存本地 —— **清档即可绕过**，玩家永远抽不到保底，
且排查时会去查概率配表，不会想到持久化。

【产出】服务端保底字段 + 与账号绑定的存储

【判据】清空客户端数据后重新登录，保底计数仍是清档前的值。

【审】`audit/godot/monetization.md#4`

### Step 3　概率表与公示页同源，且可校验　`[monetization/03#S3]`

【读】`howto/godot/monetization.md#4. 抽卡：随机与保底都在服务器`

【做】
单一数据源的概率表，公示页由**同一份数据自动生成**。
⛔ 策划填一份 Excel、代码另写一份 —— 两边迟早不一致，
而公示不一致是**合规问题**，不是显示 bug。

【产出】同源概率表 + 自动生成的公示页

【判据】改一次概率表，公示页数字随之变化；跑一次校验脚本能证明二者一致。

【审】`audit/godot/monetization.md#11`

### Step 4　中国地区四件套逐项落地　`[monetization/03#S4]`

【读】`howto/godot/monetization.md#1. ⚠ 合规优先于体验`

【做】
四项全部实现：① 不得直接投入法定货币 / 虚拟货币参与随机（加**中间游戏币**层）；
② 公示名称 / 性能 / 内容 / 数量及**概率**；
③ 公布结果并**保存记录不少于 90 日**；
④ 提供**其他获取途径**（游戏币直接购买 / 兑换）。
⛔ 漏掉第 ④ 条 —— 这是最常见的"概率公示了但依然不合规"，
公示了概率，却没给玩家不靠抽就能拿到同性能物品的等价通道。

【产出】四件套检查表（每项一个可演示的功能）

【判据】四项都能在客户端演示出来，④ 能真的用游戏币买到同性能物品。

【审】`audit/godot/monetization.md#6`

### Step 5　抽取结果留存 ≥90 日且不可改　`[monetization/03#S5]`

【读】`howto/godot/monetization.md#2. 服务端必须校验的清单`

【做】
每次抽取写一条**只追加**的记录，含时间 / 池 / 结果 / 账号。
⛔ 只记"抽了多少次"不记结果 —— 合规要求的是**结果记录**，次数不够。
⛔ 记录可被后续 UPDATE 覆盖 —— 那就不是记录，⛔ 审计时无法自证。

【产出】抽取记录表（只追加）+ 保留策略（≥90 日）

【判据】构造一条记录后尝试修改，被拒绝；90 日前的记录仍可查出。

【审】`audit/godot/monetization.md#14`

### Step 6　每日抽取次数上限与 PRD 体验　`[monetization/03#S6]`

【读】`howto/godot/monetization.md#4. 抽卡：随机与保底都在服务器`

【做】
实装每日抽取次数上限（国内常见 50 次）；在真随机与 PRD 之间做选择并说明理由。
⛔ 只做保底不做次数上限 —— 上限是**低风险高信号量**的合规动作，成本极低。
⛔ 用真随机却期望"分布均匀" —— 真随机容易连续不出货，PRD 更平滑。

【产出】次数上限配置 + 随机分布方案的书面结论

【判据】达到上限后有明确提示；连续 200 次的分布曲线符合所选方案的预期。

【审】`audit/godot/monetization.md#29`

## 3. 参考实现

```gdscript
# ⓘ 承接本步产出：客户端只展示，不参与随机
# ⛔ 随机与保底必须在服务端，本地算即等于可被改
const MAX_DRAW_PER_DAY := 50

func _on_draw_pressed(pool_id: String) -> void:
    if _draws_today >= MAX_DRAW_PER_DAY:
        _show_limit_reached()
        return
    var result := await _server_draw(pool_id)   # ⛔ 断网要有终态提示
    if result.is_empty():
        return
    _play_gacha_animation(result)
```
