# 02 掉单、补单与本地单据（商业化域）

> **本步交付**：本地单据持久化 + 重启恢复 + 可重入补单
> **对应**：流程 `howto/godot/monetization.md` · 审核 `audit/godot/monetization.md`

## 0. 交付物定义

1. 本地单据在**发起支付之前**就落盘，进程外可恢复
2. 补单可重入：任何时刻中断，下次进入都能继续
3. 单据只有在服务端确认发货后才清除

## 1. 前置检查清单

- [ ] 01 已完成（幂等键与唯一索引生效）
- [ ] 本地单据有独立存储位置（`user://` 下单独文件）
- [ ] 补单入口在启动、切前台、设置页**三处**都可触发

## 2. 工序

### Step 1　本地单据先落盘，再发起支付　`[monetization/02#S1]`

【读】`howto/godot/monetization.md#3. ⚠ 掉单：最容易丢钱的 bug`

【做】
顺序写死为：本地记录 → 发起支付 → 服务端校验 → 发货 → 标记完成 → **最后**清本地单据。
⛔ 先发起支付再补写单据 —— 付完款、发货前崩溃，这笔钱**没有任何记录**，永远找不回。

【产出】本地单据结构（订单号 / product_id / 时间戳 / 状态）+ 落盘时机

【判据】在"发起支付"之后立刻杀进程，重启后仍能看到这笔未完成的单据。

【审】`audit/godot/monetization.md#8`

### Step 2　单据持久化到进程外，不能只在内存　`[monetization/02#S2]`

【读】`howto/godot/monetization.md#3. ⚠ 掉单：最容易丢钱的 bug`

【做】
单据写进 `user://` 下的独立文件，⛔ 不放在进程变量或 `Autoload` 的成员变量里。
⛔ 用 `OS.get_unique_id()` 加密单据 —— 官方注明该串重装后**会变**，
届时此前加密的单据将**无法解密**。

【产出】单据落盘实现 + 明确的存储路径

【判据】杀进程、清内存、重载后单据仍完整可读。

【审】`audit/godot/monetization.md#24`

### Step 3　补单要可重入，不能只在启动时跑一次　`[monetization/02#S3]`

【读】`howto/godot/monetization.md#3. ⚠ 掉单：最容易丢钱的 bug`

【做】
补单做成**可重入**的状态推进：启动时跑、切回前台时跑、
设置页给玩家一个"恢复购买"按钮。
⛔ 只在启动时跑一次 —— 那次恰好断网，这笔订单就**永久掉单**了。
⛔ 补单期间不允许再次触发 —— 网络慢时玩家点了没反应，以为坏了。

【产出】补单状态机 + 三个触发入口

【判据】补单进行中断网再联网，再次进入能继续，不会卡在中间态。

【审】`audit/godot/monetization.md#22`

### Step 4　区分"可重试失败"与"终态失败"　`[monetization/02#S4]`

【读】`howto/godot/monetization.md#2. 服务端必须校验的清单`

【做】
把服务端返回的错误分成三类：可重试（网络 / 超时）、终态失败（收据无效 / 黑名单）、
已发货（幂等命中）。
⛔ 统一当成"失败"并提示玩家重试 —— 已发货的订单被反复重试，
虽然幂等会拦住，但**玩家看到的是一直报错**。
⛔ 把终态失败也放进自动重试队列 —— 无效收据永远无效，永远重试成功不了。

【产出】错误分类表 + 每类的用户提示

【判据】构造三种错误，客户端表现两两不同，且没有一种提示玩家"请重试"却注定失败。

【审】`audit/godot/monetization.md#21`

### Step 5　单据只在服务端确认后清除　`[monetization/02#S5]`

【读】`howto/godot/monetization.md#3. ⚠ 掉单：最容易丢钱的 bug`

【做】
清除本地单据的**唯一**触发条件是服务端返回"已发货"。
⛔ 客户端本地标记"发货完成"就删单据 —— 服务端没收到确认，
下次补单找不到单据，这笔发货**再也不会发生**。
⛔ 补单成功立刻删单据但发货是异步的 —— 异步发货失败则永久丢失。

【产出】单据生命周期（创建 → 推进 → 确认 → 清除）

【判据】在"服务端确认"之前杀进程，单据仍在；之后杀进程，单据已清除且不再补单。

【审】`audit/godot/monetization.md#23`

## 3. 参考实现

```gdscript
# ⓘ 承接本步产出：本地单据先落盘，服务端确认后才清除
# ⛔ 顺序不可颠倒：先写单据再发起支付
const RECEIPT_PATH := "user://iap_pending.json"

func _save_pending(order: Dictionary) -> void:
    var f := FileAccess.open(RECEIPT_PATH, FileAccess.WRITE)
    f.store_string(JSON.stringify(order))
    f.close()          # ⛔ 不落盘则崩溃后无据可依

func _clear_pending(order_id: String) -> void:
    # ⛔ 唯一调用时机：服务端返回"已发货"
    DirAccess.remove_absolute(RECEIPT_PATH)
```

## 4. 验收清单

- [ ] 发起支付前单据已落盘
- [ ] 杀进程后单据可恢复
- [ ] 补单三处入口齐全且可重入
- [ ] 三类错误表现两两不同
- [ ] 单据只在服务端确认后清除

## 5. 常见返工

| 症状 | 原因 | 回到 |
|---|---|---|
| 玩家付了钱没到货、查不到单 | 单据写在支付之后 | S1 |
| 重启后 pending 空了 | 单据只在内存 | S2 |
| 补单卡住不动 | 只在启动跑一次 | S3 |
