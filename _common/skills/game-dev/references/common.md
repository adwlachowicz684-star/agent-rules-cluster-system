# 跨引擎通用：游戏开发流程与原则

引擎-specific 的内容在各自子目录（当前：`godot/`）。
本文件只写**换引擎也成立**的部分。

## 1. 拿到需求的正确顺序

```
1. 确认引擎与版本        ← 猜错整套方案作废，必须先问
2. 确认维度              ← 2D 还是 3D？单人还是联网？目标平台？
3. 定位功能域            ← scripts/dev-route.py --need="..."
4. 加载模板
5. 按项目约束调整        ← 模板是起点不是终点
6. 提示用户跑审查        ← 写完用 code-audit 检查
```

**最容易出错的是第 1 步和第 2 步**。用户说"做个跳跃"，
2D 平台跳跃和 3D 第三人称跳跃是两套完全不同的代码。

不确定就问，别猜。

## 2. 一些跨引擎成立的原则

### 手感优先于正确性

平台跳跃的"手感"来自几个反直觉的小机制，不是物理正确性：

| 机制 | 作用 |
|---|---|
| 土狼时间（Coyote Time） | 离开平台后 0.1s 内仍可跳，容忍玩家的反应延迟 |
| 跳跃缓冲（Jump Buffer） | 落地前按的跳会在落地瞬间生效 |
| 可变跳跃高度 | 松开跳键立刻削减上升速度，短按=小跳 |
| 加速度/摩擦分离 | 起停有过渡，不是瞬间到达最高速 |

这些物理上"不正确"，但没有它们游戏手感就是"黏"。

### 状态机优于 if 嵌套

角色状态一多（idle/run/jump/fall/attack/hurt/dash），
if 嵌套会变成灾难。用状态机：

```
状态枚举 → 每个状态一个 enter/update/exit → 明确的转换条件
```

Godot 侧可以直接用 `AnimationTree` 的 StateMachine，
或代码里 `match state:`。

### 数据与逻辑分离

```gdscript
# 反例：数值散落在代码里
velocity.y = -400.0
health -= 25

# 正例：可配置
@export var jump_velocity: float = -400.0
@export var damage: int = 25
```

好处：策划能自己调，不用改代码；也便于做难度曲线。

### 事件解耦优于直接引用

A 直接持有 B 的引用 → A 和 B 绑死，改一个另一个要跟着改。
用事件总线：A 发信号，谁关心谁订阅。

代价：信号连了要记得断（见各引擎文档的"常见漏写"）。

### 频繁生成/销毁的东西要池化

子弹、粒子、伤害数字。每帧 new 会产生 GC 压力，
表现为周期性卡顿（不是持续低帧，是一阵一阵的）。

## 3. 性能：先定位再优化

**不要凭感觉优化**。常见误判：

| 直觉 | 实际 |
|---|---|
| "节点太多了所以卡" | 节点数量本身很少是瓶颈，DrawCall 和脚本逻辑才是 |
| "贴图太大" | 通常是材质切换次数（合批被打断）而非单张尺寸 |
| "物理太重" | 先确认是不是每帧在做空间查询 |

**正确顺序**：跑 Profiler → 看是 Script / Render / Physics 哪一栏高
→ 针对性优化。搞反了会白优化。

## 4. 常见架构模式

| 模式 | 用途 | Godot 实现 |
|---|---|---|
| 单例/管理器 | 全局唯一（存档、音频、场景管理） | Autoload |
| 事件总线 | 跨系统解耦 | Autoload + signal |
| 状态机 | 角色/AI 状态管理 | `match` 或 AnimationTree |
| 对象池 | 频繁生成销毁 | 见各引擎文档 |
| 组件组合 | 能力拼装（可移动+可受伤+可交互） | 子节点 + 接口约定 |

## 5. 写完之后的检查

本 skill 给方案，**判定交给 code-audit**。

```bash
python3 ../code-audit/scripts/route.py --src=<根>       # 审查侧路由
```

最常见的三类漏写（跨引擎通用）：

1. **资源没配对**：申请/连接/创建之后没有对应的释放/断开/回收
2. **把易变值硬编码**：数值、路径、动画名写死在代码里
3. **每帧做本该事件驱动的事**：`_process` 里轮询输入、查找节点、重建文本
