# _骨架 —— 通用开发流程（兜底模板）

ⓘ **本文件是层内基础件，不是功能点**（下划线前缀 = 基础件）。
用途：**当一个域还没有细化功能点时，套这个骨架开工。**

⚠ **⛔ 不允许"没有流程就凭记忆开工"。** 110 个域里目前只有 2 个有细化流程，
其余 108 个全部靠本骨架兜底。

---

## 怎么用

```bash
python3 scripts/dev-route.py --src=<项目根> --need="你的需求"
# 若输出的域有 flow/<域>/00-域流程总览.md → 用那个（更贴合）
# 否则 → 套本骨架
```

套用时：把下面六步的 `<域>` 替换成你的域，并**打开对应的 howto 和 audit**：

| 需要 | 路径 |
|---|---|
| 查做法（代码、API、参数） | `howto/godot/<域>.md` |
| 过禁忌（做完后） | `audit/godot/<域>.md` |

ⓘ 骨架不是"随便做做"。它只是把细化流程里的领域特化部分抽掉后剩下的通用部分。
**任何细化后的功能点都应能映射回这六步**——映射不上的，通常是漏了"定契约"或"异常边界"。

---

## 0　定边界

【查】`howto/godot/<域>.md` 通读一遍（这步是整体阅读，不是查某节）

【做】写下三行，写在你的开发记录里：

```text
做什么：<一句话>
不做什么：⛔ <至少两条，明确排除>
验收标准：<可观测，不是"能跑">
```

⚠ **"不做什么"必须有至少两条。** 边界不清就开工，做出来的是另一个东西——
而且等到做完才发现时，返工量比写这两行大几个数量级。

【产出】一段边界声明

【判据】能把这三行念给另一个人听，对方能复述出同样的范围

---

## 1　定契约

【查】`howto/godot/<域>.md` 里关于数据结构 / 接口设计的章节

【做】定义：

- 数据结构（存什么、不存什么）
- 对外接口（函数签名 / 信号 / 节点结构）
- **产出物**：写成能指认的形式，⛔ 不能是"做完了"

```text
产出物示例：
  ✅ HitResolver.resolve(ctx) -> HitResponse ＋ hit_resolved 信号
  ⛔ 完成了伤害结算
```

⚠ 产出物要能被下游**按名字对接**。理由见 `structure.md` 第 5.2 节——
跨域组合时，"做完了"这种产出无法对接，是返工的主要来源。

【产出】数据结构定义 + 接口签名 + 产出物声明

【判据】下游开发者只看你的产出物声明，就知道怎么接

---

## 2　最小闭环

【查】`howto/godot/<域>.md` 里"最基础用法 / 快速上手"类章节

【做】跑通**最窄的一条路**：

- 只做主干，⛔ 不做异常
- ⛔ 不做优化
- ⛔ 不做配置化
- ✅ 目标是"证明这条路能走通"

【产出】一个能演示主干的最小场景

【判据】能当场演示，且**不需要解释就能看懂在做什么**

⚠ **最小闭环必须在异常之前。** 反过来（先写异常处理）会陷入
"异常写了一半、主干还没验证"的泥潭——而且此时出错你无法定位是主干的问题
还是异常处理的问题。

---

## 3　接外部

【查】`howto/godot/<域>.md` 里"与其他系统的关系 / 相关文档"章节

【做】与已有系统对接。逐个列出接缝：

| 接缝 | 上游产出 | 我这边期望 | 是否一致 |
|---|---|---|---|
| | | | |

⚠ **不一致的接缝要显式处理**（单独立一步适配），
⛔ 不要在各处偷偷转格式——那些转换会散落多处，以后改接口时找不到。
详见 `structure.md` 第 5.3 节。

【产出】接线完成 + 接缝清单

【判据】接缝清单里每一行都标注了"一致"或"已适配"

---

## 4　异常与边界

【查】`howto/godot/<域>.md` 的 ⚠ 提示章节（做法的前提）

【做】逐项过：

- 失败路径（输入非法、依赖缺失、资源不存在）
- 边界值（0、负数、极大值、空集合）
- 时序（重复调用、并发、暂停/恢复）
- ⚠ **状态是否可恢复**（出错后能否回到已知安全状态）

【产出】每种异常的处理 + 可观测的失败表现

【判据】⚠ **每种异常都能真的复现**，⛔ 不能"代码看起来是对的"

ⓘ 这一步最常被跳过，而 bug 几乎全在这里。"只测正常路径"等于没测。

---

## 5　验收 + 过 audit

【查】`audit/godot/<域>.md`（⚠ 这是必做项，不是可选）

【做】

1. 逐条过禁忌表，每条确认"我们是怎么避免的"
2. 跑第 0 步定下的验收标准
3. ⚠ 把实测参数**回填**，⛔ 不要留"示例值"

【产出】验收记录 + 回填后的参数

【判据】
- 禁忌表每条都能说出规避方式，⛔ 不能"应该没这个问题"
- 参数有实测值，能说出**怎么测出来的**
- 若这是大功能的一部分 → ⚠ **还要做集成验收**，各部件合格不等于拼起来能用
  （见 `structure.md` 第 5.5 节）

## 与细化流程的关系

一个域被细化成功能点后，**功能点应能映射回本骨架六步**：

| 骨架步 | 角色控制域对应 | 存档域对应 |
|---|---|---|
| 0 定边界 | `00-总览` 的三项决策 | `00-总览` 的四项决策 |
| 1 定契约 | — | `01-存档结构设计` |
| 2 最小闭环 | `01-移动基座` | `02-读写与原子落盘` |
| 3 接外部 | `03-相机跟随` `04-输入映射` | `05-云存档接入` |
| 4 异常与边界 | `02-跳跃手感`（边界时序） | `03-加密完整性` `04-迁移` |
| 5 验收 | `06-手感验收` | `06-全链路验收` |

⚠ **映射不上的骨架步 = 该域的盲区**。比如角色控制域没有独立的"定契约"步——
因为它的契约就是参数表，被并进了 00 和 06。这是可接受的，但要**知道它是有意的**，
⛔ 不是漏了。
