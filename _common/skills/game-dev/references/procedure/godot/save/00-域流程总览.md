# 存档域 — 流程总览

> **本域交付**：一个断电不坏、改档能发现、版本能升级、多端能同步的存档系统。
> **对应**：流程 `flow/godot/save-migration.md` `cloud-save.md` `security.md`
> 　　　审核 `audit/godot/save-migration.md` `cloud-save.md` `security.md`

⚠ **存档是唯一"出错就不可逆"的系统** —— 玩家进度没了不会重来，会直接流失。
所以本域的功能点顺序是按**风险**排的，不是按实现便利排的。

## 0. 先决定四件事

| 决策 | 选项 | 影响 |
|---|---|---|
| **存什么格式** | JSON / `ResourceSaver`(.res/.tres) / 二进制自定义 | 迁移难度、可读性、防改档 |
| **存哪** | `user://` | ⛔ 不要存 `res://`（导出后只读） |
| **要不要加密** | 明文 / `open_encrypted_with_pass` / 自定义 | 见 03 的警告 |
| **要不要云** | 纯本地 / 云存档 | 决定 05 是否要做、冲突策略 |

⚠ **格式一旦上线就很难换**：JSON 好迁移但好改；`.res` 紧凑但版本敏感。
✅ 推荐 **JSON + 自定义 `.save` 扩展名 + 版本头**。

## 1. 功能点拆解与依赖顺序

```text
01 结构设计 ── 02 读写与原子落盘 ──┬── 03 加密与完整性 ──┐
                                  └── 04 存档迁移 ───────┼── 06 全链路验收
                                       （依赖 01 02）    │
                                  05 云存档 ←────────────┘
```

| # | 功能点 | 前置 | 为什么这个顺序 |
|---|---|---|---|
| 01 | 存档结构设计 | 无 | ⚠ **版本头必须从第一天就有**——没有版本号的存档无法安全迁移 |
| 02 | 读写与原子落盘 | 01 | ⚠ 不原子落盘 = 断电即坏档，这是最贵的一类 bug |
| 03 | 加密与完整性 | 02 | 完整性要建立在正确的读写之上 |
| 04 | 存档迁移 | 01 02 | 迁移是对已有数据的操作 |
| 05 | 云存档接入 | 02 03 | ⚠ 云同步必然有冲突，本地不牢就同步会放大损坏 |
| 06 | 全链路验收 | 01–05 | 只有全做完才能端到端验 |

## 2. ⚠ 三个最容易做反的顺序

**① 先做云存档再做本地原子落盘。** 云同步会把本地的坏状态同步到所有设备，
一个断电损坏变成全设备损坏。✅ 本地必须先生死不坏。

**② 先加密再做完整性。** 加密不代表没被改——尤其 `open_encrypted_with_pass`
派生方式弱。✅ 完整性是独立一层。

**③ 到要改数据结构时才加版本号。** 那时线上已有无版本号的存档，
只能靠猜字段来迁移。⛔ **版本号是 01 的必做项，不是后期补丁。**

## 3. 每做完一个功能点必做

1. 跑该步验收清单，逐条打勾
2. ⚠ **存档域每条验收都要真的杀进程/改文件测**，⛔ 不能只测正常路径
3. 过对应 audit 坑表

## 4. 关键约束速记

⚠ 这些是贯穿全域的红线，各功能点会反复引用：

- ⛔ 存档路径必须是 `user://`，不是 `res://`
- ⛔ 落盘必须"临时文件 + 原子 rename"，不能直接写目标文件
- ⛔ 迁移前必须备份
- ⛔ 迁移必须链式单步（v1→v2→v3），不能跳版
- ⚠ 迁移后**必须重算完整性校验**，旧签名留在上面等于给出"已验签"的假象
