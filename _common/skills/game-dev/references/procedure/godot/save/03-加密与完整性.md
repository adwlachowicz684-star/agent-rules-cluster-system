# 03 加密与完整性（存档域）

> **前置**：[02-读写与原子落盘](02-读写与原子落盘.md) 已验收
> **本步交付**：能**发现被改**、能**发现损坏**的存档（以及恰当的加密）
> **对应**：流程 `flow/godot/security.md` `save-migration.md` · 审核 `audit/godot/security.md`

⚠ **先分清两件事**：

| | 防什么 | 手段 |
|---|---|---|
| **完整性** | 文件损坏 / 被改 | 校验和 / HMAC |
| **机密性** | 被看见 / 被读 | 加密 |

⚠ **加密 ≠ 防改**。这是最容易混淆的一点。

## 0. 交付物定义

1. 手动改一个数值 → **游戏能发现**（不是静默接受）
2. 文件截断/损坏 → **能发现并退到 .bak**
3. 明确知道自己的加密强度属于哪一档（⛔ 不夸大）

## 1. 前置检查清单

- [ ] 02 已完成，读写是原子的
- [ ] ⚠ 已理解"加密不防改"
- [ ] 已决定是否需要真防作弊（单机还是联网）
- [ ] ⚠ 已知道 `FileAccess.open_encrypted_with_pass()` 的局限（见 Step 2）

## 2. 工序

### Step 1　加完整性校验

【做】
```gdscript
# 计算 JSON 的 SHA-256（或 HMAC）
var body := JSON.stringify(data.to_dict())
var ctx := HashingContext.new()
ctx.start(HashingContext.HASH_SHA256)
ctx.update(body.to_utf8_buffer())
var digest := ctx.finish()
```

⚠ **用 HMAC 而不是裸哈希**（若你希望玩家不能自己重算校验）：
`HashingContext` 支持 HMAC 模式（需提供密钥）。
ⓘ 裸 SHA-256 只能防"意外损坏"，**防不住有意改档**。

【产出】存档带校验值

【判据】手动改一个字节 → **校验失败**

### Step 2　⚠ 加密：先认清这一档的强度

【做】Godot 提供 `FileAccess.open_encrypted_with_pass(path, mode, pass)`

⚠ **官方说明它是"AES-256 但不安全"**：
- 加密本身是 AES-256 CFB + 随机 IV + 完整性校验
- ⛔ **但密钥派生是 `MD5(password)` 一次**，⛔ **无盐、无迭代**
- → 可离线批量猜密码；⛔ **不能当安全边界**

✅ 它的合理用途：**提高改档门槛、防止随手用文本编辑器改**，⛔ 不是真防作弊。

⚠ **若密码硬编码在客户端，等于没加密** —— 逆向能直接拿到。
✅ 单机游戏用它挡住"随手改"就够了，**不要声称安全**。

【产出】加密（或不加密）的决策 + 记录理由

【判据】能说清"我们防到什么程度"，⛔ 不能说"加密了所以安全"

### Step 3　校验放在哪

【做】推荐结构：
```json
{ "magic": "...", "save_version": 1, "checksum": "hex...", "payload": {...} }
```
⚠ **先算 payload 的校验，再整体加密**；
⛔ 顺序反了（先加密后算明文校验）会导致每次加密结果不同、校验永远对不上

【产出】带校验的存档格式

【判据】同样的内容存两次：⛔ **加密后字节不同**（IV 随机），但**都能通过校验**

### Step 4　⚠ 校验失败的处理（关键决策）

【做】明确策略：

| 情况 | 处理 |
|---|---|
| 校验失败但 `.bak` 有效 | ✅ 退到 `.bak`，提示玩家"存档损坏，已恢复上一次" |
| 校验失败且 `.bak` 也坏 | ⛔ **不要静默新建空档**（玩家以为进度没了）→ 明确提示 + 保留损坏文件供申诉 |
| 单机玩家自己改档被发现 | 提示 + 退备份（⛔ 不要无提示重置，会让人以为游戏有 bug） |

⚠ **绝不能"检测到改档就直接清空存档"** —— 校验误判（比如你自己改格式忘记更新）
会毁掉所有玩家的进度。

【产出】校验失败的处理流程

【判据】人为破坏校验 → 看到预期提示，**损坏文件仍保留在磁盘上**

### Step 5　不要把密钥写进存档

【做】密钥/盐若需要，走编译期常量或平台 keystore

⛔ **不要存在存档里** —— 那等于把锁和钥匙放一起

【产出】密钥管理方案

【判据】dump 存档文件，grep 不到密钥

## 3. 参考实现

```gdscript
# save_crypto.gd — Godot 4.x
const HMAC_KEY := "…"   # ⚠ 仅提高门槛；客户端内置 = 可逆向，不是安全边界

static func hmac_sha256(body: String, key: String) -> String:
    var ctx := HashingContext.new()
    ctx.start(HashingContext.HASH_SHA256, key.to_utf8_buffer())
    ctx.update(body.to_utf8_buffer())
    return ctx.finish().hex_encode()

static func wrap(data: Dictionary) -> String:
    var payload := JSON.stringify(data)
    return JSON.stringify({
        "magic": SaveData.MAGIC,
        "save_version": data.get("save_version", 0),
        "checksum": hmac_sha256(payload, HMAC_KEY),
        "payload": payload,
    })

static func unwrap(text: String) -> Dictionary:
    var outer = JSON.parse_string(text)
    if outer == null or not (outer is Dictionary):
        return {}
    if outer.get("magic", "") != SaveData.MAGIC:
        return {}                       # ⚠ 不是我们的文件
    var payload := outer.get("payload", "") as String
    if hmac_sha256(payload, HMAC_KEY) != outer.get("checksum", ""):
        return {}                       # ⚠ 校验失败 → 调用方退 .bak
    var inner = JSON.parse_string(payload)
    return inner if inner is Dictionary else {}
```

## 4. 验收清单

- [ ] 改一个字节 → 校验失败
- [ ] 截断文件 → 校验失败
- [ ] 校验失败 → **退到 `.bak`** 而不是清空
- [ ] 校验失败且 `.bak` 也坏 → **保留损坏文件**，明确提示
- [ ] ⛔ 没有"检测到改档就清空存档"的逻辑
- [ ] 同样内容存两次：字节不同但**都能过校验**
- [ ] dump 存档 grep 不到密钥
- [ ] ⚠ 能说清自己防到什么程度（⛔ 不能声称"加密了所以安全"）
- [ ] 完整性校验**独立于加密**（去掉加密后校验仍工作）

## 5. 常见返工

⚠ **以为加密就防改** —— 改密码后重算即可绕过。完整性是独立一层。

⚠ **先加密后算校验** —— 随机 IV 导致每次密文不同，校验永远对不上，
表现为"存档偶尔读不出来"，极难排查。

⚠ **检测到改档就清空** —— 一旦校验逻辑有 bug（比如你改了格式忘了同步），
会毁掉全量玩家存档。**这是不可逆事故。**

⚠ **密钥写进存档或硬编码还声称安全** —— 逆向几小时就能拿到。

⚠ **HMAC 密钥与存档一起分发** —— 同上。
