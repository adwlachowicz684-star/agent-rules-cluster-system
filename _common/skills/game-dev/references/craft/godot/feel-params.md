# 手感参数：带区间的技艺值（Godot 4.x）

ⓘ **本册的性质**：这里的值**不是官方数值，是行业经验区间**。

与 howto 层的区别：howto 写"这个 API 怎么用、有什么坑"，那些是**可核实的事实**；
本册写"这个参数该给多少"，那些是**没有标准答案的取舍**。

⛔ **不要把本册的值当成官方口径引用**。需要官方口径时查 howto。

---

## 0. 怎么用这张表

每个参数给四样东西，缺一样就不算写完：

| 项 | 作用 |
|---|---|
| **区间** | 常见取值范围 |
| **选哪端** | 什么类型的游戏取大、什么取小 |
| **失效形态** | 给太大/太小分别"看起来像什么 bug" |
| **调法** | 怎么在 30 秒内试出合适值 |

⛔ **只抄中间值是最差的做法**。区间两端的游戏体验是不同的，取中值等于
两边都不讨好——表现为"说不上哪里不对，但就是不够爽"。

ⓘ 调参的总原则：**先设到明显过大，再往下收到"刚好不别扭"**。
从过小往上加永远加不到位，因为轻微的不足不容易被察觉，而轻微的过量很明显。

## 1. 土狼时间（Coyote Time）

| | |
|---|---|
| **区间** | **80 – 150 ms**（平台跳跃） |
| **选哪端** | 精确平台（蔚蓝、超级肉肉哥）取 **80–100**；休闲平台取 **130–150** |
| **失效（过大）** | ⛔ 角色离开地面很久还能跳 → 玩家会觉得"我明明掉下去了怎么还能跳"，**失去掌控感** |
| **失效（过小）** | ⚠ 玩家觉得"我按了没跳"，但说不清是自己的问题还是游戏的——**这类抱怨最难归因** |
| **调法** | 站在平台边缘反复走出-起跳，逐步加大直到"明显太宽容"，再减 20ms |

⛔ **土狼时间不能靠 `is_on_floor()` 自然实现**——离开地面的那一帧就返回 false 了。
必须记录"上次着地时间"，判 `now - last_grounded < coyote_ms`。

ⓘ 一个常见错法：用**帧数**而不是时间。物理帧 60 TPS 下 8 帧 ≈ 133ms 看着没问题，
但导出到 144Hz 设备或开了物理插值后，**手感随帧率变化**。

## 2. 跳跃缓冲（Jump Buffer）

| | |
|---|---|
| **区间** | **100 – 200 ms** |
| **选哪端** | 节奏快的动作游戏取 **100–120**（太长会"提前跳"）；物理解谜取 **180–200** |
| **失效（过大）** | ⛔ 玩家在空中按了跳，落地瞬间自己跳起来 → **像是输入粘住了** |
| **失效（过小）** | ⚠ 与土狼时间过小的失效形态**几乎一样**，两者容易互相掩盖 |
| **调法** | 落地前 300ms 按跳，逐步加大到"提前太多"，再减 30ms |

⛔ **缓冲必须在 `_physics_process` 里消费**，写在 `_process` 里会因帧率不同
导致实际缓冲时长漂移（见 howto `howto/godot/platformer-feel.md`）。

ⓘ 与土狼时间的分工：土狼时间管"离开地面后还来得及"，缓冲管"落地前按了算数"。
⛔ **两者都设成最大值会让游戏变得很"滑"**——所有操作都成功，反而没有精准感。

---

## 3. 可变跳跃高度（Variable Jump Height）

| | |
|---|---|
| **区间** | 轻点跳高度 = 按住跳高度的 **40% – 60%** |
| **选哪端** | 精确平台取 **40%**（区分度大，需要精细控制）；休闲向取 **60%** |
| **失效（区分度不足）** | ⛔ 轻点与按住高度接近 → **这个机制等于没做**，但代码在跑、检查全绿 |
| **失效（截断过狠）** | ⛔ 松手立刻停 → 像撞到天花板，很突兀 |
| **调法** | 轻点与按住各录一次量最高点，逐步调 `CUT_SPEED` 让比值落进区间 |

⛔ **截断不是归零**：`velocity.y = 0` 会让角色"急停"。
正确写法是 `velocity.y = maxf(velocity.y, -CUT_SPEED)` —— **保留一部分上升速度**。

ⓘ `CUT_SPEED` 的量级参考：约为 `jump_velocity` 的 **25% – 40%**
（`jump_velocity` 420 时，约 **-100 到 -170**）。

⚠ **改了跳跃高度要重测跳距**：关卡按原高度设计的跳距会全部失效。
⛔ 这是"调手感调出关卡 bug"的典型路径 —— 手感调好了，关卡变得过不去。

## 4. 顿帧（Hitstop / Freeze Frame）

| | |
|---|---|
| **区间** | 轻击 **30–80 ms** · 重击 **100–200 ms** · 必杀/处决 **200–350 ms** |
| **选哪端** | 写实向取小（顿帧会破坏"真实感"）；卡通/横版取大 |
| **失效（过大）** | ⛔ 连击时变成幻灯片 → **连击越打越卡**，玩家会以为掉帧 |
| **失效（过小）** | ⚠ 打上去"没分量"，像打在棉花上 |
| **调法** | 单次调到"明显卡"，再减半 |

⛔ **顿帧的实现方式决定了会不会出 bug**：

- ✅ **缩放时间**（`Engine.time_scale` 设 0 附近，或 `delta *= 0`）—— 安全
- ⛔ **挂起主线程**（`OS.delay_msec`）—— 会连带卡住音频与网络，**联机时必然出问题**

⚠ 联机时顿帧**只影响本地表现**，不能影响权威模拟。用 `time_scale` 会影响
`_physics_process` 的调用节奏，所以多人项目通常**只冻结动画与特效、不冻结物理**。

ⓘ 顿帧的价值不在"卡"，而在**把打击的瞬间从连续时间里切出来**。给太多会廉价，
给太少没有——关键是要**分层**（轻/重/必杀不同），一刀切的顿帧立刻显得廉价。

## 5. 屏幕震动（Trauma 模型）

| | |
|---|---|
| **区间** | trauma 增量：小事件 **0.1–0.2** · 中 **0.3–0.4** · 大 **0.6–0.8** |
| **衰减** | **1.5 – 3.0 / 秒**（快节奏取大） |
| **映射** | ⛔ **必须平方或立方**（`shake = trauma²`），线性映射的震动"很机械" |
| **失效（过大）** | ⛔ 玩家看不清画面 → 晕动症投诉 |
| **失效（过小/线性）** | ⚠ 像"画面在抖"而不是"世界在震" |

⛔ **不要用 `randf()` 每帧直接改相机位置**——那是抖动不是震动，
表现为高频噪点式的位移，**看一眼就知道是没调过的**。

ⓘ 正确模型：维护一个 `trauma`（0–1），每帧 `trauma -= decay * delta`，
位移量 `= max_offset * trauma² * noise(t)`。用 `FastNoiseLite` 取噪声比 `randf` 平滑。

⚠ 平移与旋转**要分开配**：平移幅度大、旋转幅度小。等量的旋转会让人晕。

## 6. 输入到画面的延迟预算

| | |
|---|---|
| **区间** | **< 100 ms** 感觉"即时" · **100–150 ms** 可察觉但可接受 · **> 150 ms** 明显迟钝 |
| **失效** | ⛔ 超过 150ms 时玩家会说"这游戏手感很差"，但**说不出是延迟**——会归咎于角色速度或重力 |

ⓘ 延迟的四个来源，按贡献排序：显示（显示器/垂直同步）> 物理帧 > 输入轮询 > 逻辑。

- ⛔ **物理帧 60 TPS 本身就贡献 16.7ms 平均延迟**，动作游戏提到 120 TPS 是常规做法
- ⚠ 垂直同步在低刷屏上会贡献整整一帧，**输入延迟预算能被它单独吃掉**

## 7. 相机跟随阻尼

| | |
|---|---|
| **区间** | 平滑系数 **5 – 15**（`lerp` 或 `damp` 的速率） |
| **选哪端** | 快节奏动作取 **10–15**（几乎硬跟）；探索类取 **5–8**（有余韵） |
| **失效（过硬）** | ⚠ 角色高速移动时画面"钉死"，缺少速度感 |
| **失效（过软）** | ⛔ 角色跑出画面边缘 → **玩家看不到自己在哪**，这是最严重的一类 |

⛔ **阻尼必须用帧率无关的方式写**。`lerp(a, b, 0.1)` 每帧调用在 144Hz 下
比 60Hz 快得多——表现为"高刷屏上相机更硬"。正确写法用 `exp(-rate * delta)`。

ⓘ 前瞻（look-ahead）：朝移动方向偏移 **1–3 米** 是行业惯例，超过 3 米会让玩家
看不到身后，被偷袭时无法反应。

---

## 8. 命中反馈的四个要素

打击感不是"特效加得越多越好"，是**四个要素的时间对齐**：

| 要素 | 时长 | 要点 |
|---|---|---|
| 顿帧 | 30–200 ms | 见上 |
| 屏震 | 100–300 ms | 见上 |
| 粒子/闪白 | **闪白 2–4 帧**（不是 100ms，是按帧算） | ⛔ 超过 4 帧像"曝光过度" |
| 音效 | 立即，不晚于画面 **1 帧** | ⛔ 音效晚于画面是最容易被察觉的廉价感来源 |

⛔ **闪白按帧算而不是按秒算**：60fps 下 3 帧 = 50ms，144fps 下 3 帧 = 21ms。
按毫秒写会在高刷屏上闪得太久。

ⓘ 四要素**叠加而非加量**：把顿帧从 80ms 加到 300ms 不会更爽（会变卡），
但"顿帧 + 2 帧闪白 + 轻微屏震"的组合远强于单一要素拉满。

## 9. 顶点悬停（Apex）

| | |
|---|---|
| **区间** | 顶点附近重力 **×0.4 – ×0.7** · 判定窗口 **±50–150 ms** |
| **选哪端** | 需要空中微调的取 **0.4**（明显滞空）；写实向取 **0.7** |
| **失效（过大）** | ⛔ 角色"飘"，像月球重力 |
| **失效（过小）** | ⚠ 做了等于没做 |

⚠ 判定用**速度接近 0** 而不是高度：`abs(velocity.y) < threshold` 比
判断"是否到达最高点"稳定——后者需要用导数，会抖。

---

## 10. 一个总判据

> **手感参数的正确值，是"玩家注意不到它存在"的那个值。**

⛔ 玩家一旦注意到某个参数，通常意味着它**过量**了。
土狼时间被察觉 = 太宽容；屏震被察觉 = 太晃；顿帧被察觉 = 太卡。

ⓘ 唯一的例外是**玩家主动要求**的：难度选项里放"辅助宽容度"滑块，
让玩家自己调土狼时间和缓冲——这时被察觉是设计意图。

| 项 | 怎么验 |
|---|---|
| 顿帧时长是否随帧率变化 | 用 `howto/godot/timescale.md` 的做法，在 30/60/144 fps 下各测一次实际时长 |
| 屏震平方映射的实际观感 | 录屏逐帧看位移曲线是否平滑衰减 |
| 相机阻尼的帧率无关性 | 强制 30fps 与 144fps 跑同一段路，比较相机轨迹 |
