# backend-stability — 反模式清单（审核用）

> 本文件**只写「不能怎么做」**，用于流程结束后审核自己的产出、约束边界。
> 「怎么做」见同 skill 的流程部分：`howto/godot/backend-stability.md`
>
> 边界：本篇是**稳定性与事故响应**。运营侧（A/B、灰度、补偿）见 `audit/godot/ops.md`。

## 常见坑

| # | 本能以为 | 实际 |
|---|---|---|
| 1 | 上线前压一次就够 | 韧性是四层能力；**无超时+无限流+无熔断+无界重试**会把抖动放大成雪崩 |
| 2 | 限流算法随便选 | 按"允许突发/允许排队"选；固定窗口**边界两倍尖峰** |
| 3 | burst 设大点没关系 | 退化成"偶尔超售"；漏桶队列无限长会 **OOM** |
| 4 | 限流返回 500 或断开 | 要状态码+业务码+提示+`Retry-After` |
| 5 | 登录限流提示"账号或密码错误" | 那是给攻击者的**账号枚举能力** |
| 6 | 熔断只看异常数 | **不统计超时会把"永不返回"当健康** |
| 7 | 所有调用共用一个熔断阈值 | 登录/支付/发货/战斗结算代价不同，要**按类型拆** |
| 8 | Half-open 全量放行 | 会把刚恢复的依赖**再次打挂** |
| 9 | 降级就是隐藏报错 | 是**产品预先批准**的能力降级，要有可见表现与自动关闭条件 |
| 10 | SSH 改生产配置挺快 | 不应是常规路径，开关要正式发布 |
| 11 | 超时设短点更安全 | 太短会让长尾请求反复重试；要按 **P99.9** 校准 |
| 12 | 所有失败都重试 | 参数校验/权限/幂等冲突**不可重试** |
| 13 | 固定间隔重试 | 要**退避 + 抖动**；且 jitter 要覆盖**首次重连** |
| 14 | 重试不用幂等键 | 重试支付只是把重复发货风险换成一次失败 |
| 15 | 只在网关重试就够 | 三层叠加可把单次失败变 **27 倍**压力 |
| 16 | 早点分库分表 | **过早分片**把索引优化变成跨库事务与运维重构 |
| 17 | 分片键选分布均匀的 | 要**贴合访问路径**；选错会每次扫全分片 |
| 18 | 看集群均值就行 | 选错的表现是"均值很低但**某分片持续报警**" |
| 19 | 读写分离解决性能 | 只降读压力，**不消除复制延迟** |
| 20 | 缓存穿透/击穿/雪崩一回事 | 三种现象三种解法，必须分开治理 |
| 21 | TTL 固定值 | 要加**随机抖动**，否则成批过期 = 雪崩 |
| 22 | 大表 DDL 低峰手工执行 | 要审查锁模式+回滚步骤，⛔ 禁止手工粘长 SQL |
| 23 | 容量 = 峰值 QPS × 2 | 要从业务事件推全链路；还要算扇出与连接数 |
| 24 | 只测稳态 QPS | 要测**受控失败**：冷启动、击穿、单节点故障、扩容全程 |
| 25 | 自动扩容能救场 | 扩容 5 分钟而峰值 3 分钟到 → **扩容即事故原因** |
| 26 | 有 CPU/内存仪表盘就够 | 那是资源视图，**不能证明玩家体验** |
| 27 | 告警越多越安全 | **告警疲劳会拉长发现时间**，真事故被埋没 |
| 28 | 告警动作写"登录看看" | 说明层级或自动化不足，应降级或删除 |
| 29 | 事故定级靠领导判断 | 要写**明确触发条件与自动升级**规则 |
| 30 | 找到根因再恢复 | **先恢复再查根因**；止损与定位是两个目标 |
| 31 | 告警不响了就是恢复 | 要**指标回到 SLO 内**，且观察一个完整业务周期 |
| 32 | 复盘写"下次注意" | ⛔ 每项行动要**可验证**且有人有期限 |
| 33 | 3-2-1 备份 = 灾备 | **副本数量不能证明能恢复**；要演练验证 |
| 34 | RPO/RTO 基础设施定 | 必须来自**业务容忍度**（支付不能丢，客服可小时级） |
| 35 | 上多活就更可靠 | 有复制延迟、冲突、成本与合规边界，**不是免费升级** |
| 36 | 出问题回滚数据库 | **数据回滚常不可行**，主路径是向前修复 |
| 37 | 客户端固定间隔重连 | 会形成**雷鸣群**；要 jitter |
| 38 | 客户端能判定服务健康 | ⛔ 不能，也不能自行切服务器 |

## 审核时逐条问自己

1. 每一次外部调用都有**超时**吗？重试带**退避与抖动**吗？带**幂等键**吗？
2. 熔断统计里包含**超时**吗？阈值按调用类型拆分了吗？
3. 每一档降级有没有写**玩家可见表现**与自动关闭条件？
4. 限流的返回能被客户端正确区分（安全风控 / 容量限流 / 服务故障）吗？
5. 分片键贴合主要访问路径吗？有没有**按分片**看指标而不只看均值？
6. 容量模型算了**扇出与连接数**吗？压测覆盖了冷启动与扩容全程吗？
7. 扩容时间是否短于峰值到达时间？有没有预热与预留？
8. 每条 page 级告警都有**唯一一组可执行动作**吗？过去 90 天真触发过吗？
9. 事故分级是写死的触发条件还是靠人判断？
10. 回滚预案是**可执行步骤**还是一句话？有没有由第二人复核并演练过？
11. 备份**最近一次恢复演练**成功了吗？实际 RTO 记录了吗？
12. 断线重连带 jitter 吗？重连后战斗/房间/输入一致性谁负责恢复？
