# sharding-matchmaking — 反模式清单（审核用）

> 本文件**只写「不能怎么做」**，用于流程结束后审核自己的产出、约束边界。
> 「怎么做」见同 skill 的流程部分：`flow/godot/sharding-matchmaking.md`

## 常见坑

| # | 本能以为 | 实际 |
|---|---|---|
| 1 | Godot 有分服/匹配 API | **一个都没有**，全在服务端 |
| 2 | 隔离的是玩家身份 | 隔离的是**服务边界**，账号/订单是全局的 |
| 3 | 各服自增 ID 能跨服用 | 会**撞车**，要全局唯一 ID（雪花/服ID+自增） |
| 4 | 合服直接改数据 | 要**快照→dry-run→幂等迁移→保留回滚** |
| 5 | 合服重名自动处理 | 要加后缀或让玩家改名 |
| 6 | 邮件附件领取不用幂等 | 与补偿同理，会**重复发放** |
| 7 | 邮件不会满 | **满了补偿发不出去**，玩家以为没发 |
| 8 | 邮件不会过期 | 要处理**过期**与容量上限 |
| 9 | Elo 够用 | 活跃度不均要 **Glicko-2**，复杂团队要 TrueSkill 2 |
| 10 | 匹配可以在客户端算 | 必须**服务端** |
| 11 | 匹配池不用分层 | 要按**等待时间逐步放宽**分数范围 |
| 12 | 组队分数取平均就行 | 要看产品目标（平均/最高/加权） |
| 13 | 统计用客户端时间 | 可改，要 **UTC + 服务端接收时间**为主口径 |
| 14 | 昨天的数不会再变 | 有离线补发与批处理，**报表要能回溯** |
| 15 | 各端事件名随便起 | 要**事件字典统一**，否则无法分析 |
