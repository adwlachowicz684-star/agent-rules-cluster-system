# sharding-matchmaking — 反模式清单（审核用）

> 本文件**只写「不能怎么做」**，用于流程结束后审核自己的产出、约束边界。
> 「怎么做」见同 skill 的流程部分：`flow/godot/sharding-matchmaking.md`

⚠ **一句话**：合服是**带在线写入的全局状态迁移** —— 停服只是把问题简化成离线迁移；
真正难的不是搬数据，而是**证明每一行资产、关系、引用与业务语义都对得上**，且失败时能退回已知安全点。

## 常见坑

| # | 本能以为 | 实际 |
|---|---|---|
| 1 | Godot 有分服/匹配 API | **一个都没有**，全在服务端 |
| 2 | 隔离的是玩家身份 | 隔离的是**服务边界**，账号/订单是全局的 |
| 3 | 各服自增 ID 能跨服用 | 会**撞车**，要全局唯一 ID |
| 4 | 雪花 ID 配好就行 | ⚠ **NTP 回拨会复用已用时间段**；机器位要租约分配 |
| 5 | 序列号耗尽就调位宽 | ⛔ **改位宽是不兼容协议变更**，必须灰度 |
| 6 | 合服直接改生产库 | ⛔ 要**影子库 dry-run**，失败无法安全回退 |
| 7 | dry-run 用生产只读库 | ⛔ 必须**生产备份恢复的副本**，且同一一致性快照 |
| 8 | dry-run 报"无冲突"是好事 | ⚠ **要反过来查选择器是否漏表**，不是庆祝 |
| 9 | 未列出的表默认复制 | ⛔ **默认"冻结写入但暂不迁移"** |
| 10 | ID 映射主键加偏移量 | ⛔ 会破坏协议字段、缓存键、日志 join、历史订单引用 |
| 11 | 映射表用完可删 | ⛔ 是**永久审计数据** |
| 12 | 先迁移再冻结 | ⚠ 顺序反了；**GM/客服/定时任务/消费者/补偿脚本都要冻结** |
| 13 | 停客户端入口就够了 | ⛔ 后台系统仍在写库 |
| 14 | 大事务一次 INSERT 更快 | ⛔ 会打爆 DB；要小批次 + 限流（按**目标库写压力**） |
| 15 | 迁移中断从头重跑 | ⛔ **要检查点续跑**，IN_PROGRESS 批次查"已写到哪个源主键" |
| 16 | 总额对账通过就开服 | ⛔ 只证明没大规模丢失，**不证明业务正确** |
| 17 | 随机抽样几张表 | ⛔ 要**沿玩家旅程**走 + 八类专门样本（重名/会长/待领附件…） |
| 18 | 能登录就能开服 | ⚠ 不够；要运维和 QA **双签核** |
| 19 | 开服后出错就 restore | ⛔ **会抹掉真实对局/交易/充值，构成二次事故** |
| 20 | 单点错误也整体回滚 | ⛔ 优先**正向补偿 + 单玩家修复 + 审计单** |
| 21 | 回滚能回到停服时刻 | ⛔ 只能回到"数据仍是内部一致状态" |
| 22 | 重名加后缀无代价 | ⚠ 玩家失去原名、搜索变、可能近似冒充；要改名卡 |
| 23 | "原服优先"保留名字 | ⛔ 被合并服玩家会永久感到降级 |
| 24 | 公会可以合并余额 | ⛔ **保留独立账本** —— 公会含权力与资产 |
| 25 | 好友存单向边 | ⛔ A 有 B 但 B 没有 A → 骚扰与社交攻击；**双向成功才算批次提交** |
| 26 | 排行榜上下拼接 | ⛔ 会制造错误名次；要**按同一赛季/规则/截止时间重算** |
| 27 | 拍卖行订单一起迁移 | ⛔ 要先进入**禁止上新与结算期**，否则双重结算 |
| 28 | 跨服两边都写 | ⛔ **一次请求只能有一个写者** |
| 29 | 过期镜像值静默当最新 | ⛔ 要**标记"可能过期"**，尤其资产/封禁/比赛资格 |
| 30 | 匹配可以在客户端算 | ⛔ **必须服务端**；客户端⛔ 不能携带段位/分数/战绩 |
| 31 | 重复入队创建第二个排队项 | ⛔ 要返回当前队列状态 |
| 32 | 等待太久就无限放宽 | ⛔ 三条曲线同时恶化（偏差/延迟/可信度） |
| 33 | 队伍分取最高 | ⛔ **会被高分带小号操纵** |
| 34 | 队伍分取平均 | ⚠ 高手被拖累"带不动" |
| 35 | 排位塞伪装人类的 Bot | ⛔ **玩家信任问题**；排位/锦标赛默认不允许 |
| 36 | 故意掉分是玩家自由 | ⛔ 是 **ranked manipulation**，平台已明确处罚 |
| 37 | 单次掉线就封号 | ⛔ 惩罚要递增；掉线期间**必须允许重连且不允许重放同一局** |
| 38 | 赛季重置把分清零 | ⛔ 技能估计与匹配混乱**不能靠清零消除**，要软重置/衰减 |
| 39 | 邮件"已领"用一个 boolean | ⛔ 无法支持部分领取、并发、审计、回滚 |
| 40 | 附件领取直接发资产 | ⛔ 要**先 UNCLAIMED→CLAIMING 占状态**，只有更新成功的一笔入账 |
| 41 | 客户端超时就重试扣发 | ⛔ 要**重新查询状态**；部分到账比领取失败更危险 |
| 42 | 满箱就拒绝所有邮件 | ⛔ **维护补偿/付费返还/官方承诺不能被满箱阻断** |
| 43 | 全服补偿一次性插全量记录 | ⛔ 要**模板 + 资格计算 + 分批展开**，读取时生成 + 唯一键去重 |
| 44 | 重发就重新向所有人插入 | ⛔ 只重放**失败批次** |
| 45 | 邮件过期只有一个规则 | ⚠ 要**两层**：领取后相对过期 + 邮件绝对过期 |
| 46 | 客户端时间可作主口径 | ⛔ **服务端接收时间才是**；客户端时间只用于本地体验 |
| 47 | 统一 UTC = 所有自然日用 UTC | ⛔ 要**三种日切**（技术/玩家本地/运营活动日切） |
| 48 | 昨天报表变了就改缓存 | ⛔ **默认答案是重算**，不是改旧报表 |
| 49 | Kafka exactly-once = 业务 exactly-once | ⛔ 事务边界、幂等 sink、业务主键**仍须设计** |
| 50 | 字段改名在查询层翻译 | ⛔ 要**保留旧 reader**，不能让 2025 的 `gold` 变成 2026 的 `soft_currency` |

## 审核时逐条问自己

1. 有没有任何"分服/匹配"逻辑跑在客户端？
2. 全局 ID 生成器是否抗时钟回拨？机器位是否唯一？
3. 合服是否在**影子库**跑过 dry-run？冲突报告有八张子表吗？
4. 冻结清单是否覆盖 GM/客服/定时任务/消费者/补偿脚本？
5. 迁移脚本是否可重入、可续跑？
6. 校验是总额对账还是**玩家旅程对账**？有没有八类专门样本？
7. 开服后出错的第一反应是 restore 还是**正向补偿**？
8. 重名方案是否预先公告？所有显示名/索引/备注/收件人是否映射同一稳定 ID？
9. 公会余额是否被合并了？好友是否双向？排行榜是否重算？
10. 匹配分数是否**只**来自服务端？队伍分怎么算？
11. 排位有没有伪装人类的 Bot？
12. 邮件附件领取是否先占状态？补偿会不会被满箱阻断？
13. 运营数据的主时钟是不是服务端接收时间？三种日切是否定义？
14. 报表变化是重算还是改缓存？

> ⚠ **评审时必须主动要求"失败演示"**：合服演示目标库写入失败 50%、网络中断、批次卡住；
> 跨服演示原服不可达、跨服服崩溃、重复结算；匹配演示客户端伪造高分、开黑撞车、Bot 被识别；
> 邮件演示并发领取、背包满、批量发送中断；运营数据演示时钟回拨、迟到三天事件、schema 改名。
> **任何无法演示恢复流程的组件，都不得进入发布清单。**
