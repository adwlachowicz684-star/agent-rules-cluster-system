# debugging — 反模式清单（审核用）

> 本文件**只写「不能怎么做」**，用于流程结束后审核自己的产出、约束边界。
> 「怎么做」见同 skill 的流程部分：`howto/godot/debugging.md`

## 常见坑

| # | 坑 | 后果 |
|---|---|---|
| 1 | 崩溃时看 stdout | `print` 未刷新，最后一行日志骗你 |
| 2 | release 用 `assert` 校验 | 被剥离，校验消失 |
| 3 | 多线程打断点 | 断点静默失效，以为代码没跑 |
| 4 | 靠 `MEMORY_STATIC` 查 release 泄漏 | 恒为 0，得到"没问题" |
| 5 | 只看 FPS 判断瓶颈 | 无法区分 CPU/GPU，优化方向错 |
| 6 | 每帧 print 调试 | 性能数据失真，且发布版仍在打 |
| 7 | 用 Visual Profiler 看脚本耗时 | 它只测渲染，脚本看 Profiler |
| 8 | 动态 load 路径 | 导出后找不到，编辑器正常 |
| 9 | `await` 无信号源 | 永久悬挂，不报错 |
| 10 | 认为 `get_node` 失败会报错 | 返回 null，崩溃点在别处 |
| 11 | 不清理自定义埋点 | 埋点本身成为性能问题 |
| 12 | 真机不复现就认为没问题 | 真机有性能/权限/平台差异 |
| 13 | ⛔ 自定义监视器返回负数 | 官方：custom monitors 不支持负值，**静默钳到 0**。跟踪"增量/差值"类指标时负向变化全部显示为 0 |
| 14 | 监视器名不带 `/` | 官方：斜杠决定分类，无斜杠一律归入泛化 `Custom` 类，与别人的埋点混在一起 |
| 15 | 自定义监视器取值函数写得重 | 官方：该函数**每次查询都会调用**（编辑器内每秒一次），重逻辑本身成为性能问题 |
| 16 | 拿 `get_monitor` 当实时值用 | 官方：部分内建监视器**非实时更新，最多延迟 1 秒**；`TIME_FPS` 更是**每秒才更新一次**，查再快也是旧值 |
| 17 | 靠 `RENDER_TOTAL_PRIMITIVES_IN_FRAME` 顶点数对账 | 官方：因 depth prepass 与 shadow pass，该值**总是高于**场景实际顶点数（通常 2–3 倍） |
| 18 | 用 Visual Profiler 的百分比列判 90fps 项目 | 官方：目标帧时间**硬编码 16.67ms（60FPS）**，非 60 目标下百分比全部失真 |
| 19 | 不同窗口尺寸下对比 Visual Profiler 结果 | 官方：结果**随视口分辨率剧烈变化**，不同次运行必须同一视口尺寸才可比 |
| 20 | 结果靠退出编辑器后回看 | 官方：停止运行后结果仍在，**退出编辑器就没了** |
| 21 | 跨渲染器对比 Visual Profiler 分类 | 官方：Forward+ / Mobile / Compatibility 的**分类项不同**，横比无意义 |
| 22 | 用 `--frame-delay` 当帧率限制 | 官方：它用于**模拟高 CPU 负载**，限帧要用 `--max-fps` |
| 23 | 帧率尖峰后直接读 Visual Profiler 图 | 官方：尖峰会把图缩放搞坏，需**关闭 Fit to Frame** |
| 24 | 断点打在线程代码里 | 官方 Warning：GDScript 调试器**不会在线程中的代码上中断**，表现为"代码没跑" |
| 25 | 把 gutter 断点当团队共用断点 | 官方：gutter 建的断点只跨编辑器重启保留（本地），`breakpoint` 关键字**随脚本进版本控制、跨机器保留** —— 用 gutter 建的别人看不到，表现为"我这儿能断、他那儿不能" |
| 26 | 修完才写回归用例 | 用例**永远通过**，证明不了任何事；未验证"修复前会失败"就不知道它是否真走到了出错路径，这种用例在回归里是纯噪声 |
