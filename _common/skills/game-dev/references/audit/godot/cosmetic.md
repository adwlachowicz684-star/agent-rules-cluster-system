# cosmetic — 反模式清单（审核用）

> 本文件**只写「不能怎么做」**，用于流程结束后审核自己的产出、约束边界。
> 「怎么做」见同 skill 的流程部分：`flow/godot/cosmetic.md`
>
> 边界：本篇是**"不改数值、只改外观"这一整类资产**。
> 角色捏脸/体型见 `audit/godot/character-customization.md`；
> 商业化见 `audit/godot/monetization.md`；装备实例见 `audit/godot/economy.md`。
>
> ⚠ **与 `audit/godot/character-customization.md` 的分工**：
> 那篇审**技术层**（Blend Shape、合并网格、换网格骨骼兼容、染色实例材质）；
> 本篇审**资产系统层**（拥有权、优先级、有效期、授权、加载回退、同步、商业化承诺）。

⚠ **一句话**：客户端只持有**可展示缓存**，服务端保存**拥有权、有效期、优先级和授权**。

## 常见坑

| # | 本能以为 | 实际 |
|---|---|---|
| 1 | 七类外观各写一套 | 统一成模板/实例/生效三层，共用拥有·冲突·授权·回退状态机 |
| 2 | "生效范围"可有可无 | 没有它 → 活动外观变成"全游戏生效"，各模块取数不一致 |
| 3 | 槽位冲突按点击顺序覆盖 | 要按 `(scope_rank, source_rank, obtain_time, instance_id)` 仲裁 |
| 4 | 只比较付费与否就能定优先级 | 基础外观可能来自新手任务或限时回归，价格无法稳定排序 |
| 5 | 到期后槽位留空即可 | ⚠ 要**先释放槽位再设为默认/永久外观**，不能留空 |
| 6 | 外观和装备共用一个实例 | **最高优先级错误**：装备交易/分解/回滚会让时装消失，缓存失控 |
| 7 | 客户端选成功 = 库存已拥有 | 客户端改内存就能凭空造限定时装；只能是"本地预览" |
| 8 | 换装就是替换一个预制体 | `mesh`/`skeleton`/`skin` 是**三个独立入口**，要组合替换 |
| 9 | 骨骼名相同就能换网格 | ⛔ 父子层级或 Bone Rest 不同，动画仍无法共用；T-pose、手脚漂移 |
| 10 | `SkeletonProfile` 提示能拦住问题 | ⚠ 只是提示，**不阻止导入**；要自建 CI 指纹校验 |
| 11 | 换网格失败就保留错误外观 | 要整体回退上一组已验证外观 |
| 12 | 染色直接改共享材质 | ⚠ **一个玩家染色污染所有同材质对象**；`duplicate(false)` 也不深拷贝子资源 |
| 13 | 染色写进共享纹理 | 后果比改参数更持久 |
| 14 | 称号只是 UI 字符串，客户端管就行 | ⚠ 可伪造 → **冒充 GM/客服**；要服务端白名单 + 签名 |
| 15 | 客户端保存内部称号枚举 | 应只保存可展示文本与脱敏标记 |
| 16 | 表情动作没有滥用风险 | 卡动作、循环刷屏是骚扰高发点；要冷却/距离/场景过滤/举报 |
| 17 | 坐骑皮肤可以带移速碰撞 | ⛔ 一旦有数值优势就不再是"无属性付费"；要能力模板，丢弃皮肤参数 |
| 18 | 放 `cosmetic/` 目录就是外观 | 自带碰撞/根运动/被战斗读取的参数都可能是数值 |
| 19 | 外观资产预加载最省事 | 大厅同屏会打爆内存；要按需异步 + LOD + 上限 |
| 20 | 默认外观也能远端加载 | ⚠ 回退路径**自身不能依赖网络**；要零外部依赖 + 程序化占位兜底 |
| 21 | 加载完成 = 外观已展示 | 要另设 `asset_applied` 显式回调 |
| 22 | A 切 B 时 A 加载完就应用 | ⛔ 要用令牌/`slot_version`，否则旧请求覆盖新选择 |
| 23 | 离开视锥就卸载 | 可能很快回来；且共享资产被一个玩家离开就卸载会波及他人 |
| 24 | `MultiplayerSynchronizer` 能同步 Resource | ⚠ 不能可靠同步 Object；只同步 ID/版本/校验摘要 |
| 25 | 增量同步够了 | ⚠ **丢包不会自愈**：外观没有天然周期重写，要全量校正时机 |
| 26 | 全量 manifest 只在进场景发一次 | 还要：重新可见、客户端请求、定期、优先级/有效期变化、delta 缺口、查看名片 |
| 27 | "不影响平衡"写进协议就够了 | 每次热更都要扫描外观包是否含移动/碰撞/伤害/判定字段 |
| 28 | 到期消失 vs 转永久差不多 | 是**两种产品承诺**，必须购买前明确，⛔ 不能默认替运营选 |
| 29 | 外观系统可以决定能否退款 | ⛔ 不能；退款口径与地区/渠道/是否使用/消费者法有关，归订单与客服 |
| 30 | UGC 上传时审一次就行 | ⚠ 模型+贴图+动画+染色+**组合结果**可能共同违规；要三阶段 + 巡查 |
| 31 | 客户端可永久缓存 UGC 资产 | ⛔ 要用临时令牌与过期白名单；下架时立即隐藏不等刷新 |
| 32 | 账号级外观可覆盖角色选择 | ⚠ 账号共享只是**授权范围**，角色 A 的选择不应覆盖角色 B |
| 33 | 外观规则写在节点脚本里 | 节点是运行时结构，⛔ 不承担"谁拥有哪件限时时装"的真相 |

## 审核时逐条问自己

1. 七类外观是否共用**同一套**模板/实例/生效接口？还是七套互斥逻辑？
2. 生效范围字段有没有？战斗/竞技/过场/观战各自取数会不会不一致？
3. 槽位冲突是按优先级仲裁还是按点击顺序？付费与否是不是唯一排序依据？
4. **外观实例与装备实例是否分离**？装备交易/分解/回滚会不会让时装消失？
5. 客户端的"选择成功"有没有被当成拥有状态？服务端拒绝后能否撤销预览？
6. 换网格有没有校验**骨骼层级与 Bone Rest**（不只是骨骼名）？CI 有没有指纹校验？
7. 染色用的是实例材质还是共享材质？CI 有没有禁止写 `base_material`？
8. 称号/头像框是服务端签发还是客户端自定？客户端是否保存了内部枚举？
9. 表情动作有没有冷却、距离、场景过滤与举报？服务端能否中断？
10. 坐骑皮肤有没有触碰移速/碰撞/技能？CI 有没有扫描这些字段？
11. 默认外观是否**零外部依赖**？加载有没有超时、令牌、取消路径？
12. 有没有 `appearance_version` 与全量校正时机？丢包后能不能自愈？
13. 限时时装到期是消失还是转永久？**购买前**写清楚了吗？
14. UGC 有没有三阶段审核 + 巡查 + 临时令牌 + 撤销广播？

> ⚠ **最值得优先投入的不是某种换装实现，而是统一状态、服务端授权、资产约束与回退路径。**
> 只要外观数据不越界进入装备实例和坐骑能力，骨骼与材质变更被严格控制，
> 加载与同步各自具备安全底牌，七类外观就能长期扩展而不必每次重写。
