# hotupdate — 反模式清单（审核用）

> 本文件**只写「不能怎么做」**，用于流程结束后审核自己的产出、约束边界。
> 「怎么做」见同 skill 的流程部分：`howto/godot/hotupdate.md`

⚠ **两条硬限制先立住**：① **Godot 没有 `unload_resource_pack()`，只能重启进程**；
② **补丁必须在 autoload 的 `_init()` 里加载**，写进 `_ready()` 就永远不生效。

## 常见坑

| # | 本能以为 | 实际 |
|---|---|---|
| 1 | 热更就是下载文件替换 | 资源热更与代码热更**差一个量级** |
| 2 | 加载新包就自动生效 | **已缓存/已 preload 资源不会自动换血** |
| 3 | 补丁加载写在 `_ready()` | ⛔ **`_init()` 才行** —— 这是发生率最高的错误 |
| 4 | 有 `unload_resource_pack` 可卸载包 | **官方确认不存在**，只能重启进程 |
| 5 | `clear_path_cache` 能卸载 pack | ⛔ 只清单个资源缓存，**PCK 虚拟文件系统层仍挂着** |
| 6 | 代码热更是技术问题 | 是**合规问题**，后果是下架 |
| 7 | iOS 偷偷热更没事 | 审核指南 **2.5.2 明确禁止**，关注行为不看技术 |
| 8 | Lua/JS 解释器能绕开 iOS | ⛔ 解释器加载下载脚本改功能**一样违规** |
| 9 | GDScript 替换是原子的 | 脚本状态/信号/继承**不会原子切换** |
| 10 | C#/GDExtension 也能热更 | **ABI 冲突**，非常困难 |
| 11 | 一个 `GAME_VERSION` 够用 | ⛔ **四个版本号必须独立**（客户端/资源/配置/最小兼容） |
| 12 | `min_supported_client` 写客户端常量 | ⛔ **必须服务端下发** —— 否则线上事故无法踢老客户端下线 |
| 13 | 兼容判定顺序随意 | ⚠ 必须**先客户端 → 再配置 → 最后资源**，反了会缺贴图崩溃 |
| 14 | 语义版本号描述资源版本 | 资源没有"主版本不兼容"语义，要用**单调整数 + 补丁链锚点** |
| 15 | 补丁删除即回滚 | ⛔ **补丁必须是可禁用的开关**（`active`↔`revoked`），不是删除 |
| 16 | delta patch 随便叠加 | ⚠ **加载开销累积**，半年后要连解六层；要定期出合并基线 |
| 17 | 对 GDScript 字节码开 delta | ⛔ 每次构建都变，delta 无效只增开销 |
| 18 | Base Packs 重新导出一份即可 | ⚠ **必须从归档取回**，重导字节不同会导致 delta 失败 |
| 19 | 先验哈希再验签 | ⛔ **先验签再哈希**，反了给攻击者哈希 oracle |
| 20 | 只做哈希校验够了 | ⚠ 曾在"CDN 返回 200 但 body 是 HTML 错误页"集体中招 |
| 21 | `HTTPRequest` 拉整包省事 | ⛔ 整个响应体攒内存，**几十 MB 在低端机直接 OOM** |
| 22 | 下载进度不用持久化 | 崩溃后进度归零；要每 64KB 或每秒落盘 |
| 23 | 403/404 继续重试 | ⛔ **立即放弃并告警** —— 签名 URL 过期是"不该再下载"的信号 |
| 24 | 磁盘留 1.2 倍够了 | ⛔ **要留 2 倍**；下载中每 5% 复检 |
| 25 | 空间不足继续写 | ⛔ 会产生不可恢复的部分文件 |
| 26 | 先更新状态再移动文件 | ⚠ **顺序反了会造"启动即崩溃"死局** |
| 27 | 回滚代码写了就行 | ⚠ 95% 项目从未在故障路径跑过；**三种故障必须实测** |
| 28 | 开服后出错就 restore | ⛔ 会抹掉玩家真实行为，构成**二次事故** |
| 29 | 强更可以配灰度 | ⛔ **结构性矛盾** —— 同一账号两台设备行为会不一致 |
| 30 | 灰度用 `rand()` 分桶 | ⛔ 玩家每次启动换桶，A/B 数据作废 |
| 31 | 运行时热换战斗中的场景 | ⛔ **不可中断状态绝不热换**，标记下次进入生效 |
| 32 | 切场景时旧节点 `_process` 会停 | ⚠ 不会，要 `set_process(false)` + 禁输入，否则**幽灵回调** |
| 33 | 配置里带 URL 跳板没关系 | ⚠ 跨过"数据变逻辑"的线 → 判定为**变相代码热更** |
| 34 | 存档迁移可以 v1→v3 一步到位 | ⛔ **必须链式单步**，跳版会丢中间字段映射 |
| 35 | 配置热更所有字段都立即生效 | ⚠ 不可逆字段（已购货币、永久属性点）**必须 `never`** |
| 36 | 数值不合理也算配置错误要回滚 | ⛔ 是运营判断，改回数值重发；回滚会让属性来回跳 |
| 37 | Steam 版自建热更照常推 | ⚠ 会**双重更新**覆盖 depot；Steam 版以 depot 版本为准 |
| 38 | 主机也能热修 | ⛔ 每次提交重过认证（PS/Nintendo 首提 2–6 周），只能靠服务端配置与预埋开关 |
| 39 | DLC 占位资源从网络拉 | ⛔ **必须随基础包分发** —— 离线打开背包会崩 |
| 40 | 所有权校验失败 = 未购买 | ⛔ **网络失败要信任缓存**，否则玩家地铁里看到已购内容变灰 |
| 41 | 分包依赖靠加载顺序 | ⛔ 要**显式 `depends_on` 图 + CI 拓扑排序 + 环路检测** |
| 42 | 版本清单签名一次就够 | ⛔ **要带有效期** —— 旧清单可重放，回滚后又被拉回旧版本 |

## 审核时逐条问自己

1. `load_resource_pack` 是在 `_init()` 还是 `_ready()`？（**最高频错误**）
2. 有没有代码假设能"卸载" PCK？
3. 四个版本号是否独立？`min_supported_client` 是否服务端下发？
4. 补丁是"可禁用开关"还是"删除"？最近两份全量包是否常驻？
5. 安装是否三段式原子切换（staging/ready/installed）？状态变更是否在文件操作之后？
6. 三层校验（签名/哈希/结构）是否齐全且顺序正确？
7. 下载是否用 Range 断点续传？进度是否持久化？4xx 是否放弃？
8. 磁盘是否留 2 倍余量并中途复检？
9. 回滚在三种故障下是否**实测通过**？
10. 强更有没有配灰度？灰度是不是用稳定哈希分桶？
11. 配置里有没有跨过"数据变逻辑"的线（URL 跳板、功能开关、可执行表达式）？
12. 存档迁移是否链式单步 + `.bak` 备份？
13. DLC 占位资源是否本地分发？所有权校验失败时是否信任缓存？
14. 分包依赖是否显式声明并在 CI 做了环路检测？

> ⚠ **回滚测试是 release gate，不是可选项。**
> 必须模拟：下载到 70% 杀进程、PCK 内容改成全零、`load_resource_pack` 后抛异常。
> 三种都必须能启动且状态一致。
