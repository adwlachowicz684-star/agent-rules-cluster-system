# ops — 反模式清单（审核用）

> 本文件**只写「不能怎么做」**，用于流程结束后审核自己的产出、约束边界。
> 「怎么做」见同 skill 的流程部分：`howto/godot/ops.md`

## 常见漏写

| # | 漏写 | 后果 |
|---|---|---|
| 1 | 不写"客户端能判 / 不能判"清单就开工 | 每个活动都重新争论一次归属，最后一半判一半不判 |
| 2 | 去 `ProjectSettings` 里找活动开关、指望引擎内置签到组件 | 引擎不内置账号 / A/B / 远程配置 / 兑换码，白找并得出错误结论 |
| 3 | 先做界面和倒计时，资产与兑换安全排最后 | 顺序反了：拥有漂亮界面和脆弱经济 |
| 4 | 启动后才拉配置，没有内置默认值 | 离线玩家白屏或报错，⛔ 内置默认值必须编译进包 |
| 5 | 埋点不带 `experiment_id` / `group` | 没有分组就无法分析实验，只能看到总量变化 |
| 6 | 配置下载完就完事 | 还要版本 / 灰度 / 校验 / 重试 / 默认值 / 回滚六件套 |
| 7 | 用 `JSON.parse_string()` 判配置是否解析成功 | 失败返回 null，与"内容就是 null"无法区分 |
| 8 | 配置里的 64 位 ID / 订单号经 JSON 往返 | ⛔ 官方：JSON 只有 number 类型，超 2^53 静默失真 |
| 9 | 用 `ConfigFile` 存嵌套配置 / section 名带空格 | ⛔ 官方：空格之后的内容在保存和加载时都被忽略，静默截断 |
| 10 | 客户端自己 `randf()` 分桶 | 每次启动 / 闪退重启都重新分组，实验样本瞬间污染 |
| 11 | 把配置热更和 PCK 资源热更混为一谈 | PCK 换字节后已缓存旧 Resource 仍活着，默认 REUSE 返回旧对象 |
| 12 | 用本地时间算活动倒计时与资格 | 改系统时钟就能提前领奖 |
| 13 | 把校准后的客户端时间用于资格判定 | 校准值只能用于倒计时显示，不是权威时间 |
| 14 | 不检测时钟回拨与快进 | 玩家把时间往后调一天就能刷每日奖励，且不报错 |
| 15 | 活动只有三态，漏掉"结算中" | 奖励没发完却显示"已结束"，活动结束当天工单暴涨 |
| 16 | 客户端判断是否在停服维护 | 改包即可绕过，且维护期请求仍打到后端 |
| 17 | 客户端用 `OS.get_date().day` 数签到天数 | 月末把"第 31 天"渲染成"第 1 天"，⛔ 只在每月最后一天出现 |
| 18 | 补签分步写（扣货币 / 标已签 / 加计数分开） | 断网重发扣两次货币只标一次，玩家看到"钱少了没补上" |
| 19 | 把断签重置还是续接写死在代码里 | 改运营策略要发版，而策略调整频率远高于发版 |
| 20 | 战令用 `level` + `xp_in_level` 逐级模型 | 补发 / 撤回经验、跨级跳跃出现"某一级没给够"的中间态 |
| 21 | 免费 / 付费轨各存一份经验 | 买付费轨后历史进度对不上，需要补算逻辑 |
| 22 | 赛季结束靠玩家下次登录才结算 | 未登录玩家奖励永久丢失；原地覆盖导致新赛季显示上赛季进度 |
| 23 | 补偿只按玩家 ID 去重 | 不同批次被误判为重复；完全不去重则重复发刷道具 |
| 24 | 补偿自动到账直接进背包，不处理失败 | 背包满时静默消失，玩家不知道错过而后台显示"已发放" |
| 25 | 发奖失败就算了 | 无重试队列与对账，问题只在玩家投诉后暴露 |
| 26 | 先发奖再标已用 | 发奖成功、标记失败、下次重试又发一次 |
| 27 | `client_req_id` 用时间戳或 `randi()` 生成 | ⛔ 碰撞的后果是真实请求被去重丢弃（点了没反应），比重复发更难排查 |
| 28 | 客户端校验兑换码 | = 无限刷，表现为兑换量远超发码量 |
| 29 | 用 `randi()` 生成兑换码 | 种子可预测可复现，可被批量推算与扫库 |
| 30 | 兑换码字符集含 `I` `O` `0` `1` `L` | 客服工单里大量"码输不进去"，看起来是输入问题不引向生成端 |
| 31 | 核销不是事务 | 并发下同一码被两人同时兑换成功，两人都看到成功 |
| 32 | 同批次可重复领，缺玩家—批次唯一约束 | 跨批次叠加规则未写清，运营预期与实现不一致 |
| 33 | 限流做在客户端或应用层 | 扫库请求直达数据库，表现为慢查询而不是被攻击 |
| 34 | 只测正常系统时间 | 改钟才暴露的失效在正常环境全绿 |
| 35 | 只在联网环境下测 | 离线默认值与断网补发路径从未执行，而弱网用户只走这两条 |
| 36 | 只发一条正常兑换请求 | 走的是客户端过滤，服务端校验路径从未执行 |
| 37 | 手动点几次测幂等 | 达不到刷取速率，重放与并发路径未验证 |
| 38 | 只测灰度放量不测回滚 | 出事时回滚路径从未跑过，"尽快回滚"不是承诺 |
| 39 | 把运营后台 token / 签名密钥嵌进客户端 | ⛔ 官方 Warning：反编译可获取嵌入的凭据 |
| 40 | 单个 `HTTPRequest` 节点并发发多个请求 | ⛔ 官方：必须等前一个完成，并发要一请求一节点 |
| 41 | 用 `Time.get_ticks_msec()` 存盘或跨重启 | 它是引擎启动至今的单调值，不是现实时间 |
| 42 | `HTTPRequest.timeout` 保持默认 0.0 | ⛔ 默认含义是"不超时"，弱网下请求永久挂起 |
