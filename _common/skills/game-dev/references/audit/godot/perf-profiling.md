# perf-profiling — 反模式清单（审核用）

> 本文件**只写「不能怎么做」**，用于流程结束后审核自己的产出、约束边界。
> 「怎么做」见同 skill 的流程部分：`howto/godot/perf-profiling.md`

## 常见坑

| # | 本能以为 | 实际 |
|---|---|---|
| 1 | 编辑器 FPS 够就够 | 编辑器有 gizmo/热重载，**不能代表目标设备** |
| 2 | 平均 60FPS 就流畅 | **P99 才是卡顿指标** |
| 3 | 测一次就行 | 移动端要**测 10 分钟**（热节流） |
| 4 | 帧时间 = process 时间 | 含物理到渲染的全部逻辑 |
| 5 | Inclusive 高就要优化它 | **看 Self**，它可能只是调了贵函数 |
| 6 | Profiler 能看 C# | **不覆盖**，要原生工具 |
| 7 | 监视器发布版也能用 | **部分只在 debug 可用，发布版返回 0** |
| 8 | FPS 监视器实时的 | **可能延迟 1 秒** |
| 9 | primitive 数 = 三角形数 | 因 prepass/shadow **约 2–3 倍** |
| 10 | 内存泄漏看节点数 | **看对象数**更准 |
| 11 | Forward+ 能开无限灯 | 是摊销，**取决于屏幕覆盖** |
| 12 | 移动端内存有统一上限 | **按机型分档**，没有统一值 |
| 13 | 纹理压缩只省包体 | **主要省带宽** |
| 14 | Web 也能用 Forward+ | **只能 Compatibility** |
| 15 | 热节流降档一次就够 | 要带**迟滞**，否则边界跳档 |
| 16 | XR 是单眼 draw call ×2 | 每眼完整管线，要看**双眼总量** |
| 17 | XR 刷新率写死 90 | 由 **runtime 决定**，要读 API |
| 18 | 首帧卡是 GPU 问题 | 通常是 **shader 编译** |
| 19 | 自定义监视器能返回负数 | **钳到 0**，负数指标永远显示为 0 |
| 20 | 同名监视器可重复注册 | **只能注册一次**，重复报错；用 `has_custom_monitor()` 判断 |
| 21 | 先优化再补基线 | 基线已被改动污染，无法证明改动有效 |
| 22 | 优化完看一眼 FPS 就知道效果 | 不复测不留记录 = 无法回溯与归因 |
| 23 | 一次改多个变量更快 | 无法归因，出问题时只能全量回滚 |
| 24 | 项目指标只能自己 print | 官方 `add_custom_monitor()` 可进 Monitors 面板 |
| 25 | 监视器注册在业务节点上无所谓 | 节点销毁后监视器消失，应放 autoload |
| 26 | 没预热就记录 | 数据含 shader 编译与首次加载，不可复现 |
| 27 | 优化从最耗时的地方开始 | 应从性价比最高、风险最低的开始 |
| 28 | 开了 pipeline cache 首帧就不卡 | 官方称该问题**远未解决**，缓存只是缓解 |
| 29 | 预编译留给游戏内首次出现时 | 应在加载屏完成，挪到玩家本来就在等的时刻 |
| 30 | 对象数基线不用记 | 泄漏无从发现；进出关卡后应回到基线 |
| 31 | 分档只改项目设置就够了 | 还要有**运行时**降级路径，否则掉帧时不会自动降 |
| 32 | 低端机以后再适配 | 上线掉帧，且架构已定型难改 |
| 33 | 性能回退不算 bug | 与功能回退同等对待，需基线快照对比 |
| 34 | 先减三角形 | 通常瓶颈是 DrawCall，先修打断合批的问题 |
| 35 | 每帧 `intersect_shape` 靠换引擎解决 | 多数是调用频率问题，先降频 |
| 36 | 屏幕外对象继续跑逻辑无所谓 | 纯浪费 CPU，应停止处理 |
| 37 | 长时测试只在桌面跑 | 移动 / XR 测的是可持续性能，要跑 10 分钟 |
| 38 | 验收跑一次就够 | 要多次取 P50/P95/P99 |
| 39 | 物理插值缺失肉眼看得出 | 正常 TPS 下只有 1 帧拖影，需临时降到 10 才暴露 |
| 40 | 优化后不用更新基线 | 下次对比用的是旧基线，会把已优化误判成又变慢 |
| 41 | 帧预算边做边看 | 应先定死目标帧率与 P99 门槛 |
| 42 | 平台必测清单过一遍就行 | 每个平台都要逐项实测，漏测的平台上线才暴露 |
