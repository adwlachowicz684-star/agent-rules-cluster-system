# 转职 / 觉醒 —— 审核清单（Godot 4.7.2）

ⓘ 配套做法见 `howto/godot/class-awaken.md`。
每条都是"本能以为没问题、实际会出事"的具体写法。

| # | 本能以为 | 实际 | 审查规则 |
|---|---|---|---|
| 1 | 转职/觉醒/多职业是一回事 | 三者数据模型完全不同：转职替换、觉醒追加、多职业并存 N 套状态 | 确认需求是哪一个；多职业需 N 份状态 |
| 2 | 职业信息直接挂在角色上 | 职业是模板、玩家状态是实例；挂角色上无法支持多职业与回滚 | `ClassTemplate` / `ClassState` 分离 |
| 3 | 转职历史只是日志，可清理 | 它是"为什么有这个技能"的唯一依据 | `history` 只增不删 |
| 4 | 成长系数存满级终值方便 | 改等级上限要改整张表，且看不出中间等级 | 存每级增量 |
| 5 | 先扣消耗再转职更安全 | 扣了没转成 = 玩家资产凭空消失 | 试算 → 扣费 → 提交 → 失败回滚 |
| 6 | 先转职再扣消耗不会亏 | 转了没扣成 = 白嫖且难追回 | 同上，事务化 |
| 7 | 预览和提交各写一份逻辑 | 两边漂移 → "预览能穿的装备转完穿不上" | 试算与提交共用同一函数 |
| 8 | 转职后装备自动适配 | 穿不上 = 瞬间裸装，战斗力断崖 | 明确保留/降级/过渡装，且不静默卸下 |
| 9 | 兼容判定在穿戴时做 | 那时已经晚了，玩家已经转完 | 试算阶段就列出失效清单 |
| 10 | 转职时直接改 attack 等最终值 | 下次重算被覆盖 → "变高了打一场又回去" | 只改职业成长这一环，走统一计算入口 |
| 11 | 改了职业属性自然会刷新 | UI 缓存还在 → 玩家以为没转成 | 提交后立即让面板缓存失效 |
| 12 | 技能点重置是设计的一部分 | 不返还 = 玩家资产损失，等同删档 | 明示继承/全额返还/部分返还 |
| 13 | 返还"剩余点数"合理 | 玩家先点满再转职套利 | 返还当时投入量，不是当前剩余 |
| 14 | 跨职业技能天然对应 | 没有映射表 → 旧技能既不能用也不显示，且无法恢复 | 建旧→新技能映射表 |
| 15 | 转职不可逆所以不用做确认 | 不可逆 + 无确认 = 事故 | 预览 + 显式确认 + 后悔期三层 |
| 16 | 后悔期就是反向再转一次 | 污染 history，且可能不满足原职业前置条件 | 保存转职前快照来撤销 |
| 17 | 后悔期快照多存几份更保险 | 存档无限增长 | 只存最近一次 |
| 18 | 职业 ID 存引用更方便 | 改配表后旧存档指向已删除职业 | 存 ID；配表只增不改 ID |
| 19 | 读到未知职业就回落到默认 | 转职进度凭空消失且不报错 | 保档 + 明确提示数据异常 |
| 20 | 客户端判定转职条件更快 | 改内存白嫖高阶职业，且无任何日志 | 服务端判定，客户端只发意图 |
| 21 | 预览算出来就是结果 | 与服务端不一致时静默采用客户端 → 预览与结果不符 | 以服务端为准并提示 |
| 22 | 觉醒就是转职换个名字 | 觉醒保留原职业，转职替换；模型不同 | 见 #1，先定性 |
