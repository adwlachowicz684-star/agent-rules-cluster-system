# verification — 反模式清单（审核用）

> 本文件**只写「不能怎么做」**，用于流程结束后审核自己的产出、约束边界。
> 「怎么做」见同 skill 的流程部分：`howto/godot/verification.md`

## 常见坑

| # | 坑 | 后果 |
|---|---|---|
| 1 | ⛔ 把"没查清楚"记成待核对 | 这是没查，不是待核对。条目无限膨胀，最终没人再信这个清单 —— 机制退化的主因 |
| 2 | ⛔ 一条里塞两个待定结论（如"Mobile 与 Compatibility 下的表现"） | 两个结论可能**一个对一个错**，合成一条只能整体标 ok/failed，丢失一半信息 |
| 3 | 只写"待核对"不写 `验证：` | 无法判定。脚本会报出来要求补，补不上就永远悬在清单里 |
| 4 | 验证方法写成"看一下""试一下" | 不可执行、不可复现，两个人得出相反结果也无法裁定 |
| 5 | 验证方法依赖主观感受（"感觉更流畅"） | 结论不可复现，等于没验证 |
| 6 | ⛔ 把 `skipped` 记成 `ok` | 最严重的滥用：把一个**从未验证过**的结论变成"已验证"，后面所有人都会直接信它 |
| 7 | 认为 `skipped` 等于结案 | skipped 的语义是**无条件验证**（缺设备/版本），结论**仍然不确定**，必须保持待核对 |
| 8 | ⛔ `failed` 只记不改文档 | 录入不等于处理完。文档里那条错误结论还原样躺着，下一个人读到的还是错的，只是系统里多了一条没人看的记录 |
| 9 | `failed` 的 `--note` 只写"不对" | 没写"实际是什么"，等于没记；三个月后有人重遇同一问题，看不到"这条路试过、不通"，会重新踩一遍 |
| 10 | 归档时把 failed 记录删掉 | 丢掉的正是这套机制最不可替代的信息 ——"当时以为是这样、后来发现不是"的痕迹 |
| 11 | ⛔ 裸写 ⚠ 待核对反例，不放代码块 | 被 `verify.py` 当成真条目收集，清单里混进说明文字，条数与 ID 全乱 |
| 12 | 用内容哈希做条目 ID | 改一个字 ID 就变，之前录入的验证结果全部失配 |
| 13 | ⛔ 把状态写回文档本身 | 多窗口并行改文档会互相覆盖（已发生过两次）。状态放独立文件 `.verify-state.json` 就是为了避开这个 |
| 14 | 凭旧 ID 直接录入、不看校验 | ID 会在文档列表变化时漂移；脚本校验到 ID 不存在会**报错拦截**，绕过这个报错就会静默写错到别的条目上 |
| 15 | 已引官方原文且明确的结论仍标待核对 | 那就是已验证。标了只会稀释清单可信度 |
| 16 | 纯逻辑推导 / 数学结论标待核对 | 不需要真机，标了让清单看起来比实际更可疑 |
| 17 | 二手来源数字直接当已验证写进正文 | 权威性不足，且读者分不出它和官方原文的区别 |
| 18 | 发现"部分对了"却不拆条 | 判据是**一条只能有一个 result**。"部分对了"本身就是该拆的信号 |
| 19 | ⛔ 只在编辑器里验证就标 ok | 真机有性能 / 权限 / 平台差异，编辑器全绿不代表目标平台成立 |
| 20 | 版本升级后沿用旧验证结果 | 版本/平台类结论会随版本失效，"当时 ok"不等于现在 ok |
| 21 | 用 `scan-gaps.py` 查"这个 API 存不存在" | 粒度错：它找的是**域/主题**是否覆盖。查一条断言要用 `verify.py` |
| 22 | 用 `verify.py` 查"这个功能域有没有文档" | 粒度错：它管的是**一条断言**。查覆盖要用 `scan-gaps.py` |
| 23 | ⛔ 正文写成确定结论、只在角落挂个待核对标记 | 读者读的是正文。标记形同虚设，等于没标 |
| 24 | 把待核对当免责声明，标得越多越安全 | 机制的价值取决于**标得准**，标多了会稀释可信度，标少了等于没标 |
| 25 | 验证完不归档 | 清单越来越长，已验证条目被未验证条目淹没，排查时无从下手 |
| 26 | 认为"我这儿能跑"就是验证通过 | 缺设备 / 版本时应记 `skipped`，不是 `ok` |
| 27 | 多人同时改同一份状态文件 | 状态放独立文件只解决"不参与文档冲突"，同时写仍会互相覆盖 |
| 28 | 自检只在建机制时跑一次 | `verify.py --self-test` 覆盖 ID 无重复、每条有验证方法等；机制本身会坏，且坏的时候是静默的 |
