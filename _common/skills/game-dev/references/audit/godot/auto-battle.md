# auto-battle — 反模式清单（审核用）

> 本文件**只写「不能怎么做」**，用于流程结束后审核自己的产出、约束边界。
> 「怎么做」见同 skill 的流程部分：`howto/godot/auto-battle.md`
>
> 边界：本篇是**同一战斗逻辑在四种输入源下的复用**。
> 一次战斗怎么打见 `audit/godot/combat.md`；离线锚点见 `audit/godot/time-progression.md`。

⚠ **一句话**：这四类不是四个播放功能，而是**同一个战斗模拟器**
在四种输入源、时间尺度与权威域下的复用。

## 常见坑

| # | 本能以为 | 实际 |
|---|---|---|
| 1 | 四个功能 = 四套实现 | 共用**一个模拟器**：只接受 Intent、固定 tick、seeded RNG、版本化规则 |
| 2 | `Intent` 可以是按键/坐标/UI 索引 | 必须是**领域动作语义**，否则回放绑死分辨率与节点树 |
| 3 | 扫荡 = 把战斗加速 1000 倍 | 是**不带位置/碰撞/动画的结算函数**；真跑会爆 CPU 且结果不可预测 |
| 4 | AI 可以读 `enemy.current_hp` | ⛔ AI 只见**玩家可见信息**，否则托管客观强于手动 → 隐性强制 |
| 5 | AI 决策每渲染帧扫描一次 | 必须对齐**固定 tick** |
| 6 | "大招优先级最高"够了 | 优先级/条件树/CD 感知**三者分开**；且要写回"为什么选它" |
| 7 | 预览只是给玩家看个期望 | ⚠ 预告是**服务端审批过的结果**，发放必须复用同一 `preview_id` |
| 8 | 预览和发放可以各算一遍 | 会"看到一项奖励、到账另一项"；必须同一事务 |
| 9 | 扫荡幂等靠 HTTP 去重 | 要在**业务语义层**：`request_id` + 奖励 source 键 + 首次结果缓存 |
| 10 | 重复发奖时重新抽掉落 | ⛔ 不能；只返回首次结果 |
| 11 | 体力/次数/VIP 倍率客户端算 | 全部**服务端权威** |
| 12 | 战力可以直接决定扫荡胜负 | 战力⛔ 不是真实技能表达；只用于惩罚/降级/匹配，不替代战斗结果 |
| 13 | 离线按真实时间跑循环 | N 个玩家线性放大 CPU，重启/扩容/跨日会重复或遗漏；要**一次性分段推导** |
| 14 | 离线时长用客户端本地时间 | 设备时钟可改、后台被杀、热改变规则；必须服务端 `now` 与锚点 |
| 15 | 离线场次数用 `if acc >= interval` | 累积浮点误差；要整数毫秒/定点，边界"满一场才结算" |
| 16 | 离线只存总金币 | 要结构化事件日志（含 config_version、seed、prev/next_anchor） |
| 17 | 回放用 `_process(delta)` | 帧率一变输入映射与碰撞时序就漂移；必须**固定 tick** |
| 18 | 回放用全局 `randf()` / 时间戳 / 节点 ID | 无法复现；要 **seeded RNG bank** 且可保存 state |
| 19 | 可以依赖 `RandomNumberGenerator` 跨版本一致 | ⛔ 官方明确算法是**实现细节**，不能依赖 |
| 20 | 行动顺序依赖 `Dictionary` | ⚠ 官方警告迭代时删除**不可预测**；要 ID 全序 |
| 21 | 时间源用 `Time.get_unix_time_from_system()` | 只能从 `sim_tick` + 固定 STEP 推出 |
| 22 | 网络包直接改模拟状态 | 要转成**带目标 tick 的命令**，否则不同机器到达 tick 不同 |
| 23 | 回放能跨版本播放 | ⚠ 商业产品也只支持**同版本**；不是实现偷懒 |
| 24 | 回放校验和不匹配 = 作弊 | 只证明确定性已破坏或文件被改动，不必然是作弊 |
| 25 | 回放跳转时把渲染位置写回模拟器 | ⛔ 要从**最近检查点**恢复 seed/state 重新推进 |
| 26 | 零延迟观战更爽 | 可能泄露对手行动形成**上帝视角**；要按可见性过滤 + 延迟 |
| 27 | 观战把 30 秒当标准 | ⓘ 30–120 秒只是经验值，要按"观众能影响对局的时间"定 |
| 28 | 观战镜头/高亮/命中数字无害 | 会**隐式泄露隐藏状态**；要输出统一的"观战可见事件" |
| 29 | 每观众开一个模拟进程 | 大房间要事件扇出或 CDN |
| 30 | 客户端能"提交战斗结果" | 必须被拒绝；结果只能服务端评估 |
| 31 | 服务端要完整重放每场自动战斗 | 不必；保存输入摘要、seed、版本、关键事件，异常时做确定性校验 |
| 32 | 回放加速等于改模拟步长 | ⛔ 只能放大真实时间，不能改 STEP |

## 审核时逐条问自己

1. 四种模式是否共用**同一个模拟器**？有没有第二套战斗逻辑？
2. `Intent` 是领域语义还是按键/坐标？回放能脱离具体分辨率与节点树吗？
3. 自动 AI 能看到玩家看不到的信息吗？它的接口与玩家一致吗？
4. 扫荡结果谁算？客户端能不能改伤害、掉率、次数？
5. 预览与发放是同一笔事务吗？`preview_id` 绑定了版本/倍率/种子/快照吗？
6. 奖励有没有 source 幂等键？重复请求会重新抽掉落吗？
7. 离线是按真实时间跑循环，还是一次性分段推导？
8. 离线时钟用服务端还是客户端？离线日志够不够审计？
9. 回放用固定 tick 还是 `_process(delta)`？随机是 seeded bank 还是全局？
10. 行动顺序有没有依赖 `Dictionary` 或节点树顺序？
11. 回放保存了 `app_version / content_version / rules_hash / config_digest` 吗？
12. 观战有没有可见性过滤与延迟？会不会泄露隐藏状态？
13. 有没有任何一项"结果/次数/消耗/倍率/离线时长"**只跑在客户端**？

> ⚠ **建立回放黄金集**：同一输入在 Debug/Release、x86/ARM、
> 不同帧率、不同线程数下跑，比较状态哈希。
> 只加单测不够——浮点漂移会让校验失败，字典顺序依赖会让本地测试通过而正式发布后漂移。
