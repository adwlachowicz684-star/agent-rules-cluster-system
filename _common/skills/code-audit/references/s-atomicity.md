# 场景：原子性与安全判定（s-atomicity）

**触发**：多步写操作 / 批处理 / 交易 / 权限或经济判定 / 调试开关。
**风险**：中间抛错不回滚、空 catch 吞异常、fail-open（校验缺失时放行）、
调试后门默认启用。

`overlaps:` **只管「判定是否放行」**与「多步写是否整体成功」。
判定依赖的**数值**是否有限归 `s-numerics`；权限的**隔离边界**归 `s-sandbox`；
判定函数的**参数是否被使用**归 `s-contracts`。

---

## 核心判据：放行一律从严

**安全 / 经济 / 权限链路的「放行」一律按 P0 处理** ——
放行意味着白给钱、放过作弊、绕过权限。

---

## 模式清单

### A-01 (P0) 多步写操作原子性
- **正确**：先全量预检再统一动账，或 try/catch 整体回滚
- **特征**：扣减与增加在相邻行且无 `try`
- **典型**：扣库存成功、加钱包失败 → 库存没了钱没到账
- **另一半形态（易漏）：新建的资源没删除**
  多步操作在**远端或磁盘上新建了资源**，失败后这些资源**没被删除** ——
  远端分支、临时文件、租约、锁、后台任务、云上的中间对象。
  它不违反数据一致性（远端数据自洽），但留下**孤儿**：
  「远端存在、本地不知道」。详见 **A-18**
- **为什么分开报**：修复动作不同。数据没回滚 → 补回滚；资源没删 → 补补偿式清理。
  **只查「数据有没有回滚」会漏掉整条残留链**
- **确认**：列出多步链路的每一步，逐个问「这一步在远端 / 磁盘上新建了什么」
- **典型**：建分支 → 传对象 → 更新引用 → 建 PR → 清理。
  第 2 步失败时第 1 步建的分支已存在，本地状态文件里却没有它的记录

### A-02 (P1) 空 catch 吞异常
- **正确**：至少记录日志
- **特征**：`catch (e) { }`
- **定级**：吞的是**安全/经济链路**的异常 → **P0**

### A-03 (P0) fail-open（校验缺失时默认放行）
- **正确**：**fail-closed**
- **特征**：`can*` / `is*` / `should*` / `check*` 体内 `if (!x) return true`
- **确认**：放行分支是否涉及货币、解锁、封禁、权限 → 是则致命
- **典型**：`if token.is_empty() { return true }` —— 本意「没配口令就不校验」，
  实际「本机任何进程都能触发工作流」

- **变体：`if kind == "safe": ... else: <危险路径>`**
  校验的另一侧同样致命：合法值只有少数几个，判定却写成
  「等于某个特定值才走安全路径，**其余一律走另一条**」。
  于是**任何**非法 / 未来新增 / 拼错的值都落到危险那条。
- **确认**：数一数分支条件的**取值总数**与**分支数**。
  取值 3 个、分支 2 个 → 必有一个分支吞掉多种取值，看它通向哪里。
- **实测**：`wf = "direct" if opts["direct"] else (state.get("workflow") or DEFAULT)`，
  后续分流 `if wf == "pr": ... else: 直推主干`。
  `workflow` 未经取值校验 → 任何非 `"pr"` 的值都静默落到直推主干，零提示。

### A-04 (P0) 判定依赖脏数值
- **正确**：比较前先校验有限性
- **特征**：`can*` / `has*` 返回 boolean，体内有数值比较但无 `isFinite` / `numOr`
- **典型**：`hasEnough(x)` 里 `x` 是 NaN → 比较恒 false → 判定为「不够」或「够」取决于分支写法

### A-05 (P0) 调试 / 作弊 / 后门默认启用
- **正确**：`enabled` / `debug` / `cheat` / `devMode` 默认 **false**，宿主显式开启；
  生产构建应 hard fail 或剔除
- **特征**：`enabled = true` / `enabled: true` / `enabled ?? true`
- **为什么 P0**：生产构建漏配即可暴露作弊命令、经济/关卡修改能力。
  **把安全寄托于「调用方记得关」不可靠**

### A-06 (P0) 空 if 块（校验写了一半）
- **正确**：补处理体或删除整个 `if`
- **特征**：`if (...) { }`
- **注意**：命中少但**几乎条条是真问题**，优先处理

### A-07 (P1) 三元表达式两支返回同一个值
- **正确**：改写分支或删条件
- **特征**：`cond ? A : A`
- **典型**：本该 `cond ? A : B`，写错后分支失效

### A-08 (P0) 交易 / 批量数量未校验
（与 `s-numerics` N-16 同源。**报一次即可**，按实际语义归边：
数值语义为主归 `s-numerics`，经济后果为主归本场景。）

### A-09 (P1) 日志注入缺失
- **正确**：库走 logger 注入，不直接 `console.*`
- **特征**：`console.log/warn/error/info`

### A-10 (P1) 错误处理不对称（成对 API 校验不对称）
（与 `s-contracts` C-12 同源。校验口径问题归 `s-contracts`，
导致的**后果**是放行则归本场景。）

### A-11 (P0/P1) 可选降级被赋予业务语义（fail-open 的隐性形态）
- **判据**：`x.get(k, [])` / `x.get(k, {})` / `?? []` / `or {}` 在**失败路径**上
  返回空容器，随后被下游当作「业务结论」参与判断
- **确认**：把该调用强制改成失败（断网 / 429 / 返回错误体），看下游是否把空值
  解释成「没有」「全都不匹配」「无变更」这类语义
- **典型**：`rmap = {t["path"]: t["sha"] for t in tree.get("tree", [])}` ——
  API 失败时响应体没有 `tree` 键 → `rmap` 为空 →
  每个文件都落到「基线未记录」分支被拦截，
  表现为**「疑似他人改动」**，真实原因却是网络抖动/限流
- **修法**：必需键缺失**必须中止并回显原始错误**；
  空容器只允许出现在「确实为空」的业务场景，不得作为失败兜底
- **定级**：把故障伪装成安全/冲突判定 → **P0**；仅影响展示 → P2
- **为什么易漏**：它不崩、不报空指针，只是让排查方向整个偏掉
- **同类形态：类型错误版（比空值更隐蔽）**
  字段**类型不对但非空**（字符串当列表、字典当字符串、数字当对象）时，
  `len()` / 切片 / 迭代**都不会报错**，只是算出荒谬的值 →
  产出「看起来完全正常」的业务结论。
  **空值至少会被怀疑，类型错误会伪装成事实**
- **实测**：状态文件 `{"files": {}, "conflicts": "x"}` ——
  `conflicts` 应是 list 实际是字符串 → `len()` 算出 1、切片切成 `"x"` →
  输出「有 1 个文件的冲突尚未解决：**x**」→ **把所有操作全部拦死**。
  用户看到的是一个根本不存在的文件名，完全无法排查
- **确认**：对每个从持久化 / 外部读取的字段，问
  「如果它是字符串而我当列表用，会算出什么」

### A-12 (P1) 批量操作作用范围未显式限定（捎带环境既有状态）
- **判据**：批量写（提交 / 暂存 / 批量更新）不指定作用范围，默认作用于「当前全部」
- **确认**：预先在环境里放一份脏状态（别人 `git add` 过的文件、残留暂存），
  看它是否被一起卷进去
- **典型**：`git commit -m msg` 不带 pathspec →
  把调用前就已暂存的其他文件一并提交
- **修法**：一律显式传 pathspec / 显式文件列表，不用「当前状态」当隐式范围
- **降级**：该环境保证干净（CI 全新 checkout）→ P2

### A-13 (P0) 防覆盖校验的前提假设未校验（本地副本过期 → 静默回退远端）
- **判据**：防覆盖逻辑只比对「远端当前 sha == 基线记录的 sha」就放行，
  **没有校验本地副本是基于哪个远端版本改的**
- **为什么不够**：这个比对只能证明「远端没被**别人**改」，
  证明不了「本地是**从最新版**改的」。本地副本一旦过期
  （CDN 缓存的 tarball、离线包、未 pull 的旧 clone、镜像延迟），
  过期的全文 + 你的改动会被整文件覆盖上去，**把远端更新的内容回退掉，且不报错**
- **确认**：分别取「本地副本的原始版本 sha」与「远端当前 sha」，两者不等 → 本地已过期
- **典型**：从 `.../tarball/main` 拉代码，CDN 命中旧快照；
  本地改 3 个文件后推送，第一层校验 `rsha == base` 全部通过，
  实际把远端新加的一条扫描规则（含其 fixture）整体抹掉。
  同一份代码隔几分钟重下一次，两份 tarball 的 blob sha 竟然不同
- **修法**：基线里额外记录「本地开始编辑时所基于的远端 commit」，
  推送前与当前远端比对；**落后就必须先同步再提交**，不允许直接覆盖
- **定级**：**P0** —— 静默 + 不可逆 + 破坏的是别人的产出
- **同类**：`ETag` / `Last-Modified` 未校验的离线缓存、`git pull` 后才 push 的纪律被绕过
- **镜像形态：检测基准 ≠ 完成基准 → 静默漏推**
  A-13 正文讲「覆盖了不该覆盖的」；反过来同样致命 ——
  **检测「有没有改动」用的基准，与判定「同步完成」用的基准不是同一个对象**，
  于是「有改动但检测不到」，操作被静默跳过。
  与静默覆盖互为镜像：一个是做了不该做的，一个是该做的没做
- **实测**：同步脚本用 `git status --porcelain` 检测改动（对比**本地 HEAD**），
  却用**远端基线**判定同步完成 → 用户 `git commit` 之后工作区干净 →
  输出「本地没有待推送的改动」→ **改动就此卡死，且失败完全静默**
  （用户以为已同步）。这个坑在网络受限环境下命中率极高：
  git 协议被拦时，用户唯一的直觉反应就是「那我先 commit 到本地」
- **确认**：分别写出「检测基准」与「完成基准」，
  问「用户对 A 做了某个操作后，B 会不会以为什么都没发生」
- **修法**：两个基准共用同一个对象（此处应是与「远端基线」比对，
  而非与「本地 HEAD」比对）

### A-14 (P1) 安全校验过度 fail-closed，导致 bypass 成为肌肉记忆
- **判据**：校验在**本无风险**的场景也拦截，逼着用户每次都加全局绕过开关
  （`--force` / `--yes` / `--skip-check` / `|| true`）
- **确认**：列出被拦的场景，算「其实没风险」的占比。占比高 → 用户很快形成
  肌肉记忆，真有风险时也被同一个开关一起放过，**保护形同虚设**
- **典型**：防覆盖脚本对**新增文件**（远端根本不存在）也报「基线未记录，无法确认原状态」→
  每次推新文件都要加 `--force-overwrite` → 真遇到他人改动时，同一个开关照加不误
- **修法**：校验要精确到「**这个具体场景**有没有风险」，而不是「我能不能确认所有事」。
  上例正确判据是「基线没记录**且远端却有**该文件」才拦；远端也没有即纯新增，直接放行
- **定级**：P1（不直接造成损失，但**让已有的安全机制失效**）
- **注意**：这不是「放宽标准」，是把 fail-closed 用在真正需要的地方——
  泛化的严格等于没有严格

### A-15 (P0) 放行粒度与放行承诺不一致（点名级参数产生全局级效果）
- **判据**：存在「点名放行」类入参（`--force-file` / `--allow-overwrite` / allowlist /
  skip-list / `except:` 名单），实现里却把它合并进一个**全局**布尔：
  `bypass = force or bool(allowed)` / `if (opts.allow || opts.force) skipAll()`
- **为什么致命**：调用方（和用户）理解的是「只对这些对象承担风险」，
  实际拿到的是「整个闸门都开了」。**未点名的对象失去保护，而用户以为它们受保护**
- **确认**：点名**一个**对象，然后检查**未点名**的对象是否也被放行。
  被放行的对象数 > 点名数 → 命中
- **典型**：`--force-file e1.txt` 本意只覆盖 `e1.txt`，因 `bypass` 是全局的，
  整层「本地副本是否过期」校验一并失效 → 他人对 `e2.txt` 的改动被整文件回退
- **同类放大**：这类缺陷常与「被放行的对象不进二次确认清单」同时出现——
  确认对话框只列点名对象，屏幕上却写着「不会静默覆盖」
- **修法**：点名放行只在**按对象逐条判定**的那一层生效；
  全局闸门（覆盖全部对象的那种）只能由全局开关放。两层不得共用一个布尔
- **定级**：**P0** —— 静默 + 不可逆 + 实际行为与界面承诺相反
- **放大：全局开关放开了不该放开的层**（实测变体）：
  `--force-overwrite` 的语义是「允许覆盖远端」，实现里却把
  「本地冲突尚未解决」这层也一起跳过了
  （`if not force and rel in conflicts: continue`）。
  用户加它是为了推进推送，实际效果是让自己的**本地**未解决冲突被二次合并，
  冲突标记嵌套累积成两层，比单层难读得多，反而更难脱身。
  **判据**：全局开关只应放开它**名字所承诺**的那一层；
  保护本地文件不被自己弄脏的层，与「覆盖远端」无关，不得共用一个布尔

- **同源形态：确认对话框的粒度小于实际执行的粒度**
  用户确认的是 A（推送到分支），实际执行的是 A+B（推送 + 自动合并进主干）；
  且自动那段常以 `quiet=True` 静音，连「已合并」都不打印。
- **确认**：把每个确认点的提示语抄下来，与它之后**实际执行的所有写操作**比对。
  提示语里的宾语少于实际写操作 → 命中。

### A-16 (P1) fail-closed 无出口（拦截提示没给该状态下可行的解除动作）
- **判据**：防护拦下后，提示给出的出路①在该状态下**执行也无效果**，
  或②只有「关闭防护」这一条（`--force` / `--skip-check` / `|| true`）
- **确认**：**按提示逐条真跑一遍**，看能不能真的解除拦截。跑不通 = 存在无解路径
- **典型**：推送被「本地副本落后」拦下 → 提示先 `--pull`；
  而 `--pull` 的待合并集合此时为空（远端相对基线没变 / 远端删了文件 / 内容等价），
  直接 return 且不刷新同步标记 → **再推仍被拦**。
  真正能解的 `--mark-synced` 在提示里一次都没出现
- **为什么易漏**：测试只覆盖「拦截生效」与「正常路径」，
  几乎不覆盖「被拦之后能不能走出来」。用户被卡死时，
  提示里那条「关闭防护」就成了唯一出路——与 A-14 同后果
- **修法**：每条拦截提示必须给出**该状态下确实可行**的解除动作，并实测走通；
  给不出解除动作，说明防护设计缺了出口，不是用户操作不当
- **定级**：P1（不直接造成损失，但**把用户推向摧毁防护**）
- **适用范围不止「拦截提示」**：**所有错误出口**都要给出路 ——
  HTTP 状态码、`OSError`、解析失败同样要写「下一步做什么」。
  只查拦截提示会漏掉绝大多数报错
- **实测**：`401` 只回显服务端原文，不提示「检查 token 是否设置 / 是否过期」；
  `422 not fast-forward` 不引导 `--pull`，用户只会往权限/设置上猜
- **确认**：把每个错误分支的提示抄下来，问「用户看到这句，知道该干什么吗」
- **子类：检测判据本身有假阳性**（比「没给出路」更隐蔽）：
  判据是启发式的（如「内容里含 `  存在天然的假阳性 —— 讲解 git 冲突的文档正文里本来就有这些字符串。
  一旦命中假阳性，**拒绝之后没有任何绕过手段**，用户被永久卡死，
  而且提示只会重复那条无效建议（「手工改好再 --resolve」）。
  **判据**：拒绝所依赖的判据若有假阳性，必须同时提供显式绕过
  （`--resolve --force` 之类），否则拒绝等于永久阻断。
  **降低假阳性的方向**：冲突标记是**行首**的 `<<<<<<< `，
  按行 / 按结构判比子串匹配准得多

- **新实例：出路执行后状态无任何变化（「空转」）**：
  提示给的出路确实存在、**也确实执行了**，但走完**什么都没改** ——
  拦截条件原样成立，再推仍被拦。用户按提示做了全部动作，进度为 0。
  **判据**：执行出路前后，比对「拦截所依据的那份状态」是否发生变化。
  无变化 = 空转（比「出路无效」更隐蔽：用户没理由怀疑提示有问题）
- **实测（同一条缺陷第二次命中 —— 上次修复没修全）**：
  被「基线未记录该文件」拦下 → 提示 `--pull`。上一轮只修了 **commit 级**出口
  （`--pull` 空集时也刷新 `synced_commit`），**文件级**基线在
  「远端无变化，本地改动保留」分支上仍不刷新 → `--pull` 报「合并完成、0 冲突」，
  再推仍被同一条理由拦下 → **死锁**。
  **教训**：出口常不止一处状态（commit 级 + 文件级 + 索引级），
  修 A-16 要把**所有会被读到的状态**走查一遍，只修一处等于没修
- **子类：检测判据本身有假阳性**（比「没给出路」更隐蔽）：
  判据是启发式的（如「内容里含 `<<<<<<<` 就算冲突未解决」），
  存在天然的假阳性 —— 讲解 git 冲突的文档正文里本来就有这些字符串。
  一旦命中假阳性，**拒绝之后没有任何绕过手段**，用户被永久卡死，
  而且提示只会重复那条无效建议（「手工改好再 --resolve」）。
  **判据**：拒绝所依赖的判据若有假阳性，必须同时提供显式绕过
  （`--resolve --force` 之类），否则拒绝等于永久阻断。
  **降低假阳性的方向**：冲突标记是**行首**的 `<<<<<<< `，
  按行 / 按结构判比子串匹配准得多

### A-17 (P1) 复用既有对象未校验其生命周期状态
- **判据**：按名字 / ID 查找已有对象后直接复用（PR、会话、租约、连接、缓存句柄、
  后台任务），只判「存在」不判「状态可用」
- **确认**：让该对象进入**终态**（已关闭 / 已合并 / 已过期 / 已撤销），再走复用路径
- **典型**：`find_pr(state="all")` 命中一条已合并的 PR → 复用它 →
  合并接口必然拒绝 → 上层报「冲突」，真实原因却是 PR 号复用；
  改动留在随后被清理的分支上，主干没变
- **同类**：`GET /sessions/{id}` 命中已过期会话直接续用；
  连接池取出已被服务端关闭的连接不发心跳就直接用
- **修法**：复用前校验 `state == open/active`，否则按「不存在」新建；
  查找接口默认只查活跃态，需要全量时显式传参并单独处理终态
- **定级**：P1（数据通常不丢，但流程失败且**报错指向错误的排查方向**）

### A-18 (P1) 多步操作的中间产物残留（跨进程 / 跨机器）
- **判据**：跨进程或跨机器的多步操作（建分支 → 传对象 → 更新引用 → 建 PR → 清理），
  任一步失败后，已建成的**中间产物**（远端分支、临时文件、租约、锁、
  云上中间对象、后台任务）**无人清理**，形成「远端存在、本地不知道」的孤儿
- **与 A-01 的分界**：A-01 是**已写入的数据没回滚**（一致性问题）；
  本条是**新建的资源没删除**（残留问题）。数据自洽，但远端多了东西。
  **修复动作不同：A-01 补回滚，本条补补偿式清理**
- **与 L-11 / L-15 的分界**：L-11（清理不彻底）、L-15（缓存 Map 无上限）
  讲**进程内内存容器**；本条讲**跨进程 / 跨机器**的外部资源，
  进程退出后依然存在
- **确认**：在链路的**每一个**远程调用点注入失败，逐个检查三项：
  ① 远端残留（孤立对象 / 分支 / PR / 临时文件）
  ② 本地状态（是否被写成「已成功」但实际没成功）
  ③ 报错是否可理解。
  **必须逐个点测 —— 只测一个点会得出「没问题」的错误结论**
- **实测**（某推送工具，修复前）：建第 1 个 blob 失败、建 tree 失败、
  建 commit 失败、**大文件预检失败**（用户最易撞）、PATCH 之后 Ctrl-C ——
  **每个点都留下孤儿分支**
- **降级**：中间产物**有编号、能被后续命令枚举发现** → 降 P2。
  （例：PR 一旦建出就有编号、能被 `--prune` 看见 → 该提示用户，不必强行清理）
- **注意别修过头**：清理只针对**本次新建**的资源。
  复用的资源（如攒批分支）里可能已有用户攒的改动，删掉会丢东西

- **新维度：残留物落在「自己的工作目录 / 扫描范围」内**（比残留本身更危险）：
  中间产物（冲突副本 `.remote` / `.base`、备份、转储）写在**被自身变更检测覆盖的
  目录**里 → 被自己的下一轮流程当成**新内容**重新处理。
  **判据**：问「这个产物所在目录，会不会被本项目自己的检测 / 扫描 / 索引读到？」
  会 → 不只是残留，是**自我污染的循环**。展开见 **A-25**
- **降级**：中间产物**有编号、能被后续命令枚举发现** → 降 P2。

### A-19 (P0) 补偿式清理未覆盖中断路径
- **判据**：`KeyboardInterrupt` / `SIGTERM` / `SIGKILL` 在多数语言里
  **不是普通异常**（Python 中 `KeyboardInterrupt` 是 `BaseException` 子类）。
  只捕获普通异常的补偿式清理，在用户 Ctrl-C 时**完全不执行**
- **与 A-18 的分界**：A-18 是「失败后没清理」；本条是
  「**清理代码写了，但中断时不执行**」。是 A-18 的一个特定成因，
  但因为**中断是用户最常触发的失败方式**且**完全静默**，单独立条
- **确认**：在每一步注入**中断**（不是注入异常），看残留。**必须逐个步骤测**
- **实测**：同一段代码里，前 3 步（建 blob / tree / commit）中断**无残留**，
  第 4 步（PATCH ref）中断**留孤儿分支** —— 只测一个点会漏。
  而第 4 步恰恰是用户最易撞的（大文件刚传完按 Ctrl-C）
- **定级 P0 的理由**：中断是用户最常触发的失败方式，而这类残留**静默** ——
  用户完全不知道远端多了东西
- **修法**：清理 / 回滚代码用 `except BaseException`（清理后 `raise`，不要吞），
  或放 `finally`。Python 形态另见 `p-python` **PY-13**

- **A-19 扩展 —— 三类出口都要覆盖**（2026-09 回填）：
  用 `try/except` 做清理时，必须覆盖**三类出口**，缺一即成立：
  1. 异常—普通异常：`except Exception:` 能否捕获
  2. 异常—中断类：`KeyboardInterrupt` / `SystemExit` 走 `BaseException`
  3. **正常控制流：`return` / `break` / `continue` / 自然结束**
     —— **`return` 不触发 `except`**，是最容易漏的一档

  **关键判据**：资源创建点与清理点之间**存在 `return`，且清理挂在 `except`** → 必然残留。
  ```bash
  awk 'NR>=<创建行> && NR<=<清理行> && /return|break|continue/' <file>
  ```
  **修法**：① 首选 `finally`（覆盖全部三类）；② 次选统一取消异常，
  让所有提前退出走同一条清理通道：
  ```python
  class _Cancel(Exception):
      """正常取消：不提交，但走与失败相同的清理。"""
  ```
  **不要**：`try/except BaseException` + 多处 `return` 混搭 —— 第 3 档必漏。

- **实测**（某推送工具）：`try` 内 6 处 `return`，其中 4 处在常见路径上；
  用户在确认框输入 `n` 取消推送 → 远端留空分支 → 后续 `--prune` 把它判为
  「孤儿分支」并警告「删除会丢改动」，而它恰恰是刚才那次取消留下的空分支。
  **比 Ctrl-C 更常见**：取消确认是日常路径，Ctrl-C 是异常路径

- **新实例：正常 `return` 路径同样绕过清理**（比中断更常见）：
  补偿式清理只挂在 `except` 上，而流程里有**多条正常 `return`**
  （无待处理内容 / 用户在确认框按 N / 被别的校验拦下 / 预演结束）。
  这些是**最常见路径**，不是异常路径 —— 用户改了两个文件其中一个其实没变，
  或临时按 N，远端就多一个空分支。
  **判据**：把 try 块内每个 `return` 都当成一次中断来测，看残留
- **放大：创建动作本身在 try 之外**：
  资源在 `try:` **之前**创建，则创建自身失败时连「该清理什么」都还没记下来。
  **确认**：补偿式清理的 `try` 必须**从第一个有副作用的调用开始**
- **修法（清理路径唯一化）**：把「主动放弃」统一改成抛内部异常
  （`class _Abort(SystemExit)`），让 `except _Abort` 与 `except BaseException`
  **共用同一段清理**；不要在每个放弃点各写一行

### A-20 (P1) 反复失败时残留累积
- **判据**：失败时产生备份 / 转储 / 临时文件的代码，若按**序号或时间戳命名**，
  反复失败会**只增不减**。若用固定名覆盖，则要确认覆盖时机
  （不能在写一半时把好的那份覆盖掉 —— 那是 `T-09`）
- **与 L-15 的分界**：L-15 是**运行时内存增长**；本条是**磁盘 / 外部存储的累积**，
  且**只在失败路径发生**（成功路径通常有正常清理，
  **所以只跑成功路径永远测不出来**）
- **确认**：连续失败 N 次（**建议 N ≥ 5**），统计残留数量。
  **只失败 1 次测不出来** —— 这是本条最容易漏测的地方
- **实测**（fp，设计正确）：损坏备份连坏 5 次 → 始终 1 个（固定名覆盖）；
  curl 临时配置连推 20 次 → 0 个残留（用完即删）
- **修法**：固定名 + `tmp` + `os.replace` 原子替换；或失败时清理上一次的残留

### A-21 (P1) 显式指定的输入被静默丢弃
- **判据**：用户**显式点名**的参数 / 文件（区别于自动扫描得到的），
  若因不存在、类型不符、被忽略规则屏蔽而被跳过，**必须逐条告知**。
  只报聚合结果（如「没有待处理的改动」）会让
  「**打错文件名**」与「**真的没有改动**」在输出上完全一样
- **与 A-16 的分界**：A-16 是「**拦截了**但没给出口」；
  本条是「**压根没处理**，也没说」。用户连被拦了都不知道
- **确认**：构造「全部输入都无效」与「**部分输入无效**」两种场景。
  **部分无效更容易漏** —— 只要有一个成功，聚合输出就是绿的
- **实测**：① 打错文件名 `a.tx` → 输出「本地没有待推送的改动」，无任何提示；
  ② 点名目录（脚本只处理文件）→ 静默忽略；
  ③ 被忽略规则（`.gitignore`）屏蔽的文件 → 当次推送成功，
  **但之后它的改动再也不会被自动检测** —— 当下成功、之后静默漏推，最阴的一种
- **定级 P1**（不是 P0）：通常不造成不可逆损失，
  但「用户以为做了其实没做」是信任崩塌型缺陷
- **修法**：收集无效项，结束时统一打印「已忽略：xxx（原因）」

### A-22 (P1) 横切关注点在多出口重复实现，部分出口漏配
- **判据**：同一横切关注点（重试策略、超时、鉴权头、日志埋点、限流、编码处理、
  错误分类）在**多处重复实现** —— 常见于「主路径 + raw / 流式 / 批量 / 兼容分支」，
  其中一处**漏配**。**且注释往往声称「两者同一套语义」**
- **与 A-10 的分界**：A-10 是「成对 API 的**校验**不对称」；
  本条不限于校验，覆盖**所有横切关注点**，且不限「成对」——
  可以是 5 个出口漏 1 个
- **确认**：
  ① 列出所有「对外部发起调用 / 对外暴露的出口」
  ② 逐个检查该关注点是否配置
  ③ 重点看**后加的分支**（raw / 流式 / 兼容 / 批量）—— 它们是漏配高发区
  ④ **搜注释里声称「与 X 同一套」的地方，逐个比对实现**
  ⑤ **同一句「声明」有多处实现时，逐个比对它们校验了什么** ——
     漏配的往往不是配置，而是**校验本身**（见下）
- **新实例（校验漏配，比配置漏配更隐蔽）**：三处「声明本地已同步」
  （`init_baseline` / `pull` / `mark_synced`），只有 `init_baseline`
  真的比过「本地 vs 远端」（不一致直接拒绝建基线）；
  另两处**只比了「远端 vs 基线」**就声明「本地已与远端一致」——
  从未比过本地内容。回退场景下远端 == 基线，于是直接放行，
  本地旧版本静默覆盖主干
- **为什么这条难发现**：三处的函数名、输出文案都不同，
  看起来是三件独立的事；只有把「各自校验了什么」并排写出来，
  才看得出其中两处**校验范围小于声明范围**（与 T-14 同源）
- **实测**（同一条缺陷在同一处**两次出现**）：
  第一次 —— `api()` 的 raw 分支不重试 5xx，而注释明确写「raw 也退避重试」，
  实现没跟上（**raw 只用于拉大文件，大文件恰恰最容易撞 5xx**）；
  第二次 —— 同一处的重试判定里参数名写成 `p`（函数里叫 `path`），
  抛 `NameError`，**注释和实现正好相反**
- **为什么易漏**：主路径有测试覆盖，**后加的分支往往没有**；
  且这类缺陷只在特定输入下触发（大文件、特定状态码）
- **修法**：抽成统一的装饰器 / 上下文 / 中间件，所有出口共用；
  做不到就在每个出口旁写同一句注释并加一条一致性测试
- **确认**补充 ⑤：**修复是否只补了被发现的那一维** —— 主路径上同一关注点
  往往不止一项配置（重试 / 退避时长 / 限流提示 / 超时 / 错误分类），
  修的时候只补了报错的那一维 → 同维度其它项在新分支上依然缺失。
  **改完要问：这次修的是「这一类」还是「这一项」？**
  实测第三次复发：429 的 `Retry-After` 退避与限流提示只加在 JSON 分支，
  raw 分支仍只有固定 `2**attempt` —— 而 raw 恰恰只用于拉大文件，最容易撞 429

### A-23 (P1) 部分成功的报错未区分「已生效」与「未生效」
- **判据**：多步操作中**不可撤销的那一步已成功**，只有收尾步骤
  （写状态 / 回执 / 更新索引 / 发通知）失败，但报错**没说明主体已生效** →
  用户认为整体失败 → **重跑** → 重复建对象 / 重复扣款 / 重复发信
- **与 A-01 / T-09 的分界**：A-01（不回滚）、T-09（写入非原子）都讲**怎么修**；
  本条讲**怎么报** —— 报错的措辞决定用户下一步动作
- **确认**：让**收尾步骤单独失败**（磁盘满 / 只读 / 权限），
  看报错里有没有「xx 已成功，仅 yy 失败」
- **实测**：推送成功 → 写基线失败 → 只报 `[Errno 28] No space left on device`。
  用户不知道推送其实已成功，下一跑还被判「本地副本落后」→ 挡在门外。
  **而撞到这个错误时用户最自然的反应是重置基线** ——
  那会丢掉防覆盖的参照，把最危险的事做了
- **修法**：报错写三段 —— ① 哪一步成功了 ② 哪一步失败了
  ③ **该做什么 / 不该做什么**（上例应显式劝阻重置基线）
- **定级 P1**：不直接造成损失，但**把用户推向摧毁防护**（与 A-14 同后果）


---

- **更早期形态：收尾步骤失败且**返回值根本没被检查**
  原文讲「报错没说清已生效」；比它更早一步是
  **压根不知道失败了** —— 收尾步骤（本地提交 / 回执 / 索引更新）
  用默认参数调用，失败只打印一行警告或完全静默，
  而此时**主体已生效且状态已按成功落盘**。
- **确认**：找出主操作成功之后的每一步，逐个问
  「它的返回值 / 退出码被检查了吗？失败了会不会影响下一次运行的判断？」
- **实测**：推送（远端 PATCH 已成功）之后本地补提交
  `git add` → `git diff --cached` → `git commit` 三步均未检查失败，
  而 `synced_commit` 已写盘 → 下次检测把已推内容再列一遍，
  第一层又判「已一致」而跳过。

### A-24 (P0) 工具产物与业务数据共用命名空间

- **判据**：程序生成的**辅助文件**（备份、转储、冲突副本、临时文件、日志，
  典型后缀 `.remote` / `.base` / `.orig` / `.bak` / `.tmp` / `-copy`）满足两条：
  ① 写在**用户数据目录内**（工作区、项目根、用户可编辑目录）
  ② 命名规则是**用户可能自然采用的模式**（`<原文件名>.<后缀>`）
  → 会**静默覆盖**用户的同名业务文件

- **与 A-20 的分界**：A-20 是「自己产生的垃圾越堆越多」（残留累积）；
  本条是「**撞了别人的东西**」（命名空间冲突）。修复动作不同：
  A-20 加清理，本条改存放位置

- **确认**：
  ```bash
  grep -nE "open\(.*(\+ *[\"']\.|%s *\+ *[\"']\.)" <file>
  # 确认：① 写在哪 ② 用户是否可能已有同名文件
  ```

- **三反问定级**：会报错吗（**否**，静默）｜用户会遇到吗（低频但必然有人遇到）
  ｜能恢复吗（**数据已永久损坏**）→ **P0**

- **修法**：
  ```python
  # ① 首选：物理隔离到专属目录（仓库外 / 系统临时目录）
  AUX_DIR = "/var/lib/mytool/aux"        # 或 tempfile.mkdtemp()
  open(os.path.join(AUX_DIR, rel + ".remote"), "wb")

  # ② 次选：写入前检查存在性，冲突即中止
  if os.path.exists(target):
      raise SystemExit(f"{target} 已存在，拒绝覆盖（疑似你的业务文件）")
  ```
  **不要**：靠「用户一般不会取这个名字」来假设安全

- **实测**（某推送工具）：`pull()` 冲突时写 `rel + ".remote"`；
  用户仓库中真实存在 `config.txt.remote`（远程配置模板是完全正常的命名）
  → 静默覆盖，无备份、无提示、不可恢复。
  **同一写入模式还在删除副产物时出现**（按名字匹配删除，可能删掉用户的文件）

- **同类**：编辑器/工具把 `.swp` `.DS_Store` `.orig` 写进用户目录；
  构建脚本把中间产物输出与源文件同目录且同名不同后缀

### A-25 (P1) 单向属性写入（只升不降）

- **判据**：同步 / 应用函数形如
  ```python
  if <condition>:
      apply(state_a)
  # 缺少 else: apply(state_b)
  ```
  属性**只能单向漂移**：满足条件时设置，不满足时沿用旧值，**从不回退**

- **典型**：只 `chmod +x` 不 `chmod -x`、只 `enable` 不 `disable`、
  只 `set` 不 `unset`、只 `add` 不 `remove`、只 `setEnabled(true)` 不 `setEnabled(false)`

- **确认**：看同步函数里 `if` 有没有配对的 `else` / 反向操作

- **后果**：远端 / 上游已把该属性改回，本地**永远同步不回来** →
  下次同步又把旧值推上去 → **双向反复**。
  用户症状是「这个文件每次都显示有改动」，但看 diff 又看不出内容变化

- **修法**：
  ```python
  if mode == "100755":
      os.chmod(full, 0o755)
  else:
      os.chmod(full, 0o644)          # 必须补反向分支
  ```

- **实测**（某推送工具）：`_write_local()` 只在 `mode == "100755"` 时 chmod，
  远端把可执行位去掉后本地 0755 文件拉取后**不回退**
  → `local_state_map()` 仍判 100755 → 与远端永久打架

- **降级**：属性本身**只允许单向**（如「已读」标记、单调递增计数器）→ 不报

- **第二形态：多值模式字段 + 重建路径继承旧值 = 无出口**
  布尔属性之外还有**模式 / 枚举字段**：`workflow`、`mode`、`strategy` 之类，
  只在满足某条件时写入新值，从不写回另一个值。
  比布尔属性更糟的一点是**重建路径会继承旧值**——
  重置 / 重建状态的入口（如 `--reset-baseline`）读取旧状态并沿用该字段，
  于是连「推倒重来」都切不回另一个模式。
- **后果差异**：布尔属性形态的症状是「反复打架、每次都显示有改动」；
  模式字段形态的症状是**用户被永久锁定在某个模式且没有任何提示**。
- **确认**：① 该字段有几个合法取值？② 每个取值**有没有写入路径**？
  ③ 重建 / 迁移路径是否沿用旧值？有取值写不进去 → 命中。
- **实测**：某推送工具 `state["workflow"]` 只在 `--direct` 时写 `"direct"`；
  写 `"pr"` 的路径只有「PR 推送成功后」一处，且 `--reset-baseline` 继承旧值。
  于是一次 `--direct` 之后**没有任何命令行入口**能回到 PR 工作流。

### A-26 (P1/P0) 拦截判据改了，提示里的出路没跟着改（修一处、开一处）
- **判据**：防护 X 拦下后提示「用 B 解除」，而 **B 自身要经过 X（或 X 依赖的前置校验）**。
  X 的判定条件被**改强**之后，B 也走不通了 —— 但那段提示是**另一处的字符串**，
  没同步更新 → 用户严格按提示操作，陷入 `被拦 → 跑 B → 被同一判据拦 → 再建议跑 B` 的死循环
- **与 A-16 的分界**（两者常被混为一谈，确认方法完全不同）：
  - A-16 是「提示里**从来没有**可行出路」—— 靠**逐条真跑一遍**就能发现，静态审查也能看出
  - 本条是「出路**曾经可行**，判据变更后失效」—— **只在变更时暴露**，
    静态审查看不出来（提示本身写得很合理），必须**回归**才能发现
- **确认**（改动拦截判据时必做）：
  ① 列出该拦截提示里的**每一条**解除动作
  ② 逐个追进去：它是否经过本判据？是否被同一条件拦下？
  ③ **改动判定条件后，重跑 ②** —— 这一步是唯一能发现本条的时机
- **实测**（同一处代码的两个 P0 相隔一轮）：
  第四轮报「本地回退后 `--pull` 静默放行、推送时静默覆盖主干」；
  作者加了 `_refuse_if_rewound()` 把三个「声明已同步」的出口全堵上 —— 修对了。
  但**主推送路径那条拦截的解除方式清单没跟着改**，仍是
  `--pull` / `--mark-synced` / `--force-overwrite`，而前两条现在都会被
  `_refuse_if_rewound` 拦下。于是从「静默回退」降级成「**按提示操作走不出去**」：
  用户看到的仍是那三条，前两条跑完回到原点，真正能解的 `git reflog`
  只在 `_refuse_if_rewound` 内部打印、没进解除方式清单
- **为什么易漏**：改的人专注在「让拦截生效」，提示在**另一段字符串**里，
  不在改动点附近，`diff` 看不出二者的关联；
  测试只覆盖「拦截生不生效」，不覆盖「被拦之后能不能走出来」
- **修法**：把「解除方式」当作判据的**一部分**来维护 ——
  ① 改动判定条件时，同步检查所有打印该出路的分支；
  ② 更好：抽成 `_refuse_if_rewound(state, action)` 这类**统一函数**，
     让判据与出路文案**待在同一处**，改一个必然看到另一个
- **定级**：P1（用户卡住，不丢数据）；
  若剩下的唯一出路是 `--force` / 关闭防护 → **升 P0**（与 A-14 / A-16 同后果）

### A-27 (P0) 三态布尔化（保守返回值被当成肯定信号）
- **判据**：判定函数的返回值承载**两种否定语义**，调用方却按布尔直接分支：
  `False` 既表示「确定为否」，也表示「信息不足、无法判断」。
  于是「未知」被读成「安全」，防护在**最该拦的那一类输入上**静默放行
- **与 A-03 / A-15 / A-16 的分界**：
  A-03 是**判定本身**写反（fail-open）；A-15 是**放行粒度**与承诺不一致；
  A-16 是拦截后**出路无效**。本条是**返回值的语义容量不够**——
  判定逻辑、粒度、出路全都对，错在 `True/False` 装不下三种结论
- **确认**：列出所有返回布尔的判定函数，逐个问：
  `False` 的两种来源（确定为否 / 数据缺失）在调用方那里**是否被区分**？
  典型信号：函数体里有 `if not xxx: return False` 的**早期返回**，
  而 `xxx` 缺失与「确实不匹配」在语义上是两回事
- **实测**：推送脚本的 `_local_matches_baseline()` 在「基线里没有这个文件」时
  返回 `False`（函数注释写明这是**保守值，不算「已知未改动」**），
  调用方按 `revert if f(...) else overlap` 二分，把它一律读成「本地确实改过」
  → 归入可放行集合。后果：分支基点 = 最新主干，`ours` = 本地旧内容、
  `theirs == base` → 合并方判定「你故意回退」并直接采纳，**合并成功、零报错**
- **修法**：三选一，按侵入性递增——
  ① 返回三态（`True` / `False` / `None`），调用方显式处理 `None`；
  ② 返回 `(结论, 依据)` 元组；
  ③ 拆成两个函数（`is_changed()` / `is_known_unchanged()`）
- **定级 P0**：静默 + 不可逆 + **输出还在撒谎**
  （上例中被放行的文件被标注为「不会静默覆盖」）。与 A-15 同族，建议一并查

- **新实例：外部命令的退出码也是三态**（同一形态，换个载体就不认识了）：
  ```python
  rc = subprocess.run(["git","merge-base","--is-ancestor",old,cur]).returncode
  if rc == 0:  return False, None      # 正常前进
  if rc == 1:  return True, "已回退"    # 确定的「是」
  return False, None                   # rc>1：查不到 old、仓库异常
  ```
  `rc>1` 的语义是「**无法判断**」，却被写进与 `rc==0` 相同的 `return False, None`
  → 调用方读成「未回退 = 安全」→ **在最该拦的时候放行**。
  而 `old` 提交被 gc 回收时 git 返回 **128**，恰恰**更像**本地被动过的信号
  （reset / rebase / amend 都会换掉提交），不是「一切正常」的信号
- **识别信号**：函数末尾那个**兜底 return**，与「确定为否」的 return 长得一模一样 ——
  凡是「多个 return 返回同一个值」的判定函数，都要问一句：
  这些 return 的**语义真的相同吗**

- **同源形态：上游状态字段的语义容量不足**
  不只是**自己的函数返回值**会容量不够，**上游 API 的状态字段**同样会：
  一个取值同时表示多种真实成因，调用方按单义去分支。
- **确认**：列出上游状态字段的**全部**取值，逐个问
  「这个取值可能由几种成因产生？这几种成因的处置方式一样吗？」
  处置不同却共用一个取值 → 命中。
- **实测**：GitHub `mergeable_state == "blocked"` 既可能是
  「必需状态检查未过」（处置：等 CI），也可能是
  「需要 review / 需解决会话」（处置：找人）。

### A-29 (P1) 判据过宽：用存在性 / 非空代替语义判定
- **判据**：判定「某能力 / 规则 / 开关是否启用」时只读**键存在 / 字段非空 / 数组非空**，
  不读其**取值**：`if any(k in prot for k in KEYS)`、`if cfg.get("rules")`、`if policies`
- **为什么错**：上游对「启用」与「未启用」**常常都返回该键**。
  GitHub 对任何受保护分支都返回 `allow_force_pushes` / `allow_deletions`；
  配置系统对「显式关闭」也常写成 `{"enabled": false}`。
  **存在性只能证明「有这个维度」，证明不了「这条规则生效」**
- **确认**：拿一个**确认未启用**的样本，看判定函数的输入里那个键是否仍在。
  键仍在却返回 True → 过宽
- **后果**：合法操作被无谓拒绝。用户要么放弃该功能，
  要么**真的去关掉保护配置**（安全水位被降低）
- **修法**：判到**取值层**，且只把**真正阻止本操作**的那几条规则当作拦截依据
  ```python
  BLOCKING = ("required_pull_request_reviews", "restrictions")
  if any(prot.get(k) for k in BLOCKING):      # 读取值，不是读存在性
      refuse()
  ```
- **定级**：P1（不造成不可逆损失，但侵蚀安全配置）；
  若拒绝的是**唯一的合规路径**，导致用户关闭保护 → P0
- **与相邻判据的分界**：**A-27** 是「**自己的返回值**语义容量不够」；
  本条是「**读外部结构时判据粒度不对**」。
  **K-41**（异常处理过窄）的对偶面：库里已有「过窄」，本条补「过宽」一侧。
  **A-14**（过度 fail-closed）后果同族、成因不同：
  A-14 是判据太严导致 bypass 成肌肉记忆，本条是判据粒度不够导致误杀
- **实测**：某推送工具 `_refuse_direct_if_protected()` 用 9 个键做 `any(k in prot)`，
  含 `allow_force_pushes` / `allow_deletions` / `required_status_checks`。
  只要仓库开了**任何**保护，条件恒为真 → 纯 CI 保护（最常见配置）的仓库里
  `--direct` 被无谓拒绝。真正阻止直推的只有
  `required_pull_request_reviews` 与 `restrictions`

### A-30 (P1) 修复覆盖面小于问题覆盖面，且验证只盯已修那处

- **与 A-22 / T-11 的分界**：A-22 讲「配置在多出口漏配」、T-11 讲「判据在多入口漏改」，
  两者都在**代码侧**；本条讲**验证侧** —— **变异集的覆盖面必须与问题覆盖面同构**
- **确认**：
  ① 列出该判据命中的**全部**出口（grep 同族调用点）
  ② 逐个确认是否都已修
  ③ 逐个确认变异集里是否有对应的一条；缺一条 = 该出口永久免检
  ④ 特别检查「已被修好的那一处」—— 它最容易被当成变异锚点，
     而同族未修处被忽略
- **实测**（某推送工具第四轮）：`PY-15`（subprocess 编码）入库后，
  symlink 目标的编解码有 **4 个出口**，只修了 1 个；
  变异也只锁那 1 个 → 剩余 3 处（含 pull 与推送两条主路径）
  在第四轮人工通读才发现，其中 2 处实测崩溃
- **为什么难自查**：已修那处的锚点**一定存在**（好写变异），
  未修处往往形态略不同（`.encode()` / `decode(..., "replace")`），
  锚点写不中就 `NOT_APPLIED` —— 若把 NOT_APPLIED 当静默跳过，缺口就永久隐身
- **修法**：变异按**出口**编号（`M-PY15-01a/01b/01c/01d`），每个出口一条；
  `NOT_APPLIED` 必须显式报警，不许静默跳过
- **定级**：未修出口在**主执行路径**上 → P1；仅在边缘分支 → P2
