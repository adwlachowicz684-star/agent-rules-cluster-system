# 六步流程展开

## 第 1 步：摸清现状（不要跳过）

开工前必须搞清楚五件事，否则后面全在瞎扫：

| 要搞清 | 怎么看 | 为什么 |
|---|---|---|
| **技术栈与外壳形态** | 根目录配置文件（tauri.conf.json / package.json / Cargo.toml / electron） | 决定扫哪些语言、哪些模式适用 |
| **模块划分** | 一级子目录 + 注册表文件（registry.js / mod.rs / plugins.json） | 决定「单元」怎么切，报告按什么分节 |
| **是否有两套实现** | 入口文件（index.html vs index.react.html）、双语言同名文件 | 有就要做**差异比对**，这是整机审查的高产区 |
| **是否已有历史报告** | `审查报告*.md` / `审计*` / `audit/` / `docs/` | 避免重复劳动；已有则本轮是「修复复核」，用 `--pre-existing` 标记 |
| **规模** | 排除 node_modules / target / dist / vendor 后的行数 | >5 万行必须分模块推进，不要试图一次读完 |

输出一张**模块表**（模块名 / 路径 / 文件数 / 行数 / 是否已有结论 / 本轮是否审），
后续每完成一个模块回来打勾。

### 规模分档

| 行数 | 策略 |
|---|---|
| < 5 千 | 全量通读 + 扫描 |
| 5 千 ~ 5 万 | 扫描定位 → 按模块精读，每模块一次往返 |
| > 5 万 | 扫描定位 → **先审地基模块**（外壳 / 引擎 / 公共层）→ 再审业务模块。地基有问题的结论会推翻业务模块的判断 |

**地基优先**：外壳、插件引擎、公共工具层、配置系统先审。
它们的缺陷会影响所有上层模块，早发现能避免上层做无用功。

## 第 2 步：全库模式扫描

```bash
python3 scripts/scan-app.py --src=<根>                  # 全量，先扫一遍
python3 scripts/scan-app.py --src=<根> --p0             # 致命级优先处理
python3 scripts/scan-app.py --src=<根> --json > base.json    # 存基线
```

扫描器按**模块**聚合输出。先看每个模块的命中总数与 P0 数，
排出「最可疑模块」顺序，再逐个进入第 5 步。

**自检**：拿到扫描器第一件事是 `--self-test`，确认 28/28 通过。
永远 0 命中的检查等于没有检查；改过模式逻辑后必须重跑。

## 第 3 步：文档一致性扫描（整机审查特有）

```bash
# 原 doc-scan.py 已于 2026-09-14 拆成两个（语义相反，见 changelog）：
#   doc-deliverable.py —— 交付物三件套（README/测试/示例）
#   doc-promise.py     —— 文档承诺一致性（文档说的 vs 代码有的）
python3 scripts/doc-deliverable.py --src=<根>
python3 scripts/doc-promise.py --src=<根>
```

产出三类候选，全部需人工核对：

1. **命令不存在** —— README 写 `npm run test:bridge`，package.json 里没有 → 文档说谎
2. **引用的文件不存在** —— README 目录树写了 `plugins/foo/bar.md`，实际没有 → 断链
3. **数量声明待核对** —— README 说「22 套主题」，代码里数出 23 条 → 口径不一致

第 3 类最容易被忽略但最伤人：下一个接手的人按文档的数字去理解系统，
从第一条就是错的。

## 第 4 步：验证候选（不可省略）

对每条候选做三件事，**做完再决定报不报**：

1. **读该处上方的注释** —— 排除设计意图（最高频误报）
2. **读调用上下文** —— 排除「参数已在上游夹紧」「内部私有方法」等后果不成立的情况
3. **想清楚后果** —— 说不出「什么场景下暴露、表现为什么症状」的，不成立

批量族（J09/J10 这类全库几十条）的正确处理：
**抽样确认 3~5 条 → 若性质一致则按族批量报一条**，不逐条写报告。
逐条写几十条同质问题会把真正的 P0 淹掉。

## 第 5 步：分模块精审

按第 1 步排的顺序，逐个模块做。每个模块过五张清单：

| 维度 | 读哪份 | 典型发现 |
|---|---|---|
| 契约与双实现 | `s-contracts.md` / `s-sandbox-host.md` | 孤儿组件、双栈能力不对等、扩展取不到宿主状态 |
| 沙箱与权限 | `s-sandbox.md` / `s-sandbox-security.md` | 桥接无白名单、隔离后静默失效、CSP 只覆盖一个入口 |
| 原生后端 | `s-backend.md` | 整文件读入 OOM、命令注入面、空口令放行 |
| 生命周期 | `s-lifecycle.md` | 只注册不注销、定时器叠加、blob 未 revoke |
| 构建与卫生 | `s-build.md` | 打包范围过宽、硬编码清单、无 CI |

**每个模块审完立刻写结论**，不要攒到最后——攒着会丢细节。

## 第 6 步：分级、报告、修复清单

见 `common-severity.md`（定级）与 `common-reporting.md`（格式）。

## 推进节奏（>5 万行项目参考）

```
第 1 轮  摸清现状 + 全量扫描 + 文档扫描          → 模块表 + 候选池
第 2 轮  地基模块精审（外壳 / 引擎 / 公共层）    → 地基结论
第 3 轮  业务模块精审（按可疑度排序，分批）       → 各模块结论
第 4 轮  跨模块议题（全局一致性、平行实现、分工） → 全局议题章节
第 5 轮  汇总分级 + 报告 + 修复清单 + 批次建议
```

每轮结束更新一次模块表。**不要在第 2 轮就报业务模块的详细问题**——
地基结论可能推翻它们。

## 「审查 + 修复」两段式

默认**只审不改**。用户批准后再进修复阶段：

1. 按批次修（P0 → 安全 → 一致性 → 清理），每批修完跑一次测试与扫描
2. 修复后**重跑全量扫描**，比对基线，确认没有引入新问题（regression 一律按 P0 下限处理）
3. 更新报告里的「验证过没问题的部分」
