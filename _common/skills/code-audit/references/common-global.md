# 全局一致性检查（跨单元）

模式扫描只看单个模块内部。以下问题**必须跨单元比对**才能发现，且往往是系统性的。

## 一、坐标系口径

一个库里同时存在多套坐标约定时，调用方必然踩坑。

| 项 | 可能的冲突 |
|---|---|
| Y 轴方向 | 屏幕坐标向下 vs 世界坐标向上 |
| 矩形表示 | `min/max` 是数值大小 vs 「左下/右上」语义 |
| 旋转基准 | 0 度朝哪、顺时针还是逆时针 |
| 角度单位 | 度 vs 弧度（同一库混用是灾难） |

**怎么查**：
1. 找出所有涉及 y 的运算，看符号约定是否一致
2. 找出所有 `IRect` / `Rect` 类定义，比对注释里的「左下」「左上」描述
3. 找出所有角度参数，确认单位标注

**判据**：同一库内若存在两套口径，**必须有显式的转换层**且文档写明在哪个边界转换。
发现隐式混用 → 定为全局议题，需统一裁决，不要在各单元单独修。

## 二、边界包含语义

同一个「是否重叠/相切」的判断，在不同实现里用了不同的比较符：

```
ds.rectsOverlap   用  <   → 相切不算重叠
_core.rectOverlaps 用  <=  → 相切算重叠
```

**怎么查**：搜索所有 `overlap` / `intersect` / `contains` / `inside` 类函数，
比对它们的边界比较符与注释描述。

**判据**：语义必须统一，或至少在函数名上区分（如 `overlapsStrict` vs `overlapsInclusive`）。
不一致 → 定全局议题。

## 三、时间单位

全库 `dt` 用秒还是毫秒？混用差 1000 倍且**不报错**。

**怎么查**：
1. 列出所有带 `dt` / `duration` / `timeout` / `elapsed` 的参数
2. 比对配置字段（如 `durationMs`）与代码参数（如 `dt`）的单位
3. 检查单个单元内部是否自相矛盾

## 四、平行实现

同一功能出现两套实现时，调用方不知道该用哪个，且两套的缺陷修复不同步。

**怎么查**：按功能语义找重名/近义的类与目录：

| 已发现的平行实现 | 分工建议 |
|---|---|
| 图搜索：`pathfind` vs `pathfinding` | 保留覆盖更全的一个，另一个进兼容期并迁移示例 |
| 空间索引：`spatial` vs `ds.SpatialHash` | 若分工明确（泛型对象 vs number id）可保留，但要在 README 维持选择矩阵 |

**判据**：不禁止平行实现，但必须**写明分工**，且不能有第三套继续出现。
发现无分工说明的平行实现 → 定全局议题。

## 五、共享地基层的正确性优先

基础设施（如 `_core` / `ds` / `utils`）的缺陷会传染所有依赖它的单元。

**原则**：先修地基，再回归上层。上层单元报的缺陷，要先确认是不是地基引起的。

**复核流程**：
1. 确认该地基问题在台账里的状态（未修 / 已修 / 待验证）
2. **不要相信台账的「已修」** —— 实测复现一遍
3. 若确实已修，关闭时要**绑定修复 commit + 回归测试**，不能只更新审查文字

历史上出现过：台账宣称地基问题已修，但当前提交的源码与复现结果相反。
这类「文档说已修、代码没修」的偏差比缺陷本身更危险，因为它会阻止后续修复。

## 六、容量与配额的全局口径

各单元的容量上限（历史记录、日志、缓存、桶数量）应当有一致的量级约定，
不要有的单元 50、有的 1e7。

**怎么查**：比对各单元 `limit` / `capacity` / `maxHistory` 类的默认值与上限。

## 七、示例与交付物约定

每个单元的交付物约定要一致。用 `scripts/doc-scan.py` 检查。

注意**先确认该仓库自身的示例组织约定**：

- 若约定是「每单元一个专属示例文件」→ 用 `--strict` 模式
- 若约定是「批量综合示例」→ 默认模式（被任何示例引用即算有）

两种约定下缺失清单会差很多倍（实测同一仓库：1 个 vs 117 个），
判据错了会得出无意义的结论。

## 输出格式

全局议题与单元缺陷**分开列**，因为它们处理方式不同：

| 类型 | 处理 |
|---|---|
| 单元缺陷 | 该单元内修复 |
| 全局议题 | 需统一裁决，写成单独章节，列出冲突点与建议口径 |

全局议题不要在单个单元的报告里重复展开，只在总报告里列一次。
