# 公共层（必跑）

无论命中哪些场景，这一份都要读、都要守。**这里不放任何具体模式**——
只放「怎么组织一次审查」与「什么算一个问题」。具体判据在各场景文件里。

## 一、流程（六步）

| 步 | 做什么 | 产出 |
|---|---|---|
| 0 | 读本文 | — |
| 1 | **摸清现状**：技术栈、模块划分、是否两套实现、是否已有历史报告、规模 | 模块表 |
| 2 | **路由**：`scripts/route.py --src=<根>`；人工审核后定场景 | 场景清单 |
| 3 | **扫描**：按场景跑对应扫描器 | 候选池 |
| 4 | **验证候选**（不可省略）：过滤误报 | 确认后的问题 |
| 5 | **精审**：逐模块过场景判据 | 各模块结论 |
| 6 | **汇总**：定级 + 报告 + 修复清单 + 批次 | 交付物 |

展开见 `common-workflow.md`。

**防护型代码额外必查**（有 fail-closed / force / allowlist / 乐观锁的都算）：
每个防护单独生效 ≠ 组合起来安全。第 4、5 步之外**再走一遍**
`common-manual-review.md` 第 8 项「防护的组合与出口」——放行参数的组合、
被拦之后能否走出来、终态对象是否被复用。
实测某工具 41 项测试全绿，6 条问题**全部**出自这三类盲区。

## 二、路由协议（关键）

### 脚本是精确辅助，不是结论

`route.py` 做的事：按**确定性信号**扫一遍（目录名、文件名、正则命中、构建配置），
输出「命中场景 + 证据」。它解决的是「AI 靠感觉猜会漏」——
AI 看到"这项目像有插件"是猜，脚本扫到 `plugins/` 是事实。

**它做不到、必须由你做的**：

| 脚本 | 你 |
|---|---|
| 探测到 `src-tauri/` → backend | 用户只审前端 → **手动剔除** |
| 没扫到 `postMessage` | 相关代码在没扫到的路径 → **手动补** |
| 命中 8 个场景 | 按 P0 密度取前 4，其余列候选 |

**输出必须带证据**（命中几个文件、哪条正则命中多少次），
没有证据的命中不能进加载列表。

### 不设命中上限，改为分批

**命中多少个就审多少个，一个都不能丢。** 截断会漏检——大项目命中 10+ 个场景是正常的，
把"第 5 名之后"降为候选，审着审着就忘了，等于没扫。

正确做法是**分批加载**：

```
命中 10 个 → 分 3 批（每批 ≤4）
   第 1 批  s-backend, s-sandbox, s-numerics, s-contracts
   第 2 批  s-structures, s-boundary, s-lifecycle, s-build
   第 3 批  s-state, s-atomicity
```

- 一批**审完再加载下一批**，不要一次全读（一次读 11 个 = 每个都读不深）
- 批大小用 `--batch=N` 调（默认 4）
- **每批结束回头问一次**：这个模块里有没有我还没加载的场景的特征 → 增量路由
- 分批只影响**阅读节奏**，不影响**覆盖范围**

### 增量路由（最易漏）

场景不是一次定完的。**精审中发现新的结构特征 → 回路由层补加载**：

```
审 numerics 时发现代码里有个对象池      → 补 s-structures
审 contracts 时发现插件走 postMessage   → 补 s-boundary
审 lifecycle 时发现有个 Rust 后端在起子进程 → 补 s-backend
```

**没有这条，场景拆得越细越容易漏扫。** 每审完一个模块回头问一次：
「这个模块里有没有我还没加载的场景的特征？」

## 三、三件套（问题成立的硬门槛）

一条问题要成立，必须同时给出：

1. **位置** —— `文件:起止行`
2. **证据** —— 实测输出，或可验证的推导链
3. **后果** —— 什么场景下暴露、表现为什么症状

**说不出后果的问题不成立** —— 通常意味着它不是真问题，或没想清楚。

## 四、验证候选（第 4 步，不可省略）

扫描器产出的是**候选**。每条过三关再决定报不报：

1. **读该处上方的注释** —— 排除设计意图（最高频误报）
2. **读调用上下文** —— 排除「参数已在上游夹紧」「内部私有方法」
3. **想清后果** —— 说不出场景与症状的，不成立

**批量族的正确处理**：某条模式全库几十条 → 抽样确认 3~5 条，
性质一致则**按族合并报一条**，不逐条写报告。
逐条写几十条同质问题会把真正的 P0 淹掉。

## 五、定级

| 级别 | 定义 |
|---|---|
| **P0** | 对外承诺完全失效 / 崩溃 / 泄漏 / 安全放行，且**静默** |
| **P1** | 边界错误、契约不一致、部分模式失效、文档说谎 |
| **P2** | 一致性、可维护性、体验 |
| **P3** | 加固 / 优化建议 |

**8 条升级规则**（满足任一即 P0）：安全链路放行 · 静默失效 · 承诺完全失效 ·
文档把缺陷记为设计意图 · 不可逆污染 · 资源无上限 · 随时长累积的泄漏 ·
隔离模式下能力失效。

完整定义、降级条件、驳回清单见 `common-severity.md`。

## 六、驳回清单（提高信噪比）

遇到以下情况**不要报**：

1. **证据不足** —— 只有推理没有实测
2. **这其实是设计意图** —— **没读注释就报问题是最高频的误报来源**
3. **后果不成立** —— 触发路径不存在（内部私有方法、参数已上游夹紧）
4. **重复劳动** —— 已审结的地基模块或已知全局问题
5. **超出范围** —— 本轮只审不改；「顺手重构」一律不做
6. **风格偏好** —— 命名、格式、架构口味不构成缺陷

## 七、报告与清单

报告结构、修复清单格式、批次建议、复核流程见 `common-reporting.md`。
模板见 `assets/report-template.md`，执行清单见 `assets/review-checklist.md`。

**必写三件事**：

1. **审查方式与边界** —— 静态还是实测？跑过测试吗？没跑过写明原因
2. **验证过没问题的部分** —— 后续复核最值钱的一节
3. **待验证项** —— 依赖运行时才能定论的，明确列出

## 八、跨场景边界（避免重复报）

场景之间有三处天然交叠，**按下表归属，不要两边都报**：

| 交叠点 | 归谁 | 另一个只管什么 |
|---|---|---|
| 订阅 / 退订 | `s-lifecycle`（是否成对、是否清理） | `s-boundary` 只管通道本身的 origin / 握手 / 白名单 |
| 文档承诺 | `s-contracts`（文档 vs 实现） | `s-build` 只管构建与交付物是否齐全 |
| 资源上限 | `s-backend`（原生侧读入/分配） | `s-structures` 只管 JS 侧 TypedArray / 对象池 |

每个场景文件开头都有 `overlaps:` 声明，冲突时以该声明为准。

## 九、两段式（审 + 修）

默认**只审不改**。用户批准后再进修复：

1. 按批次修（P0 → 安全 → 一致性 → 清理），每批修完跑一次测试与扫描
2. 修复后**重跑全量扫描**比对基线，确认没引入新问题（`regression` 一律按 P0 下限）
3. 更新报告里的「验证过没问题的部分」
