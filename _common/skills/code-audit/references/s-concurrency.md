# 场景：并发与生命周期（s-concurrency）

**触发**：多线程 / 协程 / goroutine / 进程池 / 异步任务 / 锁 / 信号量 / 消息队列消费。
**风险**：共享状态无保护、取消不传播、任务泄漏、超时后状态不回滚、重试不幂等。

`overlaps:` **只管「并发执行流之间的状态与生命周期」**。
单线程内的订阅/定时器成对归 `s-lifecycle`；通道本身的 origin/握手归 `s-boundary`；
多步写不回滚归 `s-atomicity`；锁中毒崩溃归 `s-backend` K-21/K-22。
**语言语法形态**在各语言包里（`p-python` PY-04 / PY-07），此处记跨语言判据，同源不重复报。

> **为什么独立成域**：并发缺陷原本散在 A-（原子性）、B-（握手）、L-（生命周期）里，
> 但三者都没处理完整链条：**共享状态 → 取消传播 → 清理配对 → 部分失败回滚**。
> 本场景是这条链的唯一检索入口。

---

## 核心判据：并发问题要回答五个问题

静态规则只能发现线索。每条候选必须回答：

```
□ 哪个状态被共享？（不共享就没有竞态）
□ 哪个执行流负责清理？（没人负责 = 泄漏）
□ 取消/超时如何传播到子任务？（不传播 = 挂死）
□ 超时或出错后状态回滚到哪？（不回滚 = 部分成功）
□ 有什么测试或运行证据能证明上面几条？（没证据 = unverified）
```

**答不上来的按 P0**——说明没人想清楚过。

## 模式清单

### R-01 (P0) 共享可变状态无同步证据
- **判据**：多个执行流读写同一状态，文件/包内找不到任何同步原语
  （`Lock` / `Queue` / `channel` / `mutex` / `atomic` / immutable）
- **确认**：列出被共同读写的变量；确认是否真共享（传值不共享，传引用才共享）
- **降级**：任务间无共享状态（参数传入、结果返回）→ P2
- **各语言形态**：Python `Thread` 无 Lock（PY-04）· Go map 跨 goroutine 无 mutex ·
  Java `HashMap` 并发写 · C++ 裸指针跨线程
- **确认跨进程互斥必须用子进程**：测试若用**线程**验证锁，测的是同一进程内的
  `threading.Lock`，**测不出跨进程的真实竞争**。
  真实场景是两个进程时，必须起子进程重验
- **实测**：某推送工具的并发测试用线程跑全部通过；改用两个**子进程**重验
  才确认互斥真的成立（等待 0.99 秒）
- **同类**：容器 / 网络文件系统（virtiofs、overlayfs、共享目录）上 `flock`
  未必可靠 —— **实测过才能下结论**，不能假定它一定生效

### R-02 (P0) 任务 / 协程泄漏
- **判据**：起后台任务，但**没有**取消机制、等待机制，也没有退出测试
  （Go 无 `context` / `WaitGroup`；Python 无 `join` / `shutdown`；Java 无 `shutdown()`）
- **确认**：反复创建任务的路径，看任务数是否单调增长
- **典型**：每次请求起一个 goroutine 监听，请求结束不取消 → 随运行时长累积到 OOM

### R-03 (P0) 取消 / 上下文未传播
- **判据**：函数接收了 `context` / `CancellationToken`，但新起的任务、
  HTTP 调用、DB 查询、定时器**没收到**它
- **确认**：上游超时后，下游是否还在跑（画调用链逐个看入参）
- **典型**：`ctx` 只用于最外层，内部 `http.Get` 用的是 `context.Background()` →
  上游超时，下游继续占着连接

### R-04 (P0) 锁顺序不一致（死锁）
- **判据**：多把锁在不同函数里获取顺序相反，或无锁分级文档
- **确认**：构造「A 持锁1等锁2 / B 持锁2等锁1」的时序
- **修法**：全局锁序 + 按序获取；或用单锁/无锁结构
- **定级**：P0（死锁不可恢复，且只在特定时序下出现，测试期难复现）

### R-05 (P0) TOCTOU（先检查后使用）
- **判据**：`if check(x): use(x)` 中间无锁、无原子条件
- **确认**：check 与 use 之间是否有其他执行流能改 `x`
- **典型**：检查余额 → 扣款，中间被另一笔交易改掉 → 超卖 / 负余额
- **修法**：`compare_and_swap` / 数据库条件更新 `WHERE balance >= amt` / 事务内重查

### R-06 (P0) 超时后资源与状态未回滚
- **判据**：`with timeout` / `select` / deadline 触发后，连接、事务、文件、锁
  没有明确关闭或回滚
- **确认**：在超时分支里查 close / rollback / release 是否齐全
- **典型**：RPC 超时抛错，但本地已扣的库存没回滚 → 库存凭空消失

### R-07 (P0) 重试 / 重投不幂等
- **判据**：写操作超时或消息重投后重试，**无幂等键、无状态机去重**
- **确认**：同一请求连发两次，看是否产生两条记录 / 两次扣款
- **修法**：幂等键 + 唯一索引；或状态机保证「已处理」直接返回
- **注**：与 `s-boundary` B-10 附带的「重试幂等性」同源，此处从业务后果角度记一次
- **幂等性要按端点单独论证**（fp，可作正面范例）：
  「非写操作一律不重试」不是唯一正确答案 ——
  | 请求 | 能否重试 | 理由 |
  |---|---|---|
  | GET | ✅ | 幂等 |
  | 超时（curl 退出码 28） | ❌ | **服务端可能已生效**，重试会重复建对象 |
  | 5xx | ✅ | 服务端未处理 |
  | 429（GET） | ✅ | 限流下读可退避 |
  | 429（POST） | ❌ | 重发非幂等写风险更大 |
  | `POST /git/blobs` | ✅ | **内容寻址**，重发得到同一个 sha，天然幂等；且大文件最易撞 5xx |
- **重试的可观测性（易漏）**：重试造成的失败，报错里必须能区分
  「**我重试了**」与「**别人抢先了**」。否则排查方向整个偏掉
- **实测**：`PATCH /git/refs` 重试时撞 `422 not fast-forward` →
  上层那句「出现并发提交，已中止」把自己的重试**误报成他人抢先提交** →
  用户据此去排查根本不存在的并发（与 A-17 同源）

### R-08 (P1) 退出不收敛
- **判据**：进程收到 SIGTERM 后，任务队列、定时器、订阅没有收敛到关闭点
- **确认**：发 SIGTERM 后进程是否立刻退出；退出时是否有数据丢失
- **典型**：K8s 滚动更新时正在处理的消息被强杀 → 半处理状态
- **锁的实现：`flock` 在强杀后不释放（易漏）**
  `flock` 由内核在 **fd 关闭时**释放。进程被 `timeout` / SIGKILL 后 fd 不关 →
  **锁不释放** → 后续所有运行**永久卡死**。
  而 `timeout` 与 `&` 后台是常规用法，这个坑很容易踩
- **修法**：单实例锁改用「写 PID 文件 → 校验 PID 是否存活 →
  不存活则判定陈旧锁并接管」
- **确认**：起一个持锁进程，`kill -9` 杀掉，看下一个进程能否获得锁
- **同类**：`atexit` / `finally` / 析构函数在 SIGKILL 下**同样不执行** ——
  任何「靠退出钩子清理」的设计在强杀场景下都不可靠（与 A-19 呼应）

### R-09 (P1) 后台任务不可观测
- **判据**：无 metrics / log / trace 能证明后台任务**已退出**
- **确认**：内存缓慢上涨时，能否从监控定位到是哪个任务没退
- **典型**：只能靠 OOM 重启缓解，无法定位泄漏源

### R-10 (P1/P0) 析构 / 回收期跨线程访问
- **判据**：`__del__` / finalize / C++ 析构里访问仍被其他线程持有的对象，或加锁/做 IO
- **确认**：回收期模块可能已销毁，调用会抛异常或死锁
- **定级**：析构里**加锁** → **P0**（可与持锁线程形成死锁）；仅做 IO → P1

## 各语言的判据绑定

| 语言 | 关键形态 |
|---|---|
| **Go** | context 未取消 · `WaitGroup` 计数不匹配 · 无缓冲 channel 阻塞 · 重复 close · map 并发写 · mutex 值拷贝 |
| **Java** | `ExecutorService` 未 shutdown · `ThreadLocal` 在线程池串数据 · `InterruptedException` 被吞 · `HashMap` 并发写 · synchronized 粒度过粗 |
| **C/C++** | 数据竞争 · 锁序 · 条件变量缺谓词（`while` 而非 `if`）· 析构期访问 · RAII 未覆盖异常路径 |
| **Python** | `Thread`/`Executor` 无 Lock（PY-04）· `__del__` 加锁（PY-07）· GIL 误当成线程安全 |

**GIL 不是同步**：`x += 1` 在 CPython 里也不是原子的（LOAD / ADD / STORE 三步），
不要因为"有 GIL"就认为不需要锁。

## 常见误报

- **任务间确实无共享状态**（纯计算、参数传入）→ 不是竞态，降 P2
- **只读共享**（不可变对象、初始化后不再写）→ 无需同步
- **`asyncio` 单线程协程且无 `await` 让出点** → 实际串行
- **注释说明了为什么不用锁**（如「此处由上游串行化」）→ 先读注释再报
- **测试代码里起线程** → 短生命周期，降 P3
