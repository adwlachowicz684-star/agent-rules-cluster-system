# 场景：契约与承诺（s-contracts）

**触发**：有对外 API / 接口声明 / README 承诺 / 两套实现 / 插件注册契约。
**风险**：声明了却没接线、文档与实现不一致、双实现能力分叉、死契约。

`overlaps:` **只管「声明 vs 实现」的一致性**。构建产物是否齐全归 `s-build`；
接口参数是否成对校验归 `s-atomicity`；文档里的命令能否跑通归 `s-build`（CI 部分）。

---

## 核心原则：把文档当需求文档

**整机/库审查中占比最高、用户最能感知的一类。**
下一个接手的人（包括下一个 AI）是靠 README 认识这个项目的——
文档说错了，他从第一条理解就是错的。

---

## 模式清单

### C-01 (P0) 声明的特性未接线（孤儿组件 / 死代码）
- **判据**：存在组件/模块/命令的**定义**但全仓库无**引用**；或定义了回调却没传
- **确认**：全局搜该标识符，只出现在自身定义与导出处 → 确认。
  **注意动态引用**（注册表、字符串拼接、构建配置自动扫描）
- **典型**：`PluginSettingsDrawer.tsx` 全仓库唯一命中自身 → Vite 模式「设置」按钮永不出现
- **修法**：接线，或删除并在文档里去掉该承诺
- **定级**：无降级。声明了却完全不可用 = 对外承诺完全失效

### C-02 (P1) 双实现 / 多栈能力不对等
- **判据**：README 或注释声称两套实现（原生/构建版、A 语言/B 语言、新旧并存）行为一致
- **确认**：把两套入口的功能点列成**两列逐项比对**，重点比对
  **回调 / 钩子 / props / 命令注册**四类接线
- **典型**：React 外壳比无构建外壳少 4 个回调（设置抽屉、侧边栏注入、
  快捷键转发、CSP 上报）→ 焦点进 iframe 后 ⌘B/R/, 全失效
- **降级**：差异只在不影响功能的呈现细节（文案、顺序）→ P2

### C-03 (P1) 文档默认值 / 数量 / 清单与代码不符
- **判据**：文档写「默认 X」「共 N 个」「M 套」，代码里是另一个值
- **确认**：定位代码里的常量/数组，数一遍
- **典型**：README 说 22 套主题，`PRESET_THEMES` 实际 23 条；
  README 说 4 个测试脚本，package.json 里 13 个
- **降级**：数量差 1 且不影响理解 → P2

### C-04 (P0) 文档把缺陷记为设计意图
- **判据**：文档描述某行为为「设计如此 / 已修复 / 已知限制」，实际是 bug 且未修
- **确认**：按文档描述的路径去代码里找对应实现，看它是否真的做了
- **典型**：README 声称「隔离后由插件自报基调，已修复」，实际自报字段没接上
- **定级**：P0。它会**阻止下一个人修复**

### C-05 (P0) 接口字段声明但从未被赋值/读取（死契约）
- **正确**：实现它，或连同 README/JSDoc 声明一起删
- **特征**：接口字段在模块内只出现 1 次（声明处）
- **确认**：同目录其他文件是否使用

### C-06 (P0/P2) 参数声明但函数体内从未使用
- **正确**：用起来或删除
- **特征**：类方法 / 独立函数 / 箭头方法三种形态
- **降级**：刻意保留的签名参数（接口一致性）→ P2 或忽略

### C-07 (P1) 文档未覆盖主要模块
- **判据**：仓库里有大模块（行数占比 >10%）在文档里完全没有章节
- **确认**：模块表 vs 文档目录，逐个对

### C-08 (P1) 注释与代码矛盾
- **判据**：注释说做了 X，代码没做（或做了相反的 Y）
- **确认**：**先确认自己没读错注释**——很多注释是在解释「为什么不能那样写」
- **降级**：注释描述历史行为、代码后来改过 → P2，改注释即可

### C-09 (P1) 同名常量清单重复定义且已分叉
- **判据**：同一语义的清单（变量白名单、主题变量表、命令列表）在两处各定义一份，内容不同
- **确认**：diff 两份清单，确认哪份是权威来源
- **典型**：`host.js` 的 `THEME_VARS` 与 `themes.js` 的 `THEME_VARS` 已分叉，
  导致插件拿到的主题快照缺一大半变量
- **降级**：**不同插件各自定义同名常量是常态**（取值本就不同）→ 忽略。
  只有**同一区域内**出现不同取值才算分叉

### C-10 (P2) 清单遗漏
- **判据**：CSS/代码里定义了某变量，但主题/配置清单里没列
- **后果**：该变量无法被主题覆盖 + 切主题时不会被清理（残留旧值）
- **典型**：CSS 定义了 `--r: 14px`，`THEME_VARS` 只有 `--r-md`

### C-11 (P1) 多订阅者互相顶掉
- **正确**：数组或 Set 存订阅者，`on()` 返回取消函数
- **特征**：`this._onXxx = fn` 直接赋值 → 第二个订阅者顶掉第一个

### C-12 (P1) 成对 API 校验不对称
- **正确**：抽 `private _normalize(raw)`，所有入口共用
- **特征**：`set`/`add`、`register`/`import`、`preview`/`upgrade` 一个有校验一个没有
- **注意**：需两个成员都出现才触发
- **规律**：**后加的便捷入口最容易漏校验**

### C-13 (P2) 死代码 / 重复实现（未被模块声明引用）
- **判据**：源文件存在但未被任何模块声明（`mod`）/ 构建入口引用
- **确认**：动态引用、待启用备份除外
- **定级**：**两份内容近似但已分叉的重复文件最危险**（改了不生效）→ 升 P1
- **典型**：`src/af.rs` 与 `src/fpx/af_flow.rs` 内容近似，`fpx/` 那份是死代码副本

## 文档一致性扫描

```bash
python3 scripts/doc-promise.py --src=<根>                 # 承诺 vs 实现
python3 scripts/doc-promise.py --src=<根> --commands-only # 只查命令是否存在
python3 scripts/doc-deliverable.py --src=<根> --missing-only  # 单元三件套是否齐全
```

三类候选**全部需人工核对**：

1. **命令不存在** —— README 写 `npm run xxx`，package.json 里没有 → 文档说谎
2. **引用文件不存在** —— README 目录树写了某路径，实际没有 → 断链
   （文档常只写文件名不写完整路径，扫描器会按 basename 全仓库兜底找）
3. **数量声明待核对** —— README 说「22 套」，代码里数出 23 → 口径不一致

第 3 类最容易被忽略但最伤人。

## 双实现比对（高产区，C-02 的展开）

存在两套实现时**必须做差异比对**，不能只看其中一条。比对清单：

```
□ 入口文件各自加载了什么
□ 宿主的回调/hooks 各实现了哪些（逐个列，不要凭印象）
□ 扩展的可用能力集合是否一致
□ 配置项是否一致（一套有的设置项另一套没有）
□ 快捷键/命令注册是否一致
□ 状态持久化是否共用同一份存储
□ 构建产物里是否都带上了（硬编码清单最常在这里出问题）
```

**最快的方法**：把两套的钩子实现名单列成两列，逐个 grep 确认。

## 「扩展取不到宿主状态」的三类根因

| 根因 | 判据 | 症状 |
|---|---|---|
| 宿主状态挂在**主窗口**全局对象上 | `window.__XXX__` | 沙箱里取不到 → **静默空** |
| 宿主没在桥接里暴露该能力 | 桥接方法表里没有 | 隔离态下取不到 |
| 上下文快照在挂载时拷贝，之后不更新 | `theme: readTheme()` | 状态变更后读到旧值 |

**「扩展自己另开监听器绕过」是强信号** —— 说明官方通道缺失，看到就该报。

## 常见误报

- **动态引用** —— 注册表、构建配置自动扫描会让静态分析误判为孤儿
- **不同插件各自定义同名常量** —— 见 C-09 降级条件
- **注释解释了为什么那样写** —— 先读注释
- **按栈分流的隐藏** —— 某些条目在特定模式下故意隐藏


## 人工检查项


### C-14 (P1/P0) 预览所见 ≠ 实际所执行（确认的是另一件事）
- **判据**：`--dry-run` / 预览 / 二次确认界面展示的**对比基准**，
  与真正执行时用的基准不是同一个对象
- **确认**：分别打印「预览的基准」与「执行的基准」，看是否指向同一版本/同一分支/同一快照
- **典型**：预览跑 `git diff HEAD`（本地快照），推送却以 `base_tree=远端最新` 为底 ——
  远端比本地新时，**用户确认的内容和他推上去的内容不是一回事**
- **同类形态**：预览按本地时间算、执行按服务端时间算；
  预览读缓存、执行读实时；预览单条、执行批量
- **修法**：预览必须与执行共用同一个基准对象；做不到就在预览里**显式标注基准是什么**
- **定级**：用户据此做**不可逆决定**（覆盖、删除、覆盖他人改动）→ **P0**；否则 P1
- **为什么易漏**：两边都「看起来合理」，只有把两个基准并排写出来才看得出分叉

### H-03 安全增强把回归测试打挂了（静默失效）

给代码加安全校验（来源校验、鉴权、白名单）后，**测试构造的假数据可能不再满足新条件**，
于是行为层断言失效 —— 而源码层断言（搜文本）仍然绿，CI 看不出异常。

**检查方法**：新增/收紧任何入口校验后，回头跑一遍行为层测试，
确认失败数是 0 且**行为断言真的执行了**（不只是"没报错"）。

**实例**：2026-09-14 nexus-panel。`plugin-sdk.js:514` 新增
`if (e.source !== window.parent) return;`，而 `handshake-test.mjs:69`
构造 `MessageEvent` 时没设 `source` → `null !== window.parent` → 直接 return。
实测：`通过 9 项，失败 3 项`，且失败的全是行为层
（"收到 mount 后执行了挂载" / "挂载后回发 mounted" / "重复 mount 幂等"）。
**源码层 6 项全绿，所以不至于全瞎，但行为覆盖归零了。**

**修法**：
```js
const ev = new sdkWin.MessageEvent('message', { data: {...}, source: sdkWin.parent });
```

**同类**：断言依赖源码文本距离的测试也很脆 —— `shell-audit-test.mjs` 断言
`expected.is_empty()` 到 `BROWSER_GUARD_HEADER` 的距离 ≤200 字符，
实际 300（中间隔了 6 行注释）→ 代码是对的，断言过时了。
先剥注释再匹配，或放宽窗口。


### H-04 发现一个 bug 后，主动搜「同源副本」

复制粘贴的代码会**成簇出错**。修一个之前先搜同结构的地方，否则修完还有第二个。

**检查方法**：定位到 bug 的**结构特征**（不是字面），用它去搜全项目。

**实例**：2026-09-14 nexus-panel。`plugin-config.js:60` 的订阅函数
注册匿名箭头、注销 `fn` 本身（引用不同 → 注销失效）。
用结构特征 `addEventListener?.(..., (e) => fn(` 去搜，
发现 `external-policy.js:100` 的 `onPolicyChange` **结构完全一样**。

两处实测（真实 EventTarget，会比对函数引用）：
```
onPluginConfigChange：off() 后派发，回调被调用 1 次 → ❌
onPolicyChange：      off() 后派发，回调被调用 1 次 → ❌
```

而且两处**都零调用** —— 「没接线」和「注销 bug」叠加，
一旦接线泄漏立刻生效。源报告只报了前者。

### H-05 安全清单的前后端副本分叉

同一份安全清单在前后端各存一份，迟早分叉；分叉后**通常只有一份生效**，
另一份是过期副本。风险不在当下，在于有人误以为它生效。

**检查方法**：找前端的 `FORBIDDEN` / `BLOCKED` / `DENY` / `ALLOW` 常量，
与后端同名常量逐条比对。

**实例**：同上。前端 `FS_FORBIDDEN`（11 条，**零引用**）vs
后端 `FORBIDDEN_DELETE`（16 条，生效）。后端多
`/lib` `/boot` `/root` `/program files` `c:\program files` 5 条。
当前后端生效所以无漏洞，但如果有人调用前端那份做预校验，保护就缺 5 条。


### H-08 「已核实为干净」的维度也要反向抽查

报告里"查过、没问题"的清单**风险最高**：结论错了就不会再有人复查。
抽查方法不是重跑一遍，而是**验证它的否定面是否真的成立**。

**实例 A（数字对但口径要澄清）**：报告称 `setInterval` 全部配对。
实测 `grep setInterval` = 8、`clearInterval` = 5，看似 3 处未配对。逐个查：
| 位置 | 实际 |
|---|---|
| `ToolsPanel.tsx:388/466` | **不是定时器** —— `const [interval, setInterval] = useState(...)` 是 React state setter |
| `tab-drag.js:239` | 注释「用 rAF 而不是 setInterval」，不是调用 |
| 其余 4 处 | ✅ 真配对 |

**结论成立**，但数字口径必须写进报告，否则下轮按字面复查会以为报告错了。
→ 这条也是扫描器已知误报模式：**`setInterval` 可能是 React state setter 名**。

**实例 B（表述要限定范围）**：报告称「自研代码零 `console.log`」。
实测全项目 2 处，都在 `plugins/demo-module/`。若"自研代码"排除 demo 插件则成立
——**但表述必须写明排除范围**，否则就是个等着被推翻的结论。

### H-09 属性驱动的 innerHTML（直接赋值扫描会漏）

扫 `innerHTML =` 只能找到**字面赋值点**，找不到**属性驱动**的：
```js
else if (k === 'html') el.innerHTML = v;   // h() 的 html: 属性直通
```
这是 hyperscript 的常见设计，**当前无风险**（唯一调用方传静态字符串），
但它是**无转义的公开 API 且无警示**——将来有人传模板变量就是 XSS。

**检查方法**：除了 `innerHTML`，还要搜 `html:` / `dangerouslySetInnerHTML` /
`insertAdjacentHTML` / `outerHTML`，并确认**每个调用方传的是字面量还是变量**。

**修法**：不加转义（会破坏"传 HTML"的语义），改为在 JSDoc 写明
「仅接受可信 HTML，传用户输入前必须自行 escapeHtml」。


### H-10 「测试全绿但功能未接线」——单测覆盖不到的失效模式

**单元测试验证的是"函数对不对"，没人验证"有没有被用上"。**
一个函数可以有 9 条用例全部通过，同时在**生产代码里零调用**。

**这类问题的共性**：
- 迁移函数（`migrate*` / `upgrade*` / `backfill*`）—— 最危险，**不调用就静默丢数据**
- 执行器 / 适配器注入（`xxxFetch` / `xxxPush` / `xxxHandler`）
- 校验函数（`validate*`）—— 不调用 = 输入无校验
- 工厂函数（`make*`）

**检查方法**：统计每个导出的**生产代码**引用数（排除 tests），
对"仅测试引用"的导出发出告警。注意收紧口径：
排除定义文件内的自调用、排除 `import *` 的使用。

**实例 A（后果最重）**：2026-09-14 nexus-panel。
`credentialStore.ts:157` 的 `migratePlaintext` 注释写着
「把历史遗留的明文密钥加密…用户无感，也不用手工重新填一遍」，
**生产代码 0 处调用**，只有 `tests/crypto.test.ts` 引用 6 次。

完整失效链（三处代码各自都"合理"，合起来丢数据）：
1. `decryptStore` 丢弃非密文 → `out.push({...sc, secret: ''})`
   （这本身对：非密文不该被当明文返回）
2. 保存副作用把空值写回磁盘；`encryptStore` 对空密钥不加密 → 空值持久化
3. 本该救场的 `migratePlaintext` 从未被调用

**用户视角**：凭据面板显示 secret 为空 → 以为是"从没填过"；
`failed` 列表也为空 → 界面不报警。**632 个测试全绿**。

**实例 B**：`runner.ts` 定义了 `githubFetch` / `githubPush` 接口并在缺失时**明确报错**
（"未提供 GitHub 拉取执行器"），但生产代码**零处注入**。
而 `App.tsx` 的默认工作流模板里就用了这个节点 → **用户拖出来一跑必然失败**。

> **关键区分**：这类问题**不是**"代码写错了"，而是"代码没接上"。
> 静态扫描能发现，跑测试发现不了。

### H-11 同一威胁模型下，新组件没跟上老组件的加固

项目里已有组件针对某种攻击做了加固，**后加的同类组件往往一条都没跟上**。
对比两个组件的防护清单，差异项就是漏洞。

**检查方法**：找到已加固组件的防护清单（通常在头部注释里写明原理），
逐条去新组件里找对应项。

**实例**：同上。`af_flow.rs` 的 webhook 面对"浏览器跨站触发"已加固，
且其注释写明了原理：
> `<img>`/`<script>`/`<form>` 根本没法加自定义头；`fetch` 加了自定义头 →
> 浏览器先发 OPTIONS 预检 → **本服务不处理 OPTIONS → 预检失败 → 请求发不出去**

| 防线 | webhook（已加固） | MCP（后加） |
|---|---|---|
| 自定义头校验 | ✅ 要求 `x-nexus-webhook` | ❌ 无 |
| token | ✅ 有（空时自动生成随机） | ❌ 完全没有 |
| OPTIONS | ✅ **不处理** → 预检失败 | ❌ **返回 204** → 预检通过 |
| CORS | 无（不需要） | ❌ `ACAO:*` + `ACAH:*` |

**MCP 把这条链路的每一环都反着做了。**

两个易漏点：
- **服务端不检查 `Content-Type`** → 攻击者发 `text/plain`（浏览器归为简单请求，
  **不触发预检**），服务端照样按 JSON 解析 → **连预检这关都绕过了**
- **默认全开**：`cfg.mcp_tools.get(name).copied().unwrap_or(true)` ——
  配置没写就是开启，而默认配置为空 → **所有工具默认可用**


### H-12 根目录配置：扫子目录项目时会整片漏掉

**.github / .editorconfig / lint 配置 / 安全策略 / Dockerfile 通常在仓库根目录，
不在被审的子目录里。** 按子目录过滤会把它们全部跳过。

**实例（我自己的教训）**：审 `tauriTools` 时我只解压 `nexus-panel/` 子目录
（过滤条件 `'/nexus-panel/' in path`），于是连续六轮报告都写「无 CI」。
**实际 CI 一直存在** —— `.github/workflows/ci.yml` 在仓库根，
而且它第一步就挂了（见 H-13）。**"没有 CI"和"CI 是死的"是完全不同的结论**，
我因为漏扫给出了后者，还把它当成了前者。

**检查方法**：拿到仓库后先 `tar -tzf` 或列顶层目录**确认完整结构**，
再决定扫描范围。子目录项目要**额外扫一次根目录**。

### H-13 CI 自身可能从未成功过——先验第一步

**CI 文件存在 ≠ CI 在起作用。** 一个 step 引用的脚本不存在 → 退出码 1 →
`fail-fast` 下**后续 step 全部跳过** → 之后的检查一次都没跑过。

**检查方法（成本极低）**：把 CI 里每个 `run:` 命令**在本地原样跑一遍**，看退出码。

**实例**：同上。`ci.yml` 第一步 `npm run config:check`，
而 `package.json` 里没这条 script：
```
$ npm run config:check
npm error Missing script: "config:check"
退出码: 1
```
结果：跨端契约检查、Vite 构建、三个冒烟测试**从未执行**。

**最讽刺的是 CI 自己的注释**：
```yaml
# 手改一处忘一处是老毛病，这一步挡住漂移
- name: 配置漂移检查
  run: npm run config:check        # ← 挡漂移的这一步，自己就没接上
```

**两个加重信号**（出现了就基本可以确认）：
1. **脚本文件还在，只是 npm 入口没了** → 说明是入口被误删，不是功能移除
2. **README 也还在引用这个命令** → 说明"入口应该存在"是被公认的

**同类风险**：CI 里跑了测试，但**只跑了一部分**（本项目只跑 3/24 个测试脚本，
且最关键的 `test:xss` / `test:handshake` 都不在其中）。
要逐条比对「已接线脚本」与「CI 实际跑的脚本」。

### H-14 诊断工具自己的行号可能不准（剥离文本未映射）

自研的 lint / audit 工具常先做文本预处理（剥注释、去空行、展开宏），
**然后在处理后的文本上算行号** → 报告位置与实际位置系统性偏移。

**检查方法**：工具报了一个位置 → **立刻去原始文件该行核对**。
对不上就是行号映射有 bug，此时**工具报的所有位置都不可信**。

**实例**：2026-09-14 nexus-panel 的 `js/style-audit.js:80`：
```js
const text = String(css || '').replace(/\/\*[\s\S]*?\*\//g, '');
const lineOf = (i) => text.slice(0, i).split('\n').length;
```
块注释被替换成**空字符串**（而非等行数换行）→ 行结构丢失，
但 `lineOf` 仍在这份已删减的文本上算行号。

实测偏差：agent-flow 报 L1210 / 实际 L1290（**80 行**）；
project-group 报 L192 / 实际 L207（**15 行**）。

**确认根因的方法**：复刻同样的预处理，数目标在**处理后**文本里的行号，
若与工具报告一致 → 确认是映射问题。
（本例复刻 `replace` 后得 L1210 与 L192，**与报告完全一致**）

**修法**：剥离时替换成**等行数换行**而非空串，或记录偏移量映射回原始行号。

**连带影响**：行号不准 + 存在误报时，**误报会掩盖真缺陷**。
本例中 `var-未定义@L1210` 是真缺陷（拼写错误的变量名），
另两条（`--tag-hover` / `--tag-press` 由 React 内联 style 注入）是误报
—— 三者混在一起，真缺陷很容易被一并忽略。
