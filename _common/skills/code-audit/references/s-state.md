# 场景：状态与配置（s-state）

**触发**：有 store / 序列化 / 配置快照 / 主题系统 / 能力探测。
**风险**：反序列化无兜底导致整块数据不可用、快照不随状态更新、降级后永不重试、
内联样式压过后续注入。

`overlaps:` **只管状态本身的正确性与新鲜度**。
状态容器的**容量上限**归 `s-structures`；配置项参与**数值运算**归 `s-numerics`；
配置项是否**被文档正确描述**归 `s-contracts`；持久化到**后端文件**归 `s-backend`。

## 模式清单

### T-01 (P2/P1) 存储反序列化无兜底
- **正确**：`try { return JSON.parse(raw) } catch { return defaultValue }`
- **特征**：`JSON.parse(localStorage.getItem(...))` 无 try/catch
- **确认**：一条脏数据（历史版本写入、手工改过）是否让**整个** store 不可用
- **定级**：影响范围是「该模块全部持久化数据」→ **P1**
- **兜底要挡三层，不是一层**（实战最常见的漏法：只挡了第一层）
  | 层 | 要挡什么 | 漏了会怎样 |
  |---|---|---|
  | ① 语法 | 能不能解析 | 已覆盖（本条正文） |
  | ② **类型** | 是不是预期的结构 | **合法 JSON 但结构不对 → 裸 `AttributeError`** |
  | ③ **打开** | `open` / 读取本身会不会抛 | 路径是目录 → `IsADirectoryError`；是 FIFO → **挂死** |
- **类型层必须查的四类**：
  ① 顶层是不是对象（`[1,2,3]` / `"hello"` / `42` 都是合法 JSON）
  ② 已知字段的类型对不对（`files` 是列表而非字典）
  ③ **是不是 `null`** —— `json.load` 返回 `None` 与「文件不存在」是同一个信号，
  放过去会**静默引导用户重建**，把唯一能判断「远端是否被改过」的参照丢掉
  ④ 路径**是不是常规文件**（`stat` + `S_ISREG`，挡住目录、FIFO、`/dev/zero`）
- **实测**：状态文件路径被 `mkdir` 成目录 → 裸 `IsADirectoryError`；
  `/dev/null` → 走语法错被拦下 ✅；自引用软链 → `os.path.exists` 返回 False，
  当作「没有基线」（理论上是静默丢参照，但现实中碰不到，不值得加代码）
- **确认**：写 8~10 个「**合法 JSON 但结构不对**」的样本逐个喂进去，看有没有裸崩

⑤ **枚举字段是否在取值白名单内**
  状态文件里的模式 / 类型 / 版本字段（`workflow` / `kind` / `version`），
  缺白名单校验时，任何非法值都会落到调用方的 `else` 分支。
  **若那个 `else` 恰好是危险路径**（直推主干、跳过校验），
  一次手改 / 一次旧版本写入就等于关掉防护，且零报错。
  确认：把每个枚举字段的合法取值列出来，逐个构造非法值喂进去，
  看是被明确拒绝，还是静默落到某个分支。

### T-02 (P2) 变更监听器解绑失效
- **判据**：注册时包了箭头函数 `addEventListener(E, e => fn(...))`，
  解绑时却传原始 `fn` → 永远摘不掉
- **确认**：看 `onXxxChange` 的返回值是否真能停止回调
- **定级**：每次调用累积一个监听器，且回调里有重活 → **P1**

### T-03 (P2/P1) 降级后不重试
- **判据**：能力探测失败后把 `null` 写进「已缓存」标志，后续永不重试
- **确认**：该能力是否可能在初始化之后才就绪（异步注入、延迟加载）。是 → **P1**
- **典型**：`if (_cache !== undefined) return _cache;` 且 `_cache` 被赋过 null

### T-04 (P2) 快照不随状态更新
- **判据**：上下文对象在挂载时拷贝一份状态快照（如 `theme`），状态变更后不更新
- **确认**：看消费方是否**被迫自己另开监听器绕过**（**这是强信号**）
- **典型**：插件为了拿主题变更自己再注册一个 message 监听器，与 SDK 内置监听器并存

### T-05 (P2) 内联样式压过后续动态注入
- **判据**：首屏/兜底逻辑用 `element.style.xxx = v` 而非注入 `<style>`
- **确认**：内联样式优先级最高，后续主题系统写 CSS 变量覆盖不住
- **典型**：首屏防闪用内联 `background` → 切到浅色主题后底色卡在深色那一版
- **降级**：该值后续不会再变 → 忽略

### T-06 (P1) 状态字段只有置 true 没有复位
（与 `s-lifecycle` L-10 同源，此处从「状态机是否正确」角度记一次；
按实际影响定级，不要两边都报。）

### T-07 (P2) 配置项默认值与文档不符
（与 `s-contracts` C-03 同源。若已按 C-03 报，此处不重复。）

### T-08 (P1) 配置迁移 / 版本兼容缺失
- **判据**：持久化结构变更但无 version 字段、无迁移路径
- **确认**：老版本数据加载后是否静默产生错误结构（而非报错）
- **定级**：静默损坏 → P0；报错（能被发现） → P1

- **相邻形态：新增防护依赖**新增字段**，而存量数据没有该字段**：
  ```python
  old = state.get("local_head")
  if not old:
      return False, None        # 没记过 → 跳过，不猜
  ```
  字段缺失时「跳过」看似稳妥，实际是**这道防护对全部存量状态文件一律不生效**，
  且**没有任何提示** —— 用户以为装了防护，其实是空的。
  要等下一次成功同步把字段补上，防护才真正启用
- **与本体（T-08）的区别**：T-08 是**老数据结构**加载后**坏掉**；
  本形态是结构**没坏**、迁移也做了，只是**新增能力在存量数据上空转**。
  后者更安静：没有报错、没有异常，只有「防护本该拦住却没拦住」
- **确认**：新增一个持久化字段时，问「**存量数据没有它时会怎样**」——
  若答案是「某项防护不生效」，必须打印一行说明，不能静默跳过
- **定级**：P2（防护空转）→ 若该防护防的是**不可逆操作** → **P1**

### T-09 (P2) 状态写入非原子（部分成功）
（与 `s-atomicity` A-01 同源。状态机跨多个字段时优先归 `s-atomicity`。）

### T-10 (P1) 主题/配置快照缺项导致能力失效
- **判据**：快照清单遗漏了实际使用的变量/字段（同 `s-contracts` C-10）
- **后果**：该变量无法被覆盖 + 切换时不会被清理（残留旧值）
- **典型**：`THEME_VARS` 两份清单已分叉 → 插件拿到的主题快照缺一大半变量

### T-11 (P1) 基线快照维度不全（只记内容不记元数据）
- **判据**：比对基线只存内容哈希（blob sha / 内容 md5），不存 mode、类型、时间戳
- **确认**：**只改元数据、不改内容**（如 `chmod +x`）时，比对判为「一致」→ 跳过
  → 该变更永远推不上去**且不报错**
- **典型**：`if lsha == rsha: continue  # 内容已一致，跳过` ——
  用户改了可执行位，脚本说「已一致」，远端 mode 始终不变
- **修法**：比对改用元组 `(mode, sha)`；基线结构变更时加 `version` 字段并留迁移路径
- **定级**：变更静默丢失 → P1；若丢的是权限/可执行性这类安全相关属性 → **P0**
- **修一处漏一处（易复发）**：修这条时只改了**主校验**那一处，入口的「要不要处理」判据还是老写法（只比 sha）→
  变更既推不上去也拉不下来，且 `--pull` 报「没有需要合并的」
- **确认**：改完主校验后，**回查所有比对的入口**（待推送集合 / 待拉取集合 / 跳过判断），逐个改成比 `(mode, sha)`
- **扩散面：同一判据的**所有**使用点，包括一次性工具脚本**（实测踩到）：
  审查某脚本时把「用 `os.stat().st_mode & 0o111` 判 git mode」记成了缺陷，
  该脚本也确实加了 5 样本探测来修它 —— 但**审查者自己写的推送工具**里
  还是同一个判据，没有任何防护。沙盒（virtiofs）上一律 0777，判据恒为真，
  于是把 9 个 .md / .json 全推成了 100755。
  **判据**：一条判据被写进技能之后，**回查所有用到它的代码** ——
  含一次性脚本、CI、迁移工具、自己的辅助脚本。写下来 ≠ 已经应用。
  **为什么难自查**：修的时候注意力在「被审对象」，工具代码不在视野内；
  而工具恰恰最常跑在特殊环境（容器 / 挂载盘 / CI）里，正是判据最容易失效的地方。

### T-12 (P1) 自污染输入（回读自身上一次的产出作默认值）
- **判据**：程序把「自己上一次写入的值」读回来当默认输入，形成闭环
- **确认**：连跑两轮，看第二轮的输入是否等于第一轮的输出。是 → 值被固化
- **典型**：推送脚本用 `git log -1 --format=%B` 取提交信息，
  而它自己在推送成功后会补一个同信息的 commit →
  **从第二次起所有提交信息完全相同**，且没人报错
- **修法**：优先级必须是「显式入参 > 交互输入 > 自动生成」，
  且自动生成**不得回读自身产出**（用文件清单等外部事实兜底）
- **注意**：这类缺陷**第一轮表现正常**，只在第二次起暴露，手工测试极易漏

### T-14 (P2) 同步声明的作用范围大于实际同步的范围
- **判据**：「已同步 / 已包含远端全部改动 / 已是最新」这类**全局声明**，
  实际只同步了子集（用户点名了几个文件、或待处理集合本来就是空的）
- **确认**：让它声明「已同步」，然后检查**未被本次处理**的对象是否真的也同步了。
  有任何一个没同步 → 声明是假的
- **典型**：`if not conflicted: state["synced_commit"] = head_sha` ——
  判据只看「没冲突」，不看「处理了几个」。于是
  `--pull 不存在的文件`（循环里 continue，冲突数为 0）和
  `--pull 单个文件`（其余文件的远端改动根本没拉）都会声明
  「✅ 本地已包含远端全部改动，可直接推送」
- **为什么仍有危害（即便下游会拦）**：下游的文件级校验确实可能拦住实际覆盖，
  但用户已经**读到一句假的状态声明**，据此跳过真正的同步步骤，
  然后在下一步被拦住、排查方向整个偏掉。谎报状态本身就是缺陷
- **修法**：只有「已处理集合 ⊇ 远端相对基线变过的全部对象」时才做全局声明；
  拉子集或集合为空时，只报「本次合并 N 个」，不声明全局同步
- **同类**：增量拉取后声称「已全量」、缓存预热了一部分就标记「已就绪」、
  迁移了部分表就声明「迁移完成」
- **定级**：P2（谎报状态、误导排查）；若下游无兜底、直接据此覆盖 → **P1**

- **加重形态：声明时把**证据字段**一起覆盖了**（P0，比谎报更严重）：
  ```python
  state["synced_commit"] = head_sha
  state["local_head"] = _local_head()      # ← 把「回退证据」改写成当前 HEAD
  ```
  不仅谎报「已同步」，还**顺手抹掉了能证明它在撒谎的那份数据**。
  后果从「误导排查」升级为「**下一次再也检测不到**」：
  防护依赖 `local_head` 判断是否回退，而这一行正好把它写成了回退后的值，
  于是后续所有检测都看到「一切正常」→ 静默覆盖真实发生
- **为什么这条最狠**：谎报状态至少留下了线索（下次检测还能发现）；
  **改写证据则连线索都没了** —— 用户和工具都无从知道发生过什么
- **确认**：凡是「声明状态已达成」的代码，检查它**同时写入了哪些字段**；
  若其中有**用于检测该状态是否真的达成的判据字段**，就是本形态
- **修法**：判定不通过时**只 return，不写任何字段** —— 保留证据比推进流程重要
- **同批实例**：三处「声明已同步」（`init_baseline` / `pull` / `mark_synced`），
  只有 `init_baseline` 真的比过本地 vs 远端（不一致直接拒绝建基线），
  另两处漏了同一个校验 —— 见 A-22

### T-13 (P1) 状态更新被提前 return 跳过（分支工作流不落盘主状态）
- **判据**：函数有多个提前 `return` 的分支（预演 / 暂存 / 攒批 / 错误处理），
  而状态或基线的更新代码只写在**最后那一路**
- **确认**：把每个提前 `return` 的分支都走一遍，检查状态**是否落盘**。
  未落盘 → 后续流程读到的是上一次的旧状态
- **典型**：推送流程在「攒批」分支直接 `return`，基线更新代码在它之后 →
  基线停在旧版本 → 之后做三方合并时拿旧版本当合并基 →
  **同一个人的连续两次改动被判成互相冲突**（本地文件被写进冲突标记）
- **同类**：`--dry-run` 之外的分支也跳过落盘；错误处理分支 `return` 前忘了保存
- **修法**：把状态更新**提到所有分支之前**，让全部工作流共用一条落盘路径；
  提前 return 只允许发生在「确实无需记录」的分支上，且要写明理由
- **与 T-11 的区别**：T-11 管基线**记哪些维度**，本条管**记不记**
- **定级**：P1（数据不丢，但把用户推进手工修复流程）
- **镜像形态：预演在校验之前就 return（易漏）**
  不只是「状态没落盘」—— **`--dry-run` 分支若排在校验之前 return**，
  预演就**跑不完所有校验**，拍不出必然发生的失败 →
  「预演通过」给用户虚假信心
- **实测**：大文件预检排在 `--dry-run` 判断之后 →
  `--dry-run` 拍不出「这个文件 12MB 会被拒」，用户得真推一次才知道
- **确认**：给 dry-run 喂一个**必然失败**的用例（超大文件 / 非法参数），
  看它报不报。不报 = 预演提前 return 了
- **修法**：预检**提到 dry-run 判断之前**；dry-run 时只打印警告不中止
- **相邻形态**：预览与执行**两边基准不同**（预览用一个基准、执行用另一个）
  是另一类问题，与本条不同 —— 本条是「预演**压根没跑完校验**」。
  两类都要查

### T-15 (P0) 预演开关的作用范围小于命令集
- **判据**：`--dry-run` / `--check` / `--plan` 这类预演开关只在**主流程末段**
  判断，而**子命令分发在它之前** → 破坏性子命令照常执行。
  常伴随第二个症状：预演时**不持锁**（`enabled=not dry`），
  于是预演与实际运行走的是两条不同的并发路径
- **与 T-13 的分界**：T-13 是「预演没跑完**校验**」（少报风险）；
  本条是「预演没拦住**动作**」（直接造成副作用）。前者给虚假信心，后者真删东西
- **确认**：把**每个**子命令与 `--dry-run` 组合一遍，逐个问「它改了什么」：
  删除、合并、拉取、写状态、改配置 —— 只要有一个真实生效即为命中。
  别只看主推送/主执行路径
- **实测**：推送脚本 `--dry-run --delete-branch <名字>` **真的删掉了远端分支**；
  `--dry-run --merge` 真的合并 PR；`--dry-run --pull` 真的改写本地工作区。
  三者还有一个共同点：`main()` 里锁的开关写成 `enabled=not dry`，
  预演时**无锁**，与真实运行的并发行为不一致
- **修法**：在子命令分发**之前**做一次门禁，白名单放行只读与纯预演路径：
  ```python
  MUTATING = ("merge", "close_pr", "pull", "resolve", "delete_branch", ...)
  if dry and any(opts[k] for k in MUTATING):
      raise SystemExit("--dry-run 只支持 …；上述子命令会真实改动，已拒绝执行")
  ```
  锁的开关与 `dry` **解耦**，改为「只要可能写就加锁」
- **定级 P0**：用户心智模型是「预演=无害只读」，实际造成**不可逆**改动（删远端分支）

## 检查方法

**逐个问「这个值在什么时刻被读、什么时候会变」**：

```
□ 初始值从哪来（默认 / 存储 / 探测）
□ 会在什么时机变（用户操作 / 外部事件 / 异步就绪）
□ 变更后谁会被通知（监听器 / 快照 / 重新读取）
□ 读失败会怎样（兜底 / 抛错 / 静默空）
□ 写入失败会怎样（回滚 / 部分成功 / 静默丢）
□ 结构变了老数据怎么办（迁移 / 兜底 / 损坏）
□ 提前 return 的分支有没有落盘？（T-13）
□ 「已同步」的声明，覆盖了全部对象还是只覆盖了子集？（T-14）
□ 预演开关挡住了每一个子命令吗？还是只挡了默认路径？（T-15 → P0）
□ 预演时的锁还在吗？锁的条件是「会不会写」还是「是不是预演」？（T-15 → P0）
□ 写状态的每个取值都有写入路径吗？外部降回去时本地跟着降吗？（→ A-25）
□ 这条判据，我自己的工具脚本里是不是还没按它改？（T-11 扩散面）
```

## 常见误报
