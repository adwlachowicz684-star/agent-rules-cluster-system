# 场景：跨边界通信（s-boundary）

**触发**：`postMessage` / IPC / 桥接层 / iframe / 事件总线 / 请求-响应协议。
**风险**：来源未校验、握手竞态、退订不精确、无超时悬挂、目标 origin 通配。

`overlaps:` **只管通道本身**（origin、握手、超时、消息格式）。
通道两端的**订阅是否成对清理**归 `s-lifecycle`；
通道能否被**被隔离方滥用**归 `s-sandbox`；
通道传的**数值**归 `s-numerics`。

---

## 四个必须

1. **必须校验来源** —— 接收侧 `e.source !== expected.contentWindow` 直接 return
2. **必须有去重/去重标记** —— 握手类消息只处理一次
3. **必须有超时兜底** —— 不能无限等响应
4. **必须有精确退订** —— 按订阅 id 而非事件名

---

## 模式清单

### B-01 (P1) 消息监听不校验来源
- **判据**：`addEventListener('message', h)` 的处理器里只校验数据字段，
  不校验 `e.source` / `e.origin`
- **确认**：该文档里是否嵌套了第三方 iframe 或引用第三方脚本。
  有 → 攻击者可伪造消息驱动内部流程
- **降级**：同文档内无第三方内容、且消息只触发幂等的展示逻辑 → P2

### B-02 (P0) 桥接/分发方法无白名单
（与 `s-sandbox` S-02 同源。**若已按 S-02 报，此处不重复**。
判定角度：S-02 关注「被隔离方能否自授权」，B-02 关注「动态派发本身是否安全」。）

### B-03 (P1) 握手竞态 / 重复握手
- **判据**：双向握手（ready ↔ init）里任一侧会对同一消息重复响应
- **确认**：画一次时序，看是否存在 `init → ready → init` 的环。
  **去重标记**是否每次实例重建
- **典型**：收到 init 就回发 ready，而 ready 又触发对端发 init → 无限往返，
  每轮重建上下文与订阅

### B-04 (P1) 订阅退订不精确
- **判据**：退订时按**事件名**匹配摘除（常见 LIFO 取最近一个），而不是按订阅 id
- **确认**：构造「同一事件订阅两次、以不同顺序退订」的路径，看是否会摘错 handler
- **典型**：改一次设置就多一个 handler → 按一次快捷键执行两次

### B-05 (P1) postMessage 目标 origin 通配
- **判据**：`postMessage(data, '*')`
- **确认**：消息里是否含敏感数据（主题变量、配置、DOM 结构）。
  含 → P2；含凭据/路径 → **P1**

### B-06 (P2/P1) 请求-响应无超时或超时未清理
- **判据**：pending Map 里的请求只有「成功回调时删除」，无超时兜底
- **确认**：对端崩溃/不发响应时是否永久悬挂
- **定级**：pending 随用户操作持续增长 → **P1**（内存泄漏）

### B-07 (P2) 错误消息透出内部细节
- **判据**：错误信息里回显完整本地路径、堆栈、配置内容
- **降级**：纯本地工具、无网络出口 → P3

### B-08 (P1) 消息格式无版本 / 无校验
- **判据**：消息体直接解构使用，无 type 判别 / 版本字段 / 字段存在性检查
- **确认**：对端版本不一致时是否静默产生错误行为

### B-09 (P1) 返回值未过滤不可克隆字段
- **判据**：桥接返回值里含函数 / Symbol / DOM 节点
- **失效**：`structuredClone` 抛错，**整条响应失败而不只是该字段**

### B-10 (P1) 响应成功判定不靠状态码
- **判据**：按「字段存在性」判成功（`"sha" in resp` / `resp.get("ok")`）而**不看状态码**；
  或客户端吞掉错误（`curl -s` 不配 `-w`、fetch 不查 `res.ok`、SDK 默认不抛）
- **确认**：让服务端返回 403 / 422 的**错误体**，看调用方是否当成正常响应继续解析
- **典型**：`curl -s` 把 422 的 `{"message":"Validation Failed"}` 原样返回，
  解析后靠 `if "sha" not in blob` 猜；有的调用点直接 `resp["object"]["sha"]` → KeyError 崩栈
- **修法**：显式取状态码（`curl -w "\n%{http_code}"` / `res.ok`），
  非 2xx 一律中止并**回显响应体**（否则 403 和 422 的排查成本一样高）
- **附带判据（重试幂等性）**：重试是否区分方法 —— 对**非幂等 POST** 盲目重试，
  超时但已生效的请求会重复建对象 / 重复计账；5xx / 429 才值得退避重试
- **降级**：调用方对每个调用点都做了字段级校验且失败可观测 → P2

## 检查方法

对每个通道画一张表：

| 通道 | 发起方 | 接收方 | 是否校验来源 | 是否超时 | 是否可退订 | 载荷含敏感? |
|---|---|---|---|---|---|---|

**握手类消息单独画时序图**，确认没有环。

## 常见误报

- **B-01 同文档内无第三方内容** —— 降级 P2
- **B-05 载荷是公开常量** —— 降级
- **注释解释了为什么用 `'*'`**（如跨 origin 且 origin 动态）→ 确认后降级，
  但应改为动态传入具体 origin
