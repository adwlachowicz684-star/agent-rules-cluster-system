# 报告规则

## 报告结构：默认拆分，不写成一个大文件

**整机审查产出「一个目录」，不是一个文件。** 用 `assets/report-template-split.md`：

```
审查_<项目名>/
├── 00-索引.md                 ← 必写：文件表 + 各文件 P0/P1/P2 计数 + 最值得先看 5 条
├── 01-主窗口-<子系统>.md
├── NN-主窗口-构建与配置.md
└── NN-插件-<名称>.md
```

- **主窗口按子系统拆**（Vanilla 外壳 / React 外壳 / 原生后端 / 构建配置），
  不按文件类型拆
- **插件一个一份**；无问题的插件不建文件，只在索引记「已审 · 未发现问题」
- **≥5 个文件打包 zip 再交付**
- 单模块 / 小工具审查才用 `assets/report-template.md`（七节单文件版）

拆分报告的四条硬约束（详见模板）：

1. **只写问题，不写过程** —— 不写「上轮核对」「工具改进」「扫描统计」
2. 每条必须有**位置 + 后果**
3. **误报段必写** —— 扫描命中但人工确认不是问题的全记下来，防下轮重复排查
4. 同类问题**合并**成一条，位置列全

## 七节单文件版（仅单模块审查用）

按 `assets/report-template.md` 填充。七节：

1. **结论** —— 一两句话：核心做对了什么、问题集中在哪、是否阻断发布
2. **总览表** —— 各级别数量 + 模块 × 状态表
3. **问题清单** —— 按级别分组，每条给三件套 + 建议 + 影响面
4. **逐模块结论** —— 每个模块一行：阻断发布 / 需修 / 需加固 / 未发现问题
5. **验证过没问题的部分** —— **必写**，避免后续重复报已修问题
6. **架构裁决** —— 跨模块议题（平行实现、分工说明、全局一致性）
7. **附** —— 复现脚本、扫描基线、审查方式说明

## 修复任务清单格式

与报告分开（或作为独立章节），**可勾选、可派工**：

```markdown
### [编号] 级别 · 一句话问题

- **位置**：`文件:起止行`
- **证据**：实测输出 / 可验证推导链
- **后果**：什么场景暴露、什么症状
- **影响面**：同文件/同族的其他入口是否也有
- **修复要点**：具体改法（可直接粘贴的代码）
```

编号规则：`<族字母>-<两位序号>`（如 `M-01`、`R-03`、`A-04`），
跨模块议题用 `G-<序号>`。编号一旦分配不再变更（即使定级调整），
便于后续对照。

## 批次建议

清单末尾必须给**修复顺序**，按「依赖 + 收益」排：

```
第一批（阻断级）   —— 接线类、静默失效类，1~2 天
第二批（安全健壮） —— 资源上限、注入面、错误处理
第三批（一致性）   —— 清单统一、双实现对齐、文档
第四批（清理）     —— 死代码、构建脚本、CI
```

**同类问题聚批修**：同一族的几十条（如只注册不注销）作为一批，
不要拆成几十个任务。

## 必写的三件事

1. **审查方式与边界** —— 静态分析还是实测？跑过测试吗？
   没跑过就写明「未实测（静态分析）」与原因（如依赖装不齐、无工具链）
2. **验证过没问题的部分** —— 逐个列实测结果。这是后续复核最值钱的一节
3. **待验证项** —— 依赖运行时行为才能定论的，明确列出，让落地的人去验

## 审查方式声明（必写）

```markdown
> **验证方式说明**：本次为**静态代码审查**。沙盒环境无法访问 npm registry
> （依赖未装齐）、无 Rust 工具链，因此 `npm run test:*`、`tsc --noEmit`、
> `cargo check`、真机运行均未执行。清单中每条都标注了文件与行号，
> 落地前建议先本地跑一遍测试与真机验证。
```

**不得把静态分析伪装成实测。**

## 复核（针对已有报告）

1. 对照历史报告的每条结论，逐条确认「修了 / 没修 / 引入了新问题」
2. 修了的：实测复现一遍再关闭（台账「已修」不等于真修）
3. 引入新问题的：标 **regression**，一律按 P0 下限处理
4. 本次新发现的：与存量分开计数，标 **pre-existing** 的不要算成增量
5. 重跑扫描，比对基线（行数守恒前提下）

## 命名

| 产物 | 命名 |
|---|---|
| 整机报告 | `审查报告_<项目名>.md` |
| 模块报告 | `审查_<模块名>.md` |
| 修复清单 | `修复任务清单_<项目名>.md` |
| 扫描基线 | `扫描结果_全量.txt` / `扫描结果_P0.txt` |
| 文档候选 | `文档一致性_候选.txt` |

## 硬约束（复述）

- 三件套缺一不可
- 没实测就标 `unverified`
- 先报不改，批准后再动源码
- 报告要能交给一个不认识该项目的人执行
