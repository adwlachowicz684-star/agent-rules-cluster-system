# 外壳-扩展契约（第 5 步 · 维度一）

适用于：插件体系、微前端、脚本机制、任何「宿主 + 可扩展模块」的结构。

## 先画三张图

动手前把这三张图画出来，后面所有判断都基于它们：

1. **挂载图**：扩展怎么被加载（同页 / 沙箱 / 子进程），生命周期有几个阶段
2. **通信图**：双向各有哪些通道（直连、桥接、事件总线、IPC），各自能传什么
3. **能力图**：扩展能调用哪些宿主能力，每项**在哪一侧执行**

第三张最关键。**「在哪一侧执行」决定了隔离后还能不能用。**

## 契约五问

对每个扩展能力问一遍：

| 问 | 不成立时的典型症状 |
|---|---|
| 宿主声明了这个钩子/回调吗？ | 特性完全没接线（A02） |
| 两套外壳都接了吗？ | 一套能用一套不能（A01） |
| 隔离态下走哪条通道？ | 静默失效（D01） |
| 卸载时清理干净了吗？ | 重载后行为翻倍（F02） |
| 文档里写了这个能力吗？ | 承诺失效（A03/A05） |

## 双实现比对（高产区）

存在两套实现时（原生 + 构建版 / 双语言 / 新旧并存），**必须做差异比对**，
不能只看其中一条就下结论。

比对清单：

```
□ 入口文件各自加载了什么
□ 宿主的回调/hooks 各实现了哪些（逐个列，不要凭印象）
□ 扩展的可用能力集合是否一致
□ 配置项是否一致（一套有的设置项另一套没有 = A01）
□ 快捷键/命令注册是否一致
□ 状态持久化是否共用同一份存储
□ 构建产物里是否都带上了（G02 硬编码清单最常在这里出问题）
```

**最快的方法**：把两套的钩子实现名单列成两列，逐个 grep 确认。
Nexus Panel 就是靠这一步一次性发现 React 外壳少了 4 个回调（设置抽屉、
侧边栏注入、快捷键转发、CSP 上报）。

## 「扩展取不到宿主状态」的三类根因

| 根因 | 判据 | 症状 |
|---|---|---|
| 宿主状态挂在**主窗口**全局对象上 | `window.__XXX__` | 沙箱里取不到 → **静默空** |
| 宿主没在桥接里暴露该能力 | 桥接方法表里没有 | 隔离态下取不到 |
| 上下文快照在挂载时拷贝，之后不更新 | `theme: readTheme()` | 状态变更后读到旧值（C04） |

**「扩展自己另开监听器绕过」是强信号**——说明官方通道缺失。看到就该报。

正确形态：宿主在桥接里提供能力，扩展优先走桥接、失败再降级直连。
参考实现形态：

```js
// 先走桥接（隔离态也可用）
if (bridge && typeof bridge.list === 'function') {
  try { return await bridge.list(); } catch {}
}
// 降级直连（仅非隔离时可用）
return window.__NEXUS__?.getPlugins?.() ?? [];
```

## 消息通道的四个必须

1. **必须校验来源** —— 接收侧 `e.source !== expected.contentWindow` 直接 return（B01）
2. **必须有去重/去重标记** —— 握手类消息只处理一次（B03）
3. **必须有超时兜底** —— 不能无限等响应（B07）
4. **必须有精确退订** —— 按订阅 id 而非事件名（B04）

## 加载与错误边界

| 检查项 | 期望 |
|---|---|
| 加载超时 | 有上限（如 10s），超时后显示错误而非永久转圈 |
| 加载失败 | 插件崩溃只影响自己，不拖垮宿主 |
| 错误信息 | 转义后展示（插件名同样来自外部清单，只转义正文不转义名字 = 门锁了留着窗） |
| 重试入口 | 错误界面提供「重试」 |

## 常见误报（先排除再报）

- **注释解释了为什么不能那样写**：如「这里不能回发 ready，会互等死锁」——
  看起来是缺功能，实际是刻意设计
- **动态引用**：注册表、构建配置的自动扫描会让静态分析误判为「孤儿文件」
- **按栈分流的隐藏**：某些条目在特定模式下**故意**隐藏（如无构建模式隐藏 React 插件）
