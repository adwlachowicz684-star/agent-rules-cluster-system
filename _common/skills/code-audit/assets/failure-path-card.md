# 失败路径速查卡（写探针时对照）

> 对标 `adversarial-inputs-card.md`（数值场景速查卡）。
> 那张卡问「**输入**会不会击穿它」，这张卡问「**失败**之后会发生什么」。

## 为什么要单独审失败路径

**功能测试全绿只证明「成功时行为正确」。**
可靠性真正的差别在：

```
失败时留下什么？  →  残留（远端孤儿、磁盘累积）
失败时报什么？    →  可理解性（用户能不能自查）
失败后下一步？    →  出口（还是只能关掉防护？）
```

**实测依据**：某工具 41 项测试全绿，人工精审发现的 6 条问题**全部**出自失败路径；
既有 11 套测试中，专门问「失败之后会发生什么」的两个新套件**一上来就是红的**
—— 说明这个维度之前是空白。

---

## 四类探测手法

| 手法 | 怎么用 | 抓到过什么 | 关键要点 |
|---|---|---|---|
| **逐点注入失败** | 在多步链路的**每一个**调用点注入失败，逐个看残留 | 僵尸分支、孤儿分支 | **必须逐个点测**，只测一个点会漏 |
| **逐点注入中断** | 注入 Ctrl-C / SIGKILL 而**非**异常 | PATCH 之后的残留 | 中断**不是**异常，`except Exception` 抓不到 |
| **重复失败 N 次** | 连续失败 **≥ 5 次**，统计残留数量 | 备份文件只增不减 | **只失败 1 次测不出来** |
| **反向改回去** | 把修复回退，确认用例变红 | 验证 8 条修复的有效性 | 不变红 = 用例在测别的东西 |

### 三个「必须」

1. **必须逐个点测** —— 同一段代码里，前 3 步中断无残留、第 4 步有残留是常态
2. **必须重复多次** —— 累积型缺陷只在第 2 次之后才显形
3. **必须注入中断而非异常** —— 两者的代码路径完全不同

---

## 每一步都要检查的三项

```
① 远端 / 磁盘残留（孤立对象、分支、PR、临时文件、锁）
② 本地状态（有没有被写成「已成功」但实际没成功）
③ 报错是否可理解（有没有说下一步做什么）
```

**第 ② 项最阴**：状态被写成「已成功」→ 下次运行认为无需重试
→ **改动永久丢失且不报错**。

## 探测手法库

| 套路 | 用途 | 备注 |
|---|---|---|
| 钩住 `subprocess.run` 抓实参 | 验证敏感信息不进 argv | 只有**真实 argv** 能证明最终形态 |
| 起本地 HTTP 服务收真实请求 | 验证注入是否真生效 | 比推理可靠（「无法利用」的结论靠它得出） |
| 注入 `builtins.open` 而非替换上层函数 | 让错误**真的从被测代码内部抛出** | 替换上层会让新代码根本不执行 |
| 用**子进程**而非线程验跨进程锁 | 线程测不出进程级互斥 | 也测不出网络文件系统上 flock 的可靠性 |
| 改环境变量 + 起子进程验时区 | 沙盒常是 UTC 且可能没装 tzdata | 用 POSIX 格式 `CST-8`，不用 `Asia/Shanghai` |
| 按 PID / `mkdtemp` 隔离测试路径 | 避免并发互踩 | 固定路径是并发测试的**头号陷阱** |
| 断言与 UTC **有差值** | 防止时间测试恒真 | `mktime` vs `timegm` 在 UTC 下相同 |

## 常见残留物清单

写探针时逐项对照，问「失败后这个还在吗」：

| 类别 | 具体 | 相关判据 |
|---|---|---|
| **远端** | 孤立分支、未合并的 PR、孤儿 commit、云上中间对象 | A-18 |
| **磁盘** | 临时文件、`.tmp`、备份（`.bak` / `.corrupt`）、锁文件 | A-20 |
| **进程** | 后台任务、子进程、未回收的线程池 | R-02 / R-08 |
| **状态** | 被写成「已成功」的状态文件、过期的基线 | A-13 / T-13 |
| **本地工作区** | 冲突标记、部分写入的文件、残留暂存 | A-23 |

## 一句话

> 写测试的人按「功能」组织用例，
> 而缺陷藏在「**功能之间的交叠**」与「**失败路径的下一步**」里。
> 审完正常路径，记得把每个失败点**逐个走一遍**。
