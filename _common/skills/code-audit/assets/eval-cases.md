# 评测集（Eval Suite）

验证 skill 的**触发准确性**：该触发的要触发、不该触发的别抢。
改动 description 或 SKILL.md 结构后重跑一次。

来源：Anthropic 企业侧部署规范要求每个 skill 配 3–5 条评测用例，
覆盖「该触发 / 不该触发 / 模糊边界」三类。社区评分模型中
**触发准确性权重 0.25，是所有维度里最高的**——skill 不被触发，写得再好也没用。

## 该触发（应命中本 skill）

| # | 输入 | 期望行为 |
|---|---|---|
| E1 | 「审一下 event-bus 这个单元」 | 触发；走六步流程，先跑模式扫描 |
| E2 | 「这个库 3451 项测试全绿，能发布吗」 | 触发；指出测试全绿 ≠ 可发布，走对抗性输入核查 |
| E3 | 「damage-pipeline 报的 P0 修了吗，帮我复核」 | 触发；先确认是否真修过，实测复现而非信台账 |
| E4 | 「帮我找出这个库里所有会导致主线程挂死的地方」 | 触发；重点扫 B01/T01/T02/Q01 |
| E5 | 「把这个代码库收敛成零缺陷可放心拷贝的状态」 | 触发；依赖合规 + 三件套 + 全量扫描 |

E2、E3 刻意对应两个真实认知：测试全绿照样有 39 个 P0；台账说"已修"不等于真修。

## 不该触发（保持沉默）

| # | 输入 | 期望行为 |
|---|---|---|
| N1 | 「帮我写个快速排序」 | 不触发（普通编码任务） |
| N2 | 「解释一下 TypeScript 的泛型」 | 不触发（知识问答） |
| N3 | 「把这个函数重构成策略模式」 | 不触发（重构，非审查） |
| N4 | 「review 一下这个 PR 的 diff」 | **边界**：PR 审查可用本 skill 的模式库，但六步流程针对全库单元；若用户明确要 PR 审查，说明差异后由用户决定 |
| N5 | 「跑一下 ESLint」 | 不触发（现成 linter 能覆盖，本 skill 做的是 linter 扫不出的语义层） |

N5 说明本 skill 定位：**做 linter 扫不出的语义层**（算法语义、文档一致性、跨单元一致性）。

## 模糊边界（需澄清或直接试跑扫描）

| # | 输入 | 处理 |
|---|---|---|
| B1 | 「这段代码有问题吗」 | 先跑一次模式扫描，有候选再深审；无候选直接回报 |
| B2 | 「帮我优化一下这个模块」 | 区分：要性能 → 部分适用；要可读性 → 不触发 |
| B3 | 「检查一下有没有 bug」 | 触发，但限定范围（单文件则跳过依赖扫描与三件套统计） |

## 通过标准

- 5 条「该触发」全部命中，且至少 3 条正确走到第 2 步（模式扫描）
- 5 条「不该触发」至多 1 条误触发
- 触发后能正确选择 reference：写探针时读 `adversarial-inputs`，定级时读 `severity`
