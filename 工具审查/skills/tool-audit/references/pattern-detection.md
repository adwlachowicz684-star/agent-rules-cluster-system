## A 族 · 承诺失效（8 条）

整机审查中占比最高、用户最能感知的一类。**把文档当需求文档逐条对实现。**

### A01 双实现/多栈能力不对等 · P1 · 机扫：否
- **判据**：README 或注释声称两套实现（原生 / 构建版、A 语言 / B 语言、新旧并存）行为一致
- **确认**：把两套入口的功能点列成两列逐项比对，重点比对**回调/钩子/props/命令注册**四类接线
- **降级**：差异只在不影响功能的呈现细节（文案、顺序）→ P2
- **修法**：抽共享模块，两套外壳共用同一份实现；或在文档里明确标注差异

### A02 声明的特性未接线（孤儿组件/死代码）· P0 · 机扫：否
- **判据**：存在组件/模块/命令的**定义**但全仓库无**引用**（孤儿），或定义了回调却没传
- **确认**：全局搜该标识符，只出现在自身定义与导出处 → 确认。注意动态引用（注册表、字符串拼接）
- **降级**：无。声明了却完全不可用 = 对外承诺完全失效 → P0
- **修法**：接线，或删除并在文档里去掉该承诺

### A03 文档默认值/数量/清单与代码不符 · P1 · 机扫：是（doc-scan 第 3 类）
- **判据**：文档写「默认 X」「共 N 个」「M 套」，代码里是另一个值
- **确认**：定位代码里的常量/数组，数一遍
- **降级**：数量差 1 且不影响理解 → P2

### A04 文档把缺陷记为设计意图 · P0 · 机扫：否
- **判据**：文档描述某行为为「设计如此/已修复/已知限制」，实际是 bug 且未修
- **确认**：按文档描述的路径去代码里找对应实现，看它是否真的做了
- **典型**：README 声称「隔离后由插件自报基调，已修复」，实际自报字段没接上
- **定级**：P0。它会阻止下一个人修复

### A05 文档未覆盖主要模块 · P2 · 机扫：是（doc-scan）
- **判据**：仓库里有大模块（行数占比 >10%）在文档里完全没有章节
- **确认**：模块表 vs 文档目录，逐个对

### A06 注释与代码矛盾 · P1 · 机扫：否
- **判据**：注释说做了 X，代码没做（或做了相反的 Y）
- **确认**：读代码确认。**先确认自己没读错注释**——很多注释是在解释「为什么不能那样写」
- **降级**：注释描述的是历史行为，代码是后来改的 → P2，改注释即可

### A07 同名常量清单重复定义且已分叉 · P1 · 机扫：是（J13）
- **判据**：同一语义的清单（变量名白名单、主题变量表、命令列表）在两处各定义一份，内容不同
- **确认**：diff 两份清单，确认哪份是权威来源
- **典型**：`host.js` 的 `THEME_VARS` 与 `themes.js` 的 `THEME_VARS` 已分叉，
  导致插件拿到的主题快照缺一大半变量

### A08 死代码/重复实现（未被模块声明引用）· P2 · 机扫：是（R08/P02）
- **判据**：源文件存在但未被任何模块声明（`mod`）/ 构建入口引用
- **确认**：确认不是动态引用、不是待启用的备份。**内容近似但已分叉的重复文件**最危险——
  改了不生效，是后续维护的陷阱
- **定级**：若两份内容已分叉，升 P1

## B 族 · 跨边界通信（8 条）

适用于 postMessage、IPC、桥接层、事件总线。

### B01 消息监听不校验来源 · P1 · 机扫：是（J01）
- **判据**：`addEventListener('message', h)` 的处理器里只校验数据字段，不校验 `e.source` / `e.origin`
- **确认**：看该文档里是否嵌套了第三方 iframe 或引用第三方脚本。有 → 攻击者可伪造消息驱动内部流程
- **降级**：同文档内无第三方内容、且消息只触发幂等的展示逻辑 → P2

### B02 桥接/分发方法无白名单 · P0 · 机扫：是（J02）
- **判据**：`ns[method](...args)` 这类动态取成员后调用，没有允许列表
- **确认**：枚举该模块的全部导出，找出**能改写安全策略/配置**的那些（如 `savePolicy`）
- **典型**：隔离插件可调用 `pluginConfig` 与 `external` 模块的任意导出 →
  自己把外链策略改成 allow-all、把域名标成 trusted，整个外链治理形同虚设
- **定级**：P0（权限链路的放行）

### B03 握手竞态 / 重复握手 · P1 · 机扫：否
- **判据**：双向握手（ready ↔ init）里任一侧会对同一消息重复响应
- **确认**：画一次时序，看是否存在 `init → ready → init` 的环。**去重标记**是否每次实例重建
- **典型**：收到 init 就回发 ready，而 ready 又触发对端发 init → 无限往返，每轮重建上下文与订阅

### B04 订阅退订不精确 · P1 · 机扫：是（B04 补充判据）
- **判据**：退订时按**事件名**匹配摘除（常见 LIFO 取最近一个），而不是按订阅 id
- **确认**：构造「同一事件订阅两次、以不同顺序退订」的路径，看是否会摘错 handler
- **典型**：改一次设置就多一个 handler → 按一次快捷键执行两次

### B05 隔离态自报数据未被接上 · P0 · 机扫：否
- **判据**：宿主在隔离态下采样不到子文档，设计了「子方自报 X」机制，
  但宿主构造下游入参时**没有带上 X 字段**
- **确认**：从自报消息的接收处一路跟到消费处，看字段是否传到底
- **典型**：`reportedBase` 自报了，但 `adaptInput` 构造时没写进去 →
  判定基调一致 → 不反转 → 深色面板上一块刺眼的白，**且不报错**
- **定级**：P0（静默且对外承诺失效）

### B06 postMessage 目标 origin 通配 · P1 · 机扫：是（J03）
- **判据**：`postMessage(data, '*')`
- **确认**：消息里是否含敏感数据（主题变量、配置、DOM 结构）。含 → P2；含凭据/路径 → P1

### B07 请求-响应无超时或超时未清理 · P2 · 机扫：否
- **判据**：pending Map 里的请求只有「成功回调时删除」，无超时兜底
- **确认**：看对端崩溃/不发响应时是否永久悬挂
- **定级**：若 pending 会随用户操作持续增长 → 升 P1（内存泄漏）

### B08 错误消息透出内部细节 · P2 · 机扫：否
- **判据**：错误信息里回显完整本地路径、堆栈、配置内容
- **降级**：纯本地工具、无网络出口 → P3

## C 族 · 状态、配置与持久化（7 条）

### C01 两份同名清单已分叉 · P1 · 机扫：是（J13）
（同 A07，此处从「消费方拿到残缺数据」角度再计一次。）

### C02 清单遗漏 · P2 · 机扫：否
- **判据**：CSS/代码里定义了某变量，但主题/配置清单里没列
- **确认**：导致两个后果——**该变量无法被主题覆盖**，且**切主题时不会被清理**（残留旧值）
- **典型**：CSS 定义了 `--r: 14px`，`THEME_VARS` 只有 `--r-md` → 扁平主题想改默认圆角改不动

### C03 内联样式压过后续动态注入 · P2 · 机扫：否
- **判据**：首屏/兜底逻辑用 `element.style.xxx = v` 而非注入 `<style>`
- **确认**：内联样式优先级最高，后续主题系统写 CSS 变量覆盖不住
- **典型**：首屏防闪用内联 `background` → 切到浅色主题后底色卡在深色那一版
- **降级**：该值后续不会再变 → 忽略

### C04 快照不随状态更新 · P2 · 机扫：否
- **判据**：上下文对象在挂载时拷贝一份状态快照（如 `theme`），状态变更后不更新
- **确认**：看消费方是否被迫自己另开监听器绕过（**这是强信号**）
- **典型**：插件为了拿主题变更自己再注册一个 message 监听器，与 SDK 内置监听器并存

### C05 存储反序列化无兜底 · P2 · 机扫：是（J04）
- **判据**：`JSON.parse(localStorage.getItem(...))` 无 try/catch
- **确认**：一条脏数据（历史版本写入、手工改过）是否让**整个** store 不可用
- **定级**：影响范围是「该插件全部持久化数据」→ 升 P1

### C06 变更监听器解绑失效 · P2 · 机扫：是（J05）
- **判据**：注册时包了箭头函数 `addEventListener(E, e => fn(...))`，
  解绑时却传原始 `fn` → 永远摘不掉
- **确认**：看 `onXxxChange` 的返回值是否真能停止回调
- **定级**：每次调用累积一个监听器，且回调里有重活 → 升 P1

### C07 降级后不重试 · P2 · 机扫：是（J06）
- **判据**：能力探测失败后把 `null` 写进「已缓存」标志，后续永不重试
- **确认**：该能力是否可能在初始化之后才就绪（异步注入、延迟加载）。是 → P1

## D 族 · 沙箱、权限与安全边界（8 条）

### D01 隔离后能力静默失效 · P0 · 机扫：是（J07）
- **判据**：扩展/插件层**绕过宿主上下文**直连底层 API（`@tauri-apps/api`、
  `window.parent`、`__TAURI_INTERNALS__`），而宿主提供的是 `ctx.invoke` / 桥接
- **确认**：在宿主设置里开启严格沙箱/隔离 → 该能力是否**静默**失效（无报错、无提示）
- **典型**：agent-flow 直连 `@tauri-apps/api/core` 的 invoke/listen，
  开启严格沙箱后 run_node / watch / webhook / fs_op / 读图全部失效且不提示
- **定级**：P0。文档承诺「隔离切断的是直连通道，不是能力」，实际两者都被切断

### D02 被隔离方仍能自授权 · P0 · 机扫：是（J02，同 B02）
- **判据**：隔离方通过桥接能调用到**改写自身权限策略**的方法
- **确认**：枚举桥接可达的方法，看是否包含策略写入类

### D03 扩展读取宿主全局单例 · P1 · 机扫：是（J08）
- **判据**：插件里直接读 `window.__XXX__`（挂在**主窗口**上的运行时对象）
- **确认**：该插件是同页挂载还是 iframe 沙箱。iframe → 取不到 → **静默空**
- **典型**：概览页「插件总数 0」、移除按钮点了没反应（可选链不报错）
- **修法**：宿主在桥接里提供 `plugins.list` / `plugins.remove`，扩展优先走桥接、
  失败再降级直连

### D04 安全策略缺失或只覆盖部分入口 · P0 · 机扫：是（R09/P04）
- **判据**：有多个入口（多份 HTML / 多套构建配置）但 CSP / 权限配置只写在其中一份
- **确认**：逐个入口查。注意**构建工具的配置文件是按 JSON Merge Patch 合并而非替换**——
  主配置里的安全项在另一套配置下依然生效，反之则要看清谁覆盖谁
- **典型**：主配置 `csp: null`，只有无构建入口的 HTML 里有 CSP meta → Vite 模式裸奔

### D05 路径黑名单未规范化 · P1 · 机扫：是（R05）
- **判据**：危险路径用**字符串比较**判定（小写化 + 去尾斜杠 + `==` / `starts_with`），
  未做 `canonicalize` / 路径归一
- **确认**：构造 `/etc/..`、`C:\Windows\..`、含 `./` 的变体，看是否绕过
- **定级**：保护的是删除/写入这类不可逆操作 → P0

### D06 命令字符串拼接 / 可执行路径无白名单 · P0 · 机扫：是（R06）
- **判据**：`Command::new("cmd").args(["/c", "start", "", url])` 这类把外部输入喂给 shell；
  或可执行文件完整路径来自用户配置且无白名单
- **确认**：外部输入里含 `&` / `|` 时是否被 shell 二次解析
- **修法**：改用官方 opener / 直接 spawn 并传参数数组；路径做白名单 + 用户确认

### D07 URL / 协议未校验 · P1 · 机扫：部分（J12）
- **判据**：外部传入的 URL 直接用于导航、iframe src、插件入口
- **确认**：是否校验协议白名单（http/https/mailto）。`javascript:` / `file:` 是否可达
- **典型**：插件入口填外域地址 → 代码来自网络，且能访问宿主数据

### D08 凭据加密密钥可由同存储推导 · P1 · 机扫：否
- **判据**：「免口令」模式的密钥素材（设备特征、随机盐）**全部**存在同一个可被读出的存储里
- **确认**：攻击者拿到存储文件后能否离线复现密钥。能 → 加密只防「随手打开 DevTools 看一眼」
- **典型**：`deviceSalt` 也存在 localStorage，则整条链可离线复现
- **修法**：盐由原生侧生成并存在应用数据目录；或在首次使用时引导选口令模式
- **降级**：文档已明确说明该模式的防护边界 → P2

## E 族 · 资源、健壮性与终止性（8 条）

### E01 全量读入内存后再截断 · P1 · 机扫：是（R01）
- **判据**：`fs::read(p)` / `read_to_string` 一次性读入，之后才按 `max_bytes` 截断
- **确认**：看截断是在**读入前**（`take`）还是**读入后**（`bytes[..len.min(cap)]`）。
  后者 = 上限参数形同虚设
- **典型**：读一个 10GB 文件直接把内存打满
- **定级**：`max_bytes == 0` 时退化为 `usize::MAX` → P0

### E02 无错误处理的锁/解包 · P1 · 机扫：是（R02）
- **判据**：`lock().unwrap()` / `unwrap()` 出现在可能失败的路径上
- **确认**：release profile 是否 `panic = "abort"`。是 → 一次锁中毒 = 应用直接崩
- **定级**：配 `panic = "abort"` 且在关键路径 → P0

### E03 网络服务无请求体上限 / 无超时 · P0 · 机扫：是（R03）
- **判据**：按客户端声明的 `content-length` 直接分配缓冲；或 accept 后无读写超时
- **确认**：本机任意进程能否 OOM 打挂应用 / 慢速连接能否占满线程
- **典型**：`vec![0u8; content_len]` → 声明 10GB 就分配 10GB

### E04 递归遍历不识别符号链接与环 · P1 · 机扫：是（R04）
- **判据**：目录递归（拷贝、备份、扫描）用 `is_dir()` 判断，未用 `symlink_metadata`
- **确认**：项目是否大量使用 junction / symlink。是 → 遇到目录环会无限递归爆栈
- **定级**：可被普通用户操作触发（建个链接）→ P0

### E05 跨设备重命名无回退 · P2 · 机扫：是（R10）
- **判据**：`fs::rename` 无错误处理 / 无 copy+delete 回退
- **确认**：跨卷/跨设备必然失败，用户看到莫名其妙的「移动失败」

### E06 循环/迭代上限可被配置放大到卡死 · P1 · 机扫：否
- **判据**：有全局硬上限，但节点/模块自设的上限值未做合法性校验
- **确认**：传 `Infinity` / 极大值 / `undefined` 时是否被 clamp

### E07 阻塞式固定 sleep 轮询 · P2 · 机扫：是（R07）
- **判据**：`thread::sleep` / `setTimeout` 固定值轮询等待状态
- **确认**：该等待是否有更精确的信号（`transitionend` / 事件 / 条件变量）。有 → 应替换
- **典型**：主题切换后采样等待由「400ms 兜底 + 4 轮 × 260ms + 3 次稳定采样」串成 ~1.5s 卡顿

### E08 每连接/每任务一线程无并发上限 · P1 · 机扫：是（R07）
- **判据**：`thread::spawn` 在 accept 循环里无计数限制
- **定级**：监听端口可被本机任意进程访问 → P0

## F 族 · 生命周期与泄漏（7 条）

### F01 成对 API 缺一侧 · P0 · 机扫：是（J09）
- **判据**：注册无注销、获取无释放、订阅无退订、start 无 stop
- **确认**：确认缺的那一侧是否**随运行时长累积**。是 → P0
- **典型**：`addEventListener` 无配对 `removeEventListener`；`registerShortcut` 无 unregister

### F02 监听器/定时器在重挂载时叠加 · P1 · 机扫：是（J10）
- **判据**：`addEventListener` / `setInterval` 在可能重复执行的初始化流程里
- **确认**：是否有 generation 标记或先 remove 再 add
- **典型**：插件重载一次，同一事件的 handler 多一个 → 按一次快捷键执行两次

### F03 objectURL / blob 未释放 · P2 · 机扫：是（J11）
- **判据**：`createObjectURL` 无配对 `revokeObjectURL`
- **确认**：是否有统一收口（关闭预览 / 卸载时统一 revoke）。无 → 随预览次数累积
- **定级**：在热路径（列表渲染、每帧）→ P1

### F04 卸载时未清理子进程 / 定时器 / 监听器 · P1 · 机扫：是（J10）
- **判据**：有 `onDestroy` / `unmount` / `dispose` 钩子但清理项不全
- **确认**：逐项列出该模块创建的外部资源，对照钩子里的清理项

### F05 解绑引用不一致 · P2 · 机扫：是（J05，同 C06）
- **判据**：`removeEventListener(type, fn)` 的 `fn` 与注册时不是同一引用
- **典型**：注册时 `this._onMessage.bind(this)` 产生新引用，解绑时传的是另一个绑定

### F06 缓存 Map 无上限增长 · P1 · 机扫：否
- **判据**：`Map.set(k, v)` 无对应的 `delete` 且 key 来自外部/递增序列
- **确认**：key 是否有界（固定枚举 vs 用户输入 vs 时间戳）
- **典型**：pending 请求表、进程注册表、监听器表

### F07 卸载后仍被外部持有并继续使用（且不报错）· P1 · 机扫：否
- **判据**：对象销毁后无状态标记，外部仍持有引用
- **确认**：销毁后调用是否**静默**产生错误结果（而非抛异常）
- **定级**：静默 → P1；抛异常（能被发现） → P2
