## 三、问题清单

共 8 条：**P0 ×1**、P1 ×3、P2 ×4。

### P0-1　防覆盖校验的前提假设未校验：本地副本过期 → 静默回退远端　[A-13]

- **位置**：第一层校验 `if rsha != base: blocked.append(...)`——只比对「远端当前 sha == 基线记录的 sha」
- **为什么不够**：这个比对只能证明「远端没被**别人**改」，证明不了「本地是**从最新版**改的」。本地副本一旦过期，过期的全文 + 你的改动会被整文件覆盖上去，**把远端更新的内容回退掉，且不报错**
- **证据**（本次推送过程中实测）：
  ```
  同一 URL（.../tarball/main）三次下载，scan-app.py 的 blob sha：
    第 1 次 → 9dbee0…     远端 API 当时 → f5c25b…   ❌ 过期快照
    第 2 次 → f5c25b…     远端 API 当时 → f5c25b…   ✅
    第 3 次 → b1b94e…     远端 API 当时 → b1b94e…   ✅（远端又前进了）
  ```
  第 1 次下载缺少远端已有的 `R11` 规则（9 行）与其 `APP-R11` fixture；
  若不核对直接推送，会把这两项**整体抹掉且无任何提示**。
  第二次与第三次之间远端又推进了 `J09` 规则的接收者感知重写（+72 行）。
- **后果**：静默 + 不可逆 + 破坏的是别人的产出。**这是本次审查发现的唯一 P0，也是唯一在真实推送中触发的一个**——前 4 条是静态与探针测出来的，这一条是推送时踩到的。
- **修法**：基线里额外记录「本地开始编辑时所基于的远端 commit」；推送前与当前远端比对，**落后就必须先同步再提交**，不允许直接覆盖。操作层面的替代做法：用 contents API 逐个核对 blob sha，不信任 tarball 快照。
- **定级**：P0 —— 静默、不可逆、破坏他人产出。

### P1-1　文件 mode 推断依赖 `os.access`，在容器环境恒为真　[K-30]

- **位置**：`local_state_map()` 中 `mode = "100755" if os.access(full, os.X_OK) else "100644"`
- **证据**（实测）：
  ```
  git config core.fileMode           → false
  chmod +x x.sh && git add x.sh
  git ls-files -s x.sh               → 100644   （git 不跟踪执行位）
  ls -l t1                           → -rwxrwxrwx
  os.access(X_OK)                    → True      （所有文件恒真）
  ```
- **后果**：沙盒/容器里 `os.access` 恒为真，**任何**进入改动列表的文件（含 `.md` / `.json` / `.py`）都会被判为 `100755` 推上远端。这与该脚本上一版「一律 `100644`」的错误**方向相反、同样致命**——两种环境各错一边，且都不报错。
- **修法**：mode 只取版本库索引（`git ls-files -s`）；索引缺失（新文件）时**回退 `100644`**——宁可丢执行位，也不要把文档变成可执行。

### P1-2　符号链接绕过路径校验，可读到仓库外文件　[K-07]

- **位置**：`safe_rel()` 用 `os.path.normpath`，不解析符号链接
- **证据**（实测）：
  ```
  ln -s /etc <repo>/etcdir
  safe_rel("etcdir/passwd")          → "etcdir/passwd"   （通过校验）
  os.path.realpath(...)              → /etc/passwd       （越界=True）
  open(...)                          → "root:x:0:0:root:/root:/bin/bash"
  ```
- **后果**：仓库内一旦存在指向外部的目录链接，`explicit` 模式即可把 `/etc/passwd`、`.env`、SSH 私钥等内容推上**公开**仓库。写入公开仓库不可逆。
- **修法**：`normpath` 后再 `realpath`，与 `ROOT` 的 `realpath` 比较。
- **定级说明**：触发前提是仓库内已有恶意/异常链接（本地攻击面），故不升 P0；但后果不可逆，不按普通 P2 处理。

### P1-3　元数据（mode）变更被静默跳过　[T-11]

- **位置**：第一层校验 `if lsha == rsha: print("内容已与远端一致，跳过"); continue`
- **证据**（实测）：构造「已跟踪文件仅 `chmod +x`、内容不变」，blob sha 与远端相同 → 判定为一致 → 跳过。
- **后果**：只改可执行位的变更**永远推不上去**，输出却是「内容已与远端一致，跳过」——用户以为推成功了。比对基线只存 blob sha、不存 mode 是根因。
- **修法**：比对改用 `(mode, sha)` 元组；基线结构加 `version` 字段并留迁移路径。

### P2-1　`git()` 丢弃子进程返回码　[K-31]

- **位置**：`def git(*args)` 只取 `.stdout.strip()`
- **证据**（实测）：`git add -- b.txt secret.txt`（`secret.txt` 被 `.gitignore` 忽略）退出码 **1**，函数仍返回空字符串；正常文件虽进了暂存区，但失败对调用方完全不可见。
- **后果**：git 命令失败一律静默，只表现为「本地没补提交」。用户看到「✅ 已推送」会认为一切正常。
- **修法**：检查 `returncode`，非 0 时至少告警并回显 stderr。

### P2-2　重试未区分幂等性　[B-10 附]

- **位置**：`api()` 对 429/5xx/超时统一重试 3 次，包含 `POST /git/blobs`、`/git/trees`、`/git/commits`
- **证据**：`--max-time 60` 超时后 `returncode != 0` → 进入重试分支，而这些 POST 非幂等。
- **后果**：超时但服务端已建对象时重复创建。功能上无害（孤儿对象不被引用），但白白消耗 API 限流额度，大批量推送时可能触发限流。
- **修法**：仅对 GET 与幂等写重试；非幂等 POST 重试前先按 sha 查询是否已存在。

### P2-3　状态文件无版本字段，`remote` 字段存而不校验　[T-08]

- **位置**：`init_baseline()` 写入的 `state`；`main()` 从未比对 `state["remote"]`
- **证据**：代码事实。
- **后果**：把脚本改去推另一个仓库时，旧基线仍生效，第一层校验会把所有文件判为「基线未记录 / 可能被他人改动」——方向是 fail-closed（安全），但报错信息把人引向「有人动了我的远端」，真实原因是仓库换了。**报错指向错误方向 = 排查成本极高**。
- **修法**：入口校验 `state["remote"] != f"{OWNER}/{REPO}"` 时明确报「基线属于另一个仓库」；`state` 加 `version`。

### P2-4　预览无大小预检，符号链接预览会打开目标文件

- **位置**：`preview()` / `_local_lines()`
- **证据**：代码事实——每个待推文件都要拉一次远端 blob 全文。
- **后果**：改动文件多时预览要拉全部远端内容（几 MB 级），明显卡慢；`_local_lines` 对 `120000` 类型的链接文件会 `open()` 到链接目标，预览内容与将要推送的内容（目标路径字符串）不一致。
- **修法**：超过 256 KB 直接跳过预览只报大小；symlink 预览直接展示 `os.readlink()` 结果。

### P2-5　大文件上限与超时不匹配

- **位置**：`MAX_BLOB_BYTES = 50MB` 与 `--max-time 60`
- **证据**：50 MB base64 后约 67 MB，60 秒在慢网下必然超时；超时即触发 P2-2 的三次重试。
- **后果**：大文件不是「推送失败」，而是「超时 ×3 后失败」，期间已重复上传多次。
- **修法**：上限降到 10 MB，超时按文件大小动态计算，超时后不重试。

## 五、验证过没问题的部分

实测确认正确，后续复核可直接跳过：

1. **符号链接 blob sha 算法** —— `hash-object --stdin` 喂 `os.readlink()` 得 `3b8822…`，与 `git ls-files -s` 记录一致；若误用 `hash-object <path>` 会跟随链接算成目标文件 sha（`9230cd…`）。当前实现正确。
2. **HTTP 非 2xx 拦截** —— mock 服务返回 422 + `{"message":"Validation Failed"}`，被正确拦截并回显状态码与响应体。
3. **路径越界基础防护** —— `../secret`、`/etc/passwd`、`~/x`、`a/../../b` 均被 `safe_rel` 拒绝；`src/./a.js` 正确归一为 `src/a.js`。
4. **参数解析** —— `-m` / `--message=xxx` / `--dry-run` / `--yes` / 未知参数报错，均正常。
5. **原子写基线** —— `tmp` + `os.replace`，写一半崩溃不产生坏 JSON；`load_state` 另有 `JSONDecodeError` 兜底与可操作提示。
6. **`--init-baseline` 覆盖保护** —— 基线已存在时不再直接重写，提示改用 `--reset-baseline` 并二次确认。

| **P2-5** | 上限 50→10 MB；超时按体积动态算（30 s 保底，每 MB +10 s，10 min 封顶） | `_timeout_for`：0 MB→30 s、5 MB→80 s、100 MB→600 s ✅ |

### 修复中额外发现并一并修掉的

**新增文件被无谓拦截**：原逻辑「基线没记录 → 拦住要 `--force-overwrite`」没区分远端是否有该文件。
实际上**远端也不存在**时是纯新增，不存在覆盖风险，每次都拦纯属噪音。
已改为：只有「基线没记录**且远端却有**」才拦（这才是真无法确认原状态的情况）。
