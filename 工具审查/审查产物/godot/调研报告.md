# Godot 4.x 静态代码审查语言包调研报告

## 摘要

Godot 4.x 的多数严重缺陷并非“语法错误”，而是生命周期、对象所有权与引用语义组合产生的误用；但其中相当部分具有清晰源码特征。`Node.queue_free()` 在帧末释放节点及其子树，`Node.free()` 则立即释放；在信号发射、回调链或自身帧逻辑中调用 `free()` 可能使后续访问落到已释放对象上，因此普通销毁应优先 `queue_free()`。[1] 生命周期顺序是 `_init`、`_enter_tree`、子节点递归就绪后的 `_ready`、`_process`/`_physics_process`、移除或释放时的 `_exit_tree`；`tree_exiting` 才是节点仍有效时的主要反初始化点。[1]

最值得做成规则的是：跨场景/Autoload 连接未在 `_exit_tree`/`_Ready` 配对清理；重复创建 Tween 前未 `kill()`；`create_timer()` 引用未保存；`remove_child()` 后未 `queue_free()`；以及 3.x 遗留的字符串信号、`KinematicBody`、`move_and_slide(...)` 等 API。官方明确：被绑定节点释放时绑定 Tween 会销毁，但自由 `SceneTree.create_tween()` 不一定如此；Resource 是引用计数对象，不应把普通 Resource 当作 Node 调用 `queue_free()`。[2][4] 这些规则应按“确定性缺陷—高可疑模式—运行时验证”三级输出，不能把纯静态命中直接标成已确认缺陷。

## 1. 生命周期、清理点与典型误用

**回调顺序决定“何时拿引用、何时释放引用”，而不是反过来。** Godot 4 加入树时，父节点先 `_enter_tree`，子节点后 `_enter_tree`；就绪时子节点先 `_ready`，父节点后 `_ready`。[1] 因此 `_enter_tree` 适合连接父级或全局信号、加入组、配置尚未依赖子节点的状态；`_ready` 适合访问已解析的子节点并设置依赖关系；`get_node("$Child")` 和 `find_child()` 在 `_init` 里不安全，因为此时节点尚未进入树，子节点也尚未就绪。

![Godot 4 生命周期顺序](/data/workspace/dr:godot-review:20260917/fig_lifecycle.png)

*图 1：节点从创建到释放的典型顺序；父子递归规则是父先 enter_tree、子先 ready。数据来源：Godot 官方 Node 类文档 [1]*

**`tree_exiting` 是“节点仍有效”的清理点，`_exit_tree` 只是离开树前的回调。** 官方把 `tree_exiting` 描述为节点仍然有效、适合做反初始化的地方；随后才完全离开树并发出 `tree_exited`。[1] GDScript 中，连接清理可放在 `_exit_tree`；C# 中可用 `_ExitTree`，或依据对象类型在 `Dispose` 中清理非树资源。必须断开的不是“树内父子信号”，而是可能跨越对象生命周期的引用：Autoload、全局事件总线、长期存活管理器、Timer 或 Tween 仍在运行时、外部协程保存的引用。

| 生命周期事件 | 安全动作 | 不应做的事 |
|---|---|---|
| `_init` | 纯数据初始化；设置可由构造器接收的参数 | 访问子节点、发出树内信号、调用 `get_node` |
| `_enter_tree` | 连接跨对象信号、加入组、设置输入处理 | 假定子节点已就绪；执行依赖子组件的逻辑 |
| `_ready` | 缓存节点引用、配置子节点、连接局部信号 | 重复连接同一信号而不去重或清理 |
| `_process`/`_physics_process` | 使用已缓存引用做帧逻辑或固定步逻辑 | `get_node`、`find_child`、频繁 `instantiate`、新建数组/字典 |
| `_exit_tree` | 断开跨生命周期连接、取消重复回调 | 再执行重入式 `queue_free()` 或假定节点已经销毁 |
| 释放完成 | 不再访问 `self`、字段及缓存回调 | 让外部闭包继续持有并访问本节点 |

**`queue_free()` 与 `free()` 的差异是“延迟销毁与立即销毁”，不是“异步与同步”的语义糖。** `queue_free()` 将节点排入当前帧结束时删除；删除时连同子节点一起删除，之后对节点及其子节点的引用失效。[1] `free()` 立即释放。因此以下写法属于高风险：`emitter.signal_name.emit()` 之后立即 `free()` 仍可能由其他已调度回调访问该对象；节点在自身信号回调链中被 `free()` 后，若链后段或后续信号处理器访问同一实例，可能出现失效对象访问。审查规则应标记为“建议改为 `queue_free()`”，而不是无条件把所有 `free()` 判错，因为某些纯逻辑 `Object` 或引擎工具代码中确实存在同步释放需求。

**`_process` 与 `_physics_process` 混用的核心问题是速率和权威状态不一致。** `_process(delta)` 的调用间隔随渲染帧率变化；`_physics_process(delta)` 按固定物理步运行，默认目标为每秒 60 次。[1] 若把角色速度积分、碰撞移动放在 `_process`，低帧率时可能出现不同时间步、物理插值或抖动；若把相机输入、纯视觉动画、网络冷却放在 `_physics_process`，会浪费固定步预算。规则应命中“`_process` 中出现 `move_and_slide/move_and_collide/apply_central_force`”以及“`_physics_process` 中每帧 `get_node`/实例化对象”两类模式，其余需要结合项目是否锁定帧率判断。

## 2. 六大泄漏源及 GDScript/C# 规则

**跨生命周期信号连接是泄漏和悬空回调的第一大来源。** Godot 4 的推荐连接形式是 `Signal.connect(Callable)`；C# 优先使用事件订阅 `+=`。官方明确：当发送者或接收者是普通 GodotObject 且被释放时，相关连接通常自动断开；但 C# 捕获外部变量的 lambda、C# 自定义信号连接等情形下不会自动断开。[2][5] 因而规则不应把“未显式 disconnect”一律视为泄漏，而应针对“连接对象比当前节点更长寿”判为高风险。

| 语言 | 正例 | 反例与问题 |
|---|---|---|
| GDScript | `_exit_tree` 中 `if bus.signal_name.is_connected(_handler): bus.signal_name.disconnect(_handler)` | 只在 `_ready` 反复连接 Autoload 信号；`_exit_tree` 无对应断开 |
| GDScript | `timeout.connect(_on_tick, CONNECT_ONE_SHOT)` | `lambda` 内联连接，却期望之后用字面 lambda 断开 |
| C# | `_ExitTree(){ Timer.Timeout -= _tick; }` | lambda 捕获变量后连接，对象释放后仍被委托持有 |
| C# | `button.Pressed += OnPressed;` | 为 GDScript 自定义信号连接后未保存 delegate，导致无法 `-=` |

确认方法：先静态命中跨场景/Autoload 连接，再运行时调用 `get_signal_connection_list()`；C# 可比对 `Delegate.Target`、对象存活和连接数。对于 `CONNECT_ONE_SHOT`，静态规则不应要求“必须 disconnect”，因为它本应触发一次后自动断开。[2]

**Tween 未 kill 的风险集中在重复创建和离树后继续运行。** `Node.create_tween()` 会把 Tween 绑定到当前节点；`SceneTree.create_tween().bind_node(node)` 也可显式绑定。官方说明：绑定对象不在树中会暂停 Tween，绑定对象释放时 Tween 自动销毁。[3] 这意味着“节点释放后 Tween 一定泄漏”并不准确。真正可静态检出的是“没有保存 tween 引用、也没有 `bind_node`，却在函数内每帧/每事件重新 `create_tween()`”，以及“对同一个属性重复 tween 却没有先 `kill()`”。官方明确建议保存 tween，并在重新动画前 `kill()` 旧 Tween。[3]

```gdscript
# 反例：每次触发都新增 Tween，旧 Tween 状态难以审计，也可能持续持有属性写入权
func flash() -> void:
    create_tween().tween_property(self, "modulate", Color.WHITE, 0.2)

# 正例：保存引用，重启前 kill
var flash_tween: Tween
func flash() -> void:
    if flash_tween != null and flash_tween.is_running():
        flash_tween.kill()
    flash_tween = create_tween()
    flash_tween.tween_property(self, "modulate", Color.WHITE, 0.2)
```

C# 对应为保存 `Tween` 成员，重启前 `_tween?.Kill()`；不要以 `new Tween()` 代替 `CreateTween()`，因为 Tween 应由 SceneTree 或 Node 创建并由引擎调度。[3]

**`create_timer()` 与 `Timer` 节点不是同一种对象。** `SceneTree.create_timer()` 返回 `SceneTreeTimer`，属于 `RefCounted`；时间到达后若无引用会被释放。官方特别指出，若要保持引用，需要显式保存它。[6] 因此 `await get_tree().create_timer(1.0).timeout` 通常安全，因为 await 状态会持有返回对象；但 `var t = get_tree().create_timer(1.0)` 之后不保存 `t`、又期待后续停止或复用，则属于可疑模式。Timer 节点是 Node，连接 `timeout` 后如果不 `stop()` 且持续重复触发，会重复执行回调；只 `remove_child(timer)` 不会释放它，仍需 `queue_free()`。

```gdscript
# 反例：每次物理帧新建一个无法停止的一次性延时
func _physics_process(_delta: float) -> void:
    await get_tree().create_timer(1.0).timeout
    do_something()

# 正例：使用有状态 Timer 节点，或把冷却字段放在 _process/_physics_process 中累积
@onready var cooldown := $CooldownTimer
func _ready() -> void:
    cooldown.timeout.connect(_on_cooldown)
func start() -> void:
    if not cooldown.is_stopped(): return
    cooldown.start()
```

C# 中 `SceneTreeTimer` 可通过 `await ToSignal(GetTree().CreateTimer(1.0f), SceneTreeTimer.SignalName.Timeout)` 使用；Timer 节点则保存成员并配对 `Start()`/`Stop()`、`QueueFree()`。注意 `create_timer()` 的 timer 不是普通 Timer 节点，不能调用 `start/stop`；这条跨类型误用适合静态检查。

**Resource 的“泄漏”通常是引用或缓存未释放，而不是忘记调用 `free()`。** Resource 继承自 `RefCounted`，官方说明其按引用计数管理，引用归零时释放；`load()` 与 `preload()` 会进入按路径缓存的全局资源缓存，当所有引用释放后缓存条目才移除。[4] 所以审查规则应区分：普通 `Resource.new()`/`load()` 不需要 `free()`；用 `Resource` 成员变量持有大型纹理、音频、场景等长期引用才是风险；把 Resource 当 Node 调用 `queue_free()`/`free()`，或把 PackedScene 当成已实例化的 Node 使用，也应判错。

`preload()` 在脚本解析阶段加载，`load()` 在运行时执行到该行时加载；这不改变引用计数机制，但意味着 `preload` 会让资源更早常驻。代码里连续出现 `load("res://...")`/`preload("res://...")` 只说明重复取引用，不应直接判“加载两次导致双倍内存”，因为同路径通常返回缓存资源。真正应确认的是：Autoload、静态字段、常驻 manager 是否长期持有 Resource，以及临时 Image/Texture 等是否在局部作用域释放后还有别处强引用。

**`remove_child()` 不等于释放，是 Godot 最具源码特征的经典错误。** 官方只在 `queue_free()` 说明中描述释放会移除节点；从 `_exit_tree` 文档也可推出 `remove_child()` 只使节点离开树，并不销毁它。[1] 可静态命中的写法是：

```gdscript
get_parent().remove_child(self)
# 之后既没有 queue_free(self)、返回给 owner 保管，也没有重新 add_child
```

如果变量随后没有重新加入树、也没有保存供后续使用，应标“孤儿节点风险”。C# 的 `GetParent().RemoveChild(this)` 同理。此处不能只正则匹配 `remove_child`：编辑器拖拽、状态机切换或对象池可能合法地把节点移出树。确认方法应检查其后是否 `QueueFree()`、是否赋值给持久字段、是否被重新 `AddChild()`。

**闭包和长期单例会绕过节点树可见性形成泄漏。** GDScript 的 lambda 是 Callable，捕获的外部变量会延长其生命周期；C# lambda 捕获变量后生成的委托，Godot 无法可靠把它关联到创建实例，因此不会随实例释放自动断开。[5] Autoload 事件总线订阅、静态字典保存 Node、循环 `Node -> Callable/Delegate -> 外部对象 -> Node`，都可能在节点树外形成引用环。静态可检出的特征是“Autoload/静态字段 + Array/Dictionary += self/Node/Callable”或“lambda 连接并捕获外部对象”。确认方法是监控 `Performance.OBJECT_COUNT` 和 `OBJECT_ORPHAN_NODE_COUNT` 的场景切换前后差值，并在场景卸载后打印仍存活对象；这不能仅靠 AST 判定。

## 3. 性能缺陷与确认方法

**2D 批处理规则应写成“打断条件清单”，不能把 DrawCall 当成唯一指标。** Godot 的 CanvasGroup 会把子 CanvasItem 作为单个对象绘制并读取 backbuffer；它会扩大 backbuffer 区域，因此过大的 `fit_margin`、`clear_margin` 以及 `use_mipmaps` 有性能代价。[8] CanvasItem 的 `clip_children` 与 CanvasGroup 不能嵌套，若祖先裁剪或属于 CanvasGroup，子节点开启裁剪会有非预期行为。[9] 可静态命中的条件包括：`CanvasGroup` 下子节点有不同 `material`、Light2D 相关设置不同、纹理/CanvasTexture 状态不同、裁剪/CanvasGroup 嵌套、重复创建 ShaderMaterial 而不复用。

```gdscript
# 反例：每帧复制材质，容易造成材质状态碎片化
func _process(_delta: float) -> void:
    var m := ShaderMaterial.new()
    m.shader = outline_shader
    m.set_shader_parameter("color", current_color)
    sprite.material = m

# 正例：使用 Material 实例参数或共享材质，避免每帧 new
@onready var mat: ShaderMaterial = $Sprite.material
func update_color(c: Color) -> void:
    mat.set_shader_parameter("color", c)
```

需要运行时确认：用 Godot 的调试器或渲染分析器观察可见对象、draw call、状态变化和帧时间；只看到“很多节点”不能自动判定 DrawCall 高。

**`Label.text` 没有 Cocos 式 `cacheMode` 能一键开关。** Godot 4 的 Label 类文档列出 `text`、`autowrap_mode`、`clip_text`、`visible_characters` 等，但未定义类似 Cocos 的缓存模式属性。[10] 因此规则应表述为“高频每帧全量改 text 有成本，尤其大文本、自动换行和裁剪”，而不是断言存在统一 `cacheMode`。正例是仅在文本值变化、且变化后新值不同于旧值时赋值；若需要逐字打印，优先减少 `visible_characters` 更新频率，或为大量日志文本分页/虚拟化。C# 同样是只在值变化时设置 `Label.Text`。该规则属于“高可疑性能提示”，应由 Profiler 中 Script/CanvasItem 耗时确认。

**每帧访问节点路径和做重分配是通用热点。** `_process`/`_physics_process` 内出现 `get_node(...)`、`$"..."`、`find_child(...)`、`get_tree().get_nodes_in_group(...)`、`PackedScene.instantiate()`、`Array.new()`、`Dictionary.new()`、字符串格式化后写入 UI，都是可命中特征。其成本取决于节点数、树深度和每帧调用次数，不能把所有命中都当阻塞缺陷。正例是在 `_ready`/`@onready` 缓存引用，在组成员变化时更新缓存，用对象池预先实例化并重用对象；确认方法是观察函数自耗时、分配次数和帧尖峰。

**物理体选型错误既是正确性也是性能问题。** `CharacterBody2D/3D` 由脚本驱动、不受物理力直接控制，适合玩家角色和自定义运动；`RigidBody2D/3D` 由物理引擎积分，适合受冲量、扭矩和碰撞自然影响的物体；`StaticBody2D/3D` 适合不变形且不自动移动的静态碰撞体；`AnimatableBody2D/3D` 适合按代码或动画移动、能够带动碰撞体的平台等对象。[11] 因此静态规则应命中“`RigidBody` 脚本每帧直接覆盖 `position/linear_velocity` 而不使用力/冲量”、“`CharacterBody` 在 `_process` 中做 `move_and_slide`”、“静态碰撞体却持续在每帧修改变换”。确认方法是在 Physics 分析器中观察接触数、碰撞形状数、固定步耗时，并检查抖动/穿透。

**`PhysicsDirectSpaceState` 查询昂贵与否取决于形状、结果数和被查询对象数。** 官方提供 `intersect_shape`、`intersect_point`、`intersect_ray`、`cast_motion` 等方法，并允许 `max_results` 限制返回数量以节省处理时间。[12] 在 `_process` 中每帧对大量单位做区域扫描，或用未限制结果的形状查询，是清晰热点；少量射线检测本身不一定有问题。规则应推荐缓存 `PhysicsDirectSpaceState`，复用查询参数，使用碰撞层和掩码，尽量在 `_physics_process` 中执行，并将每帧查询数量限制在可解释范围。

## 4. 3.x→4.x 迁移对照与静态规则

![3.x 到 4.x 高频破坏性迁移规则](/data/workspace/dr:godot-review:20260917/fig_migration.png)

*图 2：七类最容易在旧项目中残留破坏性语法的迁移规则。数据来源：Godot 官方 Signal、CharacterBody2D、C# Signals、C# API 差异文档及升级指南 [2][5][7][11][13]*

**信号 API 是最清晰的“版本气味”。** Godot 3 的 `connect("pressed", self, "_on_pressed")` 或 `connect("pressed", obj, "method", [], CONNECT_ONESHOT)` 使用信号名字符串、目标对象和回调字符串；Godot 4 推荐 `button.pressed.connect(_on_pressed)`，或使用 `Callable(self, "_on_pressed")`。[2] 因此正则 `(connect|disconnect)\s*\(\s*"[^"]+"(?:\s*,|\s*\))` 对 GDScript 是强迁移气味；`Object.connect("...")` 也不应一概判错，但出现旧式四个参数形式应判为高风险。C# 应检查 `GodotObject.Connect(SignalName.X, new Callable(...))` 是否仍用于可转为事件 `+=`/`EventName +=` 的场合；连接 GDScript 自定义信号时必须保存 delegate 以便 `-=`。[2][5]

**属性、协程与场景实例化 API 必须成套迁移。** `export`→`@export`、`onready var`→`@onready var`；`yield(get_tree(), "idle_frame")`→`await get_tree().process_frame`；`yield(signal, "completed")`→`await signal`；`PackedScene.instance()`→`instantiate()`。[13] GDScript 的正则气味包括 `^\s*export\s`、`^\s*onready\s`、`yield\s*\(`、`\.instance\s*\(`；C# 包括 `KinematicBody2D`/`KinematicBody3D`、`Position3D`、`Spatial`、`yield`、`GetNode(...).Connect("...")` 等。注意 C# API 使用 PascalCase，搜索时需用 `SignalName.X`、`OnPressed`、`QueueFree`、`CreateTween` 等大小写，而不是照搬 GDScript 的 snake_case。[7]

| 维度 | Godot 3.x | Godot 4.x | 审查判据 |
|---|---|---|---|
| 角色节点 | `KinematicBody2D/3D` | `CharacterBody2D/3D` | 出现旧类名即标迁移问题 [11] |
| 运动 API | `move_and_slide(velocity, up)` | `velocity`、`up_direction` 为属性，`move_and_slide()` | 出现带参调用应判错 [11] |
| 导出 | `export var` | `@export var` | 新项目仍写裸 `export` [13] |
| 延迟就绪 | `yield(get_tree(), "idle_frame")` | `await get_tree().process_frame` | 旧式字符串 yield [13] |
| 实例化 | `scene.instance()` | `scene.instantiate()` | `\.instance\(` [13] |
| C# 事件 | 常见旧连接形式 | 优先事件 `+=`、`-=` | GDScript 自定义信号必须保存 delegate [2][5] |

`move_and_slide()` 的无参化尤其容易制造“能编译但行为改变”的问题：Godot 4 中通过 `velocity`、`up_direction`、`floor_max_angle`、`floor_snap_length` 等属性配置。[11] 审查器应把 `move_and_slide\s*\(` 作为强气味；若参数是 `velocity, Vector2.UP` 之类，可直接判为破坏性迁移。反之，空调用本身不是错误。

## 5. 静态可检出性与人工判断边界

**AST 能可靠识别“错误结构”，但不能证明运行时生命周期一定错误。** 下表按源码特征把规则分成三档。正则适合快速扫描，但对 GDScript 的动态类型、函数别名、宏式生成代码和场景文件中的编辑器连接会误报；完整实现应使用 Godot 的 GDScript 解析器/语言服务器信息或 tree-sitter，对 C# 使用 Roslyn。

| 规则 | 可静态特征 | 检出等级 | 仍需人工/运行时确认 |
|---|---|---:|---|
| 字符串式信号连接 | `\.connect\(\s*"[^"]+"`、`disconnect\(\s*"[^"]+"` | 高 | 是否来自配置/动态连接 |
| 旧 export/onready | `^export `、`^onready `、不带 `@` | 高 | 是否脚本本就是 3.x |
| yield | `yield\s*\(` | 高 | 是否迁移遗留 |
| KinematicBody | `\bKinematicBody[23]D\b` | 高 | 是否仅出现在注释/字符串 |
| instance() | `\binstance\s*\(` | 高 | PackedScene 以外的同名方法 |
| move_and_slide 带参 | `move_and_slide\s*\([^)]` | 高 | 用户是否自定义同名方法 |
| remove_child 无释放 | `remove_child\(` 后无 `queue_free`/重新持有 | 中 | 对象池、状态切换、返回给调用者 |
| 跨场景连接未断开 | Autoload/静态字段 `.connect` 且文件内无断开 | 中 | 是否同树自动清理、是否重复连接 |
| Tween 未 kill | `create_tween\(` 无保存引用、无 `kill()` | 中 | 是否已绑定、作用域是否自然结束 |
| create_timer 未持有 | `create_timer(` 返回值未保存又非 `await` | 中 | 单帧使用后是否无后续控制需求 |
| Label 每帧赋值 | `_process/_physics_process` 中 `text =` | 中 | 是否每帧真的变化、文本规模 |
| get_node/find_child 每帧 | 帧回调内 `get_node\(`、`find_child\(` | 中 | 调用次数、树规模 |
| queue_free/free 时序 | 信号发射者/回调自身 `free()` | 中 | 释放后是否真有访问 |
| 闭包捕获 Node | lambda 捕获 Node 并连接长期信号 | 中 | 是否保存 delegate、是否循环引用 |
| Resource 缓存滞留 | Autoload/静态字段长期持有 Resource | 低—中 | 是否最终无引用、是否真正泄漏 |
| DrawCall 打断 | 不同 material、CanvasGroup/裁剪嵌套 | 中 | 实际渲染顺序、批次和帧耗时 |
| 物理查询热点 | 每帧 PhysicsDirectSpaceState 全量扫描 | 中 | 查询数量、结果数、固定步预算 |

建议的 CI 输出是 JSON，而不是把每条警告都当作阻断错误。每个问题至少包含：`file`、`line`、`rule_id`、`evidence`、`confidence`、`fix_suggestion`。例如 `GDOT-LEAK-001` 为“跨生命周期信号未清理”，`GDOT-MIG-004` 为“move_and_slide 带参”；`severity` 由“官方明确且静态可证”与“高嫌疑但需运行验证”两个字段共同决定。

人工确认的最小实验设计是：进入目标场景，记录 `Performance.OBJECT_COUNT` 与 `OBJECT_ORPHAN_NODE_COUNT` 基线；反复打开/关闭 UI、生成/销毁对象、切换场景；比较前后差。若只创建不销毁导致计数单调增长，说明存在所有权问题；若对象数不涨但内存涨，更可能是 Resource 缓存、纹理或 C# 托管对象未释放。Tween、Timer、信号和闭包还应单独做“对象销毁后继续触发”的测试：人为缩短循环并观察是否仍收到回调或是否访问失效对象。

## 6. 反直觉坑与规则化表述

**本能以为 `remove_child` 会释放节点，但实际它只解除父子关系；节点、脚本字段、信号连接和闭包引用仍可能活着。** [1] 规则：`remove_child` 后必须证明节点被 `queue_free`、加入对象池或重新 `add_child`，否则为可疑泄漏。

**本能以为信号连接只要任一方释放就会全部清理，但实际 C# 捕获变量的 lambda 和自定义信号等情形不会自动断开。** [5] 规则：长期对象连接短命对象的 lambda 时保存 delegate/handler 并在退出树时显式 `-=`/`Disconnect`。

**本能以为 Tween 一定随节点释放，但自由 `SceneTree.create_tween()` 并不会因为目标节点离树而自动结束。** [3] 规则：保存 Tween 引用，重复启动前 `kill()`；若要随节点销毁，用 `Node.create_tween()` 或显式 `bind_node()`。

**本能以为 `create_timer()` 返回的 timer 是 Timer 节点，但它没有 `start/stop`，且若不持有引用可能提前失去控制。** [6] 规则：区分 `Timer` 节点和 `SceneTreeTimer`；需要停止/复用就保存引用或使用 Timer 节点。

**本能以为 Resource 和 Node 一样需要 `queue_free()`，但 Resource 是 `RefCounted`，引用归零才释放。** [4] 规则：普通 Resource 不调用 Node 的释放 API；真正的重点是删除最后一个强引用，而非手动“释放资源”。

**本能以为 `preload` 与 `load` 会各自生成独立副本，但同路径资源会进入全局缓存。** [4] 规则：不重复加载不能自动等同于内存增长；泄漏判断依据是引用数和缓存是否仍有强引用。

**本能以为 `_ready` 中子节点一定可用，但 `_init` 阶段不可用。** [1] 规则：把子节点依赖从 `_init` 移到 `_ready`/`@onready`；`@onready` 的解析发生在进入场景树时。

**本能以为 `_exit_tree` 中节点已经销毁，但官方说明 `tree_exiting` 才是节点仍有效时的清理点。** [1] 规则：在 `_exit_tree`/`tree_exiting` 处理反初始化；不要在本回调之后再访问已释放外部状态。

**本能以为 `queue_free()` 立即销毁，但它只在当前帧结束时删除。** [1] 规则：调用后同一帧代码不能假设对象已经消失；不要在随后逻辑继续访问它。

**本能以为 `_process` 和 `_physics_process` 都能安全放移动，但两者速率与用途不同。** [1][11] 规则：角色碰撞运动进 `_physics_process`；视觉动画、输入与计时进 `_process`。

**本能以为 `Label` 有 Cocos 式缓存开关，但 Godot 4 Label API 没有提供等价 `cacheMode`。** [10] 规则：只能靠“值未变化则不赋值”、降低更新频率、避免超大文本和自动换行来优化。

**本能以为 CharacterBody 受力控制，但它不受物理力直接影响；相反 RigidBody 若被每帧覆盖位置，物理积分会失效。** [11] 规则：按控制方式选体，不按命名习惯选体。

## 7. 可交付的语言包设计

**规则应分为“禁止、高风险、提示”三级，并给出机器可执行的证据片段。** 建议规则 YAML/JSON 至少包含：`id`、`title`、`languages: [gdscript, csharp]`、`severity`、`evidence_regex/AST_selectors`、`message`、`good_example`、`bad_example`、`fix`、`confidence`、`references`。例如 `GDOT-LIFECYCLE-002` 可定义为“在 `_init` 访问子节点”，`evidence` 为函数名 `_init` 与 `get_node|find_child|\$` 同函数出现；`GDOT-LEAK-003` 定义为“`create_tween()` 结果未保存且未 `bind_node`”。

```yaml
- id: GDOT-LEAK-003
  title: 重复创建 Tween 前未 kill
  languages: [gdscript]
  severity: warning
  confidence: high
  evidence:
    - "create_tween\\s*\\("
  message: 未保存的 Tween 可能持续控制属性；重复触发时优先保存引用并在重启前 kill。
  good_example: |
    if tween and tween.is_running():
        tween.kill()
    tween = create_tween()
  bad_example: |
    create_tween().tween_property(self, "modulate", c, 0.2)
  references: [3]
```

对于 C#，AST 选择器可使用“方法调用 `CreateTween` 的返回值未赋给字段/局部变量且方法内无 `BindNode`”“`_PhysicsProcess` 中调用 `GetNode`”“`RemoveChild` 后无 `QueueFree`/字段赋值”。对 GDScript，除正则外还应识别 `signal_name.connect(Callable)` 与 `SignalName.X += Handler` 的配对；不强制要求所有 `connect` 都有 `disconnect`，否则会误伤同生命周期父子节点连接。

**优先级建议按“破坏性迁移—确定性生命周期错误—高频泄漏—性能提示”排序。** 第一梯队是 3.x API 残留、`queue_free/free` 在回调链中的误用、节点移除后无释放、字符串信号和 `move_and_slide` 带参；第二梯队是跨场景信号、Tween、Timer、每帧 `get_node`、每帧 `Label.text`；第三梯队是批处理打断、物理查询频率和 Resource 长期引用。这样可以避免大量低置信度“性能提示”掩盖真正会在场景切换时复现的内存与崩溃问题。

## 8. 结论与使用限制

**语言包的最小可用集合可以只覆盖约 15 条规则，但必须正确处理 Godot 的所有权边界。** 最值得优先实现的是：旧式信号连接、`remove_child` 后无释放、跨生命周期连接未清理、Tween 无 kill、Timer 与 SceneTreeTimer 混淆、每帧节点查找、每帧实例化和重分配、`free()` 与 `queue_free()` 误用、CharacterBody/RigidBody 误选、`move_and_slide` 参数迁移。它们既有明确代码特征，也能被简单测试验证。

**静态检查不能证明资源是否真正泄漏，只能证明所有权关系可疑。** 尤其信号自动断开、Tween 绑定、C# lambda 和 Resource 缓存都依赖运行对象关系；语言包应把证据、置信度和修复建议分开输出。本报告主要依据 Godot 4.0—4.7 官方 API 文档；不同 4.x 小版本在个别默认行为、调试 API 和废弃警告上可能变化，语言包发布前应在目标引擎版本上用最小复现项目验收。
